<span id="introduction"></span>
## Introduction

The Armv8-M includes robust security and memory protection features such as TrustZone for Armv8-M, the Memory Protection Unit (MPU), and Privileged Execute-never (PXN). These features efficiently isolate critical security firmware and private data, enforce privilege rules, separate processes, and apply access controls. 
The Armv8.1-M architecture introduced **Pointer Authentication** and **Branch Target Identification** extension known as **PACBTI**, which enhances these capabilities by introducing new techniques to detect Return-Oriented Programming (ROP) and Jump-Oriented Programming (JOP) vulnerabilities. In return-oriented programming, instructions before a function return are used to build [gadgets](https://developer.arm.com/documentation/102433/0200/Return-oriented-programming) in the executable code region. Similarly, in jump-oriented programming, instructions before function calls or switch-case statements (indirect jumping) are used to build gadgets in the executable code region.

[ ![Figure1. Gadget attack code](/media/2025/Armv8.1-M_PACBTI_Support_Gadget_Attack_Code.png)](/media/2025/Armv8.1-M_PACBTI_Support_Gadget_Attack_Code.png)

*Figure1. Gadget attack code [1]*

Please refer to the [Stack-smashing-and-execution-permissions document](https://developer.arm.com/documentation/102433/0200/Stack-smashing-and-execution-permissions) to find out more about stack smashing, return-oriented programming, and jump-oriented programming. [The blog](https://community.arm.com/arm-community-blogs/b/architectures-and-processors-blog/posts/armv8-1-m-pointer-authentication-and-branch-target-identification-extension) talks in depth about Armv8.1-M PACBTI.
PACBTI is designed to catch common exploitable software errors, but it is not the ultimate solution for all ROP and JOP attacks. It relies on a robust software model, where it can be a powerful tool when combined with good software development practices. A sensible compiler implementation for the PACBTI extension should ensure that all PAC and BTI functionality is correctly inserted into the compiled code.


<span id="pointer authentication"></span>
## Pointer Authentication

<span id="pointer authentication code creation"></span>
#### Pointer Authentication Code creation

One of the key uses of the PAC feature is to detect corruption of return addresses in function calls. Because the return address is often stored on the stack, there is a risk that stack corruption can change the return address, allowing an attack to be carried out. The process of creating a Pointer Authentication Code (PAC) can be referred to as signing the pointer. To create a PAC, the pointer, a modifier, and a secret key are used as inputs to a cryptographic mechanism, which produces a 32-bit fixed length code known as Pointer Authentication Code. The PAC instruction uses fixed registers, Link Register (LR) as the pointer, Stack Pointer (SP) as the modifier, and R12 for storing the generated PAC. This operation is illustrated in the following figure where:

- **PAC**: 32-bit authentication code.
- **Modifier (MOD)**: 32-bit value from an input register.
- **Pointer (PTR)**: Address to be protected.
- **Key**: 128-bit secret key.
- **Cryptographic Mechanism**: Example: [QARMA](https://eprint.iacr.org/2016/444.pdf).

[ ![Figure2. Creating PAC](/media/2025/Armv8.1-M_PACBTI_Support_Creating_PAC.png)](/media/2025/Armv8.1-M_PACBTI_Support_Creating_PAC.png)

*Figure2. Creating PAC [2]*

The modifier must be a value that is not changed where it must have the same value at the beginning and at the end of the function, that is why the stack pointer (SP) can be used as the modifier where its value can be changed during the function execution, but the value at the end of the function will be the same as the value at the very beginning.

<span id="pointer authentication code validation"></span>
#### Pointer Authentication Code validation

The compiler inserts the authentication instruction (**aut**) at the end of the function where it compares the PAC created at the very beginning of the function with the one created after the function execution (**PACreturn**), the two values must be the exact same indicating no corruption to any of the following:

* The pointer.
* The modifier.
* The secret key.
* The original PAC.

If the original PAC does not match **PACreturn** then an **INVSTATE** UsageFault exception is generated by the authentication instruction. Any speculatively executed instructions should be terminated ensuring that there are no observable side-effects due to the corrupted, pointer, modifier, key, or PAC.

[ ![Figure3. Validating PAC](/media/2025/Armv8.1-M_PACBTI_Support_Validating_PAC.png)](/media/2025/Armv8.1-M_PACBTI_Support_Validating_PAC.png)

*Figure3. Validating PAC [2]*

<span id="branch target identification"></span>
## Branch Target Identification

The mechanism used to create and identify valid branch landing pads is called Branch Target Identification (BTI). The processor can be configured in such a way that when BTI is enabled, all indirect branches must target landing pads. If the target address of the branch instruction does not have a landing pad, then the processor triggers an exception. This reduces the number of possible targets addresses and therefore reduces the number of possible gadgets that can be created using JOP.
These jump instructions are called **BTI setting** instructions, and when executed, they set a specific bit (**EPSR.B**) to one. A **BTI clearing**, or **landing pad**, instruction clears **EPSR.B** to zero. The BTI setting instruction must always be followed by a BTI clearing instruction, otherwise an **INVSTATE** UsageFault exception will be raised. The general Armv8.1-M BTI behavioral model is described in the following figure:

[ ![Figure4. BTI behavior](/media/2025/Armv8.1-M_PACBTI_Support_BTI_Behavior.png)](/media/2025/Armv8.1-M_PACBTI_Support_BTI_Behavior.png)

*Figure4. BTI behavior [2]*

When the exception is generated, **EPSR** is stacked as normal, so the state of **EPSR.B** is saved. Before entering the handler, **EPSR.B** is cleared to zero, since BTI may not be enabled in the handler. The handler will terminate the thread since any authorization failure is a clear indication of tampering.

<span id="implementation in FreeRTOS-Kernel"></span>
## Implementation in FreeRTOS-Kernel

<span id="configurability"></span>
#### Configurability

The PACBTI is an optional extension introduced in Armv8.1-M. Even though it is optional, Arm strongly recommends using the PACBTI security feature. If it's implemented in the hardware, then PACBTI must be implemented together. However, it is possible to enable/disable them individually using CONTROL register. Also, the PACBTI can be enabled/disabled individually using the compiler options. Therefore, we introduce kernel configuration options to support different possible PACBTI configurations.

<span id="for cmake projects"></span>
#### For CMake Projects

The appropriate toolchain options would be set automatically when the user choose one of the following configurations:

| **Configuration option** | **Values** | **Description** |
|--------------------------|-----------|---------------|
| **FREERTOS_ARM_V_8_1_M_PACBTI_CONFIG** | **ARM_V_8_1_M_PACBTI_CONFIG_STANDARD** | PACBTI Security Feature Standard Configuration (PAC enabled without leaf functions support, and BTI enabled). |
| | **ARM_V_8_1_M_PACBTI_CONFIG_PACRET_LEAF_BTI** | PACBTI Security Feature Standard + Leaf Configuration (PAC with leaf functions support, and BTI enabled). |
| | **ARM_V_8_1_M_PACBTI_CONFIG_PACRET** | PACBTI Security Feature with only PAC enabled. |
| | **ARM_V_8_1_M_PACBTI_CONFIG_PACRET_LEAF** | PACBTI Security Feature with PAC and PAC for leaf functions support enabled. |
| | **ARM_V_8_1_M_PACBTI_CONFIG_BTI** | PACBTI Security Feature with only BTI enabled. |
| | **ARM_V_8_1_M_PACBTI_CONFIG_NONE** | PACBTI Security Feature disabled. |

**Note**
**For CMake projects**, the appropriate toolchain options should be set by the user for all the compiled code other than the kernel code (i.e., application, libraries, etc..) if they chose to enable PAC and/or BTI.

<span id="for non-cmake projects"></span>
#### For non-CMake Projects

User can choose whether to enable/disable PAC and/or BTI using the following C configuration macros:

| **C Configuration macro** | **Values** | **Description** |
|--------------------------|-----------|---------------|
| **configENABLE_PAC** | **1** | PAC Security Feature enabled. |
| | **0** | PAC Security Feature disabled. |
| **configENABLE_BTI** | **1** | BTI Security Feature enabled. |
| | **0** | BTI Security Feature disabled. |

**Note**
**For non-CMake projects**, the appropriate toolchain options should be set by the user for all the compiled code (i.e., application, kernel code, libraries, etc..) if they chose to enable PAC and/or BTI.
**Example for setting the appropriate ARMClang toolchain options in case of enabling both PAC and BTI**
```sh
armclang —target=arm-arm-none-eabi -march=armv8.1-m.main+pacbti -mbranch-protection=bti+pac-ret source.c -c -o source.o
armlink source.o —library_security=pacbti-m -o output.elf
```

The **prvConfigurePACBTI** function is invoked during the scheduler start process (i.e., before the first task is started) to configure the special purpose control register PAC and BTI bits as per the user configuration.

<span id="dedicated pac key for each task"></span>
#### Dedicated PAC key for each task

To harden the security, each task is assigned a dedicated PAC key during the task initialization process, so that attackers need to guess all the tasks' PAC keys right to exploit the system using Return Oriented Programming.
The kernel now supports the following:

* A PAC key set with a random number generated and is saved onto the task's context when a task is created.
* As part of scheduling, the task's PAC key is stored/restored to/from the task's context when a task is unscheduled/scheduled from/to run.

**Random number generation**

The kernel provides the user the ability to implement their own random number generator function by implementing the **vApplicationGenerateTaskRandomPacKey** 
API which is required by the kernel in the ARMv8.1-M port code when PAC is enabled. This function is expected to accept a pointer to a 4-word (128-bits) array to be filled with a 128-bit random number representing the task’s PAC key.

<span id="FreeRTOS examples demonstrating PACBTI"></span>
## FreeRTOS examples demonstrating PACBTI

Arm has introduced the following examples hosted on [FreeRTOS-Partner-Supported-Demos repository](https://github.com/FreeRTOS/FreeRTOS-Partner-Supported-Demos) to demonstrate the PACBTI security feature: 
* The MPU example [**CORTEX_M85_MPU_PXN_PACBTI_FVP_ARMCLANG_IAR**](https://github.com/FreeRTOS/FreeRTOS-Partner-Supported-Demos/tree/main/CORTEX_M85_MPU_PXN_PACBTI_FVP_ARMCLANG_IAR)
* The non-MPU example [**CORTEX_M85_PACBTI_FVP_ARMCLANG_IAR**](https://github.com/FreeRTOS/FreeRTOS-Partner-Supported-Demos/tree/main/CORTEX_M85_PACBTI_FVP_ARMCLANG_IAR)
* The task dedicated PAC key example [**CORTEX_M85_TASK_DEDICATED_PAC_KEY_FVP_ARMCLANG**](https://github.com/FreeRTOS/FreeRTOS-Partner-Supported-Demos/tree/main/CORTEX_M85_TASK_DEDICATED_PAC_KEY_FVP_ARMCLANG) 

These examples demonstrate how the new Pointer Authentication and Branch Target Identification (PACBTI) security feature introduced in Armv8.1-M architecture extension can be used on Cortex-M85 processor. To harden the security, the MPU and the non-MPU examples encompasses [TrustedFirmware-M](https://www.trustedfirmware.org/projects/tf-m/) running on the secure side of the Armv8.1-M processor, and the FreeRTOS-Kernel along with the application's tasks running on the non-secure side of the Armv8.1-M processor. The three examples are based on Corstone-315 Ecosystem Fixed Virtual Platform (Arm Cortex-M85 CPU and Ethos-U65 NPU).
The MPU and the non-MPU examples consist of two tests (i.e. Pointer Authentication Test and Branch Target Identification Test). In the Pointer Authentication Test, the FreeRTOS task would call one of the application's functions which would tamper the stacked Link Register (LR) value before validating the Pointer Authentication Code at the end of the called function, this will lead to failure of aut (authentication instruction) resulting in UsageFault exception being triggered.
During the Branch Target Identification Test, the FreeRTOS task will attempt to jump to the middle of one of the application's functions where this will result in UsageFault exception being triggered as the address jumped to is not a BTI clearing instruction. The UsageFault exception handler is designed in a way to recover gracefully by checking if the exception was triggered intentionally.
Whereas the task dedicated PAC key example consists of two main tasks. These tasks' job is to make sure that the task's randomly generated PAC keys are stored/restored robustly without being altered.
These tasks perform the following sequence:
1. Fetch the randomly generated dedicated PAC key for each task once they start running.
2. Move the task to blocked state by calling vTaskDelay() function.
3. As part of the context switching handler, the task's PAC key is restored after the task is unblocked, where the value of the PAC key before and after the blockage should be the same to prove the soundness of the task's dedicated PAC key storing/restoring procedure.
4. If the task's PAC key before and after the blockage are not the same, a configASSERT() statement would be triggered.
