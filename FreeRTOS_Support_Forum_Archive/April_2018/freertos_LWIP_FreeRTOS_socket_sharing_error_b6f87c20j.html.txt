I&#8217;m not sure which lwIP forum is most helpful, but did you try <a href="http://lwip.100.n7.nabble.com/lwip-users-f3.html">this one</a> ?
Within FreeRTOS+TCP, it is explicitly allowed to share a socket between two tasks: one may write, and the other may read. No semaphore ( mutex ) is needed to do so.
But when writing ( or reading ) to the same socket from two tasks, the socket must be protected with a mutex.
I think that under Linux or Windows, you will meet the same limitations.
But if I were you, I would invest time and energy in finding a way to keep a socket within a single task. If the return data comes from another task, let the socket-owning task gather that data and send it.
And more: if you use the <code>select()</code> function, a single task can handle multiple sockets.
B.t.w. you can download FreeRTOS+TCP from here:
<pre><code>https://github.com/aws/amazon-freertos/tree/master/lib/FreeRTOS-Plus-TCP
</code></pre>
And if you&#8217;re looking for demo application using FreeRTOS+TCP:
<pre><code>https://freertos.org/FreeRTOS-Labs/RTOS_labs_download.html?0
</code></pre>
Note that that ZIP file contains an older release of FreeRTOS+TCP.

The person who replied to you ( Simon Goldschmidt ) knows a lot more about lwIP than I do.
He mentioned an important thing: &#8220;but only recent [..] versions support aborting waiting read threads on close&#8221;.
When sharing a socket between threads, the closure of the socket must be well synchronised. Only one task may actually close the socket, while the other keeps his hands off. Any ongoing API must be aborted before the socket can be closed.
As for FreeRTOS+TCP : blocking API&#8217;s like <code>FreeRTOS_send()</code>, <code>FreeRTOS_recv()</code>, and <code>FreeRTOS_select()</code> can be interrupted ( signalled ) by calling:
~~~
<h1>if( ipconfigSUPPORT_SIGNALS != 0 )</h1>
<pre><code>/* Send a signal to the task which reads from this socket. */
BaseType_t FreeRTOS_SignalSocket( Socket_t xSocket );
</code></pre>
<h1>endif</h1>
~~~
There is also an ISR version : <code>FreeRTOS_SignalSocketFromISR()</code>.
After the signal, any active API&#8217;s will return with an error <code>-EINTR</code>.
But, as I said earlier, I prefer not to share sockets among tasks. I know that you can not call both <code>send()</code> and <code>recv()</code> in a blocking way simultaneously. But there are many techniques to get around this, most importantly the use of <code>select()</code>.
Here is a rough sketch, symbolically:
~~~
    for( ;; )
    {
        /* Call select and sleep for N ms. <em>/
        select();
        if( has_write_data() &amp;&amp; scoket_has_tx_space() )
        {
            write( s, buf, length, DONTWAIT );
        }
        if( socket_has_rx_data() )
        {
            read( s, buf, max_length, DONTWAIT );
        }
        if( connection_was_closed() )
        {
            /</em> Remove it from the select group. */
            FD_CLR( s, &amp;event);
            close( s );
        }
    }
~~~

</div></div><div class="thread-post"><h3 class="thread-post-title">LWIP + FreeRTOS socket sharing error</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 27, 2018</div><div class="thread-post-content">If you google the keywords &#8220;lwip select example&#8221;, you will find good examples. I&#8217;m not sure if it is all compatible with lwIP v1.40.
There is a lot of documentation about <code>select()</code>. It exists in every OS. It is a system call and it means: 
~~~
    &#8220;Here is a set of handles (=sockets) and events (Read, Write, Exception)&#8221;
    &#8220;Please return when at least on event happens, or when a time-out occurs.&#8221;
~~~
A Read event means that you may read.
Be careful with the Write event: switch it off when not needed, otherwise <code>select()</code> keeps on returning immediately saying: &#8220;You may write to socket x&#8221;.
The Exception event means that an error occurred.
A TCP server on a big (multi-core) host will typically <code>fork()</code> (create a new task) for every new client. In an embedded project, this is risky: you might run about of memory / resources.
I did write an FTP-server that uses <code>select()</code>: from a single task, hundreds of connections can be handled.
I tend to embed a socket (handle) in a structure that contains the complete information about that client.
After disconnection, this structure will be freed.
