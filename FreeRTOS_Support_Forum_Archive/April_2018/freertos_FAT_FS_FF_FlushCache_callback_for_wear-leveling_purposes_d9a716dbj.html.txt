  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FAT FS FF_FlushCache callback for wear-leveling purposes</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sameerazer">sameerazer</a> on April 24, 2018</div><div class="thread-post-content">Hello there,
I&#8217;m using FreeRTOS+FAT provided <a href="https://www.freertos.org/FreeRTOS-Labs/downloads/160919_FreeRTOS_Labs.zip?dl=0">here</a>.
In addition I&#8217;m using this <a href="https://github.com/dlbeer/dhara">library</a> for wear levelling. 
This wear-leveling layer includes a function to flush changes to the physical media: 
~~~
dhara<em>map</em>sync()
~~~
Is there a way to provide
~~~
FF<em>Error</em>t FF<em>FlushCache( FF</em>IOManager_t * pxIOManager )
~~~
with a callback to my wear-leveling function?
Currently, I have a user-level function (adapted from FreeRTOS&#8217;s common demo) that flushes both the FAT FS and the wear leveling caches. 
~~~
void FF<em>SPIDiskFlush( FF</em>Disk<em>t *pxDisk )
{
    if( ( pxDisk != NULL ) &amp;&amp; ( pxDisk->xStatus.bIsInitialised != 0 ) &amp;&amp; ( pxDisk->pxIOManager != NULL ) )
    {
        FF</em>FlushCache( pxDisk->pxIOManager );
        dhara<em>error</em>t err = 0;
        int ret = dhara<em>map</em>sync(map, &amp;err);
        if(ret != 0) {
            FF<em>PRINTF(&#8220;map</em>sync failed with %d/%sn&#8221;, ret, dhara_strerror(err));
        }
    }
}
~~~
This works fine. However, I want to ensure that
~~~
dhara<em>map</em>sync()
~~~ 
is called whenever
~~~
FF_FlushCache()
~~~ 
gets called by the non-public functions of the FAT FS. 
</div></div><div class="thread-post"><h3 class="thread-post-title">FAT FS FF_FlushCache callback for wear-leveling purposes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 24, 2018</div><div class="thread-post-content">Hi Sameer, you&#8217;re not the only person requesting this feature.
We&#8217;ve added a function field to the disk property called <code>fnFlushApplicationHook</code>. If defined, the hook will be called every time <code>FF_FlushCache()</code> is being called.
Now, how do I pass the latest version to you? FreeRTOS+FAT is still in the Labs, which means that it doesn&#8217;t appear in the official AWS releases.
The 160919 release is running far behind, and therefore the patch won&#8217;t apply correctly.
Please find attached the latest version of FreeRTOS+FAT, in which you will find the <code>fnFlushApplicationHook</code> that you&#8217;re looking for.
Regards, Hein
</div></div><div class="thread-post"><h3 class="thread-post-title">FAT FS FF_FlushCache callback for wear-leveling purposes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 24, 2018</div><div class="thread-post-content">ps. I even wrote some comments in <code>ff_ioman.h</code> about this feature:
~~~
/*
 * Some low-level drivers also need to flush data to a device.
 * Use an Application hook that will be called every time when
 * FF<em>FlushCache() is called. The semaphore will still be taken
 * to avoid unwanted reentrancy.
 * For example:
 *
 *     void FTL</em>FlushData( struct xFFDisk *pxDisk )
 *     {
 *         // You may or may not inspect &#8216;pxDisk&#8217;
 *         FTL_FlushTableCache();
 *     }
 *
 * Make sure you bind the function to the disc object, right after creation:
 *
 *    pxDisk->fnFlushApplicationHook = FTL_FlushData;
 */
~~~

</div></div><div class="thread-post"><h3 class="thread-post-title">FAT FS FF_FlushCache callback for wear-leveling purposes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 25, 2018</div><div class="thread-post-content"><blockquote>
  is there a repository I should be aware of when it comes to FreeRTOS Labs? 
</blockquote>
Unfortunately there isn&#8217;t. FreeRTOS+FAT has become a bit of an orphan. All time and energy goes to the products in the <a href="https://github.com/aws/amazon-freertos">AWS/FreeRTOS release</a>
But I am still actively maintaining FreeRTOS+FAT: implementing requests and fixes.
Please comment your findings with the informal FreeRTOS+FAT &#8220;release&#8221; here above.
Here is a complete list of all changes since the 160919 Labs release:
● <code>ff_dir.c : FF_MkDir()</code>
refuse to create a directory with an empty name
● <code>ff_fat.c : FF_GetFreeSize()</code>
in case of an error, return 0
● <code>ff_file.c : FF_FileSize()</code>
This function returns the size of a file, or a negative number in case of an error.
Hence, the maximum size returned was returned is 2 GB.
We&#8217;ve added a new function:
<code>FF_Error_t FF_GetFileSize( FF_FILE *pxFile, uint32_t *pulSize );</code>
which separates the length from the error code.
● <code>ff_file.c : FF_ExtendFile()</code>
Sometimes while building up a file, it may be more efficient not to flush the changes immediately. When defining <code>ffconfigFILE_EXTEND_FLUSHES_BUFFERS</code> as <code>0</code>, there is no immediate flushing.
● <code>ff_file.c : FF_Seek()</code>
Seeking didn&#8217;t work for sizes larger than 2 GB. Although the parameter <code>int32_t lOffset</code> is signed, it will now be casted to 32-bits unsigned:
<code>ulPosition = ( uint32_t )lOffset;</code>
All options (<code>SET</code>, <code>CUR</code>, and <code>END</code> ) re-tested.
● <code>ff_file.c : FF_Close()</code>
<code>FF_FlushCache()</code> is now called at the end of the function in order to also write the last changes.
● <code>ff_format.c : FF_Format()</code>
A variable <code>lRemaining</code> should have been declared unsigned: <code>uint32_t</code>.
Also: a small optimisation for large SD-cards:
&#8220;Putting the FAT-table into the second 4MB erase block gives a higher performance and a longer life-time&#8221;
● <code>ff_format.c : FF_Partition()</code>
<code>ulHiddenSectors</code> must be at least <code>1</code>
( see <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/d2b6524a/?limit=250#e1ea">this post</a> )
● <code>ff_ioman.c : FF_CreateIOManger()</code>
<code>FF_CreateEvents</code> shall only be called in case an <code>pxIOManager</code> was successfully created.
● <code>ff_ioman.c : FF_DeleteIOManager()</code>
Added a call to <code>FF_DeleteEvents()</code>, which will delete the event group belonging to the I/O manager.
● <code>ff_ioman.c : FF_FlushCache()</code>
Added a user application hook per disk: <code>fnFlushApplicationHook()</code>. This is useful for e.g. NAND-drivers.
● <code>ff_ioman.c : FF_Mount()</code>
Make sure that <code>pcVolumeLabel</code> is null-terminated.
● <code>ff_ioman.c : FF_IncreaseFreeClusters()</code>
A lock is needed before <code>ulLastFreeCluster</code> can be changed. But before taking this lock, check if has already been taken to avoid a dead lock.
● <code>ff_locking.c : FF_DeleteEvents</code>
This is a new function which deletes ( frees up ) the event group belonging to an I/O manager.
● <code>ff_stdio.c : ff_filelength()</code>
This function will now call <code>FF_GetFileSize()</code> in order to get the <code>unsigned</code> length of a file, increasing the maximum reported size from 2 to 4 GB.
● <code>ff_sys.c : *</code>
This module combines several I/O managers ( = disks ) into a single file system that starts with a root <code>"/"</code>.
All code in<code>ff_sys.c</code> has been re-written ( re-styled ) and re-tested.
