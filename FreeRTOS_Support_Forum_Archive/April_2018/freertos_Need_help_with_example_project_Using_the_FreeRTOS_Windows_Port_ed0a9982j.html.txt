<h3 class="thread-post-title">Need help with example project &#8220;Using the FreeRTOS Windows Port&#8221;</h3>
<div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 8, 2018</div>
<div class="thread-post-content">Hi Jiaxin Long, <code>vApplicationIPNetworkEventHook()</code> is being called from the IP-task, and it is not allowed to call <code>FreeRTOS_bind()</code> from within the IP-task.<br />
The best solution is to keep <code>vApplicationIPNetworkEventHook()</code> very short, just set a variable:
<p>~~~</p>
<p>BaseType_t xMustCreateSockets = pdFALSE;<br />
extern void vCreateSockets();</p>
<p>void vApplicationIPNetworkEventHook()<br />
{<br />
/* If the network has just come up&#8230;<em>/<br />
if( eNetworkEvent == eNetworkUp )<br />
{<br />
/</em> Remember that sockets must be created. */<br />
xMustCreateSockets = pdTRUE;<br />
}<br />
}</p>
<p>~~~</p>
<p>And check this variable from within on of your tasks:</p>
<p>~~~</p>
<p>void vMyTask( void *pvArg )<br />
{<br />
for( ;; )<br />
{<br />
if( xMustCreateSockets != pdFALSE )<br />
{<br />
xMustCreateSockets = pdFALSE;<br />
vCreateSockets();<br />
}<br />
}<br />
}</p>
<p>~~~</p>
<p>Another possibility is to created your tasks from within the hook, as is being done in the FreeRTOS+TCP example projects.</p>
<p>What we should have done is write in <a href="https://www.freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_UDP/API/vApplicationIPNetworkEventHook.shtml">the documentation</a> that blocking +TCP API&#8217;s may not be called.</p>
<p>Also we&#8217;d better add a <code>configASSERT()</code> in <code>FreeRTOS_bind()</code>:</p>
<p>~~~<br />
BaseType<em>t FreeRTOS</em>bind( Socket<em>t xSocket, struct freertos</em>sockaddr * pxAddress, socklen<em>t xAddressLength )<br />
{<br />
IPStackEvent</em>t xBindEvent;<br />
FreeRTOS<em>Socket</em>t *pxSocket = ( FreeRTOS_Socket_t * ) xSocket;<br />
BaseType_t xReturn = 0;</p>
<pre><code> ( void ) xAddressLength;
</code></pre>
<ul>
	<li>configASSERT( xIsCallingFromIPTask() == pdFALSE );<br />
~~~</li>
</ul>
<p>So it will assert in case <code>FreeRTOS_bind()</code> is called from <code>vApplicationIPNetworkEventHook()</code> or other application hooks.</p>

FreeRTOS</em>indet<em>addr</em>quick() are available. If ipconfigINCLUDE<em>FULL</em>INET<em>ADDR is<br />
not set to 1 then only FreeRTOS</em>indet<em>addr</em>quick() is available. */</p>
<h1>define ipconfigINCLUDE<em>FULL</em>INET_ADDR 1</h1>
<p>/* ipconfigNUM<em>NETWORK</em>BUFFER_DESCRIPTORS defines the total number of network buffer that<br />
are available to the IP stack. The total number of network buffers is limited<br />
to ensure the total amount of RAM that can be consumed by the IP stack is capped<br />
to a pre-determinable value. */</p>
<h1>define ipconfigNUM<em>NETWORK</em>BUFFER_DESCRIPTORS 60</h1>
<p>/* A FreeRTOS queue is used to send events from application tasks to the IP<br />
stack. ipconfigEVENT<em>QUEUE</em>LENGTH sets the maximum number of events that can<br />
be queued for processing at any one time. The event queue must be a minimum of<br />
5 greater than the total number of network buffers. */</p>
<h1>define ipconfigEVENT<em>QUEUE</em>LENGTH ( ipconfigNUM<em>NETWORK</em>BUFFER_DESCRIPTORS + 5 )</h1>
<p>/* The address of a socket is the combination of its IP address and its port<br />
number. FreeRTOS<em>bind() is used to manually allocate a port number to a socket<br />
(to &#8216;bind&#8217; the socket to a port), but manual binding is not normally necessary<br />
for client sockets (those sockets that initiate outgoing connections rather than<br />
wait for incoming connections on a known port number). If<br />
ipconfigALLOW</em>SOCKET<em>SEND</em>WITHOUT<em>BIND is set to 1 then calling<br />
FreeRTOS</em>sendto() on a socket that has not yet been bound will result in the IP<br />
stack automatically binding the socket to a port number from the range<br />
socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER to 0xffff. If<br />
ipconfigALLOW<em>SOCKET</em>SEND<em>WITHOUT</em>BIND is set to 0 then calling FreeRTOS_sendto()<br />
on a socket that has not yet been bound will result in the send operation being<br />
aborted. */</p>
<h1>define ipconfigALLOW<em>SOCKET</em>SEND<em>WITHOUT</em>BIND 1</h1>
<p>/* Defines the Time To Live (TTL) values used in outgoing UDP packets. */</p>
<h1>define ipconfigUDP<em>TIME</em>TO_LIVE 128</h1>
<h1>define ipconfigTCP<em>TIME</em>TO_LIVE 128 /* also defined in FreeRTOSIPConfigDefaults.h */</h1>
<p>/* USE_TCP: Use TCP and all its features */</p>
<h1>define ipconfigUSE_TCP ( 1 )</h1>
<p>/* USE_WIN: Let TCP use windowing mechanism. */</p>
<h1>define ipconfigUSE<em>TCP</em>WIN ( 1 )</h1>
<p>/* The MTU is the maximum number of bytes the payload of a network frame can<br />
contain. For normal Ethernet V2 frames the maximum MTU is 1500. Setting a<br />
lower value can save RAM, depending on the buffer management scheme used. If<br />
ipconfigCAN<em>FRAGMENT</em>OUTGOING<em>PACKETS is 1 then (ipconfigNETWORK</em>MTU &#8211; 28) must<br />
be divisible by 8. */</p>
<h1>define ipconfigNETWORK_MTU 1200</h1>
<p>/* Set ipconfigUSE<em>DNS to 1 to include a basic DNS client/resolver. DNS is used<br />
through the FreeRTOS</em>gethostbyname() API function. */</p>
<h1>define ipconfigUSE_DNS 1</h1>
<p>/* If ipconfigREPLY<em>TO</em>INCOMING_PINGS is set to 1 then the IP stack will<br />
generate replies to incoming ICMP echo (ping) requests. */</p>
<h1>define ipconfigREPLY<em>TO</em>INCOMING_PINGS 1</h1>
<p>/* If ipconfigSUPPORT<em>OUTGOING</em>PINGS is set to 1 then the<br />
FreeRTOS_SendPingRequest() API function is available. */</p>
<h1>define ipconfigSUPPORT<em>OUTGOING</em>PINGS 0</h1>
<p>/* If ipconfigSUPPORT<em>SELECT</em>FUNCTION is set to 1 then the FreeRTOS_select()<br />
(and associated) API function is available. */</p>
<h1>define ipconfigSUPPORT<em>SELECT</em>FUNCTION 1</h1>
<p>/* If ipconfigFILTER<em>OUT</em>NON<em>ETHERNET</em>II_FRAMES is set to 1 then Ethernet frames<br />
that are not in Ethernet II format will be dropped. This option is included for<br />
potential future IP stack developments. */</p>
<h1>define ipconfigFILTER<em>OUT</em>NON<em>ETHERNET</em>II_FRAMES 1</h1>
<p>/* If ipconfigETHERNET<em>DRIVER</em>FILTERS<em>FRAME</em>TYPES is set to 1 then it is the<br />
responsibility of the Ethernet interface to filter out packets that are of no<br />
interest. If the Ethernet interface does not implement this functionality, then<br />
set ipconfigETHERNET<em>DRIVER</em>FILTERS<em>FRAME</em>TYPES to 0 to have the IP stack<br />
perform the filtering instead (it is much less efficient for the stack to do it<br />
because the packet will already have been passed into the stack). If the<br />
Ethernet driver does all the necessary filtering in hardware then software<br />
filtering can be removed by using a value other than 1 or 0. */</p>
<h1>define ipconfigETHERNET<em>DRIVER</em>FILTERS<em>FRAME</em>TYPES 1</h1>
<p>/* The windows simulator cannot really simulate MAC interrupts, and needs to<br />
block occasionally to allow other tasks to run. */</p>
<h1>define configWINDOWS<em>MAC</em>INTERRUPT<em>SIMULATOR</em>DELAY ( 20 / portTICK<em>PERIOD</em>MS )</h1>
<p>/* Advanced only: in order to access 32-bit fields in the IP packets with<br />
32-bit memory instructions, all packets will be stored 32-bit-aligned, plus 16-bits.<br />
This has to do with the contents of the IP-packets: all 32-bit fields are<br />
32-bit-aligned, plus 16-bit(!) */</p>
<h1>define ipconfigPACKET<em>FILLER</em>SIZE 2</h1>
<p>/* Define the size of the pool of TCP window descriptors. On the average, each<br />
TCP socket will use up to 2 x 6 descriptors, meaning that it can have 2 x 6<br />
outstanding packets (for Rx and Tx). When using up to 10 TP sockets<br />
simultaneously, one could define TCP<em>WIN</em>SEG_COUNT as 120. */</p>
<h1>define ipconfigTCP<em>WIN</em>SEG_COUNT 240</h1>
<p>/* Each TCP socket has a circular buffers for Rx and Tx, which have a fixed<br />
maximum size. Define the size of Rx buffer for TCP sockets. */</p>
<h1>define ipconfigTCP<em>RX</em>BUFFER_LENGTH ( 1000 )</h1>
<p>/* Define the size of Tx buffer for TCP sockets. */</p>
<h1>define ipconfigTCP<em>TX</em>BUFFER_LENGTH ( 1000 )</h1>
<p>/* When using call-back handlers, the driver may check if the handler points to<br />
real program memory (RAM or flash) or just has a random non-zero value. */</p>
<h1>define ipconfigIS<em>VALID</em>PROG_ADDRESS(x) ( (x) != NULL )</h1>
<p>/* Include support for TCP hang protection. All sockets in a connecting or<br />
disconnecting stage will timeout after a period of non-activity. */</p>
<h1>define ipconfigTCP<em>HANG</em>PROTECTION ( 1 )</h1>
<h1>define ipconfigTCP<em>HANG</em>PROTECTION_TIME ( 30 )</h1>
<p>/* Include support for TCP keep-alive messages. */</p>
<h1>define ipconfigTCP<em>KEEP</em>ALIVE ( 1 )</h1>
<h1>define ipconfigTCP<em>KEEP</em>ALIVE_INTERVAL ( 20 ) /* in seconds */</h1>
<h1>define portINLINE __inline</h1>
<h1>endif /* FREERTOS<em>IP</em>CONFIG_H */</h1>
<p>~~~</p>

<div class="thread-post-content">
<p>Your application will use IP-address &#8220;172.25.218.200&#8221;. What is the IP-address of the PC that you use for testing?</p>
<p>I think it is the best to give the application its own unique IP-address. If it is the same as the PC, there will be conflicts.</p>
<p>There is a problem with &#8220;ping RTOSDemo&#8221; : this will either use LLMNR or NBNS: those are protocols based on UDB broadcasting and multi-casting respectively. I think that the request will end-up in the PC&#8217;s IP-stack and it may not reach the application.</p>
<p>So &#8220;ping 172.25.218.200&#8221; should work in your case.</p>
<p>And if it does not: try to add &#8220;172.25.218.200&#8221; to your LAN network card so it gets 2 IP-addresses:</p>
<p>~~~<br />
172.25.218.xxx // Your usual PC&#8217;s IP address<br />
255.255.0.0 // Net-mask</p>
<pre><code>172.25.218.200  // The IP-address of the application
255.255.0.0     // Net-mask
</code></pre>
<p>~~~</p>
<p>It is also possible to use an entirely different IP-address for the application, like e.g. 192.168.1.xxx</p>
<p>Now I&#8217;m not sure what happens to the MAC address of the secondary IP-address. Maybe the PC will assign the existing MAC-address from the hardware.</p>
<p>Do you have a second PC connected to the same LAN? Can you try ping from that PC?</p>
<p>If this all doesn&#8217;t work, I would start debugging: see if any packets arrive in the driver here:</p>
<p>~~~<br />
/* WinPCAP function. <em>/<br />
void pcap_callback( u_char *user, const struct pcap_pkthdr *pkt_header, const u_char *pkt_data )<br />
{<br />
&#8230;<br />
uxStreamBufferAdd( xRecvBuffer, 0, ( const uint8_t</em> ) pkt<em>header, sizeof( *pkt</em>header ) );<br />
uxStreamBufferAdd( xRecvBuffer, 0, ( const uint8<em>t* ) pkt</em>data, ( size<em>t ) pkt</em>header-&gt;caplen );<br />
}<br />
~~~</p>
<p>See if the packets are treated by the IP-task here:</p>
<p>~~~<br />
static void prvIPTask( void <em>pvParameters )<br />
{<br />
&#8230;<br />
case eNetworkRxEvent:<br />
/</em> The network hardware driver has received a new packet. A<br />
pointer to the received buffer is located in the pvData member<br />
of the received event structure. */<br />
prvHandleEthernetPacket( ( NetworkBufferDescriptor_t * ) ( xReceivedEvent.pvData ) );<br />
break;<br />
~~~</p>
<p>And finally, see if any packets gets sent here:</p>
<p>~~~<br />
DWORD WINAPI prvWinPcapSendThread( void <em>pvParam )<br />
{<br />
&#8230;<br />
uxStreamBufferGet( xSendBuffer, 0, ( uint8_t * ) &amp;xLength, sizeof( xLength ), pdFALSE );<br />
uxStreamBufferGet( xSendBuffer, 0, ( uint8_t</em> ) ucBuffer, xLength, pdFALSE );<br />
}<br />
~~~</p>
<p>And if the ICMP (=echo) packet doesn&#8217;t get answered, you may discover the reason why.</p>
