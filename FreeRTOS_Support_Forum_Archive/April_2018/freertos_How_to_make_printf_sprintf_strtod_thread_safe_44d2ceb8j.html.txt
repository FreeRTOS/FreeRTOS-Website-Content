  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcrocker">dcrocker</a> on April 3, 2018</div><div class="thread-post-content">Since converting my project to run as 3 FreeRTOS tasks I have been getting a few hard faults each hour. The fault address is within the <em>Balloc function</em> in libc.a from the ARM M4 gcc library. I understand that the most likely cause is that even though my own code does not use dynamic memory allocation after the initialisation phase, library functions printf, sprintf, strtod etc. (all of which two of my application tasks call regularly) call malloc/free, and the standard library memory management functions are not thread safe by default. What is the recommended way of making the memory allocation performed by these library functions thread safe? Is there a library version of libc for ARM M4 that is already compatible with FreeRTOS?
I read that newlib&#8217;s malloc and free call __malloc<em>lock and __malloc</em>unlock functions to allow them to be made thread safe. So I implememted those functions using a recursive mutex, and verified that they are present in the linker map instead of the original versions. However, although the problem may be less frequent after doing that, I still had a crash after about 90 minutes &#8211; in _Balloc again.
Thanks &#8211; David
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 3, 2018</div><div class="thread-post-content">Is it an option for you to not use the malloc() and free() functions at 
all?  I think GCC has options to direct these calls elsewhere, but if 
not you can implement them yourself to just call pvPortMalloc() and 
vPortFree(), as per:
void *malloc( size_t xSize )
{
     return pvPortMalloc( xSize );
}
and likewise for free().
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 4, 2018</div><div class="thread-post-content">In addition to Richard&#8217;s remark about replacing <code>malloc()</code> and <code>free()</code>, I have a question: what version of <code>heap_x.c</code> are you using? <a href="https://www.freertos.org/a00111.html">Here you&#8217;ll find</a> a good explanation about the options that are available.
<blockquote>
  How to make printf/sprintf/strtod thread safe
</blockquote>
Are you sure that mentioned functions allocate memory? I thought that they are thread-safe because they store all temporary data on stack ( but I&#8217;m not a GCC-expert ).
As the stack usage of <code>printf()</code> functions can be quite high, an alternative implementation is being used in some FreeRTOS demo applications, which you can download <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/8fbac97d/45ce/attachment/printf-stdarg.c">from here</a>
Those functions are all thread- and ISR-safe ( although it is not recommended to use these functions from within an ISR ).
In these posts you will find more information about <code>printf-stdarg.c</code>:
<a href="https://sourceforge.net/p/freertos/discussion/382005/thread/8fbac97d">sprintf %f corrupts stack </a>
<a href="https://sourceforge.net/p/freertos/discussion/382005/thread/a9094bfc">hardfault with sprintf/snprintf/vsprintf/vsnprintf, newlib, newlibnano, tinyprintf </a>
You&#8217;re not the only person having problems with the <code>[v][s][n]printf</code> functions.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on April 4, 2018</div><div class="thread-post-content">One thing to check is what options newlib was built with, as the use of malloc<em>lock/mallooc</em>unlock is configured at library build time. One test is if you DON&#8217;T define those functions, do they show up in the link map? If not, then malloc/free isn&#8217;t calling them.

<ul>

<li>I verified that my linker address map originally contained labels __malloc<em>lock and __malloc</em>free supplied by libc, and that after I replaced them, those were gone and only my own versons were present. So I conclude that newlib does refer to them.</li>
<li>I need to print floats, and I understand that the FreeRTOS version of printf etc. doesn&#8217;t support them. Perhaps I should add support for floating point formats to it.</li>
<li>I understand that strtod also allocates dynamic memory under some circumstances, so I need to handle that function too.</li>
<li>Replacing malloc/free by one of the FreeRTOS versions may be an option, but I am puzzled that adding the semaphore didn&#8217;t fix the problem.</li>
<li>Thanks for the links, I previously found some but not all of them.</li>
</ul>
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcrocker">dcrocker</a> on April 4, 2018</div><div class="thread-post-content">I did some more digging and found:
<ul>
<li><code>_Balloc</code> is used by strtod, not printf</li>
<li>Although my code does use strtod, it should never be called when the system is idle (which is when it was crashing with a hard fault eventually). Which leaves me puzzled.</li>
<li>I didn&#8217;t have configUSE<em>NEWLIB</em>REENTRANT set in my config. This would explain the problem I think, because strtod uses big-number structures that need to be per-task</li>
<li>Unfortunately, when I set configUSE<em>NEWLIB</em>REENTRANT and rebuild, I can get the system to run but the diagnostics indicate that RAM usage has increased by many kB and there is no longer any free memory. I think this is because of all the stuff in<code>_struct reent</code> that I dont need, such as the stdin/stdout/stderr stuff.</li>
</ul>
I think this leaves me a few options:
<ul>
<li>Try to save RAM  elsewhere in the project &#8211; but I&#8217;ve already done this several times, and I want to add a lot more tasks so I can&#8217;t really afford a <code>_reent</code> struct for each one anyway</li>
<li>Compile my own version of newlb without the stdio stuff and other stuff that I don&#8217;t need in <code>_reeent</code></li>
<li>Wrap calls to strtod in a mutex. This will work for strtod, but I may hit similar problems with other functions in newlib</li>
<li>Write my own version of strtod. I only need to parse floats, not doubles, so with luck I can skip the big number stuff and not need to use any heap.</li>
</ul>

It turns out when when printing floating point formats, printf uses a buffer in the <code>_reent</code> struct. As I cannot afford the large amount of storage associated with having a reeent struct for each task, I&#8217;ll have to find another solution. I&#8217;ve switched to newlib-nano and in that version, the floating point bits that use the reent struct are in a separate file, vfprintf_float.c. So it looks like I can just take that file, hack it it to use the stack instead and include those functions in my project. Or maybe just disable scheduling around it.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 5, 2018</div><div class="thread-post-content">Normally, if the problem is only with floating point values, the root 
cause is a misaligned buffer.  Floating point requires 8-byte alignment. 
  The stack MUST be 8-byte aligned, but if if this is inside a FreeRTOS 
task then it should already be &#8211; but maybe there are other buffers that 
must also be?
</div></div><div class="thread-post"><h3 class="thread-post-title">How to  make printf/sprintf/strtod thread safe</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcrocker">dcrocker</a> on April 5, 2018</div><div class="thread-post-content">Thanks, Richard. I&#8217;m fairly sure it is because both tasks are using the buffer in the same reent struct to convert the float.
