</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskIncrementTick changed to xTaskIncrementTick</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 24, 2013</div><div class="thread-post-content"><blockquote>
  I see that vTaskIncrementTick was changed to xTaskIncrementTick &#8211; was just trying to help 
  with a port and &#8216;upgraded&#8217; from 7.4.0 to 7.5.3 &#8211; I searched this forum didn&#8217;t see any 
  mention of it.
</blockquote>
The change was made to all ports in V7.5.0.  Search for &#8220;Compatibility information for FreeRTOS port writers:&#8221; in http://www.FreeRTOS.org/History.txt.  It is a major performance enhancement for ports that can make use of it.  A context switch should only be performed if xTaskIncrementTick() returns pdTRUE.
<blockquote>
  So, it may appear there is an issue with the stack overflow checking method.
</blockquote>
It is known that some architectures that have segmented memory have a problem with stack overflow checking (x86 for example), but I&#8217;ve just checked the MSP430X demo and, in the demo at least, it is turned on.  Maybe there is an issue when it goes above 0xffff (max 16-bit value)?  That would seem to be borne out by your other posts as it appears the linker pukes if you try creating an array over that size.
Regards.
