  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vTaskSuspendAll, xTaskResumeAll and configUSE_PREEMPTION = 0</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pronkin">pronkin</a> on October 24, 2013</div><div class="thread-post-content">Hi everybody, for one of my project I use Cooperative Multi-threading (<em>configUSE_PREEMPTION</em> = 0)
And think that <em>vTaskSuspendAll</em> and <em>xTaskResumeAll</em> are useless in this case
Since <em>xTaskResumeAll</em> may cause YIELD and I use heap_3 Malloc scheme
<h1>vTaskSuspendAll();</h1>
<h1>{</h1>
<h1>pvReturn = malloc( xWantedSize );</h1>
<h1>traceMALLOC( pvReturn, xWantedSize );</h1>
<h1>}</h1>
<h1>xTaskResumeAll(); //It can YIELD here</h1>
It means <em>pvPortMalloc</em> can cause a context switch  (little confusing)
Here is some bad scenario:
1) Some work with critical data structures
2) Decide to malloc some memory, while data structures not correct
3) After <em>pvPortMalloc</em> other task can get access to wrong data 
4) End work with critical data structures and free memory
Maybe in case of <em>configUSE_PREEMPTION</em> = 0 <em>vTaskSuspendAll</em> and <em>xTaskResumeAll</em> should be empty?
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskSuspendAll, xTaskResumeAll and configUSE_PREEMPTION = 0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on October 24, 2013</div><div class="thread-post-content">Initial thought is to keep them, but to just not yield if configUSE_PREEMPTION is 0, but second thought is you might be right to just compile them out all together.
When the RTOS is suspended interrupts can happen but context switches cant, but if you are using cooperative scheduling then context switches are not going to happen anyway.
But even when configUSE_PREEMPTION is 0 a context switch can happen if you for example send to a queue and there is a task blocked on the queue &#8211; but that is more expected behavior whereas calling resumeAll and getting a context switch isnt.
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskSuspendAll, xTaskResumeAll and configUSE_PREEMPTION = 0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pronkin">pronkin</a> on October 24, 2013</div><div class="thread-post-content">hm, yes <em>vTaskSuspendAll</em> can be used in cooperative sheduller to avoid 
context switch in <em>QueueSend</em> or <em>SemaphoreGive</em>, so <em>vTaskSuspendAll</em> can&#8217;t be empty.
But context switch in <em>pvPortMalloc</em> not expected (for me)
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskSuspendAll, xTaskResumeAll and configUSE_PREEMPTION = 0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 7, 2013</div><div class="thread-post-content">Take a look at the head revision in SVN &#8211; the co-operative behaviour has been changed, and as such it will probably be released as V7.6.0.
Now a context switch is only performed if the calling task is blocked.  For example, if you attempt to write to a queue with a block time specified and the queue is full then the task will block and another task will start running.  However, if you successfully write to the queue, and writing to the queue causes a task of higher priority to unblock, then a context switch will <em>not</em> occur &#8211; the original task will continue executing until it either blocks or calls taskYIELD().
Likewise when changing the priority of another task, or unsuspending another task, etc.  A context switch will not occur even if the API call makes a higher priority task ready to run.
Regards.
