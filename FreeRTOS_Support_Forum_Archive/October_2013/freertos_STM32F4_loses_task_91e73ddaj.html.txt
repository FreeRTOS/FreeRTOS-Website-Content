  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32F4 loses task</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dpursell">dpursell</a> on October 1, 2013</div><div class="thread-post-content">Hello,
I&#8217;m developing using Red Suite 5 and FreeRTOS 7.5.2 on the STM32F4. A certain task seems to be getting dropped from the task list after running for an hour or so, after which the program will either behave erratically or hardfault right away.
When crashing, the program appears to be trying to swap in an invalid task address (pxCurrentTCB == 0x0) during the PendSV interrupt handler. Additionally, the internal bookkeeping data is inconsistent: uxCurrentNumberOfTasks == 9, but only 8 tasks exist in the list returned by uxTaskGetSystemState(). Also pxReadyTasksLists[3].uxNumberOfItems == 2 (the lost task and another task ran at the same priority), but there only seems to be one valid item, the other is a pointer to pxReadyTasksLists[3].xListEnd.
I&#8217;m 99% sure it&#8217;s not a stack problem, I&#8217;m using &#8220;#define configCHECK<em>FOR</em>STACK_OVERFLOW  2&#8243; and when calling uxTaskGetSystemState() or manually checking stacks in the debugger I&#8217;ve never come within 150 bytes for any task, and never within 500 bytes for the task in question.
I&#8217;m guessing I have an interrupt priority problem, since that seems to be the most common issue on the Cortex-M chips, but as far as I can tell I&#8217;m doing everything correctly.
~~~~~
// Definitions in FreeRTOSConfig.h
<h1>define configLIBRARY<em>LOWEST</em>INTERRUPT_PRIORITY         0xF</h1>
<h1>define configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY    5</h1>
<h1>define configKERNEL<em>INTERRUPT</em>PRIORITY         ( configLIBRARY<em>LOWEST</em>INTERRUPT<em>PRIORITY &lt;&lt; (8 &#8211; configPRIO</em>BITS) )</h1>
<h1>define configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY    ( configLIBRARY</em>MAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY &lt;&lt; (8 &#8211; configPRIO</em>BITS) )</h1>
// Called when the program starts before any other NVIC functions
NVIC_SetPriorityGrouping(3);
// Calls to install each individual interrupt, where:
//   irq is the interrupt number
//   prio is the assigned priority, I only use (configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY + 0) to (configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY + 2)
NVIC<em>SetPriority(irq, prio);
NVIC</em>EnableIRQ(irq);
~~~~~
Here&#8217;s information from the hard fault:
R0 = 2001C064
R1 = 0
R2 = 0
R3 = 20000F74
R12 = 200004BC
LR [R14] = 557CF342  subroutine call return address
PC [R15] = 557CF342  program counter
PSR = 6000000E
BFAR = E000ED38
CFSR = 00000001
HFSR = 40000000
DFSR = 00000001
AFSR = 00000000
SCB_SHCSR = 00000400
Any insight into what might be going wrong would be greatly appreciated, I&#8217;ve been banging my head against this for a few days without much progress. If anything is unclear I would be happy to elaborate.
Thanks,
David
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 loses task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 1, 2013</div><div class="thread-post-content"><blockquote>
  NVIC_SetPriorityGrouping(3);
</blockquote>
This is almost certainly the cause of your problem.  Change the &#8220;3&#8221; to a &#8220;4&#8221;.  As you are using V7.5.2 I would also recommend defining configASSERT() as some additional asserts were added to catch exactly this problem.
If you have not already done so, take a look at:
http://www.freertos.org/RTOS-Cortex-M3-M4.html
Noting the red text ;o)
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 loses task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dpursell">dpursell</a> on October 1, 2013</div><div class="thread-post-content">Thanks for the quick response Richard,
I should have pointed this out, but I&#8217;m using the function NVIC<em>SetPriorityGrouping(), not NVIC</em>PriorityGroupConfig() (note slightly different name). I am not using the standard peripheral library so NVIC<em>PriorityGroupConfig() and NVIC</em>PriorityGroup<em>4 are not available. Instead I found this function in my core</em>cm4.h file:
~~~~~
static __INLINE void NVIC<em>SetPriorityGrouping(uint32</em>t PriorityGroup)
{
  uint32<em>t reg</em>value;
  uint32<em>t PriorityGroupTmp = (PriorityGroup &amp; (uint32</em>t)0x07);               /* only values 0..7 are used          */
  reg<em>value  =  SCB->AIRCR;                                                   /* read old register configuration    */
  reg</em>value &amp;= ~(SCB<em>AIRCR</em>VECTKEY<em>Msk | SCB</em>AIRCR<em>PRIGROUP</em>Msk);             /* clear bits to change               <em>/
  reg_value  =  (reg_value                                 |
                ((uint32_t)0x5FA &lt;&lt; SCB_AIRCR_VECTKEY_Pos) |
                (PriorityGroupTmp &lt;&lt; 8));                                     /</em> Insert write key and priorty group */
  SCB->AIRCR =  reg_value;
}
~~~~~
I am fairly certain that my call to NVIC<em>SetPriorityGrouping(3) does the exact same thing as your suggested NVIC</em>PriorityGroupConfig(NVIC<em>PriorityGroup</em>4) since NVIC<em>PriorityGroup</em>4 is defined as 0x300.
Additionally I have tried using 0 instead of 3, and also have the assert defined as:
~~~~~
<h1>define configASSERT( x ) if( ( x ) == 0 ) { taskDISABLE_INTERRUPTS(); for( ;; ); }</h1>
~~~~~
but it never registers any problems.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 loses task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 1, 2013</div><div class="thread-post-content">Ah yes, I didn&#8217;t notice that subtle change.
Are you using the STM32 standard peripheral library at all?  If not, you can probably not call any of the priority grouping functions &#8211; and just leave it at its default.  That is how all the other Cortex-M ports work.  There is only a special case for STM32 because the standard peripheral libraries silently bug your code if the priority grouping is left at its default value (you will see why if you step through the STM32 version of &#8220;priority set&#8221;).
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 loses task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dpursell">dpursell</a> on October 1, 2013</div><div class="thread-post-content">Ah, thanks for the clarification. As suggested, I&#8217;ve removed the NVIC_SetPriorityGrouping() call, and the configASSERT still never triggers so I assume you are correct that it was not necessary in my case. However, the original problem still remains, the same task continues to disappear after running for a while.
I will try to keep troubleshooting and post results here if I discover anything, in case others are having a similar problem. If anything comes to mind you think I should try, or any specific variables I should examine in the debugger, please let me know.
Thanks,
David
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 loses task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dpursell">dpursell</a> on October 2, 2013</div><div class="thread-post-content">It looks like the problem was caused by interrupt nesting, but I&#8217;m still not sure why the nesting caused corruption of the internal FreeRTOS structures. I doubt it&#8217;s a bug in FreeRTOS since nobody else seems to have noticed this, so I&#8217;m probably doing something wrong, but at least for now I&#8217;ve worked around it by just assigning my interrupts to the same priority.
I&#8217;m attaching a FreeRTOS+ Trace clip showing the problem. My two tasks are named &#8220;MPU&#8221; and &#8220;Amulet&#8221;, and they have the same FreeRTOS priority. This exact sequence seems to be present immediately before each crash:
1. Idle task is active
2. SPI interrupt (prio = 7) releases a semaphore
3. &#8220;MPU&#8221;, waiting on SPI semaphore, becomes ready
4. Before &#8220;MPU&#8221; becomes active, UART5 interrupt (prio = 6, logically higher than SPI) pushes into a queue
5. &#8220;Amulet&#8221;, waiting on UART5 queue, becomes ready
6. &#8220;Amulet&#8221; becomes active
7. &#8220;MPU&#8221; tries to become active, but somehow pxCurrentTCB is now NULL and the program crashes
If by chance anyone is experiencing a similar issue, my advice is to set your interrupts to be the same priority, seemed to work for me.
Thanks,
David
