</div></div><div class="thread-post"><h3 class="thread-post-title">Faster context switching</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on March 6, 2007</div><div class="thread-post-content">WRT ulCriticalNesting.
Each task has its own interrupt status as part of its context.&nbsp; You therefore need to save the interrupt status when context switching.&nbsp; This can be done easily by saving and then restoring the ulCriticalNesting variable.&nbsp; 
Older versions of the ARM port did not do this because the critical section implementation was different.&nbsp; 
To enter a critical section the old version would push the status register onto the stack then disable interrupts.
To exit a critical section the old version would simply pop the status registers from the stack.
This method takes care of nesting automatically using the stack and therefore does not need the ulCriticalNesting variable.&nbsp; The problem was it only worked at certain optimization levels.&nbsp; Low optimization you can modify the stack without upsetting access to stack variables, the same is not true at high optimization.
The AVR/GCC port still uses the old method because the compiler does not care for that processor.
Dave.

</div></div><div class="thread-post"><h3 class="thread-post-title">Faster context switching</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/embeddedc">embeddedc</a> on April 8, 2007</div><div class="thread-post-content">Some API functions can be called before the scheduler is started.&nbsp; These API functions may use critical nesting.&nbsp; Initializing the critical nesting count to non zero ensure interrupts don&#8217;t mistakenly get enabled prior to the scheduler starting.
The critical nesting count is stored as part of the context of each task and therefore is automatically cleared to zero when the first task starts.

</div></div><div class="thread-post"><h3 class="thread-post-title">Faster context switching</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on April 9, 2007</div><div class="thread-post-content">The nesting count is stored as part of the task context.&nbsp; The initial context of the task has the count set to zero so when the context is restored zero is written into the nesting count.
Dave.
</div></div><div class="thread-post"><h3 class="thread-post-title">Faster context switching</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/adarkar9">adarkar9</a> on April 9, 2007</div><div class="thread-post-content">You might be laboring under the same false assumption that I made a while ago.&nbsp; Just because you are in a &quot;critical section&quot; does not guarantee that a context switch won&#8217;t occur.&nbsp; For more details, check out the thread &quot;Yield in critical section?&quot; in this forum &#40;dated 2006-05&#41;.&nbsp; In a nutshell, the kernel sometimes does yield from within &quot;critical sections&quot; and expects to continue execution with interrupts disabled.&nbsp; Therefore you cannot assume that ulCriticalNesting is zero when a context switch occurs.
