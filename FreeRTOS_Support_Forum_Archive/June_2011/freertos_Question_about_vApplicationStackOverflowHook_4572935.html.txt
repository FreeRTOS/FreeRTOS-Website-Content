  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Question about vApplicationStackOverflowHook</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/anguel78">anguel78</a> on June 14, 2011</div><div class="thread-post-content">Hello&#33;  
When I look at this function:  
<pre><code>void vApplicationStackOverflowHook( xTaskHandle *pxTask, signed portCHAR *pcTaskName );
</code></pre>
I get the impression that one is able to receive the handle to and the name of the overflowing task through pxTask and pcTaskName. Is this correct? On the other hand I am a bit confused, because the function does <strong>not **seem to return a **pointer</strong> to an xTaskHandle but just an xTaskHandle as pxTask.  
Regards,<br />
Anguel
</div></div><div class="thread-post"><h3 class="thread-post-title">Question about vApplicationStackOverflowHook</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 15, 2011</div><div class="thread-post-content">Nothing is returned, only input into the function.  
Yes you are correct that the task name and handle are passed in to assist in identifying the offending task.&nbsp; However, note that often a stack overflow will result in these values being corrupt anyway &#8211; in which case you have to inspect the pxCurrentTCB variable directly.  
Recovering from a stack overflow without restarting/resetting is extremely difficult unless you are using a microcontroller and FreeRTOS port that support an MPU.&nbsp; That is because, without an MPU you only know the corruption has occurred after it has occurred so don&#8217;t necessarily know what is corrupt &#40;unless you allocate a lot of padding after the stack&#41;, whereas with an MPU you know a corruption is about to happen before it actually occurs so get a chance to prevent it.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Question about vApplicationStackOverflowHook</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/anguel78">anguel78</a> on June 15, 2011</div><div class="thread-post-content">Thanks for the detailed explanation&#33;  
Actually I had tested the following on PIC32 before asking:  
<pre><code>void vApplicationStackOverflowHook(xTaskHandle *pxTask, signed char *pcTaskName )
{
    bad_task_handle = pxTask;     // this seems to give me the crashed task handle
    bad_task_name = pcTaskName;     // this seems to give me a pointer to the name of the crashed task
    mLED_3_On();   // a LED is lit when the task has crashed
    for( ;; );
}
</code></pre>
As you say, both bad&#95;&#42; variables may contain unreliable information because of the overflow. BTW the FreeRTOS book says that only the task name may be corrupt for some reason.  
Is it a good idea to at least &#8220;try&#8221; to perform a MCU reset from the vApplicationStackOverflowHook&#40;&#41;?  
Regards,<br />
Anguel
</div></div><div class="thread-post"><h3 class="thread-post-title">Question about vApplicationStackOverflowHook</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 15, 2011</div><div class="thread-post-content">If your application can cope with a reset, then that is a reasonable thing to do.&nbsp; However, I would say, what you don&#8217;t want is your system continuously or sporadically resetting without you knowing &#8211; just because a stack somewhere needs a little adjustment &#8211; so if the hook function is called you want it logged somewhere.  
Another point is, the hook function is called from the tick hook.&nbsp; That means, in the code you posted above, while you sit in the null loop no tasks will execute.&nbsp; However, interrupts that have a priority above the tick interrupt will continue to execute.&nbsp; If you want to halt everything then globally disable interrupts before entering the null loop.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Question about vApplicationStackOverflowHook</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/anguel78">anguel78</a> on June 15, 2011</div><div class="thread-post-content">You are right, during development a MCU reset in the hook is pointless. I thought of using the reset in a production system, just in case some overflow occurs for some reason.  
Also thanks to the hint with the interrupts.
