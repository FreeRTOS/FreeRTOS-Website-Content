</div></div><div class="thread-post"><h3 class="thread-post-title">Mutex runs not correct ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on June 28, 2011</div><div class="thread-post-content">If the priorities are the same then a switch between the tasks will happen when a tick interrupt happens. I cannot tell from your code how long printf&#40;&#41; will take to execute, maybe a tick interrupt happens once every 50 calls to printf&#40;&#41;, maybe 50 interrupts happen during one printf&#40;&#41; call, who knows. Also, does printf&#40;&#41; stop the processor executing when it is called. Sometimes that is the case when if printf&#40;&#41; is directed out a debug port.  
Have you checked xMutexLed was actually created correctly and is not NULL?  
As the tasks are the same priority and make a blocking call, then there is a chance that the pattern you expected would happen during execution, as when one task gives the mutex back the other one will unblock and start executing. That is not guaranteed though as it depends on the timing of the execution relative to the tick interrupts firing. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Mutex runs not correct ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 28, 2011</div><div class="thread-post-content">The issue is that giving a semaphore that another task is waiting on, does not automatically give them them the semaphore, but unblocks them so when they next get time, they will try and take it. Since each task after giving immediately takes it back, on the next tick when the other task gets time, it finds that the semaphore isn&#8217;t available and blocks again.   
What you should do is add a taskYield after the give, thus giving the other task a chance to grab the semaphore before it tries to take it back.

</div></div><div class="thread-post"><h3 class="thread-post-title">Mutex runs not correct ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 29, 2011</div><div class="thread-post-content">In fact, if sending a semaphore unblocks a task of greater than or equal priority to the sending semaphore, then a task a yield will automatically be performed within the API function itself &#8211; so putting a yield after the xSemaphoreGive&#40;&#41; should not, in theory, make a difference.&nbsp; It was a logical suggestion though.  
There is not really enough information in your post to provide a definitive answer, for example, what is printf&#40;&#41; doing?&nbsp; Have you tried flushing stdout after calling printf&#40;&#41;.&nbsp; Which port are you using? etc.  
There are two plausible theories, that I could not verify without actually having your code to debug in front of me.&nbsp; The first is less plausible than the second, because the timing would have to be very critical:  
1&#41; Task A takes the semaphore.<br />
2&#41; Task B blocks on the semaphore.<br />
3&#41; Task A prints out is message, that takes 98/100ths of a tick period.<br />
4&#41; Task A then yields, that takes 1/100th of a tick period.&nbsp; There is now only 1/100th of a tick period left.<br />
5&#41; Task A yields as it gives the semaphore back.<br />
6&#41; Task B runs, but only has 1/100th of a tick period left to execute so does not do much.<br />
7&#41; A tick interrupt occurs and re-selects task A to run before task B has done anything.<br />
8&#41; Task A takes the semaphore&nbsp; and continues on its merry way.&nbsp; When task B runs again, the semaphore is still not available &#40;task A has it again&#41; so blocks once more.  
or  
1&#41; Task A takes the semaphore.<br />
2&#41; Task A prints out its message, that does not take very long at all, say 5/100ths of a tick period.<br />
3&#41; Task A gives the semaphore back.&nbsp;<br />
4&#41; Task B has not run since Task A originally took the semaphore because Task A&#8217;s operation only took a fraction of a tick period, so task B is not Blocked on the semaphore when task A gives it back, and therefore no automatic context switch occurs and Task A just continues on and takes the semaphore again.  
The third scenario would be that printf&#40;&#41; is doing something dramatic to the debug interface, which is halting the CPU or messing with interrupts, and so nothing can be guaranteed about how the application will execute.  
You could use the trace macros to find out the actual execution pattern, then you would have an absolute answer, but that would take probably twenty minutes to set up and require a mechanism of obtaining the trace output.  
Regards.
