</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V7.0.1 Software Timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 7, 2011</div><div class="thread-post-content">I have just done a quick experiment and cannot replicate this behaviour.  
The timer task will be in the Blocked state unless a timer API function is being called, or a timer has expired.&nbsp; If another task or interrupt is continuously using timer API functions, or a timer has its period set to a very low number &#40;so it continuously expires&#41; then the timer task will have processing to perform all the time &#8211; and therefore starve lower priority tasks of processing time &#40;just like any other task would&#41;.&nbsp; If the timer task has the highest priority, and it is performing processing all the time, then no other tasks would run &#40;again, it just behaves like any other task&#41;.  
Are you using timers with very short periods?<br />
Are you continuously calling timer API functions?<br />
Do you have configASSERT&#40;&#41; defined to trap some misuse scenarios?  
Regards.
