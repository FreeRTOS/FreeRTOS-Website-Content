</div></div><div class="thread-post"><h3 class="thread-post-title">ISR rules in FreeRTOS book for PIC32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 10, 2011</div><div class="thread-post-content"><blockquote>
  The FreeRTOS book for PIC32 states that an unmodified classic ISR &#40;i.e. with no special RTOS wrapper in assembler&#41; can still be used with FreeRTOS as long as the ISR does not cause a task to change state. Does that simply mean that the ISR should not make any FreeRTOS API calls or are there also other catches?
</blockquote>
As I recall, that pretty much sums it up.&nbsp; A task can only change state through an API call being made.  
<blockquote>
  Another rule is that a classic unwrapped ISR used with FreeRTOS must not be interrupted. But interrupted by what?<br />
  &#45; By the kernel? I.e. ISR should have same or higher interrupt priority as the kernel?<br />
  &#45; By another ISR that uses API calls?<br />
  &#45; Or also by ANY other classic or FreeRTOS-aware ISR having a higher interrupt priority than my classic ISR?
</blockquote>
Again, as I recall, it would mean by any interrupt that will enter through the FreeRTOS wrapper code.  
What you refer to as &#8216;classic&#8217; interrupts enter through code that is generated by the compiler.&nbsp; If you declare the function as an interrupt the compiler generated different function prologue and epilogue assembly code.&nbsp; Again, if my recollection is correct, you can tell the compiler whether the body of the interrupt should run with interrupt enabled or disabled.&nbsp; If you tell the compiler to enable interrupts then the compiler generated prologue code will include a line to enable interrupts.&nbsp; Be aware that if you have &#8216;classic&#8217; interrupts then the stack you have to allocate to <strong>each</strong> task will be much larger as it will have to &#40;potentially&#41; hold an entire interrupt stack too.  
If you enter an interrupt through the FreeRTOS wrapper code, then there is a lot of &#8216;extra&#8217; stuff that goes on.&nbsp; For example, it keeps a note of whether interrupts are nested or not, and only re-enables interrupts that have a priority higher than the currently executing interrupt.&nbsp; It also switches to a dedicated ISR stack to radically reduce the amount of RAM that has to be allocated to the stack of each task &#8211; because the task stacks will only ever have to hold the task stack, and never a &#40;potentially nested&#41; interrupt stack on top.  
Because of the extra code in the FreeRTOS wrapper &#40;the interrupt nesting count, stack swapping, etc&#41; you cannot mix &#8216;classic&#8217; and FreeRTOS interrupts in the same nesting.  
You could probably have a &#8216;classic&#8217; interrupt nest with an existing stack of nested &#8216;FreeRTOS&#8217; interrupts, so the &#8216;classic&#8217; interrupt stacks are always on top &#40;I think the FreeRTOS demo does this with a high frequency timer, but would have to double check&#41;, but never intermingle the two or have a FreeRTOS interrupt on top of a classic interrupt.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">ISR rules in FreeRTOS book for PIC32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on June 18, 2011</div><div class="thread-post-content">One very minor one is that you have to write the wrapper by hand instead of just telling the compiler a function is an interrupt handler. That is very easy though, you just cut and past the wrappers supplied in the demos, and use the macros supplied in the FreeRTOS port.  
I suppose one other is that the wrappers give you the ability to nest interrupts and to swap to an interrupt stack, which takes a bit longer to execute than compiler generated interrupt code. The benefits greatly outweigh the extra CPU cycles though in nearly all cases. That is especially true when you consider the amount of RAM swapping stacks saves you.
