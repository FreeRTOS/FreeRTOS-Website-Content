</div></div><div class="thread-post"><h3 class="thread-post-title">heap_4 strange xFreeBytesRemaining</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 16, 2014</div><div class="thread-post-content">Hi Louis,
A few months ago I have tested heap_4.c thoroughly for several hours in a simulator. I was amazed by its simpleness and its speed. The test was randomly allocating memory and returning other memories. As long as my testing program was well-behaving, it didn&#8217;t encounter any problem.
There are two obvious rules for &#8220;good behaviour&#8221;:
<ul>
<li>Never write outside the allocated space</li>
<li>Only call vPortFree() once for each memory pointer</li>
</ul>
The heap_x.c modules do have a bit of error checking but it&#8217;s very minimal to save CPU time.
I hope you have configASSERT defined:
~~~~
void vPortFree( void <em>pv )
{
    &#8230;
    /</em> Check the block is actually allocated. */
    configASSERT( ( pxLink->xBlockSize &amp; xBlockAllocatedBit ) != 0 );
    configASSERT( pxLink->pxNextFreeBlock == NULL );
}
~~~~~
I once added an extra field to check the validity of the memory blocks:
~~~~
<h1>define INTEGRITY<em>STAMP</em>TAKEN   33333</h1>
<h1>define INTEGRITY<em>STAMP</em>FREE    11111</h1>
/* Define the linked list structure.
 * This is used to link free blocks in order
 * of their memory address. */
typedef struct A_BLOCK_LINK
{
<h1>if( HEAP<em>INTEGRITY</em>TEST != 0 )</h1>
<pre><code>uint32_t ulStamp;
</code></pre>
<h1>endif</h1>
<pre><code>struct A_BLOCK_LINK *pxNextFreeBlock; /* The next free block in the list. */
size_t xBlockSize;           /* The size of the free block. */
</code></pre>
} BlockLink_t;
~~~~~
Find attached a version of heap_4.c which has such extension. You might want to have a try with it.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">heap_4 strange xFreeBytesRemaining</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 16, 2014</div><div class="thread-post-content">Replying to two posts:
<blockquote>
  I hope you have configASSERT defined:
</blockquote>
His version pre-dates that, and several other recent debug assisting asserts, which may help identify the problem.
<blockquote>
  so that means timer tick too, right?
</blockquote>
Definitely right.  The allocation schemes could be altered to make them interrupt safe, but as delivered they are not (because to do so would mean interrupts would have to remain off for a non-deterministic time, and that is something FreeRTOS just does not allow).
You could of course have two memory allocation regions, one for tasks and one for interrupts.
