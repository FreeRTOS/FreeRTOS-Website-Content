Overview:
I have 2 Tasks, Process() and SDCardStream() + SPI DMA that streams fills a DBuffer every 100ms.
Process() is in High priority and always takes ~50ms to complete.
SDCardStream() is in Normal priority and usually takes ~6ms (but sometimes 80ms, uSD BusyState) to complete.
I <em>MUST</em> complete one Process() task per 100ms tick.
The buffer allows me to &#8220;miss&#8221; an SD write and complete it later, this is why I thought FreeRTOS is the solution.
Problem:
If I don&#8217;t wrap the functions with a critical section I get fatal errors (FR<em>DISK</em>ERR, ..).
<pre><code>    taskENTER_CRITICAL();
    res = f_open(&amp;MyFile, filename, FA_CREATE_ALWAYS | FA_WRITE);
    taskEXIT_CRITICAL();
</code></pre>
If I disable Process() it also works.
If I have a critical section, and the function will take 80ms, Process() won&#8217;t be called on time (i.e I won&#8217;t have enough time before the next tick).
** Is this a known issue?
** Is there a way to break FatFs in the &#8220;idle&#8221; wait periods (e.g. while it waits uSD to get out of busy state) 
** Can you suggest a lead / idea?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FatFs : Works only with taskENTER_CRITICAL</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 2, 2014</div><div class="thread-post-content">ChaN and most FS drivers will have some kind of protection.
~~~~~
    /* The <em>FS</em>REENTRANT option switches the reentrancy of the FatFs module.
    /
    /   0: Disable reentrancy. <em>SYNC</em>t and <em>FS</em>TIMEOUT have no effect.
    /   1: Enable reentrancy. Also user provided synchronization handlers,
    /      ff<em>req</em>grant, ff<em>rel</em>grant, ff<em>del</em>syncobj and ff<em>cre</em>syncobj
    /      function must be added to the project. */
~~~~~
If you are sure that SDCardStream() is the <strong>only</strong> user, there is no need for protection at all.
If you have multiple users, you might want to enable <em>FS</em>REENTRANT and provide sync routines. taskENTER_CRITICAL() is too heavy for this type of protection.
But: is your SD-card accessed through SPI? And does that interfere with Process() ?
What else is Process() doing that could disturb access to the SD-card?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FatFs : Works only with taskENTER_CRITICAL</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 2, 2014</div><div class="thread-post-content">You should not be using taskENTER_CRITICAL to protect something that can take 6ms, let alone 80ms. A mutex is a much better option here, as that will only block the other tasks that try to use the file system. (The code may even support a locking method inside itself which you can connect to such a mutex).

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FatFs : Works only with taskENTER_CRITICAL</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 3, 2014</div><div class="thread-post-content">Hi Ariel,
You known that if you post code like this, you have to promise something in return? At least a chardonnay, or a home-made crumble apple pie 🙂
You&#8217;re giving <code>configMINIMAL_STACK_SIZE</code> to uSDThread(). Disabling interrupts will avoid that the stack will be overwritten, and thus hide the problem.
Especially when opening/closing files, a lot of stack space may be needed.
These <code>ChaN</code> defines influence the stack usage:
~~~~~
<h1>define <em>USE</em>LFN    2       /* 0 to 3 */</h1>
<h1>define <em>MAX</em>LFN    128     /* Maximum LFN length to handle (12 to 255) */</h1>
/* The <em>USE</em>LFN option switches the LFN feature.
/
/   0: Disable LFN feature. <em>MAX</em>LFN has no effect.
/   1: Enable LFN with static working buffer on the BSS.
/   2: Enable LFN with dynamic working buffer on the STACK.
/   3: Enable LFN with dynamic working buffer on the HEAP. */
~~~~~
Tip: use a big stack (>= 1024 words, 4KB), and look at the actual stack usage.
(see http://www.freertos.org/Stacks-and-stack-overflow-checking.html)
PS. defining <code>_FS_REENTRANT</code> is not enough, you&#8217;ll also have to define ff<em>req</em>grant()/ff<em>rel</em>grant().
You don&#8217;t need it as long as uSDThread() is the only FS user.
Regards,
Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FatFs : Works only with taskENTER_CRITICAL</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 6, 2014</div><div class="thread-post-content">Hi Ariel,
<blockquote>
  ChaN&#8217;s error: FR<em>DISK</em>ERR
</blockquote>
Many developers will have seen this error, but there is not enough information available to say anything about the cause.
ChaN&#8217;s FS is a great driver, but when it encounters an error, you&#8217;ll only see a code like: &#8216;FR<em>DISK</em>ERR&#8217;. This may have 54 different reasons 🙂
What I would do is create a new version ff_debug.c with some more logging:
<pre><code>#define ABORT(fs, res) { fp-&gt;err = (BYTE)(res); LEAVE_FF(fs, res); }
</code></pre>
In <code>ABORT()</code> you could log at least <code>__LINE__</code>.
But <code>FR_DISK_ERR</code> may be thrown in many more cases, like here:
<pre><code>if (nxt == 0xFFFFFFFF) { res = FR_DISK_ERR; break; } /* Disk error? */
</code></pre>
Are you sure your SD-card is still 100% sane? It must have got corrupted earlier when you had the stack problems. Did you try this again after formatting the card?
You could also test your low-level SD-card driver: write and read-back many sectors at different locations (after which it&#8217;ll need formatting again).
Think, think: you&#8217;re writing that:
<blockquote>
  without the critical section I get FR<em>DISK</em>ERR
  only when Process() is active
</blockquote>
Would the other task <code>ProcessingLoop</code> need more stack, maybe? You also gave it a minimum stack while it does use the math library?
Good luck!
Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FatFs : Works only with taskENTER_CRITICAL</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 7, 2014</div><div class="thread-post-content">Simplification is always good to solve a problem.

I suppose that your SD-card driver uses interrupts. 
Here is all information: http://www.freertos.org/RTOS-Cortex-M3-M4.html

~~~~~
/* The highest interrupt priority that can be used by any interrupt service
routine that makes calls to interrupt safe FreeRTOS API functions.  DO NOT CALL
INTERRUPT SAFE FREERTOS API FUNCTIONS FROM ANY INTERRUPT THAT HAS A HIGHER
PRIORITY THAN THIS! (higher priorities are lower numeric values. */
<h1>define configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY  10</h1>
~~~~~

Hein

Does your project define any interrupt and are the priorities not too high?
Literally: are the priorities used numerically not lower (reverse logic) than the value of: <code>configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY</code> ?
Especially, somewhere in &#8216;portable/xx/ARM_CM3/port.c ,
make sure that these two configASSERT&#8217;s will do their job:
<pre><code>configASSERT( ucCurrentPriority &gt;= ucMaxSysCallPriority );
configASSERT( ( portAIRCR_REG &amp; portPRIORITY_GROUP_MASK ) &lt;= ulMaxPRIGROUPValue );
</code></pre>
A second question: Did you define:
<pre><code>void vApplicationTickHook( void );
</code></pre>
As you probably know, the freedom to write code inside this call-back function is very limited, because it is called from the <s>Idle task</s> tick interrupt.

I ended up simply configuring the SDIO driver to use DMA, which works well.
(that might lead to another undocumented DMA conflict issue(DMA Maximum Transactions), but thats a problem for another day :))
