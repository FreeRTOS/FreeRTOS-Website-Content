  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Stack on ATMEGA8</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">I use FREERTOS on an ATMEGA8 &#40;1k SRAM, 8k FLASH&#41; and if I have two tasks everything is OK, if I put another &#40;3 in total&#41; system seems to get stuck on one of them or something like that. Then I experimented by increasing the stack size for the two previously working tasks and I verified my theory. Once I increase the total stack size allocated from all tasks above 220bytes the system gets stucked.
I don&#8217;t really have a problem, I can do my job with two tasks. I just want to ask if this should happen or not?
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on July 25, 2005</div><div class="thread-post-content">1K SRAM is not very much.&nbsp; Each task has it&#8217;s own stack, plus any static data you have.&nbsp; This all has to fit into this 1K.&nbsp; There is also the stack for the idle task.
Can you implement one of your tasks as an idle hook?&nbsp; This would save you some RAM, but can only be done if the task never makes a blocking call &#40;the task must always be available to run&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">I fixed the problem by increasing the TOTAL&#95;HEAP&#95;SIZE size from 500bytes to 700bytes. It&#8217;s a little bit misleading that Task&#8217;s STACK is being allocated on the HEAP &#40;- I&#8217;m sure that the OS masters will laugh now claiming that &quot;where else could it be allocated on?&quot;&#41; 😀
People having similar problems should look at: http://www.freertos.org/FAQMem.html
and experiment with different values for TOTAL&#95;HEAP&#95;SIZE. &#40;Don&#8217;t forget to &#8216;make clean&#8217; and then &#8216;make all&#8217; again in case that &quot;FreeRTOSConfig.h&quot; is not included in your Makefile&#8217;s dependencies&#41;.
It&#8217;s still strange the way that application stalls always in the same way&#33; Perhaps some macros inside &quot;xTaskCreate&quot; could enable a message to be popped. Some additional documentation about memory management would be welcome&#33; 😀
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">Note: By increasing the HEAP SIZE from 500bytes to 700bytes I can have two more tasks. When I add another task it gets stuck in exactly the same way as before&#33; &#8211; Very strange&#33; I am used to see really unstable behaviour when a system runs out of memory &#8211; in freeRTOS it seems like the scheduler just stops task switching.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on July 25, 2005</div><div class="thread-post-content">Where does it get stuck?
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">Thank you Anonymous. In fact this is an academic conversation&#33; 😀 My application is simple enough and can be easily implemented with just two tasks. If anyone is interested in the AVR Gas Meter, more information can be found here: http://lookfwd.doit4me.gr/blog/index.php?blog=2&amp;title=the&#95;avr&#95;gas&#95;meter&amp;more=1&amp;c=1&amp;tb=1&amp;pb=1.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">Ok, This was a really hot question that gave a lot of hot answers&#33; 😀
I&#8217;ve put some UART &quot;traces&quot; like these:
ABCDE &#8211; initialization of tasks
kl &#8211; view procedure
1 &#8211; ADC measure task
5 &#8211; Key-Scan task
6 &#8211; Demo task
7 &#8211; Demo task
During normal operation it traced like this:
klmABCDE
13kl &#8211; 756
13kl &#8211; 5
13kl &#8211; 7655
13kl &#8211; 765
13kl &#8211; 5765 17655 17655 1765
13kl &#8211; 7565
When I added another task, it traced like this:
klmABCDE
Which means that the thread switching doesn&#8217;t even start. By hacking the source of vTaskStartScheduler&#40;&#41;, I put some additional traces that revealed that the &quot;problem&quot; was once creating the IDLE task. xTaskCreate kindly returned pdFAIL and vTaskStartScheduler&#40;&#41; was returning imediatelly.
Of course I&#8217;ve never imagined that something like this could happen and I haven&#8217;t put a &quot;HEY, WHAT DO YOU THING YOU&#8217;RE DOING?&quot; message after vTaskStartScheduler&#40;&#41; inside main&#40;&#41;.
That&#8217;s all&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack on ATMEGA8</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lookfwd">lookfwd</a> on July 25, 2005</div><div class="thread-post-content">And, as my project completes, one last world of attention: &quot;If your application has 3 user tasks that must all be at different priorities then use priorities 3 &#40;highest&#41;, 2 and 1 &#40;lowest &#8211; the idle task uses priority 0&#41;.&quot; In this case, do set configMAX&#95;PRIORITIES configuration variable to 4. That is the number of your priorities + the idle priority.
Internally, configMAX&#95;PRIORITIES is being used like this: 
if&#40; uxPriority &gt;= configMAX&#95;PRIORITIES &#41; &#123;
&nbsp;&nbsp;&nbsp; uxPriority = configMAX&#95;PRIORITIES &#8211; 1;
&#125;
As a result, you will never get a warning while at the same time, your highest priority levels will get &quot;flatten&quot;.
