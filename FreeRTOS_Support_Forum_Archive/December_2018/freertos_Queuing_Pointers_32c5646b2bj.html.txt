  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Queuing Pointers</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sarahaka">sarahaka</a> on December 16, 2018</div><div class="thread-post-content">Queuing pointers is different from queuing copies of the data in the sense that for pointers: 
    1. &#8220;The owner of the RAM being pointed to is clearly defined.&#8221;
    2. &#8220;The RAM being pointed to remains valid.&#8221;
 In the book, it is mentioned that:
&#8220;A pointer should never be used to access data that has been <strong>allocated on a task stack.</strong> The data will not be valid after the stack frame has changed.&#8221; Does this mean that I need to the data on the heap using malloc?
I understand that a task looks like this (it never exits):
~~~
void task(){
    int x; 
    while(1){
        &#8230;
    }
}
~~~
The variable x is allocated on the task stack, correct? However a task never exists, meaning its stack reamins for the lifetime of the program. Can I still use the variable x as a pointer to access data?
Thank you
</div></div><div class="thread-post"><h3 class="thread-post-title">Queuing Pointers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on December 16, 2018</div><div class="thread-post-content">Basically yes. But as  documented you have to ensure that the task resp. the scope of the local variable is never exited, which makes it invalid.
Also be aware that the compiler (optimizer) has no idea about tasks and might do interesting things with  local/stack variables i.e. using CPU registers instead of allocating space on the stack.
However, probably when using a pointer of a local variable as argument of a non-inlined function you can successfully enqueue the address of this local variable.
</div></div><div class="thread-post"><h3 class="thread-post-title">Queuing Pointers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 16, 2018</div><div class="thread-post-content">One big thing to remember when passing data as a pointer is that you don&#8217;t get a snapshot of the value the pointer points to, but whatever happens to be stored in memory at the time of access, which isn&#8217;t what the programmer normally expects at quick thought. Also, since now the data is available to multiple tasks at once, the programmer needs to be prepared to handle all the syncronization issues for access.
Generally, when sending data via a pointer, you want to at least conceptually think of the data as being owned by the task that has been sent the pointer, and no longer by the task that sent it, which is a bit hard to do mentally when it is a local stack variable.
