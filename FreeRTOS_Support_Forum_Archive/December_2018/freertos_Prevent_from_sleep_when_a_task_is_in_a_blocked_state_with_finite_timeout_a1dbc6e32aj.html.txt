  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Prevent from sleep when a task is in a blocked state with finite timeout</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kkoovalsky">kkoovalsky</a> on December 11, 2018</div><div class="thread-post-content">Hello all.
I&#8217;m running FreeRTOS V9.0.0 on STM32L432KC.
I have a problem in preventing the device from going to sleep. At startup I have some tasks which I need to run without sleep. They use <code>vTaskDelay</code> and also some of the tasks use functions like <code>xQueueReceive</code> with timeouts which are finite (no <code>portMAX_DELAY</code>). The problem is that when one of the tasks gets blocked on such functions the device goes to sleep and I do not want it to. In general I want to implement some kind of mechanism which allows to prevent from sleeping if there are tasks which wait for something with a finite timeout. I can&#8217;t find any API which allows me to distinguish tasks which wait for something with finite timeout (e.g. those which have called <code>vTaskDelay(pdMS_TO_TICKS(200))</code>, <code>xQueueReceive(q, pdMS_TO_TICKS(200))</code>,  <code>xSemaphoreTake(mux, pdMS_TO_TICKS(200))</code>&#8230; ) from those which are blocked indefinitely (<code>xQueueReceive(q, portMAX_DELAY)</code>,  <code>xSemaphoreTake(mux, portMAX_DELAY)</code>&#8230; ) .
The second problem is that I want to determine that in the <code>configPRE_SLEEP_PROCESSING()</code>  callback (it&#8217;s a macro &#8211; I know &#8211; but in general it&#8217;s defined as a callback in my app). When I try to call <code>uxTaskGetSystemState</code> in the callback I get a hardfault. I don&#8217;t know then whether I can call FreeRTOS specific functions in this callback and I can&#8217;t find any information about that in the documentation.
I&#8217;m thinking about two solutions:
1. Implement some kind of internal FreeRTOS mechanism, but then I need to edit FreeRTOS code, what&#8217;s quite intrusive and I don&#8217;t want to do it
2. Instead of using <code>vTaskDelay</code> implement a mechanism based on a hardware timer which wakes up the task after the specifed time and the timer is able to wake up the device from sleep. The problem here is that I would need to connect somehow the timer with the FreeRTOS code for the task which call functions like <code>xQueueReceive</code> or <code>xSemaphoreTake</code> with a finite timeout.
3. Manually add some flags which can be set/reset from task code and checked in the <code>configPRE_SLEEP_PROCESSING</code> callback. This is for me an ugly solution (but the simplest one) because every programmer in the team needs to remember about that when implementing a task, it can be error-prone and time-wasting when debugging.
My question is if there is some kind of out of the box mechanism in FreeRTOS which allows to implement 2.  solution or is there a way to determine in the <code>configPRE_SLEEP_PROCESSING</code> callback whether any task is in the &#8220;delayed&#8221; state, what means that it is waiting for something with a finite timeout?
</div></div><div class="thread-post"><h3 class="thread-post-title">Prevent from sleep when a task is in a blocked state with finite timeout</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 11, 2018</div><div class="thread-post-content">I&#8217;m a little confused.  Are you asking for a method of optionally selecting if the MCU should go into a sleep mode depending on the state of the application tasks?  If so, your third option does not look like a bad choice to me as it is simple.  Perhaps implement a &#8216;sleep manager&#8217; with which tasks can register.  You can keep a nesting count of whether to go to sleep &#8211; if a task does not want the system to enter a sleep state it calls a function to increment the nesting count, when it is happy for the system to go into a low power state it can call a function to decrement the nesting count.  Then the pre-sleep-processing macro need just check the nesting count &#8211; if it is zero it can enter a low power state otherwise it aborts going into a low power state.
</div></div><div class="thread-post"><h3 class="thread-post-title">Prevent from sleep when a task is in a blocked state with finite timeout</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kkoovalsky">kkoovalsky</a> on December 12, 2018</div><div class="thread-post-content">Yeah, I know that&#8217;s the simplest solution and works well but it&#8217;s intrusive. I need to remember all the time that my application can interfere with sleep so each task I create and run has to register in the sleep manager. It adds a lot of boilerplate.
Thanks, @Richard Barry, I will implement this in such a way as you suggested.
I hoped that there is some kind of way which allows to determine whether there is any task which waits for something with a finite timeout.
</div></div><div class="thread-post"><h3 class="thread-post-title">Prevent from sleep when a task is in a blocked state with finite timeout</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on December 12, 2018</div><div class="thread-post-content">I thought that the current tickless implementation did something like that as there is a check for how long until the next task will awake, so you don&#8217;t go into tickless if that is too soon. There is an upper limit to that, as I believe the tick rollover is considered such an event, but with a 32 bit tick that will be far enough in the future to generally not happen. IF you know the upper bound for your finite timeouts, just set that threshold above that value.
