In the Micrium uC/OS-II, which is the RTOS I used to work in my previous work, there is a pair of API functions  OSIntEnter and OSIntExit  intended to notify the Kernel about the interrupt being processed, I think in order to prevent Scheduler switching to some task during the interrupt and also to keep track of interrupt nesting. This example is taken from the Micrium web-site:
MyISR:
    Save CPU registers;
    OSIntEnter();               /* Or, OSIntNestingCtr++ */
        :
    Process ISR;
        :
    OSIntExit();
    Restore CPU registers;
    Return from interrupt;
The same approach exists in the Segger&#8217;s embOS. They have a similar API: OS<em>INT</em>Enter() and OS<em>INT</em>Exit()
I don&#8217;t see a similar API in the FreeRTOS (checked in the User Manual). If it is indeed true, would one here be so kind as to explain me why in the FreeRTOS I don&#8217;t need to notify the Scheduler about the interrupt being processed?
Thanks in advance for any help!
</div></div><div class="thread-post"><h3 class="thread-post-title">Interrupt Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 13, 2018</div><div class="thread-post-content">For most ports ( platforms ), FreeRTOS does not have an equivalent of <code>OSIntEnter()</code>/<code>OSIntExit()</code>
But for instance, for Atmel&#8217;s UC3A, there is such a thing:
~~~
<strong>attribute</strong>((naked)) void spi<em>0</em>interrupt<em>handler(void)
{
    portENTER</em>SWITCHING<em>ISR();
    {
        handler</em>spi(0);
    }
    portEXIT<em>SWITCHING</em>ISR();
}
~~~
The interrupt is declared as <code>naked</code>, i.e. without the usual save and restore context. In stead, the two macro&#8217;s take care of this.
Note that in this case, the return value of <code>handler_spi()</code> determines if a task switch is required ( register <code>r0</code> ).
For platforms using ARM, the interrupt handlers are simpler: they look like ordinary functions.
In all cases, within an interrupt handler, you can only use a subset of the FreeRTOS API&#8217;s, i.e. the ones that end with <code>FromISR</code>

</div></div><div class="thread-post"><h3 class="thread-post-title">Interrupt Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 13, 2018</div><div class="thread-post-content"><blockquote>
  So the question is how the Scheduler knows the code is running from interrupt?
  Isn&#8217;t there a danger that it will switch the interrupt to some task?
  Doesn&#8217;t the scheduler run from PendSV , so seemingly it can do this unwanted context switching.
</blockquote>
You do not have to worry about this. You just write the ISR code, keeping it as short as possible. If a context switch becomes necessary, it will take place <strong>after</strong> your ISR is ready.
<blockquote>
  Did you mean to say that I have to always call portENTER<em>SWITCHING</em>ISR()
  and portEXIT<em>SWITCHING</em>ISR inside my ISR?
</blockquote>
No, that is not necessary, unless you&#8217;re using a platform like Atmel UC3.
<blockquote>
  Also can I assume that this specific ISR API takes care to prevent the context
  switching while an ISR running is ongoing?
</blockquote>
As for ARM: this has to do with priorities: the priority of your ISR&#8217;s should higher than the priority of PendSV. If you have <code>configASSERT()</code>, the CPU priority will be checked in every API you call from an ISR.

Read more about configASSERT() <a href="https://www.freertos.org/a00110.html">here</a>.
<blockquote>
  But PendSV does have a higher priority&#8230;
</blockquote>
The higher the number, the lower the priority
<blockquote>
  As I understand the priority of PendSV is configurable
</blockquote>
Sure it is. You can use ISR&#8217;s with a lower priority as long as they do nothing with the FreeRTOS kernel.
<blockquote>
  but&#8230; doesn&#8217;t kernel itself takes care for that ? 
</blockquote>
Like I said, the kernel can check the current ISR priority during every <code>FromISR()</code> API.
This is being done for instance in <code>xQueueGenericSendFromISR()</code> when it calls the macro <code>portASSERT_IF_INTERRUPT_PRIORITY_INVALID()</code>.
<a href="https://www.freertos.org/RTOS-Cortex-M3-M4.html">The page</a> you mention is indeed very clear and helpful

</div></div><div class="thread-post"><h3 class="thread-post-title">Interrupt Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 16, 2018</div><div class="thread-post-content">In FreeRTOS there is a separate API for use in interrupts &#8211; namely the 
functions with &#8220;FromISR&#8221; in their name.  There are pros and cons to any 
approach of course, but FreeRTOS&#8217;s approach here means:
1) You do not need to tell the kernel you are in an interrupt, you just 
have to use the right API functions when you are.
2) The API functions can be tuned for use when inside interrupts &#8211; for 
example you can&#8217;t block inside an interrupt so there is no block time 
parameter to pass into an ISR safe function and no logic in the 
implementation of the ISR function to handle blocking.
3) The non ISR functions can also be tuned as they do not need to check 
to see if you are inside an interrupt before deciding what to do.
