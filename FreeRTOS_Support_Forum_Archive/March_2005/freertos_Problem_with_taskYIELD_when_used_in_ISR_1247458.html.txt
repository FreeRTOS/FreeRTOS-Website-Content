  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem with taskYIELD() when used in ISR</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on March 13, 2005</div><div class="thread-post-content">I am using the PIC port with version V2.6.0 of&nbsp; FreeRTOS.
I have an ISR handling all&nbsp; I2C activity.&nbsp; The application task places data in a queue then blocks on a semaphore waiting for the ISR to &#8216;give&#8217; it.&nbsp; The code at the end of the ISR is as follows:
if&#40; cSemaphoreGiveFromISR&#40; SSPdata.SSPSemaphore,&#40;&nbsp; portCHAR &#41; pdFALSE &#41; &#41;
&nbsp;&nbsp;&nbsp; taskYIELD&#40;&#41;;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 
I&#8217;ve discovered that the call to taskYIELD sometimes does not unblock the waiting task immediately,&nbsp; in this case the unblock occurs at the next Tick.&nbsp; With a slow tick rate this delay can, of-course, be significant. This seems to be due to the following:
If&nbsp; the scheduler is suspended when the ISR is invoked:
1.&nbsp; The call to taskYIELD&#40;&#41; at the end of the ISR saves the context and calls vTaskSwitchContext&#40;&#41;. This sees that the scheduler is suspended so returns to taskYIELD&#40;&#41; without a task switch. 
2&#46; When the ISR returns, and cTaskResumeAll&#40;&#41; executes, the task placed in the xPendingReadyList&nbsp; by the call to cSemaphoreGiveFromISR&nbsp; gets moved to the ready list. However, there is not a call to taskYIELD during cTaskResumeAll&#40;&#41;,&nbsp; unless one or more ticks were lost during the schedulers suspension. The result is that the context switch has to wait for the next tick.
If when cSemaphoreGiveFromISR&#40; &#41; is called, the scheduler is not suspended, then the task switch occurs immediately, as I would have expected.
By setting a port bit just before the call to cSemaphoreGiveFromISR&#40; &#41; , then having the&nbsp; blocked task reset it when it unblocks, I can see that the time spent with the port bit high varies by up to one complete tick.
I have a feeling that I&#8217;ve missed something important here, but despite my best efforts, can&#8217;t see what.
FreeRTOS is a very impressive piece of work, and must have required Herculean effort to get it to this stage.
Regards,
John Franklin.

&gt; vTaskSwitchContext&#40;&#41;. This sees that the scheduler is suspended so returns to
&gt; taskYIELD&#40;&#41; without a task switch.
This is correct.&nbsp; 
A good optimisation might be for cSemaphoreGiveFromISR&#40;&#41; not to return true if the scheduler is suspended.&nbsp; This would prevent the save/restore of the context and could be achieved with the following modification:
Look for the function cQueueSendFromISR&#40;&#41; in queue.c.&nbsp; In this function there is one place where pdTRUE can be returned.&nbsp; Change this to:
if&#40;&nbsp; ucSchedulerSuspended == pdFALSE &#41;
&nbsp;&nbsp;&nbsp; return pdTRUE;
else
&nbsp;&nbsp;&nbsp; return pdFALSE;
Two points to note:
1&#41; You would have to make ucSchedulerSuspended accessible.&nbsp; Currently it is declared static in tasks.c.
2&#41; I have not tested this&#33;
I will have a look at this possible optimisation, and if satisfactory include it in the V3.0.0 release.
A similar change could be made for the ISR queue receive function.
&gt; 2. When the ISR returns, and cTaskResumeAll&#40;&#41; executes, the task placed in the
&gt; xPendingReadyList&nbsp; by the call to cSemaphoreGiveFromISR&nbsp; gets moved to the ready
&gt; list. However, there is not a call to taskYIELD during cTaskResumeAll&#40;&#41;,&nbsp; unless
&gt; one or more ticks were lost during the schedulers suspension. The result is
&gt; that the context switch has to wait for the next tick.
If a task is unblocked while the scheduler is locked it is placed in the pending read list &#40;as you say&#41; and the context switch does not occur.&nbsp; A context switch cannot occur when the scheduler is suspended.
Here is another optimisation that will make the kernel behave how you want:
Go to the function cTaskResumeAll&#40;&#41; in tasks.c.&nbsp; Find the line:
if&#40; usCurrentNumberOfTasks &gt; &#40; unsigned portSHORT &#41; 0 &#41;
Within this if statement there is a while loop that takes tasks from the pending list and places them in the ready list.&nbsp; You will then see an if&#40;&#41; statement that catches up with any ticks that occurred while the scheduler was suspended.&nbsp;&nbsp; If any ticks were missed then a YIELD&#40;&#41; occurs &#8211; but what you want if for a YIELD&#40;&#41; to occur if either a tick was missed OR a task was removed from the pending list.&nbsp; This could be done thus:
&nbsp;&nbsp; if&#40; usCurrentNumberOfTasks &gt; &#40; unsigned portSHORT &#41; 0 &#41;
&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;portCHAR cYieldRequired = pdFALSE;&nbsp; // &lt;&lt;&lt;&lt;&lt; new variable.
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;/&#42; Move any readied tasks from the pending list into the 
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;appropriate ready list. &#42;/
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;while&#40; &#40; pxTCB = &#40; tskTCB &#42; &#41; listGET&#95;OWNER&#95;OF&#95;HEAD&#95;ENTRY&#40;&nbsp; &#40; &#40; xList &#42; &#41; &amp;xPendingReadyList &#41; &#41; &#41; &#33;= NULL &#41;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#123; 
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;vListRemove&#40; &amp;&#40; pxTCB-&gt;xEventListItem &#41; &#41;;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;vListRemove&#40; &amp;&#40; pxTCB-&gt;xGenericListItem &#41; &#41;;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;prvAddTaskToReadyQueue&#40; pxTCB &#41;;
&nbsp;&nbsp; 
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;// &lt;&lt;&lt;&lt; Added if statement.
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;if&#40; pxTCB-&gt;ucPriority &gt; pxCurrentTCB-&gt;ucPriority &#41;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#123;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;cYieldRequired = pdTRUE
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#125;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#125;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;/&#42; If any ticks occurred while the scheduler was suspended then
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;they should be processed now.&nbsp; This ensures the tick count does not
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;slip, and that any delayed tasks are resumed at the correct time. &#42;/
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;if&#40; ucMissedTicks &gt; 0 &#41;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#123;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;cYieldRequired = pdTRUE;&nbsp; // &lt;&lt;&lt;&lt;&lt; New line
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;while&#40; ucMissedTicks &gt; 0 &#41;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#123;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;vTaskIncrementTick&#40;&#41;;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#8211;ucMissedTicks;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#125;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#125;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;if&#40; cYieldRequired &#41;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#123;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;/&#42; As we have processed some ticks it is appropriate to yield
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;to ensure the highest priority task that is ready to run is
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;the task actually running. &#42;/
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;cAlreadyYielded = &#40; signed portCHAR &#41; pdTRUE;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;taskYIELD&#40;&#41;;
&nbsp;&nbsp;&nbsp; &#95;&#95;&#95;&#95;&#125;
&nbsp;&nbsp; &#125;
This way the cYieldRequired flag gets set to true if EITHER a tick was missed OR a task with higher priority than the current task was removed from the pending list.
Hope this makes sence &#8211; I have put in all the &#95;&#95;&#95;&#95;&#95; to try and retain the indentation.
Again I have not tried this but it seems to be another good candidate for the V3.0.0 release.
Let me know what you think or if you have any problems.

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with taskYIELD() when used in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on March 18, 2005</div><div class="thread-post-content">Hello Richard.
Apologies for the delay. As you will see I have been busy. I implemented the changes to&nbsp;&nbsp; 
 cTaskResumeAll&#40;&#41;, as per your suggestions. This did indeed produce the required behaviour, i.e. the waiting task is always woken immediately on return from the ISR rather than having to wait for the next Tick. However, as with my own modification to cTaskResumeAll&#40;&#41;, I started getting erratic behaviour in my application, and occasional crashes. The symptoms were seemingly almost random. Minor unrelated changes to my application code would apparently cure the problem.
 I have finally tracked down the cause which, surprisingly, appears to be a bug in the C18 v2.20 compiler and nothing to do with the freeRTOS changes. The compiler produced code that precedes the invocation of a function was, sometimes, incorrectly pushing the function parameters onto the stack. The code did not take care of&nbsp; the situation in which the stack pointer crosses from one bank to the next, i.e. only the lsb of the stack pointer was being incremented. This is in spite of the memory model being selected as multi-bank..&nbsp; I tried a simple demo app on another PC just to check that the MPLAB settings hadnt been screwed up in some way, but with exactly the same result. Moving to the latter C18 version&nbsp; v2.40 cured the problem. Any code modifications that slightly altered the placing of the stack in ram could push the stack pointer away from a stack boundary so masking the problem and explaining the apparent random behaviour.
So in conclusion, the modifications to cTaskResumeAll&#40;&#41;&nbsp; seem to work fine. 
Thanks again for the help.
Regards,
John Franklin.
