  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Usage of configMAX_SYSCALL_INTERRUPT_PRIORITY on STM32 Cortex M3</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gourmetsel">gourmetsel</a> on August 5, 2016</div><div class="thread-post-content">I&#8217;m using an STM32F10 microcontroller with FreeRTOS V8.2.3 port for the Cortex M3. The microcontroller has four priority bits implemented. I understood that the highest priority of any interrupt using system calls is defined by configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY. FreeRTOS expects this priority to be stored in the upper nibble of configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY for this specific core.
configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY will be written to the BASEPRI register to enter a critical section and zero will be written to it when exiting the critical section (basically this disables the function of BASEPRI). This is the reason why configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY shall never be set to zero.
I saw in xPortStartScheduler in port.c that configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY is explicitly asserted to being non-zero:
configASSERT( configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY );
I just wanted to share that it might make sense to include the position of the priority bits of the particular core into this assertion. For the microcontroller I&#8217;m using in this case, I could set configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY to 0x0F, not get the assertion to fail, but still break the critical section mechanism.
In this case the assert could look like:
configASSERT( configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY &amp; CM3</em>PRIORITY_MASK );
where CM3<em>PRIORITY</em>MASK is 0xF0.
Matthias
</div></div><div class="thread-post"><h3 class="thread-post-title">Usage of configMAX_SYSCALL_INTERRUPT_PRIORITY on STM32 Cortex M3</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 5, 2016</div><div class="thread-post-content">Thank you for the interesting input.
There is no real portable way of achieving this without adding in 
additional dependencies on the FreeRTOSConfig.h values, as currently 
only configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY and 
configKERNEL</em>INTERRUPT_PRIORITY are mandated.  However, the code does 
manually check the number of priority bits implemented by testing the 
hardware directly &#8211; so the assert could then be moved to that part of 
the code (where the number of bits is known).
