</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_FD_SET on a Listening TCP Socket</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 7, 2016</div><div class="thread-post-content">A deferred interrupt handler is a task that is used to perform what 
would otherwise be performed in an interrupt service routine.
Often an Ethernet interrupt wants to allocate a buffer.  Depending on 
the buffer allocation scheme it might be that the buffer cannot be 
allocated from the interrupt, so the interrupt handler just unblocks a 
high priority task, and the buffer allocation and other interrupt 
processing is then performed in the task.
The idea is a deferred interrupt handling task is blocked to wait for an 
interrupt then, when an interrupt occurs, the interrupt handler unblocks 
the task that is waiting and returns directly to that task so the 
interrupt processing occurs contiguous in time just as if it had been 
performed in the interrupt itself.  (the interrupt handler interrupts a 
lower priority application task, and returns to a higher priority 
deferred interrupt handler task.
Search for &#8216;deferred&#8217; on the following page: 
http://www.freertos.org/FreeRTOS-Plus/FreeRTOS<em>Plus</em>TCP/Embedded<em>Ethernet</em>Porting.html

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_FD_SET on a Listening TCP Socket</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joehinkle">joehinkle</a> on August 9, 2016</div><div class="thread-post-content">I found the issue.
At this ime, I would call it a stack issue related to conflicting config options.
If the user has enabled config setting (as I had) ipconfigTCP<em>HANG</em>PROTECTION, the the new socket created by the listen is NOT assigned to the listening sockets&#8217;s &#8220;pxPeerSocket&#8221;.
A select on a listening socket for eSELECT_READ is not capable because the listening&#8217;s socket &#8220;pxPeerSocket&#8221; is not set.
Root-cause of my issue &#8230; FreeRTOSIPConfig.h CAN NOT have option &#8220;ipconfigTCP<em>HANG</em>PROTECTION&#8221; enabled and expect select to respond to a &#8220;eSELECT_READ&#8221; on  a listening socket.
Dis-Abled option ipconfigTCP<em>HANG</em>PROTECTION &#8212; it works as expected.
So, I would suggest you have an issue with the implementation of option ipconfigTCP<em>HANG</em>PROTECTION as it breaks the select capability.
Joe

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_FD_SET on a Listening TCP Socket</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on August 11, 2016</div><div class="thread-post-content">About &#8216;ipconfigTCP<em>HANG</em>PROTECTION&#8217; : I don&#8217;t think there is an issue with the anti-hanging protection. There is indeed a difference in behaviour, and for good reasons:
~~~~
<h1>if( ipconfigTCP<em>HANG</em>PROTECTION != 0 )</h1>
<pre><code>/* You will only see a new socket as soon as the 3-way hand-shake is ready. */
</code></pre>
<h1>else</h1>
<pre><code>/* You will receive a new socket immediately after its creation,
i.e. after the first SYN. */
</code></pre>
<h1>endif</h1>
~~~~
With anti-hanging protection, the IP-stack takes care of the new socket until it is fully connected. In case it fails, the socket will be closed by the stack. It will have a timer running, so incase the peer dies, the socket will be closed by the stack.
Without the anti-hanging protection, the application is made responsible for closing the new socket in case the 3-way handshake was not successful.
With &#8216;ipconfigTCP<em>HANG</em>PROTECTION == 0&#8242; your select() will return a READ event, and accept() does succeed, but the 3-way handshake is still failing.
Later we found why the handshake didn&#8217;t work: there was a misconception about <code>xNetworkInterfaceOutput()</code> should work.
~~~~
BaseType<em>t xNetworkInterfaceOutput(
    NetworkBufferDescriptor</em>t * const pxNetworkBuffer,
    BaseType_t xReleaseAfterSend )
~~~~
If <code>xReleaseAfterSend</code> is false, it means that the NetworkBuffer is passed as read-only. Once the function <code>xNetworkInterfaceOutput()</code> returns, the NetworkBuffer may not be accessed any more.
If <code>xReleaseAfterSend</code> is true, the ownership of the NetworkBuffer is passed to the driver and the driver may (must) release the buffer after using it. It may still be accessed after returning from the function.
A driver that works with so-called zero-copy transmissions will define:
~~~~
<h1>define ipconfigZERO<em>COPY</em>TX_DRIVER                ( 1 )</h1>
~~~~
These drivers will always be called with <code>xReleaseAfterSend</code> == true. The Network Buffers will be passed to DMA. When DMA is ready transmitting a buffer, it shall be released by the driver.
