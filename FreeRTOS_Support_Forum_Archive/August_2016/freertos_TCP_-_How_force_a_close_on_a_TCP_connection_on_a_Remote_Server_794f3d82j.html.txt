Looking at the Wireshark data, +TCP replies with a RST, ACK to the server&#8217;s ACK.
+TCP is not using the same SEQ that the server provided in the ACK for the RST reply.  Is that why the server is ignoring the RST and keeps the connection open?

</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP &#8211; How force a close on a TCP connection on a Remote Server</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 20, 2016</div><div class="thread-post-content">Hi Joe,
If you look in FreeRTOS_Sockets.c, you will find the implementation of 
prvGetPrivatePortNumber(), and there is a comment in the function &#8220;This 
needs to be randomised&#8221; [at least, you will see the comment if you are 
using the head revision code rather than the last release code].
The function provides port numbers between 
socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER and 
socketAUTO<em>PORT</em>ALLOCATION<em>MAX</em>NUMBER, with the first call always 
returning port number socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER.
You can update this function, and we can do here as well, so that on the 
first call it instead chooses a random number between 
socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER and 
socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER.

</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP &#8211; How force a close on a TCP connection on a Remote Server</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on August 20, 2016</div><div class="thread-post-content"><blockquote>
  If +TCP had replied with the Server&#8217;s SEQ instead of it&#8217;s
  connection SEQ &#8212; would THAT have terminated the connection?
</blockquote>
Tomorrow when I&#8217;m not tired I will look at your questions again.
But when a RST is sent, the actual ACK  and SEQ numbers do no matter.
A TCP connection is identified by 4 &#8220;numbers&#8221; : source IP address + port number, and the target IP address and port number. If a sending host receives a RST matching with these 4 numbers, the socket owner must see an error like <code>ECONNRESET</code>
Applications like browsers on any OS will surely behave correctly in this respect.
The correct way to actively shutdown a +TCP connection is as follows:
~~~~
    FreeRTOS<em>shutdown( xSocket );
    for( ;; )
    {
        xResult = FreeRTOS</em>recv( xSocket, ucBuffer, sizeof( ucBuffer ), 0 );
        if( ( xResult &lt; 0 ) &amp;&amp; ( xResult != -pdFREERTOS<em>ERRNO</em>EWOULDBLOCK ) )
        {
            FreeRTOS_closesocket( xSocket );
            xSocket = NULL;
            break;
        }
    }
~~~~
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP &#8211; How force a close on a TCP connection on a Remote Server</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 21, 2016</div><div class="thread-post-content">Correction!   My post here https://sourceforge.net/p/freertos/discussion/382005/thread/794f3d82/#3cf0/39ac was not accurate.  The first port number used is already a randomly selected port number between socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER and socketAUTO<em>PORT</em>ALLOCATION<em>END</em>NUMBER.  This is because FreeRTOS_IPInit() calls vNetworkSocketsInit(), and vNetworkSocketsInit() uses ipconfigRAND32() to randomise the first private port number used.  This does however rely on ipconfigRAND32() operating correctly.  If you do not define ipconfigRAND32() in FreeRTOSIPConfig.h it will get defaulted to just calling the rand() function provided by your C run time library &#8211; but you need to call srand() with appropriate entropy to seed the random number.

</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP &#8211; How force a close on a TCP connection on a Remote Server</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kenchang1">kenchang1</a> on November 10, 2017</div><div class="thread-post-content">I have encountered this issue too. The usage of random ports is a workaround, but the real solution is described in the RFC793 page 34, figure 10.
In this case the SEQ number of the RST packet does matter. It has to be equal to the ACK number of the server&#8217;s reply. If you do that the server will close it&#8217;s connection and FreeRTOS+TCP can connect  (with the same local port) to that remote port again in the next connect attempt.
So, this is my fix in the +TCP stack:
In file FreeRTOS<em>TCP</em>IP.c, line 2335, function prvHandleSynReceived(), I have added 1 line of code:
<code>pxTCPWindow-&gt;ulOurSequenceNumber = FreeRTOS_ntohl( pxTCPHeader-&gt;ulAckNr );</code>
This seems to work, the server will close it&#8217;s connection and I can connect to it again.
Please let me know whether this is the right way to fix it. Could there be side effects? Because ulOurSequenceNumber has suddenly changed?
Addtional comment: 
Line 2332: <code>pxTCPHeader-&gt;ucTCPFlags |= ipTCP_FLAG_RST;</code> should be
<code>pxTCPHeader-&gt;ucTCPFlags = ipTCP_FLAG_RST;</code>
Correct?
regards,
Ken
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP &#8211; How force a close on a TCP connection on a Remote Server</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 10, 2017</div><div class="thread-post-content">Ken, thank you very much for noticing and reporting this!
Here below is a patch that sets both the Sequence and the ACK number as expected by the host
( other RST packets are being sent with the correct values. In those cases the SEQ and ACK are just swapped ).
In <code>FreeRTOS_TCP_IP.c</code>, in function <code>prvHandleSynReceived()</code>, around line 2331 :
~~~
         FreeRTOS<em>debug</em>printf( ( &#8220;%s: flags %04X expected, not %04Xn&#8221;,
             pxSocket->u.xTCP.ucTCPState == eSYN<em>RECEIVED ? &#8220;eSYN</em>RECEIVED&#8221; : &#8220;eCONNECT<em>SYN&#8221;,
             usExpect, ucTCPFlags ) );
         vTCPStateChange( pxSocket, eCLOSE</em>WAIT );
+
+        /* Send RST with the expected sequence numbers, otherwise it will be ignored. */
+        pxTCPWindow->ulOurSequenceNumber = FreeRTOS_htonl( pxTCPHeader->ulAckNr );
+        pxTCPWindow->rx.ulCurrentSequenceNumber = ulSequenceNumber;
+
&#8211;        pxTCPHeader->ucTCPFlags |= ipTCP_FLAG_RST;
+        pxTCPHeader->ucTCPFlags = ipTCP_FLAG_RST;
         xSendLength = ( BaseType_t ) ( ipSIZE_OF_IPv4_HEADER + ipSIZE_OF_TCP_HEADER + uxOptionsLength );
         pxTCPHeader->ucTCPOffset = ( uint8_t )( ( ipSIZE_OF_TCP_HEADER + uxOptionsLength ) &lt;&lt; 2 );
~~~
Still I would like to urge users to use a random value for <code>srand()</code>, especially while you are testing, experimenting, and doing many reboots.
But with the patch here above, it will be easier to detect the problem: the socket will get the <code>eCLOSE_WAIT</code> status much quicker.
Thanks again.
