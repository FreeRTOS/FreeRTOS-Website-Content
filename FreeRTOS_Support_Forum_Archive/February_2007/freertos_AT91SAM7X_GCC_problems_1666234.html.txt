  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AT91SAM7X + GCC problems</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 7, 2007</div><div class="thread-post-content">I&#8217;m having a very difficult time getting FreeRTOS running on the Atmel AT91SAM7X-EK evaluation board.&nbsp; I&#8217;ve got FreeRTOS 4.1.3, GNUARM 4.10, and newlib, and am unable to get either the lwIP&#95;Demo&#95;Rowley or even a simple light blinker to work.
After adding a syscalls.c &#40;stubbed, except for &#95;sbrk, which is implemented as per Red Hat&#8217;s documentation&#41;, the lwIP demo compiles, but crashes with an undefined instruction in udp&#95;recv.
A simple application &#40;full code available on request&#41; does better, but exhibits strange behavour: if I just let the code run, it dies with a data abort after a few ticks have elapsed.&nbsp; Depending on what debug stuff I&#8217;ve put in, it either dies towards the beginning of portRESTORE&#95;CONTEXT, as called from vPreemptiveTick, or towards the end of vTaskSwitchContext, at the listGET&#95;OWNER&#8230; line.
In both cases, it looks like the pxCurrentTCB variable is being set to something random &#40;in the former crash, it&#8217;s 0xa5a5a5a5, which is suspiciously like some guard value, and in the latter case it&#8217;s in the high 0xb000s&#41;.
That&#8217;s not the weird part, though.&nbsp; If I attach a JTAG debugger &#40;SAM-ICE, with Segger&#8217;s GDB server&#41;, and set a breakpoint in vPreemptiveTick, the code runs fine if I hit &quot;continue&quot; after the breakpoint.&nbsp; On the other hand, even with the debugger attached, and no breakpoint, I get the same crash.
I scattered various debugging traces throughout the code, looking for a corrupted pxCurrentTCB.&nbsp; What&#8217;s weird is that in a few cases, including the trace statements made everything work&#33;
Compiling with -fomit-frame-pointer made the code go longer &#40;about 15 ticks&#41;, but it still crashes.
Any help would be appreciated.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7X + GCC problems</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 7, 2007</div><div class="thread-post-content">&gt; After adding a syscalls.c &#40;stubbed, except for &#95;sbrk, which is implemented as
&gt; per Red Hat&#8217;s documentation&#41;, the lwIP demo compiles, but crashes with an undefined
&gt; instruction in udp&#95;recv.
I don&#8217;t know why you are adding syscalls.c and a different newlib.&nbsp; The demo should compile with the standard GNUARM installation, with no additions required.
As per the WEB docs &#8211; I have only tested this using a Windows host.&nbsp; Are you using a Linux distribution?&nbsp; Maybe there are some differences?
&gt; A simple application &#40;full code available on request&#41; does better, but exhibits
&gt; strange behavour: if I just let the code run, it dies with a data abort after
&gt; a few ticks have elapsed.&nbsp; Depending on what debug stuff I&#8217;ve put in, it either
&gt; dies towards the beginning of portRESTORE&#95;CONTEXT, as called from vPreemptiveTick,
&gt; or towards the end of vTaskSwitchContext, at the listGET&#95;OWNER&#8230; line.
The simplest task would be something along the lines of:
void vTask&#40; void &#42; pvParaemters &#41;
&#123;
&#95;&#95;&#95;&#95;for&#40; ;; &#41;
&#95;&#95;&#95;&#95;&#123;
&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;vTaskDelay&#40; 500 &#41;;
&#95;&#95;&#95;&#95;&#95;&#95;&#95;&#95;vParTestToggleLED&#40; 0 &#41;;
&#95;&#95;&#95;&#95;&#125;
&#125;
Then in main&#40;&#41;
int main&#40; void &#41;
&#123;
&#95;&#95;&#95;&#95;prvSetupHardware&#40;&#41;;
&#95;&#95;&#95;&#95;/&#42; Setup the IO required for the LED&#8217;s. &#42;/
&#95;&#95;&#95;&#95;vParTestInitialise&#40;&#41;;
&#95;&#95;&#95;&#95;xTaskCreate&#40; vTask, &quot;TASK&quot;, configMINIMAL&#95;STACK&#95;SIZE &#42; 2, NULL, 1, NULL &#41;;
&#95;&#95;&#95;&#95;vTaskStartScheduler&#40;&#41;;
&#95;&#95;&#95;&#95;return 0;
&#125;
Then &#42;&#42;very importantly&#42;&#42; set configUSE&#95;IDLE&#95;HOOK to 0 in FreeRTOSConfig.h.&nbsp; If you do not do this the program will crash as the idle hook will attempt to access the USB peripheral which is not setup in this simple case.
Is this the sort of demo you created?&nbsp; If not, can you try this code?
&gt; In both cases, it looks like the pxCurrentTCB variable is being set to something
&gt; random &#40;in the former crash, it&#8217;s 0xa5a5a5a5, which is suspiciously like some
&gt; guard value, and in the latter case it&#8217;s in the high 0xb000s&#41;
0xa5a5a5a5 is the value that the stack is filled with when the task is created.
Make sure you are using the startup files and linker script that comes with the demo.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7X + GCC problems</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 7, 2007</div><div class="thread-post-content">&gt; I don&#8217;t know why you are adding syscalls.c and a different newlib. The demo should compile
&gt; with the standard GNUARM installation, with no additions required. 
The GNUARM build of newlib supplies its own syscalls &#40;read, write, etc&#41;, which assume the presence of an Angel&#95;SWI monitor.&nbsp; Since neither FreeRTOS nor I provide one of these, the syscalls will fail to function.&nbsp; For what it&#8217;s worth, my build of newlib was compiled with 
../newlib-1.14.0/configure &#8211;target=arm-elf &#8211;prefix=/var/gnuarm 
&nbsp; &#8211;with-float=soft &#8211;disable-newlib-supplied-syscalls &#8211;enable-multilib
This is identical to the GNUARM build, except for the addition of the &#8211;disable-newlib-supplied-syscalls option.&nbsp; I eventually wish to provide my own versions of read, write, and so forth, so I can, say, provide a debugging channel over the serial port, or a flash-based file system, so this is important to me.
On a lark, I re-installed GNUARM, which also installed their build of the library.&nbsp; At that point, I was able to get both the shortened demo that you discuss, as well as my own &#40;similar&#41; project working.&nbsp; &#42;However&#42;, I can&#8217;t use sprintf: if I make even a single call to sprintf, for some reason, the timer ticks stop appearing.&nbsp; This is true for my own demo, as well as for the stripped-down version &#40;blinking LED only&#41; of the lwIP demo.
I&#8217;m using Windows, for what it&#8217;s worth.
I can provide all the source for both my demo and the stripped down lwIP demo, if it would make things easier.
Right now, I&#8217;m re-building newlib using the exact specifications provided on the GNUARM site, and I will test whether &#42;this&#42; build works.
Thanks for your help so far.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7X + GCC problems</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 8, 2007</div><div class="thread-post-content">Just my very humble opinion but it sounds like your stack is too small.&nbsp; Calling sprintf eats up lots of stack space so you may be overflowing the stack.&nbsp; You can try doubling or tripling your stack size and see if that clears things up.&nbsp; Then you can check how much stack is being used and adjust it accordingly.&nbsp; 
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7X + GCC problems</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hockeymonk">hockeymonk</a> on February 10, 2007</div><div class="thread-post-content">Also try reducing the FreeRTOS heap size in FreeRTOSConfig.h. I reduced configTOTAL&#95;HEAP&#95;SIZE from 22000 to 15000 and lwIP no longer crashes. I think this is related to lwIP memory usage being outside the control of FreeRTOS memory management. Depending on your user task you may need to prevent FreeRTOS from overrunning the lwIP TCB structures.
Just a thought&#8230;
