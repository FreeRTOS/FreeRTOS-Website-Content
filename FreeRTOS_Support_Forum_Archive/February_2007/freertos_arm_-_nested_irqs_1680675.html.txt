&#40;a&#41; you depend on the interrupt controller to prioritize IRQs
&#40;b&#41; and you re-enable IRQs within an IRQ.
here&#8217;s the short problem description:
freeRTOS, at startup runs in SVC mode, and switches to SYS mode at the first task.
The ARM &#8211; unlike other CPUs does not automatically push anything on the stack.
This is also true of IRQs, ARM instead switches to IRQ mode.
The current CPSR is saved, and the return address+4 is put into the IRQ-R14 &#40;LR&#41; 
register. If a second higher priority IRQ occurs, IRQ-R14 is overwritten.
Yes, one could make this work &#8211; writing hand crafted IRQ routines in ASM but 
it is not possible to &#95;reasonably&#95; write any IRQs in C using this approach.
&#45;&#8212;&#8212;&#8212;&#8212;&#8212;-
Here&#8217;s the scenario where I see it failing:
0&#41; Initial state: No irqs pending, in &quot;system mode&quot; tasks running.
1&#41; IRQ occurs.
2&#41; CPU switches to IRQ-MODE, 
&nbsp;&nbsp;&nbsp;&nbsp; IRQ-R14 holds return address.
&nbsp;&nbsp;&nbsp;&nbsp; SPSR holds saved PSR value.
3&#41; Code saves some registers, and for example
&nbsp;&nbsp;&nbsp; does &quot;sub lr,lr,&#35;4&quot;
4&#41; &#8212; NOTE &#8212; Nowhere do I see the code leave 
&nbsp;&nbsp; ARM&#95;ISR mode that is the fundamental problem&#33;

&nbsp;&nbsp; Example: Demo/ARM7&#95;LPC2106&#95;GCC/serial/serialISR.c
&nbsp;&nbsp; They often call other C functions in the standard way.
6&#41; Remember: the chip has a priority based IRQ controller.
&nbsp;&nbsp; Assume that a low-priority IRQ has just occured.
&nbsp;&nbsp; And &#8211; another HIGH PRIORITY irq is about to occur.
&nbsp;&nbsp; To &quot;nest&quot; interrupts you:
&nbsp;&nbsp; &#40;a&#41; allow the IRQ controller to manage priorities
&nbsp;&nbsp; &#40;b&#41; you then just re-enable IRQs in the CPU early in the IRQ routine.
&nbsp;&nbsp; ie: Often you handle the critical stuff as fast as possible
&nbsp;&nbsp; then re-enable IRQs, and take care of the time consuming 
&nbsp;&nbsp; part later, but as part of the same interrupt.
&nbsp;&nbsp; 
7&#41; During normal function calls the CPU, and the compiler 
&nbsp;&nbsp; make use of R14&#40;lr&#41; as the return address.
&nbsp;&nbsp; But remember this question: Which R14 is it? I direct 
&nbsp;&nbsp; your attention to the ARM&#95;ARM book 2.3 Registers.
&nbsp;&nbsp; Remember: &#8216;hidden&#8217; functions also include the

&nbsp;&nbsp; helper compiler routine. 
&nbsp;&nbsp; Since the CPU is in IRQ mode, R14/LR =&gt; IRQ&#95;R14.
&nbsp;&nbsp; &#91;The same can be said about R13/SP&#93;
&nbsp;&nbsp; The contents of the LR register &#40;depending on the
&nbsp;&nbsp; optimization level, type of function, etc&#41; holds
&nbsp;&nbsp; the return address back to your code, or is often
&nbsp;&nbsp; used as an extra temp-register in between calls.
9&#41; The plan here is: &quot;nested interrupts&quot;.
&nbsp;&nbsp; The IRQ has not been ACKed in the IRQ controller.

&nbsp;&nbsp;&nbsp; PROBLEM: remember: The CPU is still in IRQ MODE

&nbsp;&nbsp;&nbsp; &#91;or something else, R13/SP is a problem also&#93;
11&#41; PROBLEM: the current &quot;r14&quot; &#8211; is return address

The code as per the FreeRTOS.org download does not implement nesting of interrupts for the ARM &#8211; I have an example somewhere that implements it, but have never had the need to use it in anger.
The idea is to process interrupts at the task level &#8211; within handler tasks.&nbsp; The ISR grabs the data from the interrupting peripheral, passes the data to the handler task, clears the interrupt, and nothing else.&nbsp; This is therefore very fast negating the need for interrupt nesting.&nbsp; The handler task will generally be created at a priority higher than the application tasks, and, as the handler is woken from within the ISR, execution passes directly from the exiting ISR to the handler task &#40;contiguous in time as if it were all done in the ISR&#41;.&nbsp; The processing then occurs at the task level with interrupts enabled.&nbsp; Handler tasks can be assigned a priority to reflect their relative priority in the system proving a more flexible approach than many hardware interrupt prioritisation systems &#40;some architectures, not others&#41;.&nbsp; I believe from reading the FAQ that this is what the ARM RTOS guys suggest also.
The FreeRTOS.org demos include two methods of entering interrupt routines.&nbsp; The first is to save and restore the context on entry the the ISR function &#8211; with each ISR vectored directly from the interrupt controller.&nbsp; The second is to save and restore the context from a single common interrupt entry point &#8211; then call the relevant handler having inspected the interrupt controller to see which handler to execute.&nbsp; To nest interrupts the second method is required so you can switch to user/system mode prior to calling the interrupt function itself.&nbsp; Both methods have pros and cons &#40;what doesn&#8217;t&#41;.&nbsp; The two biggest problems with the latter method is 1&#41; non deterministic stack usage, 2&#41; saving/restoring the context even when you don&#8217;t need to removing any performance gains you might expect from nesting interrupts.&nbsp; It pro is the simplicity to code and reduced code size.
&gt; 5&#41; ISR routines are typically written in C these days.
&gt;&nbsp;&nbsp; Example: Demo/ARM7&#95;LPC2106&#95;GCC/serial/serialISR.c
&gt;&nbsp;&nbsp; They often call other C functions in the standard way.
Take a look at the STR9 demo for the alternative method mentioned above &#40;this does not do the mode switching&#41;.
&gt;&nbsp;&nbsp; To &quot;nest&quot; interrupts you:
&gt;&nbsp;&nbsp; &#40;a&#41; allow the IRQ controller to manage priorities
&gt;&nbsp;&nbsp; &#40;b&#41; you then just re-enable IRQs in the CPU early in the IRQ routine.
You must switch to user/system mode if you want to re-enable interrupts.
&gt;&nbsp;&nbsp; ie: Often you handle the critical stuff as fast as possible
&gt;&nbsp;&nbsp; then re-enable IRQs, and take care of the time consuming 
&gt;&nbsp;&nbsp; part later, but as part of the same interrupt.
I would disagree.&nbsp; Without a kernel I might be forced to do it in the interrupt.&nbsp; With a kernel I would not do any consuming in an interrupt.&nbsp;&nbsp; Not to say one way is more correct than another.
&gt; 
&gt; 8&#41; In this example &#8211; say your C code was dividing
&gt;&nbsp;&nbsp; something, and was in the middle of the &#8216;divide&#8217;
&gt;&nbsp;&nbsp; helper compiler routine. 
I would not recommend performing a division in an ISR, but am happy for others to disagree ;-&#41;

There are some significant benefits to using the prioritised hardware interrupt controller, e.g. the AIC on the AT91 series.
Logically, anything you can do with nested prioritised hardware interrupts you can also do with nested prioritised tasks and unnested interrupts.&nbsp; However, it&#8217;s always going to be perform worse &#40;more latency, more jitter, less throughput&#41;.&nbsp; Now I would be the first person to say that if you are only using 10% of your CPU and your shortest hard deadline is 100ms then you might as well use the easy unnested interrupt solution.
But if you are using 95% of your CPU and have deadlines that are just 5us away, you cannot afford to go that way.
Also, you have two classes of ISR &#8211; those that must synchronise with a task &#40;sem/queue&#41; and those that just need to run to service hardware but don&#8217;t synchronise with tasks &#40;perhaps they just update shared memory, for example&#41;.&nbsp; Often ISRs in the latter category have the shortest deadlines.
Coarsely, you can assume that if your shortest hard deadline for reacting to an IRQ is &lt;= 10xcost&#40;context switch&#41; you should really be thinking about using prioritised nested interrupts rather than tasks.
As a compromise if all your short deadlines can be serviced by non-synchronising ISRs, you could use the FIQ context to implement those.&nbsp; But there will be cases where FIQ is in use for other functions or where you must synchronise and so cannot use FIQ &#40;no path from FIQ to FreeRTOS at present&#41;.
So let&#8217;s assume it&#8217;s worthwhile to support IRQ nesting for at least some of the community, what does it take to do it?
&#40;1&#41; The CPSR&#95;irq.I bit is cleared as soon as possible after an IRQ is taken.
&#40;2&#41; The CPSR&#95;swi.I bit is cleared as soon as possible after an SWI is taken, i.e. before it considers whether a new task should be scheduled.
&#40;3&#41; Non-synchronising ISRs can still participate in the nesting scheme and can save and restore only that minimum state that they will corrupt.
&#40;4&#41; Synchronising ISRs do not need to worry about re-entrancy of the sanctioned FreeRTOS ISR API calls.
&#40;5&#41; Use the available vectoring hardware to prioritise interrupts and generate the vector of the ISR to take.
&#40;6&#41; Make sure that the enabling of IRQ is in control of the ISR, not generic &#8211; ISRs sometimes have other stuff that must be handled first, and if you don&#8217;t enable it, you revert to normal non-nested ISR configuration.
First off, you need the right hardware &#8211; the AT91SAM926x has a Advanced Interrupt Controller &#40;AIC&#41;, which is also present on other AT91 ARM designs I think.&nbsp; I think the LPCxxxx parts have a VIC instead which does much the same thing.&nbsp; If all you have is a single IRQ line &#40;i.e. a raw ARM chip&#41;, then you need to write a s/w emulation of something like the AIC and run it as a preamble to the IRQ handler &#8211; I am not going to get into that here&#33;
The challenges in supporting nested interrupts are multiple interrupted contexts and switching between them in a well ordered way:
Task &#40;mode User or System, R0-R12, SP&#95;user, LR&#95;user, CPSR&#95;user&#41; &#8211; this is where the current active task has its state &#40;we don&#8217;t care about anything but the active task, obviously&#41;.
taskYIELD &#40;mode Supervisor, R0-R12, SP&#95;svc, LR&#95;svc, SPSR&#95;svc and CPSR&#95;svc&#41; &#8211; you jump onto this one when you use SWI to request a taskYIELD and maybe this could be used for other SWI accessed functions too one day.
IRQ &#40;mode IRQ, R0-R12, SP&#95;irq, LR&#95;irq, SPSR&#95;irq and CPSR&#95;irq&#41; &#8211; you jump this one whenever an IRQ is taken.
Note: IRQ can interrupt either SVC or User/System modes or IRQ modes.&nbsp; When IRQ interrupts IRQ there is obviously only one SP&#95;irq, LR&#95;irq, SPSR&#95;irq and CPSR&#95;irq, so care needs to be taken to make sure these are shared properly.
A global variable xExceptionNesting will be initialised to zero.
Exception entry will be:
if&#40;xExceptionNesting++ == 0&#41;
&#123;
&nbsp; // Outer most exception.
&#42; push LR&#95;exception, R0-R12, SP&#95;user, LR&#95;user, SPSR&#95;exception &#40;==CPSR&#95;user&#41; and ulCriticalNesting count onto the task stack.
&#42; save the resulting top of stack pointer to the current TCB.
&#42; clear the global xTaskWokenByException
&#125;
else
&#123;
 // Nested exception.
&#42; push LR&#95;exception, SPSR&#95;exception to exception stack.
&#42; push any of R0-R12 that the exception handler will clobber to the exception stack.
&#125;
&#42; run any ISR-specific code that must be run with interrupts off.
&#42; clear CPSR&#95;exception.I flag to enable nested exceptions.
&#42; runs any ISR-specific code that can be run with interrupts on.
// The global xTaskWokenByException gets updated by calls to &#42;FromISR&#40;&#41; automatically, 
// and these are either rewritten to be re-entrant or to protect critical sections with 
// disable/enable IRQ code.
&#42; set CPSR&#95;exception.I flag to disable nested exceptions.
if&#40;&#8211;xExceptionNesting &#33;= 0&#41;
&#123;
&nbsp; // Nested exception exit
&#42; pop any of R0-R12 that the exception handler saved from the exception stack.
&#42; pop SPSR&#95;exception and LR&#95;exception from the exception stack.
&#125;
else
&#123;
&nbsp; // Outer most exception exit
&#42; examine the global xTaskWokenByException and if set, call vTaskSwitchContext to update the current TCB.
&#42; recover the top of stack pointer from the current TCB.
&#42; recover LR&#95;exception, R0-R12, SP&#95;user, LR&#95;user, SPSR&#95;exception &#40;==CPSR&#95;user&#41; and ulCriticalNesting count from the task stack.
&#125;
&#42; return from exception &#40;to task or outer exception&#41; using appropriate manipulation of LR&#95;exception.

</div></div><div class="thread-post"><h3 class="thread-post-title">arm &#8211; nested irqs</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/quantum-leaps">quantum-leaps</a> on March 5, 2007</div><div class="thread-post-content">Before re-inventing the wheel, here are some resources relevant to this discussion:
1&#46; The NXP &#40;former Philips&#41; application note “Nesting of Interrupts in the LPC2000”
&#40;http://www.nxp.com/acrobat&#95;download/applicationnotes/AN10381&#95;1.pdf&#41; shows how to write ISRs that are capable of nesting in C with some admixture of inline assembly. This approach works for IRQs only. Problems might arise if you allow both FIQ and IRQ to preempt each other.
2&#46; The ARM Technical Support Note “Writing Interrupt Handlers” shows how to write IRQs that are capable of nesting. The ARM approach shows an assembler “wrapper” that calls the ISR in C. Again, this particular implementation works only for IRQ and can be problematic for FIQ preempting IRQ.
3&#46; The Micrium Application Note AN1011 &#40;http://www.micrium.com/arm&#41; describes the uC/OS-II port to the ARM. The most interesting part of this AN is the assembler part of the port, which provides both IRQ and FIQ that can nest. It also provides quite a generic context switch for ARM.
4&#46; The Quantum Leaps Application Note “QP and ARM” &#40;http://www.quantum-leaps.com/downloads/qdk.htm&#35;ARM&#41; shows how to implement fully-preemptive single-stack kernel on the ARM. Such kernel is much smaller and faster than any traditional multiple-stack kernel, such as uC/OS-II, or FreeRTOS. For event-driven systems &#40;i.e., most embedded systems&#41; the limitations of the single-stack kernel don’t matter. Please see the ESD article “Build a Super Simple Tasker” &#40;http://www.embedded.com/showArticle.jhtml?articleID=190302110&#41; for more information.
