When using semaphores, you would have to check all sockets that are owned by the task. I would embed each socket in an object that describes exactly the current status.
If you look at the FTP/HTTP server on <a href="https://www.freertos.org/FreeRTOS-Labs/downloads/160919_FreeRTOS_Labs.zip?dl=0">freertos/tcp</a>, it will become clear what I mean.
The status can be:
<ul>
<li>Wait for connect</li>
<li>Receiving a file</li>
<li>Sending a file</li>
<li>Idle state, waiting for a new command</li>
<li>Waiting for a closure</li>
</ul>

Sorry, you&#8217;re right: the example doesn&#8217;t use a semaphore but <code>FreeRTOS_select()</code>. The implementation is the same however: every socket is embedded in a structure that stores the status of the connection. All sockets are checked in every loop.
<blockquote>
  160919<em>FreeRTOS</em>Labs
</blockquote>
Please note that the +TCP sources in that distribution are very old. It is still there because of the old demo&#8217;s that used +FAT, and the FTP/HTTP servers.
The latest release of +FAT can be found on the <a href="https://freertos.org/FreeRTOS-Labs/downloads/FreeRTOS-Plus-FAT-160919a-MIT.zip?dl=0">/labs download page</a>. +TCP can be found on e.g. <a href="https://github.com/aws/amazon-freertos/">github/aws</a>
<blockquote>
  This is the callback for Receiving:
  <code>static BaseType_t Callback_OnReceive ( Socket_t xSocket, void * pData, size_t xLength )</code>
  <code>{</code>
   <code>Callback_Message_t Callback_Message;</code>
   <code>Callback_Message.type = Callback_Receive;</code>
   <code>Callback_Message.Receive.xSocket = xSocket;</code>
   <code>Callback_Message.Receive.pData   = pData;</code>
   <code>Callback_Message.Receive.xLength = xLength;</code>
</blockquote>
Oops: the pointer <code>pData</code> will become invalid after the function returns. So you only access it from within this function.
<blockquote>
  I call FreeRTOS_recv to get the data out. Is this correct?
</blockquote>
Yes that is OK.
<blockquote>
  I can only see receivedData with -128 (connection closed) or 0 (zero bytes).
</blockquote>
The data were flushed ( not stored ) because your function <code>Callback_OnReceive()</code> returned a positive value. When it returns zero, the data will be stored in the RX stream buffer of the socket.
<blockquote>
  Should I retrieve the data inside the callback?
</blockquote>
No let the socket store it and you retrieve it later.
<blockquote>
  How does FreeRTOS IP know that the data received has been used and therefore can be discarded?
</blockquote>
So yes, it looks at the return value: 1 = data consumed, 0 = please store data
<blockquote>
  if ( receivedData == FREERTOS_ECLOSED )
</blockquote>
Note that there are two error codes that are not fatal: <code>-pdFREERTOS_ERRNO_EAGAIN</code> and <code>-pdFREERTOS_ERRNO_EINTR</code>. All other negative values must be treated in the same way as <code>-pdFREERTOS_ERRNO_ENOTCONN</code>: call <code>closesocket()</code>.

Could I suggest that maybe it is better to do it the other way. Never to take the data out.
In this way no buffer needs to be allocated by using pvPortMalloc in the callback function:
~~~
    pData<em>new = pvPortMalloc ( xLength );
    memcpy ( pData</em>new, pData, xLength );
~~~
Instead this is done in the receiver task:
~~~
    pData<em>new = pvPortMalloc ( Callback</em>Message.Receive.xLength );
    receivedData = FreeRTOS<em>recv ( Callback</em>Message.Receive.xSocket, pData<em>new/*pvBuffer*/,  Callback</em>Message.Receive.xLength, 0/<em>xFlags</em>/ );
~~~
This would make the time inside the callback function smaller and deterministic. The allocation method can be time underterministic (I think there are some heap management methods in FreeRTOS that are deterministic but others aren&#8217;t&#8230;).
Instead of allocating memory one could declare a static variable of say 100 bytes, big enough to conatin any legal message. This would make the code faster and deterministic.
Another way would be to use a setsockopt call:
~~~
reeRTOS<em>setsockopt ( IPreceiver</em>Socket, 0, FREERTOS<em>SO</em>TCP<em>RECV</em>HANDLER<em>CONSUME</em>DATA, 0 or 1 &#8230; );
~~~
Before setting the callback function change FREERTOS<em>SO</em>TCP<em>RECV</em>HANDLER<em>CONSUME</em>DATA to 0, don&#8217;t consume or 1, consume.
If this is called after setting the callback function, it has no effect.
Default value could be 0, don&#8217;t consume.
