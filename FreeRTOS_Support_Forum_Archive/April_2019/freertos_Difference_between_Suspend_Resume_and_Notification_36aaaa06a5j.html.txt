  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Difference between Suspend/Resume and Notification</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fbascon">fbascon</a> on April 8, 2019</div><div class="thread-post-content">Hi guys,
I use FreeRTOS 9. I ask your help to understand a topic.
I&#8217;ve an interrupt event (ISR) that resume a thread (with a priority above normal). The thread resumed, after doing its work, suspend itself  (until the ISR resume it again.. and so on). 
The mechanism described above uses the vTaskSuspend and xTaskResumeFromISR() functions. What&#8217;s the difference if I use a Notification instead (the thread wait a flag given by the interrupt event and so on) ?
Thank for your replies,
F.B
</div></div><div class="thread-post"><h3 class="thread-post-title">Difference between Suspend/Resume and Notification</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on April 8, 2019</div><div class="thread-post-content">By using a notification, if the interrupt happens before the task suspends itself, the notification is remembered, so the task won&#8217;t stop. If that happens with suspend/resume then the resume gets ignored because the tasks isn&#8217;t suspended.
Also, with notifications, you can put a timeout, so if the notification doesn&#8217;t arrive in a given time, the task resumes automatically, with a return code telling it of the timeout.
</div></div><div class="thread-post"><h3 class="thread-post-title">Difference between Suspend/Resume and Notification</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 8, 2019</div><div class="thread-post-content">First &#8211; what you are doing is dangerous &#8211; and that is noted in the
documentation for the xTaskResumeFromISR() function API documentation.
I think the xTaskResumeFromISR() API may have even been deprecated in
later versions to try and stop people doing this.
The problem with your technique is resuming a task is not a &#8216;latching&#8217;
operation &#8211; that is &#8211; there is no memory or history of it so resumes can
be missed.
Consider a scenario where:
1) An interrupt resumes a thread.
2) The thread starts running and executes part way through the code that
needs to execute before is suspends itself again on the next iteration
of its loop.
3) The interrupt executes again, and resumes the thread, but the thread
was not suspended as it had not reached to call to vTaskSuspend() yet,
so resuming the thread has no effect, and there is no memory of the
interrupt ever calling xTaskResumeFromISR().
4) The task continues executing and reaches the point where it suspends
itself again &#8211; but it is already too late and the previous interrupt is
missed.
Now consider the same operation using a task notification, queue,
semaphore, event group, message or stream buffer, etc. &#8211; all of which
latch events&#8230;example using a task notification used as a counting
semaphores:
1) An interrupt sends a notification to a task, incrementing the task&#8217;s
notification value to 1.
2) The task unblocks due to the notification, decrements it notification
count to 0 (that happens atomically inside the API function), and starts
to execute but only gets part way through the code that needs to execute
before it blocks on the notification again the next time through its loop.
3) The interrupt executes again, sends a notification to the task,
incrementing the task&#8217;s notification count to 1 again even though the
task was not blocked on the notification.
4) The interrupt executes again, sends a notification to the task again,
incrementing the task&#8217;s notification count, this time to 2.
Now the fact that two interrupts have occurred are latched in the
notification count &#8211; effectively memorising that the events occurred.
5) The task continues executing and reaches the point where it blocks on
the notification &#8211; but the notification count is already set to 2 so the
task doesn&#8217;t block, but instead decrements the count to 1, and continues
to execute the code.
6) The task continues executing and reaches the point where it blocks on
the notification again &#8211; but the notification is still set to 1 so the
task doesn&#8217;t block, but instead decrements the count to 0, and continues
to execute.
7) The task continues executing and reaches the point where it blocks on
the notification &#8211; this time the notification is 0 so the task blocks to
wait for the next interrupt.
In this case &#8211; no interrupts are lost.
</div></div><div class="thread-post"><h3 class="thread-post-title">Difference between Suspend/Resume and Notification</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fbascon">fbascon</a> on April 9, 2019</div><div class="thread-post-content">Dear Richard Barry and Richard Damon,
Thanks for your helpful replies. I have better understood how the Resume and Suspend functions work. 
Now I&#8217;ve implemented the following meccanism with thread Task Notifications:
<ul>
<li>The thread waits a flag from interrupt handler (I use cmsis layer):
~~~
while( osSignalWait(THREAD<em>WAKE</em>UP,osWaitForever).status != osErrorValue )
{
// do something&#8230;
}
~~~</li>
<li>The interrupt wake up the thread by sending the flag:
<code>if( idtask != NULL ) osSignalSet(idtask,THREAD_WAKE_UP);</code></li>
</ul>
