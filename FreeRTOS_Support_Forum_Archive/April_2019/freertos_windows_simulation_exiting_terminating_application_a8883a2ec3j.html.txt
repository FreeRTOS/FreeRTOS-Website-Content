  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">windows simulation exiting/terminating application</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dukb">dukb</a> on April 9, 2019</div><div class="thread-post-content">I use windows simulation built with MinGW.  Recently we updated freertos from 9.0.0 to 10.1.1.
I faced issue that our application never ends. I checked port.c and found out that in <em>vPortEndScheduler</em>  there was <em>TerminateProcess( GetCurrentProcess(), 0 );</em>  which is now exchanged with <em>exit(0)</em>.
<em>TerminateProcess</em>  (Windows API function) unconditionally terminate current task (thread in this case) and all other tasks (threads) in same process.  It doesn&#8217;t call any local destructors so in C++ application it should be called manually. <em>exit</em> (stdlib function) call destructors of locals in current thread (task) but do NOT finish other threads somehow (on linux it seems to work).
In the application there are even tasks created in the task which call vPortEndScheduler() so local destructor call <em>vTaskDelete</em> so task is closed but thread is not terminated because <em>vPortCloseRunningThread</em> is called only when <em>if( pxTCB == pxCurrentTCB )</em>  is fulfilled (looks like when task to delete is same as current running task .)
When all actions connected with <em>exit</em> ends application simply do other threads so to finish it <em>taskkill</em> needs to be used.
How freertos task in case of Windows simulator should be finished/closed/deleted?
Did anyone tries the behavior of <em>exit</em> with MSVC compiler?
</div></div><div class="thread-post"><h3 class="thread-post-title">windows simulation exiting/terminating application</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidefer">davidefer</a> on April 9, 2019</div><div class="thread-post-content">This is missing in the port. We had to implement it ourselves.
static xThreadState createdThreadsList[configMAX<em>PROCESSES];
static uint16</em>t createdThreadsNum = 0U;
In pxPortInitialiseStack add:
    createdThreadsList[createdThreadsNum].pvThread = pxThreadState->pvThread;
    createdThreadsNum++;
You have to let prvProcessSimulatedInterrupts return when you want to stop the application (we have done it with a dedicated simulated interrupt).
Then  you can terminate all the threads:
    for (int i=0; i&lt; createdThreadsNum; i++)
    {
        ulErrorCode = TerminateThread(createdThreadsList[i].pvThread, 0);
        configASSERT(ulErrorCode);
    }

</div></div><div class="thread-post"><h3 class="thread-post-title">windows simulation exiting/terminating application</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dukb">dukb</a> on April 10, 2019</div><div class="thread-post-content">Generally our application has one &#8220;main&#8221; task which create others tasks.  &#8220;Main&#8221; task is inside  C++ &#8220;main&#8221; class.  So I noticed that changing <em>TerminateProcess</em> to <em>exit(0)</em> is good because destructors will be called.  But as I mentioned application didn&#8217;t finished itself.
So my first solution was that I call <em>TerminateProcess</em>  when &#8220;main&#8221; task is deleted (deletion of the task I have in destructor of my &#8220;main&#8221; class) inside* vPortCloseRunningThread* instead of <em>ExitThread</em> . But there is disadvantage of this solution that when task wants to be finished by itself during standard operation <em>TerminateProcess</em> is executed and application finished.
 After davidefer replied to my post then I tried the proposition. I removed <em>exit(0)</em>  in <em>vPortEndScheduler</em>  and signaled scheduler to finish endless loop (and enabled interrupt so scheduler could be called).  Then my application can reach <em>return</em> statement  in main function in main thread and destructors also will be called (even for objects outside of my &#8220;main&#8221; task).  So this solutions sound even better.
Unfortunately there are still some threads which are not finished and application still exist. Strange thing is when application reach main there are 4 threads already. I&#8217;m not sure if it has anything in common in affinity (which is set to 1 core further).
Next I took @davidefer port.c from
https://sourceforge.net/p/freertos/discussion/382005/thread/d8a09bc895/#f70d
and result is still the same.
So  I still call <em>TerminateProcess</em> in <em>vPortCloseRunningThread</em>  which is executed because <em>pxCurrentTCB</em> was not changed and it keeps &#8220;main&#8221; task (the task trigger process termination). The whole thing is called in &#8220;main&#8221; class destructor which is called at the end of my application. I know the solution is not elegant but it works 🙂
@davidefer ->  one remark to termination of threads at the end of schedule. I think in
    for (int i=0; i&lt; createdThreadsNum; i++)
    {
        ulErrorCode = TerminateThread(createdThreadsList[i].pvThread, 0);
        configASSERT(ulErrorCode);
    }
    configASSERT should be removed since tasks can be finished dynamically during operation and TerminateThread can return 0. I think the best it to ignore it and try with next one.
