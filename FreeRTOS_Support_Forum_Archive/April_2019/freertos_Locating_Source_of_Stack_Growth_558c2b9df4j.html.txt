  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Locating Source of Stack Growth</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hillridge">hillridge</a> on April 16, 2019</div><div class="thread-post-content">I&#8217;m having an issue where a task is overflowing its stack (or at least appears to be) at some unpredictable point in time.
I have vApplicationStackOverflowHook enabled, and found that one of my tasks was triggering it.  I added a call to uxTaskGetStackHighWaterMark() in that task, and monitor the result.  Upon creation, the HWM reports back as 34.  The task itself is quite simple: read an ADC, convert the result to a properly formatted string, send it out the debug serial port.  There&#8217;s nothing in there that should cause the stack to grow or shrink after the initial pass through the While(1) body of the task, but I also haven&#8217;t fully investigated all of the calls to some vendor supplied driver functions. 
However, if I wait for the code to crash (by getting trapped in vApplicationStackOverflowHook()), then go back and look at the debug port output, I see that this task&#8217;s stack&#8217;s HWM keeps decreasing sporadically with the last reported value before crash being 10.  The time it takes for this to happen is variable and unpredictable.   I&#8217;ve kept an eye on it over the last 20 minutes and it&#8217;s only down to 30 now 
What are potential causes of this?  My first thought was interrupts, but It&#8217;s my understanding that the FreeRTOS port I&#8217;m using (for a Cortex-M4) uses a separate stack for exceptions/interrupts.  How can I confim this is true?  Is there another component of the RTOS  that can cantribute to stack growth like this?
Thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/waveringradiant">waveringradiant</a> on April 16, 2019</div><div class="thread-post-content">Something you said there:
<blockquote>
  The task itself is quite simple: read an ADC, <strong><em>convert the result to a properly formatted string</em></strong>, send it out the debug serial port.
</blockquote>
Question:  any chance you&#8217;re using something like <code>sprintf()</code> to format the string?  Traditionally the &#8220;printf&#8221; family of functions are very hard on the stack&#8230;
If you&#8217;re using sprintf(), try commenting that out and just send a byte like &#8216;A&#8217; out the port, and see if the stack overflow goes away&#8230;
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hillridge">hillridge</a> on April 16, 2019</div><div class="thread-post-content">I am using sprintf, but the format of what I&#8217;m printing never changes, including the character count.  What in that function could cause the stack usage to increase suddenly after being the same for the last X-hundred calls? 
I will try your suggestion, though the unpredictable nature of this issues makes it hard to tell if a change has removed the problem.   
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pete-bone">pete-bone</a> on April 16, 2019</div><div class="thread-post-content">Hi Adam,

If so you should probably check if the libc implementation you are using supports reentrancy for the sprintf() function.
Kind Regards,
Pete
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/waveringradiant">waveringradiant</a> on April 16, 2019</div><div class="thread-post-content">Yes you ask a very good question&#8230; I could speculate on possible causes, but there are many.
In Handler mode (exceptions), the CM4 always uses the main stack.  While in Thread Mode, depending on configuration, the application mode could also be using the main stack. (I use many RTOSes, I can&#8217;t recall how FreeRTOS is configured by default, I suspect it might be everything uses the main stack)
Also if you are using the FPU in or more tasks, the amount of context stacked depends on FPU usage.  (You only need to save/stack FPU regs for task(s) that use the FPU).
There are other possibilities to explain why &#8220;doing the same thing sometimes behaves differently&#8221; due to the asynchronous nature of interrupts (for example, nested interrupts), but I don&#8217;t even know if you&#8217;re using the FPU and/or nested interrupts.
Often soemthing like this happens when things line up in time &#8220;in just the wrong way&#8221;
So let&#8217;s see about printf() and then go from there.  Fun problem but not when you&#8217;re the one on the short end trying to ship a product&#8230;
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 16, 2019</div><div class="thread-post-content">Can&#8217;t recall if the HWM is in bytes or words, would need to look at the
docs or source to see &#8211; but in any case &#8211; 30 odd does not sound very
much.  It is conceivable that you call sprintf() lots of times with no
problem because there didn&#8217;t happen to be a context switch to another
task within the call, then at some point there is a context switch &#8211; at
which point the task&#8217;s context is also saved to the stack and boom &#8211; it
overflows.
In answer to another post in this thread &#8211; on Cortex-M parts FreeRTOS
uses a different stack for interrupts.
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hillridge">hillridge</a> on April 16, 2019</div><div class="thread-post-content">Thanks Pete, I <em>think</em> all the printf family of functions I&#8217;m using are thread safe and reentrant, but I will check to make sure once I dig them out of the IDE that obfuscates things somewhat.
Richard &#8211; I believe it is in words.  So you&#8217;re saying that when my issue is happening I may just be timing things right with maximum stack usage (due to the extra overhead of sprintf) at the moment of a context switch? That&#8217;s plausible.  I&#8217;m going to simply increase the stack for now and see if it continues to grow beyond where it would normally overflow.
</div></div><div class="thread-post"><h3 class="thread-post-title">Locating Source of Stack Growth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hillridge">hillridge</a> on April 16, 2019</div><div class="thread-post-content">Oh I am well aware of &#8220;in just the wrong way&#8221;. I spent the better part of a week debugging an intermittent I2C issue that turned out to be triggered by a context switch perfectly timed between a write and read operation.
You did bring up a point that prompts  a new question from me &#8211; my processor has a built in FPU, and I do make use of it in some tasks.  Do I need to manually do something to stack the FPU regs, or is that handled automatically?  I haven&#8217;t seen any FPU related issues yet, but I may have just been lucky.  
Richard&#8217;s post below brought up something I hadn&#8217;t thought of which ties sprintf and interrupts together, and I think it&#8217;s likely the root cause.  I have a bit of investigating to do though.

Just wondering if the usual suspect (printf) was chewing up the stack&#8230;
