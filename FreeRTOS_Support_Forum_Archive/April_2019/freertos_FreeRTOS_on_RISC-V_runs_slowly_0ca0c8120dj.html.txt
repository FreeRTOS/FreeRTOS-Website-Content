  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS on RISC-V runs &#8220;slowly&#8221;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nickolasb">nickolasb</a> on April 5, 2019</div><div class="thread-post-content">Hi all,
I recently put together FreeRTOS and freedom-e-sdk to run on a HiFive1 board, but it was running slower than it should. I realised later that FreeRTOS was working correctly, but that the calculated ticks were too long. For example: the demo used pdMS<em>TO</em>TICKS( 1000 ) to delay a task for 1 second. However that would take minutes of real time.
In the end I had to use these values to get close to the real time delays:
define configCPU<em>CLOCK</em>HZ ( 17500 )
define configTICK<em>RATE</em>HZ ( ( TickType_t ) 100 )
Please, have anyone tried FreeRTOS on a HiFive1 and got different results?
And do you think it is a problem to &#8220;lie&#8221; to FreeRTOS about the clock, in order to get timers close to real time values?
Thanks!
More details:
&#8211; Regarding freedom-e-sdk, I&#8217;m using this commit as the base:
https://github.com/sifive/freedom-e-sdk/tree/dca1dfaf1cfb80ec30a7a16b899efa1040e3451d
It is much simpler compared to current implementation using metal library.
&#8211; I also tried running FreeRTOS on an Arty A7-100T FPGA and got the exact same results.
&#8211; freedom-e-sdk tries to measure the CPU frequency by checking the CSR mtime:
https://github.com/sifive/freedom-e-sdk/blob/dca1dfaf1cfb80ec30a7a16b899efa1040e3451d/bsp/env/freedom-e300-hifive1/init.c#L141 
And the values the boards printed was:
arty: 64959283Hz
hifive: 264971878Hz
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS on RISC-V runs &#8220;slowly&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on April 5, 2019</div><div class="thread-post-content">You shouldn&#8217;t need to &#8216;lie&#8217; to FreeRTOS. The likely problem is that the port layer has a bug for that system and isn&#8217;t setting up the tick timer right. The define configCPU<em>CLOCK</em>HZ should only be used by the port layer to setup the timer, which should also be using the configTICK<em>RATE</em>HZ define.  If the ticks aren&#8217;t occuring at the right rate, that setup function is wrong.
I don&#8217;t know those particular systems/projects, but I do know how FreeRTOS works, and getting wrong period tick interurpts it the responsibility/fault of the port layer in port.c in a function called an named to set up the system timer (I don&#8217;t have the code in front of me to get the exact name, but it should be obvious looking throgh port.c). Values being that far off sounds like something may be wanting values scaled differently than being provided.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS on RISC-V runs &#8220;slowly&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 5, 2019</div><div class="thread-post-content">What is generating the clock input to the MCU? </div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS on RISC-V runs &#8220;slowly&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nickolasb">nickolasb</a> on April 9, 2019</div><div class="thread-post-content">Thanks for you prompt response.
And thanks to your answers I (almost) found the issue!
There are two cycle counters on RISC-V, as described on the The RISC-V Instruction Set Manual Volume II: Privileged Architecture (https://content.riscv.org/wp-content/uploads/2017/05/riscv-privileged-v1.10.pdf):
&#8211; &#8220;The mcycle CSR holds a countof the number of cycles the hart has executed since some arbitrary time in the past.&#8221; (section 3.1.16)
&#8211; &#8220;Platforms provide a real-time counter, exposed as a memory-mapped machine-mode register, mtime. mtime must run at constant frequency, and the platform must provide a mechanism for determining the time base of mtime.&#8221; (section 3.1.15)
I found considerable evidence that mtime frequency is 32768 Hz, or 32KHz:
&#8211; The SiFive E31 Core Complex Manual v2p0 (https://sifive.cdn.prismic.io/sifive%2Fb06a2d11-19ea-44ec-bf53-3e4c497c7997<em>sifive-e31-manual-v2p0.pdf) on section 6.3 says:
&#8220;mtime is a 64-bit read-write register that contains the number of cycles counted from the rtc</em>toggle signal described in the E31 Core Complex User Guide.&#8221;
&#8211; And in turn the E31 Core Complex User Guide says on section 8.2.1:
&#8220;Generally, rtc_toggle is connected to either a Real Time Clock (e.g. 32.768 kHz) or to the base clock input frequency of the platform.&#8221;
The code that tries to measure the clock takes the mcycle/mtime difference into account:
https://github.com/sifive/freedom-e-sdk/blob/dca1dfaf1cfb80ec30a7a16b899efa1040e3451d/bsp/env/freedom-e300-hifive1/init.c#L42
It looks to correctly measure how many &#8220;mcycle cycles&#8221; happened between each &#8220;mtime cycle&#8221;, and then uses the 32KHz to calculate the mcycle frequency.
But the code on FreeRTOS/Source/portable/GCC/RISCV/port.c, more specifically, the function vPortSetupTimerInterrupt, wasn&#8217;t considering it. I &#8220;fixed&#8221; it dividing the clock by 32KHz, which is the frequency of the mtime cycles:
const uint32<em>t ulTimerIncrementsForOneTick = ( uint32</em>t ) ( ( configCPU<em>CLOCK</em>HZ / 32768) / configTICK<em>RATE</em>HZ );
Now it calculates the next tick using &#8220;mtime cycles&#8221;, which happen at a frequency of 32KHz.
By the end the timers are no longer wrong by a factor of 8000. However, they are still wrong by a factor of 4. (32/8=4)
So I&#8217;ll continue looking into what is wrong. I&#8217;ll probably explore this sentence:
&#8220;Generally, rtc_toggle is connected to either a Real Time Clock (e.g. 32.768 kHz) or to the base clock input frequency of the platform.&#8221;
Please, if you have anything to say, or know who could I talk to about fixing the file above, leave a response.
