  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">ARM Initialized stack alignment assert fail</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/johandc">johandc</a> on August 9, 2011</div><div class="thread-post-content">For ARM EABI the required stack alignment is 8 bytes. This has recently been addressed in V 6.0.0 and onwards by providing a check on any malloced stack pointer. And while this alignment works fine &#40;on most platforms &gt;= 32bit, check previous post: &#8220;EABI Stack Alignment on ARM7&#8243;&#41;, the problem is what happens next.  
In task.c line i have the following code:  
<pre><code>pxTopOfStack = pxNewTCB-&gt;pxStack + ( usStackDepth - ( unsigned short ) 1 );
pxTopOfStack = ( portSTACK_TYPE * ) ( ( ( uintptr_t ) pxTopOfStack ) &amp; ( ( uintptr_t ) ~portBYTE_ALIGNMENT_MASK  ) );
/* Check the alignment of the calculated top of stack is correct. */
configASSERT( ( ( ( uintptr_t ) pxTopOfStack &amp; ( uintptr_t ) portBYTE_ALIGNMENT_MASK ) == 0UL ) );
</code></pre>
&#40;Notice that I replaced unsigned long with uintptr&#95;t in order to make compiling on 8-bit AVR working. To fix previously said bug&#41;. The assertion here does not fail.  
This ensures that the top of stack pointer is now aligned.   
Then there is a call:  
<pre><code>pxNewTCB-&gt;pxTopOfStack = pxPortInitialiseStack( pxTopOfStack, pxTaskCode, pvParameters );
</code></pre>
And now there is a second alignment assertion, which fails:  
<pre><code>/* Check the alignment of the initialised stack. */
configASSERT( ( ( ( uintptr_t ) pxNewTCB-&gt;pxTopOfStack &amp; ( uintptr_t ) portBYTE_ALIGNMENT_MASK ) == 0UL ) );
assertion "( ( ( uintptr_t ) pxNewTCB-&gt;pxTopOfStack &amp; ( uintptr_t ) portBYTE_ALIGNMENT_MASK ) == 0UL )" failed: file "../src/freertos/tasks.c", line 508, function: xTaskGenericCreate
Exit 1
</code></pre>
This is because the ARM7tdmi based port stacks an uneven number of elements &#40;17&#41; to the task stack. This does not mean that the task stack itself will be unaligned because the original top of stack was stored in the task context itself. So the second assertion does nothing to ensure that the stack of the task is aligned. Rather it checks if the size of the stored context is even or odd…  
I added a pxTopOfStack-; to the beginning of initializeStack to make it stack 18 elements, and now the assertion does not fail, and the code also works…  
Is this going to be a future requirements that all ports must initialize the task context with a number of elements which corresponds to the stack alignment?
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Initialized stack alignment assert fail</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 9, 2011</div><div class="thread-post-content">What is the point of the line:  
<pre><code>configASSERT( ( ( ( unsigned long ) pxNewTCB-&gt;pxTopOfStack &amp; ( unsigned long ) portBYTE_ALIGNMENT_MASK ) == 0UL ) );
</code></pre>
If the top of the stack has the right alignment, then you populate the stack will variables and the newly populated stack has bad alignment, it will be corrected when the task starts for the first time. When the task starts its context will be popped off, leaving the stack pointer at the top of the stack, which has already been checked for correct alignment so there is not a problem.  
It might be though, that the check is there for when the task is swapped out next. If it has 8 byte aligned stack entering the SWI interrupt, and has its context pushed to the stack, and that push leaves it only 4 byte aligned, then it will have 4 byte alignment&nbsp; in the interrupt routine. However, interrupts don&#8217;t use the task stack.  
Experimenting I see that when a task starts its stack is aligned to 8, as I expected, even though the assert fails. Entering vPortYieldProcessor it also has 8 alignment, but that depends on the start up code as the SWI stack is allocated there. vPortYieldProcess then saves the task context to the task stack, and that does not effect the SWI stack, so the SWI stack remains 8 byte aligned. The same it true for the tick interrupt.  
<strong>So, my take is that everything is working perfectly except the assertion quoted above, which might be right for some ports, but is creating a false assert for ARM7</strong>. Maybe it is only relevant for when a stack grows the other way?
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Initialized stack alignment assert fail</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/johandc">johandc</a> on August 10, 2011</div><div class="thread-post-content">Thank you Dave.  
I didn&#8217;t want to jump to too many conclusions in my original post, but in fact, we have come to the <strong>exact same conclusion</strong> as you have. We also considered the stack alignment of ISR&#8217;s, but as you say, they run on their own stack. We conducted a short test with stack alignment both in task and in an ISR and found that removing the second alignment assertion is safe on ARM7.  
However, because we don&#8217;t have richard&#8217;s words for it yet, we didn&#8217;t remove it completely. We adjusted the size of the initial stacked context to 18 instead of 17 in order to &#8220;trick&#8221; the assertion.  
BTW. kudo&#8217;s to the FreeRTOS developers for a nice and much more clean V7.0.1. I like the use of taskENTER&#95;CRITICAL instead of portENTER&#95;CRITICAL, and the use of assertions is very good. I&#8217;d like to see even more of them implemented in the future. :-&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Initialized stack alignment assert fail</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 10, 2011</div><div class="thread-post-content">&#8220;I agree with Dave&#8221;.&nbsp; The assertion is not correct for the ARM7 as it is.&nbsp; The question is what is best to do about it.&nbsp; It was put in to catch errors introduced during maintenance work, rather than when ports are first created.&nbsp; One option is just to remove it, another would be to have a directive in portmacro.h, which then makes it on a port by port basis.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Initialized stack alignment assert fail</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 11, 2011</div><div class="thread-post-content">I want the assertion to stay in tasks.c because, while in the ARM7 case it is superfluous, in other ports it is not.&nbsp; Therefore it is valuable when a port is being created.&nbsp; I have therefore instead, gone through all the ARM7 ports and, in pxPortInitialiseStack&#40;&#41;, after the line:  
<pre><code>pxOriginalTOS = pxTopOfStack;
</code></pre>
I have added the lines:  
<pre><code>    /* To ensure asserts in tasks.c don't fail, although in this case the assert
    is not really required. */
    pxTopOfStack--;
</code></pre>
This costs 4 bytes of stack per task, which is a pity, but not a killer.&nbsp; That now seems to fix the incorrect assertion problem.  
Please let me know if you agree with this, and if indeed it is the same fix you described yourself.  
Thanks &#8211; feedback is always appreciated.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Initialized stack alignment assert fail</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/johandc">johandc</a> on August 11, 2011</div><div class="thread-post-content">Indeed it is the same fix, here is the start of our initialize function as it looks right now:  
<pre><code>portSTACK_TYPE *pxPortInitialiseStack( portSTACK_TYPE *pxTopOfStack, pdTASK_CODE pxCode, void *pvParameters )
{
portSTACK_TYPE *pxOriginalTOS;
    pxOriginalTOS = pxTopOfStack;
    /* Use this to align context to 8 bytes */
    pxTopOfStack--;
</code></pre>
Thank you for evaluating the issue and making a decision. Some times that is last part the hardest :-&#41;  
Regards,<br />
Johan.
