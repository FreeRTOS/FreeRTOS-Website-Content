  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/baranov">baranov</a> on August 12, 2011</div><div class="thread-post-content">Hello. I am not really sure that the problem is FreeRtos related.&nbsp;<br />
I have a project with one task consisting only of vTaskDelay&#40;5000&#41;;<br />
When I compile the project with medium and high optimization options it works fine. When I switch to low it goes to Hard Fault Interrupt. When I single step, it runs to vPortStartFirstTask&#40;&#41; and gets into:  
<pre><code>vPortSVCHandler;
    ldr r3, =pxCurrentTCB
    ldr r1, [r3]
    ldr r0, [r1]
    ldmia r0!, {r4-r11}
    msr psp, r0
    mov r0, #0
    msr basepri, r0
    orr r14, r14, #13
    bx r14
</code></pre>
On exit from it my debugger shows:<br />
**Usage fault: Attempt to use a coprocessor instruction&#33; **<br />
Of course I tried to vary stack and heap sizes but it did not clarify the situation.<br />
Could anybody give a clue, what did the optimization option change?  
</div></div><div class="thread-post"><h3 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 14, 2011</div><div class="thread-post-content">I am guessing, and it is just a guess, that you are using a Cortex-M3 device. If so, then IAR V5.x is out of date.&nbsp; Other than that, how is your C start up code written?&nbsp; The symptom you describe can often happen when the start up is written completely in C, and is caused by a loop variable being stored on the stack with zero optimisation &#40;and so getting wiped out by its own initialisation code&#41; compared to the same variable being held in a register at higher optimisation &#40;and so being safe from being wiped out by memory clearing and initialisation code&#41;.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/baranov">baranov</a> on August 15, 2011</div><div class="thread-post-content">Thank you very much&#33;. Yes, it is STM32.&nbsp; I will try IAR 6.10. 
</div></div><div class="thread-post"><h3 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/baranov">baranov</a> on August 15, 2011</div><div class="thread-post-content">IAR 6.10 did not help.<br />
I saw that in <strong>&#8220;medium</strong>&#8221; option&nbsp; vPortSVCHandler&nbsp; enters assembler function shown above&nbsp; with<br />
LR = 0xFFFFFFF9, which is correct and in &#8220;<strong>low</strong>&#8221; option LR has some other value. In my case it is e.g. 0x800D7FF. I guess, I simply have to use medium optimization.  
</div></div><div class="thread-post"><h3 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 15, 2011</div><div class="thread-post-content">Can you post the code that initializes the C run time environment. The bit that zeros out the memory, normally in a file called crt0 or cstart or startup, etc.
</div></div><div class="thread-post"><h3 class="thread-post-title">IAR 5.41 getting to Hard Fault with low opt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/baranov">baranov</a> on August 15, 2011</div><div class="thread-post-content">I think, I solved the problem.<br />
I had:  
<pre><code>const intvec_elem __vector_table[] =
{
    { .__ptr = __sfe( "CSTACK" ) },
    __iar_program_start,
    NMIException,
    HardFaultException,
    MemManageException,
    BusFaultException,
    UsageFaultException,
    0, 0, 0, 0,             // Reserved
   SVCHandler,
    DebugMonitor,
    0,                      // Reserved
    PendSVC,
    SysTickHandler
};
</code></pre>
and  
<pre><code>void SVCHandler( void )
{
#ifdef FREERTOS
    vPortSVCHandler();
#endif
}
</code></pre>
I replaced it by:  
<pre><code>const intvec_elem __vector_table[] =
{
    { .__ptr = __sfe( "CSTACK" ) },
    __iar_program_start,
    NMIException,
    HardFaultException,
    MemManageException,
    BusFaultException,
    UsageFaultException,
    0, 0, 0, 0,             // Reserved
   vPortSVCHandler,
    DebugMonitor,
    0,                      // Reserved
    PendSVC,
    SysTickHandler
};
</code></pre>
It eliminated call from SVCHandler and now it works with low optimization too.<br />
Any comments including scornful will be highly appreciated.
