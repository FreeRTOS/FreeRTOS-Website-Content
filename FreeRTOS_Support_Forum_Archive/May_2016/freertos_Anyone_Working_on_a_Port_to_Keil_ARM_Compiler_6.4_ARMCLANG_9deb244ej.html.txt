  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ppotts">ppotts</a> on May 25, 2016</div><div class="thread-post-content">Keil/ARM dropped an updated MDK that comes with a version of ARMCLANG:
C:Keil_v5ARMARMCLANGbin>armclang &#8211;version
Product: MDK-ARM Standard Cortex-M only 5.20
Component: ARM Compiler 6.4
Tool: armclang [5c29cb00]
Target: unspecified-arm-none-unspecified
I would love to use this compiler for my project as it has support for a much more modern version of C++, a lot better static analysis, more warnings, compiles faster, does the dishes and mops the floor, etc.
However, it supports a different syntax for inline assembly, and Keil&#8217;s docs don&#8217;t describe it well.
I&#8217;m not sure I&#8217;m up to the task of porting FreeRTOS myself. I&#8217;m willing to try, but if it is going to be extremely hairy I&#8217;ll probably have to give up and use the old compiler.
My target is a SAM4E16E (Cortex-M4) chip. FreeRTOS is working great for me with the older ARMCC compiler.
Is anyone else using this new compiler? Anyone else attempting a port?
One possibility that occurred to me: could I build FreeRTOS as a static library, with the old compiler, and drop it into a project built with ARMCLANG?
Maybe not, as that won&#8217;t help with functions that are really macros.
Any suggestions welcome.
Thanks,
Paul R. Potts
</div></div><div class="thread-post"><h3 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 25, 2016</div><div class="thread-post-content">We have used CLANG before, and as it tries to support GCC syntax, had 
success building and running the FreeRTOS GCC port with it BUT did find 
we had to make one small modification to the port layer in order for 
this to work.
The issue was related to the use of the <strong>attribute</strong>((naked)) 
qualifier, which didn&#8217;t work quite as advertised.  It is supposed to 
prevent any compiler prologue or epilogue code being generated, as per 
GCC&#8217;s use of the qualifier.  As I recall it removed most of the compiler 
generated prologue, but left in some stack manipulation code.  That was 
some time ago though, and I believe that issue has since been fixed.
</div></div><div class="thread-post"><h3 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 25, 2016</div><div class="thread-post-content">Forgot to mention the static library option &#8211; assuming CLANG complies 
with the ARM EABI, which I would be surprised if it didn&#8217;t, then you 
should be able to mix and match compilers used to build and then 
subsequently link to static libraries.  Again this is something we have 
done ourselves, but not with CLANG.
</div></div><div class="thread-post"><h3 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ppotts">ppotts</a> on May 25, 2016</div><div class="thread-post-content">Thanks for the suggestions. I am pressing on with it &#8212; I have some changes to my portmacro.h that seem to compile. I should be able to test it all pretty soon.
</div></div><div class="thread-post"><h3 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ppotts">ppotts</a> on May 26, 2016</div><div class="thread-post-content">I have good news &#8212; my whole project is up and running using armclang!
I did have trouble building the FreeRTOS source itself, so I built that as a library with the old compiler. That required setting &#8220;Enum Containers always int&#8221; and adding the compiler flag &#8220;&#8211;wchar32&#8221; in order to make a library that would link with the armclag-built code.
I have not been able to test everything yet but the basic tasks seem to be running with their expected timing, including interrupt handling with yielding from ISRs.
So far the only thing tricky I did was to make changes in portmacro.h.
<pre><code>#define portFORCE_INLINE __attribute__((always_inline))
</code></pre>
Then using the GCC syntax for assembly, for example, in ulPortRaiseBASEPRI:
<pre><code>__asm( "mrs %[ulReturn_], basepri; msr basepri, %[ulNewBASEPRI_]; dsb; isb" : [ulReturn_] "=r" (ulReturn) : [ulNewBASEPRI_] "r" (ulNewBASEPRI) );
</code></pre>
I have not tried <strong>attribute</strong> ((naked)) or looked at the generated assembly to see if it can be slimmed down. Right now I&#8217;m just happy it works so far.
I will be testing more so I&#8217;ll post updates if I come across anything strange.
I would like to get the FreeRTOS sources building with clang but I will have to look into that more later; there were problems with compiler intrinsics and other port-specific things.
</div></div><div class="thread-post"><h3 class="thread-post-title">Anyone Working on a Port to Keil/ARM Compiler 6.4 (ARMCLANG?)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 26, 2016</div><div class="thread-post-content">I wonder if ARM&#8217;s distribution is intended to build ARM compiler syntax. 
  The distribution we used was the &#8216;vanilla&#8217; one, which was happy with 
building GCC code (barring the one err mentioned in my previous post).
