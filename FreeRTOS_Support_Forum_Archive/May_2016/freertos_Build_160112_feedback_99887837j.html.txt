  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Build 160112 feedback</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jtbr">jtbr</a> on May 18, 2016</div><div class="thread-post-content">I thought I&#8217;d share my experience building this for an Atmel SAMV71Q21.
<ol>
<li>The Atmel software framework (ASF) includes FreeRTOS 7.0.3 as the latest version, and that will not work with +TCP, as it is missing some functionality. I built with the latest 8.2.3.</li>
<li>It&#8217;s important NOT to use the ASF module &#8220;PHY Ethernet MAC (GMAC) (driver)&#8221;, as this is superseded by the driver included in +TCP (under NetworkInterface/ATSAM4E). Otherwise the build will be tedious with conflicts, and it&#8217;s confusing as there are at least 5 gmac.h files. Hopefully the new driver is indeed compatible, but I haven&#8217;t gotten so far as to test yet.</li>
<li>configMAC<em>INTERRUPT</em>PRIORITY needs to be defined in FreeRTOSConfig.h in order to build, but it&#8217;s not clear how to set this (relative to other priorities used by +TCP). </li>
<li>FreeRTOS upgrade issues: configMAX<em>PRIORITIES needs to be an integer (with no casting [with older FreeRTOS it was <code>((unsigned portBASE_TYPE) 5)</code> and that bonks]). If you want to use vTaskList(), you now need to set a new configUSE</em>STATS<em>FORMATTING</em>FUNCTIONS to 1.</li>
<li>With respect to the <a href="http://www.freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/TCP_Networking_Tutorial_Adding_Source_Files.html">instructions</a>, it is also necessary to include  srcfreertos_plus-tcpportableNetworkInterface&#91;microcontroller] in the include paths. And in case step 2 of the instructions is confusing, you need to build all the .c files in that directory (not just NetworkInterface.c).</li>
<li>The code has a number of multiple declarations (FreeRTOS_netstat(), etc&#8230;) : it may be helpful to compile with -Wredundant-decls (in GCC) to find and eliminate them.</li>
<li>FreeRTOS_Sockets.h erroneously uses <code>#if __cplusplus</code> instead of <code>#ifdef __cplusplus</code>. </li>
<li>If you have certain warnings enabled in GCC, you&#8217;ll get hundreds of warnings about packed structs causing inefficient alignment. Under most circumstances these warnings are helpful, but not here. May I suggest using portable/Compiler/GCC/pack<em>struct</em>start.h to do this:
&#8220;`
/* disable warnings about inefficient alignment caused by packed (they are deliberate here) */</li>
</ol>
<h1>pragma GCC diagnostic push</h1>
<h1>pragma GCC diagnostic ignored &#8220;-Wattributes&#8221;</h1>
<h1>pragma GCC diagnostic ignored &#8220;-Wpacked&#8221;</h1>
<code>and at the end of pack_struct_end.h this:</code>
/* restore diagnostics */
<h1>pragma GCC diagnostic pop</h1>
&#8220;`

I would be grateful if you could post your code (at least the driver 
level, if the application cannot be posted) to the FreeRTOS Interactive 
site.  We are aware of people using FreeRTOS+TCP on various chips and 
would like to create a library of such things, but people seem to 
&#8216;forget&#8217; to post their code: 
http://interactive.freertos.org/forums/21211265-FreeRTOS-TCP
Comments below:
<blockquote>
  <ol>
  <li>configMAC<em>INTERRUPT</em>PRIORITY needs to be defined in FreeRTOSConfig.h
  in order to build, but it&#8217;s not clear how to set this (relative to
  other priorities used by +TCP).</li>
  </ol>
</blockquote>
You can use the SAM4E example as a reference here.  In most cases you 
would want to use <a 
href="http://www.freertos.org/RTOS-Cortex-M3-M4.html">the highest 
priority from which FreeRTOS API functions can be called</a>, but it is 
somewhat application dependent as the network might not be your highest 
priority.  The SAM4E demo has it set to 
configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY.
<blockquote>
  <ol>
  <li>FreeRTOS upgrade issues: configMAX<em>PRIORITIES needs to be an integer
  (with no casting [with older FreeRTOS it was ((unsigned
  portBASE</em>TYPE) 5) and that bonks]). If you want to use vTaskList(),
  you now need to set a new configUSE<em>STATS</em>FORMATTING_FUNCTIONS to 1.</li>
  </ol>
</blockquote>
That cast is often getting in the way now, normally when the definition 
is used in a pre-processor directive which doesn&#8217;t understand the cast.
<blockquote>
  <ol>
  <li>If you have certain warnings enabled in GCC, you&#8217;ll get hundreds of
  warnings about packed structs causing inefficient alignment. Under
  most circumstances these warnings are helpful, but not here. May I
  suggest using portable/Compiler/GCC/pack<em>struct</em>start.h to do this:
  |/* disable warnings about inefficient alignment caused by packed
  (they are deliberate here) <em>/ &#35;pragma GCC diagnostic push &#35;pragma
  GCC diagnostic ignored &#8220;-Wattributes&#8221; &#35;pragma GCC diagnostic
  ignored &#8220;-Wpacked&#8221;|
  and at the end of pack_struct_end.h this:
  |/</em> restore diagnostics */ &#35;pragma GCC diagnostic pop|</li>
  </ol>
</blockquote>
Right.  In this case packed structures is a necessity.
<blockquote>
  <ol>
  <li>The code has a number of multiple declarations (FreeRTOS_netstat(),
  etc&#8230;) : it may be helpful to compile with -Wredundant-decls (in
  GCC) to find and eliminate them.</li>
  </ol>
</blockquote>
Not sure about this one and will have to follow your suggestion to see.
<blockquote>
  <ol>
  <li>FreeRTOS_Sockets.h erroneously uses |&#35;if __cplusplus| instead of
  |#ifdef __cplusplus|.</li>
  </ol>
</blockquote>
Fixed &#8211; thanks.
