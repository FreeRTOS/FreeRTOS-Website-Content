  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Message Queue Errors</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dnewby">dnewby</a> on December 4, 2015</div><div class="thread-post-content">FRTOS v8.2.0
DEV HW: Freescale TWR-K60D100M (ARM Cortex M4)
I have a simple producer consumer set up:
Producer and Consumer task priorities are equal.
void vMsgProducerTask(task<em>param</em>t pvParameters)
{
    char message[MSG<em>SIZE];
    printf(&#8220;starting producer tasknr&#8221;);
    uint32</em>t x = 0;
    for(;;)
    {
        sprintf(message,&#8221;Message # %d&#8221;,x);
        printf(&#8220;producing message %dnr&#8221;,x);
        CHECK<em>ERR(OSA</em>MsgQPut(msgQ1<em>handle,message) != kStatus</em>OSA<em>Success);
        x++;
        OSA</em>TimeDelay(3000);
    }
    OSA_TaskBlock();
}
void vMsgConsumerTask(task<em>param</em>t pvParameters)
{
    char message[MSG<em>SIZE];
    printf(&#8220;nrstarting consumer tasknr&#8221;);
    for(;;)
    {
        memset(message,0,MSG</em>SIZE);
        CHECK<em>ERR(OSA</em>MsgQGet(msgQ1<em>handle,message,OSA</em>WAIT<em>FOREVER) != kStatus</em>OSA<em>Success);
        printf(&#8220;consuming message: %snr&#8221;,message);
    }
    OSA</em>TaskBlock();
}
int main(void)
{
    hardware_init();
    TaskCreate(CONSUMER);
    TaskCreate(PRODUCER);
    vTaskStartScheduler();
}
OSA<em>MsgQPut() maps to xQueueSendToBack()
OSA</em>MsgQGet() maps to xQueueReceive()
So when this code is ran, the following happens:
1. Consumer task starts, blocks waiting for message. Queue adds consumer task to xTasksWaitingToReceive.
2. Producer task starts, creates message. uxMessagesWaiting increments. Producer task yields.
3. Consumer task resumes. Consumer task runs and blocks for new message.
4. Producer task resumes. Break before generating message. This time, the queue has added the producer task to the xTasksWaitingToReceive list. 
In xTaskRemoveFromEventList(), the xEventListItem next and previous values are 0&#8217;s and this causes a hard fault in uxListRemove().
I would think that the consumer task should be added to the waiting list for the message queue (as was done in the first iteration), but the producer task was added instead. And the producer task doesnt need to wait for the queue&#8230;
Any thoughts, suggestions, etc for this?
</div></div><div class="thread-post"><h3 class="thread-post-title">Message Queue Errors</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 4, 2015</div><div class="thread-post-content">First a couple of comments:
<ul>
<li>I can&#8217;t see anything in your code that shows the queue being created.  Maybe you just left that out for brevity, but it would be interesting to see what the queue is being created to hold.  The main reason for asking is that you are declaring a buffer on the stack of one task, then sending that buffer to the other task &#8211; but how is the message going through the queue?  If it is copying the buffer into the queue then that should work, albeit perhaps in not the most efficient way.  If on the other hand you are just queuing a pointer to the buffer then the consumer will end up with a pointer to memory that is declared on the stack of another task &#8211; that is not good &#8211; especially as the producer is able to overwrite the memory at any time.</li>
<li>How is printf() implemented?  You are calling it from more than one task, which means it may need to be called from a critical section (vTaskSuspendAll()/xTaskResumeAll() for example).  Also, make sure its implementation is not going to interfer with the execution of the task.</li>
<li>Where did the OSA_nnn functions come from?  Are they from the Freescale KSDK?  If so, I&#8217;m sure they will be fine, but if not, try calling the native API directly.  That would at least allow me to see how the API was being used.</li>
</ul>
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Message Queue Errors</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 7, 2015</div><div class="thread-post-content">I&#8217;m afraid the fact that the message<em>size parameter is being multipled by sizeof( uint32</em>t ) makes me realise I don&#8217;t know how the OSA_nnn version of the functions are intended to be used.  Normally when creating a queue you would pass in the queue item size exactly as you would expect to get back when calling sizeof() on the data type being queued.  In this case it looks like it is wanting the number of 32-bit values &#8211; which would suggest it could possibly also want 32-bit alignment &#8211; which may be the cause of your issue.
</div></div><div class="thread-post"><h3 class="thread-post-title">Message Queue Errors</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dnewby">dnewby</a> on December 8, 2015</div><div class="thread-post-content">It looks like I can adjust the size of the message (by altering the message structure) and can get it to work just fine. But, if I create the queue with a size that is different than that of the message that will be posted to it, it will end up with some unexpected behaviors. Is that what you would expect? Even if the object you are posting is smaller than the defined size when you created it?
</div></div><div class="thread-post"><h3 class="thread-post-title">Message Queue Errors</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 8, 2015</div><div class="thread-post-content">In FreeRTOs each space in the queue is the same size.  For example, lets say each space in 10 bytes.  If you then try to queue an 4 byte object, then 10 bytes will be copied into the queue &#8211; so you will get the 4 bytes you intended, plus the 6 following bytes.  That should not be a problem when sending to a queue &#8211; but the opposite is not true.  In the above example, when reading from the same queue, you must supply a buffer that is at least 10 bytes long, as 10 bytes will be copied out of the queue.
