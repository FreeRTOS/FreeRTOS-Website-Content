</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to stop the scheduler when leaving bootloader to go to main application?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on January 22, 2016</div><div class="thread-post-content">Is this what you are doing:
set up VTOR for the boot loader
run boot loader
disable interrupts completely in the core (cpsid i instruction)
set up VTOR for the application code
jump to start up routine for the application to configure the C run time (dont enable interrupts here)
jump to application main()
Interrupts will be enabled when the scheduler starts.

</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to stop the scheduler when leaving bootloader to go to main application?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 23, 2016</div><div class="thread-post-content"><blockquote>
  I am not sure I understand the Cortex interrupts and how the FreeRTOS
   port uses them completely,
</blockquote>
You are not the only one, which is why we provide the following page:
http://www.freertos.org/RTOS-Cortex-M3-M4.html &#8230;. but the more you try 
and explain it the more complex it becomes ;o)
FreeRTOS never disables interrupts completely, it only masks them up to 
a user defined priority.  The difference is:
<ul>
<li>The &#8220;cpsid i&#8221; instruction globally disables all interrupts within the 
processor core itself.</li>
<li>taskDISABLE_INTERRUPTS masks interrupts up to the user defined 
priority, but does not globally disable all interrupts, so some 
interrupts remain enabled.</li>
</ul>
<blockquote>
  The taskENTER_CRITICAL seems to set BASEPRIO to 0x10 (the 4 high bits
   are significant). I think that means it should disable everything
  with lower priority than the highest priority 0, right?
</blockquote>
No, it disables everything with the priority 0x10 and lower.  Remember, 
on the ARM Cortex-M, the lower the numeric priority the higher the 
logical priority.  So, setting BASEPRI to 0x10 does not disable 
interrupt priority 0 (or 1, 2, etc.) because those priorities have a 
lower numeric value and therefore a HIGHER logical priority.  This is 
why it is so confusing for people.
<blockquote>
  It appears that the system timer tick is running at priority zero
</blockquote>
It shouldn&#8217;t be, it should be running at the lowest possible priority. 
As above, 0 is the highest possible priority, not the lowest, and the 
tick definitely must not run at priority 0.
If you are using a recent version of FreeRTOS then ensure <a 
href="http://www.freertos.org/a00110.html#configASSERT">configASSERT()</a> 
is defined, because that will automatically check the interrupt priority 
settings for you, and the assert will fail if they are wrong.
</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to stop the scheduler when leaving bootloader to go to main application?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ppotts">ppotts</a> on January 29, 2016</div><div class="thread-post-content">Thank you for taking the time to explain. If you are willing to take a little longer I think I am just about there. I have read that document you linked to yet again. This must be the fifth time&#8230; I also read this: http://embeddedgurus.com/state-space/2014/02/cutting-through-the-confusion-with-arm-cortex-m-interrupt-priorities/
I think there is further confusion due not only to the reversed counting of priorities, but to the use of a subset of bits that is shifted towards the high bits.
So,
In my build, __NVIC<em>PRIO</em>BITS is 4
configLIBRARY<em>LOWEST</em>INTERRUPT<em>PRIORITY is 0xF
configLIBRARY</em>MAX<em>SYSCALL</em>INTERRUPT_PRIORITY is 0x1
I take this to mean that 1 is the next-to-highest priority (not numerically highest, but logically highest).
The document says &#8220;The RTOS interrupt nesting scheme splits the available interrupt priorities into two groups &#8211; those that will get masked by RTOS critical sections, and those that are never masked by RTOS critical sections and are therefore always enabled. The configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY setting in FreeRTOSConfig.h defines the boundary between the two groups.&#8221;
However, I don&#8217;t find this to be perfectly clear. &#8220;Defines the boundary&#8221; could be read as either &#8220;this value and logically higher values are not masked,&#8221; or &#8220;values logically higher than this value are not masked.&#8221; So I am not clear whether priority 1 can be masked by FreeRTOS critical sections.
There are two more macros, configKERNEL<em>INTERRUPT</em>PRIORITY and configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY that are based on the previous two macros but take into account the number of priority bits, to shift them into the high bits.
So in this case configKERNEL<em>INTERRUPT</em>PRIORITY becomes 0xF &lt;&lt; 4 = 0xF0
That should be the logically lowest priority ready to put into BASEPRI
The other one is configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY and that turns into 1 &lt;&lt; 4 = 0x10
That should be the logically next-to-highest priority ready to put into BASEPRI
Trying to figure out the actual priority used for the system clock is buried under more layers of macros. It looks like my port defines #define portNVIC<em>SYSTICK</em>PRI                ( ( ( uint32<em>t ) configKERNEL</em>INTERRUPT_PRIORITY ) &lt;&lt; 24UL )
Which should mean that is 0xF0000000
It looks like that is formatted to be placed in portNVIC<em>SYSPRI2</em>REG
That is defined as ( * ( ( volatile uint32_t * ) 0xe000ed20 ) ) but I don&#8217;t find that address in any of the chip headers so I&#8217;m not certain what that is, but I&#8217;ll take it as a given that the lowest available priority setting is assigned to the system tick.
But I&#8217;m still unclear on why taskENTER<em>CRITICAL could not disable that. We seem to have a chain of definitions, taskENTER</em>CRITICAL -> portENTER<em>CRITICAL -> vPortEnterCritical() which calls portDISABLE</em>INTERRUPTS -> vPortRaiseBASEPRI -> which sets BASEPRI to configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY which is 0x10 (next-to-highest logical priority, shifted into the high bits).
That should have blocked the timer tick, which has the the lowest logical priority, right? (But it did not seem to in my case, because disabling the timer tick fixed the crash problem, while calling taskENTER_CRITICAL only did not).
You wrote &#8220;No, it disables everything with the priority 0x10 and lower. Remember, 
on the ARM Cortex-M, the lower the numeric priority the higher the 
logical priority. So, setting BASEPRI to 0x10 does not disable 
interrupt priority 0 (or 1, 2, etc.) because those priorities have a 
lower numeric value and therefore a HIGHER logical priority. This is 
why it is so confusing for people.&#8221;
But I think putting 0x10 in BASEPRI should allow interrupts with numeric priority 0 and disable interrupts with numeric priority 1 or greater (lower logical priority). (Remember, the bits are shifted up by 4).
If that is not the case&#8230; then it seems like the port is not defining things sensibly, with its definitions of configKERNEL<em>INTERRUPT</em>PRIORITY and configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY, because using those values would never disable _any</em> of the actual 16 interrupt priority levels used on this chip? I think if that was the case, the port would not work right.
Thanks for any clarification.
</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to stop the scheduler when leaving bootloader to go to main application?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on January 29, 2016</div><div class="thread-post-content">configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY is the highest logical priority that can use the API, so the highest priority that is masked by a critical section. If configLIBRARY</em>MAX<em>SYSCALL</em>INTERRUPT_PRIORITY is 1 then a critical section will mask priority 1 interrupts, but not priority 0 interrupts. I think it might be impossible to mask priority 0 interrupts actually because writing 0 to BASEPRI enables all interrupts.
The system clock has to have the lowest priority so it looks like 0xF0 is right for that here, and yes I think the same the BASEPRI of 0x10 should block that.
