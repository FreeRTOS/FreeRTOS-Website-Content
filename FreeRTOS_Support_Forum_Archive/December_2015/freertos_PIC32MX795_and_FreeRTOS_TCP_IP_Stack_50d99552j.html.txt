</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX795 and FreeRTOS TCP/IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 12, 2015</div><div class="thread-post-content">Hi Dani,
<strong>About the memory use of FreeRTOS +TCP</strong>
&#8220;Network Buffer Descriptors&#8221; are the objects that hold the network messages. They normally have a short life, after a few ms they are delivered to their destination.
The UDP protocol uses discrete messages. Therefore these message will stay in their &#8216;Network Buffer Descriptors&#8217; while waiting to be picked up by <code>FreeRTOS_recvfrom()</code>.
When TCP receives new data, the contents of the &#8216;Network Buffer Descriptors&#8217; is copied to an RX stream buffer. Outgoing data (<code>FreeRTOS_send()</code>) will be copied a the TX stream buffer.
The advantage is that if you send many small messages, they will end up into a single contiguous buffer, and sent-out in maximum-size packets (MSS).
So every connected TCP socket will get a TX and RX stream buffer. Once a stream buffer is created, its size is fixed.
The default stream buffer sizes are defined with:
~~~~~
/* Define the size of Rx buffer for TCP sockets. */
<h1>define ipconfigTCP<em>RX</em>BUF_LEN          ( 3 * 1460 )</h1>
/* Define the size of Tx buffer for TCP sockets. */
<h1>define ipconfigTCP<em>TX</em>BUF_LEN          ( 2 * 1460 )</h1>
~~~~~
But indeed they can be adjusted at runtime, see:
http://www.freertos.org/FreeRTOS-Plus/FreeRTOS<em>Plus</em>TCP/API/setsockopt.html
Probably the easiest way is to use is <code>FREERTOS_SO_WIN_PROPERTIES</code>. It will overwrite the above defaults in a single call.
Set the window properties <strong>before</strong> a socket gets connected: the listening socket that will <code>accept()</code> a new connection, or a client socket that will <code>connect()</code> to a remote one.
Note that when <code>accept()</code> succeeds, all socket properties will be inherited by the new child socket, including stream buffer sizes (and also the local port number will be the same as its parent socket).
<strong>Using BufferAllocation 1 or 2 ?</strong>
Have you seen the difference between BufferAllocation<em>1 and BufferAllocation</em>2?
Both modules will provide this number of Network Buffer Descriptors:
~~~~~
<pre><code>#define ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS    ??
</code></pre>
~~~~~
Version 1 is more efficient, it reserves all buffer space by calling the user-provided <code>vNetworkInterfaceAllocateRAMToBuffers()</code> right after start-up.
The advantage of version 1 is that all network buffer descriptors are guaranteed to be available and no more calls to <code>pvPortMalloc()</code> are necessary.
In version 2 only the Descriptors are allocated at start-up, and the actual Buffers will be malloc&#8217;d when needed. Small messages will use small buffers.
In general: platforms with more than enough (SD)RAM will use <code>BufferAllocation_1.c</code>.
<strong>About the backlog parameter in <code>listen()</code></strong>
Looking at http://linux.die.net/man/2/listen :
<pre><code>int listen(int sockfd, int backlog);
</code></pre>
The official meaning of <code>backlog</code> is the following:
&#8220;The backlog argument defines the maximum length to which the queue of pending connections for sockfd may grow.&#8221;
FreeRTOS is typically running on a smaller system with less resources and the definition is slightly (only slightly) different:
&#8220;The backlog argument defines the maximum of connections that can be established to the socket simultaneously.&#8221;
It is important to let +TCP send keep-alive messages in an idle connection:
~~~~~
<pre><code>/* Include support for TCP keep-alive messages. */
#define ipconfigTCP_KEEP_ALIVE              ( 1 )
#define ipconfigTCP_KEEP_ALIVE_INTERVAL     ( 20 ) /* in seconds */
</code></pre>
~~~~~
Otherwise a service might become unreachable because of &#8216;dead&#8217; connections.
A TCP connection becomes dead if the remote device is switched off suddenly without properly closing the connection.
If keep-alive messages are being used, +TCP device will quickly detect that the remote end doesn&#8217;t respond any more.
An alternative to the above is it send keep-alive message at the user level. In a Telnet client for instance you could send empty lines (CR/LF) regularly to keep the remote end happy.
Enough text for now. I hope it clarifies things, and if not, please ask!
Regards

</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX795 and FreeRTOS TCP/IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 1, 2016</div><div class="thread-post-content">Hi Dani,
The Nagle algorithm has indeed not been implemented in the +TCP stack. Many real-time programmers tend to disable this feature because they want their messages to be delivered instantly.
Can you make an estimate of how many packets of what size you expect to be sending?
Normally the delayed ACK of 200 ms (on the remote end) shouldn&#8217;t bother you. And if it does bother, you&#8217;d have to look at the following:
1) The default size of the socket TX buffer:
~~~~~
  /* Define the size of Tx buffer for TCP sockets. */
  #define ipconfigTCP_TX_BUF_LEN            ( 2 * 1460 )
~~~~~
2) Or maybe you&#8217;ve set it manually:
~~~~~
  The socket option &#8216;FREERTOS<em>SO</em>SNDBUF&#8217;
~~~~~
3) Or you can set both the buffer- and WIN-sizes in a single call to FreeRTOS_setsockopt() :
~~~~~
  Or the socket option &#8216;FREERTOS<em>SO</em>WIN_PROPERTIES&#8217;
~~~~~
Explanation:
Suppose that your TX buffer size is very small, 1000 bytes. You send 1000 bytes and the remote end delays the ACK for 200 ms.
What you can do (without changing buffer sizes), is send 2 times 500 bytes. As there is no Nagle algorithm, the packets will be sent immediately and the remote end will reply with an ACK after the second packet.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX795 and FreeRTOS TCP/IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 4, 2016</div><div class="thread-post-content">Hi Daniel,
<blockquote>
  we see 200ms delay between the outgoing packets on our http
  server implementation. There is one outgoing paket per ack. 
</blockquote>
I already proposed a solution for the 200ms ACK problem in an email, I will repeat it here so that other users can also read it:
Use the socket option &#8216;FREERTOS<em>SO</em>WIN_PROPERTIES&#8217;, because it allows you to set both the buffer size and WIN (as a multiple of MSS).
This post has two attachments in a ZIP file:
html_one.pcap : page loads in 9.3 seconds using a 730-byte buffer :
~~~~~
    #define ipconfigTCP<em>MSS ( 730 )
    xWinProps.lTxBufSize = ipconfigTCP</em>MSS;
    xWinProps.lTxWinSize = 1;
~~~~~
This is when WIN == 1 * MSS, very ineffective. +TCP must wait for 200 ms after every packet.
html_two.pcap : page loads in 0.3 seconds using a 1072-byte buffer :
~~~~~
    #define ipconfigTCP<em>MSS ( 536 )
    xWinProps.lTxBufSize = ( 2 * ipconfigTCP</em>MSS );
    xWinProps.lTxWinSize = 2;
~~~~~
Now WIN == 2 * MSS and the communication is pretty efficient.
Regards.
