  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">lwip port for STM32F107 repeats tx packets</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermajo">hermajo</a> on February 1, 2010</div><div class="thread-post-content">I just started to work with the freeRTOS port including the lwIP stack for the STM32 communication line devices.<br />
Everything works fine, but I found that every packet is sent twice. Diving deeper into the code I found that this<br />
is obviously done intentionally: a field &#8216;SendCount&#8217; is maintained with the Tx descriptor, which is evaluated in<br />
the Tx interrupt processing to repeat the last sent packet.  
<h2>Has anyone an idea, why this is implemented that way?</h2>
Joerg
</div></div><div class="thread-post"><h3 class="thread-post-title">lwip port for STM32F107 repeats tx packets</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 1, 2010</div><div class="thread-post-content">I would guess the Ethernet driver was copied from a uIP demo.&nbsp; It is quite common in uIP to send packets twice as a technique to speed up the ACK coming back from the other end of the link.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">lwip port for STM32F107 repeats tx packets</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stf12">stf12</a> on February 2, 2010</div><div class="thread-post-content">Hi Joerg,<br />
I observer this behavior and more over I found that the Ethernet driver is configured to work in promiscuous mode.<br />
I propose a fix to both this bugs. You find more information at the following web page <a href="http://developers.stf12.net/just-another-eclipse-demo-str91x">http://developers.stf12.net/just-another-eclipse-demo-str91x</a>. See the bug report &#35;B3.3 and &#35;B3.4  
Regards,<br />
Stefano

thanks a lot for your reply. For some reasons I didn&#8217;t look up the project page….<br />
I&#8217;m not sure id the fix you have described there is sufficient.<br />
I modified the source at thres positions:<br />
&#40;1&#41; in xEthInitialise&#40;&#41;:  
<pre><code>        /* SendCount must be initialized to 2 to ensure the Tx descriptor looks
         as if its available (as if it has already been sent twice. */
        [s]xTxDescriptor.SendCount = 2;[/s]
                xTxDescriptor.SendCount = 1;
</code></pre>
&#40;2&#41; in vMAC&#95;ISR&#40;&#41;  
<pre><code>        if (xTxDescriptor.SendCount == 0) {
            /* Send again! */
            (xTxDescriptor.SendCount)++;
[s]         xTxDescriptor.Status = ETH_DMATxDesc_OWN | ETH_DMATxDesc_LS
                    | ETH_DMATxDesc_FS | ETH_DMATxDesc_TER | ETH_DMATxDesc_TCH
                    | ETH_DMATxDesc_IC;
            ETH-&gt;DMASR = ETH_DMASR_TBUS;
            ETH-&gt;DMATPDR = 0;
[/s]            vReturnBuffer((unsigned char *) xTxDescriptor.Buffer1Addr);
        } else {
</code></pre>
&#40;3&#41; in vSendMACData&#40;&#41;  
<pre><code>    [s]while ((xTxDescriptor.SendCount &lt; 2) &amp;&amp; (xTxDescriptor.Status &amp; ETH_DMATxDesc_OWN) == ETH_DMATxDesc_OWN) {[/s]
    while ((xTxDescriptor.SendCount &lt; 1) &amp;&amp; (xTxDescriptor.Status &amp; ETH_DMATxDesc_OWN) == ETH_DMATxDesc_OWN) {
</code></pre>
At least it seems to work and my peer server application is not longer confused about the duplicated packets ;-&#41;<br />
