  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC24 / dsPIC port and DSP addressing modes</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ericwalker">ericwalker</a> on February 22, 2010</div><div class="thread-post-content">I have experimented with FreeRTOS in the past on a dsPIC33 but at the time was not using any DSP libraries.&nbsp; I am begining a new project that will require using several of the DSP library routines and was about to build it on top of FreeRTOS to make handling the multiple tasks easier when I came across the following post on the Microchip forums.  
<a href="http://www.microchip.com/forums/tm.aspx?m=478816">http://www.microchip.com/forums/tm.aspx?m=478816</a>  
The issue stems from the special addressing modes used by certain DSP routines.&nbsp; These require the use of the MODCON register which FreeRTOS appears not to push/pop when needed.  
Has anyone here had any experience with this issue?  
-Eric  
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 / dsPIC port and DSP addressing modes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 23, 2010</div><div class="thread-post-content">It shouldn&#8217;t be too hard to add the saving of that and the related registers &#40;I suspect that you would need to save MODSRT/END registers too. You just need to add the Push/Pop to vPortYield in portasm&#95;dspPic.s, and the matching pop to the portRESTORE&#95;CONTEXT macro in port.c, and add initial values for the registers in the stack frame defined in xInitialStack in port.c  
That should be all the places that know about the stack frame used for task switching &#40;you may need to raise the minimum stack size a bit to compinsate for the additional information on the stack&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 / dsPIC port and DSP addressing modes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ericwalker">ericwalker</a> on February 23, 2010</div><div class="thread-post-content">Richard,  
Thanks for the quick reply.&nbsp; It has been several months since I played with FreeRTOS and I have not yet used the DSP functionality of the dsPIC so I am a bit hesitant to jump right in and make changes to the kernel code.&nbsp; But, if nobody else has worked around this issue and can say exactly what they changed &#8211; and that they tested it and it worked &#8211; then I may have to tackle this myself.&nbsp;   
Someone on the Microchip forum mentioned that another RTOS had a DSP flag that would tell the kernel whether or not to save the DSP related registers.&nbsp; This seem like best general solution, adding a setting to the FreeRTOSConfig.h file.  
Can anyone confirm or deny that the changes mentioned are the only ones I would need to make?  
Thanks again.  
-Eric  
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 / dsPIC port and DSP addressing modes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 23, 2010</div><div class="thread-post-content">The dsPIC port was created some time back, but I seem to recall discussing this with Microchip at the time and the feeling was that the true deep DSP context didn&#8217;t need to be part of the task context because it was very unlikely that an application would make use of it from more than one task in any case.&nbsp; If only one task is using the registers then they don&#8217;t need saving or restoring &#8211; unless you can tell me otherwise&#40;?&#41;.&nbsp;   
In this sense I suppose the DSP registers are being treated sort of like a peripheral, although code is generated automatically that uses the registers by the compiler so its a bit of a weak analogy.  
richard&#95;damon is right in that it should be a trivial task to add the DSP registers if it is thought necessary &#8211; that is if you are going to be performing DSP routines from more than one task.&nbsp; All that should be required is extra space to be reserved on the stack where the stack is initially set up &#8211; then the DSP registers to be pushed and popped along with the other registers in the portSAVE&#95;CONTEXT&#40;&#41; and portRESTORE&#95;CONTEXT&#40;&#41; macros.  
<blockquote>
  Someone on the Microchip forum mentioned that another RTOS had a DSP flag that would tell the kernel whether or not to save the DSP related registers. This seem like best general solution, adding a setting to the FreeRTOSConfig.h file.
</blockquote>
Yes this would be a good solution too and this is in effect how we deal with processors that have floating point hardware.&nbsp; Rather than have the overhead of saving and restoring floating point registers for every task, even if the tasks aren&#8217;t using floating point &#40;as most don&#8217;t&#41;, the task-switched-in and task-switched-out macros are configured to save and restore the floating point registers for just the tasks that have indicated that they need them.&nbsp; It makes a very efficient &#40;in both memory and execution time&#41; solution, but is perhaps just a little ugly?  
I would be interested to know how people are using the DSP libraries in real life applications.&nbsp; In my experience &#40;which is limited to my experience&#41; they would tend to be used for things like field orientated motor control, which is performed very quickly and repeatedly, and therefore I would image the original assumption that this would not be done from more than one task would hold.&nbsp; Maybe that is too restrictive?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 / dsPIC port and DSP addressing modes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ericwalker">ericwalker</a> on February 23, 2010</div><div class="thread-post-content">Richard,<br />
I appreciate your involvement in this issue.&nbsp;<br />
In my application I will probably be doing some convolution and/or filtering of data coming from the ADC at one rate and then running a PID loop at a lower rate.&nbsp; I am very early in the design of this project – which is for graduate work, not my day job – so I am speculating a bit on what I will need to do.<br />
If I am limited to running all the DSP routines from one task that is probably not a significant problem.&nbsp; However, I anticipate I will have DSP processing running at very different rates, the input filtering, CIC, etc. the I &amp; Q processing, the PID loop, etc.&nbsp; At this stage I would think it might be easier to separate these in to more than one task if possible.<br />
Unfortunately I am not up to speed enough right now to add much original input to this discussion.&nbsp; I just started reading through the Programmer’s Reference Manual last night to try to better understand the special addressing modes of the DSP class instructions and how those might be affected by context switches or even interrupts.&nbsp; I will also have to study the FreeRTOS code to understand what it is doing on context switches.<br />
There was some continued discussion on the Microchip forum, and one comment specifically, that I may still need to save and restore the MODCON register but, that it may not be possible to have DSP class routines running in more than one thread because some of the status bits are read-only and so cannot be restored by a context switch.&nbsp; Unfortunately, as I said before, I am not familiar enough with the inner working yet to confirm or deny this assertion.&nbsp;<br />
Thanks again for your time on this issue.  
-Eric
