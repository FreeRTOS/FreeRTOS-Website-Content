  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Call to xTaskGetTickCount in an ISR</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrecas">jrecas</a> on February 25, 2010</div><div class="thread-post-content">Hi guys  
I have noticed that if you call xTaskGetTickCount inside an interrupt, the FreeRTOS &#40;for msp430&#41; stops working. I think this is due to the portENTER&#95;CRITICAL&#40;&#41;; / portEXIT&#95;CRITICAL&#40;&#41;; inside xTaskGetTickCount, because the interrupts should no be enabled in any case inside my ISR.  
Can be this a bug in the msp430 port? should I implement a new funtion &#40;xTaskGetTickCountFromISR&#41; that just return the tickcounter without enter/exit critical?  
Thanks&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Call to xTaskGetTickCount in an ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 25, 2010</div><div class="thread-post-content">No this is not a bug but the expected behavior. The rule is, if the function does not end in &#8220;FromISR&#8221; then don&#8217;t call it from an ISR.  
The critical section is necessary on the MSP430 if you have configUSE&#95;16&#95;BIT&#95;TICKS set to 0, which would be normal. When this is so the tick count is 32 bits but the processor is only 16 bits so accesses will never be atomic.   
If you protect the tick count with the critical section when you are executing tasks then you should just be able to access the variable directly when you are executing interrupts but you might have to remove its static qualification. Or you could provide a FromISR version of xTaskGetTickCount&#40;&#41; that does not have the critical section.
</div></div><div class="thread-post"><h3 class="thread-post-title">Call to xTaskGetTickCount in an ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrecas">jrecas</a> on February 25, 2010</div><div class="thread-post-content">I understand why the critical section is necessary, but I didn&#8217;t know that functions without FromISR can not be called inside an ISR.  
I will implement the new FromISR version.   
Thank you&#33;&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Call to xTaskGetTickCount in an ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrecas">jrecas</a> on February 25, 2010</div><div class="thread-post-content">BTW in the msp430 implementation taskYIELD&#40;&#41; does not have a FromISR and is called in the Usart Rx ISR. It is safe to use it inside an interrupt? And can be called inside a function that has been called from an ISR? I mean, the ISR calls a function that, after sending some data through a queue &#40;using send From ISR&#41; may need taskYIELD&#40;&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Call to xTaskGetTickCount in an ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 25, 2010</div><div class="thread-post-content"><blockquote>
  BTW in the msp430 implementation taskYIELD&#40;&#41; does not have a FromISR and is called in the Usart Rx ISR.
</blockquote>
If that is what the official demo is doing then it will be fine &#8211; however this does not hold true for all ports, some of which have a different yield function or mechanism for use inside an interrupt.
