  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Semaphore monopolization</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akuros">akuros</a> on February 23, 2010</div><div class="thread-post-content">FreeRTOS V6.0.2 and V5.0.2.  
It is possible to make taking semaphore impossible. It happens when tasks running on equal priorities try to take semaphore. First one &#40;see task1 below&#41; takes semaphore rarely for short time, the second one &#40;see task2 below&#41; takes semaphore for longer time but gives it back for a very short time. Takin semaphore in task1 never succeeds. Explicit taksYIELD&#40;&#41; would walk around this problem, but it has significant impact on performance.  
Simply giving semaphore doesn&#8217;t switch context to waiting task.<br />
I think it is a BUG but I can&#8217;t make a bug request. Can anyone help?  
<pre><code>xSemaphoreHandle sem ;
void task1(void *pvParam)
{
    while(1) {
        if (xSemaphoreTake(sem, 100)) {
            // BUG! We should be able to go into here, but it never happens
            xSemaphoreGive(sem) ;
            vTaskDelay(100) ;
        }
    }
}
void task2(void *pvParam)
{
    while (1) {
        if (xSemaphoreTake(sem, 50)) {
            // Let's do something time consuming with semaphore taken
            vTaskDelay(100) ;
            xSemaphoreGive(sem) ;
        }
    }
}
int main( void )
{
    prvSetupHardware();
    xTaskHandle thDummy ;
    sem = xSemaphoreCreateMutex();
    xTaskCreate(task1, (signed portCHAR*)"1", configMINIMAL_STACK_SIZE, NULL, 1, &amp;thDummy) ;
    xTaskCreate(task2, (signed portCHAR*)"2", configMINIMAL_STACK_SIZE, NULL, 1, &amp;thDummy) ;
    vTaskStartScheduler();
}
</code></pre>
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 23, 2010</div><div class="thread-post-content">xSemaphoreGive&#40;&#41; calls xQueueGenericSend&#40;&#41;.&nbsp; Then within xQueueGenericSend&#40;&#41; &#40;on line 474 of V6.0.2&#41; there is a call to xTaskRemoveFromEventList&#40;&#41; which will return true if the queue send caused a task of EQUAL OR HIGHER priority to unblock &#40;despite what the comment says&#41;. xTaskRemoveFromEventList&#40;&#41; returning true will cause a yield, which is what you say should happen but isn&#8217;t. It looks ok to me.  
It is possible that in your example the timing is such that one task always yields to the other just at the end of the time slice, meaning that a yield is performed back again almost immediately. This would be legitimate behavior.
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akuros">akuros</a> on February 23, 2010</div><div class="thread-post-content">I is not about timing. Code below still shows the problem  
<pre><code>xSemaphoreHandle sem ;
void task1(void *pvParam)

}
void task2(void *pvParam)

    }
}
</code></pre>
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akuros">akuros</a> on February 23, 2010</div><div class="thread-post-content">What is interesting, taskYIELD is called within xSemaphoreGive, but it looks like double context switch happens. Unblocked task was transferred to ready list, byt then taskYIELD cause context switch to the next one.
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rawka">rawka</a> on February 24, 2010</div><div class="thread-post-content">Akuros, I think your code works as designed, too.   
As I understand, in your example task2 will poll the system constantly and it excludes task1 processing with the semaphore. So task1 will &#8211; most likely &#8211; never got available time-slice to run &#40;but it could happen, if the scheduler break task2 execution after sem.give and before the sem.take, but this is very unlikely&#41;, because they are on same priority level, and task2&#8217;s sem.give will not force a context switch.  
However, I&#8217;m not telling that there isn&#8217;t bug in the scheduler, but I think this is not that scenario, where the scheduling fails.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akuros">akuros</a> on February 24, 2010</div><div class="thread-post-content">Probably the code works as designed, but not as intended. task1 and task2 are on the same priority to keep priorities count as low as possible, to lower memory usage for semaphore and speedup scheduling mechanism. As I suspect a semaphore &#40;as a queue&#41; contains priority list of tasks waiting for the semaphore to unblock them on xSemaphoreGive. If it doesn&#8217;t work as in example, semaphore could be built on simple volatile portBASE&#95;TYPE, and could have significant lower memory usage.  
However, I think it is still a bug, because in xQueueGenericSend there is an intended taskYIELD when we are giving back a semaphore which other task &#40;on priority &gt;= current&#41; is waiting on.   
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 24, 2010</div><div class="thread-post-content">I&#8217;m not really following this.  
It would appear to me that when a task gives a semaphore back then a context switch will be performed if there is a task of equal or higher priority that was blocked waiting for the semaphore.&nbsp; I think this is the expected and wanted behaviour.  
If two tasks of equal priority then attempt to take the semaphore either could get it &#8211; there are no guarantees there.  
Have I missed something?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore monopolization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akuros">akuros</a> on February 24, 2010</div><div class="thread-post-content"><blockquote>
  If two tasks of equal priority then attempt to take the semaphore either could get it &#8211; there are no guarantees there.
</blockquote>
But when a task is already blocked on semaphore, and semaphore holder gives it back the context switch should be performed to the next waiting for this semaphore. In the example context switch is performed, but context remains in task giving semaphore. So the otther task has no chance to take it.  
On xSemaphoreGive expected and wanted behaviour is that the context is switched to the next task waiting on the semaphore. And this task should be able to take it, because it is waiting for it. If there was such guarantee here, it would be really useful.  
Regards.
