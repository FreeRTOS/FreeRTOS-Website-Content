  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Scheduling</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bfleming">bfleming</a> on July 16, 2012</div><div class="thread-post-content">_Pardon the brevity of this post, I wrote up a fairly length discussion only to have it flagged as SPAM; which instead of letting me just log in decided to just delete all my work. _  
In vxWorks I could have n tasks all blocked on the same rate semaphore, and have a &#8216;scheduler&#8217; task reset the rate semaphore causing all blocked tasks to become ready at which point they&#8217;d run in priority order. The biggest benefit was the &#8216;scheduler&#8217; task didn&#8217;t have to know how many tasks were in the system, just when to release which rates.   
How would I do something similar in freertos? I bought the PDFs hoping they would have the solution &#40;it didn&#8217;t&#41;. The examples in the book barely discuss dealing with more than one task. If I only had 1-2 tasks I wouldn&#8217;t need an OS.  
The queue API specifically says it only release ONE reader on a block, which isn&#8217;t good. And since semaphores seems to be 2nd class citizens they suffer the same unfortunate fate.  
Ideas?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 17, 2012</div><div class="thread-post-content">One way to active this is to have a list of semaphores to be signaled when the time comes, and rather than signal just one, run a loop and signal the whole list. If you need to do this a lot, it shouldn&#8217;t be hard to write a simple set of routines to manage this, adding the feature as a layer above the FreeRTOS kernel. The fact that is can be easily done as a user routine may be one reason the capability isn&#8217;t built into the core of FreeRTOS.
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bfleming">bfleming</a> on July 17, 2012</div><div class="thread-post-content">I guess my one concern, and maybe it really isn&#8217;t, is that triggering the semaphores in a loop isn&#8217;t atomic. I&#8217;ll also have to setup an framework for everyone to share the semaphores that each task wants triggered if I truly want a decoupled system.  
I know what I did in vxWorks was more of a trick than a feature, but I&#8217;ve looked at other APIs and it seems that doing a reset on a semaphore is common, and it may have come from posix. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 17, 2012</div><div class="thread-post-content">If you want the operation atomic, then just disable the scheduler before signaling all the semaphores, then re-enable it after, then no task can interfere with the process by being started when it is signaled. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 17, 2012</div><div class="thread-post-content">It is not always a good idea to call API functions with the scheduler disabled &#40;depends on the API function itself&#41;, but you can temporarily raise the task priority to the highest in the system during the operation, then lower it back to its original priority afterwards.  
Regards.
