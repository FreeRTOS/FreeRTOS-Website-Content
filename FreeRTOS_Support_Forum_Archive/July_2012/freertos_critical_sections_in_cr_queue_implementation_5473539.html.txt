  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">critical sections in cr queue implementation</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on July 26, 2012</div><div class="thread-post-content">While implementing optimized critical section macros for the MSP430 port, I notice that xQueueCRSend and xQueueCRReceive use portDISABLE&#95;INTERRUPTS&#40;&#41;/portENABLE&#95;INTERRUPTS&#40;&#41; instead of portENTER&#95;CRITICAL/portLEAVE&#95;CRITICAL to implement a critical section &#40;at least, in V7.1.1&#41;.  
An unusual but valid design for MSP430 programs is to leave interrupts disabled at all times except when in low power mode.&nbsp; The new macros I&#8217;ve implemented restore the interruptibility state to what it was when the first critical section was entered, rather than unconditionally enabling interrupts, so FreeRTOS can be used with applications that follow this design.  
Explicitly enabling interrupts in xQueueCRSend and xQueueCRReceive breaks this feature for MSP430 programs that use coroutines.  
Since taskENTER&#95;CRITICAL is defined in terms of portENTER&#95;CRITICAL, I believe it should be possible to assume the port-named versions are available, and to use them &#40;if the intent was to avoid &#8220;task&#42;&#8221; invocations in coroutine support&#41;.&nbsp; Is there a reason why the existing critical section approach is required for these functions?  
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">critical sections in cr queue implementation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 26, 2012</div><div class="thread-post-content">I don&#8217;t really recall, although the co-routines run at the lowest priority and are co-operative, so the critical section nesting is not as necessary.  
I would be interested in seeing your code, as I&#8217;m sure would others, so please post it up to the FreeRTOS Interactive site once it is complete.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">critical sections in cr queue implementation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on July 26, 2012</div><div class="thread-post-content">Since the blocking coroutine calls are leaf functions and must be invoked from the coroutine function itself I would not expect a fully coroutine-based application to involve nesting, but I also wouldn&#8217;t want interrupts enabled for me after the call completes if they were disabled before the call.&nbsp; Refining &#8220;critical section&#8221; so that doesn&#8217;t happen would seem to make things more clear.  
I&#8217;m working on a generalization of freertos-mspgcc &#40;already on github at <a href="https://github.com/pabigot/freertos-mspgcc%29.">https://github.com/pabigot/freertos-mspgcc&#41;.</a>&nbsp; The new version will provide FreeRTOS support for all MSP430 chips in a single port, leveraging an external library for peripheral/MCU-specific functionality and reducing the dependency on mspgcc &#40;IAR and CCS should, at least theoretically, be supported as well&#41;.&nbsp; I&#8217;m optimistically hoping to have some compelling examples implemented in an initial public release in about a week, and will post an announcement when that happens.
</div></div><div class="thread-post"><h3 class="thread-post-title">critical sections in cr queue implementation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 26, 2012</div><div class="thread-post-content">The official FreeRTOS MSPGCC port has issues with the latest MSPGCC versions, and this is noted in the &#8220;Known Issues&#8221; list on the download page.&nbsp; Could you please post a link to your github repository in the FreeRTOS Interactive site, then I will add a link to the FreeRTOS Interactive post in the Known Issues list so people know where to go for up to date versions.&nbsp; Thanks&#33;
