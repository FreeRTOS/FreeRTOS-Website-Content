  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32 CAN receive interrupt issues</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/skv19">skv19</a> on July 5, 2012</div><div class="thread-post-content">Hi All,  
I have an issue&nbsp; with CAN interrupt in STM32 Cortex-M3 and couldn&#8217;t figure out what is wrong. Here is my code design:<br />
///////CAN Receive interrupt////////////////////<br />
&#123;<br />
CAN&#95;Receive&#40;CAN1, CAN&#95;FIFO0, &amp;RxMsg&#41;;<br />
/&#42;&#42;&#42;Do some processing on received message&#42;&#42;&#42;/<br />
portBASE&#95;TYPE xHigherPriorityTaskWoken = 0;<br />
xSemaphoreGiveFromISR&#40;SEM&#95;DEVICE&#95;COMP&#95;TASK&#95;ID, &amp;xHigherPriorityTaskWoken&#41;;<br />
&#125;<br />
//////Task waiting on semaphore////// &#8211; Task created using &#8220;xTaskCreate&#40;&#41;&#8221; &amp; priority set as &#8220;3&#8221;, Stack size as 256 bytes<br />
&#123;<br />
Wakes up this task and process received data &amp; do a CAN Tx message which causes other node to send back another CAN message<br />
&#125;<br />
/////////////////CAN interrupt is set as follows///////////////<br />
&#123;<br />
NVIC&#95;InitTypeDef NVIC&#95;InitStructure;<br />
NVIC&#95;InitStructure.NVIC&#95;IRQChannel = USB&#95;LP&#95;CAN1&#95;RX0&#95;IRQn;<br />
NVIC&#95;InitStructure.NVIC&#95;IRQChannelPreemptionPriority = configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY;<br />
NVIC&#95;InitStructure.NVIC&#95;IRQChannelSubPriority = 0x0;<br />
NVIC&#95;InitStructure.NVIC&#95;IRQChannelCmd = ENABLE;<br />
NVIC&#95;Init&#40;&amp;NVIC&#95;InitStructure&#41;;<br />
&#125;<br />
Also used NVIC&#95;PriorityGroupConfig&#40; NVIC&#95;PriorityGroup&#95;4 &#41;;<br />
Used defaults settings for Freertos as below:<br />
/&#42; This is the raw value as per the Cortex-M3 NVIC. Values can be 255 &#40;lowest&#41; to 0 &#40;1?&#41; &#40;highest&#41;. &#42;/<br />
&#35;define configKERNEL&#95;INTERRUPT&#95;PRIORITY 255<br />
&#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY 191 /&#42; equivalent to 0xb0, or priority 11. &#42;/<br />
/&#42; This is the value being used as per the ST library which permits 16 priority values, 0 to 15. This must correspond to the configKERNEL&#95;INTERRUPT&#95;PRIORITY setting. Here 15 corresponds to the lowest NVIC value of 255. &#42;/<br />
&#35;define configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY 15   
In a slower message communication it works, but if I send lots of messages to STM32 it fails. It doesn&#8217;t receive all &amp; CAN receive interrupt doesn&#8217;t work anymore. Ideally I want ISR to be completed &amp; then run the task. Don&#8217;t want to interrupt ISR. Any help would be appreciated.   
Thanks,<br />
SKV  
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 CAN receive interrupt issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 6, 2012</div><div class="thread-post-content">From a kernel usage point of view, I cannot see anything obviously wrong, but I don&#8217;t know what the call:  
CAN&#95;Receive&#40;CAN1, CAN&#95;FIFO0, &amp;RxMsg&#41;;   
does &#8211; although that it outside the scope of FreeRTOS support I have some comments.  
It looks like CAN&#95;Receive is placing data into RxMsg?&nbsp; How does the task that handles the CAN data read the data received by the interrupt &#8211; is RxMsg simply a global variable?&nbsp; Is there anything to prevent another interrupt &#40;when interrupts are coming in a bit faster&#41; overwriting the data in RxMsg either before the task has processes it, or worse still, while the task is still processing it?  
<blockquote>
  Ideally I want ISR to be completed &amp; then run the task
</blockquote>
The task can&#8217;t possible run before the ISR has completed, and if you want the task to run immediately after the ISR completes ensure the priority of the task is relatively high &#40;compared to other tasks in the system&#41; and call   
<pre><code>portEND_SWITCHING_ISR( xHigherPriorityTaskWoken );
</code></pre>
as the last line in your interrupt handler.  
&#91;if you post more code, please ensure the code is inside the codify tags to make it easier to read &#8211; the little icon above the text input box with &#8220;&lt;&gt;&#8221; on it&#41;.  
Regards.  
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 CAN receive interrupt issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cd334">cd334</a> on July 6, 2012</div><div class="thread-post-content">Hi all&#33;  
I&#8217;ve an other idea:<br />
Don&#8217;t process the CAN message in the interrupt. Make a queue and send the message to a task through queue. And in this task process the message.<br />
If the message processing in interrupt too long, then the input FIFO in the uC CAN pherpherie is full, then you can lost messages.  
///////CAN Receive interrupt////////////////////<br />
&#123;<br />
&nbsp;&nbsp;&nbsp; portBASE&#95;TYPE xHigherPriorityTaskWoken = pdFALSE;  
&nbsp;&nbsp;&nbsp; CanRxMsg RxMsg;  
&nbsp;&nbsp;&nbsp; CAN&#95;Receive&#40;CAN1, CAN&#95;FIFO0, &amp;RxMsg&#41;;  
&nbsp;&nbsp;&nbsp; xQueueSendFromISR&#40; xQueue&#95;CAN&#95;RX, &amp;RxMsg, &amp;xHigherPriorityTaskWoken &#41;;  
&nbsp;&nbsp;&nbsp; portEND&#95;SWITCHING&#95;ISR&#40; xHigherPriorityTaskWoken &#41;;<br />
&#125;
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 CAN receive interrupt issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/skv19">skv19</a> on July 6, 2012</div><div class="thread-post-content">Richard &amp; cd334,  
Thanks for your suggestions. CAN&#95;Receive&#40;&#41; is ST library function &amp; if copies received data to RxMsg a global buffer.<br />
At this point I am not worried about the data integrity &#40;may be later&#41; because there are only 2 nodes on CAN bus &amp; I am trying to establish a reliable messaging scheme here. The idea is Node1 sends data and Node 2 responds with an ack, during this time Node1 is in waiting state &amp; once it receives Ack it send another packet &amp; it goes on like that for about 18 messages.  
On Node2 it receives msg in an interrupt handler posts a semaphore &amp; the task waiting on this semaphore wakes up &amp; sends ACK.  
I have tested this on an Eval board before porting to Freertos. In eval board it worked just fine with out any RTOS &amp; tasks.  
The issue I am seeing here is, it starts working good for about 8 of 18 packets &amp; from there on no more receive interrupts getting generated in STM32. The tasks are still working good.  
At this point I don&#8217;t know where to look for. Any ideas???<br />
What happens when it receives a CAN message when RTOS is executing a critical section?   
Regards,<br />
SKV
