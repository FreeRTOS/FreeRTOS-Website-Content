  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">avoid double thread locking of malloc/free on IAR EW for MSP430 with heap_3.c</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gmenhennitt">gmenhennitt</a> on January 30, 2014</div><div class="thread-post-content">IAR Embedded Workbench for MSP430 (and, I would guess, other IAR products) has an option &#8220;Enable thread support in library&#8221;. If this is ticked, the library puts locks around calls to malloc() and free() to give thread safety. The developer is responsible for implementing four functions to implement the locking (see <a href="http://supp.iar.com/FilesPublic/UPDINFO/005691/arm/doc/infocenter/DLIBThreadSupport.html">http://supp.iar.com/FilesPublic/UPDINFO/005691/arm/doc/infocenter/DLIBThreadSupport.html</a>). When using this with FreeRTOS, it seems to be sufficient that locking calls vTaskSuspendAll() and unlocking calls xTaskResumeAll() (similar to what heap_3.c does).
However, that means that FreeRTOS&#8217;s pvPortMalloc() and vPortFree() in heap<em>3.c do the lock and unlock twice &#8211; once in heap</em>3.c and once in the IAR library. I&#8217;m not sure what the overhead of this is, or if there are any adverse effects (I doubt that there are). But it&#8217;s fairly trivial to avoid.
I&#8217;ve modified FreeRTOS.h to add a new config option configLOCK<em>MALLOC</em>FREE which causes the duplicate calls to be omitted. I then set that in FreeRTOSConfig.h to 1. Then I wrapped the calls in heap_3.c in #if&#8217;s so that they get omitted.
The attached files are diffs against FreeRTOS 7.6.0 to implement this, together with a sample file locking.c that can be added to the project to implement the locking.
Graham

So they&#8217;re needed for anything that doesn&#8217;t know about FreeRTOS e.g. any third party libraries, or any calls from inside the IAR libraries. They&#8217;re used for C++ new/delete too.
