  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xQueueCreate() returns invalid handler</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nex12345">nex12345</a> on December 28, 2016</div><div class="thread-post-content">I&#8217;m facing an error within vSemaphoreCreateBinary(..). The macro looks like this:
~~~
<h1>define vSemaphoreCreateBinary( xSemaphore ){                                                       </h1>
<pre><code>    ( xSemaphore ) = xQueueCreate( ( unsigned portBASE_TYPE ) 1, semSEMAPHORE_QUEUE_ITEM_LENGTH );  
    if( ( xSemaphore ) != NULL )                                                                    
    {                                                                                               
            xSemaphoreGive( ( xSemaphore ) );                                                           
    }                                                                                               
</code></pre>
}
~~~
The application runs into a hardfault within xSemaphoreGive(). xSemaphore, which is a pointer, is pointing to the address 0xc18f04f. This is not a valid address and accessing it leads to a hardfault. 
I used the debugger to step through xQueueCreate() line by line but wasn&#8217;t able to detect sth abnormally. 
Here is a screenshot which shows that the pointer pxNewQueue points to address 0x20001130. This is a valid address.
<img src="https://img3.picload.org/image/railaddo/screenshot_1.png" alt="ScreenShot" />
I do not understand why the address changes to 0xc18f04f? Any hint is highly appreciated.
I&#8217;m using FreeRTOS V6.1.1 with Atollic TrueSTUDIO 7.0.1 on a STM32F205.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate() returns invalid handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nex12345">nex12345</a> on December 28, 2016</div><div class="thread-post-content">I was able to reproduce the same behaviour in an other project where FreeRTOS isn&#8217;t used at all. The issue is not related to FreeRTOS.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate() returns invalid handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nex12345">nex12345</a> on December 29, 2016</div><div class="thread-post-content">I spent another day looking at this issue. The issue is caused by a collision of heap and stack. TrueSTUDIO comes with two options: Dynamic heap size (default) and Fixed heap size. In projects where no RTOS is used Atollic recommends to use the dynamic option. This worked fine and I was able to solve above issue by this change for projects where FreeRTOS is not used.
However, for projects with FreeRTOS a dynamic heap size doesn&#8217;t seem to be an option. Out of the user guide: 
<blockquote>
  If using an RTOS, it is recommended to generate a system calls file, and select
  the Fixed Heap size option. This option requires that the <em>Min</em>Heap<em>Size
  symbol is defined in the linker script .ld file. The .ld file is stored in the root
  directory of the currently selected project. The heap size defined by
  _Min</em>Heap_Size must meet the heap size required by the application.
</blockquote>
The IDE automatically created a linker and a syscalls file. For the linker file it makes no difference whether dynamic or fix heap size has been selected &#8211; it looks the same in both cases. Here the interessting lines of the linker script:
~~~
/* Highest address of the user mode stack <em>/
_estack = 0x2001c000;    /</em> end of 112K RAM */
/* Generate a link error if heap and stack don&#8217;t fit into RAM <em>/
_Min_Heap_Size = 0;      /</em> required amount of heap  <em>/
_Min_Stack_Size = 0x400; /</em> required amount of stack */
/* Specify the memory areas */
MEMORY
{
  FLASH (rx)      : ORIGIN = 0x08000000, LENGTH = 768K
  RAM (xrw)       : ORIGIN = 0x20000000, LENGTH = 112K
  MEMORY_B1 (rx)  : ORIGIN = 0x60000000, LENGTH = 0K
}
~~~
Heap size is 0 and stack size is 1K. <strong>Is it somehow possible to calculate those values before building the application? Shall the minimal heap size be equal to the FreeRTOS config value configTOTAL_HEAP_SIZE?</strong>
The second auto generated file is the syscalls file. This file changes completely when you compare projects with dynamic heap size and fix heap size. I think the central part of this file is the implementation of the function <em>sbrk(int32t incr)</em>:
~~~
caddr<em>t _sbrk(int32</em>t incr)
{
  extern uint32<em>t _Min</em>Heap<em>Size; /* _Min</em>Heap<em>Size symbol defined in the linker script. */
  extern uint8</em>t end asm(&#8220;end&#8221;);
  const uint8<em>t *max</em>heap = (uint8<em>t*)((uint32</em>t)&amp;end + (uint32<em>t)&amp;</em>Min<em>Heap</em>Size);
  static uint8<em>t *heap</em>end;
  uint8<em>t *prev</em>heap_end;
  if (heap<em>end == 0)
    heap</em>end = &end;
  prev<em>heap</em>end = heap<em>end;
  if (heap</em>end + incr > max<em>heap)
  {
//    write(1, &#8220;Heap and stack collisionn&#8221;, 25);
//    abort();
    errno = ENOMEM;
    return (caddr</em>t) -1;
  }
  heap_end += incr;
  return (caddr<em>t) prev</em>heap<em>end;
}
~~~
The collision detection fails obviously as _Min</em>Heap_Size is 0. Unfortunately the application does not abort at this point but continues to run. The consequence was in my case that the pointer of a queue was overridden and invalid. I would prefer to enter an endless loop if application runs out of heap. <strong>What do you think &#8211; does this make sense? Does the function itself make sense when used with FreeRTOS??</strong>
Thanks in advance for any help.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate() returns invalid handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 29, 2016</div><div class="thread-post-content">The function looks like it would make sense (but maybe not with Min<em>Heap</em>Size == 0) to provide a seperate malloc heap. It should return -1 to signal that there isn&#8217;t more memory, and maybe the heap functions can&#8217;t handle that on the initial allocation. The proper value of Min Heap will depend on how much heap memory is needed from this heap.
