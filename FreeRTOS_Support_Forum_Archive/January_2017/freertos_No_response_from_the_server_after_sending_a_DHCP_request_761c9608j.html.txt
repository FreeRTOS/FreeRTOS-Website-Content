  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">No response from the server after sending a DHCP request</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/orifai01">orifai01</a> on January 12, 2017</div><div class="thread-post-content">Hello,
I have a working FreeRTOS + TCP/IP application which manages to receive and send responses to pings.
In WireShark can see that FreeRTOS sends DHCP discover messages as both unicast and broadcast, yet there is no response received from the server (I suppose I should look for a packet directed to my MAC address, shall enter the first query in eConsiderFrameForProcessing function). What could be the reason for that?
Attached are shapshot of FreeRTOS discover request and a DHCP discover of some service (which I couldn&#8217;t turn off) for comparison.
https://s29.postimg.org/49b73hwxj/Discover<em>Packet</em>Free<em>RTOS.png
https://s24.postimg.org/5b788fbv9/Discover</em>Packet<em>Not</em>Free_RTOS.png
</div></div><div class="thread-post"><h3 class="thread-post-title">No response from the server after sending a DHCP request</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/orifai01">orifai01</a> on January 12, 2017</div><div class="thread-post-content">For some reason, setting  ipconfigDRIVER<em>INCLUDED</em>TX<em>IP</em>CHECKSUM and ipconfigDRIVER<em>INCLUDED</em>RX<em>IP</em>CHECKSUM to 0 has solved the problem.
</div></div><div class="thread-post"><h3 class="thread-post-title">No response from the server after sending a DHCP request</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 12, 2017</div><div class="thread-post-content">Hi Orit,
When developing DHCP it can be handy to install a temporary DHCP-server on your own laptop. In that way you make sure to see all messages in WireShark.
Here is an example of a DHCP server: https://sourceforge.net/projects/dhcp-dns-server I chose the option &#8220;Run stand alone&#8221;, it runs from a command-prompt.
The DHCP client will use both &#8216;unicast&#8217; and &#8216;broadcast&#8217;, it starts with a unicast (<code>dhcpBROADCAST</code> flag cleared).
When the answer comes in, it is directed to UDP port 68, and <code>xPortHasUDPSocket()</code> should return pdTRUE for that port.
Make sure that your EMAC accepts the Ethernet broadcast address of all 1&#8217;s.
</div></div><div class="thread-post"><h3 class="thread-post-title">No response from the server after sending a DHCP request</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 12, 2017</div><div class="thread-post-content">Our posts were crossing each other.
<blockquote>
  enabling LLMNR and setting ipconfigDHCP<em>REGISTER</em>HOSTNAME to 1 have solved the problem.
</blockquote>
Good to hear. I&#8217;m not sure why changing those features would make DHCP working.
I tested the DHCP client with LLMNR, with NBNS, and also without any name service at all.
Does LLMNR cause different settings in your NetworkInterface.c ?
</div></div><div class="thread-post"><h3 class="thread-post-title">No response from the server after sending a DHCP request</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/orifai01">orifai01</a> on January 12, 2017</div><div class="thread-post-content">Hi Hein, thank you for your answer.
As mentioned above, apparently setting ipconfigDRIVER<em>INCLUDED</em>TX<em>IP</em>CHECKSUM and ipconfigDRIVER<em>INCLUDED</em>RX<em>IP</em>CHECKSUM to 0 has solved the problem. I&#8217;ll enable the  Checksum Offload Engine in the ethernet controller (LAN9220) in order to set them again to 1.
</div></div><div class="thread-post"><h3 class="thread-post-title">No response from the server after sending a DHCP request</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 12, 2017</div><div class="thread-post-content">All good, you&#8217;re getting closer and closer.
Note that the &#8220;Checksum Offload Engine&#8221; must be studie well: test it with TCP, UDP, and ICMP messages. Some EMAC&#8217;s want you to set the checksum field(s) to zero first, others don&#8217;t care about the value.
Please feel free to publish you NetworkInterface.c or send it to us directly, so I can have a look.
Thanks, Hein
