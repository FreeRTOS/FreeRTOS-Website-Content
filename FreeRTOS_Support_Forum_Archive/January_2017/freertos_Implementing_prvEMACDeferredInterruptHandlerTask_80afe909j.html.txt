The function will go sleeping until an interrupt has occurred, which is soon after <code>TaskNotifyGiveFromISR()</code>. Note the <code>for(;;)</code> loop.

● xHigherPriorityTaskWoken will be pdTRUE, and the YIELD will succeed
● The task running <code>prvEMACDeferredInterruptHandlerTask()</code> is unblocked immediately ( unless there are other runnable tasks with a higher priority ).

</div></div><div class="thread-post"><h3 class="thread-post-title">Implementing prvEMACDeferredInterruptHandlerTask</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 5, 2017</div><div class="thread-post-content">Hi Orit,
I would be curious to see <code>smsc9220_RxStatusFifoLevelIrq()</code>.
In general: there are many possible triggers for <code>ETHERNET_IRQn</code>. Only the triggers that you need (RX, error?) should be enabled (the others are said to be &#8220;masked off&#8221;). Now if your interrupt-handler is called, the cause of the interrupt must be reset / cleared. How it is to be cleared depends on the peripheral.
In some cases it suffices to read the STATUS bits, sometimes a logical <strong>0</strong> or <strong>1</strong> must be written to the status-bit in order to reset it. Yet in other cases, nothing has to be done.
So if you observe that the interrupt keeps on being called, try to make clear what the reason is and how it can be cleared.
I do not think it is necessary to call <code>Common_DisableIrq()</code> and <code>Common_EnableIrq()</code> from within the interrupt handler.

~~~~

{

  this action will probably not reset the cause of the interrupt.
  It is documented as a R/WC bit: Read/Write Clear:
  A register bit with this attribute can be read and written.
  However, a write of a 1 clears (sets to 0) the corresponding
  bit and a write of a 0 has no effect

}
~~~~
<blockquote>
  I would like the task function to read received bytes every time
  interrupt occurs. I do not want the interrupt to occur during the
  reading process so I disable it, and enable it after reading a packet.
</blockquote>
You better leave the interrupt enabled all the time, no problem. All it does is make your task runnable. The next call to <code>ulTaskNotifyTake()</code> will succeed immediately without blocking.
If you disable the RX interrupt, you might miss data or receive them too late.
<blockquote>
  The problem is that the interrupt keeps on being called because I
  receive a lot of packets, and no other task can run.
</blockquote>
I dare to doubt this theory 🙂
Please check which interrupt bits are enabled in <code>INT_EN</code> and make sure that during the interrupt, the corresponding bits in <code>INT_STS</code> will be cleared.
That will stop the heavy load of interrupts.
If you still see too many RX data, make sure that the MAC filtering is OK: do not use promiscuous mode but set certain MAC addresses that are used by your device.
<blockquote>
  Is it better to implement this listener as a simple reading function
  (without a loop) and call xTimerPendFunctionCallFromISR() instead of a task?
</blockquote>
I don&#8217;t think so.
The proposal is as follows:
~~~~
    for( ;; )
    {
        ulTaskNotifyTake( pdFALSE, ulMaxBlockTime );
        for( ;; )
        {
            xBytesReceived = smsc9220<em>recv</em>size();
           if( xBytesReceived &lt;= 0 )
           {
               break;
           }
           /* send the received packet to the IP-task. */
        }
    }
~~~~
The ETH interrupt remains active (enabled) all the time. If an interrupt occurs while reading RX packets, that is no problem. Only <code>vTaskNotifyGiveFromISR()</code> will be called, causing the next <code>ulTaskNotifyTake()</code> to &#8220;fall through&#8221;.
Please have a look of one of the other ports, such as:
<pre><code>FreeRTOS-Plus-TCP/portable/NetworkInterface/ATSAM4E/NetworkInterface.c
</code></pre>
Its interrupt handlers will also set a (volatile) bit to indicate what type of interrupt has occurred. This is tested later in the task.
