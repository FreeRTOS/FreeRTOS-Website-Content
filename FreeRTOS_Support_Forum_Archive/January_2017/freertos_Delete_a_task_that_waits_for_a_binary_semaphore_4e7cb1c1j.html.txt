  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Delete a task that waits for a binary semaphore</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apica">apica</a> on January 23, 2017</div><div class="thread-post-content">Hi,
I&#8217;m developing a middle layer between a peripheral an upper layers, and this middle layer has a binary semaphore. 
The upper layers (threads) call the &#8220;Request&#8221; function of the middle layer, this takes the binary semaphore (xSemaphoreTake) to allow only one access to the peripheral at a time. Once the use of the peripheral is finished, the upper layer executes the &#8220;Release&#8221; function of the middle layer that releases the semaphore.
Now suppose the case that the semaphore is taken, and other upper layer (thread) executes the Request function. This will lead the thread to be waiting for the semaphore. If this thread is externally deleted, will the semaphore keep correct values? Is it safe to do?
Thank you
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 23, 2017</div><div class="thread-post-content">I hope I understand your question:
When a task is being killed, the OS won&#8217;t know which semaphores were taken by the task. 
I my opinion, it is more transparent to let a task kill itself. So if you want to kill a task, send it a message or set some flag to which it will respond. The task will know perfectly which resources it has claimed and what to do to terminate properly.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apica">apica</a> on January 23, 2017</div><div class="thread-post-content">Thank you Hein.
Yes, it would be easier if the task terminates itself and releases all the resources but I&#8217;m not sure if it is compatible with the low power. The xSemaphoreTake it was supposed to be blocked &#8220;forever&#8221; until the resource became available.
From your reply, I guess you are saying to avoid the &#8220;forever&#8221; semaphore and check from time to time a flag (or something else) to know if it has to terminate itself. Is that right?
Thank you
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 23, 2017</div><div class="thread-post-content">Are you asking what happens if the middle layer task gets deleted while 
it has the semaphore, or what happens if a higher level task that is 
blocked waiting for the semaphore gets deleted?  If you are just talking 
about the latter case, where a task attempts to take a semaphore, 
blocks, then gets deleted before it unblocks, then nothing happens &#8211; 
everything will be fine.  The task will get deleted and removed from the 
list of tasks waiting for the semaphore.  This holds for binary 
semaphores but not necessarily other types of semaphore.
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 24, 2017</div><div class="thread-post-content">I generally find that I don&#8217;t need to delete/recreate tasks, and that people doing this tend to be thinking much more of a unix type model with full processes, and not a micro-kernal with tasks (which are much more like threads on bigger machines). The key thing is that if you are going to delete a task, you are almost certainly going to also be recreating the task later, and without a lot of careful analysis, you need to be prepared for the create task to fail. The major way to be sure that the create will succeed (other than not deleting in the first place so you don&#8217;t need to recreate) is to have a lot of memory, but then there isn&#8217;t much need to delete the task in the first place.
Because tasks are NOT full blown processes of the unix ilk, you need to take a lot of care to be sure the task is in a proper state before deleting it (so you don&#8217;t lose resources), which tends to make it simplest that if you do delete tasks, it is them self-deleting, otherwise it is very hard to avoid race conditions.
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apica">apica</a> on January 24, 2017</div><div class="thread-post-content">Yes, it was the second case (isn&#8217;t easy to explain).

</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apica">apica</a> on January 24, 2017</div><div class="thread-post-content">Hi Richard, thank you for your reply.
I understand your aproach. The main goal to delete / suspend / block a task is to enter in a low power mode. When the system decides to stop the device, it has to tell to the modules to stop working.
If a &#8220;release&#8221; function is executed from a upper layer, this function needs to stop the thread somehow and all its used resources (semaphores, queues, perihperals, ..).
So, to set a bigger scope to thre problem:
How would you deal with low power while using freeRTOS based systems?
Thank you very much.
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 24, 2017</div><div class="thread-post-content">A task that is block indefinately on a semaphore or queue will not prevent the system from entering low power mode (the key is indefinately or at least for a long time), This generally SHOULD be the normal state for any task that doesn&#8217;t have something immediately to do anyway.
</div></div><div class="thread-post"><h3 class="thread-post-title">Delete a task that waits for a binary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 24, 2017</div><div class="thread-post-content"><blockquote>

  prevent the system from entering low power mode
</blockquote>

power, if configUSE<em>TICKLESS</em>IDLE is set to 1 (on ports that implement it).
