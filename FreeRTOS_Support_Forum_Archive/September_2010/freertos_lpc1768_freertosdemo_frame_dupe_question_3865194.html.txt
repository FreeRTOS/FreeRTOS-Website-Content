lpcxpresso compile and debug environment.<br />

&nbsp; I had to modify the freertos demo code to support the lan8720 phy on the lpcxpresso board. The code changes were limited to the phy init and link status routines.&nbsp; Code seems to be working pretty much as expected, the web server delivers pages properly.<br />

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;<br />

&nbsp;&nbsp;&nbsp; Thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">lpc1768 / freertosdemo  frame dupe question</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 24, 2010</div><div class="thread-post-content">The biggest drawback of uIP is the fact that you can only have one packet outstanding on the network at any one time.&nbsp; This means<br />
communicating with a desktop machine is very slow because the desktop will wait 200ms between receiving a packet and acknowledging the packet.&nbsp;&nbsp; This is standard practice in non real-time TCP/IP stacks to minimise network traffic &#8211; it waits to see if any more packets come so it can acknowledge more than one packet at a time.  
There are ways around this and so speed up communication without having to change the configuration of your desktop TCP/IP stack, but like everything in engineering &#8211; there are trade off&#8217;s to be made.&nbsp; Gain in one place, loose in another.&nbsp; I have several schemes I&#8217;m working on &#40;code named FreeTCPIP&#41;, but one easy way of speeding up uIP is to simply send each packet twice.&nbsp; This tricks the other end into thinking it has missed a packet, and this causes it to send the ACK immediately.&nbsp; The cost of this is more bits on the wire, but if you have a decent DMA&nbsp; the microcontroller hardly notices.  
Regards.
