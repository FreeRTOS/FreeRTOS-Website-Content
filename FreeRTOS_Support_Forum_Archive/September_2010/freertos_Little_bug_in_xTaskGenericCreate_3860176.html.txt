</div></div><div class="thread-post"><h3 class="thread-post-title">Little bug in xTaskGenericCreate() ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 21, 2010</div><div class="thread-post-content">First, you should NOT be getting tick interrupts inside of a critical section, this would be a major bug in the port. Critical sections should disable every interrupt that might interact with FreeRTOS, and the tic interrupt definitely counts for that.  
If the problem is that between the portEXIT&#95;CRITICAL and the assigning to pxCreatedTask the created task referes to &#42;pxCreatedTask, that does look like a problem in FreeRTOS.  
At first glance, maybe the returned value should be set before scheduling the task to run.  
If you don&#8217;t want to change FreeRTOS, a couple of solutions come to mind,<br />
1&#41; Place the create inside of a Critical Section by the calling task. Hopefully this doesn&#8217;t impact performance too bad, it does say you have interrupts down longer than you want.  
2&#41; Place at the beginning of the created task, assign the handle with xTaskGetCurrentTaskHandle&#40;&#41;

</div></div><div class="thread-post"><h3 class="thread-post-title">Little bug in xTaskGenericCreate() ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 21, 2010</div><div class="thread-post-content">First &#8211; thanks for the kind words.  
I understand better now the potential issue you are reporting &#8211; however I still don&#8217;t think it is an issue.  
The handle to a task is just a pointer to the tasks TCB.&nbsp; It is optional as to whether you want this information passed out of the xTaskCreate&#40;&#41; function or not.&nbsp; You would want the handle if you were to do something later on, like delete the task, change its priority, suspend it, etc.  
In the scenario you describe:  
1&#41; Task A calls xTaskCreate&#40;&#41; to create Task B, and passes in a valid &#40;non NULL&#41; address for pxCreatedTask.<br />
2&#41; During the task creation, in the critical section, a tick interrupt becomes due, but is held pending.<br />
3&#41; As soon as the critical section is exited the tick interrupt executes and selects task B to run.&nbsp; The newly created task does not know its own task handle but can obtain it through the API call that richard&#95;damon pointed out.&nbsp; Normally it doesn&#8217;t need to know its own handle as it can refer to itself by using a NULL handle in API calls anyway &#40;that is normal practice&#41;.&nbsp; At this point pxCreatedTask is <strong>not</strong> assigned, but Task A is not running in any case so it does not matter.<br />
4&#41; Task B leaves the Running state and the scheduler &#40;at some point in the future&#41; selects Task A to run again.&nbsp; Task A starts from the point it left off, so assigns the task handle to pxCreatedTask before it ever gets a change to actually use the value &#40;it happens before it leaves the xTaskCreateFunction&#41;.  
In this scenario there should be no issues.&nbsp; However, if TaskA passed in the address of a global variable as pxCreatedTask, and Task B tried using the global variable, then there would be a problem &#8211; but as I said it would not be normal for a task to use its own handle, it should just use NULL as the handle if it wants to manipulate its own state or delete itself.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Little bug in xTaskGenericCreate() ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 21, 2010</div><div class="thread-post-content">Richard, while pxCreatedTask will be a local variable &#42;pxCreatedTask may well &#40;in fact I would say often&#41; point to a global. The newly created task could access that variable to attempt to gets its handle for some operations, and in this case it could get an incorrect value. The documentation sort of implies, but doesn&#8217;t really promise, the invariant that the location passed will hold the handle of the task for the life of the task &#40;assume the user doesn&#8217;t destroy the value himself&#41;, but the code really on makes this happen for the calling task without pointing out the limitation. There shouldn&#8217;t be a problem with assigning to the passed handle location before enabling the task, getting around the problem, and this makes the invariant what would be expected.
