I have a project that we are using FreeRTOS in. I want to have a number of tasks periodically and for that I use vTaskDelayUntil. So far everything is quite nice and easy.  
What I&#8217;m looking for is to stop a task &#40;not end it, not preemptive it, so it starts all over next period&#41; if it goes on too long. For example a extreme value that&#8217;s not thought of, creating a inf-loop.  
This is because we&#8217;re working with sensors and controllers and the timing need to be rather good and consistent.   
For example, Task1 in a period goes over its deadline. Task2 have lower priority and gets delayed, from then on Task2 will be delayed since&nbsp; vTaskDelayUntil reads the tick-count when entering a task.  
Example 2, Task1 in a period goes over its deadline, not finishing putting sensor values in a message queue, Task2 have higher priority and preemptives it. Task2, Task3… TaskN finishes and Task1 continues, going over into the new period.  
I know this is a bit academic due to the fact that the processor won&#8217;t be used 100% but since the system in this project is going to be on a truck we want it to be robust for future task-scheduling, saftey etc.  
Best regards  
FYI, this is a student project, so if I said something stupid, I blame it on that.<br />
For the curoius people, we&#8217;re using a TI devel-board, RM48HDK, and will implement inverse kinematic, automatic control and more. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Setting deadline for tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 11, 2013</div><div class="thread-post-content"><blockquote>
  For example, Task1 in a period goes over its deadline. Task2 have lower priority and gets delayed, from then on Task2 will be delayed since&nbsp; vTaskDelayUntil reads the tick-count when entering a task.
</blockquote>
I&#8217;m not sure I understand your point exactly, but if Task1 is using vTaskDelay&#40;&#41; then the start of the next cycle will not be effected by the time the last cycle ended.&nbsp; There is no slippage of time.&nbsp; For example, if Task1 wants to execute every 100 ticks then, and &#40;for simplicity&#41; assume the start time is 0.  
&#45; The first execution will be at time 100.&nbsp; Lets assume it ends at time 150.  
&#45; The next execution will be at time 200.&nbsp; Lets assume it ends at time 290.  
&#45; The next execution will be at time 300.&nbsp; Lets assume it ends &#40;for whatever reason&#41; at time 410.  
&#45; The next execution will happen immediately as it should have started at time 400, but the time is already 410.&nbsp; Lets assume it ends at time 490.  
&#45; The next execution will be at time 500 &#8211; still on time, even though one of the cycles overran by 10.  
<blockquote>
  Example 2, Task1 in a period goes over its deadline, not finishing putting sensor values in a message queue, Task2 have higher priority and preemptives it. Task2, Task3… TaskN finishes and Task1 continues, going over into the new period.
</blockquote>
Ultimately, you only have a fixed amount of CPU power.&nbsp; A good event driven &#40;not polling&#41; design using an RTOS will allow you to extract more useful work from that fixed amount of power &#40;because code only executes when there is actually something to do&#41;.&nbsp; Therefore, if it is not possible to meet your deadlines with an RTOS then you will not be able to without one &#40;assuming the design makes good use of the RTOS, that is&#41;.  
If the amount of CPU power is not the issue then you will have to employ some defensive programming.&nbsp; Set up another task that monitors the timing of other application tasks, or do this from the tick hook function.&nbsp; You can see crude examples of this with the &#8216;check&#8217; tasks in the FreeRTOS demo applications.&nbsp; You can then catch a task breaking its deadlines, as well as tasks that are stuck somewhere.&nbsp; Tasks can also monitor their own timing, but that only allows them to detect broken deadlines, obviously if they are stuck somewhere then their own self checking will not work &#40;because they are stuck&#41;.  
The question then is, what do you do if you find a task has missed its deadline?&nbsp; Redesign your system?&nbsp; If you just restart the task then chances are it will just miss a deadline again in the future, so you have not really solved anything, just masked unwanted behaviour.  
Regards.

  The question then is, what do you do if you find a task has missed its deadline?  Redesign your system?  If you just restart the task then chances are it will just miss a deadline again in the future, so you have not really solved anything, just masked unwanted behaviour.

Hello Richard, just read your post here, while I was asking myself the same question as Figgae before. There are several options what a system could do in order to recover from timing faults (missed deadlines). This question is typical for any soft-realtime scenario, and depends on the desired system behaviour. After missing its deadline, the current job could be simply stopped, skipped, a task could even perform some kind of graceful degradation, reduce its complexity and so on. The actual question for me is, is there any notion of a &#8220;deadline&#8221; in FreeRTOS and if not is it possible to implement it? From a tasks point of view there should be a kind of callback or an event propagated to the task when the system reaches the deadline point and the task has not yet completed its current job. This leads to another question: is there any opportunity for a task to voluntarily give up control until the beginning of next period? Consider for example RTSJ, periodic threads have periods, deadlines, costs and a special waitForNextPeriod() method which blocks the thread until the beginning of next period indicating to the system a successful job completion. When a deadline point in time is reached and the appropriate task has still not blocked in waitForNextPeriod() a deadline miss is indicated to the task by a special event. It would be very helpful if FreeRTOS would provide such mechanisms too. The question is, is there any chance to implement it?
