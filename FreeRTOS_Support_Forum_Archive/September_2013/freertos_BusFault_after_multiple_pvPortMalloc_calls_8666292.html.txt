I&#8217;m currently developing an application on an Cortex-M3 &#40;STM32F103ZG&#41; using FreeRTOS 7.5.0 &#40;non-MPU&#41;. The memory allocation implementation used was heap2, switched to heap4 now, but the following error still occurs.  
The IDE used is Keil µVision with MDK-ARM toolchain 4.21 &#40;C compiler 4.1.0.713&#41;<br />
The application consists of about 20 tasks.  
Under certain circumstances, a task does some extensive data operations. This includes allocating &#40;quite big&#41; memory blocks &#40;one is 8K&#41;, reading in a file from SD card and freeing the block again after processing. According to xPortGetFreeHeapSize, after freeing, the memory is available again &#40;but what about fragmentation?&#41;. This task &#42;always&#42; does the memory allocating and freeing. But the file reading is only done under the circumstances.<br />
After these operations, uxTaskGetStackHighWaterMark reports 100 byte &#40;words?&#41; minimal stack remaining for this task.  
After the task has finished the operations, a context switch to another task occurs, which also tries to allocate some memory for a buffer. This is when the BusFault occurs. The bus fault does not occur there when the previous task doesn&#8217;t do these extensive operations.  
In the BusFault&#95;Handler, Keil reports the following &#40;Fault reports window&#41;:

</div></div><div class="thread-post"><h3 class="thread-post-title">BusFault after multiple pvPortMalloc calls</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 4, 2013</div><div class="thread-post-content">Why do you have configASSERT&#40;&#41; commented out &#8211; it is there to help you catch problems in your code.  
Are you using the STM32 peripheral library from ST?&nbsp; If so, then before spending time looking into this, I recommend upgrading to FreeRTOS V7.5.2, uncommenting configASSERT&#40;&#41; and then running the same application.&nbsp; V7.5.2 contains code specifically for users of the ST peripheral libraries, which have some special Cortex-M3 configuration requirements &#40;unlike any other dirvers we have encountered, they require you to change the Cortex-M3 configuration from its power up default&#41;.&nbsp; See <a href="http://www.freertos.org/History.txt">http://www.freertos.org/History.txt</a>  
Try that then get back to us to let us know if it caught a &#40;Cortex-M3&#41; configuration issue.&nbsp; If not, we can try to diagnose your problem.  
Regards.

thanks for your reply.<br />
I upgraded to FreeRTOS 7.5.2 and uncommented configASSERT, creating a function so I can inspect the file and line number.  
Upgrading fixed the assert in PortValidateInterruptPriority &#40;line 650&#41; I got in v7.5.0.&nbsp; And yes, I&#8217;m using the STM32PeriphLib &#40;and thus calling NVIC&#95;PriorityGroupConfig&#40;NVIC&#95;PriorityGroup&#95;4&#41;; before scheduler starts&#41;  
Now I don&#8217;t get configASSERTs anymore.  
Indeed, the problem occurs when actually reading the file into the buffer. If I don&#8217;t write anything into the buffer, everything works fine.<br />
The buffer I&#8217;m allocating memory for is a struct &#40;well, an array of them&#41; consisting of multiple char-arrays, each struct is 36 byte in size. I&#8217;m using configASSERT now to check if I write out of the buffer and/or the character arrays, but that doesn&#8217;t happen.  
…<br />
Actually, the sizes of the character array were kind of &#8220;uneven&#8221; &#40;10, 5, 3, 4, 6, 3, 5 Bytes&#41;. I just changed it to &#40;10, 6, 4, 4, 6, 4, 6&#41;, resulting in a total of 40 bytes per struct. And now it works fine, the error is gone.<br />
Looks like it was an alignment problem?
