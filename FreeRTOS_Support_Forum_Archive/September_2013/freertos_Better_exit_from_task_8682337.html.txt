  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Better exit from task</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ta8086">ta8086</a> on September 12, 2013</div><div class="thread-post-content">Currently, if someone is terminating a task, it is necessary to delete it before end of task function. Otherwise a HardFault exception will occur. I think it is very simple to make &#8220;automatic&#8221; &#40;in FreeRTOS&#41; finishing of tasks &#8211; to finish function without exceptions or at least to jump in predefined error routine. Currently thousands of people waste hours and days to discover the simple reason for HardFaults &#8211; including me recently for second time &#40;created a new task but had forgotten to delete/while&#40;1&#41; the task&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Better exit from task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 12, 2013</div><div class="thread-post-content">Yes, on one processor it is very easy to have the task function&#8217;s return address return the task to a clean exit point.&nbsp; FreeRTOS supports some 34 architecture cores though, and how this is implemented directly will be different on each one.&nbsp;   
It is well documented that you must not run off the end of a task, but if people are doing that, then maybe there could be a compromise solution that is portable by adding a common task entry point that includes a call to vTaskDelete&#40;&#41; if it is ever exited.&nbsp; Something like:  
void vCommonTaskEntryPoint&#40; void &#42;pvUserTaskCode, void &#42;pvUserTaskParameters &#41;<br />
&#123;<br />
&nbsp;&nbsp;&nbsp; /&#42; Start the task. &#42;/<br />
&nbsp;&nbsp;&nbsp; pvUserTaskCode&#40; pvUserTaskParameters &#41;;  
&nbsp;&nbsp;&nbsp; /&#42; If the user routine ever exits ensure the task is deleted cleanly. &#42;/<br />
&nbsp;&nbsp;&nbsp; vTaskDelete&#40; NULL &#41;;<br />
&#125;  
If you want that possibility to be investigated for feasibility then please add a feature request using the SourceForge feature request tracker.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Better exit from task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on September 12, 2013</div><div class="thread-post-content">That would not be a good solution because it creates a stack frame on each task&#8217;s stack that persists for the lifetime of the task but is never actually used.
</div></div><div class="thread-post"><h3 class="thread-post-title">Better exit from task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 13, 2013</div><div class="thread-post-content">Let me point out some of the costs to make vTaskDelete be called automatically if a task function returns:  
1&#41; It will likely cost stack space on many processors to build a stack frame to use for the return.  
2&#41; If means it will be impossible to exclude to code for vTaskDelete from the program image.  
3&#41; This means that you must also include vPortFree in the program image  
4&#41; This means that you can&#8217;t use heap1.c, the simplest &#40;and smallest&#41; heap implementation.  
This is a fairly high cost to impose on all users to help people who don&#8217;t read the documentation.  
What might make sense is that on those ports that it is cheap to do so, set the return address to go to a function that just hangs &#40;loop forever&#41;, with a comment that if you get hear some task returned without deleting itself. There are likely some ports where this isn&#8217;t cheep enough, so it shouldn&#8217;t be promised behavior.
</div></div><div class="thread-post"><h3 class="thread-post-title">Better exit from task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ta8086">ta8086</a> on September 13, 2013</div><div class="thread-post-content">OK, but it is not necessary to call vTaskDelete automatically. It is enough to add only a return address in the beginning of the stack before calling the task function. This return address will point to a default &#8220;blank&#8221; function &#8211; it may contain only &#8220;while &#40;1&#41;&#8221; loop. The cost of this solution will be 4 bytes in each task&#8217;s stack. It can be optional and enabled by default for debug mode. The benefit of this solution is that you will not get HardFault exception which cannot be tracked by stack calls.
</div></div><div class="thread-post"><h3 class="thread-post-title">Better exit from task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 13, 2013</div><div class="thread-post-content">This is a good discussion with some good points being made.  
Maybe there could be something done with configASSERT&#40;&#41; &#8211; so you get an assertion if you drop out of a task.&nbsp; Any overhead incurred would then only be while configASSERT&#40;&#41; was defined.&nbsp; The problem with that is your stack usage would then change depending on if configASSERT&#40;&#41; was defined or not.  
Another alternative would be to start changing port layers as they are worked on &#8211; so gradually over time the newer and more popular ports would get new functionality added, but the older ports would never get the behaviour change.&nbsp; The down side of that would be the documentation would become confusing as the behaviour would depend on the port.  
Regards.
