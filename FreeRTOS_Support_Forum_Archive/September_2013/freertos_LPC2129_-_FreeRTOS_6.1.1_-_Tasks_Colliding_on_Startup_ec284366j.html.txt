  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">LPC2129 &#8211; FreeRTOS 6.1.1 &#8211; Tasks Colliding on Startup</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jsiegel2">jsiegel2</a> on September 22, 2013</div><div class="thread-post-content">LPC2129 &#8211; FreeRTOS 6.1.1 &#8211; Tasks Colliding on Startup
Hi,
A few years back I inherited from FreeRTOS code that I&#8217;ve been steadily adding features to. Recently, my tasks have stopped launching properly due to an apparent &#8220;collision&#8221; on startup.
This is using GCC 4.7 and an ARM7 (LPC2129). I print to UART for debug, so that&#8217;s where I get most of my information. I create the tasks with:
<blockquote>
  if (!(Tasks<em>Initialized &amp; TASK</em>ACCEL)) {
      if (Task<em>Accel</em>Init() == 0)
          Tasks<em>Initialized |= TASK</em>ACCEL;
  }
  if (!(Tasks<em>Initialized &amp; TASK</em>GPS)) {
      if (Task<em>GPS</em>Init() == 0)
          Tasks<em>Initialized |= TASK</em>GPS;
  }
  if (!(Tasks<em>Initialized &amp; TASK</em>OBD2)) {
      if (Task<em>OBD2</em>Init() == 0)
          Tasks<em>Initialized |= TASK</em>OBD2;
  }
  if (!(Tasks<em>Initialized &amp; TASK</em>SD)) {
      if (Task<em>SD</em>Init() == 0)
          Tasks<em>Initialized |= TASK</em>SD;
  }
  if (!(Tasks<em>Initialized &amp; TASK</em>UPLOAD)) {
      if (Task<em>Upload</em>Init() == 0)
          Tasks<em>Initialized |= TASK</em>UPLOAD;
  }
</blockquote>
and it seems that everything is initialized properly. Then, I allocate stack to the tasks.
<blockquote>
  xTaskCreate(vTask<em>Accel, (const signed char *)&#8221;Accel&#8221;, 46, NULL, tskIDLE</em>PRIORITY+1, NULL);
  xTaskCreate(vTask<em>GPS</em>Parse, (const signed char *)&#8221;GPS Parse&#8221;, 50, NULL, tskIDLE_PRIORITY+1, &amp;xTask_GPSHandle);
  xTaskCreate(vTask_OBD2, (const signed char *)&#8221;OBD2&#8243;, 100, NULL, tskIDLE_PRIORITY+2, &amp;xTask_OBD2Handle);
  xTaskCreate(vTask_Record, (const signed char *)&#8221;Record&#8221;, 70, NULL, tskIDLE_PRIORITY+3, &amp;xTask_RecordHandle);
  xTaskCreate(vTask_Upload, (const signed char *)&#8221;Upload&#8221;, 136, NULL, tskIDLE_PRIORITY+3, &amp;xTask_UploadHandle);
</blockquote>
When I start the scheduler with vTaskStartScheduler(), the first few tasks start, and I am able to print a message like &#8220;Task _____ started.&#8221; Once it gets to the last two tasks, it launches  Task<em>Upload and Task</em>Record concurrently (that is, Task<em>Record interrupts Task</em>Upload &#8211; such that my print &#8220;* vTask<em>Upload Started&#8221; and &#8220;*vTask</em>Record<em>Started&#8221; merge and form &#8220;* vTas* vTask</em>Uploak_Recad() Sord() tartedStartn&#8221;).
What might be happening here? Stack collision? Something else? I thought it could be due to sharing a common priority, but that code has been unchanged since 2011 and this is a new problem.
On a related note, I&#8217;m attempting to upgrade to 7.5.2 and having trouble because something in the OS creates a .text section (6.1.1 did this when it defined ulCriticalNesting = 9999UL; and it stopped when I set it to undeclared and then define it in main.c). How might I find our which variable is causing this initialization so I can get a binary file > 1 GB? 
Thank you all!

  LPC2129 &#8211; FreeRTOS 6.1.1
</blockquote>
That is <strong>very</strong> old!
<blockquote>
  if (!(Tasks<em>Initialized &amp; TASK</em>ACCEL)) {
  if (Task<em>Accel</em>Init() == 0)
  Tasks<em>Initialized |= TASK</em>ACCEL;
  }
</blockquote>
What are these pieces of code doing?  From your post it looks like you don&#8217;t actually create the tasks until after this sequence has executed, so maybe it is just initialising data that is going to be used by the tasks?
<blockquote>
  and it seems that everything is initialized properly. Then, I allocate stack to the tasks.
  xTaskCreate(vTask<em>Accel, (const signed char )&#8221;Accel&#8221;, 46, NULL, tskIDLE</em>PRIORITY+1, NULL);
</blockquote>
Calling vTaskCreate() is doing a <strong>lot</strong> more than allocating stacks to the tasks, it is actually creating the tasks.  The stack is allocated to the task as part of the process of creating the task.
<blockquote>
  I am able to print a message like &#8220;Task _ started.&#8221;
</blockquote>
A lot of support requests result from people trying to print from tasks.  Are your print routines using mutual exclusion?  Do you have enough stack in your tasks to handle a print function &#8211; which if you are using the GCC libraries will be massive.  I can&#8217;t remember if V6.x.x had stack overflow detection, but if it did make sure it is turned on.
<blockquote>
  such that my print &#8221; vTask<em>Upload Started&#8221; and &#8220;vTask</em>Record<em>Started&#8221; merge and form &#8221; 
  vTas vTask</em>Uploak_Recad() Sord() tartedStartn&#8221;).
</blockquote>
&#8230;so you are not using mutual exclusion on your print function.
<blockquote>
  What might be happening here? Stack collision? Something else?
</blockquote>
Don&#8217;t think so &#8211; it sounds like it is behaving as expected.  Both the tasks you mention are running at the same priority, so there is no reason to suppose they will not interrupt each other.  Processing time is shared between tasks of equal priority (time slicing).  It is probably that your older applications ran in such a way you just didn&#8217;t notice it happening because each print message completed before the next started.
<blockquote>
  On a related note, I&#8217;m attempting to upgrade to 7.5.2 and having trouble because something >in the OS creates a .text section (6.1.1 did this when it defined ulCriticalNesting = >9999UL; and it stopped when I set it to undeclared and then define it in main.c). How >might I find our which variable is causing this initialization so I can get a binary file > 1 GB?
</blockquote>
I&#8217;m not sure I follow this one, why do you need > 1GB binary image, and why would have a .text section prevent that.  I would expect <strong>all</strong> the kernel code to be in the .text section, as that is the section that holds executable code.  
Normally the ulCriticalNesting variable will be the only one that is not initialised to 0, so it will appear in a data section other than .bss but not the .text section &#8211; although the value copied into the variable will appear in flash.  If any others are then you should be able to see them from the .map file generated when you build your project (if your build is not generating a map file then you can request GCC creates one using the -Map=output.map linker option).
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">LPC2129 &#8211; FreeRTOS 6.1.1 &#8211; Tasks Colliding on Startup</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 22, 2013</div><div class="thread-post-content"><blockquote>
  created two sections aligned 1GB apart
</blockquote>
Sounds like your linker script is wrong.
<blockquote>
  point a round-robin scheme simply will not hand off control 
</blockquote>
If you have configUSE_PREEMPTION set to 1 in FreeRTOSConfig.h then the tasks will time slice automatically.  A context switch will occur between two tasks of equal priority on the tick interrupt.  One task does not need to hand off to the other.  It is possible for lower priority tasks to get starved of processing time if higher priority tasks are using all the available time though.
Regards.
