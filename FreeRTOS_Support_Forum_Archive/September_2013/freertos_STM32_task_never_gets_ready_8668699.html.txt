</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 task never gets ready</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 5, 2013</div><div class="thread-post-content">The general rules are  
&#8220;don&#8217;t call API functions from critical sections&#8221;<br />
&#8220;call the FromISR versions inside interrupts&#8221;<br />
&#8220;call the standard &#40;not the FromISR versions&#41; from tasks&#8221;  
That keeps the rules simple and easy for people to follow.&nbsp; In reality whether these rules matter or not depends on the situation and more importantly on the port being used.&nbsp; On an STM32, doing what you are doing <strong>should</strong> be ok, I do similar things myself to optimise code, but with a bit of inside knowledge that you won&#8217;t get from the API.&nbsp; It is however not a well tested usage scenario.  
The STM32 implements a nest-able critical section inside the xQueueSendToBackFromISR&#40;&#41; function, so the critical section outside the function is obsolete, but provided this code is only executed from a task and not an interrupt, it should not be harmful.&nbsp; I presume in this case the critical section is there to protect the &#8216;u&#8217; variable, rather than the queue access.  
Going back to the original problem, am I correct in that the fundamental issue is that a task is blocked on a queue with a timeout, and if the timeout expires without any data arriving, then the task should unblock, but doesn&#8217;t?  
You also mention that, after the task should have unblocked &#40;but didn&#8217;t&#41;, the tick interrupt is still executing, but xTaskIncrementTick&#40;&#41; is returning false, hence no context switch is performed.  
Can you step through xTaskIncrementTick&#40;&#41; when this situation has occurred?&nbsp; We need to determine what it thinks the status of the system is.&nbsp; Basically we need to determine what state the task is in, is it still blocked on the queue, and if not, where is it.&nbsp; Maybe there just has been a data corruption within the kernel controlled data.  
I get nervous with printf&#40;&#41; being used in tasks, especially if Newlib is being used &#40;it is too big for small embedded systems, there is a new Newlib Nano now, but even so…&#41;, so I will also be interested to see if you notice a difference when you replace the printf&#40;&#41; with a direct write to the serial port.&nbsp; Start by writing to the serial port using a simple polling function to keep things as small as possible to start.&nbsp; If that works, we can add back in the DMA, and if that works, build up to adding back printf&#40;&#41;, until the problem occurs again.  
There is a very small and very limited printf&#40;&#41; implementation that comes with FreeRTOS that just requires you to write a character output function.&nbsp; You will find lots of copies of printf-stdarg.c in the FreeRTOS/Demo directory.&nbsp; It is a third party file though.

</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 task never gets ready</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 6, 2013</div><div class="thread-post-content">I think I can see why this is happening now.  
In previous versions of FreeRTOS the tick interrupt performed a context switch on each tick.&nbsp; Doing that meant tasks using<br />
&#8220;FromISR&#8221; functions inside the tick hook didn&#8217;t need to pend a context switch from inside the tick hook function because a context switch was going to be performed anyway.  
V7.5.x changed that behaviour so a context switch is only performed when xTaskIncrementTick&#40;&#41; returned pdTRUE &#8211; that is a major efficiency improvement but does have the effect that the tick hook function must now be treated like any other interrupt, with a context switch being pended if the &#8220;FromISR&#8221; function &#40;xSemaphoreGiveFromISR&#40;&#41; in this case&#41; unblocks a task of equal or higher priority than the current Running state task.&nbsp; In fact, the way it is, the last parameter to the &#8220;FromISR&#8221; functions is no longer really optional, especially if there are no other tasks in the system &#40;which would only be the case is test code such as this, not real applications, although a user opting to set it to NULL is also opting to delay when the task will run, but the documents say it will be on the next tick&#41;.  
This needs to be highlighted and the documentation updated accordingly.&nbsp; It might be that a check is inserted into the xTaskIncrementTick&#40;&#41; function so it returns true if the highest priority ready state task is above the currently running task &#8211; but that would have a run time impact.&nbsp; Instead, maybe an ASSERT&#40;&#41; could be added to check this, with a comment above the assert noting the circumstances that can cause it to be hit.&nbsp; That way the additional hit would only effect development builds.
