</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD in an ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 7, 2011</div><div class="thread-post-content"><blockquote>
  In the dsPIC33 demo, the serial driver interrupt routine has a taskYIELD, but in the Using the FreeRTOS Real Time Kernel, Sep 2011 edition &#40;for the PIC32&#41; stated that only API that end with FromISR are allowed in ISR
</blockquote>
The PIC32 book is for the PIC32, which in architecture terms is about as far away from a dsPIC as you can get.&nbsp; Why would it talk about an exception for a dsPIC any more than it would for a Cortex-M3?  
Not calling a function that does not end in FromISR from an ISR is a very good general rule in all cases.&nbsp; Some, but not many, ports can tolerate taskYIELD&#40;&#41; being called from an ISR, provided it is the last instruction in the ISR.&nbsp; In most cases, where this is the case, the call to taskYIELD&#40;&#41; is hidden behind a macro called portYIELD&#95;FROM&#95;ISR&#40;&#41;, or portEND&#95;SWITCHING&#95;ISR&#40;&#41;.&nbsp; The PIC24/dsPIC port is rather old, and that is probably why it was not done in that case.&nbsp; The documentation page for that port &#40;<a href="http://www.freertos.org/portpic24_dspic.html%29">http://www.freertos.org/portpic24&#95;dspic.html&#41;</a> does however say how it is done, albeit rather briefly.
