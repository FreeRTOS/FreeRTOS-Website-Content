  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">RL78 and priority level of interrupt</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/frantzca">frantzca</a> on October 26, 2011</div><div class="thread-post-content">Hi,  
I use Freertos with RL78 target and the compiler used is IAR. My Freertos configuration doesn’t use the preemption &#40;configUSE&#95;PREEMPTION == 0.&nbsp;   
I’ve encountered some “jitter” problems with a timer interrup. This regular interrupt must be acknowledged in my application without this jitter. I have checked the reason of this jitter and I’ve seen that the macro taskYIELD&#40;&#41; use the BRK instruction. The acknowledgement of this interrupt disables all interrupts &#40;like DI&#41;, and my normal interruption is served only after each RETB instruction. &#40; For my test, I have got only one active&nbsp; task and this task is suspended by call of vTaskDelay&#40;&#41; , so portYield&#40;&#41; is called everytime&#41;  
Furthermore, the RL78 can have 4 levels of interruption.   
My questions are as follows:  
1&#41; It is possible to introduce the concept of priority level and have the same behaviour as RX62N, with the 2 parameters?<br />
&#35;define configKERNEL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;<br />
&#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;   
2&#41; Additionally and to avoid any problems with the interrupt being disabled in the main loop &#40;in case there is none preemption option&#41;, is it possible to not disabled the global flag interrupt &#40;as BRK instruction made&#41; or retabish it ?   
Thank you in advance for your answers.<br />
&nbsp;   
</div></div><div class="thread-post"><h3 class="thread-post-title">RL78 and priority level of interrupt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 26, 2011</div><div class="thread-post-content">These comments are made without having done any testing, so they are just ideas:  
1&#41; It may be possible to re-enable interrupts in the BRK handler to allow interrupts to nest <strong>provided</strong> the interrupts that do nest do not call any FreeRTOS API functions.  
2&#41; If you want nested interrupt to have access to the interrupt safe FreeRTOS API &#40;the API functions that end in FromISR&#40;&#41;&#41;, then you would have to change the ENTER/EXIT critical functions to mask off a subset of priorities only, maybe up to priority 2.&nbsp; You would also have to implement portSET&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#40;&#41; and portCLEAR&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#40;&#41; to do the same thing, with the SET macro returning the original interrupt priority, and the CLEAR macro restoring the original interrupt priority.  
Regards.
