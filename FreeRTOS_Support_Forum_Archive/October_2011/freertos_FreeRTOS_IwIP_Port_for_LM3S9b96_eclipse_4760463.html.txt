Which version of FreeRTOS is in <a href="http://code.google.com/p/lumweb/">http://code.google.com/p/lumweb/</a> ?&nbsp; If it is V5 or higher, then it should be 100% backward compatible with FreeRTOS V7 &#40;in theory&#41;, and all you need to do is drop the latest files over the top of the older files in your project and rebuild.&nbsp; If it is earlier than V5 you are using something that is really really old, and there was a change to either the xQueueSendFromISR&#40;&#41; or xQueueReceiveFromISR&#40;&#41; function &#40;I forget which, without looking it up, but it is documented in <a href="http://www.FreeRTOS.org/History.txt%29">http://www.FreeRTOS.org/History.txt&#41;</a> which makes it not quite compatible with V7.  
<blockquote>
  I can build it without an error, but every time I write it into the flash from my board and reboot the board, my board is &#8220;damaged&#8221;. it reacts on nothing, the jtag interface doesn&#8217;t work and the reset button doesn&#8217;t work. </blockquote>
So I think there is a basic hardware configuration failure
I would guess you are correct &#8211; but don&#8217;t know for sure.&nbsp; It is probably re-configuring the pins required for your debugger.&nbsp; It could be other things though.&nbsp; I would suggest commenting all the code out, then adding bits in one thing at a time until you find the bit that is stopping the debugger working.  
<blockquote>
  I am wondering why the demo is called CORTEX&#95;LM3Sxxxx. Where can I tell the application that I have a LM3S9B96?
</blockquote>
The demo was written long before the LM3S9Bx processors came out, but FreeRTOS runs on any Cortex-M device as it only uses the core.&nbsp; The demo might configure pins for LEDs or a peripheral that is messing you up, but the FreeRTOS kernel itself definitely won&#8217;t be.  
I presume you have populated the interrupt vector table correctly with the FreeRTOS functions?  
If you look at the documentation page for the demo you are using it gives you a list of the hardware it has been tested on.  
<a href="http://www.freertos.org/portlm3sx965.html">http://www.freertos.org/portlm3sx965.html</a>

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + IwIP Port for LM3S9b96 + eclipse</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 23, 2011</div><div class="thread-post-content">It sounds like your 1 ms task is starving lower priority tasks of CPU time, so if it was not the DHCP it would be something else. I suggest doing the 1 ms processing in an interrupt triggered by a timer. If you set the priority of the interrupt above configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY &#40;so a lower numerical value&#41; then the interrupt will be very accurate but can&#8217;t use freeRTOS calls.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + IwIP Port for LM3S9b96 + eclipse</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 23, 2011</div><div class="thread-post-content">How have you implemented this 1ms &#8220;hard real time&#8221; task? What is it waiting on so that it starts it processing, and how is it telling the system it is done &#40;this may be the same thing&#41;.   
How much time is it going to take to do it processing every 1ms.  
All tasks &#40;except maybe idle priority tasks&#41; should have in their processing loop some form of a &#8220;wait for something&#8221; be it time or a semaphore or queue to tell them to start up. If they don&#8217;t, then they will naturally just take up all the processor time at that level and not let lower priority tasks run. Note that a &#8220;Yield&#8221; doesn&#8217;t really count, as&nbsp; that will let other tasks of the SAME priority run, but not lower.
