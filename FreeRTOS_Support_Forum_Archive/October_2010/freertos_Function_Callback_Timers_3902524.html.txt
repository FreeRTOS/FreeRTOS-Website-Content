  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Function Callback Timers</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/byates">byates</a> on October 18, 2010</div><div class="thread-post-content">Hello all,  
I am running freeRTOS on a cortex m-3. I need a way to implement time-out handling.&nbsp; I figure the easiest way to go about this is create a timer task that checks timer values every 1 second and calls an associated function when they expire. I would also need a small function library for creating, deleting, and modifying timers.<br />
Seeing as this is likely a common problem, and figured I would check to see if there are any open source libraries available to do this sort of thing with freeRTOS. Does any one have any suggestions on how to go about implementing this, or potential problems I may run into?  
Thanks&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Function Callback Timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on October 18, 2010</div><div class="thread-post-content">Can you explain a little more about what you mean by time out handling? I think most of the communication API functions allow a block time to be stated, and return fail if the block time times out before the communication event happened successfully. You could check the return value from the API function and handle the time out there, or do I miss the point?  
It sounds like your timers are just execute once timers. If you want periodic timers then look at adding something to the tick hook.
</div></div><div class="thread-post"><h3 class="thread-post-title">Function Callback Timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/byates">byates</a> on October 18, 2010</div><div class="thread-post-content">I have thought about using a comm API function call with a timeout, but that would result in blocking a thread that I would rather not block.  
Here&#8217;s an example of how I would be using these. I have one thread that turns on a gps receiver. When the gps device is turned on, I would like to start a 1 minute timer. If a gps fix is acquired, I would kill the timer. If the timer expires before a gps fix is acquired, I would like to turn off the gps receiver.  
I could block for 1 minute in the thread on a semaphore generated by a gps fix being acquired, and then take action depending on the return value. But this would result in that thread being blocked for a minute when I need it too continue execution.  
I am also very memory constrained and need to minimize the number of tasks I use
</div></div><div class="thread-post"><h3 class="thread-post-title">Function Callback Timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on October 19, 2010</div><div class="thread-post-content">Byates, a question comes up, in what thread should the timeout function get called?&nbsp; A running thread can not suddenly be yanked to do this operation, so fundamentally you need a new thread to handle this timeout. This thread could wait on a queue which you send signals on &#40;based on the value sent&#41;. The first signal marks that the GPS is started. When the task get that it sets a flag and waits again for 1 minute. If a lock is obtained, you send it a second signal and the task clears the flag. If the task times out, and the flag says you last started, you know that it is time to shut down the receiver.   
One thing to help with the memory would be to see if you can use co-routines instead of tasks, which could save memory for task stacks.
</div></div><div class="thread-post"><h3 class="thread-post-title">Function Callback Timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 19, 2010</div><div class="thread-post-content">Quoting from several posts:  
<blockquote>
  When the gps device is turned on, I would like to start a 1 minute timer
</blockquote>
The timing constraints are very course then, which makes it easier.  
<blockquote>
  in what thread should the timeout function get called?&nbsp; A running thread can not suddenly be yanked to do this operation, so fundamentally you need a new thread to handle this timeout
</blockquote>
I think it depends on the structure of the other tasks I suppose, also, what the task that is using the GPS is doing while no signal is available.&nbsp; If it has no work to do until there is no signal then the problem would not exist, so I assume it has other functionality it must maintain while waiting for the signal.  
Presumably it will be checking the signal status before trying to use the GPS data anyway?&nbsp; In which case some status variables could be set from an interrupt to say when the signal was locked &#40;assuming the GPS generates interrupts&#41; if it would take to long to query the GPS device directly.&nbsp; The interrupt could also clear the timer.&nbsp; The task that used the GPS data would then just have to check the status variables.&nbsp; In this case the tick hook could be used for the timer functionality.&nbsp; When the GPS receiver was switched on the timer count down value would be set.&nbsp; The tick hook would decrement the count down value, and set one of the status variables accordingly &#40;timeout condition&#41;, or call a function, if the decrement caused the count down value to change from 1 to 0.&nbsp; In all other cases no further action would be taken.&nbsp; Obviously the decrement would only occur if the count down values was greater than 0.  
I do have a timer module that allows timers to be created and deleted on the fly, but it is very, very, very &#40;get the idea&#41; old.&nbsp; I might not even be able to find it now.&nbsp; My problem with it is finding an efficient way to process timers.&nbsp; FreeRTOS never walks through a linked list from within an interrupt or while interrupts are disabled, so a linked list of timers that are processed in the tick is against the design philosophy &#40;responsiveness and determinism being the issues&#41;.&nbsp; Statically declared/coded timer functionality as described in the paragraph above is less of a problem as simple switch statements, etc. can be used.  
Regards.
