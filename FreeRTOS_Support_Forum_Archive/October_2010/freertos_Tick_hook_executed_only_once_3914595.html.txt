  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Tick hook executed only once</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/esorol">esorol</a> on October 26, 2010</div><div class="thread-post-content">Hi  
I have a piece of example code for the ATmega644 which behaves, in my opinion, somewhat unexpectedly. When the system starts up, I want to run the system with idle task only and see how many times the hook is called. After this, the system can continue initialization. For this reason, I create the task to init the system but request it to delay for 100 milliseconds right away.  
In the tick hook, I keep track of some support info &#40;not included in the code I intend to post&#41; but also check to see when the 100 milliseconds have passed and I can continue initialization.  
My problem is that the tick hook is called only once, during the entire execution of the program. Thus, the idle task remains the only task running and the rest of the firmware is never inited. From what I can gather, after executing the hook and the code in vPortYieldFromTick function, the &#8220;reti&#8221; command is not executed so the tick interrupt is not re-enabled.  
In the next post I will attach a sample AVR Studio project which &#40;for me&#41; causes the problem.  
Best regards,  
// Esorol
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick hook executed only once</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/esorol">esorol</a> on October 26, 2010</div><div class="thread-post-content">Ok, it seems I need to open a bug &#40;?&#41; to post the project. So I thought I&#8217;d wait and see if someone has opinions.  
The reason for wanting to check how many times the idle hook is called when the system is &#8220;idling&#8221; is that I can use this benchmark later in the firmware for estimating the CPU load. By counting the number of times the idle hook is called during normal execution, and comparing to the idling benchmark, I can get a rough idea of how much time is spent in the idle task.  
// Esorol
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick hook executed only once</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/esorol">esorol</a> on October 26, 2010</div><div class="thread-post-content">Update: tried different optimization levels, and it seems that this might be the cause of the problem. In  
<pre><code>void SIG_OUTPUT_COMPARE1A( void )
    {
        vPortYieldFromTick();
        asm volatile ( "reti" );
    }
</code></pre>
the &#8220;reti&#8221; instruction seems to have been optimized away. Is there a way to require that it <strong>not</strong> be optimized away?  
// Esorol
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick hook executed only once</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on October 26, 2010</div><div class="thread-post-content">As far as I thought, the only purpose of the volatile keyword after the asm was to prevent the reti being optimized away &#40;and to prevent asm instructions from being reordered&#41;. Are you sure that is what is happening though? It might be that the reti is being placed inside vPortYieldFromTick&#40;&#41;, I have seen that sort of behavior from GCC before and in this case would almost certainly cause a failure. Try looking at the assembly code in the debugger.
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick hook executed only once</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/esorol">esorol</a> on October 27, 2010</div><div class="thread-post-content">Hi  
Thanks for the reply. I compared the code which is generated with -O3 optimization level &#40;does not work correctly&#41; and that of -O2 optimization &#40;works&#41;. In the -O2 optimization, the call to vPortYieldFromTick is compiled as a &#8220;subroutine&#8221; which is actually CALL-ed. The code snippet posted above thus generates two assembler instructions, CALL and RETI which is quite correct.  
At the -O3 level, however, the vPortYieldFromTick is inlined instead of CALL-ed. For some reason, the compiler then leaves out the RETI instruction, preferring the RET which is defined at the end of the vPortYieldFromTick function &#40;see below&#41;.  
<pre><code>void vPortYieldFromTick( void ) __attribute__ ( ( naked ) );
void vPortYieldFromTick( void )
{
    portSAVE_CONTEXT();
    vTaskIncrementTick();
    vTaskSwitchContext();
    portRESTORE_CONTEXT();
    asm volatile ( "ret" );
}
</code></pre>
So now that the error mechanism is detected, is there a need to &#8220;fix&#8221; this somehow?  
// Esorol
