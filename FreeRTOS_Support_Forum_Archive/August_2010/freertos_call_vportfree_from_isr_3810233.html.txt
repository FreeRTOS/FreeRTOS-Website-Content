</div></div><div class="thread-post"><h3 class="thread-post-title">call vportfree from isr</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 14, 2010</div><div class="thread-post-content"><strong>Never</strong> call a function that does not end in FromISR from an ISR.
</div></div><div class="thread-post"><h3 class="thread-post-title">call vportfree from isr</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 14, 2010</div><div class="thread-post-content">As was said, calling any FreeRTOS function that doesn&#8217;t end in FromISR in an ISR is an invitation for trouble. As it turns out, memory management &#40;malloc/free type functions&#41; do not work well in an ISR, because of there need to set up periods where they are not disturbed while they manipulate structures shared among multiple tasks &#40;the free store list&#41;. In general, there are 3 categories of ways to implement this: Disabling Interrupt, Disabling the Scheduler, or a Mutex. Some of the manipulations that a memory management routine does may take long enough that you sometimes don&#8217;t want to use the disabling interrupt method &#40;so FreeRTOS uses a Disabling the Scheduler method&#41;, but this is not compatible with the use of memory management during isrs, as that needs to use the Disabling Interrupt method.  
One option is to take the memory management routines &#40;vPortFree, vPortMalloc&#41; and rewrite them &#40;that is one reason it is nice to use open source, you have the source to modify&#41; to use critical sections instead of schedule disabling, and then add a FromISR version that assumes it is in an interrupt and thus doesn&#8217;t need the critical section. It would then be nice to submit this version back for others to use, maybe as a heap&#95;2isr.c  
The other option is to change the structure of your program a bit. If you only need free in the isr, once solution would be to set up a queue that rather than actually doing the free in the isr, it pushes the memory pointer on the queue, and then a task pops the pointer off and calls free. If you need to allocate in the isr, it gets a bit trickier, but often the buffer size needed is known ahead of time, so you can preallocate a buffer&#40;s&#41; for it to use.
</div></div><div class="thread-post"><h3 class="thread-post-title">call vportfree from isr</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/smarini1963">smarini1963</a> on August 18, 2010</div><div class="thread-post-content">this means that using the file heap&#95;2.c create a file heap&#95;2isr.c<br />
and internally substitute to tasksuspendall the portENTER&#95;CRITICAL&#40;&#41;<br />
and to taskresume all the portEXIT&#95;CRITICAL&#40;&#41;  
is it right?  
thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">call vportfree from isr</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 19, 2010</div><div class="thread-post-content">Yes, and then create another function vPortFreeFromISR that is just like vPortFree except it omits the portENTER&#95;CRITICAL&#40;&#41; and portEXIT&#95;CRITICAL&#40;&#41; and use THAT function inside the ISR.
