</div></div><div class="thread-post"><h3 class="thread-post-title">Demo code stuck at programming</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 24, 2010</div><div class="thread-post-content">From your question I am presuming you are talking about the demos that come with the PIC32 version of the FreeRTOS eBook.  
The MPLAB projects are configured to run on the PIC32MX795F512L-80I/PT &#40;which as a new generation part definitely does need the &#35;pragma config FSRSSEL = PRIORITY&#95;7 for it to be stable&#41;.&nbsp; Unfortunately I have never tried them on the PIC32MX360F512L, but I do know that the 360 part has 32K of RAM while the 795 part has 128K of RAM.&nbsp; The demo itself only uses a tiny amount of RAM, but I suppose the debugger might make assumptions as to which parts of the data space it can use itself, so my first question is, did you re-target the project correctly for this different part?&nbsp; There could also be differences in the flash programming I suppose &#40;but don&#8217;t know&#41;.  
It is strange that such a small change would cause a problem though.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Demo code stuck at programming</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 24, 2010</div><div class="thread-post-content"><blockquote>
  I haven&#8217;t changed anything about RAM parts
</blockquote>
Sounds like your memory map is very wrong then. Look in the IDE for a project setting that selects the part being used, that might then automatically correct he memory map. Alternatively, look in the files that are included as part of the project to see if there is a linker script. Finally, some projects will have a MCU specific header file included that sets all the configuration options. Look at the top of FreeRTOSConfig.h to see if there is such a header file.
