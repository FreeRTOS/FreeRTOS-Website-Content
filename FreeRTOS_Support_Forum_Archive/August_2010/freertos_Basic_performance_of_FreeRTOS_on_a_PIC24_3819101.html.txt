I have one more question.&nbsp; In my application I need to manage an RF module in an extrememly time dependent way so I think it needs to be interrupt driven with a priority higher then the FreeRTOS scheduler/dispatcher priority.&nbsp;&nbsp; Is it possible for this interrupt based code to wakeup normal FreeRTOS tasks from time to time such as when data is available?&nbsp;&nbsp; I think in Microsoft Windows OS driver programing, this is solved with DPCs which allows the interrupt routes to post a callback that gets run by the OS back at the scheduler IRQ level.&nbsp; Does FreeRTOS have anything like this or possibly even a solution to this problem?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/danlhenry">danlhenry</a> on August 20, 2010</div><div class="thread-post-content">You don&#8217;t need a development board.&nbsp; The instructions for that port include how to run using MPLAB&#8217;s MPSIM component.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 20, 2010</div><div class="thread-post-content">I haven&#8217;t done a detail timing analysis like what you are asking, but as been said, that can be done with the simulator.  
As to higher speed interrupts waking up tasks, yes that is very possible. What is normally done is the task wait on a semaphore take, and a high speed interrupt does a semaphore give, or if a little bit of data needs to be sent, use a queue, interrupt puts into the queue, task pops data out of the queue.   
One thing to note, is that interrupt that interact with FreeRTOS can not nest, so if the RF module needs to signal a task with FreeRTOS operations, it will be disable during the tick interrupt.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/armag1234">armag1234</a> on August 20, 2010</div><div class="thread-post-content">Thanks, I found the instructions for the PIC24F port and I&#8217;m playing with the simulator now to see some of the timing info.

Interrupts &lt;= Scheduler IRQ&#40;including tasks&#41; can call into the scheduler<br />
Scheduler IRQ &#8211; This is the IRQ most of the FreeRTOS APIs run at&#40; this includes IRQs running at the scheduler IRQ &#41;<br />
Interrupt &gt; Scheduler IRQ can&#8217;t interact with FreeRTOS  
I need my RF IRQs to run at a higher priority then the scheduler so that it can&#8217;t be interrupted&#40; or disabled &#41; at all by FreeRTOS, yet be able to unblock FreeRTOS tasks when data is received.&nbsp; As I understand it, this is not possible with FreeRTOS as it is implemented today because higher priority IRQ can not interact with FreeRTOS tasks or objects.&nbsp; Correct?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/armag1234">armag1234</a> on August 20, 2010</div><div class="thread-post-content">BTW, like I said I think the way this is solved in the Microsoft Windows Driver programming model is that high priority routine queues a callback that runs after the interrupt finshing that runs at the scheduler IRQ.&nbsp;&nbsp;&nbsp; This callback can then set the semaphore that you refer to. I&#8217;m not sure how Linux solves this problem.  
The problem is that I don&#8217;t see a clean way to add this to the FreeRTOS programming model.&nbsp; The best solution I can think of is to burn a microcontroller resource like a hardware timer set to a very small value that can be armed inside the high priority interrupt that runs at the scheduler priority.&nbsp;&nbsp; This interrupt could call functions on the semaphore and then call yield.&nbsp; No nesting would occure.

</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/armag1234">armag1234</a> on August 21, 2010</div><div class="thread-post-content">Absolutely&#33;  
&#8220;ISR&#8217;s running above the kernel priority are never masked out by the kernel itself, so their responsiveness is not effected by the kernel functionality. <strong>However, such ISR&#8217;s cannot use the FreeRTOS.org API functions</strong>. The fast timer interrupt test within this demo demonstrates this configuration.&#8221;  
This limitiation is too much for my application so I need to find a work around.&nbsp; Either by changes in my application or changes to the FreeRTOS source code.&nbsp;&nbsp; I want to be able trigger calls to API functions due to events that happen during the higher priority interrupts.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 21, 2010</div><div class="thread-post-content">The PIC processors tend to have a lot of interrupt vectors, and it is easy to &#8220;force&#8221; an interrupt &#40;you just set the corresponding IF register&#41;. A good solution is to use one of the interrupt vectors for a peripheral you are not using, set its priority to configKERNEL&#95;INTERRUPT&#95;PRIORITY and have the high priority interrupt set the IF for that vector. This lower priority vector can then call the FromISR API.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/danlhenry">danlhenry</a> on August 21, 2010</div><div class="thread-post-content"><blockquote>
  <strong>However, such ISR&#8217;s cannot use the FreeRTOS.org API functions.</strong>
</blockquote>
No, I&#8217;m referring to the the paragraph &#40;a.&#41; immediately above what you quoted, that describes an interrupt <em>returning</em> to a kernel priority level handler that it had just awakened.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 21, 2010</div><div class="thread-post-content">I think you are misunderstanding what the topic is describing. The Interrupt handling &#8216;tasks&#8217; that is described is a normal task, that is assigned a very high FreeRTOS priority, so that when the interrupt wakes it up, it will execute immediately upon return from the ISR &#40;after the context switch that happens at the end of that ISR&#41;.   
It is NOT returning to a &#8216;kernel priority level handler&#8217;, but to a &#40;non-interrupt level&#41; handler task to continue to process the effects of the interrupt. The idea is to have a very small ISR, that does the minimal work required, as fast as possible, to service the interrupt, and that then passes control &#40;via a synchronizing primitive&#41; to a handler TASK to complete the longer parts of the servicing.   
The PIC24 currently &#40;as far as I know&#41; does not implement the configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY option yet, so all interrupt that use the FromISR API are at configKERNEL&#95;INTERRUPT&#95;PRIORITY, so do not have nesting.

It would be nice though if some portable mechanism were available for doing this.&nbsp;&nbsp;&nbsp;&nbsp; Ive been trying to think of ASM code that could wrap the &#40;&gt;KERNEL&#95;INTERRUPT&#95;PRIORITY&#41; interrupt to do this without resorting to undocumented tricks and I can&#8217;t quite see how to do it.  
Is this a common mechanism on other CPU archetectures to be able to manually set an interrupt flag to force an interrupt?
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 22, 2010</div><div class="thread-post-content">Forcing interrupts like this is hardly &#8220;undocumented&#8221;, the Microchip manuals clearly talk about this as an valid operation. I would also say that it is fairly common on this scale of processors to have some way to &#8220;simulate&#8221; an interrupt of some sort &#40;the mechanism may vary though&#41;. Somehow &#8220;portable&#8221; and dealing this close to the hardware doesn&#8217;t really happen.&nbsp; The whole structure is ISR&#8217;s is fairly loaded with device dependencies &#40;there are a number of common aspects, but there is always a core of device dependencies around&#41;.  
For the PIC24, you don&#8217;t need to &#8220;wrap&#8221; anything. The high level interrupt is written just like any normal interrupt routine. If you want to trigger the configKERNEL&#95;INTERRUPT&#95;PRIORITY isr, you just use a line like &#95;xxIF = 1; to request the interrupt &#40;xx being the device you are using to for this&#41;, so you actually don&#8217;t need to drop into ANY asm code.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/armag1234">armag1234</a> on August 22, 2010</div><div class="thread-post-content">Thanks for the info.&nbsp; Like I said, I&#8217;ve confirmed on both the simulator and a real PIC that the &#95;xxIF = 1 works.&nbsp; It&#8217;s too bad Microchip didn&#8217;t dedicate a few of those 100 some interrupt sources specifically for this.&nbsp; It&#8217;s appears the &#95;xxIF needs to be for a real peripheral that isn&#8217;t used by the firmware.  
I also realized I don&#8217;t need any ASM for the &#95;xxIF =1 solution.&nbsp;&nbsp; I was simply trying to think of an alternative through ASM that would give the same result by pushing and poping items from the stack without using the &#95;xxIF = 1 trick.  
Anyway, thanks for everyone&#8217;s help.
</div></div><div class="thread-post"><h3 class="thread-post-title">Basic performance of FreeRTOS on a PIC24</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 22, 2010</div><div class="thread-post-content">The problem with trying to &#8220;fake&#8221; the interrupt with asm code, would be that if you are in a critical section or a configKERNEL&#95;INTERRUPT&#95;PRIORITY interrupt, you don&#8217;t want to actually go straight to your low level isr, but need to hold off until that critical section or interrupt is over.   
I suppose one option would be to put a test at the end of the critical section and interrupt, to see if you should do something and go to it. This of course has a cost of doing this test all the time, and needing to special code for your case &#40;or building some framework to handle a general case here&#41;.
