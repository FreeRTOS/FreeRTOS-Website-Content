  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem using a minary semaphore</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/barbercolman">barbercolman</a> on August 18, 2010</div><div class="thread-post-content">I have a serial communications task and a display task. The serial task creates a binary semaphore at task initialization<br />
&nbsp;&nbsp;&nbsp; vSemaphoreCreateBinary&#40; xPacketReceivedSemaphore &#41;;<br />
The receive interrupt gives the semaphore after a packet is received.<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; xSemaphoreGiveFromISR&#40; xPacketReceivedSemaphore, &amp;xHigherPriorityTaskWoken &#41;;<br />
The serial task sends a new request for a packet of data after receiving a packet or one second without receiving a packet<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if&#40; xSemaphoreTake&#40; xPacketReceivedSemaphore, &#40;1000 / portTICK&#95;RATE&#95;MS&#41; &#41; == pdTRUE &#41;&#123;<br />
This process works well as long as communications is started before the display task starts. If the display task before the first packet is received the serial task get to the xSemaphoretake and never returns.  
Any idea what is happening? This processor is not starved. the vApplicationIdleHook is being called. I am using freeRtos 6.03 and a PIC32MX.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem using a minary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 18, 2010</div><div class="thread-post-content">The first question is what does the display task have anything to do with the serial operation?   
Second, the take you have shown will return after the second &#40;unless you have corrupted something or the time has stopped&#41;. If a packet isn&#8217;t sent and the semaphore raised, it will return pdFALSE and not go into the statements controlled by the if, so that clause should only process the previous packet, and after the if, should be the statement to request the next one..
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem using a minary semaphore</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/barbercolman">barbercolman</a> on August 19, 2010</div><div class="thread-post-content">It is a very good question. It should not, but it does.   
When it works a new packet is sent as soon as the last packet is returned. If a packet is not responded to a new packet will be sent after the 1 second delay.  
This does work but only when a packet has been sent and responded to before the graphics task has started. It does not make sense to me. I think my next step is to look in task.c and see why the communications task is not running.
