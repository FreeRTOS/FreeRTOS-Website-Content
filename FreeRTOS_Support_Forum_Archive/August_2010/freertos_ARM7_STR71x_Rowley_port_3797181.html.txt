We need to determine what, after hitting the task, is the route cause.&nbsp; The first thing I would suggest is to stop your task from doing anything, and disable interrupts.&nbsp; So add something like:  
<pre><code>taskDISABLE_INTERRUPTS();
for( ;; ); /* NULL loop. */
</code></pre>
at the top of the task.&nbsp; If the task still executes, sits in the null loop, and does not crash then the next thing to do would be remove the taskDISABLE&#95;INTERRUPTS&#40;&#41;; call to see if it is still happy, and to see if the tick interrupt will execute repeatedly.  
Things to check/note:  
1&#41; You set Supervisor mode before calling main&#40;&#41;, although I think in this case that must already be true.  
2&#41; You set up stacks for at least IRQ and Supervisor modes, other modes if you use them too.  
3&#41; You are installing the FreeRTOS SWI handler, and using IRQ interrupts in a FreeRTOS compatible way.

</div></div><div class="thread-post"><h3 class="thread-post-title">ARM7 STR71x Rowley port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 6, 2010</div><div class="thread-post-content">IRQ interrupts can be implemented in two ways.&nbsp;   
1&#41; Save/Restore the task context from a central point, before calling the application code, removing the need for the application interrupt handlers to perform any save or restore operations explicitly.&nbsp; This allows easier implementation of ISRs, but can be execution time inefficient if not all interrupts have the potential to perform a context switch as the save/restore is executed on each interrupt.  
2&#41; Vector directly to an application defined interrupt handler, where the context save/restore is included explicitly in the application defined ISR definition.&nbsp; This can be more execution time efficient where not all interrupts have the potential to perform a context switch, but less code size efficient as the context save/restore code will be duplicated in each ISR definition that has the potential to perform a context switch.&nbsp; It also complicates the ISR implementation.  
It appears your code is using method 1.&nbsp; Line 514 in <a href="http://ideone.com/HGLsU">http://ideone.com/HGLsU</a>  
vPortPreemptiveTick&#40;&#41;&nbsp; is called in response to tick interrupts, after the task context has been saved.&nbsp; However, it is declared naked so the compiler will not generate any prologue or epilogue code for it, and it does not include any explicitly itself.&nbsp; The function will be entered, but execution will just run off the end of the function without attempting to return.&nbsp; Remove the naked attribute.  
Conversely, vPortYieldProcessor&#40;&#41;&nbsp; is jumped to directly from the vector table, before any context saving and restoring is performed &#40;goes through the SWI rather than IRQ&#41;.&nbsp; It is declared naked, BUT uses the portSAVE/RESTORE&#95;CONTEXT&#40;&#41; macros to perform the necessary prologue and epilogue entry and exit routines.  
Maybe not everything, but at least something to start off with.  
Regards.
