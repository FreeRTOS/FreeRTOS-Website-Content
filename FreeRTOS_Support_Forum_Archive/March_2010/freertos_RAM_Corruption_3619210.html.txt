  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">RAM Corruption</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">I am attempting to track down a RAM corruption issue.  
Project Info:  
Processor: STM32F103VE &#40;Coretx M3&#41;<br />
Tools: ARM RVDS 4.0 SP3<br />
Free RTOS V6.0.4<br />
Using Portability Functions: RVDS-&gt;ARM&#95;CM3  
It appears that the Main Stack Pointer &#40;MSP&#41; is being corrupted when the RTOS is starting up. I traced it down to a function that sets the MSP. The function is called vPortStartFirstTask. On completion of this function the MSP is pointing directly in the middle of an array that I have defined to hold some data for my LCD. This is causing the LCD data to become corrupted.  
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 19, 2010</div><div class="thread-post-content">Normally cortex m3 chips will define a stack either as a simple array or by reserving space using the linker script. In either case the first position in the vector table should be set to point to the stack. Is this the case in your application?   
Is the linker script reserving space for your LCD buffer, or is that just using C variables?  
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">I put a break point at the entry point my my main function and then looked vector table as you suggested. It apears that the SP address that is located in the vector table is not correct.  
I am using a static C varaiable to hold the LCD data.
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">Actually the SP matches what is defined in the startup&#95;stm32f10x&#95;hd.s file.  
&#95;&#95;initial&#95;spTop EQU&nbsp;&nbsp;&nbsp; 0x20000400&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; stack used for SystemInit&#95;ExtMemCtl<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; always internal RAM used   
The problem is that my static array for the LCD data is showing an adddress, in the debugger, of 0x200001D8 and has a length of 0x610 Bytes.
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 19, 2010</div><div class="thread-post-content">So that explains the corruption, the question now is how did it get to be like that?&nbsp; It sounds like a linker script error.  
Is your application based on a demo from the main FreeRTOS zip file?
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">I agree that it looks like a linker issue. I think I may be missing something my the linker directive file &#40;scatter file&#41; or in the project settings.&nbsp; The project is not bassed on the demo in the Free RTOS zip file. I didn&#8217;t think there was a demo for ARM RVDS. I though that only CM3 ones were for MDK. 
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/thomask">thomask</a> on March 19, 2010</div><div class="thread-post-content">davedoors wrote:  
&gt; Normally cortex m3 chips will define a stack either as a simple array or by<br />
&gt; reserving space using the linker script. In either case the first position in<br />
&gt; the vector table should be set to point to the stack.   
As I reported on 15.12.2009, &#8220;Potential stack problem on STM32&#8221;, there are use cases where the &#95;actual&#95; stack pointer will have to differ from the &#95;initial&#95; stack pointer given in the vector table.  
The STM3210E Eval board features external memory, and the ST provided startup-code will move the stack pointer to that memory after initializing the FSMC &#40;flexible static memory&#41; controller.  
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">After looking at this some more , my MAP file generated by the linker is telling me that the Stack is located at: 0x20008128 with a length of 0x2000  
&nbsp;&nbsp;&nbsp; 0x20002128&nbsp;&nbsp; 0x00006000&nbsp;&nbsp; Zero&nbsp;&nbsp; RW&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 69&nbsp;&nbsp;&nbsp; HEAP&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; startup&#95;stm32f10x&#95;hd.o<br />
&nbsp;&nbsp;&nbsp; 0x20008128&nbsp;&nbsp; 0x00002000&nbsp;&nbsp; Zero&nbsp;&nbsp; RW&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 68&nbsp;&nbsp;&nbsp; STACK&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; startup&#95;stm32f10x&#95;hd.o  
The first entry in the vector table doesn’t match this value.   
This appears to be because the startup&#95;stm32f10x&#95;hd.s file defines the &#95;&#95;initial&#95;spTop EQU&nbsp;&nbsp;&nbsp; 0x20000400  
This value is then used in the Vectors section:  
&#95;&#95;Vectors&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; DCD&nbsp;&nbsp;&nbsp;&nbsp; &#95;&#95;initial&#95;spTop&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; Top of Stack<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; DCD&nbsp;&nbsp;&nbsp;&nbsp; Reset&#95;Handler&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; Reset Handler<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; DCD&nbsp;&nbsp;&nbsp;&nbsp; NMI&#95;Handler&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; NMI Handler  
On entry to main &#40;&#41; the MSP register value is equal to 0x2000A110. Which looks like an okay address for the stack based on the stack starting at 0x20008128 with a length of 0x2000.  
I think the problem, as tomask mentioned, is that the FreeRTOS code is initializing the MSP using what is in the vector section.  
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 19, 2010</div><div class="thread-post-content">I could introduce something for all Cortex-M3 ports whereby the address of the stack to use after the scheduler is started is set using a &#35;define.&nbsp; If the define exists then the address is used, if the define does not exist then the address from the vector table is used.  
Thoughts?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">RAM Corruption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jrubis">jrubis</a> on March 19, 2010</div><div class="thread-post-content">I checked the start up file from a STM32 sample in Keil MDK.

&#95;&#95;Vectors&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; DCD&nbsp;&nbsp;&nbsp;&nbsp; &#95;&#95;initial&#95;sp&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; Top of Stack

&#95;&#95;Vectors&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; DCD&nbsp;&nbsp;&nbsp;&nbsp; &#95;&#95;initial&#95;spTop&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ; Top of Stack

With this version the first entry in the Vector Table is:
