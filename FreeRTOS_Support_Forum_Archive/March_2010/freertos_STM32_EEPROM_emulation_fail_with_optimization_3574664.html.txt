  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32 EEPROM emulation fail with optimization</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spotdott">spotdott</a> on March 3, 2010</div><div class="thread-post-content">I am using the Code Sourcery G++ Lite gcc compiler with the optimization flag set to optimize size &#40;Os&#41;.&nbsp; Unfortunately this made the application unable to read or write to flash using EEPROM emulation.&nbsp; I tried to optimize with only a level one without success.&nbsp; This narrows down the flags to the list below:  
<pre><code>          -fauto-inc-dec 
          -fcprop-registers 
          -fdce 
          -fdefer-pop 
          -fdelayed-branch 
          -fdse 
          -fguess-branch-probability 
          -fif-conversion2 
          -fif-conversion 
          -fipa-pure-const 
          -fipa-reference 
          -fmerge-constants
          -fsplit-wide-types 
          -ftree-builtin-call-dce 
          -ftree-ccp 
          -ftree-ch 
          -ftree-copyrename 
          -ftree-dce 
          -ftree-dominator-opts 
          -ftree-dse 
          -ftree-forwprop 
          -ftree-fre 
          -ftree-phiprop 
          -ftree-sra 
          -ftree-pta 
          -ftree-ter 
          -funit-at-a-time
</code></pre>
Could one or more of these optimization flags cause EEPROM emulation to fail?
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 EEPROM emulation fail with optimization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 3, 2010</div><div class="thread-post-content">Well you could try adding in the optimisation flags one at a time until you start to get the problem again, but generally the route cause of this type of problem is something in the code being compiled, be it a volatile qualifier that is mising or something similar.&nbsp; Likewise it could be something not quite right in the compiler, but I would go through the code with a fine tooth comb first.&nbsp; These things can often be quite subtle.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 EEPROM emulation fail with optimization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spotdott">spotdott</a> on March 8, 2010</div><div class="thread-post-content">Yes it is a problem with the loop counter after optimization.&nbsp; I have setup a loop that counts the number of seconds.&nbsp; Once that counter reaches a certain size data is stored into EEPROM and the value resets.&nbsp;&nbsp; EEPROM works after the loop is diabled.&nbsp; Unfortunately declaring a variable volatile only means that the value of the variable is retrieved from SRAM instead of directly accessing it from the registers by the MCU.&nbsp; Does anyone have solved this problem before?  
Another thing that puzzles me is that after I get rid of a variable I do not use anymore in the header file STM32fx&#95;it.c &#40;the STM-32 peripheral library&#8217;s interrupt handler source file&#41; with the optmization flag set to Os, the controller throws a Hard Fault Exception near the very beginning.&nbsp; Of course Make Clean was the first thing I did.&nbsp; I searched &#40;and grepped&#41; for any occurrances where the variable might be used without luck.&nbsp; The problem is gone when I declare the variable again.&nbsp; What is weird is that I do not even have to give the variable the same as the one I removed&#33;&nbsp; It seems that as long there is A variable the firmware is happy.&nbsp; &#40;All other variables are extern in the file&#41;.&nbsp; Has anyone have encountered something similar before?
