  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Callback functions for posting to a queue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jmaygarden">jmaygarden</a> on March 10, 2010</div><div class="thread-post-content">I would like to setup a callback system for posting events to a task&#8217;s queue. However, I need to do so from both interrupt handlers &#40;xQueueSendFromISR&#41; and other tasks &#40;xQueueSend&#41;. Is there a way to determine which method should be used at runtime? Or should I just provide a different callback function for use in an ISR versus another task?  
Also, is it acceptable to use xQueueSendFromISR from another task? If so, what is different about it other than the timeout?
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 11, 2010</div><div class="thread-post-content">I believe that you can call xQueueSendFromISR at task level, IF you place the call inside a critical section or disable the interrupts. The one thing that you will need to watch out for, is if the call sets the woken flag, you will need to due a yield &#40;probably after you end your critical section&#41;.  
FreeRTOS doesn&#8217;t provide a built in way to determine if you are in an interrupt or not to allow you to make the decision, and you need a bit more than that. If you are in an interrupt routine, you will need to the FromISR version, and pass it the pointer to the woken flag that the ISR is using.&nbsp; It shouldn&#8217;t be too hard to adopt a standard interrupt entry style that clears the woken flag and sets a flag to let you know you are in an interrupt, and have standard exit code that clears the &#8220;in interrupt&#8221; flag &#40;if your architecture allows nesting of interrupt that interact with FreeRTOS, if there is such a beast, you would need to account for that&#41;, and check the woken flag to do the needed task switch. Either all interrupts can share the same woken flag, or you have a pointer to what is the &#8220;current&#8221; woken flag. You could then write a generic QueueSend that tests the in interrupt flag and call the appropriate function.
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 11, 2010</div><div class="thread-post-content">Just to add to what richard&#95;damon said, ports that support interrupt nesting should take care of the critical sections themselves, within the FromISR&#40;&#41; functions.&nbsp; Please check this though.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jmaygarden">jmaygarden</a> on March 11, 2010</div><div class="thread-post-content">Well, it does seem more straight forward to have two event posting functions &#40;ISR &amp; task level&#41; and build callbacks according to usage instead of trying to track interrupt status just to reduce it to one function with a branch…  
I&#8217;m using a Cortex-M3 and the context switch when the woken flag is set just sets the PENDDVSET bit in the NVIC controller. It&#8217;s safe to do this before the end of the interrupt, correct?  
<pre><code>bool
event_postfromisr(Event *event)
{
    portBASE_TYPE requestContextSwitch;
    bool ok;
    requestContextSwitch = pdFALSE;
    ok = xQueueSendFromISR(event-&gt;queue, event, &amp;requestContextSwitch);
    if (pdFALSE == ok) {
        /* Doh! We lost an event. */
    }
    if (requestContextSwitch)
        vPortYieldFromISR();
    return ok;
}
bool
event_postfromtask(Event *event)
{
    return xQueueSend(event-&gt;queue, event, portMAX_DELAY);
}
</code></pre>
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 11, 2010</div><div class="thread-post-content">Yes that looks fine to me &#8211; without studying it in any great detail.  
On the Cortex M3 all context switches are performed in the PendSV handler, so you are correct to say that all the vPortYieldFromISR&#40;&#41; does is set the pend bit.  
You don&#8217;t actually need to do that in every ISR &#8211; whether or not it is desirable or not is really dependent of the urgency of handling the event so is application dependent.&nbsp; If writing to the queue unblocks a task and that task has a higher priority than the running task then it will get selected at the next tick interrupt anyway.&nbsp; It is only necessary to context switch immediately if the requirements for how quickly the event must be processed are less than the time between each tick.&nbsp; Of course a really really real time system should run the task if its the highest priority anyway.&nbsp; Hope I&#8217;m not confusing things too much.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on March 23, 2010</div><div class="thread-post-content">I had the same problem, getting stuck in vListInsert.<br />
Problem is related to the interrupt priorities.<br />
The prioity of the interrupt you are calling the function xQueueSendFromISR must be greater than value you choose to use in the configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY configuration option.<br />
Note that in Cortex-M3 the greater interrupt value means lower priority for that interrupt.  
For example &#40;Cortex-M3&#41;:<br />
If you let the default value for configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY &#40;191&#41; you need to put 192 or a gretar value to the priority of any interrupt that uses any function from FreeRTOS API.<br />
And don&#8217;t forget to use functions …FromISR&#40;&#41; from within interrupt handlers.  
I hope this can help you in some way.
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jmaygarden">jmaygarden</a> on March 23, 2010</div><div class="thread-post-content">I though that the priority could be equal to configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY or lower &#40;higher number for Cortex-M3&#41;. That worked just fine for me with an STM32, but the SAM3U is having issue with it. I set configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY to configKERNEL&#95;INTERRUPT&#95;PRIORITY &#40;as shown below&#41; and it alleviated my problem. So, I know it is definitely related to interrupt priorities.   
<pre><code>#if 0
#define configKERNEL_INTERRUPT_PRIORITY         (0x0F &lt;&lt; 4) /* Priority 15, or 255 as only the top four bits are implemented.  This is the lowest priority. */
#define configMAX_SYSCALL_INTERRUPT_PRIORITY    (0x05 &lt;&lt; 4)     /* Priority 5, or 80 as only the top four bits are implemented. */
#else
#define configKERNEL_INTERRUPT_PRIORITY         (255)
#define configMAX_SYSCALL_INTERRUPT_PRIORITY    (255)
#endif
</code></pre>
I&#8217;m pretty sure I even tried using configKERNEL&#95;INTERRUPT&#95;PRIORITY for all of my interrupts and that didn&#8217;t do the trick either.  
Also, the problem is occurring with a xQueueSendFromISR from the real-time timer &#40;RTT&#41; alarm at 100 Hz. That module is very quirky. You have to poll the alarm status for 2 slow-clock cycles before exiting the interrupt. That makes the ISR take about 60 microseconds. I don&#8217;t like that one bit and perhaps it could mess up the kernel if its interrupts are blocked during that time?
</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 23, 2010</div><div class="thread-post-content">I don&#8217;t know if it is relevant in this case, but remember different M3 suppliers implement a different number of priority bits. Also different libraries expect the priority to be presented in a different way.&nbsp; For example, CMSIS libraries want the priority set in the least significant bits of the byte, while LMI libraries want the priority bits shifted up to the most significant bits of the byte.

</div></div><div class="thread-post"><h3 class="thread-post-title">Callback functions for posting to a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jmaygarden">jmaygarden</a> on March 23, 2010</div><div class="thread-post-content">You are correct. The change above breaks the FreeRTOS usage of those macros. What I actually needed to change was the value passed to NVIC&#95;SetPriority in user code. </code></pre>
