  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/seko1985">seko1985</a> on March 11, 2010</div><div class="thread-post-content">Hello everybody.<br />
Im using FreeRTOS in such configuration: at91sam7s256 + arm-none-eabi-compiler + Eclipse + jtagkey. Im using in my project two interrupt driven usarts &#40;ISRs are declared as naked&#41;. One usart is for Modbus, another one for other protocol called LonWorks &#40;im trying to develop kind of gateway between these two protocols&#41;. The problem I encountered is,that after some time of running with no problems, suddenly all interrupts are disabled &#40;from usarts and PIT interrupt&#41;, so my application is still runnig but the context switching is not performing and program stack in one task and round indefinetely in this task. No prefetch abort, no data abort. I am sure that there is no stack overflow, because i checked this. I thought that such behaviour can be caused by portENTER&#95;CRITICAL and portEXIT&#95;CRITICAL macros, but i comments line witch them and the problem still exists. maybe somoone had also encountered such problem and is able to help me or at least could told me where to find origin of problem.<br />
Thanks in advance 
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/seko1985">seko1985</a> on March 11, 2010</div><div class="thread-post-content">I&#8217;ve forgot to add, that before commenting line witch portENTER&#95;CRITICAL and portEXIT&#95;CRITICAL the interrupts were not enabling also if program was executing macro portEXIT&#95;CRITICAL &#40;i checked this using jtag and i am sure that asssembler code responsible for enabling interrupts was executing&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 11, 2010</div><div class="thread-post-content">When the problem happens, check the value of ulCriticalNesting. If you are not in a critical section then it should be 0.  
You say you declare the interrupt functions naked. Are you using the assembly wrappers for the interrupt functions, so the interrupt is entered through a wrapper that saves the context before calling a C function to do the actual interrupt processing?
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/seko1985">seko1985</a> on March 11, 2010</div><div class="thread-post-content">Yes of course there are wrappers to ISRs to both usarts and ulCriticalNesting is equal to 0 when the problem occurs. Through JTAG i can check my cpsr register value and is euqal to 1000000000000000000000000111111 &#40;this is value checked when all interrupts are disabled so the program is stack in one task&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/seko1985">seko1985</a> on March 16, 2010</div><div class="thread-post-content">Hello,<br />
This is me again. I have a question if it is possible, that too long interrupt service routine of USART can cause disabling all interrupts &#40;probably not, i cant realize such situation&#41;, i think the only effect of too long ISR is missinig some interrupts form USART. I checked my program, and problem of disabling all interrupts is caused by only one task. I have to taks and two ISR for USARTs. Both task are the same priority and when i send frames to one MODBUS task, system works perfect, but when i start to send frames to other task &#40;second USART&#41; after some time interrupts are disabled and program is getting stack in this task.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 + GCC + Interrupts Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/seko1985">seko1985</a> on March 19, 2010</div><div class="thread-post-content">Hello again<br />
I solved the problem. It was my fault beacuse I build ISR functions to one of usarts in wrong way. I had enabled interrupts from RXREADY, TXEMPTY, PARITY&#95;ERROR, BUFFER&#95;OVERRUN and FRAME&#95;ERROR and in ISR when i checked for last three mentioned interrupts i return from ISR without writing to AT91C&#95;BASE&#95;AIC-&gt;AIC&#95;EOICR, so when I send lots of messages to my hardware i probalby trigger BUFFER&#95;OVERRUN interrupt and this caused problem with disabling all interrupts.
