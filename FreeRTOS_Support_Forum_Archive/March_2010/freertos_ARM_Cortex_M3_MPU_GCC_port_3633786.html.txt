</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Cortex M3 MPU (GCC) port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 24, 2010</div><div class="thread-post-content">Going back to your original problem &#40;rather than answering your question :o&#41; the most common cause of a crash in a cortex M3 application is a misconfigured interrupt priority. This can result from a misunderstanding of how interrupts priorities are defined &#40;it is strange&#41; or the misuse of a vendor provided function used to set a priority &#40;the semantics differs between vendors and the vendors themselves get it wrong&#41;.  
This is some text from the SafeRTOS support forum, it holds true for FreeRTOS too except in FreeRTOS the priorities set by the constants can be configured:  
<blockquote>
  The SafeRTOS Cortex M3 port implements a full interrupt nesting model.&nbsp; Normally the user definable constants configKERNEL&#95;INTERRUPT&#95;PRIORITY and configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY define the interrupt priority used by the kernel itself and the maximum interrupt priority from which SafeRTOS API calls can be made respectively.&nbsp; However, when SafeRTOS is pre-loaded in ROM these constants cannot be modified.&nbsp; In the LM3S9B96 configKERNEL&#95;INTERRUPT&#95;PRIORITY is set to 255 and configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY is set to 191.   
</blockquote>
Important: The Cortex-M3 core uses numerically low priority numbers to represent HIGH priority interrupts, which can seem counter-intuitive and is easy to forget.&nbsp; If you wish to assign an interrupt a low priority do not assign it a priority of 0 &#40;or other low numeric value&#41; as this can result in the interrupt actually having the highest priority; and potentially make your system behaviour unpredictable if this priority is above portSYSCALL&#95;INTERRUPT&#95;PRIORITY. Interrupts that use the SafeRTOS API must be assigned a numeric priority of 191 or a numerically higher value to give them an interrupt priority equal to or lower than 191.&nbsp; Interrupts that make use of the SafeRTOS API must be explicitly assigned an interrupt priority as all interrupt priorities are zero by default.  
The value 191 is stated as if all eight priority bits were implemented.&nbsp; The LM3S9B96 only has three bits implemented, further the three bits are the top three bits of the byte.&nbsp; Therefore 191 is equivalent to &#40; 5 &lt;&lt; 5 &#41; , or simply 5 if a CMSIS function is used to assign a priority to an interrupt.

</div></div><div class="thread-post"><h3 class="thread-post-title">ARM Cortex M3 MPU (GCC) port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 24, 2010</div><div class="thread-post-content">Switching from the standard CM3 port to the MPU enabled CM3 port can be quite involved, unless you have experience of doing it before and have taken care not to accidentally use any shared memory from the outset.&nbsp; Once the MPU is enabled user mode tasks will not be able to access shared memory unless they are explicitly given access to a memory region &#8211; so in most cases you would have to both switch to the MPU enabled port files AND determine which tasks can legitimately access which memory.  
If you want to use the MPU enabled port then I would suggest that you start with one of the pre-configured MPU demo applications.&nbsp; That way you will have all the correct configuration from the outset &#40;the LPC17xx eBook also contains a short chapter on using the MPU port&#41; and can add in your own application code little by little so you always know you have a working configuration.  
The linker errors you are seeing are generated because the port code expects to see certain constants &#40;addresses&#41; defined in the linker script itself.&nbsp; Take a look at the linker scripts that come with the existing MPU demos.
