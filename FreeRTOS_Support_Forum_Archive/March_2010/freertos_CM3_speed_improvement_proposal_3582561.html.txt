  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">CM3 speed improvement proposal</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/artlip">artlip</a> on March 7, 2010</div><div class="thread-post-content">Hello,  
I want to propose improvements for a task switching and for a critical section code.  
The base concept is to change portYIELD, portENTER&#95;CRITICAL and portEXIT&#95;CRITICAL into macros which allows compiler to put it as inlined code. To achieve a full potential of the &#40;critical section&#41; inlined code there is also required a small change in the interrupt masking code. A compiler should be allowed to &#8220;freely&#8221; choose register used for storing constant &#40;mask value&#41;. BTW&gt; this improvement part is the same like the improvement request &#40;2709048&#41; from Samuel Tardieu.<br />
The downside of this solution is the increase of the OS code &#40;in case of tests described below it is 376 bytes&#41;. The exact size of increase depends on how many FreeRTOS functions &#40;with critical sections&#41; is used and does not depend on the number of API calls used in the application.  
I made two tests to check if this code fix will give a real speedup gain. Tests was performed using original FreeRTOS 6.0.3, GCC 4.4.3, compiler optimization -Os, STM32F103 @ 72MHz.  
1&#46; The first test was about speed of queue operations. There was configured 2 tasks with the same priority, queue with 1024 entries of 4 bytes long &#40;system tick period at 1ms&#41;.<br />
The first task puts into queue as many entries as possible. When queue is full task executes delay for one tick.<br />
The second task receives from queue as many entries as possible. When queue is empty task executes delay for one tick.<br />
There was measured number of successfull xQueueSend and xQueueReceive operations during test period &#40;20s&#41;.  
2&#46; The second test was about speed of a context switching. There was configured 2 tasks with the same priority, two binary semaphores &#8211; one of them intially acquired &#40;system tick period at 1ms&#41;.<br />
The first task acquires semaphore number 1 then releases semaphore number 2. The second task acquires semaphore number 2 then releases semaphore number 1.<br />
There was measured number of task loops during test period &#40;20s&#41;.  
Results:<br />
Test 1 &#8211; 5.8% improvement<br />
Test 2 &#8211; 15.9% improvement  
The first &#40;and obvious&#41; cause of this speedup is elimination of function calls and the second cause comes from the fact that Flash prefetch buffer is not disturbed.
