  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Starting &#8216;N&#8217; Tasks with a counting sem&#8230;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/steveb75">steveb75</a> on November 25, 2010</div><div class="thread-post-content">Hello All.  
&#40;Using PIC32 Starter Kit&#41;  
I&#8217;m trying to implement a sync/task start mechanism using counting semaphores.&nbsp; The purpose is to<br />
ensure all task Q&#8217;s/Semaphores and H/W is configured before any task begins communicating with<br />
another task.  
I have 5 tasks, each creating a Q or semaphore and corresponding H/W configuration.&nbsp; Each task calls<br />
semGive on a counting &#40;taskReady&#41; semaphore then immediately blocks on another counting &#40;taskStart&#41;<br />
semaphore.<br />
I have a 6th&nbsp; &#8216;supervisor&#8217; task that blocks on the taskReady semaphore and loops &#40;semTake&#41; around this<br />
semaphore until all tasks have reported ready.&nbsp; Once all tasks have given the taskReady semaphore, the<br />
&#8216;supervisor&#8217; task then gives the taskStart semaphore 5 times to allow each task to continue.  
The problem I&#8217;m facing is only the following two tasks that are created after the supervisor task &#40;from within main&#40;&#41;&#41;<br />
ever start i.e. supervisor is created 1st followed by task A, task B etc…. These tasks, A and B call semGive&#40;taskReady&#41; and the supervisor task unblocks twice &#40;semTake&#40;taskReady&#41;.&nbsp; A breakpoint in the third created task &#40;or any of the other tasks&#41; never hits?  
My understanding is that each task should start in accordance with the scheduler rules i.e based on the task pri or maybe the task creation order.&nbsp; After the supervisor task is unblocked twice for task A/B&#8217;s semGive&#40;taskReady&#41;, it becomes blocked again &#40;permantently&#41;.&nbsp; I would expect one of the other tasks to run and call its semGive&#40;taskReady&#41;?  
Any suggestions/advice would be greatly appreciated.  
Regards,<br />
Steve  
</div></div><div class="thread-post"><h3 class="thread-post-title">Starting &#8216;N&#8217; Tasks with a counting sem&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 25, 2010</div><div class="thread-post-content">It sounds like a very complex scheme and suspect the problem lies in its complexity somewhere.  
Why not initialize the hardware before starting the scheduler? If you want to modularize the drivers you can still have the driver encapsulate an initialization function that is called before the task is started.  
Alternatively you could have the tasks suspend themselves when they are ready and then the main task can simply check that all the tasks are suspended before starting the real work.
</div></div><div class="thread-post"><h3 class="thread-post-title">Starting &#8216;N&#8217; Tasks with a counting sem&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 25, 2010</div><div class="thread-post-content">One though, have you checked that the tasks were successfully created? If you run out of heap, then the tasks won&#8217;t all be created.
</div></div><div class="thread-post"><h3 class="thread-post-title">Starting &#8216;N&#8217; Tasks with a counting sem&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/steveb75">steveb75</a> on November 25, 2010</div><div class="thread-post-content">Thx chaps for the prompt feedback&#33;  
It seems I should not have been lazy and checked if each task was created correctly.&nbsp; Turns out more memory is required.&nbsp; Good call Richard.  
Dave &#8211; thx for your suggestion as well.  
Cheers,<br />
Steve
