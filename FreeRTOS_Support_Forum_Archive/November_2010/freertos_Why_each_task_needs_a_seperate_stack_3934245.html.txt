  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Why each task needs a seperate stack?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wendyzhu77">wendyzhu77</a> on November 7, 2010</div><div class="thread-post-content">Forgive me for this simple question, but I am new to tFreeRTOS.&nbsp; The FreeRTOS system seems to require that each task has its own stack, which is 85bytes minimum.&nbsp; So If I have multiple tasks, the memory usage is sort of large.<br />
I am wondering, why each task needs a seperate task?&nbsp; My understanding of FreeRTOS schedules tasks based on priority, and higher priority task always interrupts lower priority tasks.&nbsp; So when a task is executing, only a higher priority task would preempt it and the higher priority task would execute until it finishes &#40;or preempted or even higher ones&#41;.&nbsp; This scheme seems similar to the&nbsp; general interrupt scheme, so only one stack would suffice the need.&nbsp; Is it correct?<br />
The possibility for requiring multiple stack seems only to be when a higher priority task is blocked/suspended and willingly yield the processor to other processes &#40;i.e., the lower priority ones&#41;.&nbsp; So is it true that if the process don&#8217;t block or suspend one stack would suffice?<br />
Can anyone illustrate why multiple stacks is a must?&nbsp; Thank you very much&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Why each task needs a seperate stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on November 7, 2010</div><div class="thread-post-content">FreeRTOS is a fully preemptive system that uses the stack to store the context of each task individually. Interrupts run to completion so do not have an execution context across calls. I suggest reading the &#8216;how FreeRTOS works&#8217; section of the website.
</div></div><div class="thread-post"><h3 class="thread-post-title">Why each task needs a seperate stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 7, 2010</div><div class="thread-post-content">The higher priority task doesn&#8217;t run till it is &#8220;finished&#8221; but until it blocks &#40;waiting on a queue, semaphore or mutex, or executes a delay&#41;. At that point a lower priority task will start up. This switching back and forth is why each task needs its own stack.  
In general, tasks rarely &#8220;finish&#8221;, almost every task will be an infinite loop with a wait for resource somewhere in the loop.  
If you want to avoid the stacks, you could look at the co-routines, there are a few restrictions on what they can do, and in exchange for that, they all share the same stack.
</div></div><div class="thread-post"><h3 class="thread-post-title">Why each task needs a seperate stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wendyzhu77">wendyzhu77</a> on November 8, 2010</div><div class="thread-post-content">Thanks for your awesome replies.&nbsp; In my current system I have a fair number of periodical tasks that needs to be executed at different frequencies.&nbsp; If I assign tasks according to their execution frequencies, I would need to have one task for each frequency, e.g., 1 task for 10ms functions, 1 task for 30ms functions, etc, , then it seems I might ended up with a large number of tasks and the memory consumption seems larger than I like. If they are all in one task, then they will not be preempting and loses the purpose of RTOS.&nbsp; Is there any solution to this?&nbsp; I am thinking about Rate Monotonic scheduling so that only one stack is needed &#40;without using blocking calls, and this might make the design a little bit harder…&#41;.&nbsp;&nbsp; Any ideas?
</div></div><div class="thread-post"><h3 class="thread-post-title">Why each task needs a seperate stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 8, 2010</div><div class="thread-post-content">It sounds like co-routine might be a good fit for you. If all/most of your tasks just need for one signal to start &#40;like a timer&#41; and then just run till they produce a result, it should fit well. To allow the sharing of the stack, co-routines can&#8217;t remember anything on the stack when they block &#40;and the block can&#8217;t be is a subroutine of the task, it needs to be in the main task loop&#41;, but that shouldn&#8217;t be a problem for you the way you have described things. Co-routine CAN be interrupted by a higher priority co-routine, but they don&#8217;t round-robin at same priority level &#40;except at block/yeild points&#41;.
