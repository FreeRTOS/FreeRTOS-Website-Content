  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">heap_5 allocating outside of allowed range</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/avnimaor">avnimaor</a> on April 26, 2015</div><div class="thread-post-content">I&#8217;m using STM32F4 which has 192+64 KB of RAM. To use the 64KB I&#8217;m using heap_5.
Currently the heap is initialized for the 64KB plus the upper 64KB of the 192KB.
From the linker script file: 
~~~~~
define symbol <strong>region<em>HEAP</em>1_start</strong> = 0x10000000;
define symbol <strong>region<em>HEAP</em>1_end</strong>   = 0x1000FFFF;
define symbol <strong>region<em>HEAP</em>2_start</strong> = 0x20010000;
define symbol <strong>region<em>HEAP</em>2_end</strong>   = 0x2002FFFF;
~~~~~
Heap initialization code:
~~~~~
HeapRegion<em>t xHeapRegions[] =
{
    {   ( uint8</em>t * ) 0, 0},
    {   ( uint8_t * ) 0, 0},
    {   NULL, 0}//&lt;&lt; Terminates the array.
};
void fillHeapRegions()
{
    xHeapRegions[0].pucStartAddress = &#038;<strong>region<em>HEAP</em>1_start</strong>;
    xHeapRegions[0].xSizeInBytes = &amp;<strong>region<em>HEAP</em>1_end</strong>-&#038;<strong>region<em>HEAP</em>1_start</strong>;
    xHeapRegions[1].pucStartAddress = &#038;<strong>region<em>HEAP</em>2_start</strong>;
    xHeapRegions[1].xSizeInBytes = &amp;<strong>region<em>HEAP</em>2_end</strong>-&#038;<strong>region<em>HEAP</em>2_start</strong>;
}
~~~~~~
I&#8217;m calling fillHeapRegions before calling vPortDefineHeapRegions(xHeapRegions) in main.
My application works fine with this configuration.
The problem I&#8217;m witnessing is if I reduce the size of the memory region allocated to the heap:
~~~~~~
define symbol <strong>region<em>HEAP</em>1_start</strong> = 0x10000000;
define symbol <strong>region<em>HEAP</em>1_end</strong>   = 0x1000FFFF;
define symbol <strong>region<em>HEAP</em>2_start</strong> = 0x20012000;
define symbol <strong>region<em>HEAP</em>2_end</strong>   = 0x2002FFFF;
~~~~~~
I&#8217;m getting sporadic application crashes. When I investigated those crashes I saw a pointer to 0x20030000. Naturally this would cause a hard fault as this address is outside allowed address space.
Any idea?
Thanks,
Maor
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 26, 2015</div><div class="thread-post-content">Hi Maor,
<blockquote>
  I&#8217;m getting sporadic application crashes
</blockquote>
I would wonder if all memories given to the HEAP is not used by your program or by some stack?
You can also set the sizes more dynamically. If your linker file contains symbols like:
<pre><code>_ebss = . ;
_edata = . ;
</code></pre>
you can obtain the addresses of these variable in your C code:
<pre><code>extern void _edata;
extern void _ebss;
</code></pre>
and convert them to real addresses:
<pre><code>uint32_t end_data = ( uint32_t ) &amp;_edata;
uint32_t end_bss = ( uint32_t ) &amp;_ebss;
</code></pre>
A small remark about your code:
<pre><code>xSizeInBytes = &amp;__region_HEAP_1_end__ - &amp;__region_HEAP_1_start__;
</code></pre>
Shouldn&#8217;t it be: <code>size = end - start + 1</code> ?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/avnimaor">avnimaor</a> on April 26, 2015</div><div class="thread-post-content">First, the memory is divided to three segments, one for the statically allocated memories and the other two for the segmented heap.
As an architectural limit, I can&#8217;t move the static memories to the lower segment as hardware peripherals don&#8217;t work there.
I started the allocation by giving 64K to the static memories, and 64+64K to the heap. I got a linking error when I needed more statically allocated memory  and I resized the segments accordingly. At this point I started getting the crashes.
As for the size in bytes, it really doesn&#8217;t matter &#8211; I shouldn&#8217;t be getting allocation addresses outside of the allowed range.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on April 27, 2015</div><div class="thread-post-content"><blockquote>
  define symbol <strong>region<em>HEAP</em>1_start</strong> = 0x10000000;
  xHeapRegions[0].pucStartAddress = &#038;<strong>region<em>HEAP</em>1_start</strong>;
</blockquote>
What compiler is that? Can you check it is doing what you think by looking at the xHeapRegions structure in the debugger? It looks like it is taking the address of <strong>region<em>HEAP</em>1_start</strong> not its value. I would do this
<h1>define <strong>region<em>HEAP</em>1_start</strong> 0x10000000</h1>
xHeapRegions[0].pucStartAddress = (unsigned char*) <strong>region_HEAP_1_start</strong>;
The other thing to do would put some code in heap_5 so you can break when the memory returned is out of bounds:
if( returned address &lt; min address OR returned address > max address )
{
    asm volatile(&#8220;NOP&#8221;); // Line for break point
}
when the break point is hit look at the variables in heap_5 to see why it was out of bounds.
If you define configASSERT() it might trap an invalid vPortFree call, which might be the problem.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/avnimaor">avnimaor</a> on May 27, 2015</div><div class="thread-post-content">Still getting these issues.
The compiler is IAR 7.4. The heap regions are initialized correctly.
I even reduced the upper limit to account for heap bugs&#8230;
In the last crash I got I had a hard fault within memcpy. When I the registers I got r0 = 0x10010001. This is outside the range of the heap which the upper limit is 0x1000FF00.
This behavior is observed randomly after our PC connects to the board and configures the behavior of the application. During this phase tens of small messages are sent to the application, and many memory allocs and deallocs are called. 
Once the first phase is complete the application is stable, but the instability of the first phase is a critical issue for us.
BTW, I switched to heap<em>5 from heap</em>4, and never observed these faults before, which leads me to the conclusion that this is specific to heap_5.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 27, 2015</div><div class="thread-post-content">My reaction would be:
Make absolutely sure that your application never writes to unallocated memory. If you malloc N bytes, do not use N+1 bytes.
If you are not sure if memories get overwritten, as a test, malloc() more than you need and see if the extra bytes are still untouched before calling &#8216;vPortFree()&#8217;.
<code>r0 = 0x10010001</code> ? Beside being outside the memory, it is an unaligned address.
Sometimes I saw memcpy() crashing because it was replaced (optimised) by &#8216;inline&#8217; instructions performing 32-bit operations on a non-aligned address. I&#8217;m not sure if IAR would do the same.
In GCC this problem can be avoided by using the compiler flag &#8216;-fno-builtin-memcpy&#8217;. The memcpy() function is always safe to call, also for unaligned addresses.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 27, 2015</div><div class="thread-post-content">That is a good observation, although heap<em>4 and heap</em>5 are almost 
identical when it comes to allocation and free algorithms.  The main 
different between the two is their initial state &#8211; before anything has 
been allocated.
Do you ever call these functions from an interrupt?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">heap_5 allocating outside of allowed range</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/avnimaor">avnimaor</a> on May 27, 2015</div><div class="thread-post-content">r0=0x10010001 is probably a temporary address that was used by memcpy until it crashed. I think it&#8217;s safe to assume that the allocation routine did not return this address by itself.
I did saw malloc returning address 0x10010000 and 0x20020000 (which is the other segment top address) several times. That&#8217;s why I lowered the upper limits&#8230;.
As for use of the mallocs, I&#8217;m 99.999% sure that I don&#8217;t malloc in ISR. I&#8217;ll have to review the code, but I&#8217;m aware this is a huge no-no, and try to statically allocate/preallocate memories used in ISR.
Secondly my application is 95% C++. I overloaded all required prototypes of the &#8220;new&#8221; operator to use pvPortMalloc and vPortFree. I always access pointers to classes and I never deal directly with pointers to allocated buffer, therefore I find it hard to believe that I overwrite the end of the allocated buffers.
Again, I never observed these memory overwrites/hard faults/whatever when I used heap_4.
