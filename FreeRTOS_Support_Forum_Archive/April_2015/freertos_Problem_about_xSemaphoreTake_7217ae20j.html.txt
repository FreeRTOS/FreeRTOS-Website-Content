</div></div><div class="thread-post"><h3 class="thread-post-title">Problem about xSemaphoreTake()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 4, 2015</div><div class="thread-post-content">Hi Zhang Yi,
Good to hear.
Richard (from Real Time Engineers) already suggested to use portYIELD<em>FROM</em>ISR() or portEND<em>SWITCHING</em>ISR(), see here above.
Calling xSemaphoreGiveFromISR() does not cause a task switch. It does set the semaphore, but your task will keep on waiting eternally because of the time-out <code>portMAX_DELAY</code>:
<pre><code>if( xSemaphoreTake(xBinarySemaphore2, portMAX_DELAY) == pdTRUE)
{
}
</code></pre>
Note that the way to &#8216;initiate&#8217; a task-switch may differ a bit from port to port, in your case you use portEND<em>SWITCHING</em>ISR().
Why does this happen in two steps?
First you give to a semaphore and maybe you also write to a queue. The ISR might cause several tasks to get woken-up:
~~~~~
    void some<em>isr</em>routine()
    {
    portBASE_TYPE xTaskWoken = pdFALSE;
<pre><code>    /* These are three call that may put tasks in a runnable state.
    The variable xTaskWoken will have an OR'ed value,
    it becomes non-zero if at least one task will be come runnable. */
    xQueueSendFromISR( xQueue, &amp;vItem, &amp;xTaskWoken );
    xSemaphoreGiveFromISR( xSemaphore, &amp;xTaskWoken );
    vTaskNotifyGiveFromISR( pxTask, &amp;xTaskWoken );
    /* Now inform the OS to check if a task-switch is necessary.
    */
    portEND_SWITCHING_ISR( TaskWoken );
}
</code></pre>
~~~~~
In the above example, the ISR may wake-up several tasks. The task with the highest priority will start running first. This will happen immediately, after the &#8220;iret&#8221; instruction of the ISR.
I hope the picture is clear now?
Regard, Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem about xSemaphoreTake()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 8, 2015</div><div class="thread-post-content">To add to what Hein has already said, the portEND<em>SWITCHING</em>ISR()/portYIELD<em>FROM</em>ISR() mechanism allows better control over when a context switch is to be performed.  For example, if you receive an interrupt each time a character is received on a UART, and the interrupt handler is buffering characters, then you don&#8217;t necessarily want to perform a context switch on each character, but only when a complete message is received, so you would call portEND<em>SWITCHING</em>ISR()/portYIELD<em>FROM</em>ISR() only when the buffer contained a complete message.
&#8230;that said, if you omit the call to portEND<em>SWITCHING</em>ISR()/portYIELD<em>FROM</em>ISR(), then the task should run on the next tick interrupt anyway, so although in your case it would delay when the task executed, it would not prevent it from executing &#8211; so there is something else wrong.  Somewhere a task switch is not being performed when it should.
Can you set up a test where you have a break point that is hit in vTaskSwitchContext() <em>after</em> the interrupt that gives the semaphore has executed so you can step through the code to see why the task is not selected.
