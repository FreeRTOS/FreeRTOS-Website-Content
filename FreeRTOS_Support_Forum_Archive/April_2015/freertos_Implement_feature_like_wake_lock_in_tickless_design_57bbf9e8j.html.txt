  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Implement feature like wake lock in tickless design</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/redmilk525">redmilk525</a> on April 2, 2015</div><div class="thread-post-content">Hi, I&#8217;m using FreeRTOS 8.1.2 with tickless enabled via setting configUSE<em>TICKLESS</em>IDLE to 1. There is a condition that my task is waiting an expected event in nearly future. If I put my task into suspend, then freertos may enter sleep and make my task missing this event. Here is possible solutions I&#8217;ve tried:
(1) Redefine macro configPRE<em>SLEEP</em>PROCESSING and make it skip sleep if my task is waiting event. This is not a proper solution because this makes the tick count incorrect.
(2) Redefine macro configEXPECTED<em>IDLE</em>TIME<em>BEFORE</em>SLEEP as a function and return a huge number if my task is waiting event. But it&#8217;s build fail in size check in FreeRTOS.h
Thus I think this condition need a feature like wake lock that if some process acquire wake lock then the system won&#8217;t enter sleep. Is there a elegant way to achieve this feature without rewrite vPortSuppressTicksAndSleep or portTASK_FUNCTION()?
</div></div><div class="thread-post"><h3 class="thread-post-title">Implement feature like wake lock in tickless design</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 2, 2015</div><div class="thread-post-content"><blockquote>
  Here is possible solutions I&#8217;ve tried:
</blockquote>
I don&#8217;t think I understand the problem this is intended to be a solution to.
Which port are you using?
If you are using the Cortex-M port then an interrupt will unblock the task, so if the event you are waiting for comes from an interrupt (a reasonable assumption as the CPU is not running any code when it is in low power mode) then it will unblock in order to process the interrupt &#8211; and so not miss the event.
<blockquote>
  This is not a proper solution because this makes the tick count incorrect.
</blockquote>
If you are using the Cortex-M port, or you have created your own following the examples, then the tick count will be corrected for whatever the time is when the suppress ticks and sleep function exits.
<blockquote>
  Thus I think this condition need a feature like wake lock that if some process acquire 
  wake lock then the system won&#8217;t enter sleep. Is there a elegant way to achieve this 
  feature without rewrite vPortSuppressTicksAndSleep or portTASK_FUNCTION()?
</blockquote>
That is what the existing configPRE<em>SLEEP</em>PROCESSING macro allows you to do.
Regards.
