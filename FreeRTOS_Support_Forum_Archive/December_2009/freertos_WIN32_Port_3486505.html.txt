</div></div><div class="thread-post"><h3 class="thread-post-title">WIN32 Port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on December 12, 2009</div><div class="thread-post-content">I suspect you are printing out faster than the console can cope with, and that you are using printf&#40;&#41; without any sort of mutual exclusion &#40;two threads trying to access the console at the same time&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">WIN32 Port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 12, 2009</div><div class="thread-post-content">&gt; Still I don&#8217;t see why you would need to preempt every ms.  
You don&#8217;t, in most cases.&nbsp; Demos are provided with a 1ms pre-emption in part to test the port.&nbsp; The documentation pages for &#40;nearly?&#41; all state it is faster than necessary for most applications.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">WIN32 Port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 12, 2009</div><div class="thread-post-content">I will also add, that once you have determined the needed tick rate for an application based on resolution needed for things like timeouts, there generally isn&#8217;t a reason you can&#8217;t do task switching at this rate. You already have done the context save entering the tick interrupt, and need to do a lot of the scheduler work to see if someone higher has woken up, so switch to the next in line is fairly additional cost. Also the sort of processors FreeRTOS is aimed out don&#8217;t tend to have things like caches or swap files that cause additional penalties for switching between tasks, which is one reason OSes on bigger machines use longer execution quanta for low priority tasks.
