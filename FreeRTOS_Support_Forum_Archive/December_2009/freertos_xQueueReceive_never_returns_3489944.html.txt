  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xQueueReceive never returns</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gmulley">gmulley</a> on December 15, 2009</div><div class="thread-post-content">We have been trying for a while to track down a particularly nasty problem.&nbsp; At some point during execution one of our tasks fails to ever return from a call to xQueueReceive&#40;&#41; in spite of the fact that data has been added to the queue.  
Specifically, the task executes at priority 10, and spends most of it&#8217;s time just waiting to receive data from the queue.&nbsp; An interrupt occurs periodically and calls xQueueSendFromISR&#40;&#41; to push data into the queue.&nbsp; At this point the task should resume and process the data, but at some point it just never wakes up.  
It is important to note that we changed the critical section code to mask ALL interrupts during critical sections &#40;not just the OS tick&#41;.&nbsp; We are using the Pic24 port.&nbsp; We changed the following lines:  
In portasm&#95;PIC24.S line 56:<br />
&#96; MOV &#35;224, W0 /&#42; changed from 32 to 224 to&#42;/&#96;  
In portmacro.h line 90:<br />
&#96;&#35;define portINTERRUPT&#95;BITS &#40; &#40; unsigned portSHORT &#41; 7 &lt;&lt; &#40; unsigned portSHORT &#41; 5 &#41;&#96;  
Any suggestions/thoughts/help would be greatly appreciated&#33;

</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueReceive never returns</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mikeycosta">mikeycosta</a> on December 17, 2009</div><div class="thread-post-content">We found that disabling interrupt nesting fixes the problem.&nbsp; We tracked it down to some interrupt is corrupting the ready task list.&nbsp; But I don&#8217;t see why this would be the case.&nbsp; All our interrupt priorities are set to 1 which is the same priority as the kernel and system tick.&nbsp; I&#8217;m glad we at least know what is going on but it does not seem to make sense.  
Any ideas?
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueReceive never returns</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gmulley">gmulley</a> on December 17, 2009</div><div class="thread-post-content">We finally figured this out.&nbsp; It appears that even if two interrupts share the same priority they &#42;&#42;can&#42;&#42; interrupt each other.&nbsp; This can occur only if the interrupt flag has been cleared for the interrupt that is serviced first.&nbsp; This is what was happening with us:  
&#45; Timer 3 Interrupt cccurs and the CPU enters the timer 3 ISR<br />
&#45; Timer 3 interrupt flag cleared<br />
&#45; OS tick interrupt occurs in the middle of prvAddTaskToReadyQueue after uxTopReadyPriority had been set, but before vListInsertEnd was called.&nbsp; When the OS tick yields it decrements uxTopReadyPriority down to a low priority.<br />
&#45; When the Timer 3 interrupt is able to run again it adds the high priority task to pxReadyTasksLists<br />
&#45; Now uxTopReadyPriority and pxReadyTasksLists are out of sync.&nbsp; This meant that the high priority task was never woken up again.  
All problems were solved by making absolutely sure that all interrupt flags are cleared &#42;&#42;after&#42;&#42; the last OS call in an interrupt &#40;except for the yield&#41;.&nbsp; This ensures that interrupts that use OS functions are never nested.  
Alternately you can just disable nested interrupts if you don&#8217;t need them.
