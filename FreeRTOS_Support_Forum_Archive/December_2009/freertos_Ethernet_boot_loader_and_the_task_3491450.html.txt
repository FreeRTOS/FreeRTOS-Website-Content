  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Ethernet boot loader and the task?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yyang2000">yyang2000</a> on December 17, 2009</div><div class="thread-post-content">Hi, I wonder if someone can help me to figure out the issue as below described.  
My application is based on the sample of Cortex&#95;LM3SXXXX&#95;IAR&#95;Keil demo under FreeRTOS rev 5.4.2. It used to be booted by a serial boot loader and run just fine. Since I replaced it with an Ethernet boot loader, my application always stopped in midway during the booting. I use the on-board LED to trace the program and found the application ran and passed the hardware initialization code. After then it failed during a UART receive task creation. I use an EK-LM3S6965 Evaluation board to debug on it. It runs just fine with the debug mode. So I cannot find where or what is wrong. I have several quesitons.   
Why the serial boot loader can boot the application fine, but Ethernet boot loader not?&nbsp; &#40;Both have the same definition APP&#95;START&#95;ADDRESS = 0x1000&#41;  
Is it possible the application vector table has relocated and conflicted with Ethernet boot loader in SRAM?   
Does debug mode just runs from the application vector table at the starting address &#40;0x1000&#41;? Because debug mode does not go through the boot loader, it did not have the problem. So the problem is in Ethernet boot loader, Is it true?  
I was talking with Luminary tech support guys, they could not figure out what the cause is. I suspect the problem may relate to the FreeRTOS task priority or stack size settings. The UART receive task was set to the lowest priority that is tskIDLE&#95;PRIORITY.  
Any comments will be appreciated.  
Bill  
</div></div><div class="thread-post"><h3 class="thread-post-title">Ethernet boot loader and the task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 18, 2009</div><div class="thread-post-content">Sounds like quite a complicated problem to track down.&nbsp; I can only offer the simple suggestion to check that the UART interrupt is not firing before the scheduler is started.&nbsp; This could cause problems if the interrupt attempted to unblock a task.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Ethernet boot loader and the task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yyang2000">yyang2000</a> on December 18, 2009</div><div class="thread-post-content">Hi Richard, thanks for your replying. I am a little bit rusty. What is meant of &#8220;UART interrupt is not firing….&#8221;? does mean the UART interrupt service routine not get service?   
If my understanding is correct, the UART generates a interrupt and goes to its ISR. The ISR sends a message to the UART task through the queue. Since the task scheduler is not started yet. So it cannot access the UART task that causes problem.&nbsp; Am I right?  
In this situation, the solution may disable the UART interrupt during its initialization and enable UART interrupt just before the task scheduler starting. Any other suggestion will be welcome?  
Thanks,<br />
Bill
</div></div><div class="thread-post"><h3 class="thread-post-title">Ethernet boot loader and the task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yyang2000">yyang2000</a> on December 18, 2009</div><div class="thread-post-content">Hi Richard,   
I follow the lead you sugested that I found the problem that could be the UART interrupt is not serviced before the scheduler is started. So I disabled the UART interrupt during its initialization and enabled it during the task creation of the UART receive task routine that is prior to the forever loop starts. It works now.   
I don&#8217;t know there may be other better solutions than this.&nbsp; I wonder if you have any idea.  
Regards,<br />
Bill
