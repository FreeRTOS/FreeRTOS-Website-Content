I&#8217;m am wondering if it&#8217;s possible to create a task from a different binary file. Let say I have my &#8220;kernel&#8221; running and I&#8217;d like to start another task with a file on a sdcard or something compiled by someone else. Like on uClinux when you just execute an elf file and it gets its own process. I&#8217;d like to do this so a user don&#8217;t have to bundle the kernel to its application.   
The way I&#8217;m thinking of doing it right now is doing it without an OS and split my RAM and ROM so my kernel would be using the end of the end of the RAM and ROM and the user application the rest of the memory. To load all that I would bootstrap, load my kernel to the end of the memory and init it. Then load the user application and jump to it. Then the kernel would do it&#8217;s things using interrupts.   
Any body have a better alternative? I&#8217;m out of google buzz words to continue my research so please feed me a little.  
Thanks<br />
Francois
</div></div><div class="thread-post"><h3 class="thread-post-title">Create a new task from a différent binary</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 12, 2009</div><div class="thread-post-content">I don&#8217;t think you will have any problems with FreeRTOS itself in trying to do this. The one impact on the user program would be that you would have compiled FreeRTOS with a specific set of options &#40;in FreeRTOSconfig.h&#41; and the user has lost the ability to customize this.   
Where the difficulty lies is you are in essence needing to do a dynamic link. Your kernel section needs to find a way to know where to find the needed entries to the user program for the tasks it will provide and an entry to initialize the memory used by the user section. The user section will need to have a way to refer back to the routines &amp; data in the kernel that it needs to reference. Note that this includes not only the FreeRTOS functions themselves, but may include the parts of the run time library that FreeRTOS loaded.  
If the user is providing just a small piece of code, and your kernel is most of the application, it may be worth the pain to make this happen &#40;unless the tool set already supports this, in which case it may be easy&#41;. If the user is providing mostly full application, trying to make it &#8220;easier&#8221; on them by bundling freeRTOS on the board may be more work then they save from not just including it into their code.
</div></div><div class="thread-post"><h3 class="thread-post-title">Create a new task from a différent binary</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dsnejko">dsnejko</a> on December 12, 2009</div><div class="thread-post-content">It is possible. Not really like in uCLinux but similar to some extend.&nbsp; I have a kernel image permanent loaded&nbsp; in the flash memory and applications re&#92;-loadable. There is also a bootloader which&nbsp; can reload images to fixed addresses including the kernel and&nbsp; allows start them.&nbsp; The kernel image and apps compiled separate but shear include files. The key thing is how to link the app without os calls. The kernel image has a table which provides addresses for kernel&#8217;s calls. The table location is fixed and known to the application, also the table format and offsets for each function is predefined too and not changing. For the application each os call is replaced with a macro like<br />
move a0, table&#92;&#95;start+call&#92;&#95;offset<br />
jmp &#40;a0&#41;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;<br />
The app should be able to initialize memory belonged to os, allocate treads and start the scheduler. The kernel includes FreeRtos and dynamic memory.

</div></div><div class="thread-post"><h3 class="thread-post-title">Create a new task from a différent binary</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dsnejko">dsnejko</a> on December 13, 2009</div><div class="thread-post-content">I am using CodeWarrior and ColdFire port. All linking is done with assembler so my macro would not work for your toolchain. I have a common file included on both sides. It describes table offsets and&nbsp; macros for table insertion and calling. Something like this, name it lib&#95;links.inc:&nbsp;&nbsp;<br />
&lt;pre&gt;&lt;code&gt;<br />
&nbsp;&nbsp;&nbsp; .public &#95;xTaskCreate<br />
&nbsp;&nbsp;&nbsp; .public &#95;vTaskDelay  
&nbsp;&nbsp; INSERT&#95;LINK: .macro&nbsp; ref<br />
.org&nbsp;&nbsp; OFFSET&amp;&amp;ref<br />
.long&nbsp; ref<br />
&nbsp;&nbsp; .endm&nbsp;   
&nbsp;&nbsp;&nbsp; JUMP&#95;LINK:&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; .macro ref<br />
&amp;&amp;ref:&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; move.l&nbsp; &#95;LIB&#95;LINK&#95;TABLE&nbsp; &#43; OFFSET&amp;&amp;ref, a0<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; jmp&nbsp; &#40;a0&#41;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; .endm<br />
&lt;/code&gt;&lt;/pre&gt;  
The kernel build includes an assembler file similar to:<br />
&lt;pre&gt;&lt;code&gt;  
.global &#95;LIB&#95;LINK&#95;TABLE<br />
&nbsp;&nbsp;&nbsp; .include lib&#95;links.inc   
.text<br />
&#95;LIB&#95;LINK&#95;TABLE:<br />
&#95;LIB&#95;LINK&#95;TABLE&#95;START:<br />
&#95;FREERTOS&#95;LINK&#95;TABLE:<br />
&nbsp;&nbsp; INSERT&#95;LINK &#95;xTaskCreate<br />
&nbsp;&nbsp; INSERT&#95;LINK &#95;vTaskDelay<br />
&lt;/code&gt;&lt;/pre&gt;<br />
The application build includes an assembler file similar to:<br />
&lt;pre&gt;&lt;code&gt;<br />
&nbsp;&nbsp; .extern &#95;LIB&#95;LINK&#95;TABLE<br />
&nbsp;&nbsp; .include lib&#95;links.inc  
&nbsp;&nbsp; .text<br />
&#95;LIB&#95;LINK&#95;TABLE&#95;APP:<br />
&nbsp;&nbsp;&nbsp; JUMP&#95;LINK &#95;xTaskCreate<br />
&nbsp;&nbsp;&nbsp; JUMP&#95;LINK &#95;vTaskDelay<br />
&lt;/code&gt;&lt;/pre&gt;  
&#92;&#95;LIB&#92;&#95;LINK&#92;&#95;TABLE is a segment created in the linker command file at fixed location and known for the kernel and the app.
