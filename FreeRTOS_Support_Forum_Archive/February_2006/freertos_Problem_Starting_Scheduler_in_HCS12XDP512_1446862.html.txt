  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem Starting Scheduler in HCS12XDP512</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 22, 2006</div><div class="thread-post-content">I am trying implement the FLASH task using the RTOS Demo for the HCS12 &#40;banked&#41; as a starting point &#40;I removed all the other tasks, since I&#8217;m going for simplicity first time around&#41;.&nbsp; I had to make some changes since ProcessorExpert is not yet supported with the HCS12X.&nbsp; The changes I basically made were to setup the Periodic Interrupt Timer 0 as the RTOS Tick interrupt, hardcoding it for 1000 Hz &#40;just like the demo&#41;.&nbsp; I changed the prvSetupTimerInterrupt&#40;&#41; in port.c to simply start the PIT0 timer.&nbsp; The interrupt vector table is also updated so that the Tick ISR is serviced with the PIT0.
My problem is that in xBankedStartScheduler&#40;&#41;, the application quits with an unknown event &#40;quitting at the XIRQ interrupt for some reason&#41;.&nbsp; If I comment out the portRESTORE&#95;CONTEXT&#40;&#41;; and &#95;&#95;asm&#40; &quot;rti&quot; &#41;; lines, it runs through &#40;but obviously just sits in the loop in vMain&#40;&#41;&#41;.&nbsp; I think its somewhere not correctly restoring the context so that the rti instruction goes to the correct Task, but I&#8217;ve been hung up for a while trying to track down what&#8217;s going on.
Does anyone have any suggestions on what may be causing the problem?&nbsp; I&#8217;m thinking theres still something I need to change so that RTOS is correctly ported to the HCS12X and its memory map in regards to storing a task&#8217;s context.
Anyway, any suggestion/help is greatly appreciated&#33;
Thanks,
&#45; Mike
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem Starting Scheduler in HCS12XDP512</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 22, 2006</div><div class="thread-post-content">Not familiar with the HCS12X but some things come to mind reading your post.
1&#41; The processor expert can be a pain wrt interrupts.&nbsp; The FreeRTOS demo requires that the interrupt table be populated manually after the expert has run.&nbsp; Also there was something I recall about having a file read only so the expert does not overwrite it.&nbsp; You might one to check that out.
2&#41; Have you checked your timer without FreeRTOS?&nbsp; Simply setting up a timer and toggling a bit every 1000 ticks or something.&nbsp; Once you can guarantee that the interrupts are correct you can add the FreeRTOS code in.
3&#41; You could try not turning on the interrupt &#40;so it does not get in the way&#41; and stepping through the starting of the first task to see exactly what it does.&nbsp; Obviously it will not run without the interrupt but it is easier to debug.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem Starting Scheduler in HCS12XDP512</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on February 23, 2006</div><div class="thread-post-content">The Tick interrupt works just fine and is very accurate to 1000 Hz.
I&#8217;ve stepped through the code a bit, and found something interesting.&nbsp; When the function xTaskCreate is called, the first parameter if the address of the function that has the task code &#40;for me, that is located at memory location FE86CA&#41;.&nbsp; However, when debugging, it passes the address 86CAFE &#40;the page is appended to the end for some reason?&#41;.&nbsp; It does this with the address-of operator as well.&nbsp; I&#8217;m thinking that something is not storing correctly in the stack, and so when RTI is called from the StartScheduler, it goes to a memory location for the XIRQ ISR &#40;my vector table is setup so that each interrupt channel has its own ISR, then all the ISRs that are not used are simply blank&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem Starting Scheduler in HCS12XDP512</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nighteye">nighteye</a> on February 24, 2006</div><div class="thread-post-content">I fixed the issue.&nbsp; It has to do with the HCS12X having a larger CCR register &#40;2 bytes instead of one&#41;.&nbsp; The first 5 bits are unused for future use, then comes IPL&#91;2:0&#93;, and than the other 8 bytes.&nbsp; The two high bytes of the actual CCR register &#40;S and X&#41; need to be set to 1, or else the application ceases &#40;clearing 0 or X causes an interrupt; which is why I was getting the XIRQ interrupt due to the X flag being cleared&#41;.
So here&#8217;s what needs to be added to port.c in the function &#42;pxPortInitialiseStack
Where the CCR is save to the stack, simply add stack the extra byte 0xC0 &#40;C to set the S and X flags&#41;.
/&#42; CCR: Note that when the task starts interrupts will be enabled since I&quot; bit of CCR is cleared &#42;/
&#42;pxTopOfStack = &#40; portSTACK&#95;TYPE &#41; 0xC0;
pxTopOfStack&#8211;;
&#42;pxTopOfStack = &#40; portSTACK&#95;TYPE &#41; 0x00;
pxTopOfStack&#8211;;
So far I&#8217;ve gotten the Flash task to work correctly.&nbsp; If there are any other locations in the code where the CCR register is stacked, or unstacked, then that will need to be edited too &#40;I have just now started to actually write my application since finding this issue&#41;.
I hope this helps future users who are trying to implement FreeRTOS on an HCS12X &#40;XGate&#41;.
Cheers,
Michael

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem Starting Scheduler in HCS12XDP512</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on February 24, 2006</div><div class="thread-post-content">I had to trace the stack very carefully too, for my HCS12 port. With a new compiler and new MCU, you have to carefully count the bytes on the stack to see what address it will return to with the rti.
One more thing, I don&#8217;t know if anyone mentioned the reason the memory bank &#40;0xfe&#41; is in the LSB instead of first in the &quot;far&quot; address. It&#8217;s a new standard address type with 9S12X, I believe.
