  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leesp">leesp</a> on August 11, 2019</div><div class="thread-post-content">I am a user of Renesas RX MCU, which has a Interrupt Stack pointer, and User Stack Pointer. In a non-OS program, programmers have a choice of enabling User Stack. If:
&#8211; User Stack is not enabled: then both function call and interrupt use Interrupt Stack
&#8211; User Stack is enable: then normal function call uses User Stack, and interrrupt service rountine (and all subsequent function call before interrupt returns) uses Interrupt Stack
But how about the case of FreeRTOS for RX? I know that each task has a task stack. Does each task has a interrupt stack, or all tasks share a common interrupt stack, or there is no concept of user stack / interrupt stack?
I mean, while a task is executing, its stack is used when functions are called. But what happen if an interrupt happens? RX MCU hardware would push PC and PSW onto Interrupt Stack. Is this Interrupt Stack common to all tasks?
Or a more fundamental question: does FreeRTOS for RX use User Stack at all?
</div></div><div class="thread-post"><h3 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 11, 2019</div><div class="thread-post-content">My guess is that all the tasks would use a common ISR stack for interupts, there is no reason I can think of to have multiple ISR stacks that change for each task.
While it could have all the tasks use the ISR stack also, and ports for machines that don&#8217;t have a seperate ISR stack have to do the equivalent of that, On such a machine, when you change what task is running, you reload the stack pointer to point to the new tasks saved stack.
I would suspect that FreeRTOS would use the User Stack for tasks, and just change that user stack on task switches, as that means that each tasks doesn&#8217;t need to reserve space for the interupt stack in its stack frame.
I am not familiar with that port, so I am answering on general principles. The final answer would be in the port files for that processor.

</div></div><div class="thread-post"><h3 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 13, 2019</div><div class="thread-post-content">The software interrupt should be the lowest priority so it executes after all nested interrupts have completed. That way multiple nested interrupts can request a context switch but only one actually occurs.
</div></div><div class="thread-post"><h3 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 13, 2019</div><div class="thread-post-content">The ISR will do the yield to implement the task switch. Exactly how the task switch happens depends on the processor, but many use a software interrupt, which will be triggered in the interrupt context. On some processors, that software interrupt won&#8217;t actually happen until the ISR ends
</div></div><div class="thread-post"><h3 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leesp">leesp</a> on August 23, 2019</div><div class="thread-post-content">Dear Richard Barry/Richard Damon,
Ok I have studied vPortYield() and prvYieldHandler(). Please confirm my understanding is correct:
<ol>
<li>When timer tick interrupt happens, vTickISR() starts to run. Within vTickISR(),** software interrupt (SWINT) is requested, but it is pending** because it is of lower priority than timer tick interrupt</li>
<li>Once vTickISR()** returns from  interrupt**, software interrupt would execute immediately if there is no other higher priority interrupt. PC and PSW are pushed by hardware to Interrupt Stack</li>
<li>vSoftwareInterruptISR() starts running, which calls prvYieldHandler(). The handler would copy PC, PSW from Interrupt Stack to Task Stack (the task which is being pre-empted now), and also it would push r1-r15 to Task Stack</li>
<li>vSoftwareInterruptISR() would then restore context of the other higher priority task</li>
</ol>

</div></div><div class="thread-post"><h3 class="thread-post-title">Task stack &#8211; user stack, or interrupt stack (Renesas RX MCU)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 4, 2019</div><div class="thread-post-content">The ISR would call xSemaphoreGiveFromISR(), which puts the semaphore in the &#8216;given&#8217; state (i.e. someone can now succeed in a xSemaphoreTake() operation. If the process of giving the semaphore wakes up a task at higner priority then currently running, it well set the word provided by the &#8216;wasWoken&#8217; parameter. The ISR at its end tests this, and if it has been set, initiates the scheduler (often via a Software Interrupt, details of how this port does it should be documented in the port files for that processor).
You don&#8217;t give a semaphore to a particular task, but but various things give and take the semaphore, and the semaphore keeps track of its state (given/taken for a binary, or a given count for a counting semaphore) and the semaphore will block tasks that ask for something that it can&#8217;t do at the time (or return a error if the timeout is 0, like it will do to an ISR, since ISRs can&#8217;t block)
