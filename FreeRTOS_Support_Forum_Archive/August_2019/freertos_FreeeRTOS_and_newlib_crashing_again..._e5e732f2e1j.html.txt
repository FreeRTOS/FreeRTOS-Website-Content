</div></div><div class="thread-post"><h3 class="thread-post-title">FreeeRTOS and newlib crashing, again&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/aggarg-aws">aggarg-aws</a> on August 14, 2019</div><div class="thread-post-content">I looked into the _sbrk implementation generated by the STM32Cube IDE and as you correctly pointed out, it has a bug where it tries to ensure that heap does not grow into the stack. The intention of the code there is to ensure that the heap does not grow into MSP and therefore the code should read MSP (instead of SP). The implementation should look like:
~~~
caddr<em>t _sbrk(int incr)
{
    extern char end asm(&#8220;end&#8221;);
    static char *heap</em>end;
    char *prev_heap_end;
    char * stack_ptr;
<pre><code>if (heap_end == 0)
    heap_end = &amp;end;
prev_heap_end = heap_end;
__asm volatile ( "MRS %0, msp" : "=r" (stack_ptr) );
if (heap_end + incr &gt; stack_ptr)
{
    errno = ENOMEM;
    return (caddr_t) -1;
}
heap_end += incr;
return (caddr_t) prev_heap_end;
</code></pre>
}
~~~
As you correctly mentioned in your article, two more changes are needed:
1. The default implementation of __malloc<em>lock and __malloc</em>unlock from libc<em>nano.a(lib</em>a-mlock.o) are no-op as can be verified using &#8211;wrap. The user therefore need to provide __malloc<em>lock and __malloc</em>unlock. 
2.  The user also need to define configUSE<em>NEWLIB</em>REENTRANT to 1 in their FreeRTOSConfig.h.
After making these changes, if you use heap_3.c, pvPortMalloc will call malloc and will return heap space from the above.
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeeRTOS and newlib crashing, again&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 14, 2019</div><div class="thread-post-content">One thing to be careful here. Often malloc will be called early, before FreeRTOS has started, and at that time the sp is the right register to use (and I am not sure if msp has been setup at all).
In my experiance, configUSE<em>NEWLIB</em>REENTRANT is not needed just to use malloc and free from newlib. malloc and free do not need thread local storage, and while the lock and unlock functions are passed pointers to the current reent structure, there is nothing that they really need from it. I suppose you could use this to make a version of malloc that kept track of which task created which memory blocks to allow you to figure out where a memory like came from.
configUSE<em>NEWLIB</em>REENTRANT is only needed to be a 1 if you are using certain &#8216;higher level&#8217; functions out of the library that you want to have distinct storage for some internals. Likely the most common one would be the file system.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeeRTOS and newlib crashing, again&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/aggarg-aws">aggarg-aws</a> on August 14, 2019</div><div class="thread-post-content">I do not think we have anything specific for that as MSP stack is specified in your linker script. You can export a variable from your linker script and compare the heap space in _sbrk against that instead of comparing against MSP. 
Linker Script:
~~~
/* Boundary of stack */
_sstack = _estack &#8211; _Min_Stack_Size;
~~~
Sbrk:
~~~
caddr<em>t _sbrk(int incr)
{
    extern char end asm(&#8220;end&#8221;);
    extern char sstack asm(&#8220;</em>sstack&#8221;);
    static char *heap_end;
    char *prev_heap_end;
    char * stack_boundary = &sstack;
<pre><code>if (heap_end == 0)
    heap_end = &amp;end;
prev_heap_end = heap_end;
if (heap_end + incr &gt; stack_boundary)
{
    errno = ENOMEM;
    return (caddr_t) -1;
}
heap_end += incr;
return (caddr_t) prev_heap_end;
</code></pre>
}
~~~
The amount of stack space used can be figured from the difference of MSP and stack boundary. 
I was trying to point out that the implementation ST provides will work with the fix of reading MSP (this of course does not preserve space for MSP stack).
