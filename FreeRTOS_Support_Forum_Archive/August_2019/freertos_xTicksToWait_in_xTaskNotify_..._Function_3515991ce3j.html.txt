Why is there no** &#8220;xTicksToWait&#8221;** for <strong>xTaskNotify(&#8230;) **Function while there is one for **xQueueSend(&#8230;)</strong>
Why is Symmetry missed ?
<hr />
P.S. : Also note the Assymetry in Naming Convention: 
         {xQueueSend, xQueueRecieve} 
         ** vs** {xTaskNotify, xTaskNotifyWait}  **   instead of** {xTaskNotifySend, xTaskNotifyRecieve}
</div></div><div class="thread-post"><h3 class="thread-post-title">xTicksToWait    in    xTaskNotify(&#8230;)    Function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on August 10, 2019</div><div class="thread-post-content">I am sure that a better or more detailed answer will follow, but here is mine:
<code>xTaskNotify()</code> may need to wait for space in a queue.
When notifying a task, there is no queue, the task will be notified immediately.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTicksToWait    in    xTaskNotify(&#8230;)    Function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on August 10, 2019</div><div class="thread-post-content">sorry, typo: <code>xQueueSend</code> needs a time-out parameter because it may have to wait for space in the queue. <code>xTaskNotify()</code> can do it&#8217;s job immediately.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTicksToWait    in    xTaskNotify(&#8230;)    Function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 10, 2019</div><div class="thread-post-content">As Hein says, there is nothing for xTaskNotify to need to wait for. xTaskNotify is more like xSemaphoreGive than xQueueSend, in that a notification doesn&#8217;t need to wait for &#8216;space&#8217; for the notification. The eAction parameter describes what is done with the value word, and note that none of the options require waiting, there is an option that will report a failure if the current notification value is non-zero.
Note that since there is no option to wait for the task to take the old value first, the direct to task notifications isn&#8217;t a full replacement for a queue, but then even if you try to use it as one, it can&#8217;t really handle reliably sending the value 0.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTicksToWait    in    xTaskNotify(&#8230;)    Function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/panu28">panu28</a> on August 10, 2019</div><div class="thread-post-content">Hi, Thanks for reply &#8230;
<blockquote>
  When notifying a task, there is no queue, the task will be notified immediately. xTaskNotify() can do it&#8217;s job immediately.
</blockquote>
But Consider the scenario Recieveing TASK-<x> has still a notification pending which it hasnt processed&#8230;.. and another TASK-<y> wants to send notification to TASK-<x> 
e.g:  (Below Lines of Code could have been Avoided? if functionality was inbuilt)
~~~
RETRY<em>NOTIFICATION:
    if (xTaskNotify(hThread</em>leds, stv, eSetValueWithoutOverwrite) == pdTRUE)return true;
    if (timeout<em>ms) { vTaskDelay(pdMS</em>TO<em>TICKS(1)); timeout</em>ms&#8211;; goto RETRY_NOTIFICATION; }
~~~
P.S. : I Think xTaskNotify() has &#8220;queue&#8221; of  size &#8211; 1
</div></div><div class="thread-post"><h3 class="thread-post-title">xTicksToWait    in    xTaskNotify(&#8230;)    Function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 10, 2019</div><div class="thread-post-content">As I mentioned, Notify isn&#8217;t built on the model of a Queue, but more on the model of a semaphore. It seems not designed to be used as a Queue.
I suspect the reasoning is that if you really want a Queue like system, then likely you may want a Queue length greater than 1, but by the nature of how notifications are built, they are inherently limited to just a single mailbox word for the notification. If you want q Queue, use a Queue (or a Stream/Message Buffer)
The other factor is that the big advantage of the Direct to Task system is that it is much more efficient than using a Semaphore (or a Queue), because there is no need to have lists of tasks waiting for the notification. To allow tasks to queue up and wait for a notification to be taken removes this advantage. As currently defined, the task being notified doesn&#8217;t need to do anything much to receive the notification, maybe just clear the notification word. If there was a posibility of a task waiting on that, then after every notify take FreeRTOS would need to check about waking up somebody, at which point the Direct to Task Notification has no real advantage over using a Semaphore or a Queue. The restrictions on usage are what gives it the advantages that make it useful.
