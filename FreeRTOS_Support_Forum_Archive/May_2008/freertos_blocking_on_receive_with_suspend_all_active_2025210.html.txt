  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">blocking on receive with suspend all active</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on May 1, 2008</div><div class="thread-post-content">Unintentionally my system blocked on a receive after calling vTaskSuspendAll&#40;&#41;. It is unclear to me what the intended FreeRTOS behaviour is, but the behaviour I observed seems to be a FreeRTOS bug.
In xQueueGenericReceive&#40;&#41;, the following code is executed after the calling task is enqueued on the xTasksWaitingToReceive list.
if&#40; &#33;xTaskResumeAll&#40;&#41; &#41;
&#123;
&#95;&#95;&#95;&#95;taskYIELD&#40;&#41;;
&#125;
However, taskYield&#40;&#41; does not re-schedule because scheduling is suspended. The calling task continues, ultimately hitting the end of the do-while with xReturn==queueERRONEOUS&#95;UNBLOCK. Another iteration is performed, once again performing
vTaskPlaceOnEventList&#40; &amp;&#40; pxQueue-&gt;xTasksWaitingToReceive &#41;, xTicksToWait &#41;;
But this call corrupts the list, presumably because the item is already on the list. In my case of only the one item on the list, it is corrupted such that xListEnd locates the list item, but the list item locates itself rather than xListEnd. The next search of the list becomes an infinite loop on 
for&#40; pxIterator = &#40; xListItem &#42; &#41; &amp;&#40; pxList-&gt;xListEnd &#41;
&#95;&#95;&#95;&#95;; pxIterator-&gt;pxNext-&gt;xItemValue &lt;= xValueOfInsertion
&#95;&#95;&#95;&#95;; pxIterator = pxIterator-&gt;pxNext &#41;
in vListInsert&#40;&#41; on the next do-while iteration.
Glen
</div></div><div class="thread-post"><h3 class="thread-post-title">blocking on receive with suspend all active</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 1, 2008</div><div class="thread-post-content">What you are pointing out is a flaw in the documentation, rather than the code.&nbsp; It is not intended or that logical that these functions get called while the scheduler is suspended, but &#40;having just checked&#41; the documentation does not state this.&nbsp; I will update this right after posting this.
The SafeRTOS code has explicit checks for this condition, and returns an errSCHEDULER&#95;WAS&#95;SUSPENDED error code should it occur.
Thanks for taking the time to write your post, as a direct result the docs will be improved.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">blocking on receive with suspend all active</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 1, 2008</div><div class="thread-post-content">I was going to update the docs for all the API functions to which it is relevant, but having just had a quick scan of where the errSCHEDULER&#95;WAS&#95;SUSPENDED error is used it seems, due to their number, more appropriate to have updated the documentation for the vTaskSuspendAll&#40;&#41; function instead.
I have now added &quot; API functions that have the potential to cause a context switch &#40;for example, vTaskDelayUntil&#40;&#41;, xQueueSend&#40;&#41;, etc.&#41; must not be called while the scheduler is suspended.&quot; to both the checked in header file and the .html page on the WEB site.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">blocking on receive with suspend all active</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on May 1, 2008</div><div class="thread-post-content">Ah, I see.
Yesterday when I discussed this with a colleague, he suggested that the suspend count should be task specific &#40;much like the critical section nesting count&#41;. Then when this situation happened the suspend should be suspended &#40;so to speak&#41; &#8211; i.e. scheduling resumed&#8230; until the task unblocks.
Something to think of for the future, although I can see both pros and cons to this approach.
