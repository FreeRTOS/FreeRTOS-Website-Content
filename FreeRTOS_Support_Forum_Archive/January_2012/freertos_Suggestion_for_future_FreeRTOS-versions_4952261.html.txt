</div></div><div class="thread-post"><h3 class="thread-post-title">Suggestion for future FreeRTOS-versions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on January 17, 2012</div><div class="thread-post-content">Regarding Hungarian Notation &#8211; the original idea was for what is now termed &#8220;Application Hungarian Notation&#8221;, in which prefixes were used to distinguish the usage of variables.&nbsp; A typical example of this is to use &#8220;ssName&#8221; and &#8220;usName&#8221; to distinguish between the &#8220;safe string&#8221; version of &#8220;Name&#8221; and the &#8220;unsafe string&#8221; version of &#8220;Name&#8221; &#45; perhaps to ensure that input data has a suitable length, no awkward characters, no sql injection attacks, etc.&nbsp; The point is that these are the same types &#40;char&#42;, char, string class, whatever&#41; so the compiler can&#8217;t help you spot mistakes &#8211; the naming convention helps you avoid passing unsafe strings to functions that assume their argument is safe.&nbsp; In the context of FreeRTOS, it might be used to distinguish between different uses of &#8220;void &#42;&#8221; pointers &#8211; instead of calling them &#8220;pvXXX&#8221;, you call some &#8220;pparamsXXX&#8221;, and some &#8220;pownerXXX&#8221;, etc.  
What you use in FreeRTOS is know as &#8220;Systems Hungarian Notation&#8221;, where the letters represent types of data or return types of functions.&nbsp; A little of this can be very useful &#8211; it is very common to have &#8220;pXXX&#8221; for pointers and perhaps &#8220;fXXX&#8221; for function pointers.&nbsp; Another useful convention is an &#8220;s&#8221; suffix on arrays or similar structures.&nbsp; But the idea of embedding type information as prefix letters based on a complete misunderstanding of Simonyi&#8217;s original paper, and is mostly considered poor style.&nbsp; Any program or library that makes decent use of types is going to have too many to be able to express well in this manner &#8211; the code quickly becomes unreadable or at least unwriteable, and unmaintainable if things change.&nbsp; It doesn&#8217;t add any information that the compiler doesn&#8217;t already know and check, and any decent programmer&#8217;s editor makes it quick and easy for the programmer to find out types.&nbsp; So you are duplicating existing information in a non-standard and inconsistent way, which is never a good idea.  
Having said that, it is worth remembering that opinions on these things change over time, both through fashion and better tools and styles &#8211; when FreeRTOS was started, expert opinion on Systems Hungarian Notation was much higher than it is now.&nbsp; So while I say that it would be wrong to use it for a new system, I don&#8217;t mean to criticize the original decision when FreeRTOS was started.  
Regarding &#8220;signed char&#8221; &#45; a &#8220;char&#8221; is a character or letter, and it doesn&#8217;t make sense for a letter to be signed or unsigned.&nbsp; It doesn&#8217;t make sense to use a letter variable to hold numeric data.&nbsp; If you want a small integer, use types &#8220;uint8&#95;t&#8221; or &#8220;int8&#95;t&#8221;, because they have names that match the use you intended.&nbsp; Because of limitations of C, the underlying type of &#8220;int8&#95;t&#8221; will normally &#40;but not necessarily&#41; be &#8220;signed char&#8221; &#45; but you should insulate your code from that sort of thing.&nbsp; Also, you should not have something like &#8220;unsigned portBASE&#95;TYPE&#8221; &#45; &#8220;portBASE&#95;TYPE&#8221; should be declared as signed or unsigned as necessary in the type definition.&nbsp; And you should not use something like &#8220;unsigned long&#8221; in portable code &#8211; if you don&#8217;t want to specifically fix the size with uint32&#95;t, use &#8220;uint&#95;fast16&#95;t&#8221; or similar.  
So a better rule is &#8220;thou <em>shalt</em> use unqualified char types &#8211; because if the signedness matters, you should use a stdint.h type&#8221;.  
Regarding C++ &#8211; it&#8217;s a choice to consider.&nbsp; For something like an RTOS here, there is a great deal to be gained by using C++ and writing in an object-oriented style.&nbsp; Quite clearly there is a loss of portability to some platforms, especially the smallest and most limited.&nbsp; It is also not uncommon for toolchain vendors to charge differently for C++ tools rather than C tools.&nbsp; So it would be a question of balancing the benefits of C++ with the costs for your target users.  
Incidentally, templates are a very misunderstood part of C++.&nbsp; Badly used templates can lead to bloated code, especially with older C++ compilers.&nbsp; Well used templates can lead to smaller and faster code than you get with generic C functions, as well as being safer to use.

</div></div><div class="thread-post"><h3 class="thread-post-title">Suggestion for future FreeRTOS-versions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 18, 2012</div><div class="thread-post-content">FreeRTOS as currently written works very well with C++, just needing a thing wrapper. The one big issue is that FreeRTOS queues can only store classes with trivial copy constructors &#40;since it uses memcpy&#41;. With a bit of refactoring, I think it would be possible to have FreeRTOS provide some primitives to allow you to define a template based queue allowing them to hold any copyable/movable type.   
As for &lt;stdint.h&gt;, the one issue I have with it is that int8&#95;t is the wrong type. As defined, portable code should NOT use it, as it is not gaurenteed to exist &#40;but it is the family of types most apt to be used&#41;, as it requires and EXACT sized type. By definition int&#95;least8&#95;t will be signed char &#40;or a type with equivalent properties&#41;.

As defined, portable code should NOT use it, as it is not gaurenteed to exist &#40;but it is the family of types most apt to be used&#41;, as it requires and EXACT sized type. Types such as int&#95;least8&#95;t and int&#95;fast8&#95;t are often underused.&nbsp; If portability is vital, even on painful cpu&#8217;s which cannot address 8-bit data, then I agree that these are a better choice.&nbsp; int&#95;fast8&#95;t is typically best for local data &#8211; it is the type that has at least 8 bits, and is fastest for the cpu in question &#40;and is thus often 32-bit on 32-bit cpus&#41;, while int&#95;least8&#95;t is typically best for stored data &#40;being the smallest type with at least 8 bits&#41;.&nbsp; Often int8&#95;t &#40;being an exact size type&#41; is not actually the best choice, though it is commonly used &#40;being shorter, clearer and more specific than the others&#41;.  
Whichever you choose, all of them are better than &#8220;char&#8221; &#45; signed, unsigned or unqualified &#8211; when you want an arithmetic type.
