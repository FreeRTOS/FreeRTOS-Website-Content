  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">tickless idle mode: strange behaviour</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/keepcoding">keepcoding</a> on August 13, 2013</div><div class="thread-post-content">Hi  
The tickless idle mode is a great new feature, BUT I am having serious problems with this option. As soon as I enable the tickless idle mode by setting configUSE&#95;TICKLESS&#95;IDLE to 1 in the config file and flash the program onto the microcontroller, I cannot access it via USB any more. This means, I need to do a reset &#40;&#8217;connect on reset&#8217;&#41; and erase the whole chip to be able to reprogram the flash memory via USB. What the heck does this tickless idle mode do to my program?  
I am using a STM32F3 Discovery board and the latest FreeRTOS kernel.<br />
any hints are welcome
</div></div><div class="thread-post"><h3 class="thread-post-title">tickless idle mode: strange behaviour</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/keepcoding">keepcoding</a> on August 13, 2013</div><div class="thread-post-content">BTW: with &#8216;I cannot access it via USB any more&#8217; I mean I&#8217;m getting the following error:<br />
&#8220;Debugger &#8211; Cortex-M Error: Internal Command Error&#8221;
</div></div><div class="thread-post"><h3 class="thread-post-title">tickless idle mode: strange behaviour</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 13, 2013</div><div class="thread-post-content">Assuming you are using the default implementation, and not an STM32 customised version, then it will do nothing more than call WFI &#40;the ARM &#8220;wait for interrupt&#8221; instruction&#41;.&nbsp; I can&#8217;t think of any reason why that would prevent you accessing the chip as an interrupt will bring the system out of low power mode.  
<blockquote>
  BTW: with &#8216;I cannot access it via USB any more&#8217; I mean I&#8217;m getting the following error:<br />
  &#8220;Debugger &#8211; Cortex-M Error: Internal Command Error&#8221;
</blockquote>
From this it looks like you mention of USB is to a debug pod &#40;ST-link, J-link, or such thing&#41; rather than to the chip directly.&nbsp; Is that the case?&nbsp; Which debug pod are you using?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">tickless idle mode: strange behaviour</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/keepcoding">keepcoding</a> on August 13, 2013</div><div class="thread-post-content">Thanks for your reply. Yes, I&#8217;m using the ST-Link. Do you have an idea what might cause this problem?
</div></div><div class="thread-post"><h3 class="thread-post-title">tickless idle mode: strange behaviour</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 13, 2013</div><div class="thread-post-content">It is not something I have experienced, but I have not tried tickless mode with an ST-Link.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">tickless idle mode: strange behaviour</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imlizking">imlizking</a> on December 29, 2013</div><div class="thread-post-content">Just googling for Tickless issues and I think I have the answer for this one (a bit late I know):
When the core clock is suspended by the WFI instruction, the debugger won&#8217;t be able to access the part, so no single stepping, flash programming, etc.  I usually have an #ifdef around the __WFI() so it isn&#8217;t included in the Debug build, but is in the Release build.
