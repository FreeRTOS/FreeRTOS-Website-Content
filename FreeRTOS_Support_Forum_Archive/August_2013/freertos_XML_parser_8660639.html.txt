</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 31, 2013</div><div class="thread-post-content">In order that we can maintain the quality of this support service I would respectfully request that this forum is only used to post questions that are directly related to FreeRTOS.

</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on August 31, 2013</div><div class="thread-post-content">Of course. The absence of realloc&#40;&#41; and alloca&#40;&#41; is because FreeRTOS has currently no support for them. That&#8217;s the link to FreeRTOS.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on August 31, 2013</div><div class="thread-post-content">Use heap&#95;3.c, it just wraps the standard library functions. You can wrap the calloc function in the same way.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on August 31, 2013</div><div class="thread-post-content">That would work. But degrades overall performance of all other tasks. I heavily use malloc&#40;&#41; and free&#40;&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 1, 2013</div><div class="thread-post-content">If you use malloc and free in a multi-thread/task system, then malloc/free MUST be made aware of this as the wrapper does, otherwise you run the real risk of corrupting your heap. Some implementations will define hooks inside of these functions that you can define that might make the cost a bit smaller, but it still needs to be there.   
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on September 3, 2013</div><div class="thread-post-content">You are right.&nbsp; I forgot to mention that I use heap4.c for dynamice memory &#40;de-&#41;allocations.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 3, 2013</div><div class="thread-post-content">iIs you code calling pvPortMalloc or malloc? If the latter, you are at risk of corrupting the heap unless you are guarding all calls yourself.  
To get a calloc/realloc for the first case, either switch to heap3.c and add the simple to define functions, or write the corresponding functions for the heap4 implementation. calloc should be fairly simple, as it just needs a little math, call malloc, and then clear the buffer. realloc will take a bit more work, but there are plenty of examples of how to write a realloc around.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on September 3, 2013</div><div class="thread-post-content">I use the heap4 functions, not the standard malloc and free &#40;by including the &#8220;-Dmalloc pvPortMalloc &#8220;-Dfree pvPortFree&#8221; on the commandline&#41;. My app is running nicely, so no problems there.   
Calloc&#40;&#41; is no issue. realloc&#40;&#41; is doable, but what about alloca&#40;&#41;? alloca&#40;&#41; allocates the &#40;variable length&#41; memory on the stack instead of the FreeRTOS-heap.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 3, 2013</div><div class="thread-post-content">alloca&#40;&#41; is a somewhat non-standard function &#40;I don&#8217;t think it is defined in the ISO standards&#41;, but by its general nature, is should be thread safe as it allocates from the stack and each thread has its own stack. The one danger is that you would need to know if the version of alloca &#40;assuming it is provided by your implementation&#41; is compatible with the way FreeRTOS moves the stack.  
If your implementation does NOT provide an alloca&#40;&#41;, then it may be possible to write one yourself, but it will need to be written in assembly, as it can not be written in C, and needs a fairly good understanding on how your compiler works, snd there will likely be strange restrictions on you code to make sure your program still works &#40;declaring new variables after the alloca likely will not work right unless the compiler knows about alloca.&#41;  
Most programs that use alloca can be changed to use malloc, the biggest issue is finding where to put the free call, which is the best choice if alloca isn&#8217;t supported for you.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on September 3, 2013</div><div class="thread-post-content">The GCC based compiler I use for PIC32 &#40;XC32&#41; has a alloca.h header which contains&nbsp; the following:  
<pre><code>#define alloca(x)   __builtin_alloca(x)
</code></pre>
For temporary &#40;variable size/number&#41; allocations, alloca&#40;&#41; would be very useful. It can help to eliminate fragmentation of the heap because these allocations are task-local. Long life allocations would still use the heap.  
Any suggestions on how to determine whether the default alloca&#40;&#41; is 100% compatible to FreeRTOS?
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 3, 2013</div><div class="thread-post-content">The one thing I can think of is look at the generated assembly, and make sure that the code it generates doesn&#8217;t include a check for the stack pointer compared to a global variable, if it does, then it likely won&#8217;t work with FreeRTOS, if not it should. The problem is that alloca is often very simple, and if you ask for too much memory it just over runs the stack. This sort of operation should be compatible with FreeRTOS, as it doesn&#8217;t us any knowledge of the programs memory layout that is changed by FreeRTOS. &#8220;Nicer&#8221; versions might detect the stack overflow, but these will get confused by FreeRTOS as the stack for a task isn&#8217;t in the space the stack started out to be. The good news is that most alloca&#40;&#41;s are the quick and dirty versions that don&#8217;t error check.  
It would make sense, at least for debugging, to make sure that you have turned on the FreeRTOS stack checks if you use alloca&#40;&#41;, as it does make it much harder to estimate stack usage.
</div></div><div class="thread-post"><h3 class="thread-post-title">XML parser</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on September 4, 2013</div><div class="thread-post-content">Thank you&#33;
