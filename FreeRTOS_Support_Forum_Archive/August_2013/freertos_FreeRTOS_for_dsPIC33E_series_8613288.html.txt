The problem are the DO Loop register (DCOUNT, DOSTART, DOEND), they have changed from simple registers (with shadow register) to a 4-Level Hardware Stack. It seems that it&#8217;s not possible to save that stack! 
I think that the only solution is to not use the DO instruction (I have to check if the XC16 compiler is using it or not) for code under RTOS control.
I will do some tests and report back my results. 
P.s. I think that we have the same problem when two tasks are using push.s and pop.s as we do not save the shadow registers.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS for dsPIC33E series </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hollenweger">hollenweger</a> on October 14, 2013</div><div class="thread-post-content">Today I go the answer from Microchip (thank to Benjamin):
The XC16 compile don&#8217;t use the DO Instruction.
So I think that my dsPIC33E port is save as long as I:
&#8211; Do not use the DO instruction in some assembler code.
&#8211; Do not use the shadow register. ( <strong>attribute</strong>(<strong>interrupt</strong> , <strong>shadow</strong>) is not allowed)
&#8211; Do not use <strong>eds</strong> memory (limiting the RAM to 32 KByte)
P.s. The DO instructions and the shadow registers are allowed if used in IRQ functions that are on interrupt levels that are not under RTOS control (configKERNEL<em>INTERRUPT</em>PRIORITY).
Richard, can You confirm my findings, if it&#8217;s OK I will put my port under &#8220;Contributed Source Code&#8221;
regards

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS for dsPIC33E series </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dragonflight1">dragonflight1</a> on October 27, 2013</div><div class="thread-post-content">An update on the DO instruction.
As I noted on FreeRTOS Interactive the math libraries are likely  to use the DO instructions. I did verify that some of them use up to 2 levels (for things like IIfs and matrix stuff). The 33Es have a 4 level stack so you&#8217;re probably safe if you only have 1 or 2 tasks using the dsp libraries or use mutexs/semaphores to guard the calls.
Also I have yet to verify it (I need to try non 33e dsp processor), but I believe the documentation indicates a limit of 7/8 levels for the DOs on the dsPIC30s and dsPIC33Fs as there is a 3 bit level register and it doesn&#8217;t specify if it wraps or saturates. So, the 4 levels may not be that much more restrictive.
Also there is nothing wrong with using the EDS memory for the application code, but it is a really bad idea to even contemplate using it for stack.
It can&#8217;t be used by FreeRTOS, but you can pass pointers to it with queues and the like.
mike
