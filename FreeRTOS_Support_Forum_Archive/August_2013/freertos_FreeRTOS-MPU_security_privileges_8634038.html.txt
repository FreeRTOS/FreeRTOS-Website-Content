  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS-MPU security (privileges)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/scristalli">scristalli</a> on August 16, 2013</div><div class="thread-post-content">Hello, I am currently testing FreeRTOS-MPU on STM32F4, and it has occured to me that a restricted task could call library functions xTaskCreate or xTaskCreateRestricted in order to spawn other tasks, perhaps with malicious code inside them.<br />
Is that a behavior that should be blocked? How would someone prevent such tasks from calling xTaskCreate?  
Thanks in advance.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU security (privileges)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 16, 2013</div><div class="thread-post-content">Currently there is no way of preventing a non-privileged task from creating a privileged task, but it could conceivable done relatively simply by updating the implementation of MPU&#95;xTaskGenericCreate&#40;&#41; in the MPU port layer&#8217;s port.c file.&nbsp; The update would check to see if the scheduler was running, and if so, only allow a privileged task to be created if the MCU was already running in the privileged mode when MPU&#95;xTaskGenericCreate&#40;&#41; was called &#40;that information is already known because it is stored in the xRunningPrivileged variable within the function&#41;.  
However…in statically linked small systems there is an assumption that the system architecture is familiar with all the code s/he is building into the project.&nbsp; It is therefore unlikely to include malicious code, so any additional safe guards would primarily safe guard against simple design mistakes.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU security (privileges)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/supras">supras</a> on July 19, 2019</div><div class="thread-post-content">Hello,
This thread is a little old, but I thouht I&#8217;ll mention the issue here as it&#8217;s related.
On freertos-mpu page (http://www.freertos.org/FreeRTOS-MPU-memory-protection-unit.html) there is stated that &#8220;A Privileged mode task can set itself into User mode, but once in User mode it cannot set itself back to Privileged mode.&#8221; which seems not true. User mode task switches itself to priviledged mode before every call to freertos api &#8211; on cortex-M4 it&#8217;s as simple as executing <code>svc 2</code>. I imagine that unintended execution of this instruction can happen as a result of memory corruption (if you are unlucky). Am I missing or misunderstaning something here?
Best regards, Jan Rydzewski
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU security (privileges)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 19, 2019</div><div class="thread-post-content">I think you have it right &#8211; note in the latest incarnation which is the
V8-M code (Cortex-M33) privileged escalation can only occur from within
the kernel&#8217;s executable code &#8211; otherwise an attempt to raise privilege
is just rejected.
