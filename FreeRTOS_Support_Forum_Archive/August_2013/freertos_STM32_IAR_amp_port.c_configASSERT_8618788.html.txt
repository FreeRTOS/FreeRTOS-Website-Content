  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32, IAR &#038; port.c configASSERT</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/peter_mcc">peter_mcc</a> on August 8, 2013</div><div class="thread-post-content"><em>I am so disappointed. I just 30mins typing up this yesterday and SourceForge &#8220;had an error&#8221; when I tried to post it &#8211; so it&#8217;s all gone :-&#40; I should have learnt by now to copy things to the clipboard before submitting…</em>  
I&#8217;m trying to work out if there is a problem with my understanding or with the IAR Cortex M3 port.c file.  
I&#8217;ve just upgraded to FreeRTOS 7.5.0 and enabled the configASSERT&#40;&#41; macro. It&nbsp; showed that I had a few problems.  
I fixed the first one in <em>vPortValidateInterruptPriority&#40; &#41;</em> by making sure that I called&nbsp;&nbsp;&nbsp;&nbsp; <em>NVIC&#95;PriorityGroupConfig&#40;NVIC&#95;PriorityGroup&#95;4&#41;;</em> before calling <em>NVIC&#95;Init&#40;&amp;NVIC&#95;InitStructure&#41;;</em>. If you dig deep into the STM32 Standard Peripheral library docs it does say to do this but I didn&#8217;t notice. If you don&#8217;t do this then NVIC&#95;Init sets the interrupt priority to zero &#8211; causing <em>configASSERT&#40; ucCurrentPriority &gt;= ucMaxSysCallPriority &#41;;</em> to fail.  
But I got stuck on this one:  
<pre><code>/* Priority grouping:  The interrupt controller (NVIC) allows the bits
that define each interrupt's priority to be split between bits that
define the interrupt's pre-emption priority bits and bits that define
the interrupt's sub-priority.  For simplicity all bits must be defined
to be pre-emption priority bits.  The following assertion will fail if
this is not the case (if some bits represent a sub-priority). 
If CMSIS libraries are being used then the correct setting can be
achieved by calling    NVIC_SetPriorityGrouping( 0 ); before starting the
scheduler. */
configASSERT( ( portAIRCR_REG &amp; portPRIORITY_GROUP_MASK ) == 0x0000 );
</code></pre>
After I call&nbsp; <em>NVIC&#95;PriorityGroupConfig&#40;NVIC&#95;PriorityGroup&#95;4&#41;;</em> the priority bits in AIRCR are set to 3, not zero. To get things to work I had to change the assertion to  
<pre><code>configASSERT( ( portAIRCR_REG &amp; portPRIORITY_GROUP_MASK ) == [b]0x0300[/b] );
</code></pre>
Is that a bug in the port.c file? It seems to work ok once I&#8217;ve changed it.  
I find it still has hard-aborts in ISR&#8217;s but I&#8217;ll do some more reading before asking for help.  
Peter<br />
PS Some of the info is here to help someone else who comes across the same problem
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32, IAR &#038; port.c configASSERT</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/peter_mcc">peter_mcc</a> on August 8, 2013</div><div class="thread-post-content">PS the comment just above the assert for priorities says  
<pre><code>If CMSIS libraries are being used then the correct setting can be achieved by calling NVIC_SetPriorityGrouping( 0 ); before starting the scheduler
</code></pre>
This is the opposite of what it says on the Cortex M3/M4 page <a href="http://www.freertos.org/RTOS-Cortex-M3-M4.html">here</a>,where it says<br />
<em>Most systems default to the wanted configuration, with the noticeable exception of the STM32 driver library. If you are using an STM32 with the STM32 driver library then ensure all the priority bits are assigned to be preempt priority bits by calling NVIC&#95;PriorityGroupConfig&#40; NVIC&#95;PriorityGroup&#95;4 &#41;; before the RTOS is started</em>
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32, IAR &#038; port.c configASSERT</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 8, 2013</div><div class="thread-post-content">This is an issue specific to users of the STM32 peripheral library because the library makes assumptions about the Cortex registers which means you cannot use a default chip configuration.&nbsp;&nbsp; Read the very top entry in the revision history <a href="http://www.freertos.org/History.txt">http://www.freertos.org/History.txt</a> for your answer.  
I would also recommend adding yourself to the mailing list, or&nbsp; better still the new twitter feed. You will find links to both on the FreeRTOS website.
