  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Blocking waits in FreeRTOS? (and 2 other Q&#8217;s)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on November 27, 2004</div><div class="thread-post-content">Hi,
I&#8217;m quite interested in the FreeRTOS project &#40;and thank you for your effort&#33;&#41;.
However, I was wondering why the timer tick is not a &#40;signed&#41; long so that a -1 can be used for a forever wait &#40;blocking read&#41;?
At the moment if I want to block forever I cannot. I must pass it ULONG&#95;MAX but expect to wake up in about 42 days with a 1KHz tick &#40;or 420 days with 10ms tick&#41;.
At any rate, anyone that can live with blocking for many days &#40;if that&#8217;s what they want&#41; can also live with &quot;many days&quot;/2 &#40;by using signed&#41;.
But for folks where &quot;many days&quot; == forver, I now don&#8217;t have to put code everywhere to check of my call came back due to a timeout and now I have to call it again&#33;
ALSO &#40;2nd Q&#41;:
Is the timer tick over flow handled properly in the kernel? Since even a 10ms tick will result in 400+ days before overflow, if not checked explicitely a problem with it may have gone un-noticed.
ALSO &#40;3rd Q :&#41;:
Why no timer functionality in FreeRTOS?
TIA.
Vipin
</div></div><div class="thread-post"><h3 class="thread-post-title">Blocking waits in FreeRTOS? (and 2 other Q&#8217;s)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 27, 2004</div><div class="thread-post-content">Q1 &#8211; 
This was a decision I made mainly based on the efficiency of the list implementation &#40;which is fairly fundamental to the kernel&#41;.&nbsp; The way the implementation is, a &quot;wait forever&quot; tasks would have to be stored outside of the blocked list &#8211; requiring resources for another structure.&nbsp; 
All blocking calls return a value that can be used to determine whether the block was successful or not &#8211; so I think it is ok to put an if&#40;&#41; around the block to see why the call returned with very little overhead.
There cannot be many tasks in real world applications that are going to run less often than &quot;every 400 days&quot;.&nbsp; You can always extend the call to have a block forever option if you wish &#8211; a benefit of open source.
What is best is obviously a matter of opinion, and what is best of one application will not be for another.
Q2 &#8211; This mechanism was tested by initialising the tick to a large value to start with &#8211; rather than 0.
Q3 &#8211; FreeRTOS is a minimal kernel, but &#40;hopefully&#41; easy to extend should you wish.&nbsp; The building blocks required for the majority of applications are in place.&nbsp; Should you wish to add features then this should be straight forward.&nbsp; 
One aim of FreeRTOS is to keep everything as simple as possible.&nbsp; Adding more features increases the code size, necessitating more configuration options and less readability.&nbsp; Having said that it will grow as required over time whatever.
Not all commercial RTOS&#8217;s have every feature of every other.
All these things are of coarse just &quot;in my opinion&quot;.
Regards.
