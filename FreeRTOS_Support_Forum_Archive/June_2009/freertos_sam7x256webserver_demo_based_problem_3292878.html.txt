</div></div><div class="thread-post"><h3 class="thread-post-title">sam7x256webserver_demo based problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 4, 2009</div><div class="thread-post-content">A couple of possibilities spring to mind.
1&#41; In the code the variable c is uninitialised so could contain any value and point to any memory &#8211; if the memory is invalid then you could get a data abort.&nbsp; Even if c happens to point to valid memory strstr will scan through the memory until it happens to find a null terminator which could again take the data pointer into invalid memory.&nbsp; This is just a C thing, nothing to do with FreeRTOS.
2&#41; strstr is a standard library function which could potentially use masses of stack, so you could just be getting a stack overflow.&nbsp; See http://www.freertos.org/Stacks-and-stack-overflow-checking.html .
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">sam7x256webserver_demo based problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 22, 2009</div><div class="thread-post-content">I&#8217;m not really following, but I think you have based your application on one that uses the idle hook &#40;or was it the tick hook?&#41; to trigger USB transfers.&nbsp; If you are not starting the USB task then the queue used to unblock the USB task will not get created and the hook function attempting to write to the queue will cause a crash.
Could this be the route of your problem?&nbsp; Try setting configUSE&#95;IDLE&#95;HOOK to 0 in FreeRTOSConfig.h.&nbsp; Also try setting configUSE&#95;TICK&#95;HOOK to 0.
Regards.
