I don&#8217;t know why you are having problems, but disabling interrupts
around a printf call seems to me to be a /very/ bad idea.  printf can
take quite a bit of time to run &#8211; you certainly don&#8217;t want to disable
interrupts for a long and unpredictable time.
Try splitting it into a &#8220;snprintf&#8221; call to put the formatted output into
a buffer, then &#8220;puts&#8221; to send out the output.  Then at least you should
be able to identify which half of &#8220;printf&#8221; is causing you problems.
</div></div><div class="thread-post"><h3 class="thread-post-title">Semihosting printf call corrupts uxSchedulerSuspended variable</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 12, 2017</div><div class="thread-post-content">Hi Abdurrahman,
Here I rewrote your macro:
~~~
<h1>define safe_printf(format, &#8230;) </h1>
<pre><code>portDISABLE_INTERRUPTS();    
printf(format, ##VA_ARGS);   
portENABLE_INTERRUPTS();
</code></pre>
~~~
<code>portENABLE_INTERRUPTS()</code> just enables the interrupts, not matter whether they were enabled before calling your <code>safe_printf()</code> macro. Maybe it will end a critical section too soon.
For this reason, you can better use these couples:
~~~
<h1>define safe_printf(format, &#8230;) </h1>
<pre><code>taskENTER_CRITICAL();        
printf(format, ##VA_ARGS);   
taskEXIT_CRITICAL();
</code></pre>
~~~
These macros ( functions ) use a global variable <code>ulCriticalNesting</code>.  Only when it becomes zero, interrupts are allowed again.
I would recommend <strong>not</strong> to use <code>printf()</code> from within an ISR.
<blockquote>
  I didn&#8217;t allocate enough stack space. Also, I added the following line to prevent hardfaults
  although I don&#8217;t know the details of why the hard fault occurs.
</blockquote>
I don&#8217;t know who implemented your <code>printf()</code>. Does it come from the C-library?  What does it do, does it send the bytes to a serial port?  If so, why don&#8217;t you just call the UART routine?
</div></div><div class="thread-post"><h3 class="thread-post-title">Semihosting printf call corrupts uxSchedulerSuspended variable</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 12, 2017</div><div class="thread-post-content">David Brown ( he was quicker than me ), is very right of course, <code>printf()</code> executes far too much ( unknown ) code to be called from within a critical section.  Critical sections should be kept as short as possible.
See what you can do with the <code>sprintf()</code> routines, e.g. :
~~~
void safe<em>printf( const char *pcFormat, &#8230; )
{
char pcBuffer[ 129 ];
size</em>t xLength;
va_list xArgs;
<pre><code>va_start( xArgs, pcFormat );
xLength = vsnprintf( pcBuffer, sizeof pcBuffer, pcFormat, xArgs );
va_end( xArgs );
uart_send( pcBuffer, xLength );
</code></pre>
}
~~~
