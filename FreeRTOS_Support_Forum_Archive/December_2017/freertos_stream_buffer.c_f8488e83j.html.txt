  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">stream_buffer.c</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kg7hf">kg7hf</a> on December 18, 2017</div><div class="thread-post-content">I may have something configured wrong, but it appears that certain stream buffer functions require notifications.  This normally isn&#8217;t a problem since you can just not have stream<em>buffer.c in the compilation.  Where it becomes an issues in in mpu</em>wrappers.c when MPU<em>xStreamBufferSend() and MPU</em>xStreamBufferSendFromISR().  It seems that maybe these stream_buffer functions should be wrapped with a configuration of some sort so to not be included in the build if notifications are not supported.
Error: no definition for &#8220;xTaskNotifyStateClear&#8221; [referenced from function <em>xStreamBufferSend ..stream</em>buffer.o] 
Error: no definition for &#8220;xTaskNotifyWait&#8221; [referenced from function <em>xStreamBufferSend ..stream</em>buffer.o] 
Error: no definition for &#8220;xTaskGenericNotify&#8221; [referenced from <em>xStreamBufferSend ..stream</em>buffer.o] 
Error: no definition for &#8220;xTaskGenericNotifyFromISR  [referenced from <em>xStreamBufferSendFromISR ..stream</em>buffer.o]  
Again, I could potentially have something configured incorrectly on my end.  I&#8217;ve built on two different compilers and two different target devices with the same result though.
Paul
</div></div><div class="thread-post"><h3 class="thread-post-title">stream_buffer.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 18, 2017</div><div class="thread-post-content">I have added the following to stream_buffer.c:
<pre>
#if( configUSE_TASK_NOTIFICATIONS != 1 )
     #error configUSE_TASK_NOTIFICATIONS must be set to 1 to build 
stream_buffer.c
#endif
</pre>
and at the moment I think stream<em>buffer.c needs to be built in order to 
use the MPU port, just like event</em>group.c needs to be built in order to 
use the MPU port &#8211; unless you set your linker to remove unused symbols.
</div></div><div class="thread-post"><h3 class="thread-post-title">stream_buffer.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kg7hf">kg7hf</a> on December 19, 2017</div><div class="thread-post-content">Hi Richard,
Thanks for confirming this for me.  yes, both seem to need to be built, but I don&#8217;t see they are explicitly needed for MPU support.  I think a better long term fix would be to create a new config, something like configUSE<em>STREAM</em>BUFFERS and configUSE<em>EVENT</em>GROUPS, although the event groups didn&#8217;t give me any build troubles like the stream buffers did,  
</div></div><div class="thread-post"><h3 class="thread-post-title">stream_buffer.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 19, 2017</div><div class="thread-post-content">The idea with the stream buffers was that if you wanted to use them you 
just included the file, rather than having to set a #define.  Similar to 
when you use the software timers, you include the timers.c file. 
However when you use timers you do also have to set the configUSE_TIMERS 
constant to 1 (or whatever the constant&#8217;s name is, might have that 
wrong).  I will consider doing the same for stream buffers, but I&#8217;m not 
sure about it as, unlike with timers, there is nothing inside the kernel 
itself (tasks.c) that needs to be different if stream buffers are used. 
When software timers are used the kernel needs to know to create the 
timer task.
</div></div><div class="thread-post"><h3 class="thread-post-title">stream_buffer.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dragonflight1">dragonflight1</a> on January 31, 2019</div><div class="thread-post-content">Richard,
I realize this is an old post, and given no one else has commented &#8230;., but I would like to add a vote to making stream buffers guarded by configUSE_xxx
I have lots of FreeRTOS projects (>20 including old ones) and after many attempts at various mechanisms for managing them all I have settled on common directories for the various versions I use, and so it really makes sense to just have FreeRTOSConfig.h select what I use for each project.
Of course it is simple enough for me to add the guarding (which I have done), but it makes sense to me that this would be generally useful
