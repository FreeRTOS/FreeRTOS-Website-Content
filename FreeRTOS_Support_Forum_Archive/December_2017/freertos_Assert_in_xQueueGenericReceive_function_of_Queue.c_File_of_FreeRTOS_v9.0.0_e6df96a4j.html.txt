</div></div><div class="thread-post"><h3 class="thread-post-title">Assert in xQueueGenericReceive function of Queue.c File of FreeRTOS v9.0.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 14, 2017</div><div class="thread-post-content">The line is checking you do not try to write received data to a NULL 
pointer.  pvBuffer can be NULL if uxItemSize is 0 because no bytes are 
written.  You can work out a truth table for the inputs, it will only 
have four rows, the only output that is 0 (and therefore cause the 
assert to trigger) should be the row where
( ( pvBuffer == NULL ) &amp;&amp; ( uxItemSize != 0 ) )
If you don&#8217;t think that is the case then please post the truth table 
here so we can see (I have done it myself before posting).
If the assert is really failing then you are violating the inputs.  You 
can turn asserts off, but then your program will just crash when you try 
to write to NULL.

</div></div><div class="thread-post"><h3 class="thread-post-title">Assert in xQueueGenericReceive function of Queue.c File of FreeRTOS v9.0.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 15, 2017</div><div class="thread-post-content"><blockquote>
  Condition1 Condition2 Output Assert
  False False False No
  False True False No
  True False False No
  True True True Yes
</blockquote>
So your finding is that the assert only occurs if pvBuffer is NULL, but 
uxItemSize is not zero, which (without the assert) would result in 
received data being copied to a NULL pointer, hence the assert is correct.
<blockquote>
  Again we have dig to this issue and found that program is calling to
  xSemaphoreTake(line 248 semphr.h) where pvBuffer is passed as NULL.But
  there is some data in queue.
</blockquote>
If this is a semaphore then the assert is from an internal call where 
pvBuffer should be NULL and uxItemSize should be 0 as that is the case 
for all semaphores.  If the assert is being hit then my guess is you 
have a data corruption somewhere &#8211; maybe the semaphore&#8217;s data structure 
has been overwritten so uxItemSize is not 0?

</div></div><div class="thread-post"><h3 class="thread-post-title">Assert in xQueueGenericReceive function of Queue.c File of FreeRTOS v9.0.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on December 16, 2017</div><div class="thread-post-content"><blockquote>
  I mean full explaination of data corruption.
</blockquote>
I&#8217;m afraid that is a task for you to do.
I do have a few hints though, mistakes that most of us have ever made:
<ol>
<li>A task is running out of it <a href="https://www.freertos.org/Stacks-and-stack-overflow-checking.html">stack space</a></li>
<li>An array is written to outside its bounds, e.g. passing bad length to <code>memcpy()</code> or <code>memset()</code></li>
<li>Forget to check the result of <a href="https://www.freertos.org/a00111.html"><code>pvPortMalloc()</code></a></li>
<li>Some functions in your application try to use <code>malloc()</code> in stead of <code>pvPortMalloc()</code></li>
<li>Call non-re-entrant functions from different tasks</li>
<li>Access objects from different tasks while those objects are not thread-safe and need a mutex</li>
<li>Use of automatic variables (on stack) and forget to initialise them</li>
</ol>
<blockquote>
  Issue nature is Random.
</blockquote>
That is a typical sign of data corruption
