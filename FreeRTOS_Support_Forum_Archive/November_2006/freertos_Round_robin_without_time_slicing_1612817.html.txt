Is there a way to schedule tasks of the same priority by round robin WITHOUT time slicing? Stefan
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on November 15, 2006</div><div class="thread-post-content">So you want a yield to be performed when a task goes to sleep, calls Yield, or is woken by an event, but you don&#8217;t want an automatic yield to be performed during a tick interrupt just because a tick has occurred.
I think you can do this by simply setting configUSE&#95;PREEMPTION to 0 in FreeRTOSConfig.h.&nbsp; This will still allow interrupts to preempt the running task if they wake a task that has a priority higher than the running task if you write your interrupts to do this.&nbsp; But it will prevent the tick from cycling between tasks of equal priority.

</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on November 23, 2006</div><div class="thread-post-content">Stefan,
I am confused about which you want. First you said tasks of the same priority must work in a &quot;cooperative&quot; way. To FreeRTOS that means &quot;not preemptive&quot;. In that case, you do not want preemption because you want cooperative, or in other words a task does not get interrupted until it is ready, and calls yield.
Later you said you must have preemption. Seems to contradict.
I believe &quot;time slicing&quot; simply means that only one task runs at a time. Hence, tasks of the same priority take their slices as they come. The only way to NOT have time slicing then is to have multiple CPU running simultaneously &#40;like dual core&#41;.
I don&#8217;t see why FreeRTOS would not have what you need. Whether preemptive or cooperative mode, when tasks are the same priority, they run in the order they were scheduled. One does not get skipped because anotherone wanted it to&#8230; why would it?
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pshubel">pshubel</a> on December 7, 2009</div><div class="thread-post-content">Hi Everyone,  
It appears that in FreeRTOS you can only disable time-slicing by disabling preemption.&nbsp; Why can’t we disable time-slicing but leave preemption running?&nbsp; We might want to design a system where a bunch of tasks at the same high priority don’t share the CPU via time-slicing.&nbsp; Where is it written that tasks of the same priority must always share the CPU equally?  
Thanks  
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/el_es">el_es</a> on December 7, 2009</div><div class="thread-post-content">pshubel,<br />
It is by design.  
Imagine the scheduler works on a queue of tasks of same priority.  
Also assume that the scheduler is wholly responsible for switching tasks, i.e. the tasks can&#8217;t tell the scheduler to switch to an arbitrary task, the decision is wholly on the scheduler.  
The scheduler takes a task and lets it run for 1 tick &#40;several thousand of clock cycles, possibly&#41; then puts it into the back of the queue and lets the current top-of-queue task run, for 1 tick.   
The result will be round-robin, time-slicing.
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pshubel">pshubel</a> on December 7, 2009</div><div class="thread-post-content">Thanks.&nbsp; Maybe this feature can be added in a future revision.
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 7, 2009</div><div class="thread-post-content">Just so you know &#8211; tasks of equal priority may not necessarily share CPU time equally.&nbsp; Whether they do or not will depend on whether they just run continuously or block/delay for anything.&nbsp; You can see that two tasks of equal priority will not share CPU time equally if one spends most of its time blocked and the other never blocks.  
You can add a feature request in the SourceForge tracker for the option to turn time slicing off.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/el_es">el_es</a> on December 8, 2009</div><div class="thread-post-content">Hello Richard,   
yes, I should have mentioned that, but it seemed so obvious :&#41;<br />
This is wholly defined by &#40;sorry if inaccurate&#41; quote : &#8216;run the highest priority task that is ready to run &#40;i.e. is not blocked or sleeping&#41;&#8217;  
&#40;mind wandering&#41;  
A vague idea of non-equal time sharing would be :  
&#45; add a counter to the task control block<br />
&#45; add a reload value to the task control block<br />
&#45; decide to run the task, if the counter is less or equal to reload-value and the task is at the head of queue<br />
&#45; decrease the counter at each decision to run the task<br />
&#45; when zero, send the task to the back of queue unconditionally<br />
&#45; and reload the counter with reload-value<br />
&#8211;&nbsp; &#40;and only the above would add to the hot path&#41;<br />
&#45; also add an OS call to manipulate this reload-value from inside the task &#40;upon creation, the reload-value would automatically be set to 1&#41;  
Also some sanity checks &#40;is there another task with same priority? how many tasks altogether? Is it sane comparing to others? possibly, find a lowest common multiplier/denominator and sanitize all of them accordingly?&#41; could be introduced there.  
This is only useful if somebody needs a few separate tasks to run all-the-time &#40;non-blocking/sleeping&#41;, with some arbitrary capping of the CPU usage. I wouldn&#8217;t rather expect them to be running at &#8216;highest&#8217; OS priority though… quite the opposite. Because the weighed-round-robin taks would totally cut off everything below their priority, i.e. the idle task.  
&#40;/mind wandering&#41;  
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/el_es">el_es</a> on December 8, 2009</div><div class="thread-post-content">Oh and another thing adding to the &#8216;mind wandering&#8217;:  
&#45; if the task decides to block itself, preserve its counter while sending it to the back of the queue. This will ensure it will get its share later.
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/incrediball">incrediball</a> on December 9, 2009</div><div class="thread-post-content">&gt; Why can’t we disable time-slicing but<br />
&gt; leave preemption running?  
Because that would be like saying &#8220;Why can&#8217;t we take the motor out of the car but drive it anyway?&#8221; Time-slicing is the mechanism that enables preemption. Unless an interrupt causes a task switch, how else is a task ever going to be preempted? The interrupt that does this can be the timer tick interrupt, your own interrupt&#40;s&#41; or both.  
Or have I missed something?
</div></div><div class="thread-post"><h3 class="thread-post-title">Round robin without time slicing?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 9, 2009</div><div class="thread-post-content">incrediball, actually, if you didn&#8217;t need timeout &#40;i.e. all event waits could be wait forever for the event&#41; and didn&#8217;t need to check for the current tick count, a program could very well run with no tick interrupt. Tasks could be preempted by an interrupt signaling data available for a higher priority task, and task would also yield when they wait for a queue that doesn&#8217;t have the needed data.  
Time slicing needs preemption, but preemption does not inherently need time slicing. I suppose disabling time slicing might allow you to optimize your program a bit better, as you would only need to guard data &#40;with critical sections or mutexes&#41; that you share with tasks of different priorities, but not with those of your same priority &#40;but this could be a bit hazard prone as this optimization needs to know a lot about overall program structure&#41;.   
I could even imagine situations where this might make sense to do, if you are in a network of processors and have two data sources providing you data, it might make sense to finish your processing on one data chunk so&nbsp; you can forward it to the next processor before switching to the next chunk rather than time slicing between the two of them so the first result out gets delayed.  
I suppose that the TCB could have added to it a field for how many time slices a given task should be given at a time, and another for how many time slices it has used this time already.
