  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Mutex and tasks with different priorities</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrazoun">mrazoun</a> on September 13, 2016</div><div class="thread-post-content">Hello,
I have two tasks which use the same serial port. I prepared two functions one for &#8220;locking&#8221;, second for &#8220;unlocking&#8221; (see example bellow). I used the mutex &#8220;serLockMutex&#8221; for synchronization of usage of serial port. These functions are called from both tasks. 
When both tasks have the same priority, everything work&#8217;s well. 
When I use higher priority for TASK1, there is a problem. TASK1 (priority 2) don&#8217;t stop on xSemaphoreTake() to wait when the TASK2 (priority 1) released the mutex &#8220;serLockMutex&#8221;.
Many thank&#8217;s in advance for your support.
Zdenek
Example of functions, usefull for only one serial channel
SemaphoreHandle_t serLockMutex = NULL;
~~~
void serLockFreeRTOS (unsigned short channel, TaskHandle<em>t notifyToTask)
{
    if (serLockMutex == NULL) {
        serLockMutex = xSemaphoreCreateMutex();
        vQueueAddToRegistry( serLockMutex, &#8220;LockMutex&#8221; );
    }
    if (serLockMutex == NULL) {
        MAC</em>ERROR_LOOP;
    }
    <strong>xSemaphoreTake( serLockMutex, portMAX_DELAY );</strong>
    ser[channel].notify = notifyToTask;
}
void serUnLockFreeRTOS (unsigned short channel)
{
    xSemaphoreGive (serLockMutex);
    ser[channel].notify = NULL;
}
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">Mutex and tasks with different priorities</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 13, 2016</div><div class="thread-post-content">To make sure I understand what you are reporting &#8211; are you saying that when the tasks have different priorities the call to xSemaphoreTake( serLockMutex, portMAX_DELAY ); returns even when it doesn&#8217;t have the mutex?  Does the function return pdTRUE, so it thinks it has the mutex?  If this is the case then there could be a logic error somewhere in the code where you are calling these functions, and the task that has the mutex is not the one you think it is &#8211; or it could be a simple data corruption somewhere.  Do you have configASSERT() defined (and are you using a recent version of FreeRTOS, which has a lot more assert points to trap potential configuration errors)?
Not sure that it is related to your issue, but from the very brief snippet of code you have posted it seems you might have a logic error that could result in a race condition.
In serUnLockFreeRTOS() you give the semaphore back before setting ser[channel].notify to NULL.  Is that correct?
</div></div><div class="thread-post"><h3 class="thread-post-title">Mutex and tasks with different priorities</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrazoun">mrazoun</a> on September 13, 2016</div><div class="thread-post-content">Thank&#8217;s for your quick answer. 
I found my mistake. The problem was with giving back mutex before setting ser[channel].notify to NULL.
We are moving our project from old one cooperative OS to FreeRTOS and I need more time to understand what really means PREEMPTIVE.
Many thank&#8217;s one more.
Zdenek
