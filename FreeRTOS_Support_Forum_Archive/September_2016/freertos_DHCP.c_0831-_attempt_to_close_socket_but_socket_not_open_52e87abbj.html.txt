  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">DHCP.c 0831- attempt to close socket but socket  not open</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/glenenglish">glenenglish</a> on September 5, 2016</div><div class="thread-post-content">Found this one when I patched in the new +TCP 0831
and associated DHCP changes. an easy one to find.
in vDHCPProcess state == eWaitingSendFirstDiscover
If xApplicationDHCPHook returns <edhcpusedefault> at eDHCPPhase==eDHCPPhasePreDiscover
which sets xGivingUp==true
Down the bottom of vDHCPProcess 
xGivingUp is checked and if true, then the socket is closed.
BUT !!!!
prvInitialiseDHCP(); was never called, because of the initial eDHCPUseDefault return from  the hook
so the socket never gets born.
Until I have a good look at the best way to deal with this (maybe change code path )
really needs an assert if there is an attept to close a open socket.
I have put in 
        /* hack by GLEN <em>/
        /</em> only close socket if it was opened&#8230; */
        if (xDHCPData.xDHCPSocket!=NULL) {
            vSocketClose( xDHCPData.xDHCPSocket );
            xDHCPData.xDHCPSocket = NULL;
        }
-glen      
.
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP.c 0831- attempt to close socket but socket  not open</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kerub">kerub</a> on September 6, 2016</div><div class="thread-post-content">I think the problem is somewhere else.
The function vSocketClose do nothing if the socket is equal NULL
<pre><code>if( ( xSocket == NULL ) || ( xSocket == FREERTOS_INVALID_SOCKET ) )
{
    xResult = 0;
}.
</code></pre>
The socket xDHCPData.xDHCPSocket is set first to NULL after first attempt to close the socket.
The problem is the stucture xDHCPData  has no defined values at the start of the system.
static DHCPData_t xDHCPData;
So it does&#8217;t guarantiee that xDHCPData.xDHCPSocket  is NULL before first use.
In a static analysis of the code it would be reported as an error.
Andrzej
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP.c 0831- attempt to close socket but socket  not open</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 6, 2016</div><div class="thread-post-content">Point of information. xDHCPData above is declared as a static variable, so the C language defines that it will be zero initialized at startup, so pointer members should be NULL. (If it was declared in block scope with auto duration, then yes, it doesn&#8217;t get initialized, but file/global scoped variables are supposed to be zero initialized if not otherwise initiaized).
There are some embeded enviroments where this doesn&#8217;t happen, but those are non-conforming to the standard.
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP.c 0831- attempt to close socket but socket  not open</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 8, 2016</div><div class="thread-post-content">Glen, thanks, you are totally right. We will change it.
Andrzej points out that it doesn&#8217;t matter because NULL may be closed.  Indeed the public API <code>FreeRTOS_closesocket()</code> has this check:
~~~~
    if( ( xSocket == NULL ) || ( xSocket == FREERTOS<em>INVALID</em>SOCKET ) )
    {
        xResult = 0;
    }
~~~~
However, we recently made <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/5850be38/?limit=25#ae98">a change</a> in <code>FreeRTOS_DHCP.c</code> to use <code>vSocketClose()</code>.  That&#8217;s the internal version of <code>FreeRTOS_closesocket()</code>.  The internal version does not check for <code>NULL</code> or <code>FREERTOS_INVALID_SOCKET</code> (<code>~0U</code>).
I agree with Richard Damon that the <code>xDHCPData</code> will be zero&#8217;d after start-up, but if <code>FreeRTOS_socket()</code> fails, the socket pointer could become <code>FREERTOS_INVALID_SOCKET</code>.
The function <code>prvCreateDHCPSocket()</code> still has an assert:
<pre><code>configASSERT( ( xDHCPData.xDHCPSocket != FREERTOS_INVALID_SOCKET ) );
</code></pre>
that we better clean up now.
Please find attached a new version of <code>FreeRTOS_dhcp.c</code> without the <code>configASSERT()</code>.
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP.c 0831- attempt to close socket but socket  not open</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 9, 2016</div><div class="thread-post-content">A note about the new <code>FreeRTOS_DHCP.c</code> in the previous post: you need the latest Labs release to be able to compile it.  In fact the current 160908 release already contains the above <code>FreeRTOS_DHCP.c</code>.
The naming of the DHCP-hook and some enums have changed since the earlier 160112 release. The essence is still the same though.
See <a href="http://www.FreeRTOS.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/TCP_IP_Configuration.html#ipconfigUSE_DHCP_HOOK">here</a> for a detailed description.
The DHCP-hook define has changed:
<pre><code>s/ipconfigDHCP_USES_USER_HOOK/ipconfigUSE_DHCP_HOOK/
</code></pre>
When the old define is still in seen, an #error will be issued.
Some types and values have changed:
<pre><code>s/eDHCPCallbackQuestion_t/eDHCPCallbackPhase_t/
s/eDHCPCallbackAnswer_t/eDHCPCallbackAnswer_t/
s/eDHCPOffer/eDHCPPhasePreDiscover/
s/eDHCPRequest/eDHCPPhasePreRequest/
s/eQuestion/ePhase/
</code></pre>
And finally the hook has changed:
<pre><code>BaseType_t xApplicationDHCPUserHook( eDHCPCallbackQuestion_t eQuestion,
    uint32_t ulIPAddress, uint32_t ulNetMask );
eDHCPCallbackAnswer_t xApplicationDHCPHook( eDHCPCallbackPhase_t eDHCPPhase,
    uint32_t ulIPAddress );
</code></pre>
The parameter <code>ulNetMask</code> was dropped. It can be retrieved by calling <code>FreeRTOS_GetAddressConfiguration()</code>.
Sorry for this inconvenience.  In the 160112 release, the DHCP hook was still a new experimental feature.  It worked OK but the naming was not very clear.
We think that it will be more clear now to new users what the hook does and how it works.
