  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">New stack checking and tracing functionality</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 3, 2008</div><div class="thread-post-content">Stack overflows are the most common source of problems in FreeRTOS.org application.&nbsp; I have therefore added two new features to the SVN head of tasks.c:
1&#41; New function uxTaskGetStackHighWaterMark&#40;&#41; as described below.
/&#42;&#42;
 &#42; task.h
 &#42; &lt;PRE&gt;unsigned portBASE&#95;TYPE uxTaskGetStackHighWaterMark&#40; void &#41;;&lt;/PRE&gt;
 &#42;
 &#42; INCLUDE&#95;uxTaskGetStackHighWaterMark must be set to 1 in FreeRTOSConfig.h for
 &#42; this function to be available.
 &#42;
 &#42; Returns the high water mark for the stack of the calling task.&nbsp; That is,
 &#42; the minimum free stack space there has been &#40;in bytes&#41; since the task
 &#42; started.&nbsp; The small the returned number the closer the task has come
 &#42; to overflowing its stack.
 &#42;/
unsigned portBASE&#95;TYPE uxTaskGetStackHighWaterMark&#40; void &#41;;
2&#41; Stack overflow hook, as described below:
/&#42;
 &#42; Call the stack overflow hook function if the stack of the task being swapped
 &#42; out is currently overflowed, or looks like it might have overflowed in the
 &#42; past.
 &#42;
 &#42; Setting configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW to 1 will cause the macro to check
 &#42; the current stack state only &#8211; comparing the current top of stack value to
 &#42; the stack limit.&nbsp; Setting configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW to greater than 1
 &#42; will also cause the last few stack bytes to be checked to ensure the value
 &#42; to which the bytes were set when the task was created have not been 
 &#42; overwritten.&nbsp; Note this second test does not guarantee that an overflowed
 &#42; stack will always be recognised.
 &#42;/
If configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW is set to greater than 0 then the application must provide a function with the prototype:
void vApplicationStackOverflowHook&#40; xTaskHandle &#42;pxTask, signed portCHAR &#42;pcTaskName &#41;;
In addition, the tasks.c and queue.c code have been laced with trace macros that permit user defined trace functionality to be implemented.&nbsp; More on this later.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">New stack checking and tracing functionality</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/piero74">piero74</a> on March 4, 2008</div><div class="thread-post-content">I think this is the better place for this post &#40;i did it in other thread&#41;
Hi Richard. Hi all.
My idea about how write custom functions for stack check, using macros in create functions, is to save pxTopOfStack of each task in global var with requested stack size, when task is created. 
After, it could be possible check stack usage or stack free, using current pxTopOfStack&nbsp; and a simple difference and compare.
Function usTaskCheckFreeStackSpace could be usefull, but i think it&#8217;s slow because has to search first fill byte 0xa5.
For heap usage, my idea is to have a GV memory, which contains number of bytes allocated using pvPortMalloc, based on formulas above.
When a task is creted or when a queue is created, this variable will increase, when task or queue are deleted it will decrease. 
The value inside will give an idea of heap usage dinamically, but without care about fragmentation &#40;see heap2 schema&#41;.
I think will be a usefull information in run time or during debugging, especially when using application dynamically creates and deletes tasks &#40;or queues, etc&#41;, i.e. using LWIP tcpip stack.
I will use hooks in create e delete functions to do this, but if you think it could be usefull, this idea could be implemented in future freertos trace functions. 
Bye,
Piero
</div></div><div class="thread-post"><h3 class="thread-post-title">New stack checking and tracing functionality</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/maxim79">maxim79</a> on March 4, 2008</div><div class="thread-post-content">Hi Richard. Hi all.
The current implementation of FreeRTOS allows the current task to corrupt its own TCB in case of stack overflow. In so doing a program will detect neither the stack overflow nor the according task name. The application will end up with high probability in nirvana. I think the simplest solution for this problem is to allocate TCB and its stack in one memory block. The stack should grow away from the current TCB. This would increase the diagnostics coverage for FreeRTOS bases applications.
Bye,
Maxim

Yes, good idea, I have made the change as follows &#40;not yet checked in&#41;:
/&#42;&#42;
 &#42; task.h
 &#42; &lt;PRE&gt;unsigned portBASE&#95;TYPE uxTaskGetStackHighWaterMark&#40; xTaskHandle xTask &#41;;&lt;/PRE&gt;
 &#42;
 &#42; INCLUDE&#95;uxTaskGetStackHighWaterMark must be set to 1 in FreeRTOSConfig.h for
 &#42; this function to be available.
 &#42;
 &#42; Returns the high water mark of the stack associated with xTask.&nbsp; That is,
 &#42; the minimum free stack space there has been &#40;in bytes&#41; since the task
 &#42; started.&nbsp; The smaller the returned number the closer the task has come
 &#42; to overflowing its stack.
 &#42;
 &#42; @param xTask Handle of the task associated with the stack to be checked.
 &#42; Set xTask to NULL to check the stack of the calling task.
 &#42;
 &#42; @return The smallest amount of free stack space there has been &#40;in bytes&#41;
 &#42; since the task referenced by xTask was created.
 &#42;/
unsigned portBASE&#95;TYPE uxTaskGetStackHighWaterMark&#40; xTaskHandle xTask &#41;;
&gt; Do you think is it possible or needs very slow check? i think stack check 
&gt; are very important for safety reasons, but has to be very speed test&#33; 
Checking the current stack level against the stack boundary is a quick test, but does not guarantee that you will catch a stack overflow &#40;the stack could have overflowed prior to calling the checking function&#41;.&nbsp; Even checking the 0xa5&#8217;s on the stack is not a guarantee.
