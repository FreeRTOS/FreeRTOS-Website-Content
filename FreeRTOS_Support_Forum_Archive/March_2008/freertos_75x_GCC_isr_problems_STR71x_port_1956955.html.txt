  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">75x GCC isr problems/STR71x port</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/your_username">your_username</a> on March 2, 2008</div><div class="thread-post-content">Hello,
I&#8217;m working on a STR71X port for GCC/Rowley. 
I started with the 75x/GCC port as a base. What I noticed is that the interrupt system does not work. I&#8217;m using the code in crt0&#95;STR75x&#95;FreeRTOS.s to manage context save/restore on entry/exit from interrupts. It seems that the portSAVE&#95;CONTEXT macro leaves the user/system mode stack pointer pointing in an unsafe area &#40;namely, into the area of the interrupted task&#8217;s stack where it&#8217;s register contents will be stored&#41;. Then, later, the IRQ&#95;to&#95;SYS macro switches the processor into system mode, and then calls the handler &#40;C code&#41; to do some work with an unsafe stack pointer &#40;R13&#95;usr&#41;. 
Here is the chronology:
1&#41; An IRQ interrupt occurs, processor goes to IRQ mode and uses SP&#95;irq
2&#41; The IRQ handler, first thing, calls portSAVE&#95;CONTEXT which stores all of the user mode registers onto the system mode stack. You&#8217;ll notice that R13&#95;usr is the same before and after the call to portSAVE&#95;CONTEXT, but the fucntion did in fact store necessary data on the user mode stack. This is where the stack pointer is corrupted.
3&#41; The IRQ handler &#40;and hardware&#41; vectors the processor to a IRQ handler &#40;there are 32 of these, like WAKUPIRQHandler&#41;
4&#41; This intermediate handler changes the mode to system mode, where the stack pointer is now R13&#95;usr, which was left pointing at an unsafe memory area.
5&#41; This intermediate handler then calls a c-code handler, which can do whatever. If this handler uses the stack at all &#40;which it will&#41; then the stored registers &#40;stored durint portSAVE&#95;CONTEXT&#41; are corrupted.
As a quick fix, I added the following lines to the end of the portSAVE&#95;CONTEXT macro:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42;; Correct sp&#95;usr &#42;/
&nbsp;&nbsp;&nbsp; STMDB&nbsp;&nbsp;&nbsp; LR&#33;, &#123;LR&#125;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 
&nbsp;&nbsp;&nbsp; LDMIA&nbsp;&nbsp;&nbsp; LR&#33;, &#123;SP&#125;^
What I want to know is if anyone has used the 75x/GCC port, using the crt0&#95;STR75x&#95;FreeRTOS.s file from the demo. I&#8217;m wondering if I made some mistake or if that port really has this flaw.
Thanks in advance,
DR
</div></div><div class="thread-post"><h3 class="thread-post-title">75x GCC isr problems/STR71x port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 3, 2008</div><div class="thread-post-content">Please look at the UART0 handler which demonstrates how interrupts should be handled.&nbsp; UART0&#95;ADDR points to the address of vSerialISR which is a standard C function &#8211; the macros that change between modes should not be used.&nbsp; If you want to use one of the other interrupts then simply replace the vectored to address with a standard C function to handle the interrupt.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">75x GCC isr problems/STR71x port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/your_username">your_username</a> on March 3, 2008</div><div class="thread-post-content">Richard,
Thanks for the quick reply. I see now, ISRs are run in ISR mode on the ISR stack, no problem, simple and fast.
Have a good day,
Dave.
