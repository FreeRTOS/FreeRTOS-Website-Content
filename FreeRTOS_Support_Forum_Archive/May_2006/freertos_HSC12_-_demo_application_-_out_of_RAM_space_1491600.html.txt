  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on May 3, 2006</div><div class="thread-post-content">I am trying to run the HSC12&#95;small demo application using Freescale&#8217;s CSM12C32 module &#40;it has the MC9S12C32 MCU with 48 pins&#41;.&nbsp; I have to reassign ports/pins as the original &#40;SofTec&#41; uses the 80pin version, but the rest should be the same, i.e., 2 kB RAM. Nevertheless, the linker complains about not enough RAM for the demo application: &quot;Linker error: L1102: Out of allocation space in segment RAM at address 0xF8E&quot;. RAM is starting at 0x800 and of size 0x800.
As I am sure the application has been tested with 2kB RAM, I assume I am doing something wrong here. Did anybody else experience this and could give me a hint on what to adjust?
Thanks.
Note: The .map file summarizes RAM usage to be 1934 bytes; FreeRTOSConfig.h uses &#35;define configTOTAL&#95;HEAP&#95;SIZE &#40; &#40; size&#95;t &#41; &#40; 2048 &#8211; 256 &#41; &#41; which is 1792 bytes. But using 2048 does not make a difference.
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on May 4, 2006</div><div class="thread-post-content">I think the RAM usage in this demo is quite tight.
As an experiment, try making the heap size smaller, say by 256 bytes to start with.&nbsp; Then see if it links.&nbsp; If so see how close you can get it back to the original value.&nbsp; This will give you an idea of how close it is to fitting, and how much needs shaving off.
Does the FreeRTOS hcs12 demo use any special linker file, or just the standard one.&nbsp; I remember there was something about the processor expert screwing up interrupt vectors, but i can&#8217;t think it would do anything to the linker.
Do the larger 80pin device headers include any badly written library code that is eating ram for no reason?
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on May 4, 2006</div><div class="thread-post-content">Thanks for your input &#8211; changing the heap size does not seem to help but your advice made me look at the Processor Export CPU setting of the stack size: it was set to 80 rather than the smaller value of 30 of the original FreeRTOS HCS12 project. I guess creating/opening it with my PE set it to this default value?
I can know run all the demo tasks and the .map file indicates RAM usage of 1982 bytes, which may still be too high &#8211; I would appreciate any comments on this as it may indicate that I won&#8217;t be able to program much with 2kB RAM.
Note: I had to change one thing in main.c to correctly reset the PP5 button-interrupt:
/&#42; Clear the interrupt flag. &#42;/
PIFP = 0x60; // PIFP = 1 doesn&#8217;t work
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 4, 2006</div><div class="thread-post-content">Thanks for the heads up on the bit clearing.
On the smaller devices the demo apps are often written to take up a lot of the available RAM, if not all of it.&nbsp; You can remove some of the demo tasks to free up the RAM requirements, then reduce the amount of heap allocated to the kernel.
If you are very tight on RAM then consider using co-routines instead of tasks.&nbsp; These remove the necessity to allocate a stack to each &#8216;thread&#8217; of execution.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on May 18, 2006</div><div class="thread-post-content">Also sometimes the useless demo functions will free up a lot of RAM if removed for your own functions.
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on May 18, 2006</div><div class="thread-post-content">Oh Richard already mentioned removing the demo functions&#8230;
I want to make more clear the other thing suggested:
The demos are allocating most or all RAM for the RTOS heap. If the linker says &quot;out of RAM&quot;, then that does not mean all the RAM in the heap is used. So in fact, if you are out of RAM, you actually might be able to &#95;reduce&#95; the heap size to solve it.
In &quot;heap&#95;2.c&quot; I looked and found pxNextFreeBlock. I have tracked this variable to see how much heap I needed. It was much less than what is allocated.
</div></div><div class="thread-post"><h3 class="thread-post-title">HSC12 &#8211; demo application &#8211; out of RAM space</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on May 18, 2006</div><div class="thread-post-content">Sorry, was misleading about finding free heap space&#8230;
&#45; in &quot;heap&#95;1.c&quot; you can simply track xNextFreeByte to see how much heap used
&#45; in &quot;heap&#95;2.c&quot; looks more complicated
You would have to search the linked list starting at xStart and find the highest pxNextFreeBlock. It seems like xEnd.xBlockSize could be updated to track free space, but it isn&#8217;t. It is initialized:
xEnd.xBlockSize = configTOTAL&#95;HEAP&#95;SIZE;
