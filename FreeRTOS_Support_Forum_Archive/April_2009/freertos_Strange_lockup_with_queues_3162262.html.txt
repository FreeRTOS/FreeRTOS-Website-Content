  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Strange lockup with queues</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 1, 2009</div><div class="thread-post-content">Today, I&#8217;ve experienced a strange behaviour with FreeRTOS on STM32, using the SVN version and similar in 5.2.0 and 5.1.2.
I&#8217;ve added an ISR handler on USART3 receiving characters from a Zigbee module and sending them into a queue. Oddly enough, the system seems to loop indefinitely in vListInsert when queues are heavily used:
&#35;0&nbsp; 0x20001d2a in vListInsert &#40;pxList=0x20003c94, pxNewListItem=0x20002ab0&#41; at ../../Source/list.c:135
&#35;1&nbsp; 0x200018f0 in vTaskPlaceOnEventList &#40;pxEventList=0x20003c94, xTicksToWait=4294967295&#41; at ../../Source/tasks.c:1435
&#35;2&nbsp; 0x20001226 in xQueueGenericReceive &#40;pxQueue=0x20003c70, pvBuffer=0x20002cab, xTicksToWait=4294967295, xJustPeeking=0&#41; at ../../Source/queue.c:925
&#35;3&nbsp; 0x20000b56 in zigbee&#95;task &#40;pvParameters=&lt;value optimized out&gt;&#41; at adc.c:31
&#35;4&nbsp; 0x00000000 in ?? &#40;&#41;
&#40;gdb&#41; fr 0
&#35;0&nbsp; 0x20001d2a in vListInsert &#40;pxList=0x20003c94, pxNewListItem=0x20002ab0&#41;
&nbsp;&nbsp;&nbsp; at ../../Source/list.c:135
135&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; for&#40; pxIterator = &#40; xListItem &#42; &#41; &amp;&#40; pxList-&gt;xListEnd &#41;; pxIterator-&gt;pxNext-&gt;xItemValue &lt;= xValueOfInsertion; pxIterator = pxIterator-&gt;pxNext &#41;
&#40;gdb&#41; p &#42;pxIterator
$1 = &#123;xItemValue = 3, pxNext = 0x20002ab0, pxPrevious = 0x20002ab0,
&nbsp; pvOwner = 0x20002a98, pvContainer = 0x20003c94&#125;
As you see, pxIterator next and previous fields points onto itself, while its xItemValue is 3, which means that it&#8217;s not the latest item in the list &#40;which should have an xItemValue of portMAX&#95;DELAY, i.e. 0xffffffff&#41;. Of course, it loops indefinitely here &#40;lines number may be a little different than from the original because of my added checks in an attempt to isolate this problem&#41;.
The ISR handler produces characters at a rate of approximately 1000 cps, and the consumer task consumes them as soon as possible.
For the context, there are no memory allocation after the scheduler has started, and all the previous object allocations have been checked. Nothing fancy here, only an annoying lockup. The more tasks there are in the system, the faster the lockup happens.
If you have any idea of what may happen here, I would be interested.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 1, 2009</div><div class="thread-post-content">Btw, there is something else I might add. The two queues exhibiting problems are queues with multiple writers and a single reader:
&nbsp; &#8211; a queue of &quot;short&quot;, whose access are protected by a binary semaphore &#40;characters to write to a LCD display&#41; ;
&nbsp; &#8211; a queue of &quot;long&quot;, representing backlight information to use.
Those queues are never written into from the ISR handlers. However, the serial ISR handler is the sole poster to a third queue, and a task reads those characters, accumulate them, and then uses the other two tasks to drive the LCD, along with other tasks.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on April 1, 2009</div><div class="thread-post-content">Make sure the interrupt priority is equal to or below configMAX&#95;SYSCALL&#95;INTERRUPT priority remembering that the Cortex M3 has 0 as the highest priority NOT the lowest priority.
Also make sure you are not calling any API functions that don&#8217;t end in FromISR from an ISR.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 2, 2009</div><div class="thread-post-content">Thanks MEdwards.
I have the following in FreeRTOSConfig.h, that I got from one of the examples, and which looks right to me:
&#35;define configKERNEL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 255
&#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 191 /&#42; equivalent to 0xa0, or priority 5. &#42;/
I have not changed the default priorities for NVIC interrupts, so the greatest priority level I use is 47 for EXTI15&#95;10. It means that all the NVIC interrupts from my peripherals cannot be interrupted by the FreeRTOS kernel handlers &#40;which is required I think so that the PendSV handler really switches tasks context, not stacked interrupt ones&#41;. And the only active one at the time of the lockup is USART3, whose interrupt level is 46.
Concerning the API functions I call from the ISR handlers, only xSemaphoreGiveFromISR, xQueueReceiveFromISR, xQueueSendFromISR and portEND&#95;SWITCHING&#95;ISR are called.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 2, 2009</div><div class="thread-post-content">Also, a check in vListInsert shows that the element being inserted sometimes has a non-NULL pvContainer field, as if it already belonged to another list &#40;when vListInsert is called from vTaskPlaceOnEventList&#41;. Since pvContainer is set to NULL in both vListInitialiseItem and vListRemove, this alone looks suspicious to me.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 2, 2009</div><div class="thread-post-content">Just to be as precise as possible &#40;sorry about the fragmented additional information, I just thought about it&#41;, I need to add that my tasks do have large enough stacks &#40;128 32-bits words, same for the main &#91;interrupt&#93; stack, few basic local variables, no structs and arrays on the stack&#41;, and that the FreeRTOS stack checker &#40;set at level 2&#41; doesn&#8217;t trigger. And the behaviour is the same whether I compile with -O3 and with -Os. Same result also with GCC 4.4.0 &#40;to be released in a few days&#41; and GCC 4.3.2.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange lockup with queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 3, 2009</div><div class="thread-post-content">Ouch, of course the default priorities were much too high. I skipped the FreeRTOS page explaining exactly this.
The issue is moot, FreeRTOS works perfectly fine as usual :&#41;
