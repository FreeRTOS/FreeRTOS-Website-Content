  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">losing characters in hal_usart_os function usart_os_read</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jhenges">jhenges</a> on July 15, 2019</div><div class="thread-post-content">There seems to be a situation where the hal<em>usart</em>os code will drop the first characters of a transmission. It is not because of speed, but of order of execution.
If you perform something like (after proper initialization, etc):
<pre><code>    io_read(&amp;USART_0.io,&amp;buf1,len1) (call A)
</code></pre>
and wait for characters. Everthing will probably be fine.
But supposing you do the following next:
<pre><code>    io_read(&amp;USART_0.io,&amp;buf2,len2) (call B)
</code></pre>
and in between those two calls you performed a function which caused the characters to come into USART_0, what you will find is that the first character(s) of the transmission actually go into the previous buffer, buf1 rather than buf2.
What is supposed to happen is that the internal ring buffer is supposed to get the characters from the interrupt service routine (which it does). It is then supposed to empty the ring buffer into the desired buffer.
What actually happens is that the previous call (call A) does an initialzation on the ring buffer structure which causes the future call (call B) to incorrectly load those character(s) saved in the ring buffer to the wrong place (buf1 rather than buf2).
This would not be a problem if the destination buffer did not change between calls.
In the usart<em>os</em>read function, the middle of the code looks like this:
<pre><code>if (ringbuffer_num(&amp;descr-&gt;rx) &lt; length) {  // ***** (a)
    CRITICAL_SECTION_ENTER()
    descr-&gt;rx_size   = 0;
    descr-&gt;rx_length = length;
    descr-&gt;rx_buffer = buf;
    while (ringbuffer_num(&amp;descr-&gt;rx) &gt; 0) {
        ringbuffer_get(&amp;descr-&gt;rx, &amp;descr-&gt;rx_buffer[descr-&gt;rx_size++]);
    }
    CRITICAL_SECTION_LEAVE()
    if (sem_down(&amp;descr-&gt;rx_sem, timeout) != 0) {   // ***** (b)
        return ERR_TIMEOUT;
    }
} else {
    while (was_read &lt; length) {
        ringbuffer_get(&amp;descr-&gt;rx, &amp;buf[was_read++]);
    }
}
</code></pre>
In the two places marked by ****, the following changes should be made.
In the (a) case, the ringbuffer could have just 1 character in in which requires attention. As such, the original code would be off by 1. The test should be &lt;= rather than just &lt;.
In the (b) case, the (descr->rx<em>buffer = NULL) state is used as a flag to initialize some transfer activities in the overall code flow. (look at the interrupt callback, usart</em>os<em>fill</em>rx<em>buffer) In this example, this pointer is set to the previous buffer. So when the call come in to start a new read, the ring buffer gets emptied into the wrong target buffer because the (descr->rx</em>buffer) has not been set to NULL. The reason for adding this initialization code at (b) is for the case when you try to flush the buffer before going onto a following serial transaction.
<pre><code>if (ringbuffer_num(&amp;descr-&gt;rx) &lt;= length) {     // ***** (a)
    CRITICAL_SECTION_ENTER()
    descr-&gt;rx_size   = 0;
    descr-&gt;rx_length = length;
    descr-&gt;rx_buffer = buf;
    while (ringbuffer_num(&amp;descr-&gt;rx) &gt; 0) {
        ringbuffer_get(&amp;descr-&gt;rx, &amp;descr-&gt;rx_buffer[descr-&gt;rx_size++]);
    }
    CRITICAL_SECTION_LEAVE()
    if (sem_down(&amp;descr-&gt;rx_sem, timeout) != 0) {
        descr-&gt;rx_buffer = NULL;                    // ***** (b)
        descr-&gt;rx_size = 0;                         // ***** (b)
        descr-&gt;rx_length = 0;                       // ***** (b)
        return ERR_TIMEOUT;
    }
} else {
    while (was_read &lt; length) {
        ringbuffer_get(&amp;descr-&gt;rx, &amp;buf[was_read++]);
    }
}
</code></pre>
I have attached an updated version of hal<em>usart</em>os.c call ed hal<em>usart</em>lost<em>character</em>fix.c
