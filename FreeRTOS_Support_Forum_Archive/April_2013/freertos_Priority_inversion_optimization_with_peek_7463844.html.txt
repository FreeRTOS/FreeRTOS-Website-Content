  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Priority inversion, optimization with peek</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/meierbenjamin">meierbenjamin</a> on April 10, 2013</div><div class="thread-post-content">Hi all, I have something on my mind and would like your opinion.  
In a given application i have one SPI-ressource which is used to communicate with both a radio-chip and a graphic-display by having multiple chipselects.<br />
Task A drives the radio-chip, task B displays texts and images on the display.<br />
Task A has obviously the higher priority than task B.<br />
The SPI is guarded by a MUTEX.  
The application works, and anyone is happy.<br />
Whilst verifiing the software using the trace-facility I could detect a priority inversion.<br />
The image below shows this capture. The task A &#40;number 4&#41; attempts to get the MUTEX &#40;blue lines&#41; which is hold by the task B. Task A obviously has to wait until task B gives the MUTEX back. Which it does after it has written the whole character to the display.<br />
Task B will give the mutex back after every character before taking it again. This to make sure task A will get the SPI ressource within a useful time.  
<img src="http://mycinema.onlywork.ch/images/TraceInheritDisplayTask.png" alt="" />  
To minimize the delay of task A I could of course give and take the mutex between every single pixel I send to the display.<br />
I think this would be a huge impact in performance &#40;confirmed by a short test&#41;.  
So my Idea was to check between any pixel sending to the display whether the mutex is wanted by another task.<br />
I would check if the queue of the mutex is empty or not. When empty I then would give and take the mutex.  
Although I thing this would be much more efficient I don&#8217;t like to access kernel-objects directly &#40;without an OS function&#41;.<br />
I think it might be possible to detect whether another task is waiting by using the 
<pre><code>xQueuePeek
</code></pre>
function with the mutex-handler as the 
<pre><code>xQueue
</code></pre>
-argument.  
Thanks for your opinion.

Which trace are you using?
</div></div><div class="thread-post"><h3 class="thread-post-title">Priority inversion, optimization with peek</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/meierbenjamin">meierbenjamin</a> on April 10, 2013</div><div class="thread-post-content">I quickly tested the following:  
<pre><code>/* Test whether the mutex is wanted by another task. */
if( listLIST_IS_EMPTY( &amp;((( xQUEUE * )xSPIMutex)-&gt;xTasksWaitingToReceive) ) == FALSE )
{
    /* Share the SPI with the radio-tasks. */
    xQueueGiveMutexRecursive( xSPIMutex );
    xQueueTakeMutexRecursive( xSPIMutex, portMAX_DELAY );
}
</code></pre>
This actually works quite fine, but I had to manually import the xQUEUE-definition.  
I also testet the same with the priority-check.  
<pre><code>/* Test whether the mutex is wanted by another task. */
if( uxTaskPriorityGet( NULL ) &gt; ( tskIDLE_PRIORITY + 1 ) )
{
    /* Share the SPI with the radio-tasks. */
    xQueueGiveMutexRecursive( xSPIMutex );
    xQueueTakeMutexRecursive( xSPIMutex, portMAX_DELAY );
}
</code></pre>
The result is about the same &#40;priority-check is a tiny bit slower but much more satisfying because I don&#8217;t have to mess around with the kernel-objects&#41;.  
Thanks for the tip with the priorities.

Thanks again.

  listLIST&#95;IS&#95;EMPTY&#40; &amp;&#40;&#40;&#40; xQUEUE &#42; &#41;xSPIMutex&#41;-&gt;xTasksWaitingToReceive&#41;
</blockquote>
This does not tell you if the task waiting has lower, equal or higher priority than the task currently holding the mutex.  
<blockquote>
  uxTaskPriorityGet&#40; NULL &#41; &gt; &#40; tskIDLE&#95;PRIORITY + 1 &#41;
</blockquote>
…neither will this as it stands.&nbsp; As you then give the mutex back and retake it, the kernel scheduler will sort out which task should be given the semaphore next anyway, so maybe it does not matter in your case.&nbsp; However, if you check against the calling tasks original priority &#40;the priority it had when it took the mutex&#41; instead of tskIDLE&#95;PRIORITY + 1 then you need only give the mutex back and re-take it if the calling tasks priority has been raised &#8211; if that makes sense.

</div></div><div class="thread-post"><h3 class="thread-post-title">Priority inversion, optimization with peek</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/meierbenjamin">meierbenjamin</a> on April 10, 2013</div><div class="thread-post-content"><blockquote>
  This does not tell you if the task waiting has lower, equal or higher priority than the task currently holding the mutex.
</blockquote>
Of course not, but the performance is much better than giving the mutex back after every pixel-write. Also this particular application there can only be a higher-priority task wanting the mutex, because there are only such tasks. I discarded this &#8220;solution&#8221; anyway.  
The &#40; tskIDLE&#95;PRIORITY + 1 &#41; is actually the normal priority of the task.<br />
The priority is never changed unless it is inherited thus it will only give and re-take the mutex exactly as you described.<br />
This was just a quick and dirty implementation to test the mechanism itself. The actual implementation now saves the priority when creating the task and compares to that value.
