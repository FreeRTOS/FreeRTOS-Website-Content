</div></div><div class="thread-post"><h3 class="thread-post-title">Infinite loop in heap_4..</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 22, 2013</div><div class="thread-post-content">Most likely cause is that the data structures have somehow got corrupt, or that vPortFree&#40;&#41; has been passed an invalid pointer.  
Do you have configASSERT&#40;&#41; defined?&nbsp; Do something very simply like the following in FreeRTOSConfig.h if not:  
&#35;define configASSERT&#40; x &#41; if&#40; x == 0 &#41; &#123; taskDISABLE&#95;INTERRUPTS&#40;&#41;; for&#40;;;&#41;; &#125;  
just to see if it ever gets called &#40;in this case, if it is called, your program will just sit in the infinite loop&#41;.&nbsp; If it is called then you can write a more sophisticated version to find which line is causing it to be called.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Infinite loop in heap_4..</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 26, 2013</div><div class="thread-post-content">As was mentioned, the most likely cause is that the heap has been corrupted by accessing out side the bounds of a heap object &#40;perhaps forgetting to +1 the value of strlen when allocating blocks on the heap&#41;.  
The other possibility is that the heap has been corrupted by multi-threading issues. One big one would be calling them from ISR routines &#40;the heap&#95;&#35; routines are thread safe but not ISR safe&#41;. For heap&#95;3, there is also the possible issue of using malloc/free directly in a non-threadsafe manner.
