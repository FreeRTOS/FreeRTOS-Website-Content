  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Trouble with a mutex</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/paulgcoleman">paulgcoleman</a> on March 23, 2012</div><div class="thread-post-content">I&#8217;ve got a simple RS232 library which I&#8217;m using for debug output but it doesn&#8217;t always do what I expect. I&#8217;ve created a function to initialise the port and within that I create a mutex to protect the resource. I have a number of threads, all of which have different priorities, and any of them are free to use the RS232 library calls. What I wanted to ensure was that if one thread is preempted by a higher priority thread whilst in the middle of sending a message, it&#8217;s able to finish its message before the higher priority one gets run.  
<h2>Here is an over-simplified version of my code showing the mutex creation/calls…</h2>
static xSemaphoreHandle semRS232Tx = NULL; // mutex to protect the resource  
RS232&#95;STATUS RS232Init&#40;void&#41;<br />
&#123;  
// create the mutex which protects writes and ensures reentrancy<br />
semRS232Tx = xSemaphoreCreateMutex&#40;&#41;;<br />
if&#40;NULL == semRS232Tx&#41;<br />
return RS232&#95;FATAL&#95;ERROR;  
return RS232&#95;SUCCESS;<br />
&#125;  
RS232&#95;STATUS RS232WriteString&#40;char &#42;str&#41;<br />
&#123;<br />
if&#40;pdFAIL == xSemaphoreTake&#40;semRS232Tx, TIME&#95;IN&#95;MS&#40;1000&#41;&#41;&#41;<br />
return RS232&#95;MUTEX&#95;NOT&#95;AVAILABLE;  
// output character string here  
xSemaphoreGive&#40;semRS232Tx&#41;;  
return RS232&#95;SUCCESS;  
<h2>&#125;</h2>
Most of the time it works fine but occassionally I will get a higher priority thread message embedded in the middle of a low priority thread&#8217;s message and I don&#8217;t understand why. Can anybody see what I&#8217;ve done wrong?  
Thanks, Paul.<br />
P.S. Great little OS by the way. We looked at ThreadX which was going to cost us £4,000 just for the binaries and went with FreeRTOS in the end and it really has performed well :o&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">Trouble with a mutex</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 23, 2012</div><div class="thread-post-content">I don&#8217;t see a problem here, but is there any possibility that the message was that was interrupted could have been created with two different calls to RS232WriteString? I know that I often use something like this for serial output but use a RECURSIVE mutex, so the low level I/O can claim the mutex, but if a task needs to piece together a message out of pieces, it can take the mutex itself to avoid the output being interrupted.

RS232WriteString&#40;&#8221;string 1&#8243;&#41;;<br />

</div></div><div class="thread-post"><h3 class="thread-post-title">Trouble with a mutex</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 23, 2012</div><div class="thread-post-content">If the mutex was a recursive mutex, and your code becomes  
if&#40;pdTRUE == xSemaphoreTakeRecursive&#40;semRS232Tx, TIME&#95;IN&#95;MS&#40;1000&#41;&#41;&#41;&#123;<br />
&nbsp; RS232WriteString&#40;&#8221;string 1&#8243;&#41;;<br />
&nbsp; RS232WriteString&#40;&#8221;string 2&#8243;&#41;;<br />
&nbsp; RS232WriteString&#40;&#8221;string 3&#8243;&#41;;<br />
&nbsp; xSemaphoreGiveRecursive&#40;semRS232Tx&#41;;<br />
&#125;  
&#40;and RS232WriteString and the init function are also changed for a RecursiveMutex&#41;<br />
then the Mutex isn&#8217;t given up until the give above &#40;that is the difference with recursive muteness, the count the depth they are in use in a given task.  
I often have a number of functions that write to the serial port &#40;at the bottom a single char put, but above that writing strings, or numbers in various formats&#41;, and by using the recursive mutex, a task can take it if it wants to build a complex message, but if it just wants to send out a simple string or number, it can just call the appropriat output routine. Since the single character out routine also uses the mutex, it is impossible for to break into the middle of another tasks message. At worse, if a task is mis written then ITS messages might get broken up, but at least that points clearly to where the problem it.&nbsp; The one exception is that if an ISR wants to put out a character, It might be able to break into the stream as it can&#8217;t be protected by a Mutex, but ISRs tend not to need to put much out, except maybe for some quick debugging &#40;and then I need to realize that they might not get their data out if the serial port is full at the time&#41;.

Yes I see what you mean but surely you could achieve the same thing as you&#8217;ve described by not having a mutex in the RS232Write function at all and just replace what you have above with a regular non-recursive mutex? Maybe I should have just done that in the first place&#33;&#33;  
Regards, Paul.
</div></div><div class="thread-post"><h3 class="thread-post-title">Trouble with a mutex</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 23, 2012</div><div class="thread-post-content">Yes, you could have a single not recursive mutex, that you call outside the low level send. The reason I didn&#8217;t do that is for 2 reasons:  
1&#41; Using the recursive mutex, a task can&#8217;t forget to acquire the mutex and accidentally inject itself in another tasks output.<br />
2&#41; Often enough you are just sending a single item out, so that needing all the explicit calls is a bother.  
By the time you include the fact that the tasks may well be limited by the speed of the serial port, the small extra overhead of the recursive mutex is minimal. If I am really worried about speed here, I shouldn&#8217;t be sending a message to a serial port.
