  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Still locking after portEND_SWITCHING_ISR</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on March 13, 2012</div><div class="thread-post-content">Yesterday I asked a question about eternal lock after context switch &#40;here <a href="https://sourceforge.net/projects/freertos/forums/forum/382005/topic/5111217">https://sourceforge.net/projects/freertos/forums/forum/382005/topic/5111217</a>&#41;<br />
But unfortunately, even right procedure of serving interrupt still causes eternal lock&#33;  
It looks like this:  
<pre><code>static portBASE_TYPE xHigherPriorityTaskWoken;
    xHigherPriorityTaskWoken=pdFALSE;
    EXTI_ClearITPendingBit(EXTI_Line10);
    irq++; //for debug purposes
    if(irq==2)
        __asm("NOP"); //here I can place a break, after that all tasks remain blocked forever
    xSemaphoreGiveFromISR(IRQSemph, &amp;xHigherPriorityTaskWoken);
    portEND_SWITCHING_ISR(xHigherPriorityTaskWoken);
</code></pre>
There are two tasks, one for actual serving this interrupt, high-priority, which starts with xSemaphoreTake&#40;IRQSemph, portMAX&#95;DELAY&#41;;<br />
and another, with lower priority, which is blocked, waiting signal form high-priority task.  
I suppose, that when breakpoint is reached &#40;irq count == 2&#41;, ISR interrupts this high priority task, while it is processing last ISR &#40;irq == 1&#41;. But I don&#8217;t understand, why this is causing this lock&#33;  
When I am entering xSemaphoreGiveFromISR, I can see that it&#8217;s pxQueue-&gt;xTxLock is 0, so no actions with even list is taken, just data copy, inctement of xTxLock and return of&nbsp; FALSE;  
Also pxQueue-&gt;xTasksWaitingToReceive-&gt;uxNumberOfItems = 2.  
What does this mean, why there is two tasks, waiting for receive? The only one task, that uses this semaphore is my high-priority routine…

</div></div><div class="thread-post"><h3 class="thread-post-title">Still locking after portEND_SWITCHING_ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on March 13, 2012</div><div class="thread-post-content">No-no.<br />
This is just a driver for radio tranciever.<br />
Here is my high-priority task:  
static void taskDriverIRQHandler&#40;void &#42;pvParameters&#41;<br />
&#123;<br />
u8 Status;<br />
while&#40;1&#41;<br />
&#123;<br />
xSemaphoreTake&#40;IRQSemph, portMAX&#95;DELAY&#41;;<br />
xSemaphoreTake&#40;SPI&#95;DMA&#95;Tx, portMAX&#95;DELAY&#41;;<br />
Status=ResetIRQ&#40;&#41;;<br />
if&#40;Status&amp;TX&#95;DS&#41;<br />
&#123;<br />
xSemaphoreGive&#40;TxFIFOFree&#41;;<br />
&#125;<br />
xSemaphoreGive&#40;SPI&#95;DMA&#95;Tx&#41;;<br />
&#125;<br />
&#125;  
I want it work in such way:<br />
transmitter task &#40;low priority&#41; blocks on TxFIFOFree. Radio module asserts it&#8217;s irq pin, causing external interrupt &#8211; it&#8217;s isr is in my first post. ISR gives IRQSemph, also clearing EXIT bit.<br />
taskDriverIRQHandler task unblocks, waits for all DMA transfers to be complete &#40;actualy, they are all complete much earlier, I checked that&#41;, then sends to transiever SPI command to clear it&#8217;s internal interrupt status &#8211; without that there will be no more interrupts, as EXTI handles high-to-low transition, and IRQ pin remains constant low.<br />
Then taskDriverIRQHandler should give one more slot in TxFIFOFree, unblocking Tx task again.<br />
But it doesn&#8217;t work in that way&#33;  
What I know, is that Tx task finishes it&#8217;s DMA transfers and blocks waiting TxFIFOFree. After some time, data is being sent by module and it asserts IRQ pin. ISR serves it, unblocks taskDriverIRQHandler, wich defenitly resets module&#8217;s IRQ status.<br />
Than some black magic happens, which I can not understand or even debug &#40;because braking or even adding some tracing causes functions to execute slower and second interrupts does not ruin everything&#41;.<br />
All I know is that second interrupt arrives, my system enters ISR, but tracing internals of xSemaphoreGive call, shows that IRQSemph is considered to be locked, it&#8217;s pxQueue-&gt;xTxLock is 0, not queueUNLOCKED.<br />
So, semaphore does not unblock it, just increment lock counter &#8211; but there is no other tasks running to unblock it either.

Sorry for my questions, it is really stupid mistake.<br />
Obviously, I shouldn&#8217;t use NVIC-configuration routines like this:  
<pre><code>NVIC_InitStructure.NVIC_IRQChannel = DMA1_Channel5_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = configLIBRARY_KERNEL_INTERRUPT_PRIORITY-3;
    NVIC_InitStructure.NVIC_IRQChannelSubPriority = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;
    NVIC_Init( &amp;NVIC_InitStructure );
     NVIC_InitStructure.NVIC_IRQChannel = EXTI15_10_IRQn;
     NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = configLIBRARY_KERNEL_INTERRUPT_PRIORITY-2;
     NVIC_InitStructure.NVIC_IRQChannelSubPriority = 0;
     NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;
     NVIC_Init(&amp;NVIC_InitStructure);
</code></pre>
I wanted to set priorities to<br />
configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY-3;<br />
configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY-2;<br />

<pre><code> NVIC_SetPriority(DMA1_Channel5_IRQn,configLIBRARY_KERNEL_INTERRUPT_PRIORITY-3);

</code></pre>
