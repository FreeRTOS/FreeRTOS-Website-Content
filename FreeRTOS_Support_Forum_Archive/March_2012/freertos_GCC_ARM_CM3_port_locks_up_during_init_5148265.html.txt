  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">GCC/ARM_CM3 port locks up during init</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rodspade">rodspade</a> on March 27, 2012</div><div class="thread-post-content">I&#8217;m using the GCC/ARM&#95;CM3 port of version 7.1.0.&nbsp; My startup code creates tasks and other FreeRTOS objects, and does much other initialization before calling vTaskStartScheduler.&nbsp; It&#8217;s locking up during the init.&nbsp; I think the heap&#95;2 memory allocation is attempting to invoke the scheduler before it starts.&nbsp; I believe it goes something like this:  
I call xTaskCreate &#40;or create a queue or whatever&#41;, which calls pvPortMalloc in heap&#95;2.c.&nbsp; This calls xTaskResumeAll.  
Because other tasks have already been created, xTaskResumeAll manages the ready/pending list and possibly sets xYieldRequired.&nbsp; I suspect it is then calling portYIELD&#95;WITHIN&#95;API, which calls vPortYieldFromISR and invokes a context switch before I&#8217;ve called vTaskStartScheduler.&nbsp; The application locks up.  
I think it might work if I were to somehow make sure that interrupts can never be enabled before the scheduler starts.&nbsp; Instead, I worked around it by creating just one task, starting the scheduler, and doing the rest of my init within the task.  
Is this &#8220;expected&#8221; behavior, or should I have been able to do all my initialization before the scheduler starts?
</div></div><div class="thread-post"><h3 class="thread-post-title">GCC/ARM_CM3 port locks up during init</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 28, 2012</div><div class="thread-post-content"><blockquote>
  I think the heap&#95;2 memory allocation is attempting to invoke the scheduler before it starts.&nbsp; I believe it goes something like this:  
</blockquote>
I call xTaskCreate &#40;or create a queue or whatever&#41;, which calls pvPortMalloc in heap&#95;2.c.&nbsp; This calls xTaskResumeAll.
xTaskResumeAll&#40;&#41; will not attempt a context switch if the scheduler has not started.&nbsp; It will attempt a context switch only if either tick interrupts have been missed while the scheduler was suspended, or tasks were placed into the pending ready list while the scheduler was suspended &#8211; but there will be no ticks if the scheduler has not started, and kernel API functions that unblock a task should not be executed before the kernel is started, so neither of these conditions can be true.  
However…if you have interrupts enabled at this point, and an interrupt executes, and the interrupt itself does something to the kernel, then you will definitely have problems.  
The kernel itself will keep interrupts disabled from the point the first API call is made to the point that the scheduler is started.&nbsp; Are you manually enabling interrupts anywhere?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">GCC/ARM_CM3 port locks up during init</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rodspade">rodspade</a> on April 3, 2012</div><div class="thread-post-content">Thank you for your response.  
I am using interrupts before the scheduler starts, but I make sure that the interrupt handler does not call any rtos API before I start the scheduler.&nbsp; I overlooked the fact that the API calls to create tasks, etc. were themselves disabling interrupts and not reenabling them if the scheduler has not yet started.&nbsp; So my interrupts did not trigger, and that&#8217;s why my app was locking up.  
I explicitly reenabled interrupts after making API calls prior to starting the scheduler, and now my code works.&nbsp; However, I think it will make more sense to start the scheduler earlier and do most of my other initialization from a task, rather than trying to do things that require interrupts before I start the scheduler.&nbsp; Now that I see how it works, it makes sense to me.  
Thanks for your assistance&#33;&nbsp; :-&#41;
