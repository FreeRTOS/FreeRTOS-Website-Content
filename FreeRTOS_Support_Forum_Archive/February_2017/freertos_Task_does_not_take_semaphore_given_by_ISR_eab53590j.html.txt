  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Task does not take semaphore given by ISR</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/psjapex">psjapex</a> on February 6, 2017</div><div class="thread-post-content">Hi, I&#8217;ve been banging my head against the wall on this problem for a while now and need some advice or clarity on what should be a simple problem.
I have a &#8216;main task&#8217; that takes a static binary semaphore. The semaphore is supposed to be given or released by a PIT timer ISR. In debug, I can see that the ISR is correctly giving the semaphore, and I can also see that contex is being given directly back to the main task. However once back in the main task, the task never takes the semaphore and seemingly continues to sleep on it even though it was given by the ISR.
**Edit:
I noticed that after the ISR gives the semaphore, the uxMessageWaiting variable (inside the semaphore/queue struct) is 1 (as it should be since there is an item given in the queue). But after returning to the main task, the variable is changed to 0. So when the main task tries to take the semaphore, it looks and see&#8217;s uxMessageWaiting is still 0. I&#8217;m thinking there may be a stack or memory issue at hand here. Any advice is welcome.

</div></div><div class="thread-post"><h3 class="thread-post-title">Task does not take semaphore given by ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 6, 2017</div><div class="thread-post-content">Is this a PIC24?  Guessing from the way the ISR is written.
Not related to your problem, but reschedule (the variable) should be 
initialised to pdFALSE (0) before it is used in xSemaphoreGiveFromISR.
Is there a portYIELD<em>FROM</em>ISR() function for the PIC24?  Other than 
that, I can&#8217;t see anything standing out as being wrong.  Can you step 
into the portYIELD<em>FROM</em>ISR() function to see what happens?  If this is 
a PIC24 it should take you into the function the task being unblocked is 
blocked in &#8211; from there you might be able to see why its not executing.
</div></div><div class="thread-post"><h3 class="thread-post-title">Task does not take semaphore given by ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/psjapex">psjapex</a> on February 6, 2017</div><div class="thread-post-content">This is actually an K64 Arm cortex m4 chip on a custom board. This is being built out in Kinetis Design Studio IDE. Based on the functionality, I feel like theres an underlying memory issue in my system that is overwriting the semaphore values. See edit in original post.
</div></div><div class="thread-post"><h3 class="thread-post-title">Task does not take semaphore given by ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 6, 2017</div><div class="thread-post-content">In which case the if statement:
if(reschedule){
}
is not required.  The if is done for you inside the portYIELD<em>FROM</em>ISR() 
macro.
On this device the yield should pend the PendSV interrupt.  Is the 
interrupt being entered?
If so, the handler will call vTaskSwitchContext().  Is 
vTaskSwitchContext() selecting the task you expect?  (I think you said 
it was, but want to be sure).
</div></div><div class="thread-post"><h3 class="thread-post-title">Task does not take semaphore given by ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 7, 2017</div><div class="thread-post-content">Not sure if it matters, but you create a task that will use a semaphore that hasn&#8217;t been created yet.
<code>Task_Main</code> has a high priority of 10. If <code>Task_Main_Initialize</code> runs at a lower priority, chances are big that <code>Task_Main</code> calls <code>xSemaphoreTake()</code> for a non-existing semaphore.
Can you try swap the two statements?
