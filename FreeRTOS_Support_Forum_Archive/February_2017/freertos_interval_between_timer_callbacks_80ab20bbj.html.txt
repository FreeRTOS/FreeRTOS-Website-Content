I understand that FreeRTOS like any OS has a processing delay, but that should only mean that the first call to my callback is delayed. If the processing delay is constant, the interval between all the following calls to my callback should still be 1 ms, right (I have no other timers in my system)?

delay with a different resolution.
If the timer is expiring on every tick then what else is the system 
doing?  All your other tasks will never get a whole time slice.  How 
long does the timer callback take to execute?
</div></div><div class="thread-post"><h3 class="thread-post-title">interval between timer callbacks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/odman">odman</a> on February 24, 2017</div><div class="thread-post-content">Yes my post is confusing, sorry late at night. I&#8217;ll try to make it clearer here.
Systick is 1 ms, but the timer is set to expire approximately every 1.3s, so say 1300 ticks.
I&#8217;m reading an independent timer (PRO Timer) at the entry of the systick ISR and of the timer callback function. The callback only sends a message to a task (outside of FreeRTOS) and then gives a xSemaphoreGiveFromISR to the same task. What I did was to measure the interval between calls to the callback and see that they happen with over 1.4 s intervals, then I took that value and divided with the amounts of ticks the timer is set to and got my 1075 usec vs exactly 1000 usec for systick. Let&#8217;s forget about that math for a second and just say that the intervals between calls to my callback is > 0.1s longer than expected.
What I was elluding to was that if all processing between OS and user code actually takes 0.1s (not likely I&#8217;m running a CM4 at 38.4 MHz!) we can call this delay D.
I can see that systick is very exact, so if I&#8217;m not running tickless I should see T0, 1300*t, T1 &#8230;
where Tn is a tick resulting in callback and &#8216;t&#8217; is an empty tick. Now the absolute time I get my callback should be T0+D, T1+D, &#8230; The interval however ( (T1+D) &#8211; (T0+D) ) should still be my expected time of 1300 ticks. My intervals are actually increased so if I when I measure my intervals I see absolute times of T0+D, T1+2D, &#8230; etc.
I can come up with more exact values when I get access to the lab on Monday, but right now I&#8217;m struggling with something that doesn&#8217;t even make theoretical sense to me. 
Oh one more thing: I have tested with different intervals of both ticks and timer values. Each give me different D. I noticed that tickless mode more than doubles the delay for everything else being the same. I get your point that if my callback actually took longer to execute than the programmed timer intervals (autoreload) I would get the effects I see, but it wouldn&#8217;t change with tick/tickless or different tick intervals.
Hopefull I made more sense this time 🙂
thanks!
</div></div><div class="thread-post"><h3 class="thread-post-title">interval between timer callbacks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 24, 2017</div><div class="thread-post-content"><blockquote>
  The callback only sends a message to a task (outside of FreeRTOS) and
  then gives a xSemaphoreGiveFromISR to the same task.
</blockquote>
I don&#8217;t follow that sentence.  If the scheduler is running then there 
can&#8217;t be a task that is outside of FreeRTOS, and if there were such a 
task you would not be able to give it a semaphore (because it was 
outside of FreeRTOS so would not know what the semaphore was and the 
FreeRTOS scheduler would not be able to schedule it anyway).
<blockquote>
  What I was elluding to was that if all processing between OS and user 
  code actually takes 0.1s
</blockquote>
The time between a tick causing a timer to expire, and the timer&#8217;s 
callback executing, should be a tiny fraction of that time &#8211; provided 
there is nothing higher priority than the timer service task executing.
What are your configTIMER<em>TASK</em>PRIORITY and configMAX<em>PRIORITIES values? 
  Are there any tasks running at a priority above configTIMER</em>TASK_PRIORITY?
