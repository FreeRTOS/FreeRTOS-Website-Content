  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iweindesmedt">iweindesmedt</a> on February 27, 2017</div><div class="thread-post-content">Hi guys,
When creating a va_list containing a 64bit number, and later on popping this number off, it isnt the same value anymore.
Doing this before the kernel is started works like expected, but doing the same thing from within a thread fails.
The routine is something like this:
~~~
<h1>define BIGNUMBER    ( 1ULL &lt;&lt; 63 )</h1>
void step2(int ignoreme, va<em>list args){
    unsigned long long n = va</em>arg(args, unsigned long long);
<pre><code>if(n == BIGNUMBER){
    LED_GREEN();
}else{
    LED_RED();
}
</code></pre>
}
void step1(int ignoreme, &#8230;){
    va<em>list args;
    va</em>start(args, ignoreme);
    step2(ignoreme, args);
    va_end(args);
}
&#8230;
step1(1234, BIGNUMBER);
~~~
So all this does is passing a 64bit number through var args to a processing function that checks if the received value equals the value that was passed to it.
Attached is a quickly made MPLABX project demonstrating this if it&#8217;s not clear.
CPU is the PIC32MX695F512L, compiler XC32.
I think it has to be a FreeRTOS problem (or at least in its PIC32MX port) because again, it does work like expected when doing this if FreeRTOS is not used. Also it works when using another RTOS.
Anyone has ideas about what could be wrong?
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 27, 2017</div><div class="thread-post-content">The MZ port had a problem with byte alignment in an interrupt, but not 
in a task.  Is the code you post being called from a task?  Please check 
the stack alignment inside the task is 8-byte aligned and report back. 
Check the stack alignment on the first instruction in the task &#8211; before 
anything has been pushed to the stack by the compiler.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iweindesmedt">iweindesmedt</a> on February 27, 2017</div><div class="thread-post-content">When that code is being called from a task, it doesn&#8217;t work like expected.
When that code is NOT being called from a task, it does work like expected.
The addresses of an int in both the working and broken version:
working version: <code>-&gt;a0010b18</code> (% 8 is 0)
broken version: <code>-&gt;a0010b04</code> (%8 is 4)
Also when declaring the affected functions as <code>static</code>, the problem goes away.
You mention the MZ port, but I&#8217;m using the MX port. Not sure if that&#8217;s related.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 27, 2017</div><div class="thread-post-content">You are showing this test:
~~~
    unsigned long long n = va<em>arg(args, unsigned long long);
    if(n == BIGNUMBER){
        LED</em>GREEN();
    }else{
        LED_RED();
    }
~~~
But you do not tell what happens. Do you see an exception (alignment), or a red or a green LED?
And also: are you able to make a work-around, by calling <code>va_arg()</code> two times for the type <code>unsigned long</code>?
If I&#8217;m not mistaken:
~~~
    unsigned long n1 = va<em>arg( args, unsigned long );
    unsigned long n2 = va</em>arg( args, unsigned long );
<h1>if( ffconfigBYTE<em>ORDER == pdFREERTOS</em>BIG_ENDIAN )</h1>
<pre><code>unsigned long long n = ( ( ( unsigned long long )n1 ) &lt;&lt; 32 ) | ( unsigned long long ) n2;
</code></pre>
<h1>elif( ffconfigBYTE<em>ORDER == pdFREERTOS</em>LITTLE_ENDIAN )</h1>
<pre><code>unsigned long long n = ( ( ( unsigned long long )n2 ) &lt;&lt; 32 ) | ( unsigned long long ) n1;
</code></pre>
<h1>else</h1>
<pre><code>#error ffconfigBYTE_ORDER not defined
</code></pre>
<h1>endif</h1>
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iweindesmedt">iweindesmedt</a> on February 27, 2017</div><div class="thread-post-content">What happens:
&#8211; If the code is running from a task, the LED is RED, meaning the test failed.
&#8211; If the code is NOT running from a task, the LED is GREEN, meaning the test passed.
The <code>LED_</code> functions arent really relevant here, its just to have visual feedback on the if statement.
No runtime exceptions happen.
I ran your suggestion, but the behaviour is the same (as in: test fails when running from a task, passes when not running from a task).
With <code>BIGNUMBER</code> set to <code>0xFFFFFFFFFFFFFFFFUL</code>, debugger shows the following at the if statement:
<strong>From within a task</strong>
With the 1x <code>unsigned long long</code>: &lt;&#8211; FAILS
<code>n = 0xFFFFFFFFA5A5A5A5</code>
With the 2x <code>unsigned long</code>: &lt;&#8211; FAILS
<code>n1 = 0xA5A5A5A5</code>
<code>n2 = 0xFFFFFFFF</code>
<code>n = 0xFFFFFFFFA5A5A5A5</code>
Could the <code>0xA5</code> come from <code>#define tskSTACK_FILL_BYTE  ( 0xa5U )</code> (in tasks:c) ?
<strong>From outside a task (before starting kernel)</strong>
With the 1x <code>unsigned long long</code>: &lt;&#8211; PASSES
<code>n = 0xFFFFFFFFFFFFFFFF</code>
With the 2x <code>unsigned long</code>: &lt;&#8211; FAILS
<code>n1 = 0x00000000</code>
<code>n2 = 0xFFFFFFFF</code>
<code>n = 0xFFFFFFFF00000000</code>
Hope this is clear now
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iweindesmedt">iweindesmedt</a> on February 28, 2017</div><div class="thread-post-content">Think i found it&#8230; in this thread from 2011
http://www.freertos.org/FreeRTOS<em>Support</em>Forum<em>Archive/April</em>2011/freertos<em>FreeRTOS</em>7.0.0<em>PIC32</em>alignment<em>of</em>stack_4480228.html),
Richard suggests to add this line
<code>/* Ensure byte alignment is maintained when leaving this function. */
pxTopOfStack--;</code>
as the first line in the function <code>pxPortInitialiseStack</code> from <code>tasks.c</code>
In the current version (FreeRTOS 9.0.0), it is already there so I commented it, and the test passed. The 64bit parameter seems to be correctly aligned on the stack now.
I&#8217;m not sure which one of the two (<code>pxTopOfStack--</code> or not) is correct, but in the project I&#8217;m using this in (lots of hardware, libraries, modules,&#8230;) nothing is breaking so far. This makes me quite confident that this fix is okay, at least for the project I&#8217;m working on. But it might not be guaranteed for everyone&#8230;
What do you guys think? Is this compiler-related (I&#8217;m on XC32 v1.42) or even an error in the PIC32MX port?
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32MX: passing 64bit in a va_list doesnt work when the kernel is started</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 28, 2017</div><div class="thread-post-content">This is what the second post in this thread is referring to.  If you put 
a break point on the first instruction in a task (by which I mean the 
first assembly instruction &#8211; the function entry point &#8211; before any 
function pre-able added by the compiler) then stop on the break point &#8211; 
what is the stack pointer value?  The alignment is the important bit.
