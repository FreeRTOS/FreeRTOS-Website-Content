</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS Learning</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 28, 2017</div><div class="thread-post-content">Hi John, thanks for the clear pictures. That all looks correct to me.
As you can see, the <code>List_t</code> type has been implemented with a minimum RAM footprint. All items (elements) know to which list they belong, if any. Each node in the list is part its object.
For instance, an example taken from FreeRTOS+TCP: a network buffer is either linked into a free list or into a list of occupied buffers. In order to make it linkable, it gets a <code>ListItem_t</code> field:
~~~~
typedef struct xNETWORK<em>BUFFER
{
    ListItem</em>t xBufferListItem;   /* Used to reference the buffer form the free buffer list or a socket. <em>/
    uint32_t ulIPAddress;         /</em> Source or destination IP address, depending on usage scenario. <em>/
    uint8_t *pucEthernetBuffer;   /</em> Pointer to the start of the Ethernet frame. */
    &#8230;
} NetworkBufferDescriptor_t;
~~~~
Now <code>xBufferListItem</code> will always point to one of the two lists. You can add more <code>ListItem_t</code>&#8216;s to your objects to make them linkable to several lists.
The <code>List_t</code> type has been exposed in a header file, but normally developers will not make use of them. It is a type definition &#8220;internal to the kernel&#8221;. But you&#8217;re free to use it, of course. Note that with a few additions (wrappers), you can create both FIFO&#8217;s and stacks, based on <code>List_t</code>.
Other objects are more important for most developers: Queue&#8217;s, Semaphores, Event-Groups and the mechanisms to notify (and wake-up) a task.
