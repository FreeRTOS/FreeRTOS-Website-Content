I&#8217;m sorry but your question is difficult to understand.
<code>configTOTAL_HEAP_SIZE</code> is in <strong>number of bytes</strong>, not words:
~~~~
    static uint8<em>t ucHeap[ configTOTAL</em>HEAP_SIZE ];
~~~~
<code>xWantedSize</code>, the parameter of <code>pvPortMalloc</code> indicates the number of bytes that you want to allocate:
~~~~
    void *pvPortMalloc( size_t xWantedSize )
~~~~
The functions <code>pvPortMalloc()</code> and <code>vPortFree()</code> are alternatives for the C-functions <code>malloc()</code> and <code>free()</code>. The alternatives are created because they are thread-safe (not interrupt-safe). The standard C-functions can be used but they must be wrapped (this is done in heap_3.c).
It is up to you which module you want to use.
Here is an example:
~~~~
    /* Allocate 128 bytes: <em>/
    char *pcBuffer = ( char * )pvPortMalloc( 128 );
    if( pcBuffer != NULL )
    {
       /</em> Use the buffer: <em>/
        strcpy( pcBuffer, &#8220;Hello worldn&#8221; );
       /</em> And free it again: */
        vPortFree( pcBuffer );
    }
~~~~
I hope this answered your questions.

</div></div><div class="thread-post"><h3 class="thread-post-title">Heap_2.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 6, 2017</div><div class="thread-post-content">I would encourage you to use <code>heap_4.c</code> in stead of <code>heap_2.c</code>.
<code>heap_4.c</code>: the idea is as follows: in the beginning there is one large free block. You start allocating blocks from left to right. When a block of memory is freed, the algorithm looks if the adjacent blocks are also &#8216;free blocks&#8217;. If so, they will be joined to become one large free block. After freeing all individual blocks, the original situation will be restored: one big free block of memory.
<blockquote>
  My question is how the free space 25byte, 5byte and 35byte
  is recognised in the heap2 to coding file
</blockquote>
<code>heap_2.c</code> contains less code and in some cases it will be more efficient. It keeps a linked-list of free memory blocks, sorted on size. But it doesn&#8217;t bother re-joining those free memory blocks.
If you want to read more: have a look at all documentation, pointed out by Richard:
Dynamic memory allocation in C:
https://en.wikipedia.org/wiki/C<em>dynamic</em>memory_allocation
Specific to FreeRTOS:
