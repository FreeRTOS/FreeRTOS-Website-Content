  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AVR interrupt issue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gezab">gezab</a> on August 22, 2009</div><div class="thread-post-content">Hi,
I&#8217;m using FreeRTOS on an ATmega128 AVR. I have a problematic IRQ routine. Since this routine may cause a task switch, I&#8217;ve put an ASM wrapper around it like this:
SIG&#95;TIMER1&#95;CAPT&#95;Entry:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; portSAVE&#95;CONTEXT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; call&nbsp;&nbsp;&nbsp; SIG&#95;TIMER1&#95;CAPT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; tst&nbsp;&nbsp;&nbsp;&nbsp; r16
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; breq&nbsp;&nbsp;&nbsp; &#95;no&#95;context&#95;switch
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; call&nbsp;&nbsp;&nbsp; vTaskSwitchContext
&#95;no&#95;context&#95;switch:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; portRESTORE&#95;CONTEXT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; reti
In case of a task switch, it does not return with the I flag set, so IRQs remain disabled &#40;in spite of the RETI at the end&#41;, neither my timer capture IRQ nor the scheduler IRQ will be triggered anymore.
Anyway, if I modify the code just like it is in the preemptive scheduler call:
SIG&#95;TIMER1&#95;CAPT&#95;Entry:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; rcall&nbsp;&nbsp; SIG&#95;TIMER1&#95;CAPT&#95;Proc
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; reti
SIG&#95;TIMER1&#95;CAPT&#95;Proc:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; portSAVE&#95;CONTEXT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; call&nbsp;&nbsp;&nbsp; SIG&#95;TIMER1&#95;CAPT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; tst&nbsp;&nbsp;&nbsp;&nbsp; r16
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; breq&nbsp;&nbsp;&nbsp; &#95;no&#95;context&#95;switch
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; call&nbsp;&nbsp;&nbsp; vTaskSwitchContext
&#95;no&#95;context&#95;switch:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; portRESTORE&#95;CONTEXT
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ret
It works absolutely fine when calling it via a second stage.
Can you tell me what the problem is here, why it is not working when there&#8217;s no extra call?
Thanks and best regards,
Geza Balazs
</div></div><div class="thread-post"><h3 class="thread-post-title">AVR interrupt issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 22, 2009</div><div class="thread-post-content">I&#8217;ve just taken a quick look at the FreeRTOS WEB pages for the AVR and the source code for the AVR demo and cannot see that either the IAR or GCC ports use assembly wrappers for interrupts. Which compiler are you using? Is there a reason why you cannot write your interrupts as per the serial port example in the demo?
The AVR demos are some of the original demos, so maybe the compiler requires something different now?
Also there was a long explanation of the interrupt flag status during a context switch for the AVR ports on this forum a few months back, you might like to try searching for that.
</div></div><div class="thread-post"><h3 class="thread-post-title">AVR interrupt issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gezab">gezab</a> on August 22, 2009</div><div class="thread-post-content">Dave,
I&#8217;m using IAR EWAVR 4.20A. The reason why I&#8217;m using an ASM wrapper is that the main IRQ handler may cause a task switch and since this timer capture IRQ needs to be as fast as possible, and the context switch would save and restore all context data anyway, I&#8217;d like to get rid of saving and restoring context data at the beginning and the end of the service routine. The main handler function is written in C, with the &#95;&#95;task directive. It returns the need of the context switch in R16, and the wrapper handles the request appropriately.
Regarding the IF status I&#8217;m gonna look it up right away.
Thanks,
Geza
</div></div><div class="thread-post"><h3 class="thread-post-title">AVR interrupt issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 22, 2009</div><div class="thread-post-content">I don&#8217;t know if this is the problem, but one thing to remember is that vTaskSwitchContext assumes that all paths after it are identical, and may not actually return to your function until the task that was interrupted gets started again.&#40;I think this may depend on the port&#41;.
