  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Found bug in FreeRTOS port for Microchip PIC2</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/adamjcasey">adamjcasey</a> on October 20, 2009</div><div class="thread-post-content">Just wanted to pass along a bug I found in the port for the PIC24H &#40;from version FreeRTOSV5.4.2.&#41;  
The &#95;vPortYield assembly subroutine was putting &#35;32 into the SR to disable interrupts.&nbsp; However, this sets the CPU Interrupt Priority Level Status to level 1.&nbsp; This certainly disables the tick &#40;which is set to priority 1 in the port&#41; but not any other user settable interrupts.&nbsp; Since the default for the PIC is priority 4, this caused me to experience corruption in my context switches when tested under load.  
I changed it to set the CPU Interrupt Priority Level Status to level 7.&nbsp; This masks ALL user interrupts.&nbsp; I assume this is how it was intended to behave?  
Line 56 of the portasm&#95;PIC24.s file should change from:  
MOV &#35;32, SR  
to:  
MOV &#35;224, SR  
Also, page 16 of this document describes the register in question &#40;just for your info.&#41;<br />
<a href="http://ww1.microchip.com/downloads/en/DeviceDoc/70224c.pdf">http://ww1.microchip.com/downloads/en/DeviceDoc/70224c.pdf</a>  
</div></div><div class="thread-post"><h3 class="thread-post-title">Found bug in FreeRTOS port for Microchip PIC2</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on October 20, 2009</div><div class="thread-post-content">Please read the section about configKERNEL&#95;INTERRUPT&#95;PRIORITY on the following page: <a href="http://www.freertos.org/portpic24_dspic.html">http://www.freertos.org/portpic24_dspic.html</a> and note that only functions that have FromISR&#40;&#41; in their name can be called from interrupts above that priority. I think you have fixed a bug that does not exist.
</div></div><div class="thread-post"><h3 class="thread-post-title">Found bug in FreeRTOS port for Microchip PIC2</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/adamjcasey">adamjcasey</a> on October 21, 2009</div><div class="thread-post-content">Thanks for the reply.&nbsp; I read this link and it was informative.&nbsp; However, I still have a problem with it for the following reasons:  
1&#46; The configKERNEL&#95;INTERRUPT&#95;PRIORITY constant is not reflected in the assembly file.&nbsp; It is hard coded to CPU priority 1.<br />
2&#46; Perhaps there are good reasons for making a critical section &#8216;interruptible&#8217;, but I would argue that this is never the case during a &#42;context switch&#42;.&nbsp; This should undoubtedly be atomic.<br />
3&#46; If this is indeed an intended feature, then perhaps the kernel interrupt priority should default to the &#42;most safe&#42; priority of 7.&nbsp; Or at least the default for all the interrupt sources in the PIC24, which is 4  
I&#8217;m new to FreeRTOS but not RTOSes in general, so perhaps I don&#8217;t understand the utility of being able to interrupt a context swtich.
</div></div><div class="thread-post"><h3 class="thread-post-title">Found bug in FreeRTOS port for Microchip PIC2</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 21, 2009</div><div class="thread-post-content">The page that edwards3 linked to contains the following text: &amp;quot;Unfortunately, due to limitations in the GCC inline assembler, modifications to this value will necessitate a small update to the port source code with respect to the interrupt mask value &#40;accessed by inline assembler instructions&#41;.&amp;quot;&nbsp; The value it refers to is configKERNEL&#95;INTERRUPT&#95;PRIORITY.&nbsp; Also, I&#8217;m not sure the statement still holds true and the constant could probably be used indirectly in the asm file now, although this may make it less efficient.  
It is not normal to have configKERNEL&#95;INTERRUPT&#95;PRIORITY set to anything other than the lowest priority level.&nbsp; The PIC24 port allows interrupt nesting, but not a full nesting model as per the ports that also have configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY defined &#40;such as the PIC32 port&#41;.&nbsp; Therefore interrupt above configKERNEL&#95;INTERRUPT&#95;PRIORITY cannot cause a context switch, as you rightly point out.&nbsp; Again quoting from the linked page &amp;quot;However, such ISR&#8217;s cannot use the FreeRTOS.org API functions&amp;quot;.&nbsp;   
Hope this clarifies things.  
Regards.
