</div></div><div class="thread-post"><h3 class="thread-post-title">Pic24 Stack usage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 2, 2009</div><div class="thread-post-content">The PIC24 is &#8216;different&#8217; in that the stack grows up from low to high memory.&nbsp; I think all &#40;?&#41; the other supported architectures have the stack the other way around.&nbsp; That means these stack functions are not so well exercised on the PIC24.  
uxTaskGetStackHighWaterMark&#40;&#41; should return the minimum number of words &#40;NOT Bytes&#41; that have existed in the stack since the task was created.&nbsp; Therefore the closer the value is to zero the closer the task has come to overflowing its stack.&nbsp; I think the FreeRTOS viewer in MPLAB displays the high water mark value for each task.  
You can use the configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW to automatically catch stack overflows &#8211; set it to 2 for the best sensitivity.&nbsp; I think this should work on PIC24 too.  
The first item in the TCB points to the top of the associated task stack, but only when the task is not running.&nbsp; Its effectively the saved stack pointer for the task.  
Your pxStack and pxEndOfStack seem to be the correct distance apart.&nbsp; You say your stack is 300 words and the two pointers point 600 bytes apart, which is as expected on a 16 bit part.&nbsp; There is a discrepancy of 2 which probably comes from an &#40;unnecessary&#41;&nbsp; alignment adjustment but I would have to step through the code to be sure.  
The actual used stack at any time could be obtained from the current stack pointer value &#40;direct from the stack pointer register&#41; minus pxCurrentTCB-&amp;gt;pxStack.&nbsp; Remember this will give you bytes, not words.  
Regards.
