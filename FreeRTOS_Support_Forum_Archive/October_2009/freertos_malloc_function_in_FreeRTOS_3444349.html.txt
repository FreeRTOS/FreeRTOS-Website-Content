</div></div><div class="thread-post"><h3 class="thread-post-title">malloc function in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 1, 2013</div><div class="thread-post-content"><blockquote>
  1&#46; Does it mean I can&#8217;t use standard library sprintf as it is not thread safe?
</blockquote>
Doesn&#8217;t mean you can&#8217;t use it.&nbsp; Does mean you have to be very careful when using it.&nbsp; You can protect the non re-entrant parts of the standard library with a mutex for example, or wrap functions in a scheduler suspend/resume block.&nbsp; Some of the Newlib functions take a long time though, and using Newlib will seriously bloat your code.&nbsp; These, together with the re-entrancy problems, are reasons why most professional embedded compiler distributions based on GCC provide their own library implementations.&nbsp; Personally I try and avoid Newlib.  
If you just want a &#42;basic&#42; sprintf&#40;&#41; capability then search the FreeRTOS/Demo directory for a file called printf-stdarg.c.&nbsp; You will find lots of copies.&nbsp; Note that snprintf&#40;&#41; is defined but not implemented in that file though.  
<blockquote>
  2&#46; What is &#95;sbrk ? 
</blockquote>
Newlib needs porting to your platform, and that is one of the functions that needs porting &#40;like the read and write functions too if you try using standard out/in&#41;.&nbsp; Google will tell you more about it than you can ever wish to know.  
<blockquote>
  3&#46; Why sprintf should use malloc/free. &#40;To tell the truth I have stubbed &#95;sbrk with empty code doing nothing and returning NULL and everything worked fine. I assume sprintf uses malloc/free in some very special cases. I can dig it&#8217;s code but before going into it I want to see your suggestions as I think this is very common situation.&#41;
</blockquote>
I have done that before.&nbsp; Stub it out, set a break point in it, then test every path in your code that uses sprintf&#40;&#41; to see if the break point is ever hit.  
Just calling sprintf&#40;&#41; in your code will cause Newlib to bring in masses of other code into your binary, most of which you will not use.&nbsp; malloc&#40;&#41;/free&#40;&#41; is part of it, but it will also bring in lots and lots of floating point libraries which seems to be where the most bloat comes from.&nbsp; I think there are alternative integer only versions of printf and sprintf with slightly different names that avoid that though.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">malloc function in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 1, 2015</div><div class="thread-post-content">Hi,
A few more details, maybe:
In the code shown, you are protecting your calls to <code>malloc()</code>/<code>free()</code>. That doesn&#8217;t mean that other calls (from other tasks) will also be protected. The two stdlib functions are usually <strong>not</strong> task-safe.
Note that <code>malloc()</code>/<code>free()</code> can sometimes be called from the standard C library as well, e.g. by the <code>localtime()</code>/<code>gmtime()</code> functions.
I would not expect that KEIL&#8217;s <code>malloc()</code>/<code>free()</code> are &#8220;leaking&#8221; somehow. You could try it out by letting a single task run and do the above test a million times.
Like Richard, I would also recommend start using <code>portable/MemMang/heap_4.c</code> (or <code>heap_5.c</code> in case you don&#8217;t have &#8220;1 piece of RAM&#8221;).
You can forward the old calls to the FreeRTOS versions:
~~~~~
    /* Defining malloc/free should overwrite the
    standard versions provided by the compiler. <em>/
    void</em> malloc (size_t size)
    {
        /* Call the FreeRTOS version of malloc. */
        return pvPortMalloc( size );
    }
    void free (void* ptr)
    {
        /* Call the FreeRTOS version of free. */
        vPortFree( ptr );
    }
~~~~~
Regards.
