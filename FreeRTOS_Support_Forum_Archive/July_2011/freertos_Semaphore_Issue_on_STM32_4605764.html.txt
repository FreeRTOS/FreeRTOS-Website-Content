  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Semaphore Issue on STM32</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on July 13, 2011</div><div class="thread-post-content">I have several tasks running, and two peripherals on a single SPI port.&nbsp; I am using a semaphore to protect access to the SPI port so that one task that is using it finished before another task needs it &#40;regardless of which peripheral&#41;.&nbsp; I use xSemaphoreTake to &#8220;grab&#8221; the semaphore, and xSemaphoreGive to &#8220;release&#8221; it.&nbsp; This has been working fine for quite a while, but recently I added a new reference to one of the SPI peripherals and I&#8217;m getting an odd hang.&nbsp; It is hanging in the loop in vListInsert that has all the warnings about interrupt priorities on Cortex cores.&nbsp; But all of my interrupts are set to configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY &#40;15, lowest priority&#41;, and the hang doesn&#8217;t occur in an interrupt at all.&nbsp; What I see stepping through the debugger &#40;IAR&#41; is that one task grabs the SPI port, then a second task calls the xSemaphoreTake and blocks, as it should.&nbsp; But the first task then never gives up the semaphore, and as best I can tell no more task switches occur while the second task is blocked.&nbsp; I&#8217;m kind of at a loss on how to debug this.&nbsp; Anyone have any suggestions?
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore Issue on STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on July 13, 2011</div><div class="thread-post-content">Oddly enough, rearranging the declarations of my semaphores made the lockup go away.&nbsp; Very scary.
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore Issue on STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 13, 2011</div><div class="thread-post-content"><blockquote>
  But all of my interrupts are set to configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY &#40;15, lowest priority&#41;, and the hang doesn&#8217;t occur in an interrupt at all.
</blockquote>
You have to be very careful here on the STM32, as, unlike most &#40;all?&#41; other Cortex-M3 parts you normally have to manually set the number of pre-emption priority bits too.&nbsp; That need only be done once, during start up, before the kernel is started.&nbsp; Try placing a call to NVIC&#95;PriorityGroupConfig&#40; NVIC&#95;PriorityGroup&#95;4 &#41;; at the start of main&#40;&#41;.&nbsp; Getting the interrupt configuration wrong can have subtle side effects that you might not think are anything to do with the interrupts, but turn out to&nbsp; be.  
<blockquote>
  Oddly enough, rearranging the declarations of my semaphores made the lockup go away.&nbsp; Very scary.
</blockquote>
Yes that is scary.&nbsp; Presumably the semaphores are being created correctly before being used, otherwise they wouldn&#8217;t work at all.&nbsp; If you are saying that just changing their positioning in the memory map by changing where they are declared effects how they operate &#8211; then that could point to a problem in the linker script, overflowing heap, etc.&nbsp; Do you have stack checking turned on?&nbsp; It could just be a bug elsewhere in your application code that is corrupting RAM that was being used to hold the semaphore, but when you move it another variable is being corrupted instead.  
Regards.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore Issue on STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 13, 2011</div><div class="thread-post-content">I think it is mentioned on a lot of pages, but here is one to start with: <a href="http://www.freertos.org/portlpc2106.html">http://www.freertos.org/portlpc2106.html</a>&nbsp; Read the &#8220;Interrupt Service Routines&#8221; section, where it talks about an assembly wrapper.&nbsp; Depending on your version of GCC, you may find that the call to the C function from the assembly wrapper also needs to be done using an asm statement.  
Regards.
