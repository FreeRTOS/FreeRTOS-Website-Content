The application works great &#8211; until it crashes.<br />
This happens after processing typically 50 &#8211; 200 CAN messages.<br />
I&#8217;m getting a SIGSTOP, apparently in the IDLE task.<br />
The application receives CAN messages in the background.<br />
CAN ISR posts a msgobj&#35; &#40;one byte&#41; entry into a 5-deep queue.<br />
A task blocks on the queue, dequeues the msgobj&#35;,<br />
retrieves and processes the message, then blocks.<br />
Debugging the hardfault in CodeRed is not working,<br />
so I&#8217;ve added a few volatile flags to see what is active:<br />
&#45; the CAN ISR is not active<br />
&#45; the foreground CAN task is not active<br />
Task pane in CodeRed says IDLE task is active.  
I tried increasing the stack size without any effect.  
Any ideas what to try, or how to debug this ?<br />
Thanks in advance for any help &#33;&#33;&#33;<br />
Best Regards, Dave  
</div></div><div class="thread-post"><h3 class="thread-post-title">SIGSTOP from IDLE task (LPC11C14, CodeRed)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 11, 2011</div><div class="thread-post-content"><blockquote>
  Hi &#8211; I&#8217;m using FreeRTOS 7.0 on LPC11C14, using CodeRed toolchain.
</blockquote>
That is not an official port &#40;yet&#41; so the assistance I can give is very limited.  
<blockquote>
  The application works great &#8211; until it crashes.
</blockquote>
Stack sizes is one of the obvious ones, but it looks like you have tried that.&nbsp; You could turn the stack checking on, or try and determine the stack high water marks for more certainty &#40;there was another thread today on this forum about that&#41;.  
I&#8217;m not sure how the interrupts work in the port you are using &#8211; but if it is anything like the CM3/4 ports, then the most common cause of error is an interrupt service routine having an incorrect priority.&nbsp; If you port has a configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY or a configKERNEL&#95;INTERRUPT&#95;PRIORITY definition then take a look at point three here: <a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>  
Regards.  
Don&#8217;t they all ;o&#41;&nbsp; Of course, some work great longer than others.
</div></div><div class="thread-post"><h3 class="thread-post-title">SIGSTOP from IDLE task (LPC11C14, CodeRed)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dnadler">dnadler</a> on July 11, 2011</div><div class="thread-post-content">All tasks show plenty of available stack space,<br />
including the IDLE task &#40;thanks again for helping<br />
with that&#41;. A few more bits of information:  
configFreeRTOSConfig.h: &#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY 0 /&#42; 0 is highest &#8220;normal&#8221; M0 priority &#42;/<br />
configFreeRTOSConfig.h: &#35;define configKERNEL&#95;INTERRUPT&#95;PRIORITY 0 /&#42;&nbsp; &#42;/<br />
The systick builtin interrupt has a higher priority, but everything else is by definition lower priority &#40;numerically 0 or greater&#41;.  
no use of non-API functions in ISR; ISR only uses:<br />
&nbsp; portBASE&#95;TYPE taskUnblocked; // we hope that this will unblock CAN rx task…<br />
&nbsp; xQueueSendToBackFromISR&#40;CANrxQueue, &amp;msg&#95;obj&#95;num, &amp;taskUnblocked&#41;;<br />
&nbsp;&nbsp;&nbsp; if&#40;taskUnblocked==pdTRUE&#41; &#123;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; // tell FreeRTOS to switch context to the CAN rx task, which is not automatic…<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; vPortYieldFromISR&#40;&#41;; // because portSWITCH&#95;CONTEXT&#40;&#41;; is not implemented in this port…<br />
&nbsp;&nbsp;&nbsp; &#125;  
Any other ideas ?<br />
Thanks again,<br />
Best Regards, Dave
