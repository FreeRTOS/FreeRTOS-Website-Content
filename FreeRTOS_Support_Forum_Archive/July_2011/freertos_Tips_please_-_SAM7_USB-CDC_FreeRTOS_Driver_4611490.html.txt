  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Tips please 🙂 SAM7 USB-CDC FreeRTOS Driver</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ckronen">ckronen</a> on July 18, 2011</div><div class="thread-post-content">Dear Community,  
since I need a USB-CDC Driver for some projects, I tried the USB-CDC driver from the demo &#8220;lwIP&#95;Demo&#95;Rowley&#95;ARM7&#8221;.  
In the description, it says that it does not have a great performance due to heavy queue usage. I benchmarked the RX performance and compared it to the driver provided by ATMEL. The results when I do not process the received bytes any further:  
FreeRTOS CDC driver: ~71 kbyte/s &#40;RX&#41;<br />
ATMEL CDC driver: ~850kbyte/s &#40;RX&#41;, which is pretty close to the theoretical maximum  
Since the ~71 kbyte/s are not sufficient, I thought about implementing the ATMEL driver into the FreeRTOS environment. The biggest difference I can see, is how the received data gets taken out of the endpoint FIFO:  
FreeRTOS: The bytes are taken out of the FIFO in a Task and written to a queue &#40;byte for byte&#41;  
ATMEL: The bytes from the FIFO are copied into a buffer during the Interrupt  
What walls would I run into when taking the ATMEL driver ? Where do you see the problems ?   
Thank you very much for reading all this and giving me suggestions :-&#41;  
Greetings,  
Chris
</div></div><div class="thread-post"><h3 class="thread-post-title">Tips please 🙂 SAM7 USB-CDC FreeRTOS Driver</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 18, 2011</div><div class="thread-post-content">The biggest issue with a single buffer is that if a second message shows up before the &#8220;USB Task&#8221; processes the previous one, you need to throw away the new message. If the task can make sure this doesn&#8217;t happen &#40;limited tasks in competition to it, and not needing to wait for some other task/resource&#41; then it might not be a serious issue. The driver &#40;I am not familiar with it&#41; might be built with this sort of assumption, and maybe your application allows it too.  
One solution to this is to have several buffers that you use in rotation, so that if the task isn&#8217;t done yet, you still have a place to put the data rather than just discarding it. You will still have the possibility that you fall far enough behind that all the buffers are in use, but you can greatly cut down the risk, or the level of analysis needed to prove that you can generally keep up. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Tips please 🙂 SAM7 USB-CDC FreeRTOS Driver</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ckronen">ckronen</a> on July 20, 2011</div><div class="thread-post-content">Thanks for your answer,

I think before I port something new I will try to find out why the FreeRTOS USB-CDC driver is so slow.

</div></div><div class="thread-post"><h3 class="thread-post-title">Tips please 🙂 SAM7 USB-CDC FreeRTOS Driver</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 2, 2012</div><div class="thread-post-content">Hi Chris,  
Although your post was quite some time ago:<br />
I think the FreeRTOS USB-CDC was slow because the data were stored/queued byte-per-byte<br />
You better store packages of 64 bytes at a time, along with a length field<br />
Try to wake up the USB task from the USB-EP interrupt, both for Rx as well as Tx events, using xSemaphoreGiveFromISR&#40;&#41;.<br />
It is safer to keep interrupts short, the price is low: only a few uS delay between interrupt and wakeup.<br />
In this way I managed to get a throughput of a few hundred kB/sec &#40;on a slower UC3A&#41;  
Best regards, Hein
