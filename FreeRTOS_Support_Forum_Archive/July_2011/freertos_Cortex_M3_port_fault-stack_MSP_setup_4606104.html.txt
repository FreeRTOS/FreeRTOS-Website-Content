  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Cortex M3 port: fault-stack MSP setup</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dnadler">dnadler</a> on July 13, 2011</div><div class="thread-post-content">Hi Richard &#8211; Perhaps I&#8217;m missing something here…  
The M3 port uses the PSP &#8220;process&#8221; stack for normal processing<br />
as is recommended by ARM. In the event of a fault, the processor<br />
switches to the MSP stack. So, to handle a fault, MSP needs to<br />
be set up to point to a small dedicated stack.  
In your v7 M3 gcc port.c you have:  
<pre><code>void vPortStartFirstTask( void )
{
    __asm volatile(
                    " ldr r0, =0xE000ED08   n" /* Use the NVIC offset register to locate the stack. */
                    " ldr r0, [r0]          n"
                    " ldr r0, [r0]          n"
                    " msr msp, r0           n" /* Set the msp back to the start of the stack. */
                    " cpsie i               n" /* Globally enable interrupts. */
                    " svc 0                 n" /* System call to start first task. */
                    " nop                   n"
                );
}
</code></pre>
That would cause a fault to overwrite whatever is at the<br />
base of the &#40;linker allocated&#41; stack pool, no ?<br />
For my M0 port, I changed it to this:  
<pre><code>void vPortStartFirstTask( void )
{
  #ifdef DRN_print_diagnostics
    int answer = 46;
  #endif
  // Ensure that normal processing runs on PSP ("Process" Stack
  // Pointer, in "thread mode" or "normal mode"). Processor starts
  // out of reset using MSP, so unless the RTL has already switched, we
  // need to switch here.
  debug_printf("CONTROL register=%08x, stack in use is %sn",
               __get_CONTROL(), (__get_CONTROL()&amp;0x2) ? "PSP, OK." : "MSP, need to switch.");
  if( (__get_CONTROL()&amp;0x2) == 0 ) {
    // Ooops, we're using MSP "Main" Stack Pointer
    // Set up "process" stack pointer and switch to it
    __set_PSP(__get_MSP()); // copy current stack pointer value into PSP
    __set_CONTROL(0x00000002); // switch to "process" stack pointer PSP
    debug_printf("After stack pointer switch: CONTROL register=%08x, stack in use is %sn",__get_CONTROL(), (__get_CONTROL()&amp;0x2)?"PSP":"MSP");
    debug_printf("The answer is %d (should be 46)n",answer); // verify stack is not munged
  }
  // Handler mode (as in processing a hard fault) ALWAYS uses MSP
  // ('Main' stack pointer). So, in order for a fault to be trapped
  // safely, MSP must point to a dedicated and safe stack area.
  // Set MSP to a "safe reserved area", so an exception can run safely...
  #define FAULT_STACK_SIZE 100
  static int MSP_stack[FAULT_STACK_SIZE];
  __set_MSP((int)&amp;MSP_stack[FAULT_STACK_SIZE-2]);
    __asm volatile(
        " ldr r0, =0x0      n" /* cm0 has fixed vector table at address 0x0 */
        " ldr r0, [r0]      n"
// DRN: Next line is hazardous; MSP needs to point to a separate
// DRN: safe stack, otherwise a fault will clobber stack of someone else...
// DRN: NO:  " msr msp, r0       n" /* Set the msp back to the start of the stack. */
        " cpsie i           n" /* Globally enable interrupts. */
        " svc 0             n" /* System call to start first task. */
        " nop               n"
    );
}
</code></pre>
Do I have this right ?<br />
Also, does the built-in debug support use the MSP<br />
&#40;for example, to support semi-hosted IO, implemented<br />
via BKPT instructions&#41; ?  
Thanks as always,<br />
Best Regards, Dave  
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 port: fault-stack MSP setup</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 14, 2011</div><div class="thread-post-content">Without first refamiliarising myself with the M0 I can&#8217;t comment on the M0 code &#8211; as I say &#8211; that is not official code &#40;although M0 is on the near term road map&#41;.  
Regarding your question  
<blockquote>
  That would cause a fault to overwrite whatever is at the<br />
  base of the &#40;linker allocated&#41; stack pool, no ?
</blockquote>
Yes &#8211; that is absolutely correct and the intent.&nbsp; The stack allocated by the linker is only used by main&#40;&#41;, once the kernel is running, the stacks used by the tasks are allocated from the FreeRTOS heap &#8211; and the stacks used by interrupts/exceptions is the stack that was &#42;previously&#42; used by main&#40;&#41;.&nbsp; As main&#40;&#41; will never run again, the stack is simply re-used for a different purpose.  
Regards.
