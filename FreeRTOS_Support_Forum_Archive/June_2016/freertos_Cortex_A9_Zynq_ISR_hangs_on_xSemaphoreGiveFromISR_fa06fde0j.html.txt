There is clearly something I don&#8217;t quite get yet.  Any pointers would be helpful.
I have a DMA program that runs on the Zynq without FreeRTOS, and it runs on FreeRTOS if I use a callback function from the ISR.  The problem is, it can&#8217;t be a FreeRTOS task.  So I followed the example in Mastering the FreeRTOS Kernel in the interrupt section and I can&#8217;t understand why the application hangs in the call to xSemaphoreGiveFromISR.  
There are three tasks running and the isr handler task has the highest priority
~~~
<h1>define mainHANDLE<em>TASK</em>PRIORITY            ( tskIDLE_PRIORITY + 3 )</h1>
<h1>define mainQUEUE<em>RECEIVE</em>TASK<em>PRIORITY     ( tskIDLE</em>PRIORITY + 2 )</h1>
<h1>define mainQUEUE<em>SEND</em>TASK<em>PRIORITY        ( tskIDLE</em>PRIORITY + 1 )</h1>
~~~
The semaphore is defined as
~~~
static SemaphoreHandle_t xBinarySemaphore = NULL;
~~~
main is very simple
~~~
int main( void )
{
    prvSetupHardware();
    prvSetupDMA();

~~~
static void vHandleTask (void *pvParameters)

        xSemaphoreTake (xBinarySemaphore, portMAX_DELAY);
        printf(&#8220;Interrupt Handler rn&#8221;);
    }
}
~~~

</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex A9/Zynq ISR hangs on xSemaphoreGiveFromISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 2, 2016</div><div class="thread-post-content">Hi Sting,
I don&#8217;t know how your printf() is implemented, but the standard implementation is normally not interrupt-proof. I would try to debug it by setting some volatile variables and log those from a normal task.
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex A9/Zynq ISR hangs on xSemaphoreGiveFromISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/raymadigan">raymadigan</a> on June 2, 2016</div><div class="thread-post-content">It hangs when I comment out the printf statements.  It doesn&#8217;t hang with the printf statements when I use the callback.  The only time it hangs is when I use the BinarySemaphore to wake up the handler.
This interrupt is an AXI interrupt generated by the logic in the fpga.  Maybe the handling has to be different.  The handling of memory has to be different for the buffer descriptors because the interconnects in the fpga address memory fro 0x100000 to 0x1FFFFF.  
Since the callback mechanism seems to work I will temporarily move the wakeup of the handler to the callback routine so I can handle the data management in a task until I figure out how to debug this.
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex A9/Zynq ISR hangs on xSemaphoreGiveFromISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 2, 2016</div><div class="thread-post-content">I would agree with Hein, calling printf() from an interrupt is going to cause more problems that it solves.  I would suggest placing a breakpoint on the xSemaphoreGiveFromISR() call and stepping through the code to see what it does, how far it gets, etc.
The Cortex-A port has specific requirements for how interrupts are installed.  Are you using the FreeRTOS interrupt handler, and installing the interrupts as described on the following page: http://www.freertos.org/Using-FreeRTOS-on-Cortex-A-Embedded-Processors.html
Regards.
