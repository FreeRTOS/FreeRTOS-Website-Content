  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem debugging FreeRTOS application with GDB</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alexc63">alexc63</a> on June 23, 2016</div><div class="thread-post-content">Hello everybody,
I have the following problem.
The scenario first:
* Custom board (fully tested) with Kinetis K10 MCU
* Kinetis Design Studio 3.0.0
* Pemicro Multilink Universal debugger
* FreeRTOS 9.0.0 (I&#8217;m using the GCC / Cortex M3 port)
* I&#8217;m not using Processor Expert
The problem: when debugging a program with FreeRTOS, I can set breakpoints and step through code, but when I try to return from a function by stepping on its last instruction (i.e. closing curly bracket), gdb crashes. In the console I get the following errors:
<em>Unable to go into background mode.
Error communicating to target processor &#8211; try a RESET.
PE-ERROR: TARGET IS RUNNING</em>
The same program works as expected if I let it run without debugging. Please note that when I debug a program that doesn&#8217;t use FreeRTOS everything works like a charm.
In assembler, the offending instruction that causes the crash to happen is &#8216;mov sp,r7&#8217;. I noticed that at this point the PSP is used instead of MSP. After stepping on this instruction the crash occurs and the disassembly window shows: -__isr_vector followed by rows of <undefined instruction>: 0xffffffff.
Also, in FreeRTOSConfig.h, I have defined configTASK<em>RETURN</em>ADDRESS   0  /* return address of task is zero */ as suggested in some posts.
Thank you in advance for your help, which would be greatly appreciated.
Alex

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem debugging FreeRTOS application with GDB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xz8987f">xz8987f</a> on June 23, 2016</div><div class="thread-post-content">Hi Alex,
I don&#8217;t have a K10, but I don&#8217;t think it is a hardware problem or like that. If you have access to a Segger J-Link, then you could try a different debug connection. The message &#8216;unable to go into background mode&#8217; indicates that the debugger is not able to talk anymore to the target. This typically happens with low voltage (power supply problem).
