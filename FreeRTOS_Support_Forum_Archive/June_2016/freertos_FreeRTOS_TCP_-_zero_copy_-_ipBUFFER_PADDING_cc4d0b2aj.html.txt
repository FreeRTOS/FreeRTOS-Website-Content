uint8<em>t fillPacket[ ipconfigPACKET</em>FILLER_SIZE ];
It&#8217;s part of the socket definition.  
Question &#8230; Why have a socket element size be defined by a network buffer define?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_TCP &#8211; zero copy &#8211; ipBUFFER_PADDING</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 19, 2016</div><div class="thread-post-content">I think this is to ensure members of the packet structure that appear later on become aligned in a way that is more efficient on less capable architectures.  It is also required by some DMA peripherals on some hardware (being somewhat non-specific) which require more than 4-byte alignment.
There is a comment that may help in FreeRTOS_IP.h, but I think the comment is actually out of date, but does show that at some point the definition was only 2.  I have marked the comment as invalid, so it will get updated too.  As it appears now:
~~~
/* Space left at the beginning of a network buffer storage area to store a
pointer back to the network buffer.  Should be a multiple of 8 to ensure 8 byte
alignment is maintained on architectures that require it.
In order to get a 32-bit alignment of network packets, an offset of 2 bytes
would be desirable, as defined by ipconfigPACKET<em>FILLER</em>SIZE.  So the malloc&#8217;d
buffer will have the following contents:
    uint32<em>t pointer;   // word-aligned
    uchar</em>8 filler[6];
    &lt;&lt; ETH-header >>    // half-word-aligned
    uchar<em>8 dest[6];    // start of pucEthernetBuffer
    uchar</em>8 dest[6];
    uchar16<em>t type;
    &lt;&lt; IP-header >>     // word-aligned
    uint8</em>t ucVersionHeaderLength;
    etc
 */
~~~
I have also queried the your other question about fillPacket (which doesn&#8217;t comply with the naming standard) so will get back to you on that, but as it is not used anywhere, I think it is in place to ensure the alignment of the buffer that follows it in the structure.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_TCP &#8211; zero copy &#8211; ipBUFFER_PADDING</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 21, 2016</div><div class="thread-post-content">Hi Joe,
I&#8217;m sorry that I kept silent for so long, but it&#8217;s summer holiday time here 🙂
The reason to have the pointer located before the network buffer is the zero-copy option for UDP. A UDP payload buffer can be translated to a network buffer and vice versa with these complementary functions:
~~~~
NetworkBufferDescriptor<em>t *pxUDPPayloadBuffer</em>to<em>NetworkBuffer( void *pvBuffer )
uint8</em>t *pcNetworkBuffer_to_UDPPayloadBuffer( NetworkBufferDescriptor_t *pxNetworkBuffer )
~~~~
You are right that <strong>for some platforms</strong>, the extra 4 bytes in front of the network buffer are not essential. And so this declaration:
~~~~
    #define ipBUFFER<em>PADDING ( 8u + ipconfigPACKET</em>FILLER_SIZE )
~~~~
may sometimes be replaced with:
~~~~
    #define ipBUFFER<em>PADDING ( 4u + ipconfigPACKET</em>FILLER_SIZE )
~~~~
I don&#8217;t mind allowing <code>ipBUFFER_PADDING</code> to get overridden by a new item called <code>ipconfigBUFFER_PADDING</code> from <code>FreeRTOSIPConfig.h</code>:
~~~~
<h1>if( ipconfigBUFFER_PADDING != 0 )</h1>
<pre><code>#define ipBUFFER_PADDING    ipconfigBUFFER_PADDING
</code></pre>
<h1>else</h1>
<pre><code>#define ipBUFFER_PADDING    ( 8u + ipconfigPACKET_FILLER_SIZE )
</code></pre>
<h1>endif</h1>
~~~~
The following code was introduced just to avoid an exception:
~~~~
    /* Here a pointer was placed to the network descriptor,
      As a pointer is dereferenced, make sure it is well aligned */
    if( ( ( ( uint32_t ) pucBuffer ) &amp; ( sizeof( pucBuffer ) &#8211; 1 ) ) == 0 )
~~~~
We were in doubt about either using the live test or use a <code>configASSERT()</code>.
But as <code>pxUDPPayloadBuffer_to_NetworkBuffer</code> may also be called from user space, we decided to have the above test.
As Richard wrote, the &#8220;more than 4-byte&#8221; alignment is required by some DMA&#8217;s.
The extra 2 bytes <code>ipconfigPACKET_FILLER_SIZE</code> were indeed introduced to get a proper 32-byte alignment for all 32-bit fields in the IP- and protocol headers. Many EMAC&#8217;s have an option that says: &#8220;skip the first 2 bytes&#8221; (as you mentioned).
FreeRTOS+TCP is still being developed further: it will soon have the possibility to use IPv6 headers, and also allow for multiple interfaces (EMAC&#8217;s). We&#8217;re still looking for more users who want to test the new (still experimental) version.
If you want to use IPv6, the extra 4 bytes will also get a purpose: store the IP-type in case of a IPv4 packet.
Regards.
