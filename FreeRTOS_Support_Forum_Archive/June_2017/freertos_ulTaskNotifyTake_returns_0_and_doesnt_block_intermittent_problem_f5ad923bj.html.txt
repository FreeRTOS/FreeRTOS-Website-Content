  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">ulTaskNotifyTake returns 0 and doesn&#8217;t block, intermittent problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/odman">odman</a> on June 22, 2017</div><div class="thread-post-content">Hi. My tasks implement a state machine and the task loop looks like this:
~~~
while(ulTaskNotifyTake( pdFALSE, portMAX<em>DELAY))
  {
  }
~~~
I should mention that I&#8217;ve also tried with binary semaphores and also with a binary notify, i.e. ulTaskNotifyTake( pdTRUE, portMAX</em>DELAY). with the same results I&#8217;m describing here.
The problem is that the while loop exits with return value 0 without blocking. It happens occasionally. I have looked for stack errors and other obvious problems but have failed to find anything.
Inside the function:
<code>uint32_t ulTaskNotifyTake( BaseType_t xClearCountOnExit, TickType_t xTicksToWait )</code>
at entry:
~~~
xClearCountOnExit == 0 
xTicksToWait == 0xffffffff
pxCurrentTCB->ucNotifyState == 0
pxCurrentTCB->ulNotifiedValue == 0
ulReturn = 0
~~~
Top section:
~~~
        taskENTER<em>CRITICAL();
        {
            /* Only block if the notification count is not already non-zero. */
            if( pxCurrentTCB->ulNotifiedValue == 0UL ) // ==> true
            {
                /* Mark this task as waiting for a notification. */
                pxCurrentTCB->ucNotifyState = taskWAITING</em>NOTIFICATION;  // ==> set to 1
<pre><code>            if( xTicksToWait &gt; ( TickType_t ) 0 ) // ==&gt; true
            {
                prvAddCurrentTaskToDelayedList( xTicksToWait, pdTRUE );
                portYIELD_WITHIN_API(); // NOT BLOCKING
</code></pre>
~~~
Bottom section:
 ~~~
           ulReturn = pxCurrentTCB->ulNotifiedValue; // ==> 0
<pre><code>        if( ulReturn != 0UL )  // ==&gt; false
</code></pre>
/snip/
            pxCurrentTCB->ucNotifyState = taskNOT<em>WAITING</em>NOTIFICATION; // ==> 0
        return ulReturn; // ==> 0
~~~
The task while loop now exits and you get stuck in the task exit trap.
Any suggestions what might be going wrong? I&#8217;m using FreeRTOS 9.0.0 and it&#8217;s working fine most of the time. Thanks!
Knut
</div></div><div class="thread-post"><h3 class="thread-post-title">ulTaskNotifyTake returns 0 and doesn&#8217;t block, intermittent problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 24, 2017</div><div class="thread-post-content">The first thing that comes to mind would be an interrupt priority 
problem.  If that is not the case then I will have to do a more detailed 
study to see how what you describe could occur.  First the interrupt 
priority question:
Which device are you running FreeRTOS on?
If you are using a Cortex-M, RX100/200/600 or PIC32, does your system 
include any interrupts that use the FreeRTOS API?
If so, what is the/are the interrupt priorities set to, and what is your 
configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY value set to?

  Which device are you running FreeRTOS on?
  SiLabs EFR32FG1P, Cortex M4 based chip.
  If you are using a Cortex-M, RX100/200/600 or PIC32, does your system 
  include any interrupts that use the FreeRTOS API?
  Yes. Based on a previous discussion I use the deferred ISR method of the timer task for all my ISRs that access FreeRTOS API. There is one exception to this rule. SiLabs API requires a buffer to be returned in an ISR callback during reception. I&#8217;m doing this with my own memory pool which contain pre-allocated buffers from FreeRTOS heap4.c. Thus no FreeRTOS API function is called in runtime.
  If so, what is the/are the interrupt priorities set to, and what is your 
  configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY value set to?
  ~~~
</blockquote>
<h1>define configKERNEL<em>INTERRUPT</em>PRIORITY           ( 255 ) /* equivalent to 0xe0 (224d), or priority 7. (highest, only 3-bits) */</h1>
<h1>define configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY      ( 191 ) /* equivalent to 0xa0 (160d), or priority 5. */</h1>
&#8230;
uint32<em>t max</em>syscall<em>prio = configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY >> (8 &#8211; __NVIC<em>PRIO</em>BITS);
&#8230;
NVIC<em>SetPriority(GPIO</em>ODD<em>IRQn, max</em>syscall<em>prio + 1);
  NVIC</em>SetPriority(TIMER0<em>IRQn, max</em>syscall<em>prio + 0);
~~~
All my interrupts are set to the same priority as configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY or (configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY +1), e.g. one lower priority on ARM CM4.
