  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">+FAT ff_filelength() returns Error when file length is >2GB</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sonycman">sonycman</a> on June 5, 2017</div><div class="thread-post-content">Hello.
The ff<em>filelength() function incorrectly interprets big files (>2GB) length as error and returns zero.
This is because it uses MSB of the length value returned by FF</em>FileSize() as an error flag, which in case of the big files leads to misinterpretation of correct value as an erratic.
Regards
Vladimir.
</div></div><div class="thread-post"><h3 class="thread-post-title">+FAT ff_filelength() returns Error when file length is >2GB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 6, 2017</div><div class="thread-post-content">Vladimir, this is indeed something to be finished: files longer than 2 GB. 
Throughout the library, signed 32-bit values are used to indicate the length, and negative values are interpreted as an error.
lseek also has an intrinsic problem: 
~~~
    long lseek(int fd, long offset, int whence);
~~~
FreeRTOS+TCP is using the same syntax for <code>ff_fseek()</code>.
The Posix varian is ok, if <code>off_t</code> is a 64-bit signed integer:
~~~
    off<em>t lseek(int fd, off</em>t offset, int whence);
~~~
The +FAT library will not force people to include 64-bit arithmetic. 
Right now I have a 2 GB file ( -2,147,483,648 bytes 🙂 ) on an SD-card and I will test it. To be continued.
</div></div><div class="thread-post"><h3 class="thread-post-title">+FAT ff_filelength() returns Error when file length is >2GB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sonycman">sonycman</a> on June 6, 2017</div><div class="thread-post-content">Hello, Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">+FAT ff_filelength() returns Error when file length is >2GB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 6, 2017</div><div class="thread-post-content">All right, I made some minor changes: <code>ff_filelength()</code> will return correct values for files between 0 bytes and 4 GB.
A return value of 0 can mean two things: the size is either 0, or the handle is invalid.
~~~
size_t uxLength;
<pre><code>/* Clear errno. */
stdioSET_ERRNO( 0 );
uxLength = ff_filelength( pxFile );
if( ( uxLength != 0 ) || ( stdioGET_ERRNO() == 0 ) )
{
    /* Length equals to uxLength. */
}
else
{
    /* Invalid handle. */
}
</code></pre>
~~~
Also I introduced a new low-level function that splits up the result and the file length:
~~~
    /* Use the following function in case files may get larger than 2  GB. */
    int32_t FF_GetFileSize( FF_FILE *pFile, uint32_t *pulSize );
~~~
And more importantly: <code>FF_Seek()</code> now works correctly with sizes and offsets larger than 2GB.
Here below I attach 3 files, which are a copy of the &#8216;160919&#8217; release along with mentioned changes.
~~~
    ff<em>file.c
    ff</em>stdio.c
    include/ff_file.h
~~~
Hein Tibosch
