  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32F100RCT MCU + STM32CubeMX project: prvPortStartFirstTask() crash </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/anani">anani</a> on June 15, 2017</div><div class="thread-post-content">Hi All,
I am busy debugging STM32F100RCT MCU project. The project framework and FreeRTOS code are generated by STM32CubeMX. I was debugging (ST-Link) without any FreRTOS related issues for a couple of weeks. Suddenly prvPortStartFirstTask() execution crashed&#8230; I have checked some similar issue posts published here, but still no clue. It looks like I have all settings correct:
static void prvPortStartFirstTask( void )
{
    __asm volatile(
                    &#8221; ldr r0, =0xE000ED08   n&#8221; /* Use the NVIC offset register to locate the stack. <em>/
                    &#8221; ldr r0, [r0]          n&#8221;
                    &#8221; ldr r0, [r0]          n&#8221;
                    &#8221; msr msp, r0           n&#8221; /</em> Set the msp back to the start of the stack. <em>/
                    &#8221; cpsie i               n&#8221; /</em> Globally enable interrupts. <em>/
                    &#8221; cpsie f               n&#8221;
                    &#8221; dsb                   n&#8221;
                    &#8221; isb                   n&#8221;
                    &#8221; svc 0                 n&#8221; /</em> System call to start first task. */
                    &#8221; nop                   n&#8221;
                );
}
ASM stepping is stacked at  line: svc 0 n&#8221; /* System call to start first task. */, when I tried to run the debbuging again, it crashes.
In FreeRTOSConfig.h I have what is required:
/* USER CODE BEGIN 1 */   
<h1>define configASSERT( x ) if ((x) == 0) {taskDISABLE_INTERRUPTS(); for( ;; );}</h1>
/* USER CODE END 1 <em>/
/</em> Definitions that map the FreeRTOS port interrupt handlers to their CMSIS
standard names. */
<h1>define vPortSVCHandler    SVC_Handler</h1>
<h1>define xPortPendSVHandler PendSV_Handler</h1>
/* IMPORTANT: This define MUST be commented when used with STM32Cube firmware, 
              to prevent overwriting SysTick<em>Handler defined within STM32Cube HAL */
/* #define xPortSysTickHandler SysTick</em>Handler */
And in port.s I have the handler:
void vPortSVCHandler( void )
{
    __asm volatile (
                    &#8221;   ldr r3, pxCurrentTCBConst2      n&#8221; /* Restore the context. <em>/
                    &#8221;   ldr r1, [r3]                    n&#8221; /</em> Use pxCurrentTCBConst to get the pxCurrentTCB address. <em>/
                    &#8221;   ldr r0, [r1]                    n&#8221; /</em> The first item in pxCurrentTCB is the task top of stack. <em>/
                    &#8221;   ldmia r0!, {r4-r11}             n&#8221; /</em> Pop the registers that are not automatically saved on exception entry and the critical nesting count. <em>/
                    &#8221;   msr psp, r0                     n&#8221; /</em> Restore the task stack pointer. */
                    &#8221;   isb                             n&#8221;
                    &#8221;   mov r0, #0                      n&#8221;
                    &#8221;   msr basepri, r0                 n&#8221;
                    &#8221;   orr r14, #0xd                   n&#8221;
                    &#8221;   bx r14                          n&#8221;
                    &#8221;                                   n&#8221;
                    &#8221;   .align 2                        n&#8221;
                    &#8220;pxCurrentTCBConst2: .word pxCurrentTCB             n&#8221;
                );
}
Please help!
Best regards,
Anani

</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F100RCT MCU + STM32CubeMX project: prvPortStartFirstTask() crash </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 15, 2017</div><div class="thread-post-content">The SVC instruction effectively calls vPortSVCHandler(), which in turn 
starts the first task running.  Often people step through to the SVC 
instruction when debugging and think the crash is occurring there &#8211; 
whereas in fact unknown to them the debugger has started a task 
executing and the crash actually happens in the task.
First set a break point in vPortSVCHandler() to see if it gets hit.  If 
it does step through that program to see which task runs first.  If you 
actually get into a task then something is going wrong in a task, not 
when starting the scheduler.

</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F100RCT MCU + STM32CubeMX project: prvPortStartFirstTask() crash </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 16, 2017</div><div class="thread-post-content">You need to know where the MCU is jumping to when it calls the SVC 
instruction.  Interrupts must be enabled at that point as the asm code 
prior to the SVC call enables interrupts.  Could it be there is another 
SVC handler?  Perhaps one defined by the cube software?
Something is happening when SVC is called.  The CPU is branching 
somewhere.  You need to find where.  Interrupt priorities are not the 
problem at that point in the code, but could be later if the SVC is 
actually starting the scheduler running and you just don&#8217;t realise it.
Do you have a break point in your hard fault handler too?  Could you be 
ending up in a hard fault?
