  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC32 Non-Atomic Interrupt clear </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/grahamfclark">grahamfclark</a> on December 23, 2008</div><div class="thread-post-content">A post was made at the Microchip PIC32 forum regarding the non-atomic behaviour of certain PIC32 instructions and their danger. In particular the clearing of interrupt flags. 
The post was made by someone working for AVIS-RT rtos and is entitled &quot;Wrong way to clear an interrupt flag, very important &quot;
As a user of the FreeRTOS code I&#8217;d like to know if it also could be affected in some way?
The post is at http://forum.microchip.com/tm.aspx?m=391938&amp;mpage=1&amp;key=&amp;&#35;391938 
Graham
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Non-Atomic Interrupt clear </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on December 23, 2008</div><div class="thread-post-content">The MPLAB C32 compiler comes with all the macros you need, so I don&#8217;t see what the fuss is all about on that thread.
FreeRTOS uses just one timer, and the interrupt is cleared using the compiler provided macro mT1ClearIntFlag&#40;&#41;, which is defined as:
&#35;define mT1ClearIntFlag&#40;&#41;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#40;IFS0CLR = &#95;IFS0&#95;T1IF&#95;MASK&#41;
which is fine as far as I can see.
The demo &#40;which is not part of the kernel code&#41; uses a serial port interrupt that is cleared with mU2TXClearIntFlag so that is ok, and two high frequency timers that are cleared by writing to the IFS0bits register, so these could probably be improved although I would have to look at the code generated for them.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Non-Atomic Interrupt clear </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/grahamfclark">grahamfclark</a> on December 23, 2008</div><div class="thread-post-content">No I agree the thread seems a bit alarmist. I tend to use the macros in my code which are atomic.&nbsp; 
I had a look a the port.c and, as you mention, it does use of IFS0bits in clearing the flag so I guess the issue this guy was talking about could arise there. I can see some strange side effects as the register would certainly be inconsistent. 
To be quite frank I&#8217;m not sure how the read/modify/write sequence being interrupted by a higher priority int could cause a re-posting of that higher priority interrupt, which is what he seems to be saying. Maybe I&#8217;m being dumb. 
Any other views?
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Non-Atomic Interrupt clear </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/grahamfclark">grahamfclark</a> on December 23, 2008</div><div class="thread-post-content">Looking again, the port.c kernel code I mentioned was for PIC24 and not PIC32. So it looks as though&nbsp; the PIC32 port looks pretty clean.
