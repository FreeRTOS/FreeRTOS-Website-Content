</div></div><div class="thread-post"><h3 class="thread-post-title">Application Overwriting wrong location</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on April 19, 2012</div><div class="thread-post-content">The normal first reply is to check for stack overflows &#40;set configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW to 2 and define a stack overflow hook&#41;, but you sound experiences so I suspect you have done that already.  
As this is a cortex-m chip then the next most likely cause is an incorrect priority in one of your interrupts. Are you 100% sure that all interrupts that call FreeRTOS API functions have a priority that is equal to or lower than configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY, and that lower priority means a higher number value? Often people think this is set correctly but because of the nonsense way Cortex defines priorities mistakes can still happen.  
Which heap allocation are you using? If it is heap&#95;3 and you are using GCC or a linker script that has the stack and heap grow together, also check your interrupts stack and heap have not clashed.

</div></div><div class="thread-post"><h3 class="thread-post-title">Application Overwriting wrong location</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 23, 2012</div><div class="thread-post-content">There is no easy way for FreeRTOS to monitor the interrupt stack as the stack used by main&#40;&#41; is reused as the interrupt stack, and the size and location of the stack used by main&#40;&#41; is not easy to ascertain.&nbsp; You can normally get the details from linker constants, but not in a portable way.&nbsp; As you know the linker and linker script you are using you could set something up yourself, but the method used would not then work if somebody were, for example, using a different tool distribution.
