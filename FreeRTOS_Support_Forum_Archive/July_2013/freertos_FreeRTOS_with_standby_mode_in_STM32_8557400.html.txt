</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS with standby mode in STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 24, 2013</div><div class="thread-post-content">You could use the linker script to force the data into a known memory section, then save that section.&nbsp; That is similar to how the FreeRTOS-MPU port works &#40;it uses the PRIVILEGED&#95;DATA and PRIVILEGED&#95;FUNCTION macros to force function and variables into a linker section&#41;.&nbsp; Alternatively you would have to add some functions into the kernel code that gave you access to the addresses of file private data.  
You would have to save all the file private data &#40;static variables&#41; from source/portable/tasks.c, and the stack of every task.&nbsp; The stacks will come from the heap, and where the heap memory comes from depends on if you are using heap&#95;1, heap&#95;2, heap&#95;3 or heap&#95;4.c &#40;or your own memory manager&#41;.  
Is there much to be gained between using the second lowest low power mode &#40;which keeps the registers and RAM powered&#41; and the lowest &#40;which looses the register and RAM data&#41;?  
Is it possible just to store a little state information in flash, then just restart the system completely when the MCU comes out of sleep mode.&nbsp; When you boot the system you can read the state information out of flash to inform your application of what it was doing when it was shut down.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS with standby mode in STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 24, 2013</div><div class="thread-post-content">A mode which loses most of memory and keeps just a bit of info is intended to be used in a mode where the processor in effect &#8220;reboots&#8221; on wake up, and the application uses the saved info to restart from where it was instead of at the beginning again by saving the APPLICATION state. Each of your tasks &#40;that need it&#41; would need to be allocated space in the Non-volatile memory to save its state, and would restart base on it. This would NOT be a full stack dump, but the few key parameters needed to restart from the last key checkpoint.  
Normally it takes long enough to &#8220;restart&#8221; the processor, and would require too much state to have this happen just because you are in idle. Normally it is done when all the tasks have completed their major work &#40;so they don&#8217;t need to save much state to resume&#41;, and you are going to be waiting for some significant event that might not happen for awhile, when the processor will drop into standby.  
Normally a simple low power mode &#40;which is easier to recover from&#41; is used in the idle hooks.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS with standby mode in STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 24, 2013</div><div class="thread-post-content">You need to be carefulll not to get &#8220;milliwatt&#8221; wise but &#8220;watt&#8221; foolish, these ultra-low=power states do consume a lot less power than normal operation, but due to what is needed to recover from them, they might have a moderate wake-up cost in terms of power. If you are going to be waking up on the next timer tick, which you know will be happening soon, anyway, it can well be a net LOSS of power to go into a deep power-save mode.  
I typically have the idle loop go into a very mild low-power mode, one which requires little &#40;if any&#41; operations to wake up from.&nbsp; When the application detects that it doesn&#8217;t have anything to do now, and is waiting for a user command, it may go into a deeper sleep. The ultra low power modes like this are for when your device detects that it isn&#8217;t being used at the moment, and can go totally asleep, waiting for something to wake it up to be used again.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS with standby mode in STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 24, 2013</div><div class="thread-post-content">Yes, that is why the tickles idle mode allows you to configure how long the expected sleep time should be before it considers going to sleep.&nbsp; It also provides pre and post sleep hooks to allow application specific processing &#8211; this is how the SAM4L and RX100 reference ports set their chip specific sleep mode.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS with standby mode in STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 30, 2013</div><div class="thread-post-content">I don&#8217;t think FreeRTOS has any provisions built into it for &#8220;restoring&#8221; your state after a deep sleep &#40;the problem is that FreeRTOS doesn&#8217;t know enough about your tasks to know what to remember about them. Thus when you recreate your task, they are starting fresh. Your tasks need to look at the information saved in the non-volatile memory to restart themselves in their previous state &#40;and somehow get that data saved before going to sleep&#41;.  
As I said, deep sleep is NOT something to casually use to save power, but a deliberate decision in the code to shut down to be restored at a latter point, with only a need to save limited information across the shutdown.
