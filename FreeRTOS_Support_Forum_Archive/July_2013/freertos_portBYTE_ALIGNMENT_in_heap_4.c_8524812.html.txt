  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">portBYTE_ALIGNMENT in heap_4.c</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ta8086">ta8086</a> on July 5, 2013</div><div class="thread-post-content">I am wondering why is necessary to align PortMalloc blocks?&nbsp; My MCU is Cortex M3 / STM with 128K RAM. I have large number of small objects and lose 10-15K only for the alignments. Is there any problem if I modify heap&#95;4.c to align at byte boundary? Probably the memory access may be slower but this is less important than memory size. I read that it is not recommended to modify portBYTE&#95;ALIGNMENT macro because it is used for stack alignment.
</div></div><div class="thread-post"><h3 class="thread-post-title">portBYTE_ALIGNMENT in heap_4.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 5, 2013</div><div class="thread-post-content"><blockquote>
  I read that it is not recommended to modify portBYTE&#95;ALIGNMENT macro because it is used for stack alignment.
</blockquote>
Then you have answered your own question :o&#41;  
You must be allocating a &#42;lot&#42; of blocks to loose 10-15K in alignment padding as the current FreeRTOS release will loose a maximum of 8 bytes per allocation.&nbsp; The next FreeRTOS release does improve the amount of loss so blocks that are 8 byte aligned already don&#8217;t loose any, meaning the maximum loss per allocation is 7.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">portBYTE_ALIGNMENT in heap_4.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ta8086">ta8086</a> on July 5, 2013</div><div class="thread-post-content">I am parsing XML file. All dynamic data is about 47K &#40;about 1500-2000 small objects&#41;. I tested with portBYTE&#95;ALIGNMENT = 2 and the free memory difference at the end was about 7K &#8211; the percentage &#40;7 of 47&#41; is not small. Maybe it is a good idea to have heap&#95;5.c for &#8220;economical&#8221; pvPortMalloc. Also I think it is necessary to implement PortRealloc.
</div></div><div class="thread-post"><h3 class="thread-post-title">portBYTE_ALIGNMENT in heap_4.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/l4na">l4na</a> on July 22, 2013</div><div class="thread-post-content">Hi, I&#8217;m also interested in this topic. Just curious, Is there any specific reason to align the memory for M3 in 8 bytes &#40;is it to resolve some issues&#41;? I realize that the older FreeRTOS sets this value at 4 bytes. 
</div></div><div class="thread-post"><h3 class="thread-post-title">portBYTE_ALIGNMENT in heap_4.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 22, 2013</div><div class="thread-post-content">Heap&#95;4.c has been updated in FreeRTOS V7.5.0.  
<blockquote>
  Hi, I&#8217;m also interested in this topic. Just curious, Is there any specific reason to align the memory for M3 in 8 bytes &#40;is it to resolve some issues&#41;? I realize that the older FreeRTOS sets this value at 4 bytes. 
</blockquote>
The ARM ABI is to have 8 byte alignment.&nbsp; You probably won&#8217;t notice any difference unless you start calling library functions that assume 8 byte alignment.&nbsp; The one that shows this up normally is calling printf&#40;&#41; with a %f to format a double precision floating point value.  
Regards.
