</div></div><div class="thread-post"><h3 class="thread-post-title">how does those define work?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on July 22, 2013</div><div class="thread-post-content">In old versions if INCLUDE&#95;vTaskCleanUpResources was set to 1 then the vTaskCleanUpResources function was available for you to call, but that is obsolete now, ignore it. It might appear in old FreeRTOSConfig.h files but the function does not exist in the rtos code.  
If INCLUDE&#95;vTaskSuspend is set to 1 then the vTaskSuspend&#40;&#41; and vTaskResume&#40;&#41; functions are available for you to call. vTaskSuspend&#40;&#41; puts a task in the suspended state, vTaskResume&#40;&#41; removes a task from the suspended state.

</div></div><div class="thread-post"><h3 class="thread-post-title">how does those define work?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 22, 2013</div><div class="thread-post-content">First, in most cases a linker will remove function that are not called anyway, meaning the INCLUDE&#95; macros can all be set to 1 without any effect on the code size.&nbsp; I think GCC is the only tool chain that won&#8217;t do that by default, but it can be requested to remove unused functions using the command line options.  
A task will only be placed into a true Suspended state when it is explicit placed into the Suspended state using the vTaskSuspend&#40;&#41; function.&nbsp; This is the only possible way into the Suspended state and the RTOS will never do this itself.&nbsp;   
Don&#8217;t confuse the Suspended state with the Ready state or the Blocked state.&nbsp; In the&nbsp; Ready state as task is able to run but not actually running, it is not Suspended though, it is just not running because another task is running.&nbsp; In the Blocked state a task is not running because it is waiting for an event &#40;be that a time or an external event or a message on a queue or a semaphore, etc.&#41;.&nbsp; In the Suspended state the task is not able to run, but it is also not waiting for anything so it will remain in the Suspended state until it is removed from the Suspended state by another task.  
<a href="http://www.freertos.org/RTOS-task-states.html">http://www.freertos.org/RTOS-task-states.html</a>

</div></div><div class="thread-post"><h3 class="thread-post-title">how does those define work?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 22, 2013</div><div class="thread-post-content"><blockquote>
  First, in most cases a linker will remove function that are not called anyway, meaning the INCLUDE&#95; macros can all be set to 1 without any effect on the code size.&nbsp; I think GCC is the only tool chain that won&#8217;t do that by default, but it can be requested to remove unused functions using the command line options.
</blockquote>
I am not sure this would be generally true&#33; The &#8220;Standard Model&#8221; for compiling projects has been that each source file generates a single object file with a single module which is included in the resulting executable, with any modules needed from library files to satisfy unmet references. You often needed to be careful with the order the libraries were specified so that libraries that fulfilled requests from other libraries were listed later in the list, as the linker did just a single pass through the object files/libraries.  
To implement the exclusion of unused functions, first the complier needs to break up the object file to have a module for each function within it, as the linker can not include just part of a module. The linker then needs to scan the object files multiple times to find all referenced symbols &#40;or at least record all defined symbols and go back to get the needed modules.&#41; While this capability is very common on &#8220;big machine&#8221; compilers, I am not as sure it is universal with the sometimes older base compliers found on many of the smaller processors &#40;and smaller processors are where you most need to worry about code space consumption&#41;.  
If FreeRTOS was compiled into a library, this wouldn&#8217;t be as much of a problem, as library modules have implemented this sort of functionality, but the dependance in FreeRTOS to FreeRTOSConfig.h, which is generally a PROJECT file, makes this not as convenient.
