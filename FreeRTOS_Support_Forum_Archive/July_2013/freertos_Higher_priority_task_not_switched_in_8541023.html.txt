  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Higher priority task not switched in</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/magnuskriel">magnuskriel</a> on July 15, 2013</div><div class="thread-post-content">I am creating a watchdog &#40;WD&#41; task which monitors all other tasks. If a task does not execute within a set amount of time, the watchdog task will stop kicking the hardware watchdog, forcing a watchdog reset.<br />
To test my WD task I have forced one of the tasks to hang by using a while&#40;1&#41;. This task&#8217; priority is set to 8 and the watchdog task is set to 6. &#40;Cortex M3 device, lower numeric priority number = higher priority&#41;.<br />
After entering the while&#40;1&#41;, no other tasks run, not even the higher priority watchdog task. The systick handler is being executed during this time, but the WD task is not being switched in. I did make sure the WD task is actually created successfully and runs.<br />
OS version 7.4.0, Preemption enabled
</div></div><div class="thread-post"><h3 class="thread-post-title">Higher priority task not switched in</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 15, 2013</div><div class="thread-post-content"><blockquote>
  Cortex M3 device, lower numeric priority number = higher priority
</blockquote>
That only refers to interrupt priorities, which are controlled by the hardware, not task priorities, which are controlled by the hardware.  
A <strong>task</strong> at priority 8 that is sitting in a null loop without ever entering the Blocked state will prevent a task at priority 6 from ever running, as you have seen.&nbsp; Switch the priorities around and it will be ok.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Higher priority task not switched in</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/magnuskriel">magnuskriel</a> on July 16, 2013</div><div class="thread-post-content">Thank you, I tried swapping the priorities and it worked. This, however generates more questions.<br />
I have read through the documentation regarding priorities and and specifically those for the Cortex M3.<br />
If I use the settings that comes with the demo project &#40;&#35;define** configLIBRARY&#95;LOWEST&#95;INTERRUPT&#95;PRIORITY 15** and &#35;define <strong>configLIBRARY&#95;MAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY 5</strong>&#41;,<br />
1&#41; what range can I use for the** task **priorities? 1 to 15 or 1 to 255?<br />
2&#41; what range of task priorities will be masked out when entering a critical section?
</div></div><div class="thread-post"><h3 class="thread-post-title">Higher priority task not switched in</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 16, 2013</div><div class="thread-post-content"><blockquote>
  1&#41; what range can I use for the task priorities? 1 to 15 or 1 to 255?
</blockquote>
Please do not confuse task priorities and interrupt priorities.&nbsp; Task priorities are under the control of FreeRTOS, are the same for all ports, and are completely unrelated to interrupt priorities &#40;and therefore not restricted in any way to the value of configLIBRARY&#95;MAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&#41;.  
On all FreeRTOS ports, 0 is the lowest task priority and &#40;configMAX&#95;PRIORITIES -1&#41; is the highest task priority.&nbsp; configMAX&#95;PRIORITIES is set in FreeRTOSConfig.h.  
<blockquote>
  2&#41; what range of task priorities will be masked out when entering a critical section?
</blockquote>
No <strong>task</strong> priorities will be masked out by any critical section….ever.&nbsp;   
Only <strong>interrupt</strong> priorities are masked, and in your case interrupts that have been assigned a priority of 5 or lower will be masked.&nbsp; Note that, due to the irrational way Cortex-M handles interrupt priorities, an interrupt assigned a priority of 4 has a <strong>higher</strong> logical priority than one assigned a priority of 5 &#40;even though it is a lower number&#41; so will not be masked, whereas an interrupt of priority 6 has a logical priority <strong>lower</strong> than one assigned a priority of 5 &#40;even though it is a higher number&#41; so will be masked.  
Regards.
