  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">V5.0.2 Trace Hooks Question</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jhenshaw">jhenshaw</a> on July 8, 2008</div><div class="thread-post-content">I&#8217;ve implemented a logging scheme that logs errors to a serial terminal. Some of these come from trace hook macros like Ques Send Failed and such &#8211; mostly I&#8217;ve just implemented macros for failure conditions. Since then, I&#8217;ve had endless trouble with my app crashing, typically by ending up trying to run code located at 0x0. It finally occurred to me that requesting service from the kernel like QueSend&#40;&#41; to place characters into the serial transmit queue might be a bad idea. &#40;Duh.&#41; And, forcing my Log&#40;&#41; function to return before doing anything does indeed cause my app to go back to running OK.
So, can I call kernel services from within these macros? Or is my problem &#40;possibly&#41; that some of these macros are called within IRQ &#40;or, since it&#8217;s an Ateml AVR32 UC3A0512&#41; or the Supervisor exception context?
</div></div><div class="thread-post"><h3 class="thread-post-title">V5.0.2 Trace Hooks Question</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 9, 2008</div><div class="thread-post-content">How are characters sent to the UART?&nbsp; When you say &quot;place characters into the serial transmit queue&quot; are you referring to a FreeRTOS.org queue?&nbsp; If so then you definitely cannot call the xQueueSend&#40;&#41; function from within an ISR context, you must instead use the xQueueSendFromISR&#40;&#41; version &#8211; but I think you have been using FreeRTOS.org long enough to know that already.
It was my intention when adding the macros that they be very short, returning quickly.&nbsp; I would have to inspect their placement to know the effect of calling another queue function from within a macro, especially with regard to whether the scheduler was suspended or a critical section entered when the macro gets executed.
A couple of easy things to check are 1&#41; You are not simply running out of stack space by calling the extra code from within the macro, 2&#41; You are not getting into some form of recursion whereby a queue API fails, so you call the error log function which calls a queue function, which fails and calls the error log, etc.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">V5.0.2 Trace Hooks Question</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jhenshaw">jhenshaw</a> on July 9, 2008</div><div class="thread-post-content">Hi Richard,
Yup, chars go into a FreeRTOS.org queue. Inside the ISR, the queue ISR versions are used for the xmit &amp; receive queues. In the ISR, I receive from the TX queue, but traceQUEUE&#95;RECEIVE&#95;FROM&#95;ISR&#95;FAILED remains unimplemented. When I receive a character, that&#8217;s pushed into the RX queue and I&#8217;ve implemented traceQUEUE&#95;SEND&#95;FROM&#95;ISR&#95;FAILED to call my Log&#40;&#41; function, which then dumps chars into the TX queue. So I COULD be getting recursive errors, not sure if I am though. Unfortunately, the darned trace facility in the debugger always loses data when the jump to 0x0 happens, so I can&#8217;t tell exactly what&#8217;s going on. I assume somebody&#8217;s TCB is getting overwritten, but I can&#8217;t tell whose or when.
I think I&#8217;ve solved my problem, or at least a major one. I added detection of being within an ISR to the Log&#40;&#41; code that pushes chars onto the queue, so I&#8217;m now calling xQueueSendFromISR&#40;&#41; when Log&#40;&#41; is called from an ISR, that seems to get things running again. I had actually implemented this earlier, but other problems masked this issue and so I backed those changes out since they didn&#8217;t appear to keep the app from being killed. Your post spurred me to re-examine &amp; re-implement this, thanks &#33;
However, I take your point about short &amp; quick within ISRs, which calling printf&#40;&#41; definitely isn&#8217;t. I think I&#8217;m going to rework this code so I can avoid text formatting within the ISR and do it later within a task. That will also eliminate any recursion problems since I can check the queue free space before placing chars into it.
Thanks again&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">V5.0.2 Trace Hooks Question</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on July 9, 2008</div><div class="thread-post-content">Depending on your library, printf can be massive, use lots of stack, even attempt dymamic allocation, and be non reentrant.There are some cut down versions of sprintf in the FreeRTOS zip file that might help.
</div></div><div class="thread-post"><h3 class="thread-post-title">V5.0.2 Trace Hooks Question</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jhenshaw">jhenshaw</a> on July 9, 2008</div><div class="thread-post-content">I&#8217;m using Newlib, and I&#8217;ve seen a stack depth of about 9 calls deep from printf&#40;&#41; to my low level write&#40;&#41; routine that actually puts bytes into the queue. And I found the sprintf in the FreeRTOS.org disti &#8211; mainly because I&#8217;d forgotten I&#8217;d included it as part of the demo code months ago. Imagine my surprise when I traced a sprintf&#40;&#41; call back into my own code rather than out to the runtime library&#33; That was embarrassing. :-&#41;
The library mallocs are protected by a locking mechanism that ends up calling vTaskSuspendAll&#40;&#41;, but I note that the FreeRTOS.org docs declare this as illegal from an IRQ, so I&#8217;m liable to still be in trouble there. I&#8217;m going to move all use of printf&#40;&#41;/scanf&#40;&#41; and their cousins out to the task level, and then further guard them with a Mutex so only one task at a time can use them. In addition to keeping me re-entrancy safe, that should keep printf&#40;&#41;&#8217;s from multiple tasks from getting their output all woven together.
Sigh. A new OS, a new processor, a runtime library that I can&#8217;t rebuild and can&#8217;t tell what options were used during the build, all to build an app in an industry I&#8217;ve never worked in. Lots of fun, but it&#8217;s hard to discover &amp; remember all the rules&#33;
Now if I could just figure out why the UART is issuing receiver full interrupts when the durn cable isn&#8217;t even connected to the board&#8230;
Thanks &#33;
