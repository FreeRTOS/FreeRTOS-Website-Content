</div></div><div class="thread-post"><h3 class="thread-post-title">V8.0.1 &#8211; using vTaskList crashes to vPortFree</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 2, 2017</div><div class="thread-post-content">By memory mode, do you mean the heap memory manger?  As in using heap<em>1.c, heap</em>2.c, etc.?  That should not effect anything to do with timing directly, but could be a symptom of the code not working previously but starting to work once you switched to heap_4.c
Note heap_1.c cannot be used with anything that tries to delete previously allocated memory: http://www.freertos.org/a00111.html
</div></div><div class="thread-post"><h3 class="thread-post-title">V8.0.1 &#8211; using vTaskList crashes to vPortFree</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/k1mgy">k1mgy</a> on November 2, 2017</div><div class="thread-post-content">|| Note heap_1.c cannot be used with anything that tries to delete previously allocated memory
I suspect there&#8217;s something in the FreeRTOS code base that does just this.  Using a simple test case from the Atmel Software Framework, it works fine until I upgrade to version 8.  Then, I get the vPortFree() trap.  No malloc/free operations are in the user code.
</div></div><div class="thread-post"><h3 class="thread-post-title">V8.0.1 &#8211; using vTaskList crashes to vPortFree</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 2, 2017</div><div class="thread-post-content">vPortFree() is also called internally if you delete an object.  In that 
version (are you sure it is V8 you upgraded to and not V9?) all objects 
are allocated dynamically, which means if you free an object it will be 
deallocated too (vPortFree() will be called).  This applies to any RTOS 
object such as a task, queue, semaphore, even group, etc.
