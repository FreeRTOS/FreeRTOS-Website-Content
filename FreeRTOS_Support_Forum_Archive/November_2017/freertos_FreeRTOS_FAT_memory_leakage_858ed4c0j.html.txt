  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS+FAT memory leakage ?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/maketych">maketych</a> on November 8, 2017</div><div class="thread-post-content">Hi all,
I am using FreeRTOS version 9.0.0 and FreeRTOS+FAT version 160919 to work with SD card and USB flash drive on LPC1788. 
During testing I noticed that if unplug any connected drive and then plug in again it causes lost 40 bytes from the FreeRTOS heap.
The research showed that:
In function FF<em>CreateIOManger (file ff</em>ioman.c) structure pxIOManager allocated by ffconfigMALLOC (line 141), then at line 156 allocated EventGroup (those 40 bytes) and its handle is stored in the structure pxIOManager.
Next, in function FF<em>DeleteIOManager structure pxIOManager freed by ffconfigFREE, but previously allocated EventGroup is not freed before it and EventGroup handler is lost. So at the next time you call FF</em>CreateIOManger will create a new EventGroup. It means heap memory leakage by 40 bytes in every reconnect the drive.
It seems that in function FF_DeleteIOManager need to freed EventGroup and make it before freed a structure pxIOManager.
Is that right?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+FAT memory leakage ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 13, 2017</div><div class="thread-post-content">A summary of the changes made in the above <code>0001-Changes-since-160919.patch</code> for FreeRTOS+FAT.
Note that all changes are intended to be downward compatible.
● <code>FF_FileSize()</code> can only handle sizes up to 2GB because it returns a signed value.
~~~
Old : int32<em>t FF</em>FileSize( FF<em>FILE *pxFile )
New : FF</em>Error<em>t FF</em>GetFileSize( FF<em>FILE *pxFile, uint32</em>t *pulSize )
~~~
The old function is still there.
The function <code>ff_filelength()</code> (in <code>ff_stdio.c</code>) already returned an unsigned value <code>size_t</code>.
It will now also call <code>FF_GetFileSize()</code> to obtain the size.
If it returns <code>0ul</code>, then <code>stdioGET_ERRNO()</code> can be called to see if there was an error.
● <code>FF_ExtendFile()</code> always immediately called <code>FF_FlushCache()</code> which is sometimes not desirable.
This will now be configurable with <code>ffconfigFILE_EXTEND_FLUSHES_BUFFERS</code>, default defined as <code>1</code>:
~~~
    #if( ffconfigFILE<em>EXTEND</em>FLUSHES<em>BUFFERS != 0 )
    {
    FF</em>Error_t xTempError;
<pre><code>    xTempError = FF_FlushCache( pxIOManager );
    if( FF_isERR( xError ) == pdFALSE )
    {
        xError = xTempError;
    }
}
#endif    /* ffconfigFILE_EXTEND_FLUSHES_BUFFERS */
</code></pre>
~~~
Some users don&#8217;t like this automatic flushing of FAT sectors. In stead they want to call <code>FF_FlushCache()</code> them selves, or wait until <code>FF_fclose()</code> is being called, which will call <code>FF_FlushCache()</code>.
● <code>FF_Seek()</code> (from <code>ff_file.c</code>) and <code>ff_fseek()</code> (from <code>ff_stdio.c</code>) did not work properly on files larger that 2GB.
The offset parameter of <code>ff_fseek()</code> is a signed 32-bit long:
<pre><code>int ff_fseek( FF_FILE *pxStream, long lOffset, int iWhence )
</code></pre>
With this patch :
<pre><code>iWhence = FF_SEEK_SET : lOffset is interpreted as a `uint32_t`
iWhence = FF_SEEK_CUR : lOffset is interpreted as a a signed offset
iWhence = FF_SEEK_END : lOffset must be &lt;= 0
</code></pre>
● <code>FF_Partition()</code> : Make sure that <code>ulHiddenSectors</code> is at least 1
● <code>FF_CreateIOManger()</code> would call <code>FF_CreateEvents()</code>, event if <code>pxIOManager</code> equals NULL
When it fails to create a <code>pxIOManager</code>, it should not proceed to create the event group.
● <code>FF_DeleteIOManager()</code> caused a memory leak, the field <code>pxIOManager-&gt;xEventGroup</code> was not deleted
● <code>FF_FlushCache()</code> now has a use hook
See comments in ff_ioman.h
Some users want to perform special actions each time when the +FAT data buffers have been flushed to disk.
● <code>FF_Mount()</code> : The field <code>pxPartition-&gt;pcVolumeLabel</code> didn&#8217;t get zero-terminated
● <code>FF_IncreaseFreeClusters()</code> could get blocked under certain circumstances
It was trying to take a lock that was already taken.
● <code>ff_sys.c</code> completely tested and updated
This module was rewritten and tested with frequent calls to <code>FF_FS_Add(()</code> and <code>FF_FS_Remove()</code> in a random order.
<code>ff_sys.c</code> makes the mapping between the so-called I/O managers and the (virtual) maps where they get mounted.
Hein Tibosch
