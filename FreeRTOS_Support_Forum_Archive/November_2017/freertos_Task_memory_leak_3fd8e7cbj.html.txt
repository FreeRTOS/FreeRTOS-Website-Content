ATSAMG55 J19  (taget: G55 xPlained)
Atmel Studio 7
Description:
    App consists of 6 xTaskCreate() tasks.  One task &#8211; <strong>CmdProc</strong> &#8211;  polls a touch screen (SPI).  Another &#8211; <strong>TouchPa</strong> &#8211; processes result of touch screen touch result value (button control on LCD).
The<strong>TouchPa</strong> process takes about 10 seconds to complete.  It includes starting up a fan through GPIO, and reading ADC.  The process then enables an ADC timer event that runs for (n) seconds according to the <strong>utilTim</strong> process (which keeps track of elapsed seconds, like a stopwatch).  
First time through, everything works fine.  Second time <strong>TouchPa</strong> triggers a hard fault.
Before starting I see the following results in the task monitor:
~~~
    &#8212; task ## 8Monitor            R       0       179     1
IDLE            R       0       78      7
TouchPa         B       1       226     2
ScreenU         B       2       176     4
CmdProc         B       3       218     5
Tmr Svc         B       2       44      8
utilTim         S       0       245     6
adc_con         S       4       245     3
~~~
After the process completes, I see the following results in the task monitor:
~~~
&#8212; task ## 8Monitor            R       0       57      1
IDLE            R       0       78      7
CmdProc         B       3       97      5
ScreenU         B       2       97      4
TouchPa         B       1       62      2
Tmr Svc         B       2       44      8
adc_con         S       4       228     3
utilTim         S       0       183     6
~~~
If I then kick off the process for a second time, my hard fault handler is hit.
~~~
[Hard fault handler &#8211; all numbers in hex]
R0 = 20000f00
R1 = 20000b60
R2 = 200045f8
R3 = 200045f8
R12 = a5a5a5a5

PC [R15] = 0  program counter
PSR = 4000000e
BFAR = e000ed38
CFSR = 20000
HFSR = 40000000
DFSR = 0
AFSR = 0
SCB_SHCSR = 400
~~~
The  PC of 0 is interesting&#8230;
I note that some tasks show a reduction in available stack space after they run for the first time.  Namely:
~~~
&#8212; task ## 8Monitor            R       0       57      1
IDLE            R       0       78      7
TouchPa         B       1       226     2                   <strong>62      2</strong>
ScreenU         B       2       174     4                   <strong>97      4</strong>
CmdProc         B       3       218     5                   <strong>97      5</strong>
Tmr Svc         B       2       44      8
utilTim         S       0       245     6                   <strong>183     6</strong>
adc_con         S       4       245     3                   <strong>228     3</strong>
~~~
I&#8217;m not doing any mallocs in my code.  I suspect the crash is occurring because the <strong>TouchPa</strong>  process runs out of stack.  
The original setting is:
~~~
<h1>define TOUCHPARSE<em>TASK</em>PRIORITY            ( configMAX_PRIORITIES &#8211; 4 )</h1>
<h1>define TOUCHPARSE<em>STACK</em>SIZE               (1024/sizeof(portSTACK_TYPE))</h1>
~~~
I increased the stack size to
~~~
<h1>define TOUCHPARSE<em>TASK</em>PRIORITY            ( configMAX_PRIORITIES &#8211; 4 )</h1>
<h1>define TOUCHPARSE<em>STACK</em>SIZE               (2048/sizeof(portSTACK_TYPE))</h1>
~~~
&#8230;and now the process runs a second time.  However I get another crash with the system in an idle (polling the touch screen) state.
Questions:
1. I have no idea what a safe low-water mark is for stack remaining.  Given the numbers above, any suggestions?
2. Is #define configTOTAL<em>HEAP</em>SIZE                   ( ( size_t ) ( 15000 ) )  sufficient?
3. Is there a way to determine what actually triggers the fault?  With a PC of 0, it seems hopeless.  I thought the vApplicationMallocFailedHook  or vApplicationStackOverflowHook would trigger.  They don&#8217;t.
</div></div><div class="thread-post"><h3 class="thread-post-title">Task memory leak?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 8, 2017</div><div class="thread-post-content">Hi Mark,
<blockquote>
  <ol>
  <li>I have no idea what a safe low-water mark is for stack remaining.
  Given the numbers above, any suggestions?</li>
  </ol>
</blockquote>
You should know that better than anybody else.
What I often do is the following:
&#8211; give each task an abundant amount of stack space.
&#8211; Let it run for a really long time, try all possible functions and situations
&#8211; Measure the maximum usage of the stack space
  ( try <code>uxTaskGetSystemState()</code> and look for <code>usStackHighWaterMark</code> )
&#8211; Make an estimate of the actual usage and add some spare space
The live stack check (<code>configCHECK_FOR_STACK_OVERFLOW</code>) works fine, but it <strong>may happen</strong> that the crash comes before the stack overflow has been detected.
<blockquote>
  <ol>
  <li>Is #define configTOTAL<em>HEAP</em>SIZE ( ( size_t ) ( 15000 ) ) sufficient?</li>
  </ol>
</blockquote>
That is easier to measure: there is a hook (<code>vApplicationMallocFailedHook()</code>) which will be called when <code>pvPortMalloc()</code> fails.
<blockquote>
  <ol>
  <li>Is there a way to determine what actually triggers the fault? With a
  PC of 0, it seems hopeless. I thought the vApplicationMallocFailedHook
  or vApplicationStackOverflowHook would trigger. They don&#8217;t.</li>
  </ol>
</blockquote>
I do not know the part that you are using, but doesn&#8217;t it have special registers that get set during an exception, and that have some sort of LR register?

</div></div><div class="thread-post"><h3 class="thread-post-title">Task memory leak?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 8, 2017</div><div class="thread-post-content">Mark, I can not find <code>ms_delay()</code>, but I do see <code>delay_ms()</code> in Atmel&#8217;s ASF.

</div></div><div class="thread-post"><h3 class="thread-post-title">Task memory leak?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 8, 2017</div><div class="thread-post-content">A couple of observations, and request for some clarification.
You say the problem is in a call to vTaskDelay, but the code shown doesn&#8217;t have a call to vTaskDelay.
You are creating a mutex in the task. Is xSemaphoreSPI a global variable or a local variable. If a local variable, a mutex only accessable by 1 task doesn&#8217;t get you anything. If global, how does the other task handle the mutex not being created yet if it gets to its need to use it. I try tp create all my mutexes and the like before starting up the scheduler to avoid having to have that sort of issue.
It is a bit unusual to have a timeout of 0 for a take, as that somewhat says that you really expect that the  resource is always available when you need it. It can make some sense if you have something else to check if it is busy, but then a lot of care needs to be taken that you will still service this device often enough.
