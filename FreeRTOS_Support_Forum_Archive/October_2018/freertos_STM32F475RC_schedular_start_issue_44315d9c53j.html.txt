  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32F475RC schedular start issue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fizzyaid">fizzyaid</a> on October 29, 2018</div><div class="thread-post-content">Hi,
I&#8217;m a long time user of FreeRTOS and have never had any issues brining it up on a new platform, but I&#8217;ve got a new platform here using the STM32L475RC chip and I can&#8217;t start the scheduler.
When I break the code, it&#8217;s stuck in an assert in xPortStartScheduler
<pre><code>    #ifdef configPRIO_BITS
    {
        /* Check the FreeRTOS configuration that defines the number of
        priority bits matches the number of priority bits actually queried
        from the hardware. */
        configASSERT( ( portMAX_PRIGROUP_BITS - ulMaxPRIGROUPValue ) == configPRIO_BITS );
    }
    #endif
</code></pre>
portMAX<em>PRIGROUP</em>BITS is 7
ulMaxPRIGROUPValue is 0xffffffff
configPRIO_BITS = 4
First time I&#8217;ve ever had an issue bringing up a board and have used various STM32 processors in the past with no issues either.  I&#8217;m using the GCC CM4F port.
Any thoughts?
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fizzyaid">fizzyaid</a> on October 29, 2018</div><div class="thread-post-content">ucMaxPriorityValue = *pucFirstUserPriorityRegister;
The value of this is 0xFF which it shouldn&#8217;t be?
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 29, 2018</div><div class="thread-post-content">The value of ulMaxPRIGROUPValue looks wrong.  It comes from the code just above the lines you posted:
~~~
ulMaxPRIGROUPValue = portMAX<em>PRIGROUP</em>BITS;
while( ( ucMaxPriorityValue &amp; portTOP<em>BIT</em>OF<em>BYTE ) == portTOP</em>BIT<em>OF</em>BYTE )
{
    ulMaxPRIGROUPValue&#8211;;
    ucMaxPriorityValue &lt;&lt;= ( uint8_t ) 0x01;
}
~~~
As it starts with the value 0x07 it must have underflowed to get to 0xffffffff, which presumably means uxMaxPriorityValue was wrong so it stayed in the while() loop too long.  Can you step through this part of the code in the debugger to see if this theory is correct, and if so, how ucMaxPriorityValue came to be wrong in the first place.
As this is an STM32, did you remember to call NVIC<em>PriorityGroupConfig( NVIC</em>PriorityGroup_4 ); before starting the scheduler?
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 29, 2018</div><div class="thread-post-content">I think our posts just crossed&#8230;
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 29, 2018</div><div class="thread-post-content">If you have four priority bits then ucMaxPriorityValue should be 0xf0 &#8211; as on the Cortex-M the most significant bits hold the priority.  https://www.freertos.org/RTOS-Cortex-M3-M4.html
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fizzyaid">fizzyaid</a> on October 29, 2018</div><div class="thread-post-content">Thanks for the response Richard,
I&#8217;ve called HAL<em>NVIC</em>SetPriorityGrouping(NVIC<em>PRIORITYGROUP</em>4); before the start of the scheduler and it&#8217;s made no difference, the ucMaxPriorityValue still reads 0xff and the underflow still occurs.
I cannot see any difference between my configuration and the one that the l475 demo in the amazon freertos repo.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 29, 2018</div><div class="thread-post-content">This is just reading from a hardware register.  Extremely unlikely, but 
could it just be bad hardware?  Alternatively, could it be the start up 
code is setting the CPU into an unprivileged state so you are not able 
to read/write from the interrupt priority registers?  (which is what 
this code is doing, to automatically determine the number of priority 
bits present in the hardware implementation).
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fizzyaid">fizzyaid</a> on October 29, 2018</div><div class="thread-post-content">I&#8217;ll have to check this in the morning, I&#8217;m using Crossworks V4, a quick cursory glance I can&#8217;t see anything about setting the privileged/unprivileged mode, so I assume it&#8217;s starting up in its default configuration, whatever that happens to be.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F475RC schedular start issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fizzyaid">fizzyaid</a> on October 30, 2018</div><div class="thread-post-content">Boy do I feel stupid&#8230;..
