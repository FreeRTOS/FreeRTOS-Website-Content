</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + TCP, tutorial, STM32F7 questions.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 7, 2018</div><div class="thread-post-content">Hi Abe, you can get around the above problem by changing the declaration in your main.c to:
~~~
    const uint8<em>t ucMACAddress[ 6 ] = { configMAC</em>ADDR0, configMAC<em>ADDR1, configMAC</em>ADDR2, configMAC<em>ADDR3, configMAC</em>ADDR4, configMAC_ADDR5 };
~~~
Here is a post about the recent STM32Fxx driver:
https://sourceforge.net/p/freertos/discussion/382005/thread/e6c5bd5f/?limit=250#fbd7
It needs one of these defines: <code>STM32F7xx</code>, <code>STM32F4xx</code> or <code>STM32F2xx</code> to indicate the type of CPU. I haven&#8217;t tested it on a STM32F2 my self, but it seems to work.
I will attach the latest version here below as &#8220;STM32Fxx<em>tcp</em>driver<em>7</em>Oct_2018.7z&#8221;. It won&#8217;t refer to <code>ucMACAddress[]</code> anymore.
Please unpack the 7-zip in &#8220;FreeRTOS-Plus-TCPsourceportableNetworkInterface&#8221;.
When using this driver, you should also include:
~~~
    FreeRTOS-Plus-TCPsourceportableNetworkInterfaceCommonphyHandling.c
~~~
and add this path to the list of include directories:
~~~
    FreeRTOS-Plus-TCPsourceportableNetworkInterfaceinclude
~~~
Please tell me how it works for you.

~~~
<h1>define ETH<em>MAC</em>TXFIFO<em>WRITE</em>ACTIVE  0x00400000U             /* Tx FIFO write active */</h1>
~~~
I don&#8217;t know how to handle this. You could put an empty file:
<pre><code>portableNetworkInterfaceSTM32Fxxstm32_hal_legacy.h
</code></pre>

I mean in &#8220;portableNetworkInterfaceSTM32Fxxstm32fxx<em>hal</em>eth.c&#8221; :
~~~
 /* Includes &#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;*/
+#define __STM32_HAL_LEGACY    1
 #if defined(STM32F7xx)
     #include &#8220;stm32f7xx_hal.h&#8221;
     #include &#8220;stm32f7xx_hal_def.h&#8221;
     #define stm_is_F7    1
 #elif defined(STM32F407xx) || defined(STM32F417xx) || defined(STM32F427xx) || defined(STM32F437xx) || defined(STM32F429xx) || defined(STM32F439xx)
     #include &#8220;stm32f4xx_hal.h&#8221;
     #include &#8220;stm32f4xx_hal_def.h&#8221;
     #define stm_is_F4    1
~~~
The NetworkInterface drivers always depend on chip libraries. We had to make some changes to them and therefor we also provided a <code>stm32fxx_hal_eth.h</code>.
I hope that you can find an easy solutuion to this.

Most Network Interface&#8217;s are defining an EMAC interrupt. That ISR should not produce any logging. It is called when a packet has been received or when it has been sent.
The Windows project indeed has a separate (Windows) thread that prints a queue of logging lines. That has to do with the fact that a FreeRTOS task may not call any Windows System API&#8217;s like <code>printf()</code> and <code>fflush()</code>.
Here below a simple version of <code>vLoggingPrintf()</code> that is task-safe. I haven&#8217;t tested this code yet:
~~~
static SemaphoreHandle_t xLoggingSemaphore = NULL;
static BaseType<em>t xLoggingEnter( void )
{
BaseType</em>t xResult;
<pre><code>if( xTaskGetSchedulerState() == taskSCHEDULER_NOT_STARTED )
{
    xResult = pdTRUE;
}
else
{
    if( xLoggingSemaphore == NULL )
    {
        /* Create a mutex. */
        xLoggingSemaphore = xSemaphoreCreateMutex();
    }
    if( xLoggingSemaphore != NULL )
    {
    /* Never wait longer than e.g. 100 ms. */
    TickType_t xTicksToWait = pdMS_TO_TICKS( 100 );
        xResult = xSemaphoreTake( xLoggingSemaphore, xTicksToWait );
    }
    else
    {
        xResult = pdFALSE;
    }
}
return xResult;
</code></pre>
}
static void vLoggingExit( void )
{
    /* Code below has confirmed that the semaphore has been
    created and that it has been taken by vLoggingPrintf().
    Now release it. */
    xSemaphoreGive( xLoggingSemaphore );
}
void vLoggingPrintf( const char <em>pcFormat, &#8230; )
{
    if( xLoggingEnter() != pdFALSE )
    {
    va_list xArgs;
    /</em> Watch out with small stacks. */
    char pcBuffer[ 129 ];
    BaseType xLength;
<pre><code>    va_start( xArgs, pcFormat );
    xLength = vsnprintf( pcBuffer, sizeof pcBuffer, pcFormat, xArgs );
    uart_send( pcBuffer, xLength );
    va_end( xArgs );
    vLoggingExit();
}
</code></pre>
}

<blockquote>
  <code>/* USE_WIN: Let TCP use windowing mechanism. */</code>
  <code>#define ipconfigUSE_TCP_WIN                            ( 0 )</code>
</blockquote>
Not important yet, but I recommend using the sliding TCP windows
<blockquote>
  <code>#define ipconfigTCP_WIN_SEG_COUNT                      240</code>
</blockquote>
I recommend a lower number. This defines the maximum number of outstanding TCP segments at any time.
<blockquote>
  <code>#define ipconfigTCP_RX_BUFFER_LENGTH                   ( 1000 )</code>
  <code>/* Define the size of Tx buffer for TCP sockets. */</code>
  <code>#define ipconfigTCP_TX_BUFFER_LENGTH                   ( 1000 )</code>
</blockquote>
1000 bytes is very little. Normally this would be defined as minimal:
~~~
<h1>define ipconfigTCP<em>RX</em>BUFFER<em>LENGTH                   ( 4 * ipconfigTCP</em>MSS )</h1>
<h1>define ipconfigTCP<em>TX</em>BUFFER<em>LENGTH                   ( 2 * ipconfigTCP</em>MSS )</h1>
~~~
In the above case, the buffers are defined as a multiple of <code>ipconfigTCP_MSS</code>, which depends on <code>ipconfigNETWORK_MTU</code>, or up to 1460 bytes.
<blockquote>
  <code>#define ipconfigREPLY_TO_INCOMING_PINGS                1</code>
</blockquote>
That is OK, but it is defined 2 times.
<blockquote>
  <code>static uint8_t ucMACAddress[ 6 ] = { configMAC_ADDR0, configMAC_ADDR1, configMAC_ADDR2,</code>
  <code>configMAC_ADDR3, configMAC_ADDR4, configMAC_ADDR5 };</code>
</blockquote>
You are defining static variables/arrays in a header file. I think that all these declarations should be placed in your <code>main.c</code>.
Especially <code>ucMACAddress</code> : are you sure it must be accessible in all modules that include FreeRTOSIPConfig.h?
If you change <code>ucMACAddress</code> in e.g. <code>main.c</code>, it will not change in other modules.
Normally <code>FreeRTOS_GetMACAddress()</code> is used to read the 6-byte MAC-address.
Can you see where (in what modules) <code>ucMACAddress[]</code> is being used?

I wrote Philipp a detailed email about his Atollic project. Here below a summary:
The biggest problem that I found was the small heap, only 15 KB. That is possible, but then you&#8217;d have to reconfigure the whole project to get a smaller usage of RAM.
The STM32F767 has a lot of RAM, so why not make use of it. I attach an example of vInitHeap() that uses <code>heap_5.c</code>.
The STM32F7 has checsum offloading, meaning the the IP-task doesn&#8217;t have to waste time on calculating checksums of incoming and outgoing packets. Therefore <code>FreeRTOSIPConfig.h</code> should define:
~~~
    #define ipconfigDRIVER<em>INCLUDED</em>RX<em>IP</em>CHECKSUM     1
    #define ipconfigDRIVER<em>INCLUDED</em>TX<em>IP</em>CHECKSUM     1
~~~
After making these changes, the +TCP project worked well.

The drivers on <a href="https://github.com/aws/amazon-freertos">Github/AWS</a> still run behind.
On the FreeRTOS SVN you will find the <a href="https://sourceforge.net/p/freertos/code/HEAD/tree/trunk/FreeRTOS-Plus/Source/FreeRTOS-Plus-TCP/portable/NetworkInterface">latest versions</a>
The driver in <code>STM32Fxx</code> works for both STM32F4 and STM32F7. You will also have to include <code>Common/phyHandler.c</code> into your project, and ad a <code>-I</code> for this include directory: source/portable/NetworkInterface/include
The module <code>phyHandler.c</code> will try all PHY addresses to look for a connected PHY. If you have logging, you can see what happens. Otherwise you can also set breaks in the code and inspect variables.
So in <code>xPhyDiscover()</code> you should see that your PHY will answer.
Make sure you have <code>ipconfigUSE_RMII</code> defined to <code>1</code> in case the connection is RMII.  Define it as <code>0</code> if you have a MII.
The next step will be to see if the Link Status becomes high. You see that reflected in the variable <code>xPhyObject.ulLinkStatusMask</code>.
While you are debugging it is maybe easier to disable DHCP:
~~~
<h1>define ipconfigUSE_DHCP    0</h1>
~~~
When you see that the PHY status is high, you will see so-called gratuitous ARP requests coming from your device.
