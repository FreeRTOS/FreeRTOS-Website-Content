It would appear that dhcp tries as soon as I call FreeRTOS_IPInit() whether or not the Wifi interface is ready.
There really is no good way for the application to either query dhcp status or be warned if the process failed.  Any suggestions?
It would seem to me that we need to either extend vIPNetworkUpCalls or xApplicationDHCPHook to include this information, or allow delaying dhcp until ready.
I don&#8217;t really like the silent failures that can happen with a ulrand failure, like line 593 in FreeRTOS_DHCP.c

</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP DHCP questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 19, 2018</div><div class="thread-post-content">I think that you should call <code>FreeRTOS_NetworkDown()</code> only once?
The idea was that <code>FreeRTOS_NetworkDown()</code> will be called every 3 seconds ( see <code>ipINITIALISATION_RETRY_DELAY</code> ). You don&#8217;t have to do this.
What does your <code>xNetworkInterfaceInitialise()</code> return?  It should only return <code>pdPASS</code> when the network is up, when there is a Link Status, or when WiFi is connected.
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP DHCP questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on October 22, 2018</div><div class="thread-post-content">Following up on this, I see that part of the problem is perhaps the DHCP server order?  In my case the option  order coming from the SonicWall is:
(53) DHCP Message Type (Offer)
(54) DHCP Server Identifier
(1) Subnet Mask
(51) IP Address Lease Time
(3) Router
(6) Domain Name Server
(255) End
So when the Options hit (3) router, ulProcessed >= ulMandatorOptions and processing ends.
 Comments refer to Subnet, Gateway, and DNS as being non essential, which shouldn&#8217;t be baked into the API the way it seems to me.
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP DHCP questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on October 22, 2018</div><div class="thread-post-content">Perhaps something down the line of 
~~~
        const uint32_t ulMandatoryOptions = 3ul;
<pre><code>    ...
        case dhcpEND_OPTION_CODE:
            ulProcessed++;
            break;
</code></pre>
~~~
Edit: This doesn&#8217;t seem to work at the moment
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP DHCP questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on October 22, 2018</div><div class="thread-post-content">~~~
        /* Walk through the options until the dhcpOPTION<em>END</em>BYTE byte
        is found, taking care not to walk off the end of the options. */
        pucByte = &amp;(pxDHCPMessage->ucFirstOptionByte);
        pucLastByte = &amp;(pucUDPPayload[ lBytes &#8211; dhcpMAX_OPTION_LENGTH_OF_INTEREST ]);
~~~
What is the purpose of 
~~~
<h1>define dhcpMAX<em>OPTION</em>LENGTH<em>OF</em>INTEREST       ( 2L )</h1>
