  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Typo  bug in eARPProcessPacket() causes exception</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/murraylang62">murraylang62</a> on October 31, 2018</div><div class="thread-post-content">Hi,
There is a bug in eARPProcessPacket() in FreeRTOS_ARP.c. In FreeRTOS v10.1.1 it is on line 117:
~~~
memcpy( ( void *)&amp;( ulSenderProtocolAddress ), ( void * )pxARPHeader->ucSenderProtocolAddress, sizeof( ulSenderProtocolAddress ) );
~~~
&#8230;which should be&#8230;
~~~
memcpy( ( void *)&amp;( ulSenderProtocolAddress ), ( void * )&amp;pxARPHeader->ucSenderProtocolAddress, sizeof( ulSenderProtocolAddress ) );
~~~
For a while I thought the resulting exception was due to alignment.
This has been around for the previous two FreeRTOS versions at least, but I&#8217;ve only now got around to pointing it out.
Cheers,
Murray
</div></div><div class="thread-post"><h3 class="thread-post-title">Typo  bug in eARPProcessPacket() causes exception</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 31, 2018</div><div class="thread-post-content">Hi Murray, thanks for reporting, but you haven&#8217;t convinced me yet.
The field <code>ucSenderProtocolAddress[ 4 ]</code> is an array of bytes.  In earlier versions of +TCP, this field was called <code>uint32_t ulSenderProtocolAddress</code>.  The problem was that this field is only 2-byte aligned. On most platforms, access to an <code>uint32_t</code> must be 32-bit aligned.
Note that there are 4 occurrences of <code>ucSenderProtocolAddress</code>in <code>FreeRTOS_ARP.c</code>, and none of them has an ampersand to take the address of the array.
</div></div><div class="thread-post"><h3 class="thread-post-title">Typo  bug in eARPProcessPacket() causes exception</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/murraylang62">murraylang62</a> on November 1, 2018</div><div class="thread-post-content">Oops &#8211; I beg your pardon.
I discovered that bug in the FreeRTOS Labs some time ago in my journey to get my STM32F4 Discovery board working with all the FreeRTOS Plus goodies. It took me a while to realise that the program was sitting in a tight loop in a fault handler. I&#8217;m actually grateful to it for forcing me to learn to make fuller use of GDB. 
Since then I&#8217;ve been adding those ampersands to the FreeRTOS releases, not noticing the change from <code>pxARPHeader-&gt;ulSenderProtocolAddress</code> to <code>pxARPHeader-&gt;ucSenderProtocolAddress</code> .
Another lesson for me in the difference between fact and belief!
Thanks,
Murray
