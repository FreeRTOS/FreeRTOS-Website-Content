</div></div><div class="thread-post"><h3 class="thread-post-title">code crashing in ISR- Cortex-M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 24, 2018</div><div class="thread-post-content">I&#8217;m afraid it is not clear what the problem you describe is or why you

</div></div><div class="thread-post"><h3 class="thread-post-title">code crashing in ISR- Cortex-M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 25, 2018</div><div class="thread-post-content">Interrupts that you do not define will all end-up in the same routine ( <code>Default_Handler()</code> ), which exists of a for-ever-loop.
What you can do is define all possible interrupts:
~~~
    &#8230;
    void NMI<em>Handler()            { for( ;; ); }
//  void HardFault</em>Handler()      { for( ;; ); }
    void MemManage<em>Handler()      { for( ;; ); }
    void BusFault</em>Handler()       { for( ;; ); }
    void UsageFault<em>Handler()     { for( ;; ); }
//  void SVC</em>Handler()            { for( ;; ); }
    void DebugMon<em>Handler()       { for( ;; ); }
//  void PendSV</em>Handler()         { for( ;; ); }
//  void SysTick<em>Handler()        { for( ;; ); }
    void WWDG</em>IRQHandler()        { for( ;; ); }
    void PVD<em>IRQHandler()         { for( ;; ); }
    void TAMP</em>STAMP_IRQHandler()  { for( ;; ); }
    etc&#8230;
~~~
In this example, I commented-out the ones that are used by the application.
In this way, the <code>.weak</code> declarations, which call <code>Default_Handler()</code>, will be overwritten. Make sure to define all possible interrupts that you do not use.
Now when the undefined interrupt is called, at least you will see which interrupt was triggered.

</div></div><div class="thread-post"><h3 class="thread-post-title">code crashing in ISR- Cortex-M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 25, 2018</div><div class="thread-post-content">Are you saying the interrupt remains high for the entire time that the 
flash is being written to.  Evidently the flash is not being written to 
from the interrupt handler itself, so it would seem interpreting what 
the trace is showing is a bit tricky.  Unless the flash is being written 
to by a higher priority interrupt, which also seems doubtful as you say 
the FPGA interrupt is the highest priority.
Can&#8217;t remember if we already went through this, but which version of 
FreeRTOS are you using?  I ask because the newer the version the more 
configASSERTS() are included in the code to help determine issues 
arising from interrupt priority mis-configurations.  Do you have 
configASSERT() defined?
If the interrupts come in quickly then they will tail chain with each 
other.  So if the FPGA interrupt is executing when another FPGA 
interrupt arrives then the second interrupt will be held pending 
(assuming the first has been cleared) until the first has been handled &#8211; 
at which point the interrupt handler will just be re-entered without any 
impact on the stack.
