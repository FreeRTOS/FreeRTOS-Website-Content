</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-TCP arp reply has invalid checksum</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 14, 2018</div><div class="thread-post-content">Hi Peter, that is an interesting observation.
<blockquote>
  &#8230;but Wireshark reports a problem with the Frame Check Sequence of the arp reply.
</blockquote>
Ok
<blockquote>
  At some point, FreeRTOS-TCP sends a gratuitous arp, and after that the
  PC is able to communicate with the embedded code.
</blockquote>
Good. Sending gratuitous ARP&#8217;s has the advantage that double IP addresses can be discovered earlier, and also that your PC&#8217;s ARP- and routing-tables remain up to date.
<blockquote>
  I suspect that the PC is rejecting the ARP reply, due to the invalid checksum.
  I have attached a screenshot of Wireshark, showing the incorrect arp reply.
</blockquote>
There are 3 types of checksums, belonging to 3 layers:
<ul>
<li>Protocol checksum, calculated by the IP-task or peripheral ( TCP or UDP layer )</li>
<li>IP checksum, calculated by the IP-task or peripheral ( IP layer )</li>
<li>Frame checksum, calculated by the Ethernet peripheral ( hardware layer )</li>
</ul>
The IP-stack is not responsible for the Frame checksum. I think there is a problem with the packet length: an ARP reply is normally 60 bytes long. In your case, the ARP reply is 64 bytes long, and the extra 4 bytes seem to have a random value. Those are interpreted as the Frame check-sum.
Normally the Ethernet peripheral makes sure that all packets have the required minimum length of 60 bytes ( excluding the frame checksum, which is not visible in Wireshark ).
If that doesn&#8217;t work, you can define in your <code>FreeRTOSIPConfig.h</code>:
~~~
    #define ipconfigETHERNET<em>MINIMUM</em>PACKET_BYTES       60
~~~
Do you have <code>ipconfigETHERNET_MINIMUM_PACKET_BYTES</code> defined?
What hardware are you using?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-TCP arp reply has invalid checksum</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 15, 2018</div><div class="thread-post-content">Thanks.
A minimum packet length is 60 or 64 bytes? You are right, the standard is 64 bytes.
The reason why there is a minimum length is interesting: packets travel through a LAN at a certain physical speed.
When two short packets are sent simultaneously, both senders might not notice a collision. The first byte of the other packet would arrive only after that last byte was transmitted.
So, the longer the minimum packet, the longer the cables of a LAN may be.
Note that in a 1 Gbps LAN, a longer minimum length would be better ( like e.g. 512 bytes )
But if a packet is made longer, it must be padded with zero&#8217;s, not with random data.
Have you also tried to set <code>ipconfigETHERNET_MINIMUM_PACKET_BYTES</code> to <strong>64</strong>?
