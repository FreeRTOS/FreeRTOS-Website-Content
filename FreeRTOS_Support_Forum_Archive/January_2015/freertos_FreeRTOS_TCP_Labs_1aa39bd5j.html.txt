</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP (Labs)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 14, 2015</div><div class="thread-post-content">There are two functions that release memory allocated to a buffer.  The first releases both the buffer itself, and the descriptor that points to the buffer.  This is called vReleaseNetworkBufferAndDescriptor().  
The second releases just the buffer, on the assumption the descriptor that used to point to the buffer has already been released.  According to the documentation and your question this should be called vReleaseNetworkBuffer(), but in fact, looking at BufferAllocation2.c, it is actually called vNetworkBufferRelease().  
This is a mistake.  The naming of the functions used to be consistent, rather than have one use &#8220;release&#8221; at the beginning of the name and the other at the end &#8211; but a decision was made to change their names and (for once) it is the documentation that is correct the function should be called vReleaseNetworkBuffer() as it looks like the source code was not updated accordingly.
We now have several target specific examples for the +TCP code and another new component that will be release soon (I keep saying &#8216;soon&#8217; ;o).  At the moment there is only one driver that has been tidied up enough to allow its publication.  I have attached this.  I&#8217;m afraid its not for an STM32, but you may find it useful as a reference all the same.  It is not intended as a model implementation, for example it does not handle error conditions properly, etc., but it does work.  It also requires the head revision of the +TCP stack &#8211; which we can also send you if you like.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP (Labs)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 18, 2015</div><div class="thread-post-content">Hi Pascal,
Thanks for reporting.
Your compiler warning is correct, as is Richard&#8217;s comment 🙂
The risk of assigning a pointer to a packed struct to a normal (unpacked) pointer is to get an alignment exception later on.
~~~~~
    struct xPACKET
    {
        uint8<em>t  a;
        uint16</em>t b; /* byte-aligned */
        uint8_t  c;
    } <strong>attribute</strong>( (packed) );
<pre><code>struct xPACKET xPacket;
uint16_t *pusChecksum = &amp;( xPacket.b );
/* This assignment might cause an exception. */
*pusChecksum = 0;
</code></pre>
~~~~~
Within &#8216;usGenerateProtocolChecksum()&#8217; we know that the &#8216;usChecksum&#8217; field in the UDP/TCP/ICMP header is at least 16-bit aligned.
I would propose to insert some casts:
<pre><code>    pusChecksum = ( uint16_t * ) ( &amp;( pxProtPack-&gt;xUDPPacket.xUDPHeader.usChecksum ) );
    pusChecksum = ( uint16_t * ) ( &amp;( pxProtPack-&gt;xTCPPacket.xTCPHeader.usChecksum ) );
    pusChecksum = ( uint16_t * ) ( &amp;( pxProtPack-&gt;xICMPPacket.xICMPHeader.usChecksum ) );
</code></pre>
Can you try if Keil accepts the cast as a solution?
And if not, we&#8217;ll have to change the declaration to:
~~~~~
uint16_t usChecksum;
<h1>include &#8220;pack<em>struct</em>start.h&#8221;</h1>
<pre><code>uint16_t *pusChecksum  /* without a semicolon */
</code></pre>
<h1>include &#8220;pack<em>struct</em>end.h&#8221;</h1>
~~~~~
&#8220;_packed&#8221; is simpler but other compilers use a different notations.
GCC want this:
~~~~~
    uint16_t *pusChecksum  <strong>attribute</strong>( (packed) );
~~~~~
and for me it warns that the &#8216;packed&#8217; attribute will be ignored.
That&#8217;s because my CPU allows 16-bit access at <em>any</em> address.
Regards,
Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP (Labs)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 21, 2015</div><div class="thread-post-content">Salut Pascal,
Thank you for the PCAP. Could it be that your STM32 does not receive any packets at all? Is this firmware able to respond to pings? If not, try without DHCP first :
<pre><code>`#define ipconfigUSE_DHCP    0`
</code></pre>
If it can not receive data, you might want to check the GPIO settings of the pins involved, especially for the RX path. Remember that various pins can perform the same function, depending on the hardware design.
I just made that mistake, I trusted on the library to set all GPIO&#8217;s properly. They were set very properly, but not for my board 🙂
There are about 13 pins that need to get the peripheral ETH function 0x0b and maybe some pin that provide a 25MHZ clock for the PHY.
In the function ETH_MACAddressConfig(), I changed one line and I also made the function public:
~~~~~
-static void ETH<em>MACAddressConfig(ETH</em>HandleTypeDef *heth,
&#8211;    uint32_t MacAddr, uint8_t *Addr)
+void ETH_MACAddressConfig(ETH_HandleTypeDef *heth,
+    uint32_t MacAddr, uint8_t *Addr)
 {
     uint32_t tmpreg;
<pre><code> /* Check the parameters */
 assert_param( IS_ETH_MAC_ADDRESS0123( MacAddr ) );
 /* Calculate the selected MAC address high register */
</code></pre>
&#8211;    tmpreg = ( ( uint32<em>t )Addr[ 5 ] &lt;&lt; 8) | (uint32</em>t)Addr[ 4 ];
+    tmpreg = 0x80000000ul | ( ( uint32<em>t )Addr[ 5 ] &lt;&lt; 8) | (uint32</em>t)Addr[ 4 ];
     /* Load the selected MAC address high register */
     ( * ( __IO uint32_t * ) ( ( uint32_t ) ( ETH_MAC_ADDR_HBASE + MacAddr ) ) ) = tmpreg;
~~~~~
It will set the MO bit (nr 31) which should always be a &#8216;1&#8217;.
In the debugger I saw that a particular MAC address did not receive any messages. After setting bit 31, it did receive messages.
Correction: for ETH_MACA1HR (2HR and 3HR), it is called:
<pre><code>`Bit 31 AE: Address enable`
</code></pre>
Note that if you want to use LLMNR, you have to activate the LLMNR multicast address:
~~~~~
<h1>if( ipconfigUSE_LLMNR == 1 )</h1>
<pre><code>static const uint8_t llmnr_mac_address[] =
{ 0x01, 0x00, 0x5E, 0x00, 0x00, 0xFC };
/* Program the LLMNR address at index 1.
Index 0 is occupied by the main MAC address. */
ETH_MACAddressConfig( &amp;heth, ETH_MAC_ADDRESS1,
    ( unsigned char *)llmnr_mac_address
</code></pre>
<h1>endif /* ipconfigUSE_LLMNR */</h1>
);
~~~~~

A note about TCP, UDP and Zero-Copy:
The idea of Zero-Copy is simply said: &#8220;Avoid the use of MEMCPY&#8221;. The advantage is an increased speed, lower memory use and less power consumption.
Disadvantages of Zero-Copy may be an increased complexity and less portability of the source code (non BSD-compatible extensions).
When +TCP was being developed (and also earlier while developing +UDP), all possibilities were studied to avoid the use of MEMCPY.
These optimisations have been realised:
<ul>
<li>For UDP recv: call <code>FreeRTOS_recvfrom()</code> with the <code>FREERTOS_ZERO_COPY</code> flag and receive a pointer to a network buffer. It must be freed after reception.</li>
<li>For UDP send: create a network buffer, fill it, call <code>FreeRTOS_sendto()</code> with the <code>FREERTOS_ZERO_COPY</code> flag, and have it passed straight to the DMA descriptors for transmission.</li>
<li>For TCP recv: call <code>FreeRTOS_recv()</code> with the <code>FREERTOS_ZERO_COPY</code> flag and receive a pointer to the internal RX stream. It must be released in a separate call.</li>
<li>For TCP send: The Zero-Copy flag is ignored.</li>
<li>For NIC recv: the DMA RX descriptors can have memory pointers to (the payloads of) network buffers.</li>
<li>For NIC send: the send routine can pass the payload buffers straight to DMA (in stead of first copying their contents.</li>
</ul>
It was surprising to see how these optimisations work-out on different platforms, boards.
The efficiency of using Zero-Copy mostly depends on the type of RAM used. If RAM is on a 32-bit bus, MEMCPY can be (should be) really fast*. I was not able the demonstrate the advantages of Zero-Copy on such boards.
If RAM has 16- or 8-bit access, or if the amount of RAM is small, then it is worthwhile to think about using Zero-Copy.
<ul>
<li>The speed of memcpy for 32-bit access: if a CPU has a clock of 100MHz, it can memcpy() between 50 and 150 MByte per second.
For 16- or 8-bit memory: memcpy would do 22 MB/sec or less per 100 Mhz clock speed.</li>
</ul>
On a STM32F0xx running on 168 MHz and using internal SRAM, Zero-Copy is probably not going to bring much performance gain. Copying a full-sized frame will last less than 10 uS.
