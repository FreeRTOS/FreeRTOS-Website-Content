  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Missing bytes when using queues</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kaarebach">kaarebach</a> on January 16, 2015</div><div class="thread-post-content">Hi
I have a very simple UART application, which I have ported from another
RTOS to FreeRTOS.
But now I got problems:
very simple task:
&#8211; In my UART RX interrupt, i send byte to a queue.
&#8211; In a task, I read the bytes from the queue.
ISR:
// Read byte from UART:
u8UART<em>Data = UART</em>ReceiveByte(UART);
// Send the byte to the queue:
xQueueSendToBackFromISR(xByteQueue, &amp;u8UART_Data, &amp;xHigherPriorityTaskWoken
);
In my receiving task, I wait for a byte in the queue:
xQueueReceive( xByteQueue, &amp;u8Received<em>byte, portMAX</em>DELAY );
Extremely simple&#8230;
My problem is that I sometimes looses a byte. Not many, but maybe 1 out of
10.000.
The ISR receives EVERY bytes sent to it.
But when reading the queue, some bytes are missing.
By mistake, I used the NON-ISR xQueueSendToBack in the first version.
When using this, I never lost any bytes, but entered HardfaultHandler once
in a while.
Anyone knows why I loose bytes between xQueueSend and xQueueReceive?
thanks in advance!
br
Kaare
</div></div><div class="thread-post"><h3 class="thread-post-title">Missing bytes when using queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 16, 2015</div><div class="thread-post-content">Do you check the return value of xQueueSendToBackFromISR()?  If it returns pdFALSE then the queue was full.
Also, do you call portYIELD<em>FROM</em>ISR( xHigherPriorityTaskWoken ) (or portEND<em>SWITCHING</em>ISR( xHigherPriorityTaskWoken ) &#8211; depending on the port) at the end of your interrupt handler.  If not then adding it may allow the receiving task to drain the queue sooner.
Generally it is not recommended to use a queue to send every received byte unless the data is very slow (like typed characters from a keyboard, as an example).  It will be more efficient to store received bytes in a RAM buffer, then use a semaphore (or task notification in V8.2.0) to unblock a task when there is a whole message that needs processing.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Missing bytes when using queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kaarebach">kaarebach</a> on January 16, 2015</div><div class="thread-post-content">Thanks for quick response!
I send 35 characters every second, so the data amount is very small.
It is not typed, but, still, i should be able to handle them
My interrupt never misses a character, and my queue is never full (set to 100 bytes length). When I check the queue free size, there are never more than 5 characters in the queue.
I know it is not the most efficient way to do it, but it should be OK with this amount of data.
portYIELD<em>FROM</em>ISR and portEND<em>SWITCHING</em>ISR are not available.
Only portYIELD is.
br
Kaare

</div></div><div class="thread-post"><h3 class="thread-post-title">Missing bytes when using queues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 16, 2015</div><div class="thread-post-content">On that chip the expected way of doing this would be to add
portEND<em>SWITCHING</em>ISR( xHigherPriorityTaskWoken ).
Alternatively you can expand the macro yourself and add
if( xHigherPriorityTaskWoken != pdFALSE )
{
     vPortYield();
}
