<blockquote>
  trying to compile multiple .c files into a single .o file
</blockquote>
that sounds like the right conclusion.
Here a rule that I often use in my projects:
~~~~~
    # A rule to build an .o from a pair .c and .d
    %.o: %.c %.d
        @echo Compiling $&lt;
        $(CC) -c $(CFLAGS) -MMD -MP -MT &#8220;$<em>.i $</em>.x $*.o&#8221; -o $@ $&lt;
~~~~~
Beside compiling, this rule also creates a dependency file (*.d) for each file, so <code>.d</code> is both an input as well as an output.
Let CFLAGS also include <code>-ffunction-sections</code> and <code>-fdata-sections</code>. With these options every function will get located in its own text segment and each data object gets its own data segment. Now while linking, only those functions that are really called, and only those data objects that are referred to, will be linked into your program.
Without these compiler options, all functions would go to a single section <code>.text</code> and all data would go to <code>.data</code> or <code>.bss</code>.
I am not a fan of using libraries, unless you&#8217;re working in a team and others are not allowed to see your source code. You can give them header files and a library (.h and .a).
Now when a header <code>.h</code> is out-of-sync with a library <code>.a</code>, you can expect big problems at runtime.
