  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS MPU behavior and threat model</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yan-i">yan-i</a> on January 7, 2015</div><div class="thread-post-content">Hello,
I&#8217;ve been struggling to understand FreeRTOS-MPU port&#8217;s threat model, as documented and as developed. I am referring to a few points that are seemingly exclusive:
<ul>
<li>All of MPU-ported FreeRTOS functions first raise the privilege of the calling task, then call to the actual function, then revert their privilege back to what it was.</li>
<li>The following line from MPU docs: &#8220;A Privileged mode task can call portSWITCH<em>TO</em>USER_MODE() to set itself into User mode. A task that is running in User mode cannot set itself into Privileged mode.&#8221;</li>
</ul>
portSWITCH<em>TO</em>USER<em>MODE() simply removes the privileged bit, and prvRaisePrivilege() calls through to the portSVC</em>RAISE_PRIVILEGE svc call, which unconditionally raises a task privilege. This seems to be counter to a task not being able to set itself into privilege mode after dropping privileges.
While I understand that the FreeRTOS-MPU port isn&#8217;t specifically designed to be a MAC-like mechanism, but I&#8217;d still like to be able to provide slightly stricter control over unprivileged tasks.
Ideally, I&#8217;d like to be able to to remove the privilege bit and only allow raising of privilege for a heavily-restricted set of FreeRTOS functions. Is this a supported use case? One way we&#8217;re currently thinking of implementing this is to add a bit more logic to to the portSVC<em>RAISE</em>PRIVIELGE svc call.
Thanks!
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS MPU behavior and threat model</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on January 7, 2015</div><div class="thread-post-content">I don&#8217;t think it is possible to stop a task calling SVC, which will automatically set it into privileged mode. All you could do then is have the kernel check if it is a privileged task before you let it do anything else, returning it to user mode if necessary. Is that the extra logic you mention?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS MPU behavior and threat model</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yan-i">yan-i</a> on January 7, 2015</div><div class="thread-post-content">Yep, the idea was to add a check in the &#8216;raise privilege&#8217; handler to either limit the conditions under which a task can increase privileges, or to make sure that the lr register points inside the privileged_functions section.
On another note, I&#8217;m not sure what the sentence in the docs was referring to (can only drop privileges, not raise them). I guess it implied that only with code that doesn&#8217;t call a svc routine can you not increase your privileges.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS MPU behavior and threat model</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 7, 2015</div><div class="thread-post-content">The idea was to provide a method for a task to transition itself from 
being privileged to unprivileged, which is safe, but not the reverse 
(other than when legitimately calling an API function), which would not 
be safe.
It is sometimes easier to create a task with full privileges, then once 
the task has done whatever it needs at start up, to drop to its run-time 
state of being unprivileged.  It is purely a convenience thing.
Regards.
