  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC32 assembly wrappers problem with portEND_SWITCHING_ISR()</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbjork">pbjork</a> on January 26, 2015</div><div class="thread-post-content">I&#8217;m using the PIC32MZ processor, Harmony 1.02 with it&#8217;s version of FreeRTOS (8.x), compiler XC32 v1.34, MPLAB 2.26.  I&#8217;ve adapted the FreeRTOS dual CDC USB demo code for the USB and CDC tasks, mostly without changes.  
The Harmony configurator generates interrupt assembly code in the system<em>interrupt</em>a.S file.  The assembly code as-is seems to be pretty close to that recommended for FreeRTOS interrupt assembly wrappers.  For example:
   .extern  IntHandlerUSBInstance0
   .section .vector_132,code, keep
   .equ     __vector_dispatch_132, IntVectorUSBInstance0
   .global  __vector_dispatch_132
   .set     nomicromips
   .set     noreorder
   .set     nomips16
   .set     noat
   .ent  IntVectorUSBInstance0
IntVectorUSBInstance0:
    portSAVE_CONTEXT
    la    s6,  IntHandlerUSBInstance0
    jalr  s6
    nop
    portRESTORE_CONTEXT
    .end    IntVectorUSBInstance0
The wrapper calls the C handler function as recommended, which then calls a Harmony-provided USB driver, 
void IntHandlerUSBInstance0(void)
{
    USB<em>DEVICE</em>Tasks_ISR(sysObj.usbDevObject0);
}
When I use the assembly wrapper, the &#8230;Tasks<em>ISR() proceeds as expected and proceeds all the way into a callback function APP</em>USBDeviceEventHandler().  One of the states finishes up with the standard interrupt-ending call to a semaphore operation followed by the context switch function as follows: 
xSemaphoreGiveFromISR(appCDCData->xSemaphoreBlockUsbConfigure, &amp;xHigherPriorityTaskWoken1);
portEND<em>SWITCHING</em>ISR( xHigherPriorityTaskWoken1 );
break;
This brings us back to the &#8230;Tasks<em>ISR().  (But it is NOT the last instruction in the Harmony ISR &#8211;  there are a couple more which seems to be a no-no in the PIC32MX port docs.)  When I view the call stack, I see that the higher priority task (a CDC-related task) seems to awake right there, while the interrupt is still running, and proceeds to a spot where it happens to call portENTER</em>CRITICAL().  This generates an Assert() error, since this is not supposed to be called from an ISR.
Oddly, if I chuck the assembly wrapper and just use an ISR macro, it all works.  (BTW, there is also a system timer ISR that uses the mhc-generated assembly wrapper.)
void __ISR(<em>USB</em>VECTOR, ipl4) <em>IntHandlerUSBInstance0(void)
{
    USB</em>DEVICE<em>Tasks</em>ISR(sysObj.usbDevObject0);
}
Any comments on what is happening here?  Is the assembly code at fault?  I&#8217;ve tried various things such as declaring the ISR wrapper in the compiler instead, and &#8220;.extern&#8221;-ing it in the assembly file, to no avail.
Thanks for your consideration,
Paul

</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 assembly wrappers problem with portEND_SWITCHING_ISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 27, 2015</div><div class="thread-post-content">The PIC32 port does not need to portEND<em>SWITCHING</em>ISR() call to be at the end of the interrupt provided that:
<ul>
<li>the SW0 software interrupt used for the yield has the lowest possible interrupt priority.</li>
<li>Also I think on the MIPS core it is important to ensure the lowest interrupt priority does not become enabled in the interrupt controller during the execution of other interrupts (can&#8217;t quite remember if this is the case or not).  The FreeRTOS ASM code will re-enable interrupts above the priority of the currently running interrupt only &#8211; make sure no other code is re-enabling all interrupts.</li>
</ul>
Also ensure the system/interrupt stack is large enough.  You might want to increase the size of configISR<em>STACK</em>SIZE in FreeRTOSConfig.h to make sure.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 assembly wrappers problem with portEND_SWITCHING_ISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbjork">pbjork</a> on January 30, 2015</div><div class="thread-post-content">Okay, here&#8217;s the solution.  Contrary to the Harmony manual, you MUST NOT #define the macro OSAL<em>USE</em>RTOS when you are using FreeRTOS.  Either the macro name or the actual usage is completely misleading.  If the configurator puts it in, comment it out.  And explain why, as follows.  (Note: the RTOS demos in Harmony 1.02 all comment it out, but do NOT explain why.)
With OSAL<em>USE</em>RTOS defined (as 1), the osal<em>definitions.h file will include the source file osal</em>freertos.c.  YOU DO NOT WANT THIS.  This was the problem with the portEnterCritical() call from an ISR, and the resultant assert() error. 
Without this, the macro file osal<em>impl</em>basic.h file will be pulled in and interrupt safe calls will be made.  And you will be happy.
Real Time Engineers, please address this manual discrepancy with Microchip.  This confusion is misleading and unprofessional.  And will someone please explain what oral_freertos.c is for, if not for this?
Paul
