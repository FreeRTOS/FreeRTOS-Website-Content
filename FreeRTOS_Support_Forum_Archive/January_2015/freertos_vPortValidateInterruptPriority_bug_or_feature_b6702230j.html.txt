I am just on 8.2.0 (FreeRTOSV8.2.0FreeRTOSSourceportableIARARM_CM3) port.
I wonder if the following code really works or if i had to continue studying&#8230;.
<div class="codehilite"><pre><code>
// (port.c)
vPortValidateInterruptPriority( void ){
    uint32_t ulCurrentInterrupt;
    uint8_t ucCurrentPriority;
        /* Obtain the number of the currently executing interrupt. */
        __asm volatile( "mrs %0, ipsr" : "=r"( ulCurrentInterrupt ) );
        /* Is the interrupt number a user defined interrupt? */
        if( ulCurrentInterrupt >= portFIRST_USER_INTERRUPT_NUMBER ){
            /* Look up the interrupt's priority. */
                        //ucCurrentPriority = pcInterruptPriorityRegisters[ ulCurrentInterrupt ];
   [...]
</code></pre></div>
Since <b>pcInterruptPriorityRegisters</b> is pointing to the very beginning of the NVIC<em>IP table at [<i>#define portNVIC</em>IP<em>REGISTERS</em>OFFSET_16 ( 0xE000E3F0 )</i>], <b>pcInterruptPriorityRegisters[ ulCurrentInterrupt]</b> will in my opinion point to the wrong location (by 16 Byte to short).
Using this small modification:
<div class="codehilite"><pre><code>
ucCurrentPriority = pcInterruptPriorityRegisters[ portFIRST_USER_INTERRUPT_NUMBER + ulCurrentInterrupt ];
</code></pre></div>
<i>ucCurrentPriority</i> will be derived from the correct IRQn.
What do you think?
Kind regards, Stephan
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortValidateInterruptPriority() bug or feature?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on January 18, 2015</div><div class="thread-post-content">I was sure the code is right because I tested it when it first appeared in FreeRTOS, and I dont think it has changed since. But you made me doubt myself so I looked again.
I think you have made a mistake here
<blockquote>
  Since pcInterruptPriorityRegisters is pointing to the very beginning of the 
  NVIC<em>IP table at [#define portNVIC</em>IP<em>REGISTERS</em>OFFSET_16 ( 0xE000E3F0 )],
</blockquote>
The table begins at 0xE000E400 so the OFFSET<em>16 refers to a negative 16 from the start of the table. pcInterruptPriorityRegisters is not pointing to the very beginning of the NVIC</em>IP table it is pointing 16 bytes behind the beginning of the table.
But if you thought pcInterruptPriorityRegisters pointed to the start of the table I dont see why your modification is adding portFIRST<em>USER</em>INTERRUPT<em>NUMBER to ulCurrentInterrupt rather than subtracting portFIRST</em>USER<em>INTERRUPT</em>NUMBER from ulCurrentInterrupt?
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortValidateInterruptPriority() bug or feature?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stephanhd">stephanhd</a> on January 18, 2015</div><div class="thread-post-content">Hi Dave and thanks for taking care!
please let me explain how I came to this point: (using IAR EWARM; Cortex M4 &#8211; AT91SAM4S)
1.) NVIC<em>SetPriority(28, 11); // set somewhere at start; value visible in NVICIP29
2.) then PIOB</em>Irq is fired 
3.) and PIOB_IrqHandler is called
4.) some MessageProcessing is done and via xQueueSendToFrontFromISR() &#8230;
5.) &#8230; in vPortValidateInterruptPriority():
<pre><code>   __asm volatile( "mrs %0, ipsr" : "=r"( ulCurrentInterrupt ) );
ulCurrentInterrupt is derived as 28 (0x1C). 
Perfect as it fits to __vector_table[28] == PIOB_IrqHandler() :)
</code></pre>
6.) Status at this point in time:
    * 0xE000E3F0: it contains (uint8<em>t)0x00
    * 0xE000E400: it contains (uint8</em>t)0x00
    * 0xE000E40C: it contains (uint8_t)0x00   (this is pcInterruptPriorityRegisters[ulCurrentInterrupt])
<b>But:
    * 0xE000E41C: contains (uint8<em>t)176 (0xB0) // (11 &lt;&lt; 4) from (step 1.)
</b>
and this is exactely: 0xE000E3F0 plus 16 + 28 == 0xE000E41C
pcInterruptPriorityRegisters[portFIRST</em>USER<em>INTERRUPT</em>NUMBER + ulCurrentInterrupt]
This is as I could see it in the debugger &#8230; 
Indeed: if portNVIC<em>IP</em>REGISTERS<em>OFFSET</em>16 <b>would not be</b> pointing to 0xE000E3F0, but to 0xE000E400 (the real start of the NVIC_IP) then pcInterruptPriorityRegisters[ulCurrentInterrupt] would be fine as well.
Maybe you can help me to get the knot out of my brain? 😉
Kind regards, Stephan
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortValidateInterruptPriority() bug or feature?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stephanhd">stephanhd</a> on January 18, 2015</div><div class="thread-post-content">I found it by myself. Finally it was too simple 🙂 shame on me 😉
I made the mistake to set the idx of the __vector<em>table[] equal to the numbering of the specific IRQs like PIOB</em>IRQn; which is 12 and thats __vector_table[16 + 12 == 28].
So setting  NVIC<em>SetPriority(28, 11) is bullShit as it set the NVIC</em>IP for IRQ28 which is not equal PIOB<em>IRQn&#8230; 
Use NVIC</em>SetPriority((IRQn<em>Type)PIOB</em>IRQn, 11) instead&#8230;.
Ok sessions learned; thanks a lot and good night!
Kind regards, Stephan
