</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS demo is crashes on MSP430F5438</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 3, 2012</div><div class="thread-post-content">&#45; I can replicate your finding.  
&#45; If I go back to the version of FreeRTOS that was originally released with this demo &#40;which definitely did not have this issue&#41; then the issue can also be replicated.&nbsp; So it is not changes to the port, or to FreeRTOS that have caused the problem.  
&#45; Commenting out the line halButtonsInterruptEnable&#40; BUTTON&#95;SELECT &#41;; in prvSetupHardware&#40;&#41; allows the demo to run ok &#40;as expected, as it was the button interrupt that was causing the problem&#41;.  
Preliminary conclusion &#8211; a change between CCS4 and CCS5 is the root cause.&nbsp; I don&#8217;t know what though, although looking at the interrupt processing would seem to be a good starting point.  
&#45; Putting the call to halButtonsInterruptEnable&#40; BUTTON&#95;SELECT &#41;; back in, but commenting out the call to xQueueSendFromISR&#40;&#41; within the interrupt handler routine allows the interrupt to execute without any problem.  
&#45; Editing the interrupt handler so portYIELD&#95;FROM&#95;ISR&#40;&#41; is called does not cause the issue to return.  
Secondary conclusions &#8211; it is not executing the button interrupt itself, or yielding in the interrupt, that is the route cause.  
&#45; Removing half the tasks, and then increasing the stack size of the remaining tasks makes no difference.  
&#45; Putting everything back together, then placing a break point in the LCD task where the button interrupt message is posted, shows the interrupt is actually successfully sending a message on the queue and switching to a new task.&nbsp; This is calling a low stack sprintf&#40;&#41; function, defined in printf-stdarg.c.  
&#45; Excluding printf-stdarg.c from the build &#40;right click on the file in the project explorer and somehow find the checkbox that says &#8220;exclude from build&#8221;&#41;, do a complete rebuild, then try again and everything works as expected.  
Tertiary conclusions &#8211; there is something in the printf-stdarg.c file the compiler and/or linker is not happy with, even though the file is used with lots of other demos without issue.  
The call to sprintf&#40;&#41; defined in printtf-stdarg.c works fine for all the other messages being printed out, it seems just when the button interrupt is pushed that the problem happens.&nbsp; Please investigate that further and let me know what you find.  
Regards.

1&#46; Pushing the interrupt button causes the program to stop.<br />
2&#46; After a while it hangs.&nbsp; It seems to be a fixed amount of time.&nbsp; Not sure if that&#8217;s a feature or a bug.  
1: the problem was that &#8220;print&#8221; inside of printf-stdarg.c was running into problems on line 151.&nbsp; The value &#8220;s&#8221; was pointing into random memory space and so the copy would just write until it found a  .&nbsp; The problem is that va&#95;arg &#40;ine 150&#41; was passed an int as a type rather than a char&#42;.&nbsp; That was causing the value read back to be sign extended from a 16-bit value to a 20 bit value&nbsp; &#40;0xAEE8 to 0xFAEE8&#41; in the cast to a char &#42;.&nbsp;   
So the fix is line 150 of printf-stdarg.c should be:<br />
&nbsp;&nbsp;&nbsp; register char &#42;s = &#40;char &#42;&#41;va&#95;arg&#40; args, char&#42; &#41;;  
2: No clue at this time

FAQ follows:  
&nbsp;&nbsp;&nbsp; My board keeps getting a &#8220;break&#8221; in the code randomly even though I have no break points.&nbsp; What&#8217;s up?<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Your board is faulting for some reason.&nbsp; This can happen for two basic reasons.<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; You have a power problem.<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; The LCD on the board isn&#8217;t well behaved when not powered on &#40;I&#8217;ve no clue why&#41;.&nbsp; If you connect the top-left jumper on the board this should help.&nbsp; Another symptom of this problem is that the outputs on the board aren&#8217;t consistently driving to the same Vcc point.&nbsp;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; You are running off of battery and they are failing.&nbsp; Change the power switch to USB and connect the USB power.<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; You haven&#8217;t fully connected the USB power.&nbsp; It takes a bit of force but should go most of the way in.<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; You didn&#8217;t change to a small memory model.&nbsp; No clue why this causes problems &#40;the guy who wrote FreeRTOS is also confused as it works correctly under CCS4&#33;&#41;.<br />
