  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Queuing Question &#8211; Different Integral Types </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/westmorelandeng">westmorelandeng</a> on October 12, 2012</div><div class="thread-post-content">Hello Richard and Fellow FreeRTOS&#8217;ers,  
I have a question about Queuing &#8211; can I use one queue that is large &#8211; large being 128 bytes in an embedded system &#8211; for different integral types or is that just a no-no?  
For instance &#8211; I would like to use one General Q for a UART, let&#8217;s say &#8211; but, I need to pass different types of packets.&nbsp; I am finding the overhead of doing something like vPrintString&#40;&#41; &#40;have written my own which is similar&#41; &#8211; could be a little excessive in some cases &#8211; but will the Q &#8216;behave&#8217; properly if I were to pass something like:  
1&#41;&nbsp; a structure pointer to a communications packet that is, let&#8217;s say, 48 bytes; and then<br />
2&#41;&nbsp; a structure pointer for a 3 byte &#8216;ACK&#8217; packet<br />
3&#41;&nbsp; just a byte of some sort,<br />
…  
Does the Q only support one integral type?&nbsp; For instance; if I have sized a Q for chars but one of my structure&#8217;s has unsigned shorts, for instance &#8211; will the Q operate properly?&nbsp; I can unwrap this on the other end char-by-char &#8211; but I would like to be able to use the Qing facilities and not have to declare a specific Q for each specific type of packet.  
Thanks In Advance,<br />
John W.
</div></div><div class="thread-post"><h3 class="thread-post-title">Queuing Question &#8211; Different Integral Types </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on October 13, 2012</div><div class="thread-post-content">A queue only supports items of one type &#40;or more precisely one size&#41;. This item could be a union of the various types of object you want to queue &#40;or a struct with a flag to indicate the type and then a union&#41;.   
It could also be a void&#42; pointer &#40;or a structure with a flag and a void&#42; pointer&#41;, with the pointer pointing to the data. In this case the queue will NOT save the data pointed by, so the program needs to manage the life of these buffers and keep track of when they are free to reuse or still busy. One way to do this is to heap allocate them and free them when done. Many design rules don&#8217;t like using the heap in embedded environments, due to the fact that you need to make sure you can handle a failed allocation gracefully.&nbsp;   
Another option is to enqueue a packet in smaller pieces, where some packet use fewer pieces than others to reduce queue space used for the smaller packets &#40;if that is important&#41;. One thing to watch out for is that if multiple tasks might be adding or removing packets from the queue, that side will need a mutex or equivalent to avoid interleaving or splitting of packets.  
The third option is to just queue up a maximal size packet. This wastes queue space for small packets, but simplifies the code significantly which may be a very positive result.   
Which one to use depends a lot on the application and the sizes and likelihood of different types of packets. In general large packets are normally best to send via pointers, to avoid all the data copying that otherwise happens. 48 byte packets, particularly if a lot of the packets are of that size, may qualify as large here. It may not be large enough that variable size buffers are important and perhaps ALL packets are make 48 bytes, and take the loss of space efficiency to greatly limit program complexity. Perhaps if most packets are 48 or 3, it might make sense to have two buffer sizes, especially of the ratio of the number of needed packets of each size is known.
