&#42;&#42;configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY 159;&#42;&#42; The top 4 bits are 1001&#40;binary&#41;, which equals 9&#40;decimal&#41;. With this modification, I can use the numbers between 9 and 15 inclusive. Which means 10,11,12,13,14,15.<br />
Also, &#42;&#42;configTICK&#95;RATE&#95;HZ&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#40; &#40; portTickType &#41; 200 &#41;&#42;&#42;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#42;&#42;configMAX&#95;PRIORITIES&nbsp;&nbsp;&nbsp; 5 &#42;&#42;<br />
With the above settings, My firmware has to do the following&#40; assume 2 tasks&#41;:  
1&#46; Create two tasks when the board is powered.<br />
2&#46; One of the task&#40; Data Task&#41; should be running at 100Hz &#40;using Timer ISR&#41;.<br />
3&#46; The other task&#40;Command Task&#41; should respond for a data coming from USB or USART &amp; then process the data&#40;commands&#41; placed in queue&#8217;s.

Now,Again, if I send a command to board via already communicated path, It &#42;&#42;stops&#42;&#42; Timer2.<br />
This approach has no problems with the above six interrupt priorities &amp; their order. My firmware works fine.  
&#42;&#42;But I want to start running the Data Task at 100Hz without sending the command to start Timer2 ISR as soon as the board is powered, then communicate with board.&#42;&#42;<br />
With this approach i need to remove &#42;&#42;start&#42;&#42; &amp; &#42;&#42;stop&#42;&#42; timer commands.

  &#42;&#42;But I want to start running the Data Task at 100Hz without sending the command to start Timer2 ISR as soon as the board is powered, then communicate with board.&#42;&#42;<br />
  With this approach i need to remove &#42;&#42;start&#42;&#42; &amp; &#42;&#42;stop&#42;&#42; timer commands.  
</blockquote>
If the timer interrupt is using a FreeRTOS function, which you indicate that it is, you cannot start it when the board powers.&nbsp; You can however start it as soon as the scheduler has started.&nbsp; To do that, place the code that starts the timer at the top of the first task that runs &#8211; before the task enters its infinite loop.  
Alternatively, before starting the scheduler, ensure interrupts are disabled &#40;they should be anyway if you have called FreeRTOS API functions to create tasks&#41;, then start the timer.&nbsp; As interrupts are disabled the interrupts generated by the timer will not execute.&nbsp; Interrupts will be enabled automatically when the first task starts running, at which time the timer interrupts will start to be processed safely.  
<blockquote>
  &#42;&#42;Problem:&#42;&#42; Some times, I&#8217;m unable to open virtual COM port though it appears. This seems to be priorities assigned problem. I tried reversing the first three interrupt priorities, no use.  
</blockquote>
I&#8217;m afraid I can only comment on FreeRTOS issues, and the virtual com port is not part of FreeRTOS.  
Regards.
