  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS-MPU CM3. User task cannot call ENTER_CRITICAL?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mc4924">mc4924</a> on February 7, 2016</div><div class="thread-post-content">I am currently experimenting with FreeRTOS with MPU for Cortex M3.
It seems to me that given the settings in FreeRTOSConfig.h, an <em>unprivileged task</em> will never be able to use taskENTER_CRITICAL.
For instance, this is from the CORTEX<em>MPU</em>LM3Sxxxx_Rowley port:
<strong>FreeRTOSConfig.h</strong>
~~~~
&#8230;
<h1>define configKERNEL<em>INTERRUPT</em>PRIORITY  (( unsigned char ) 7 &lt;&lt; configUNUSED<em>PRIO</em>BITS)</h1>
&#8230;
<h1>define configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY  (( unsigned char ) 5 &lt;&lt; configUNUSED</em>PRIO_BITS)</h1>
&#8230;
~~~~
&#8216;KERNEL<em>INTERRUPT</em>PRIORITY&#8217; is the priority that is assigned to <strong>SysTick</strong>, <strong>SVC</strong> and <strong>pendSV</strong> Handlers
&#8216;MAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY&#8217; is the priority that is used in ENTER</em>CRITICAL. Any exception/interrupt with same or below  priority will be masked out between ENTER<em>CRITICAL and EXIT</em>CRITICAL.
But if KERNEL<em>INTERRUPT</em>PRIORITY is lower or same as MAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY, as it is here (bigger or equal numerical value), after ENTER</em>CRITICAL is called, the task will not be able to execute another SVC (which will have too low  a priority now), including calling EXIT<em>CRITICAL! (because EXIT</em>CRITICAL calls prvRaisePrivilege, which uses SVC 2).
So I could do one of two things:
1. give KERNEL<em>INTERRUPT</em>PRIORITY a higher priority than MAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY
2. give just the SVC handler a higher priority  than MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY
In both cases a small test application seems to work ok (i.e. a non privileged call can use ENTER_CRITICAL/EXIT CRITICAL) but I am not sure of the ramifications of this.
The priorities seem to be set this way (KERNEL<em>INTERRUPT</em>PRIORITY lower than MAX<em>SYSCALL</em>INTERRUPT_PRIORITY) for most if not all M3/M4 ports, so I guess there must be a good reason for this.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU CM3. User task cannot call ENTER_CRITICAL?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 7, 2016</div><div class="thread-post-content">I think it is deliberate that an unprivileged task cannot call enter/exit critical directly as doing so disables a subset of interrupt priorities &#8211; which only tasks running with full privileges can do.
The maximum system call priority is normally above the kernel interrupt priority to allow for a full interrupt nesting model where API calls can be made from interrupts that have a priority above the kernel interrupt priority (the kernel must always be the lowest interrupt priority).
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU CM3. User task cannot call ENTER_CRITICAL?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mc4924">mc4924</a> on February 7, 2016</div><div class="thread-post-content">Thank you for the prompt answer to my question.
Thinking about it,I guess it makes sense wanting to avoid unprivileged task blocking exceptions.
However if I was stubborn and still wanting to be able to ENTER/EXIT_CRITICAL from unprivileged tasks (maybe because I have just a very short critical section) I guess it would be better to adopt my solution n. 2 (give just the SVC a higher priority).
After all the SVC itself is quite short in itself so putting in at high priority will have a limited impact on interrupt latency.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-MPU CM3. User task cannot call ENTER_CRITICAL?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hengblom">hengblom</a> on July 30, 2016</div><div class="thread-post-content">Waking up this old thread since I ran into exactly the same problem when experimenting with MPU on Coretx-M3.
You say that it is a deliberate design that an unprivileged task shall not be able to enter a critical section. I can understand that, sort of, but if so, why does this code:
void vPortEnterCritical( void )
{
BaseType_t xRunningPrivileged = xPortRaisePrivilege();
<pre><code>portDISABLE_INTERRUPTS();
uxCriticalNesting++;
vPortResetPrivilege( xRunningPrivileged );
</code></pre>
}
check if we are unprivileged, and if so, raise the privilege level ? If an unprivileged task should not be allowed to enter a critical section, it would have been better just to assume that the task is privileged, and if it isn&#8217;t, let it crash when trying to disable interrupts. It will, as the Claudio says, crash anyway when doing EXIT-CRITICAL.
