  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">On pdMS_TO_TICKS macro definition</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/teabun">teabun</a> on February 26, 2016</div><div class="thread-post-content">Currently pdMS<em>TO</em>TICKS is defined as
~~~~
<h1>define pdMS<em>TO</em>TICKS( xTimeInMs ) ( ( TickType<em>t ) ( ( ( TickType</em>t ) ( xTimeInMs ) * ( TickType<em>t ) configTICK</em>RATE<em>HZ ) / ( TickType</em>t ) 1000 ) )</h1>
~~~~
There is a potential issue when xTimeInMs is a very large value, and configTICK<em>RATE</em>HZ is a maximum of 1000.
The result of xTimeInMs * configTICK<em>RATE</em>HZ may overflow, since both are type-casted to TickType<em>t, and the final result of pdMS</em>TO_TICKS() will be wrong.
My fix in which my TickType_t is *unsigned long* is as below:
~~~~
<h1>define pdMS<em>TO</em>TICKS( xTimeInMs ) ( ( TickType<em>t ) ( ( ( xTimeInMs ) * configTICK</em>RATE_HZ * 1ULL ) / 1000 ) )</h1>
~~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">On pdMS_TO_TICKS macro definition</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 26, 2016</div><div class="thread-post-content">Thanks for reporting this.
~~~~
    #define pdMS<em>TO</em>TICKS( xTimeInMs )
        ( ( TickType<em>t ) ( ( ( xTimeInMs ) * configTICK</em>RATE_HZ * 1ULL ) / 1000 ) )
~~~~
I would rather see an explicit cast to &#8216;uint64_t&#8217;:
~~~~
    #define pdMS<em>TO</em>TICKS( xTimeInMs )
        ( ( TickType<em>t ) ( ( ( uint64</em>t ) ( xTimeInMs ) * configTICK<em>RATE</em>HZ ) / 1000 ) )
~~~~
But there is a downside: some platforms do not implement 64-bit calculations or at a high cost. On a 8-bit MCU, a 64-bit calculation can be very expensive. In other situations, people don&#8217;t like to link in a 64-bits library to safe space in flash.
When this is not a problem then go ahead.
Another problem that has been mentioned with <code>pdMS_TO_TICKS</code> is that it may return 0. When you want a task to sleep (block), you might want a minimum of 2 clock ticks, to get at least a single clock tick.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">On pdMS_TO_TICKS macro definition</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 26, 2016</div><div class="thread-post-content">I agree with Hein that we cannot, by default, use 64-bit calculations.  Perhaps the best thing would be to leave the default calculation as it is, but then to allow the macro to be overridden in FreeRTOSConfig.h?  So the definition becomes:
~~~~
<h1>ifndef pdMS<em>TO</em>TICKS</h1>
<pre><code>#define pdMS_TO_TICKS( xTimeInMs ) ( ( TickType_t ) ( ( ( TickType_t ) ( xTimeInMs ) * ( TickType_t ) configTICK_RATE_HZ ) / ( TickType_t ) 1000 ) )
</code></pre>
<h1>endif</h1>
~~~~
The user could then define it to whatever they like.
Also remember that the macro is not used by the FreeRTOS code, it is only there for the convenience of application writers, who might choose not to use it at all.  It is also used a lot in the demo code.
</div></div><div class="thread-post"><h3 class="thread-post-title">On pdMS_TO_TICKS macro definition</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 26, 2016</div><div class="thread-post-content">One modification that I would also suggest is you should round UP the result, not down as default in C math. You can do this by adding 999 before dividing by 1000. That way a 1 ms delay on a 100 Hz tick system gives you a delay of 1 tick, not 0.
There also is the issue that many miss that an 1 tick delay is a delay to the next tick, which might happen almost immediately. If you really need a delay for at least a specified period, you need to add 1 to the number of tick to make sure you delay long enough. A delay of 1 give no minimum delay and is more like a yield, except it lets lower priority tasks execute also.
</div></div><div class="thread-post"><h3 class="thread-post-title">On pdMS_TO_TICKS macro definition</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/echristenson">echristenson</a> on March 29, 2017</div><div class="thread-post-content">Just ran into the overflow problem on this macro, as I&#8217;m using just 16-bit ticks, needing only a 10 second (10,000 tick) horizon for everything except the hourmeter:
<blockquote>
  &#8220;pound&#8221;define configUSE<em>16</em>BIT<em>TICKS          1
  &#8220;pound&#8221;define configTICK</em>RATE<em>HZ              ( ( TickType</em>t ) 1000 )
</blockquote>
The problem with re-writing it really boils down to implementation details:  If I use a constant argument that is computed at compile time, or even just once at startup, it doesn&#8217;t matter whether 64 bit types are implemented on the target or not.    Modern, fast targets wouldn&#8217;t care if it was a run-time function, but I&#8217;m really not at all CPU-power conscious.
The &#8220;proper&#8221; size of the arguments in the calculation (defined by expectations as a naive user) would need to be sizeof(argument)+sizeof(TickType<em>t), which we can conservatively decide should be 
2 * sizeof(TickType</em>t).   Good luck properly expressing that in the C programming language, especially in a portable, simple way &#8212; you&#8217;d need some decent typedef magic.
A warning in the examples is probably best, as if the definition had been partially &#8220;fixed&#8221;,say, with uint32 casts, it just hides the problem until <em>much</em> later.
For myself, I&#8217;m modifying projdefs.h and putting my definition (with a warning) in FreeRTOSConfig.h.
</div></div><div class="thread-post"><h3 class="thread-post-title">On pdMS_TO_TICKS macro definition</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 29, 2017</div><div class="thread-post-content">You should not need to edit any of the core FreeRTOS source files, just define pdMS<em>TO</em>TICKS() however you want in FreeRTOSConfig.h.  The default definition appears as below, so will only be used if pdMS<em>TO</em>TICKS is not defined elsewhere.
~~~
<h1>ifndef pdMS<em>TO</em>TICKS</h1>
<pre><code>#define pdMS_TO_TICKS( xTimeInMs ) ( ( TickType_t ) ( ( ( TickType_t ) ( xTimeInMs ) * ( TickType_t ) configTICK_RATE_HZ ) / ( TickType_t ) 1000 ) )
</code></pre>
<h1>endif</h1>
~~~
