  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">portRESTORE_CONTEXT &#8211; broken under SAM7/GCC?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 26, 2005</div><div class="thread-post-content">Hey all,
I&#8217;m trying to migrate from IAR to Rowley tools, which use GCC.
It is important to note that everything below should be read knowing that the exact same code &#40;save for GCC/IAR extension differences&#41; has been working fine under IAR.
I&#8217;m compiling the project under THUMB release with no optimizations. portISR.c is compiled under ARM, and of course Interworking is enabled.
As no Rowley SAM7S port is available, I&#8217;ve decided to do something based on the GCC SAM7 port &#40;found under SourceportableGCCARM7&#95;AT91SAM7S&#41;.
My program lives &#40;peripherals initializing well, etc&#41;, but when it gets to starting the scheduler, bad things happen.
It goes to xPortStartScheduler&#40;&#41; &#40;from the generic scheduler init code&#41;, after tasks have been created successfully.
From there, it goes to vPortISRStartFirstTask&#40;&#41;, which is located under portISR.c. GCC Interworking does it&#8217;s magic, the processor is under ARM mode.
Now what happens in vPortISRStartFirstTask&#40;&#41; is that the Scheduler attempts to restore the idle task context and start running from there, using the portRESTORE&#95;CONTEXT&#40;&#41; macro &#40;defined in portmacro.h&#41;. While in this macro, the system hangs &#40;jumps to data abort vector&#41;. 
From what I understand, the culpruit lies in these three lines:
========================
/&#42; Restore all system mode registers for the task. &#42;/
asm volatile &#40; &quot;LDMFD LR, &#123;R0-R14&#125;^&quot; &#41;;&nbsp;&nbsp;&nbsp; 
asm volatile &#40; &quot;NOP&quot; &#41;;
/&#42; Restore the return address. &#42;/
<h1>asm volatile &#40; &quot;LDR LR, &#91;LR, &#35;+60&#93;&quot; &#41;;</h1>
What happens is that LR is loaded with the default TCB stack initialization data &#40;from port.c/pxPortInitialiseStack&#40;&#41;&#41;, in this case that equals to 0xaaaaaaaa.
Needless to mention, LDR LR, &#91;LR, &#35;+60&#93; yields an alignment error &#40;and the resulting data abort exception&#41;.
In the IAR port case &#40;SAM7&#95;IAR&#41;, with different synatx yet nearly identical assembly &#40;in ISR&#95;Support.h&gt;, the above lines seem to load everything BUT R13 and R14, despite being 100% identical&#33;
What did I miss?
</div></div><div class="thread-post"><h3 class="thread-post-title">portRESTORE_CONTEXT &#8211; broken under SAM7/GCC?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 26, 2005</div><div class="thread-post-content">Ok, just solved the mystery, or so it seems.
For some reason, the processor is under different modes in each of the ports &#8211; under Supervisor mode in the IAR case and under System mode in GCC case. That&#8217;s at least what it looks like.
That causes the LDMFD instruction to actually load the data into different R13, R14 regs &#40;the processor got few sets of those, one for each mode&#41;.
Well, gotta go now, I&#8217;ll be back to report my findings tomorrow, after some sleep&#8230;
</div></div><div class="thread-post"><h3 class="thread-post-title">portRESTORE_CONTEXT &#8211; broken under SAM7/GCC?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 26, 2005</div><div class="thread-post-content">&gt; As no Rowley SAM7S port is available, I&#8217;ve decided to do something based on

&gt; What did I miss?
1&#41; Using the existing port.
2&#41; Placing the processor into Supervisor mode before starting the first task.
:-&#41;
Rowley makes life easy by providing the definition SUPERVISOR&#95;START &#40;or something similar&#41;, which does what you want.&nbsp; You therefore don&#8217;t have to change the startup code just the preprocessor settings &#8211; but will want to check the stacks are setup as required for the Supervisor and IRQ modes as a minimum.&nbsp; Setup other stacks also if your application requires it.
Best bet is to use the existing port project file as a basis for creating your application.&nbsp; This way you get the compiler settings &#40;such as SUPERVISOR&#95;START&#41; and startup code that will work &quot;out of the box&quot;.&nbsp; Once you have the example working you can then start removing the demo files and replacing them with your application code.
Regards,
Richard.
</div></div><div class="thread-post"><h3 class="thread-post-title">portRESTORE_CONTEXT &#8211; broken under SAM7/GCC?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 26, 2005</div><div class="thread-post-content">&gt; Ok, just solved the mystery, or so it seems.
&gt; 
&gt; For some reason, the processor is under different modes in each of the ports
&gt; &#8211; under Supervisor mode in the IAR case and under System mode in GCC case. 
In all ports the kernel runs in Supervisor mode and tasks run in System mode.
When creating your new port you have not placed the processor in Supervisor mode before starting the processor.&nbsp; I normally do this from the startup code, prior to calling main&#40;&#41;.
As per my reply to your original post &#8211; Rowley allows this just by defining SUPERVISOR&#95;START as a macro.
Hopefully when you try the existing supported Rowley port you will be able to get up and running quickly.&nbsp; I think you will just have to replace the SAM7X headers with SAM7S headers.&nbsp; Although even this might not be necessary as I think the S derivatives might be a subset of the X derivatives and have their common peripherals at the same register locations.&nbsp; You will obviously have to remove the files that access the MAC &#8211; being primarily the lwIP source files, the BasicWEB server example file and the SAM7&#95;EMAC driver files.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">portRESTORE_CONTEXT &#8211; broken under SAM7/GCC?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dmwilliams66">dmwilliams66</a> on October 26, 2005</div><div class="thread-post-content">I&#8217;ve just been doing a similar thing.&nbsp; I got FreeRTOS to run under Rowley on my Sam7S64 Ek board.&nbsp; I had the same error as you at the beginning.&nbsp; At the time, I thought I had fixed it by correcting my inclusion of Sam7X headers, by replacing them with Sam7S headers. Then I got to the next problem&#8230; no IRQ&#8217;s&#8230; then the next, etc. etc&#8230;
I like the FreeRTOS port because it uses all the standard Atmel headers.&nbsp; So much easier for possible future migration to a purely Open Source solution.
Here are the things I remember I did.
1&#41; you have to reduce the size of the heap
FreeRTOSConfig.h Line 56
&#35;define configTOTAL&#95;HEAP&#95;SIZE&nbsp;&nbsp;&nbsp; &#40; &#40; size&#95;t &#41; 13000 &#41;
You may need to check if there&#8217;s enough memory for your app.&nbsp; If the system runs out of memory at some crucial point, you&#8217;ll find the main&#40; &#41; returns and the processor parks it in some fast loop.
&nbsp; /&#42; Return from main, loop forever. &#42;/
exit&#95;loop:
&nbsp; b exit&#95;loop
2&#41; you&#8217;ll need to remove all the LWIP and Web stuff, but I&#8217;m guessing you did that already.
3&#41; be careful of the IRQ differences between IAR and Rowley.&nbsp; IAR needs small ASM snippets around its IRQ routines, Rowley &#40;GCC&#41; does not.&nbsp; Taking the Sam7X code as a base should help here.
4&#41; Rowley&#8217;s Interrupt project sample also illustrates a curious thing, there&#8217;s a single line of code in the main.c that assigns the IRQ vector.&nbsp; 
&nbsp; // Put LDR PC, &#91;PC, &#35;-0xF20&#93; instruction into IRQ vector in order to use 
&nbsp; // hardware interrupt vectoring.
&nbsp; &#42;&#40;volatile unsigned int &#42;&#41;0x00000018 = 0xE51FFF20;
In the FreeRTOS code, this is done in the AT91SAM7&#95;startup.S file, line 72&#8217;ish.
&nbsp; nop
&nbsp; ldr pc, &#91;PC, &#35;-0xF20&#93;&nbsp;&nbsp;&nbsp; /&#42; irq &#42;/
If you don&#8217;t have it, your code will not respond to FreeRTOS interrupts.
I&#8217;m still getting everything smoothed out, and since I&#8217;m just starting with this, I&#8217;m a struggling little.
I can send you my project if you like email me &quot;david&quot; domain is &quot;makingthings.com&quot;.
David,
