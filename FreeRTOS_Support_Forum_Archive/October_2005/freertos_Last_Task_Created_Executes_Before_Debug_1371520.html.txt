I&#8217;m using the IAR debugger &#8211; I&#8217;ve noticed the following:
The last task created seems to execute at least once before the debugger starts.
I have counters in my tasks that will count how many times they run, errors, etc. similar to those in the example code.
I&#8217;ve noticed that the last task created seems to execute at least once before the debugger starts &#40;halts the system &#8211; that is, for a debugging session&#41;.
Since the scheduler is started in main&#40;&#41; &#8211; and that isn&#8217;t called &#40;allegedly&#41; before the debugger starts &#8211; I don&#8217;t know how&nbsp; vTaskStartScheduler&#40;&#41; gets called before the debugger starts.
xTickCount shows something like 10 and the run counter
for the last task created shows 1.
Just wondering if anyone else has seen something similar and can give any insight as to what&#8217;s going on.
It obviously seems that the scheduler starts somehow before the debugger begins.
The other odd thing here is that the last task created seems to be the one that runs &#8211; even though vTaskSuspend&#40;&#41; is immediately called after it&#8217;s created.
Thanks,
John W.
</div></div><div class="thread-post"><h3 class="thread-post-title">Last Task Created Executes Before Debug</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 21, 2005</div><div class="thread-post-content">Which processor are you using?
Where are you placing the break point?
If you are placing the break point on the vTaskStartScheduler&#40;&#41; function then you should find that no tasks have yet executed, and your execution counts are all zero &#40;naturally&#41;.&nbsp; If one of your execution counts is not zero then there is a hint of memory corruption occurring some place.
The last task created is not necessarily the first task to execute, depending on priorities.&nbsp; Are you saying that placing a break point in the task itself before a call to vTaskStartScheduler&#40;&#41; you find that the execution count has already incremented when the break point is first hit?&nbsp; That would be odd.&nbsp; Again maybe the variable is corrupted, rather than legitimately incremented.
Try switching to the cooperative scheduler, just for a test, then stepping through the startup of the scheduler so you can see which tasks run and in which order.
</div></div><div class="thread-post"><h3 class="thread-post-title">Last Task Created Executes Before Debug</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 21, 2005</div><div class="thread-post-content">MSP430F1611IPM
The debugger starts at main&#40;&#41; .
Possible the task execution variable is invalid I suppose &#8211; all others read 0 &#40;zero&#41;.
xTickCount shows something like 10 &#8211; which indicates it ran briefly.
I&#8217;ll try the cooperative scheduler to see if the same thing occurs.
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">Last Task Created Executes Before Debug</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 21, 2005</div><div class="thread-post-content">The tick counter cannot be incremented by the kernel until after the scheduler has been started simply because the timer interrupt is not configured until that time&#33;&nbsp; However, an incorrect debugger configuration may actually cause this to happen as per item 2&#41; below&#8230;..
Two possibilities:
1&#41; The variables are not being initialised correctly by the startup code prior to main&#40;&#41; being called.
2&#41; Does this happen on the first execution after the hardware has been turned on?&nbsp; I suspect not, and that it only happens following at least one download, debug cycle.&nbsp; If the latter is the case then I strongly suspect that the problem will be with the debugger macros.&nbsp; If the MSP430 IDE works in the same way as the ARM7 IDE then there are various macros that can be called to configure the hardware at various times during the download process.&nbsp; These macros basically reset the hardware to its initials state &#40;turn timers off, reset UARTS, uninstall interrupt handlers, etc.&#41;.&nbsp; If you have downloaded and executed the code once then the tick interrupt will have been configured.&nbsp; When you download the code again the debugger macros should &#8216;unconfigure&#8217; it again.&nbsp; If this is not happening then the timer will continue to generate interrupts as the code is downloaded, and during the startup code, and this is a really, really bad thing as the scheduler will be in an inconsistent state during the initialisation.
I have had a similar experience using IAR with ARM.&nbsp; Is there a .mac file that is being used by your project?&nbsp; If so take a look in it to see what it is doing.&nbsp; Also as you download the code you should get some print out in the IDE about what the debugger is doing as far as initialisation goes.
Regards.
