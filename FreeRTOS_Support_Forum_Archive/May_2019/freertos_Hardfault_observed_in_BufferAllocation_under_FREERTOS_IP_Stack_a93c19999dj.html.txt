</div></div><div class="thread-post"><h3 class="thread-post-title">Hardfault observed in BufferAllocation under FREERTOS IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 24, 2019</div><div class="thread-post-content">Hi,
<blockquote>
  It was a Hardfault. (A configAssert call probably)
</blockquote>
Was it is a hard-fault or a <code>configAssert()</code>? The latter is easier to solve.
The former will end-up in <code>HardFault_Handler()</code>. Both end in a for-ever-loop.
Do you  have<code>configAssert()</code> properly defined?
Often in NetworkInterface.c, you will see calls to <code>uxGetNumberOfFreeNetworkBuffers()</code> and <code>uxGetMinimumFreeNetworkBuffers()</code>. It produces logging when the levels get low. Do you have that logging enabled?
And while you are testing, it is also good to keep an aye on the available heap memory. Both heap<em>4 and heap</em>5 are very good. I like heap_5 because you can determine dynamically how much RAM is actually available.
Can you confirm that <code>xNetworkBufferSemaphore</code> is created and valid?
You are not allocating a Network Buffer or using the +TCP API&#8217;s before <code>FreeRTOS_IPInit()</code> has successfully finished?
In more general terms: problems with Network Buffers are usually caused by:
<ul>
<li>Forgetting to release buffers</li>
<li>Releasing a buffer more than one time</li>
<li>Accessing more memory in <code>pucEthernetBuffer</code> than allocated</li>
</ul>
The free network buffers are stored in a <code>List_t</code>, which is guarded by a counting semaphore. Updates to <code>List_t</code> need critical sections.
</div></div><div class="thread-post"><h3 class="thread-post-title">Hardfault observed in BufferAllocation under FREERTOS IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ingamow">ingamow</a> on May 24, 2019</div><div class="thread-post-content">Hi,
<blockquote>
  You are not allocating a Network Buffer or using the +TCP API&#8217;s before FreeRTOS_IPInit() has successfully finished?
</blockquote>

Fixing this, sort of solved the issue. Need to do more stability tests to confirm it.
Anyway thanks so much for your feedback Mr. Hein Tibosch 
</div></div><div class="thread-post"><h3 class="thread-post-title">Hardfault observed in BufferAllocation under FREERTOS IP Stack</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 25, 2019</div><div class="thread-post-content">Glad you&#8217;ve found where the problem is, and thanks for taking the effort to report back.
It looks like you don&#8217;t have <code>configASSERT()</code> enabled. <code>xQueueSemaphoreTake()</code> is called while <code>pxQueue</code> is NULL. But also with <code>configASSERT()</code> enabled, your program would get stuck.
<code>BufferAllocation_1.c</code> does check if <code>xNetworkBufferSemaphore</code> has been created, and I will propose to make the same check in <code>BufferAllocation_2.c</code>. See my pull request <a href="https://github.com/aws/amazon-freertos/pull/674">here</a>
