  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Bringing up a SAM4S with Keil and FreeRTOS, Failure in XPortStartScheduler with configPRIO_BITS check</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ppotts">ppotts</a> on May 23, 2019</div><div class="thread-post-content">Hello all,
I have previously used FreeRTOS successfully for a project targeting the SAM4E16E. I&#8217;m now doing a project on a SAM4S2A and having some trouble. I&#8217;m using Keil uVision V5.27.1.0.
I noticed that recent uVision project wizards had the ability to include FreeRTOS, so I did that when configuring the project, rather than using the manually-configured version as in the older project. It seems like there is some conflict in how the priority bits are defined.
I&#8217;m getting a failure in xPortStartScheduler, particularly the line:
configASSERT( ( portMAX<em>PRIGROUP</em>BITS &#8211; ulMaxPRIGROUPValue ) == configPRIO_BITS );
The version of port.c I&#8217;m using comes from:
Keil<em>v5ARMPACKARMCMSIS-FREERTOS10.2.0SourceportableGCCARM</em>CM3port.c
I&#8217;m not sure this is the right version, but the values in the CM4 versions looked similar.
portMAX<em>PRIOGROUP</em>BITS is defined as 7
The version of FreeRTOSConfig.h I&#8217;m using was created under RTERTOSFreeRTOSConfig.h and defines configPRIO_BITS like this:
~~~
<h1>ifdef __NVIC<em>PRIO</em>BITS</h1>
  /* __NVIC<em>PRIO</em>BITS will be specified when CMSIS is being used. */
  #define configPRIO_BITS                     __NVIC_PRIO_BITS
<h1>else</h1>
  /* 7 priority levels */
  #define configPRIO_BITS                     3
<h1>endif</h1>
~~~
NVIC<em>PRIO</em>BITS comes from the pack: SAM4DFP1.6.1DeviceIncludeSam4Ssam4s2b.h where it is defined as 4.
So, it appears that maybe when parsing FreeRTOS.h, NVIC<em>PRIO</em>BITS is not in scope, and therefore we&#8217;re getting configPRIO_BITS equal to 3, and the runtime value of ulMaxPRIGROUPValue is 3, so it&#8217;s checking to see if 7 &#8211; 3 == 3.
I could do something to hack these generated files so NVIC<em>PRIO</em>BITS would be in scope when FreeRTOSConfig.h is parsed, but it seems like this should be something that the generated project code took care of. I&#8217;d like to do this the &#8220;right way&#8221; if possible. Any ideas where it went wrong?
Thanks,
Paul
</div></div><div class="thread-post"><h3 class="thread-post-title">Bringing up a SAM4S with Keil and FreeRTOS, Failure in XPortStartScheduler with configPRIO_BITS check</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 23, 2019</div><div class="thread-post-content">Are you saying that if configPRIO<em>BITS is manually set to 4 in
FreeRTOSConfig.h then the configASSERT() passes?  If so then it does
seem to be an include dependency issue somewhere &#8211; to which I would ask
have ARM changed the source files in any way?  FreeRTOS.h must always be
included first, then the header file for the APIs you are using (task.h,
queue.h, event</em>groups.h, etc.) &#8211; and never include FreeRTOSConfig.h
manually as it is brought in at the right time by FreeRTOS.h.
If it is not a dependency  issue, and port.c is genuinely using
__NVIC<em>PRIO</em>BITS and not the hard coded 3, and __NVIC<em>PRIOR</em>BITS is set
correctly for the device (more than once found that not to be the case),
then most likely cause is that somewhere in the start up code the
priority bits are being split between preemption and sub priorities.
That is normal on STM32, where has to be manually switched back to all
preemption priority and no sub priority (what it needs to be), but I&#8217;ve
never seen anything like that on a SAM device.
