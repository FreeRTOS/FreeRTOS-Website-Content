I&#8217;m new to embedded RTOS and I have encountered an issue where vTaskDelay() is not accurate.
i&#8217;m running a &#8220;FreeRtos Sam Example&#8221; project on Atmel Studio (SAME70 Board) that blinks the LED at a fixed rate. 
led task code as follows:
static void task_led(void *pvParameters)
{
    UNUSED(pvParameters);
<pre><code>for( ; ; ) {
    LED_Toggle(LED4);
    vTaskDelay(1000);
}
</code></pre>
}
This task is triggered every two seconds instead of one second (as intended by vTaskDelay(1000)). I did not make any changes to the code, configCPU<em>CLOCK</em>HZ is set as 1000.
Can anyone verify if this is true or point out the direction which I should be looking to check for sysTick rate?
Thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS tick interrupt not accurate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 24, 2019</div><div class="thread-post-content">You code looks Ok.
So what you observe is a LED that is on for 2 seconds, and then off for 2 seconds?
I would check the clocks of the SAME70 at start-up: is it assuming a correct speed of the X-tal? Is the processor running at the expected speed?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS tick interrupt not accurate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 24, 2019</div><div class="thread-post-content">The value of configCPU<em>CLOCK</em>HZ looks suspicious.  Are you using the
SysTick clock to generate tick interrupts?  If so I would expect it to
be in the MHz range, not 1Khz.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS tick interrupt not accurate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 25, 2019</div><div class="thread-post-content">Maybe the following helps:
<code>configCPU_CLOCK_HZ</code> is the clock rate of the CPU, up to 300 MHz for SAM E70
<code>configSYSTICK_CLOCK_HZ</code> is the clock rate that feeds the systick, possibly the same as <code>configCPU_CLOCK_HZ</code>
<code>configTICK_RATE_HZ</code> is the desired FreeRTOS tick rate, which you will put to 1000
For SAME70, the systick is initialised in <code>portable/gcc/ARM_CM7/r0p1/port.c</code> in the function <code>vPortSetupTimerInterrupt()</code> Could you check these defines and find-out the logic?
I think that:
~~~
<h1>define configCPU<em>CLOCK</em>HZ                      ( SystemCoreClock )</h1>
~~~
could you check or print the actual value of <code>SystemCoreClock</code>?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS tick interrupt not accurate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kyanc">kyanc</a> on May 27, 2019</div><div class="thread-post-content">Thanks for the replies.
@RichardBarry my mistake, i meant configTICK<em>RATE</em>HZ  = 1000.
@Hein Tibosch yes that is correct, the LED is on for 2 seconds then off for 2 seconds.
i ran a demo project without FreeRTOS (same board config settings) , no issue with tick timing. LED swtiched on for 1 second and off for 1 second.
<strong>same70_xplained.h</strong>
/#define    BOARD_MCK        300000000UL
<strong>freeRTOSconfig.h</strong>
checking on the settings, i noticed that:
/#define    configCPU<em>CLOCK</em>HZ        (BOARD_MCK &lt;&lt; 1UL)
seems like freeRTOSconfig.h defines the configCPU<em>CLOCK</em>HZ, in this case to 600MHz.
changing this value to 300MHz resulted in the correct tick rate.
I am not sure what is the reason for the left shift bit, can i assumed that it will be alright for me to just #define configCPU<em>CLOCK</em>HZ        BOARD_MCK ?
just for fun (thinking why the rate will be slower at 600MHz), I tested it with 150MHz and it resulted in a faster tick rate (0.5s). Would you happen to have any explanation as to why lowering the CPU clock rate resulted in a faster tick rate?
