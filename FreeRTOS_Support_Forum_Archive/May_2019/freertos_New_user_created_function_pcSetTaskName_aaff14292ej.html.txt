However, I&#8217;ve had to place this code within tasks.c/task.h, which has obvious drawbacks and could be condsidered going against many conventions.
My post is two fold, 
First, would/could there be any consideration to adding this function to FreeRTOS in future versions, as I feel it does serve a purpose.
Second, if anyone has some suggestions as to incorporate this routine from outside of tasks.c so the sanctity of the kernel is not touched, I would be most grateful. The function appears to be referencing items from within tasks.c that cannot be seen outside of it.
Included here is the code used for this function. It is basically a modification of pcgetTaskName:
~~~
void pcTaskSetName( TaskHandle<em>t xTaskToQuery, char *newName )
{
TCB</em>t *pxTCB;
<pre><code>/* If null is passed in here then the name of the calling task is being

pxTCB-&gt;pcTaskName[configMAX_TASK_NAME_LEN - 1] = 0;
</code></pre>
}
~~~
and the associated h file content in task.h:
~~~
/**
 * task. h
 * <pre>char *pcTaskSetName( TaskHandle_t xTaskToQuery, char *newName );</pre>
 *
 * @return The text (human readable) name of the task referenced by the handle
 * xTaskToQuery.  A task can query its own name by either passing in its own
 * handle, or by setting xTaskToQuery to NULL.
 *
 * defgroup pcTaskGetName pcTaskGetName
 * ingroup TaskUtils
 */

~~~
Appreciate any thoughts.
</div></div><div class="thread-post"><h3 class="thread-post-title">New user created function: pcSetTaskName</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 29, 2019</div><div class="thread-post-content">To add your own code into tasks.c without editing the source file:
1) Create a file called freertos<em>tasks</em>c_additions.h and place it
somewhere in the compiler&#8217;s include path.
2) Add you code into the new header file.
3) Set configINCLUDE<em>FREERTOS</em>TASK<em>C</em>ADDITIONS_H to 1 in FreeRTOSConfig.
Now the header file will be included inline at the bottom of tasks.c :o)

~~~
<h1>if( configINCLUDE<em>FREERTOS</em>TASK<em>C</em>ADDITIONS_H == 1 )</h1>

the file and could just be in the same extensions header file &#8211; if I&#8217;m
not talking around in circles here.

</div></div><div class="thread-post"><h3 class="thread-post-title">New user created function: pcSetTaskName</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on May 31, 2019</div><div class="thread-post-content">One last quick comment on your last code you showed.
You do NOT need to surrond the includes of FreeRTOS.h and task.h with an extern &#8220;C&#8221; decleration, as they were written to include that internally. Generally #include statements shouldn;t be inside ANY block structure (unless specifically designed to be). The extern &#8220;C&#8221; sometimes is needed to wrap headers that didn&#8217;t take C++ into consideration, but the extern &#8220;C&#8221; can cause issues if done indiscriminatory.
Your additions header, if it is to usable (even potentially) with C++ should be designed with
~~~
<h1>ifdef __cplusplus</h1>
extern &#8220;C&#8221; {
<h1>endif</h1>
// Prototypes for C code here
<h1>ifdef __cplusplus</h1>
}
<h1>endif</h1>
~~~
So the code is valid for both C and C++ and establishes the proper linkage.
