</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FAT    FF_FlushCache Function Implementation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 7, 2019</div><div class="thread-post-content">Kevin, you&#8217;re diving deep into it 🙂
A task that calls <code>prvGetFromFATBuffers()</code> is reading from, and/or writing to the FAT area.
It has a buffer of the type <code>FF_FATBuffers_t</code>, which contains either 1 or 2 cache buffers, depending on whether a shadow FAT must be maintained.
In an earlier version, <code>prvGetFromFATBuffers()</code> did not exists yet, and <code>FF_GetBuffer()</code> was called directly.
It turned out useful to reuse buffers whenever possible. You also see that the usefulness was empirically tested by maintaining statistics ( <code>ffconfigFAT_USES_STAT</code> ).
The rule that I mentioned earlier:
<ul>
<li>A WRITE buffer can only have a single user</li>
<li>A READ buffer can have multiple users</li>
<li>You can not obtain a WRITE buffer as long as a READ buffer exists ( and has owners )</li>
<li>You can not obtain a READ buffer as long as a WRITE buffer exists ( and has an owner )</li>
</ul>
<code>prvGetFromFATBuffers()</code> is obeying the rules except one situation: when it is looking for READ access and it finds that it already owns a WRITE buffer <strong>for the same sector</strong>.  That is considered OK.  It saves this action:
~~~
    /* Release the buffer with FF<em>MODE</em>WRITE access. <em>/
    FF_ReleaseBuffer( pxIOManager, pxBuffer );
    /</em> Get a buffer with READ access. */
    pxBuffer = FF_GetBuffer( pxIOManager, ulFATSector, FF_MODE_READ );
~~~
The above would be quite costly and have no advantage.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + FAT    FF_FlushCache Function Implementation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 8, 2019</div><div class="thread-post-content"><blockquote>
  it also bypass the mechanism that around the pxMatchingBuffer->usNumHandles
  and pxMatchingBuffer->usPersistance. Does it OK?
</blockquote>
It does not bypass these rules, it is not a back-door. <code>usNumHandles</code> and <code>usPersistance</code> are maintained by <code>FF_GetBuffer()</code> and <code>FF_ReleaseBuffer</code>.
The only thing special that it can do is the combination of read/write on a WRITE buffer: which is very efficient when updating FAT sectors.
Something about WRITE buffers: when obtaining a buffer in WRITE mode, you can choose to either read the contents of the sector from disk, or have the buffer cleared.
When you write data to an ever growing file, it is useless to read newly allocated sectors: you will overwrite all data. In this situation, the pseudo attribute <code>FF_MODE_WR_ONLY</code> is used:
~~~
<h1>define FF<em>MODE</em>READ      0x01  /* Buffer / FILE Mode for Read Access. */</h1>
<h1>define FF<em>MODE</em>WRITE     0x02  /* Buffer / FILE Mode for Write Access. */</h1>
<h1>define FF<em>MODE</em>WR_ONLY   0x42  /* Buffer for Write-only Access */</h1>
~~~
The FAT functions will typically <strong>not</strong> use the write-only mode, and always read the FAT sector before updating it.
But even if <code>FF_MODE_WR_ONLY</code> is being used, you may read back what you have just written to a cache buffer.
No your question:
<blockquote>
  Does the situation that when it is looking for READ access and it finds that it already
  owns a WRITE buffer for the same sector can only be appropriate to FATBuffer, or it can
  be appropriate to all CacheBuffer ?
</blockquote>
Other functions that access the contents of files and directories, or special sectors can also read from a WRITE buffer.
