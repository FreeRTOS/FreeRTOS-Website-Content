  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Eclipse / GDB / J-Link crash diagnosis</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/eduardo1966">eduardo1966</a> on May 1, 2019</div><div class="thread-post-content">Hi
I have been facing several crashes on the program I&#8217;m developping mainly due to uninitialised pointers and such.
Being in a multitasking system does not make bug-hunting easier since things tend to happen in an  asynchronously way.
I&#8217;m using Eclipse with GDB and J-Link,
I wonder if in the many windows and menu options provided by Eclipse I can get a better diagnostic of the reasons for a crash.
At the moment I&#8217;m facing a crash in <strong><em>mallocr() at 0x436a82</em></strong> (see attachment)
It seems quite obvious taht the stack pointer register has a bad value (<strong>0xffffffac</strong>) but how can I find where this came from?
The code that seems problematic is when inside an ISR a Give semaphore operation is done:
~~~
                                if ( xSemaphoreGiveFromISR ( GNSS<em>Buffer</em>counter<em>semaphore, &amp;xHigherPriorityTaskWoken ) != pdTRUE )
                                    /* Fatal error but we are inside an interrupt routine */
                                    SP</em>Printf<em>nmh ( &#8220;ERROR &#8211; GNSS</em>process<em>character() &#8211; Couldn&#8217;t Give semaphore GNSS</em>Buffer<em>counter</em>semaphore&#8221; );
<pre><code>                            portYIELD_FROM_ISR ( xHigherPriorityTaskWoken );
</code></pre>
~~~
The semaphore has been created with:
~~~
    GNSS<em>Buffer</em>counter<em>semaphore = xSemaphoreCreateCounting ( MAX</em>NMEA<em>SENTENCES</em>IN<em>GNSS</em>BUFFER/<em>uxMaxCount</em>/, 0/<em>uxInitialCount</em>/ );
    if ( GNSS<em>Buffer</em>counter<em>semaphore == NULL )
        SP</em>Printf<em>h ( &#8220;ERROR &#8211; GNSS</em>init() &#8211; GNSS<em>Buffer</em>counter_semaphore not created&#8221; );
~~~
thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">Eclipse / GDB / J-Link crash diagnosis</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/eduardo1966">eduardo1966</a> on May 1, 2019</div><div class="thread-post-content">I&#8217;ve increased the stack from 8K to 16K (although that should be too much) but now the program stops in an ASSERT (see below) in file port.c
~~~
            configASSERT( ucCurrentPriority >= ucMaxSysCallPriority );
~~~
where ucCurrentPriority is 0 and ucMaxSysCallPriority is 160 (A0h).
There is a very interesting big comment above the ASSERT:
<blockquote>
<pre><code>  Interrupts that use the FreeRTOS API must not be left at their
        default priority of zero as that is the highest possible priority,
        which is guaranteed to be above configMAX_SYSCALL_INTERRUPT_PRIORITY,
        and therefore also guaranteed to be invalid.
</code></pre>
</blockquote>
Time to learn about Interrupt Priorities 🙂 🙂
</div></div><div class="thread-post"><h3 class="thread-post-title">Eclipse / GDB / J-Link crash diagnosis</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/eduardo1966">eduardo1966</a> on May 1, 2019</div><div class="thread-post-content">Once the priority was set to a lower level all went well.
~~~
    NVIC<em>SetPriority ( USART0</em>IRQn, 7 );
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">Eclipse / GDB / J-Link crash diagnosis</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 1, 2019</div><div class="thread-post-content">Yes &#8211; there is a very long comment above that assert which basically
says you have the interrupt priorities misconfigured ;o)
</div></div><div class="thread-post"><h3 class="thread-post-title">Eclipse / GDB / J-Link crash diagnosis</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 1, 2019</div><div class="thread-post-content">There are some Eclipse tools, such as Atollic, that will give you a
stack trace back to the offending instruction from inside of a fault
handler &#8211; although it is possible to do that manually to &#8211; there is code
on the FreeRTOS.org site that shows you how.
https://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html
 Additionally there are premium hardware tools that will enable you to
put watchpoints on data so you can set a breakpoint if data you know is
getting corrupted changes.
