  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">How to repeat xQueueSendToBack atomically?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/oek">oek</a> on December 2, 2011</div><div class="thread-post-content">Hi all,  
In my FreeRTOS project, I want to post several messages to queues &#40;from task&#41; without the possibility of a task switching until after the group of sends. I have implemented it using vTaskSuspendAll, but this appears not to work.<br />
Here is pseudo-code of the section &#40;which is called from a task not ISR&#41;:  
<pre><code>  vTaskSuspendAll(); 
  for (i = loop through routing table)
  {
    if (route exists)
    {
      os_err = xQueueSendToBack( queue[i], &amp;blockToSend_p, 0 );
      num_routes++;
    }
  }  
  blockToSend_p-&gt;num_references = num_routes;
  xTaskResumeAll();
</code></pre>
At xTaskResumeAll I have a situation that the highest prio task shown as READY in StateViewer is &#42;not&#42; the one that is scheduled next.<br />
I am aware that the FreeRTOS documentation for vTaskSuspendAll/xTaskResumeAll specifies not to use certain RTOS calls including xQueueSendToBack while suspended; however my understanding is that one may not make calls with potential to block. Using delay 0 in &#8216;send&#8217; ensures the call does not block. What should I concluded from the unexpected sheduling behaviour?<br />
A. I&#8217;ve used the wrong design.<br />
B. It&#8217;s the right design, but a stack overflow is breaking the RTOS.<br />
I tried placing a taskYeild&#40;&#41; after xTaskResumeAll&#40;&#41; but it did not fix my crashes.<br />
Should I consider using xQueueSendToBackFromISR from task in order get queue-but-don&#8217;t-reschedule behaviour?<br />
My setup: STM32F103,&nbsp; FreeRTOS 7.0.2,&nbsp; IAR EWARM 5.30 with StateViewer plugin.  
Many thanks for your suggestions.  
Owen 
</div></div><div class="thread-post"><h3 class="thread-post-title">How to repeat xQueueSendToBack atomically?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on December 3, 2011</div><div class="thread-post-content">I&#8217;m not sure if xQueueSendToBack&#40;&#41; can be used when the scheduler is suspended, it might even depend on the port being used, but if it says not to do it then it is probably best not to.  
As an alternative, try temporarily raising the priority of the task doing the sends to be above any of the tasks doing the receives, then when all the sends are complete, drop the priority back down again and the receive tasks can then run.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to repeat xQueueSendToBack atomically?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/oek">oek</a> on December 8, 2011</div><div class="thread-post-content">Thank you for that suggestion.&nbsp;

</code></pre>
and this may have been the issue, but the build has other bugs that are not yet resolved.<br />
So I will report back a solution when the other bugs are fixed.
