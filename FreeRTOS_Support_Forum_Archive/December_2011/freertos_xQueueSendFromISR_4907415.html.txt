  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xQueueSendFromISR </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tekkkon">tekkkon</a> on December 27, 2011</div><div class="thread-post-content">Hi All,  
I have an application running on the LM3S8962. The CANBus interrupt service routine grabs the incoming CAN message and calls xQueueSendFromISR&#40;&#41; to send out the message to CANRx&#95;Task, which is dealing with processing CAN message. The application runs very good in the first 20 minutes, the CANRx&#95;Task can receive the message and process it immediately. But after 20 minutes, the task has been blocked due to the xQueueSendFromISR&#40;&#41; returns errQUEUE&#95;Full in the CAN&#95;ISR. I tried to bump up the queue size from 40 to 80, still got the problem. Can anybody give me some advice how to implement xQueueSendFromISR&#40;&#41; for the CANBus ISR and Task, and avoiding errQUEUE&#95;FULL?   
Thank you&#33;&#33;&#33;  
-Tekkon
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueSendFromISR </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on December 27, 2011</div><div class="thread-post-content">When the task unblocks, does it take out all the messages that are in the queue, or just 1? Is the priority of the task that drains the queue high enough? Have you looked at how many messages are in the queue as the application runs to see when they start backing up? Are you yielding using portEND&#95;SWITCHING&#95;ISR in the interrupt handler to make sure the task that drains the queue runs as soon as possible?
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueSendFromISR </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 28, 2011</div><div class="thread-post-content">My first guess is that there may be a problem with how you have defined your interrupt routines and you are corrupting the queue structure. Make sure that the priority of the interrupt task is proper for the port &#40;I am not familiar with this family&#41;. Also, make sure that the task does NOT call a FromISR routine to get the data.  
The 20 minute time period really sounds like it is something &#8220;random&#8221; causing the problem, and a bad interrupt nesting might be a cause.  
Another possibility is that for some reason the CANRx&#95;Task is hung up on some other call and not able to get back to reading from the queue. Are there any other blocking calls that it makes that could do this?   
Also, do you use the heap in your program during run time? One problem with this is that if you are not careful, sometimes your program will run out of memory due to leaks or fragmentation and cause things to hang up.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueSendFromISR </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tekkkon">tekkkon</a> on December 28, 2011</div><div class="thread-post-content">Thank you guys for your help. The queue turns into full all in a sudden, I I guess that&#8217;s something in the task that messed up the queue structure.&nbsp; After I turned off the application layer callback function&#40;which call the upper level function to process received CAN message&#41; in the CANRx&#95;Task,&nbsp; the CAN&#95;ISR, the queue and the task is running good so far&#40;almost 6 hours&#41;.&nbsp;   
Currently, the CAN interrupt is the only ISR has been enabled, and has been set to a high priority at 1.&nbsp; And the CAN&#95;ISR is the only source to block/unblock the CANRx&#95;Task. The CANRx&#95;Task also has the highest priority.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueSendFromISR </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 28, 2011</div><div class="thread-post-content"><blockquote>
  Currently, the CAN interrupt is the only ISR has been enabled, and has been set to a high priority at 1.
</blockquote>
Please read item three here: <a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>&nbsp; It sounds like your priority configuration is incorrect unless you have configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY also set to &#40;the equivalent of&#41; 1.  
…and read the &#8220;Interrupt Service Routines&#8221; section of the documentation page that goes with your port.
