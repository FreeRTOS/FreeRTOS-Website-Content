  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vPortStartFirstTask need basepri=0 on stm32?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/oek">oek</a> on December 8, 2011</div><div class="thread-post-content">Hi all,  
In my FreeRTOS project, I have found that vPortStartFirstTask will either run or app-fault depending on the value of<br />
configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY. With configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY=8 &#40;on the STM32 scale of 0..15 where 0 is highest prio&#41;, the code runs; with configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY=7, the code app-faults at &#8220;svc 0&#8221; in vPortStartFirstTask .  
There are 4 priority levels in use:<br />
15: systick, pendsv<br />
0: all other system interrupts<br />
8: some NVIC interrupts<br />
11: some other NVIC interrupts  
Here are two questions.<br />
1&#46; A CM3 question: I do not understand how there can be distinct behaviour with BASEPRI 7 versus BASEPRI 8. There is no interrupt at prio==7, and besides &#8220;success&#8221; in this case means successfully doing a ctx from vPortStartFirstTask .&nbsp; What is&nbsp; a possible mechanism here?<br />
2&#46; A FreeRTOS question: There are a few forum threads that tweak vPortStartFirstTask to solve CM3 issues. In one &#8220;cpsie i&#8221; was added to turn on global interrupts before &#8220;svc 0&#8221;.&nbsp; But I notice that when I step to &#8220;svc 0&#8221; in vPortStartFirstTask , that the CPU register BASEPRI is non-zero. That is, vPortSetInterruptMask has been called but not cleared. Is this intentional, or should I modify vPortStartFirstTask&nbsp; to clear the interrupt mask?  
Thanks for your suggestions.  
Regards,  
Owen  
Setup : FreeRTOS V7.0.2, STM32, IAR EWARM 5.30 .  
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortStartFirstTask need basepri=0 on stm32?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 8, 2011</div><div class="thread-post-content"><blockquote>
  With configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY=8 &#40;on the STM32 scale of 0..15 where 0 is highest prio&#41;
</blockquote>
configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY needs to be a raw priority value as it is written to the NVIC priority registers in the Cortex-M3 device, as documented in the ARM manuals.&nbsp; The priorities of 0..15 are not real Cortex-M3 priorities, and are simplified priorities for use in some library calls &#40;because the real priorities are so complex on Cortex-M devices&#41;.  
If you want a simplified priority of 8, then you need to set configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY to 0x8n, where n can be any value, but by convention, and for future proofing in case future STM32 parts implement more priority bits, should be set to f.&nbsp; Therefore, the priority you want is 0x8f.  
<blockquote>
  the code app-faults at &#8220;svc 0&#8221; in vPortStartFirstTask
</blockquote>
Presumably a hard fault because you are attempting a call to effectively a synchronous interrupt while simultaneously having that interrupt masked out.  
If you are using an STM32, also ensure you have &#42;all&#42; priority bits set as preemption priority, and none as sub-priority, that will make you life much simpler.  
<blockquote>
  But I notice that when I step to &#8220;svc 0&#8221; in vPortStartFirstTask , that the CPU register BASEPRI is non-zero. That is, vPortSetInterruptMask has been called but not cleared. Is this intentional, or should I modify vPortStartFirstTask&nbsp; to clear the interrupt mask?
</blockquote>
That is intentional, and absolutely fine.&nbsp; It prevents a systick while the scheduler is in an inconsistent state.  
Please also read the port specific configuration section of the documentation page for your port, and the &#8220;my application is not running, what could be wrong&#8221; FAQ.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortStartFirstTask need basepri=0 on stm32?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/oek">oek</a> on December 8, 2011</div><div class="thread-post-content">Mea culpa, in my first post I was speaking in terms of simplified priorities and failed to mention it. I had read the FAQ and followed it except for the part about CM3 subpriority. After removing all uses of sub-priority, my code works&#33; Thank you Richard.  
Regarding sub-priority, I found no errors in my code on setting the priorities; I was able to verify them in the registers. The issues appeared to be that with NVIC configured to use sub-priorities, the SVCall seems to be masked somehow by BASEPRI even though the SVCall priority is visible as PRI&#95;11 = 0x00 in the NVIC. Hmmm…  
All&#8217;s well that ends well. Thanks again.  
Owen
