  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Code size issue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spatil123">spatil123</a> on December 9, 2011</div><div class="thread-post-content">Hi,  
I am developing software for the&nbsp; STR912FAW44 using the IAR Embedded Workbench version 5.50.5. I am facing a problem when the code size exceeds about 64K. The code does not execute from the flash. The same code works when I debug it using a the J-Link debugger. But when I download it using the J-Link debugger it doesn’t work. I tried both the builds i.e. debug and release. The only difference between these 2 is that the “DEBUG” is defined in the debug build and NOT in the release build.  
I have set the bank 0 as a boot bank and don’t have a boot loader. I believe the debugger downloads the code to the bank 0. The bank 0 address is set as 0x0000. If I comment out some code it works. I observed the code size &#40; Code and Read only data&#41; in the map file and observed that the code doesn’t work if the size exceeds about 64K. The STR912FAW44 has 512K bytes of flash in the bank 0 and it’s divided into 8 sectors. Each sector is 64K. I have different licensed dongles and tried with them .<br />
Is there any issue in downloading the code or building it if the code size crosses the first sector boundary?&nbsp;&nbsp;   
I use the FreeRTOS ver 7.0.1 and use the initialization files 91x&#95;init.s and 91x&#95;vect.s come with that. I use the heap&#95;2.c implementation from the FreeRTOS for heap. It allocates the heap as a fixed size array. Also, I have 2 projects:<br />
1&#46; FreeRTOS project is built as a library using “C” complier and<br />
2&#46; The application project built as an executable with the “Embedded C++” compiler option.  
The Flash memory configuration used is:<br />
&nbsp;&nbsp;&nbsp; FMI&#95;BankRemapConfig&#40;4, 2, 0, 0x80000 &#41;;&nbsp; /&#42;&nbsp; FMI&#95;BootBankSize, FMI&#95;NonBootBankSize,&nbsp; FMI&#95;BootBankAddress,&nbsp; FMI&#95;NonBootBankAddress &#42;/<br />
&nbsp;&nbsp;&nbsp; FMI&#95;Config&#40; FMI&#95;READ&#95;WAIT&#95;STATE&#95;2, FMI&#95;WRITE&#95;WAIT&#95;STATE&#95;0, FMI&#95;PWD&#95;ENABLE, FMI&#95;LVD&#95;ENABLE, FMI&#95;FREQ&#95;HIGH &#41;;  
Thanks for the help you provide.
</div></div><div class="thread-post"><h3 class="thread-post-title">Code size issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 10, 2011</div><div class="thread-post-content">One thing I remember having a problem with this part was you need to make sure the startup file loads low enough in memory, the flash register power up with a predefined amount of flash, which is much smaller than you actually have, and if the start-up code is outside that, then the CPU will address-error when accessing memory outside that initial bound until the startup adjusts those registers. If you run under the debugger, the debugging executive will have done this automatically, so it won&#8217;t have caused the problem. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Code size issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 10, 2011</div><div class="thread-post-content">Sorry, I can&#8217;t help you with the technical specifics of the chip boot process or memory lay out.&nbsp; I thought maybe the vector table was using direct branches to the interrupt handler functions, and the when the code size grew too large, the branch distance was too far away.&nbsp; However, having looked at the files you reference, that is not the case as indirect 32 bit branches are used, which will always be fine.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Code size issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spatil123">spatil123</a> on December 12, 2011</div><div class="thread-post-content">Hi Richard,  
Thanks for the response. It looks like that is the case. I was looking into the map file to check the code size. The part of the code that exceeds the 64KB boundry is:<br />
&nbsp;&nbsp; Section&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Kind&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Address&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Size&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Object<br />
Initializer bytes&nbsp; ro data&nbsp; 0x00009706&nbsp;&nbsp; 0x75fe&nbsp; &lt;for P2 s0&gt;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#45; 0x00010d04&nbsp; 0x10b6c  
So the initializer bytes are crossing the boundry. How do I force the linker to place it in the lower memory area?  
Thanks  
</div></div><div class="thread-post"><h3 class="thread-post-title">Code size issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 13, 2011</div><div class="thread-post-content">What I did was to edit the linker control file and defined a new region of memory for initialization code, that was limited to the bottom 16k of memory, and placed the startup module into that region.
</div></div><div class="thread-post"><h3 class="thread-post-title">Code size issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spatil123">spatil123</a> on December 13, 2011</div><div class="thread-post-content">Richard,  
The linker file fix worked for me, although I did it differently. I just made the STR9 init module as the first module to be put in the ROM, after the interrupt vector.   
Thank you very much; this was a great help.
