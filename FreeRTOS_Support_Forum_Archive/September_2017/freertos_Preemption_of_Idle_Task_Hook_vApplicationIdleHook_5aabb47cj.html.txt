  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Preemption of Idle Task Hook (vApplicationIdleHook())</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bryce78">bryce78</a> on September 22, 2017</div><div class="thread-post-content">Hello Community,
I have a &#8220;what happens if&#8230;&#8221; type question related to using the Idle Task Hook (configUSE<em>IDLE</em>HOOK is set to 1 in FreeRTOSConfig.h).
<strong>Background:</strong> The Idle Task runs at the lowest priority (tskIDLE_PRIORITY) and therefore only runs when there is no higher priority task(s) to run.  Furthermore the hook, vApplicationIdleHook(), is called from the Idle Task so it, too, runs at the lowest priority.  This means vApplicationIdleHook() can be preempted if a higher priority task becomes scheduled to run (becomes in the Ready state) during execution of vApplicationIdleHook().
<strong>Scenario:</strong> In my FreeRTOS v9.0.0 project I use vApplicationIdleHook() for periodic (say, once per minute) low prioirty application &#8220;maintenance&#8221; &#8212; say updating some runtime statistics/counters.  Once vApplicationIdleHook() returns the application typically enters low-power tickless idle mode (portSUPPRESS<em>TICKS</em>AND_SLEEP()) shortly thereafter.  However, *during* vApplicationIdleHook() an interrupt could occur, ultimately making a high priority task state become Ready.
<strong>What happens if</strong> that interrupt were to occur? My understanding is that when the interrupt handler returns execution will jump immediately to the high priority task instead of returning to vApplicationIdleHook().  Let&#8217;s suppose the high priority task keeps busy for a long time&#8230;  After a while the high priority task has nothing to do and becomes Blocked, and (I expect) vApplicationIdleHook() resumes from whereever it was at the time of the original interrupt&#8230;and as in the typical case, enters low-power tickless idle mode.
Is my understanding correct?
I am concerned of vApplicationIdleHook() being interrupted (as above) if it has something critical to do and which is expected to complete, like write application data to non-volatile FLASH memory (which would be bad if interrupted).
What is the right way to ensure code executing at even lowest prioity (like vApplicationIdleTask()) will complete without context switch until the critical code has finished?  
Is the solution just to wrap the critical bit of vApplicationIdleHook() around taskENTER<em>CRITICAL() and taskEXIT</em>CRITICAL()?
Lastly, its <a href="http://www.freertos.org/RTOS-idle-task.html">mentioned here</a> that vApplicationIdleHook() mustn&#8217;t call any API function that can block.  Presumably this includes <strong>xSemaphoreTake</strong>(&#8230;, (TickType<em>t) portMAX</em>DELAY) and <strong>xQueueSendToBack</strong>(&#8230;, &#8230;, ( TickType<em>t ) portMAX</em>DELAY).  So, how does one add to task queues (if occasionally needed) without these blocking API calls?  Is it better (or best) practice to avoid inserting anything to task queues from vApplicationIdleHook()?  (After all, the application is supposed to be idle?!)
Thanks for reading this far &#8212; hope I explained clearly 🙂
Best,
Bryce
</div></div><div class="thread-post"><h3 class="thread-post-title">Preemption of Idle Task Hook (vApplicationIdleHook())</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 22, 2017</div><div class="thread-post-content">Sounds mostly correct. The interrupt wll go into the interrupt handler, which might wake up a higher priority task.
A critical section should normally be very short, as it disables interrupts, so a flash memory write may not take longer than you want for this. (but if writing to the flash shouldn&#8217;t be interrupted, it might be the rigth thing to do).
Another alternative is to suspend the scheduler, which will still allow interrupt to occur, but not let it activate the higher priority task until the action is done.
A third option would be that it sounds like this small section really should be considered a high priority operation, so perhaps the idle task could at that point signal a higher priority task to do the flash write. This would allow you to set its priority to allow perhaps a few very high prioity operations to interrupt you, but not lower (but still above idle) operations. An alternative here would be to have the IdleHook function raise the task priority for that section and then lower it again when done.
