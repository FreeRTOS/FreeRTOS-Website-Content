  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Binary semaphore reliability</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alainm3">alainm3</a> on September 6, 2017</div><div class="thread-post-content">Hi, a friend of mine with greater knowledge of RTOSes than myself is arguing about the reliability of this code:
1) I have a binary semaphore created like this
        myMutex = xSemaphorCreateBinary();
2) In my IRQHandler for serial input, I set a binary semaphore every time I get a new char and put it in the RX queue:
        xSemaphoreGiveFromISR(myMutex, &#8230;);
3) I have a task waiting for that semaphore:
        xSemaphoreTake(myMutex, 10);
4) Hardware is an CortexM0+ STM32F030, FreeRTOS version 7.6.0, compiler GCC
The argument is that there is a possibility of loosing a byte from my IRQ handler and that I should use a counting semaphore.
The question is: is it 100% safe to use a binary semaphore in this way (I got the example from the (payed) manual) or should I change to a counting semaphore as he says?
Thanks for making FreeRTOS and thanks for being here to help us,
Alain
</div></div><div class="thread-post"><h3 class="thread-post-title">Binary semaphore reliability</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 6, 2017</div><div class="thread-post-content">The answer depends on how you have structured your code.
A binary semaphore will only tell you that something has happened, not 
how many things have happened, so you must process ALL pending events 
before going back to wait for the semaphore again, not just assume there 
is only one event (character, in your case) pending.
See the code snippet on the following page, which shows a task 
notification being used as a binary semaphore &#8211; the concept is the same 
&#8211; not do do while{} loop clearing all events before looking for a 
notification again:
http://www.freertos.org/ulTaskNotifyTake.html
</div></div><div class="thread-post"><h3 class="thread-post-title">Binary semaphore reliability</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alainm3">alainm3</a> on September 7, 2017</div><div class="thread-post-content">Yes, that is what I did but using binay semaphore. I do process all pending events before going back to taking the semaphore.
But the argument is that an ISR could happen &#8220;at some special moment&#8221; and cause the xSemaphoreTake() <strong>not to wake up</strong>. Is it guaranteed that this &#8220;special moment&#8221; does not exist?
And BTW, I have no mention to TaskNotify anywhere in Reference Manuas v2.0.0 for FreeRTOS v8.0.0

</div></div><div class="thread-post"><h3 class="thread-post-title">Binary semaphore reliability</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 7, 2017</div><div class="thread-post-content"><blockquote>
  But the argument is that an ISR could happen &#8220;at some special moment&#8221; and
  cause the xSemaphoreTake() not to wake up. Is it guaranteed that this
  &#8220;special moment&#8221; does not exist?
</blockquote>
That &#8220;special moment&#8221; do not exist in FreeRTOS. The FreeRTOS API&#8217;s take all necessary measurements to be <strong>atomic</strong>.  In some cases interrupts are masked, in other cases the scheduler will be suspended temporarily.  As a result you can Give and Take semaphores ( notifications ) at any moment you like, without worrying about congruency.
In most cases, the task receiving bytes will be sleeping in <code>ulTaskNotifyTake()</code> or <code>xSemaphoreTake()</code>.  When the ISR comes at that moment, the function will unblock and return a non-zero value.
When the ISR comes <strong>at any other moment</strong>, the task is handling UART reception.  It will read all bytes available and call the Take function again.  That function will return immediately. And then there may, or there may not be RX bytes available.  That depends on the actual sequence of events.
You won&#8217;t miss bytes using the &#8220;binary semaphore method&#8221;, unless there is a physical overflow, which may happen if the task does not get enough CPU time.
