We call vTaskStartScheduler() quite late after power-up. By this, the xTickCount does not represent the number of ticks since power-up.
To change this we removed the scheduler startet condition from the SysTickHandler:
~~~
void SysTickHandler()
{
   //if ( xTaskGetSchedulerState() == taskSCHEDULER<em>NOT</em>STARTED )
     xPortSysTickHandler();
 }
~~~
and added the follwing return in case the scheduler is not running:
~~~
BaseType_t xTaskIncrementTick( void )
{
        [&#8230;]
        xTickCount = xConstTickCount;
<blockquote>
  <blockquote>
    <blockquote>
       if ( xSchedulerRunning != pdTRUE )
        return pdFALSE;
    </blockquote>
  </blockquote>
</blockquote>
<pre><code>    if( xConstTickCount == ( TickType_t ) 0U )
    [...]
</code></pre>
 }
~~~
Is this solution ok or is there better, less intrusive option (despite of starting the scheduler immediately after power-up)?
Thanks a lot for any help and best regards!
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 4, 2017</div><div class="thread-post-content">I&#8217;m pretty sure this is not code that we distribute:
<blockquote>
  void SysTickHandler()
  {
     //if ( xTaskGetSchedulerState() == taskSCHEDULER<em>NOT</em>STARTED )
       xPortSysTickHandler();
  }
</blockquote>
Not sure where you got it.  We don&#8217;t start the systick timer until after 
the scheduler has been started, so a check to see if the scheduler had 
been started on every single tick interrupt (and there are a lot of 
them) would seem to be wasteful and obsolete.  So in answer to part of 
your question &#8211; removing the if() would seem to be fine considering it 
is not there anyway in the official code.
After that, the important thing is to ensure the tick interrupt does not 
attempt to unblock any tasks if the scheduler is not running.
Note many of the FreeRTOS API functions will deliberately leave 
interrupts masked  up to the configMAX<em>SYSCALL</em>PRIORITY value until 
after the scheduler has started.
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 4, 2017</div><div class="thread-post-content">I generally try to get the Scheduler running quickly. I will create the Tasks/Queues/Semaphores that I can before startup and initialize basic hardware (where it doesn&#8217;t require the use of interrupts or delays), and then bring up the schedule. Operations that take time are done with the scheduler running, so they can use the same drivers as used during the &#8220;normal&#8221; operation.
The one case I could see for delaying the start of the scheduler would be if I had to read some boot information from a device that I will not need after boot. Then perhaps using a polling driver might make sense.
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hpc64">hpc64</a> on September 4, 2017</div><div class="thread-post-content">In principe I completly agree.This has also the advantage that initializations that contain long delays could be done in parallel speeding up the whole initializatoin.
It&#8217;s just that I  do not want to make this change right now and just correct the tick count.
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hpc64">hpc64</a> on September 4, 2017</div><div class="thread-post-content">I am sorry, the original code was:
~~~
void SysTickHandler()
{
   if ( xTaskGetSchedulerState() == taskSCHEDULER<em>NOT</em>STARTED )
      return;
   xPortSysTickHandler();
 }
~~~
When using just
~~~
void SysTickHandler()
{
   xPortSysTickHandler();
}
~~~
and without the above added return condition in xTaskIncrementTick the system gets stuck in the first call of xPortSysTickHandler().
The reason might be that as you mentioned abobve it is not ensured that the tick interrput does not attempt to unblock any tasks. How can this be done?
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 4, 2017</div><div class="thread-post-content">Calling xPortSysTickHandler before the scheduler is running is apt to cause problems, as it expects that it is only going to be called after the scheduler has been started (one reason FreeRTOS api calls disable the interrupts). 
One solution might be to modify the FreeRTOS code to give you access to the tick counter variable and just increment it yourself before the Scheduler has started.
The other question is if it really is important the the tick counter be time since &#8216;turn on&#8217; vs &#8216;scheduler started&#8217;. The systick isn&#8217;t designed to be an absolute time clock, but a relative clock, so where 0 is doesn&#8217;t normally matter that much. (and there have been proposals that perhaps it shouldn&#8217;t start at 0, but at some large value that will roll over in a short time to make testing that code handles the roll over easier, more important on systems with 16 bit ticks).
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 4, 2017</div><div class="thread-post-content">I wonder if it would be possible/feasible to call vTaskSuspendAll() 
before the scheduler is started, then xTaskResumeAll() from the first 
task to run after the scheduler has started (maybe from the Daemon task 
startup hook).  When the scheduler is suspended no context switches will 
be attempted, but the tick count will increment.
</div></div><div class="thread-post"><h3 class="thread-post-title">Increment xTickCount before call of  vTaskStartScheduler()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 4, 2017</div><div class="thread-post-content">You would have to make sure the Daemon task was the first to run. If being used for ISR Pend Functions it is likely highest priority, if just for Timer functions, it might not need to be. It also needs to be (I think) the only task at the priority as it is created on the call to start the scheduler and I think first created gets run first.
