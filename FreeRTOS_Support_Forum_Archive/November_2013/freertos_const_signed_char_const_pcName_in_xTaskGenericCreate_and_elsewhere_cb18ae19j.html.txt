</div></div><div class="thread-post"><h3 class="thread-post-title">const signed char * const pcName  in xTaskGenericCreate (and elsewhere)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 23, 2013</div><div class="thread-post-content">If you want to remove the warning, cast the string to a const char * const when you pass it in.  I think this is done in lots of places in the demo code.
FreeRTOS works with something like 18 different compilers, and we aim to have 0 warnings when building the FreeRTOS code.  That is not easy, and requires that the user sometimes also has to cast values.  
In this case, if the const casts were removed from the FreeRTOS code then you risk wasting RAM space at low optimisation.  If the type was removed from the cast then you would fail MISRA rule checks.  If you changed the type in the cast you would just create warnings with compilers that until that time didn&#8217;t generate warnings, while fixing warnings in compilers that previously did generated warnings (without explicit casts).
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">const signed char * const pcName  in xTaskGenericCreate (and elsewhere)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 29, 2013</div><div class="thread-post-content">This is a very subjective thing.  Every change we make to please you will upset somebody else, or in this case probably more than one somebody else.  I&#8217;m sorry we can&#8217;t please all of the people all of the time.  I have in fact just added in more of these in the latest SVN checkin directly as a result of user feedback that some were missing.
<blockquote>
  but writing redundand attributes like &#8220;signed portBASE&#8221;
</blockquote>
In that case the &#8216;signed&#8217; is <b>absolutely not</b> redundant.  You have to look at the history of the code.  Originally in many ports portBASE_TYPE was a char, and in line with I think every coding standard I have seen, and in MISRA, plain unqualified char types can simply not be used.  Probably three quarters of the compilers supported have plain chars unsigned by default (because they are embedded compilers), and the other quarter have then
signed.
<blockquote>
  where on most 32 and 16 bit platfroms portBASE is signed by default
  Would not be better to typedef in portable layer portCHAR (on my port it is already 
  defined) to char or unsigned char and use this type when string parameter is needed?
</blockquote>
Historically this was done, guess what, people complained and it was removed.  Now you want them back again, so again my point is being made quite clearly.
<blockquote>
  Another example: you are using type portSTACK<em>TYPE to specify stack type parameter type, 
  but size is not typed (maybe portSIZE</em>TYPE should be introduced). 
</blockquote>
The only real place in the code where the size of a type is important is for pointers, and there is a pointer size type for those ports that require it (the ones with eccentric number of bits for the address bus or different memory models).
As it happens &#8211; I actually agree with you on a lot of points.  If you look at the newer FreeRTOS components that are provided directly by us you will see all types come from stdint.h &#8211; and typedefs end with a &#8216;<em>t&#8217;, like C&#8217;s standard size</em>t.  I would like to change the convention used in FreeRTOS itself to match that, but to do so would result in a lot of complaints about backward compatibility being broken (the prototype of all the API functions would change).  Still, version 8 will be released as soon as we find time to document it, and as that is a major version number update that would be the time to do it.
Regards.
You used the work <i>most</i> yourself there, which sort of is my point.
</div></div><div class="thread-post"><h3 class="thread-post-title">const signed char * const pcName  in xTaskGenericCreate (and elsewhere)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 29, 2013</div><div class="thread-post-content">Richard,
Would it be worth pointing out that for 9 years now the MIRSA specification now requires that &#8220;plain&#8221; char be used for &#8220;characters&#8221; and signed char and unsigned char only be used for small numeric values so FreeRTOS is currently NOT MIRSA complient to the latest spec (MIRSA-C:2004). (Rules MIRSA-C:2004 6.1 and 6.2, REQUIRED)
I know this would be a major change in compatibility but perhaps FreeRTOS could define a type for characters, and default this to signed char unless something is set in FreeRTOSConfig.H, which would allow the &#8220;proper&#8221; definition to be used.

Does anyone know what their objection is &#8211; I have used macros/undef to create create tables from a single &#8220;source file&#8221;, the classic being enums and their string equivalents which seems an excellent use of macros &#8211; though not to MISRA&#8217;s liking.
</div></div><div class="thread-post"><h3 class="thread-post-title">const signed char * const pcName  in xTaskGenericCreate (and elsewhere)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 29, 2013</div><div class="thread-post-content">Using stdint types would be fine with me, and define the old types for compatibility. If you want to strictly follow MIRSA you need a 
typedef char FreeRTOS<em>char; 
Statement I believe, as I think the &#8220;silly&#8221; rule of never using built in types applies even though another rule says the type must be char. I suppose that does allow you at some future point to change it to wchar</em>t, but then all string constants will need to be changed too.
My guess to the objection of #undef is that you can abuse it and get unsafe code by #undef-ing a &#8220;Global&#8221; macro to a different value. This is sort of a different case, where the macro is really a &#8220;parameter&#8221; to the include file, and in my opinion actually makes the source code &#8220;safer&#8221;, being able to parse the header multiple times to make sure related data structures match.
It does have the danger of confusing some people though, I had always thought of it as a standard technique, but some programmers I have worked with had never seen it and needed help to understand the code. One they understood it though, they appreciated the convinience and safety of keeping the structures in sync.
