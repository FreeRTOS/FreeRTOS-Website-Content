Someone has asked me to look at the port for the MSP430F6659.  Note this &#8216;430 has a discontinuous memory space for internal RAM &#8211; there is a lower 16KB &lt; 0xFFFF and the rest ~ 49KB is greater than 0xFFFF.  The part has 66 KB of RAM and 512 KB of FLASH &#8211; so it is one of the &#8216;bigger&#8217; &#8216;430&#8217;s.
The &#8216;regular&#8217; &#8216;430 demo works fine as long as you don&#8217;t allocate too much memory.  So, what does that mean?  
I had a port handy for the &#8216;5635.  I didn&#8217;t have the hardware at first &#8211; the other port I posted was from stuff in the simulator.  I thought I had something that would work.  I modified the port the blink the 3 LED&#8217;s on the &#8216;PZ100USB demo board from TI &#8211; the usual LED tasks run fine using the usual demo code &#8211; no problem.
But when I try to allocate > 20KB using the FreeRTOS heap manager &#8211; the port fails.  I tried this with heap<em>1 and heap</em>3.  Using the malloc from IAR resulted in the same thing when trying to allocate > 20KB.  
I looked in the map files in both instances &#8211; and noticed this difference:
In the first case &#8211; where I allocate around 14KB of memory &#8211; the DATA20<em>Z segment falls into:
DATA20</em>Z                               2406 &#8211; 5E2F            3A2A   rel    1
and in the case that fails:
DATA20_Z                           000F0000 &#8211; 000F5229        522A   rel    1
I took a look at the port assembly and I don&#8217;t think the problem is there &#8211; but I am not 100% certain yet.  I have traced through it &#8211; one problem is the tools become a bit unstable when an error occurs; so it will take some additional time to determine what is wrong.  
I am using v7.5.3 in the port.
So &#8211; there seems to be a problem with addressing &#8211; when something is in the DATA20_Z segment when it is mapped > 0xFFFF by the linker &#8211; the port fails.  I have checked the variables that are addressed int the port assembly &#8211; I tried changing those &#8211; but the port fails in the same way.
Note xTickCount does not increment before the failure &#8211; so we are not reaching that yet.  All of the demo tasks are made successfully.
The 430 has a requirement to have all IRQ code in the lower memory &#8211; at or below 0xFFFF &#8211; I don&#8217;t think there is an issue &#8211; vPortTickISR in the port is below 0xFFFF in case you were wondering.
I will post results as I have them &#8211; I am working on this currently on a time available basis.
Thanks,
John W.

I vote for this one!
Atmel&#8217;s SAM4E Xplained board has the same problem: it has two separate banks of SRAM, each 0.5MB.
I solved it temporarily by including two instances of heap_&lt;n&#62;.c, which isn&#8217;t elegant.
Beside having more-than-one-contiguous-heap-space, it would be very useful if the actual size of the heap can be set at runtime.
~~~~~~
/* Allocate the memory for the heap. */
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
~~~~~~
Often &#8220;configTOTAL<em>HEAP</em>SIZE&#8221; is unknown at compile time, but it <strong>is</strong> known at link-time.
The linker is able to set 2 pseudo variables from which the offset and size can be calculated:
~~~~~~
extern const void __heap<em>start;
extern const void __heap</em>end;
<h1>define SIZE  ((uint32<em>t) ( ((const char*)&amp;<strong>heap_end) &#8211; ((const char*)&amp;</strong>heap</em>start) ))</h1>
<h1>define START ((uint32_t) ((const char*)&amp;__heap_start))</h1>
~~~~~~
There are several versions of heap<em>&lt;n&#62;.c of which I find _heap</em>4.c_ the best. It implements its own version of malloc/free in a very fast, efficient and correct way.
If you use heap_4.c, make sure that there are no hidden calls to standard malloc/free.
E.g. you should make the following replacements:
~~~~~~
localtime -> localtime<em>r
gmtime -> gmtime</em>r
strtok -> strtok_r
~~~~~~
and probably some more. The &#8220;_r&#8221; versions are also thread-safe because you provide your own memory.
Proposal:
~~~~~~
struct xMemoryEntry {
    uint32<em>t mem;
    size</em>t size;
};
struct xMemoryEntry entries[] = {
    { 0x61000000, 80000 },
    { 0x63000000, 80000 },
};
void main()
{
    pvPortSetMemories(entries, sizeof entries/sizeof entries[0]);
}
~~~~~~
What would you think of this?
(it is a bit tricky, because before this call, no malloc&#8217;s can be done).

</div></div><div class="thread-post"><h3 class="thread-post-title">MSP430X Port for MSP430F6659 &#8211; Has Discontinuous SRAM Memory Model</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 1, 2014</div><div class="thread-post-content">There are two fairly common requests related to the memory allocation, both of which I think already have outstanding feature request tickets:
1) Allowing static allocation.
Although not directly documented as such, there is actually already a mechanism for statically allocating the TCB and statck used by a task, but not for allocating the memory used by queues/semaphores/mutexes/etc.
It would be easy enough to add in a mechanism for statically allocating the memory for these other objects too &#8211; but there are a couple of issues that must be accounted for &#8211; firstly an unwelcome increase in the code size, and secondly increasing the complexity for end users (the more options and choices the more complex and confusing).
If static allocation is required for reasons of safety critical qualification then it is actually quite feasible to qualify heap_1.c, which cannot suffer non-determinism or memory fragmentation, so does not suffer the issues that safety critical systems try and avoid.  It is really just a statically allocated array.
2) Allow the heap to span multiple memory regions.
First a note about using the linker variables to dimension the heap rather than the configTOTAL<em>HEAP</em>SIZE constant.  I am definitely not in favour of that as it is not portable even between different GCC projects, let along to the other 17 or so compilers for which there are official FreeRTOS ports.  Also these linker variables are used by the standard library malloc and free, and I want to draw a clear distinction between the two methods (the standard library allocation and FreeRTOS allocation).
If you need a fixed size heap because your application just creates all the RTOS objects up front, then never deletes anything (which is the normal case), then the xPortGetFreeHeapSize() and xPortGetMinimumEverFreeHeapSize() functions can be used to see how much heap was actually used, then the configTOTAL<em>HEAP</em>SIZE variable can be adjusted accordingly.
It should also be noted that FreeRTOS keeps memory allocation in the portable layer as it is recognised than different embedded projects have very different memory allocation requirements.  It is therefore always possible to just add in your own version of pvPortMalloc and vPortFree to do whatever you want, however&#8230;
&#8230;heap<em>4.c is the favoured memory allocation for all applications except the most trivial or the most safety critical.  heap</em>4.c in effect keeps a linked list of free memory blocks, with the list jumping over the blocks that are allocated to the application.  At initialisation time heap<em>4.c just creates one block that covers the entire memory region on the assumption there is only one contiguous heap.  There is no reasons why heap</em>4.c could not be extended such that at initialisation time a linked list is set up whereby the first block covers the entire first contiguous heap areas, with the block pointing to the 
second contiguous heap areas, with that block pointing to the next, and so on for however many heap areas there were.
Only the initialisation code would need to change.  The code that allocates and frees memory would not need to change because to it the gaps in the memory that are actually gaps between separate heap areas would just look like gaps that were created by memory actually being allocated to the application.
The user could initialise such a heap scheme by passing in an array of structures, with each structure defining the start address and size of each available heap area.  The function to do so could just be added to the heap_4.c implementation.  Users with just a single array of memory (as per the current scheme) could ignore the new function, the more advanced users with complex memory maps could call the new function as a first step &#8211; before they create any RTOS primitives (tasks, queues, event groups, etc.).
One disadvantage of this scheme is that there is no way of telling the allocation function from which heap area it should allocate the RAM if there is more than one heap area in use.  This is actually quite important as often one heap area will be in fast internal static RAM, which is a good place to store task stacks, and another heap area might be in a huge external RAM which may be much slower and not so suitable for use as a stack.  Ideally when allocating you would want to say from which memory (fast or slow) the allocated block should come, and it might be best to ensure any changes cover that option too &#8211; although that could introduce incompatibilities&#8230;.
Regards,
Richard Barry

</div></div><div class="thread-post"><h3 class="thread-post-title">MSP430X Port for MSP430F6659 &#8211; Has Discontinuous SRAM Memory Model</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 2, 2014</div><div class="thread-post-content">[our previous two posts crossed mid Ether]
xPortGetFreeHeapSize() should be working too but you have to be careful how you interpret its results.  Just because it says there are 100 bytes left it does not necessarily mean you can allocate 100 bytes as it does not say anything about where the bytes are or how they are fragmented.
For example you may have 2 free blocks in your first region, each of which are 8 bytes each, with another block of 84 bytes in the second region.  In that case the biggest block you would able to allocate would be (typically on a 32-bit architecture at least) 76 bytes (as 8 bytes in the 84 byte block would get consumed by the heap&#8217;s own internal data structures).
