</div></div><div class="thread-post"><h3 class="thread-post-title">Event Flags in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 25, 2008</div><div class="thread-post-content">Event flags &#8211; hmm.
This is something we have discussed several times here.&nbsp; To recap in as fewer words as possible &#40;difficult for me ;o&#41; the problem with event flags is the effect they have on system responsiveness.&nbsp; I have not yet come up with a fully featured implementation that does not require loops within critical sections &#8211; which is something FreeRTOS.org tries to avoid.
Having said that I have talked to lots of people about event flags and it is clear that different people have very different definitions, some of which are more difficult to implement than others.
I was thinking an event flag was a variable in which each bit represents an event.&nbsp; Any number of tasks can pend on any combination of events.&nbsp; So an event occurring would require each task that was pended on that event to be inspected to see if the bit combination was correct for the task to be unblocked.&nbsp; The inspection could require lots of ORing and ANDing, and a loop through each pended task.
It would be good to get other definitions.&nbsp; Simpler implementations with less functionality might well be very possible without affecting system responsiveness.
Regards.

But this loop would happen only when one of the events in the event flag occurs, not everytime there is a task switch, so it would not impact system responsiveness in general, it would slow down only the event mechanism. And usually there aren&#8217;t so many tasks waiting for the same event list, maybe 3 or 4 at a time.   
However there is another definition of the event flags &#40;and easier to implement&#41; would be this:  
There are no combination of evetns, and they do not actually hold any value &#40;set or unset&#41;. But at any time the event &#8220;occurs&#8221;, all tasks waiting for it unblock.  
for example let the event be the arrival of a CAN Message.<br />
Usually this message should be processed by only one thread, but sometimes more than one thread needs it. So in most cases only 1 thread is waiting on this event, but sometimes both.<br />
When the Interrupt occurs, and the event is given a &#8220;push&#8221;, the threads waiting for it unblock, and first the one with the higher priority runs, and after that the one with lower priority.  
I Don&#8217;t think it would be very complex to implement, you actually need a list of the tasks waiting for the specific event. When a thread starts waiting it is put into blocked state and when the event is given a push, it is unblocked and put in runnable state.  
Is there any possibility for this to be implemented and integrated into FreeRTOS?

</div></div><div class="thread-post"><h3 class="thread-post-title">Event Flags in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 26, 2011</div><div class="thread-post-content">Note that for both definitions of &#8220;event&#8221;, it is actually possible to create a wrapper around the existing primitives to create the functionality, as long as you can change both ends of the current communication &#40;and if the event was a new type of structure, you would need to do this anyway&#41;.  
To create the &#8220;event&#8221; that one signal may start multiple tasks, all you need to do is make the sending task signal multiple semaphores, and each task waits on its own, and possible add that when it goes to wait, it first &#8220;clears&#8221; the semaphore with a 0 delay wait so that it will wait for the next signal. If you don&#8217;t want to hard code which events to signal, you can create a generic version which builds a list of semaphores, with a function to signal all semaphores on the list.  
For the wait for one of a multiple queues, you can create an extra semaphore which you signal when any of the queue has something put on it &#40;or removed if you are going to wait for space on a queue&#41;. Again, if you want to make a general version, you can build the appropriate lists which are processed when an &#8220;eventable&#8221; queue is accessed. There are some details to avoid race conditions that need to be addressed and may require some critical sections, and a wait for multiple queues will need to handle the case that a task waiting on multiple queue might get woken for data being available, but by the time it goes to actually get the data, it is gone &#40;to some other task&#41; and it might need to go back to the wait again.
