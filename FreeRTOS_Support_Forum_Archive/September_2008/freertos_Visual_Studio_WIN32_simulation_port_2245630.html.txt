</div></div><div class="thread-post"><h3 class="thread-post-title">Visual Studio (WIN32 simulation) port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 15, 2008</div><div class="thread-post-content">Your post is quite a co-incidence, I was just playing with the port this weekend.&nbsp; I am very impressed&#33;&nbsp; This makes a really nice test bench &#8211; I have been trying out some new TCP/IP ideas using it.
I found I had to remove the idle hook to get the debugger to behave nicely &#8211; the idle hook doing nothing but &#8216;sleeping&#8217;.
I cannot get direct access to the Ethernet interrupts so instead created a task that runs in the background generating simulated events to wake the Ethernet task.&nbsp; I think this is similar to how you are creating the tick interrupts, only you are using a Windows thread, rather than a FreeRTOS.org task.&nbsp; Is this correct?&nbsp; I know very little about native Windows programming.
To use the port I downloaded the latest &quot;Microsoft Visual C++ 2008 Express Edition&quot; &#8211; which is completely free but huge so you need a fast internet connection and plenty of disk space.
Thank you for your great contribution.&nbsp; Any volunteers for a Linux version?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Visual Studio (WIN32 simulation) port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nidujay">nidujay</a> on September 15, 2008</div><div class="thread-post-content">Hi,
I&#8217;m glad you find the port useful. 
You&#8217;re right about the Sleep. Without it you get the CPU fans running etc because the process is always busy. I have used Sleep&#40;INFINITE&#41; &#8211; We don&#8217;t use the IDLE thread except for patting the watchdog.
FreeRTOS tasks are wrapped by windows threads so yes, the solution is similar. Only thing is, the solution you have adopted brings the interrupt generators under the fold of the FreeRTOS scheduler &#40;which may or may not be a problem in your case&#41;.
Another gotcha is, the windows tick occurs every 15.xxx ms. My suggestion is to add a couple of macros to convert from ms to ticks and vise versa and use them to abstract out the delays arguments.
All the best
Dushara
