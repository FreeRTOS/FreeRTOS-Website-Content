  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Solved: ISR exception when optimizing</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apr-cn-eng">apr-cn-eng</a> on September 16, 2008</div><div class="thread-post-content">Environment: LPC2378 &#40;ARM7TDMI-S&#41;, GCC 4.3.2 &#40;same with 4.2.2&#41;
FreeRTOS mandates an ISR wrapper which:
&nbsp; &#8211; saves the task context
&nbsp; &#8211; calls the real handler
&nbsp; &#8211; restores/modifies the task context
In case there are local variables in the real handler, the wrapper has to issue an external call to the real handler because of stack preparation.
Without this call, one might run into an exception due to access beyond the memory limit.
It&#8217;s perfectly legal to declare both the wrapper and the real handler as static.
When compiling with optimization &#40;-O2&#41;, GCC may inline static functions.
This will lead to the described behaviour.
There are two ways around this:
&nbsp; &#8211; declare the real handler as non-static
&nbsp; &#8211; prevent inlineing of the real handler
I&#8217;d opt for the second variant, as declaring local functions as static is part of good coding style.
GCC provides an attribute &quot;noinline&quot; to achieve this.
For a working example see below. To see the effect in real life, comment out the noinline attribute.
Mr. Barry, please include this in the documentation and/or as a FAQ.
Also I&#8217;d suggest to update the provided demo codes accordingly.
Most of the demos use the non-static approach &#40;all for ARM7&#41;.
static void xHandler&#40;void&#41; &#95;&#95;attribute&#95;&#95; &#40;&#40;noinline&#41;&#41;;
static void xHandler&#40;void&#41;
&#123;
&nbsp;&nbsp;&nbsp; volatile u32 a;
&nbsp;&nbsp;&nbsp; volatile u32 b&#91;3&#93;;
&nbsp;&nbsp;&nbsp; a = 1;
&nbsp;&nbsp;&nbsp; b&#91;0&#93; = 1;
&nbsp;&nbsp;&nbsp; &#91;&#8230;&#93;
&#125;
static void xISR&#40;void&#41; &#95;&#95;attribute&#95;&#95; &#40;&#40;naked&#41;&#41;;
static void xISR&#40;void&#41;
&#123;
&nbsp;&nbsp;&nbsp; /&#42; Save the context of the interrupted task. &#42;/
&nbsp;&nbsp;&nbsp; portSAVE&#95;CONTEXT&#40;&#41;;
&nbsp;&nbsp;&nbsp; /&#42; Call the handler.&nbsp; This must be a separate function from the wrapper
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; to ensure the correct stack frame is set up. &#42;/
&nbsp;&nbsp;&nbsp; xHandler&#40;&#41;;
&nbsp;&nbsp;&nbsp; /&#42; Restore the context of whichever task is going to run next. &#42;/
&nbsp;&nbsp;&nbsp; portRESTORE&#95;CONTEXT&#40;&#41;;
&#125;
</div></div><div class="thread-post"><h3 class="thread-post-title">Solved: ISR exception when optimizing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 17, 2008</div><div class="thread-post-content">Thanks for your useful post.
The method for defining ARM7 interrupts was changed to the asm wrapper method because of issues in the GCC code generation.&nbsp; There were some subtle but quite severe bugs that only appeared at certain optimisation levels.&nbsp; The first work around for this was to use the -fomit-frame-pointer option, but this annoyed some users as it made debugging harder, plus it did not fix all problems.&nbsp; Using the asm wrapper meant that the code generated was completely under control of the application and did not allow GCC to include any bum asm instructions.
I don&#8217;t know if the latest versions of GCC have fixed these issues.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Solved: ISR exception when optimizing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/apr-cn-eng">apr-cn-eng</a> on September 20, 2008</div><div class="thread-post-content">Well, I haven&#8217;t had any problems both with -fomit-frame-pointer and without, regardless of optimization &#40;O0, O2&#41;. This applies to both gcc 4.2.2 and 4.3.2, based on the yagarto toolchain.
I found a earlier thread regarding this problems, but didn&#8217;t get the point completely.
So in case somebody could describe what is happening and/or how to trigger it, I&#8217;d verify the status of the actual gcc releases.
In general it would be great to have a reduced irq prologue/epilogue &#40;e.g. register saving&#41;, as it is rather time consuming for fast periodic interrupts, sometimes leading to irq separation in low-level and FreeRTOS part.
Regarding the upgrade to gcc 4.3.2, I sent a patch to Mr. Fischer, the maintainer of the yagarto toolchain. Looks like it is not yet on his site, don&#8217;t know if he is validating it still or at all.
Over here, gcc 4.3.2 runs fine, but I cannot state if all calculus optimizations introduced &#40;GMP, MPFR&#41; work as expected.
