  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">The usage of pdMS_TO_TICKS</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yuguangworld">yuguangworld</a> on November 13, 2018</div><div class="thread-post-content">In the API references for xTimerCreate, it is said that &#8220;pdMS<em>TO</em>TICKS() can only be used if configTICK<em>RATE</em>HZ is less than or equal to 1000. &#8221;  Why we can&#8217;t use this function when configTICK<em>RATE</em>HZ is larger than 1000? 
I checked the source code, the function is as follows, TickType<em>t is uint64</em>t. I don&#8217;t see any limit that is regarding the configTICK<em>RATE</em>HZ. 
~~~
<h1>define pdMS<em>TO</em>TICKS( xTimeInMs ) ( ( TickType<em>t ) ( ( ( TickType</em>t ) ( xTimeInMs ) * ( TickType<em>t ) configTICK</em>RATE<em>HZ ) / ( TickType</em>t ) 1000 ) )</h1>
~~~
I would appreciate if anyone could point out the reason. Thanks in advance!
</div></div><div class="thread-post"><h3 class="thread-post-title">The usage of pdMS_TO_TICKS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 13, 2018</div><div class="thread-post-content">pcMS<em>TO</em>TICKS() is  macro that has a default implementation, but can be overwritten to do whatever you want simply by defining the macro again in FreeRTOSConfig.h.  TickType_t can be 16-bits, 32-bits or 64-bits, depending on the architecture and FreeRTOSConfig.h settings.
The docs say it only works with tick rates at or below 1KHz as the results are stored in integers that cannot store fractions of a millisecond.
It is unusual to want a tick rate at 1KHz, let alone faster, so needing a faster tick could be a sign that something is not optimal in the run-time design.
</div></div><div class="thread-post"><h3 class="thread-post-title">The usage of pdMS_TO_TICKS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yuguangworld">yuguangworld</a> on November 13, 2018</div><div class="thread-post-content">Thanks Richard! 
If I understand correctly, to make the results are integers, we need tick rate at or larger than 1kHz. For example, if it is 100Hz, and we set xTimeInMs to be 1, and the result is not integer, as follows, 
( ( TickType<em>t ) ( ( ( TickType</em>t ) ( 1 ) * ( TickType<em>t ) 100 ) / ( TickType</em>t ) 1000 ) )= 0.1, which is not integer. 
Please let me know if I misunderstood something. 
</div></div><div class="thread-post"><h3 class="thread-post-title">The usage of pdMS_TO_TICKS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 14, 2018</div><div class="thread-post-content">Hmm, I wondering if the comment you referenced in your original post is 
actually for the portTICK<em>PERIOD</em>MS constant, which is defined as:
~~~
<h1>define portTICK<em>PERIOD</em>MS ( ( TickType<em>t ) 1000 / configTICK</em>RATE_HZ )</h1>
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">The usage of pdMS_TO_TICKS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ldb">ldb</a> on November 14, 2018</div><div class="thread-post-content">I think moreover he is confused if your tick rate is 100Hz then you can&#8217;t ask for any period shorter than 10ms, the answer for anything less is 0 ticks. He did the calc above 1ms = 0.1 but since the macro does all integer maths the return is 0 which is absolutely correct. 
The basic answer is you can&#8217;t do a 1ms delay on a 100Hz timer tick.
If you want more accurate delays than timertick itself on a task switcher you need to go into tickless operation if FreeRTOS supports it?  
Alternatively setup the delay in a way not utilizing the task switcher like just loop reading a high speed free running clock after turning off the interrupts to stop preemption. The period is way smaller than a context switch period so worst you do is jitter the task switch by the delay period.
The worst case for the above is if you called the delay just as a timer tick is due. You end up with an 11ms (10ms + 1ms hard loop delay) before you allow the next switch and the next slice ends up at 9ms. Is that acceptable is a depends situation on what you are doing and in many situations you would not even notice it.
