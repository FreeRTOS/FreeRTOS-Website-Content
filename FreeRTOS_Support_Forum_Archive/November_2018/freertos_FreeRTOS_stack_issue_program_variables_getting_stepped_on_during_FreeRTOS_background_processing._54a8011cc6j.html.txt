  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pblase">pblase</a> on November 22, 2018</div><div class="thread-post-content">Working on an Atmel ATSAMC21N-XPRO demo board (ATSAMC21N18A processor), using Atmel Studio with the GNU tools, FreeRTOS rev 10.0.0 as per the Atmel START web utility.  The main program is written in C++, with the files copied over from a separate project created by the START utility (which uses ASF 4 and only works with C; however all files have the proper 
~~~
<h1>ifdef __cplusplus</h1>
extern &#8220;C&#8221; {
<h1>endif</h1>
&#8230;
<h1>ifdef __cplusplus</h1>
}
<h1>endif</h1>
~~~
surrounding them and compile fine.  I&#8217;ve had similar code running before, without FreeRTOS, and it seems to work fine. 
In the main program file, there&#8217;s the instantiation  of a class 
Heartbeat<em>LED</em>task<em>t Heartbeat</em>LED_timer;
In the .map file, this ends up right below the FreeRTOS stuff:
~~~
 .bss           0x200004d0       0x20 ProElec<em>R2</em>ATSAMC21N.o
                0x200004d0                ErrorInfo
                0x200004d4                retval
                0x200004d8                Heartbeat<em>LED</em>timer &lt;===
 .bss           0x200004f0      0x968 thirdparty/RTOS/freertos/FreeRTOSV10.0.0/Source/portable/MemMang/heap_1.o
 .bss           0x20000e58       0xec thirdparty/RTOS/freertos/FreeRTOSV10.0.0/Source/tasks.o
                0x20000e58                pxCurrentTCB
 .bss           0x20000f44       0x3c thirdparty/RTOS/freertos/FreeRTOSV10.0.0/Source/timers.o
 ~~~
So far so good. 
The task that uses Heartbeat<em>LED</em>timer executes its loop once every 10th second and then uses 
   vTaskDelayUntil(&amp;xLastWakeTime, pdMS<em>TO</em>TICKS(HEARTBEAT<em>LOOP</em>ms)); //tenth second
to delay until the next .1 second mark. 
While the program is sleeping, between calls, the FreeRTOS steps on it; pretty much any time that FreeRTOS uses a local variable, it ends up located inside of the above variables. 
For instance, I used the data-change breakpoint to trace it and found:
Line 2016 of tasks.c is<br />
~~~
    UBaseType_t uxPendedCounts = uxPendedTicks; /* Non-volatile copy. */
~~~
which is in xTaskResumeAll(void). 
 When this executes, uxPendedCounts is located in the middle of Heartbeat<em>LED</em>timer! 
Looking at the disassembly, uxPendedCounts  is found at R7 + 4
(&#8221; 000063FC str r3, [r7, #4]&#8221;)
Sure enough, R7 is pointing right to the middle of Heartbeat<em>LED</em>timer. R7 is set somehow in the setup for xTaskResumeAll(). 
( put a screenshot in the attached .zip file)
Obviously there&#8217;s a setting wrong somewhere, but I have no clue what it could be.

that into the subject of the thread so others that use C++ themselves 
see it.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pblase">pblase</a> on November 23, 2018</div><div class="thread-post-content">Is this code executing in the task stack, or is there a separate stack for the kernal itself?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 24, 2018</div><div class="thread-post-content">I&#8217;m not sure what is meant by executing in the task stack.  Do you mean using the task stack?  FreeRTOS applications are just normal C application (C++ in this case) so how the stack is used is completly up to the compiler while tasks are running.  When an interrupt executes then the stack is swtich, but everything else uses the task&#8217;s own stacks.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pblase">pblase</a> on November 24, 2018</div><div class="thread-post-content">The code in tasks.c executes in the background, independent of any task. Ok, so it&#8217;s an application problem, either the entire application is overflowing the stack, not likely, or some memory parameter is set wrong. 
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on November 24, 2018</div><div class="thread-post-content">Paul, ALL code that executes once the scheduler starts MUST run either in the context of a task, or the context of an interrupt. There isn&#8217;t a &#8216;the task stack&#8217;, but each task is given its own stack, and the scheduler switches tasks by changing which stack is being used. 
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pblase">pblase</a> on November 24, 2018</div><div class="thread-post-content">Just as a note, several people have used FreeRTOS with C++ with few problems. 
https://stackoverflow.com/questions/20921721/freertos-with-c-main-file
https://interactive.freertos.org/hc/en-us/community/posts/210028906-Using-FreeRTOS-with-C-
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on November 24, 2018</div><div class="thread-post-content">Yes, C++ is not generally the issue. C++ problems tend to give errors at compile/link time, unless you make the big mistake of putting a non-POD type into a queue. The basic problem sounds to be memory overruns or memory map issues which are about as easy to create with C code as C++ code.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS stack issue, program variables getting stepped on during FreeRTOS background processing. </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pblase">pblase</a> on November 24, 2018</div><div class="thread-post-content">Ok. The problem was that the stack wasn&#8217;t quite big enough. The Process Stack  Pointer must be used to point to the thread stack, the Main Stack Pointer to the application stack (at the far end of memory). Since the PSP is decremented during pushes, it simply went past the end of the allocated FreeRTOS tasks.o area (where the task stacks are).
