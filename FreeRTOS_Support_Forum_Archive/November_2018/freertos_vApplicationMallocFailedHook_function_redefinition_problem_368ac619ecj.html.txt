  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/claudiorossi">claudiorossi</a> on November 19, 2018</div><div class="thread-post-content">Hi
I&#8217;am developing a FreeRTOS application on Zynq7000 with SDK 2018.2 and I have problem with vApplicationMallocFailedHook function.
I have defined my own function but the standard function present in portZynq7000.c is always called.
I have defined my own  vApplicationAssert function too, but in this case the redefinition works fine.
The two standard functions are defined in the same portZynq7000.c file so I don&#8217;t understand the 
different behaviour.
In source file I get the following comment:
/* This default malloc failed hook does nothing and is declared as a weak symbol
to allow the application writer to override this default by providing their own
implementation in the application code. */
void vApplicationMallocFailedHook( void )
{
    xil_printf( &#8220;vApplicationMallocFailedHook() calledn&#8221; );
}
Someone have suggestions? Do I need to set some different?
Thanks for help
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on November 19, 2018</div><div class="thread-post-content">If it is defined as a weak symbol as the comment says (but I don&#8217;t see the directive that makes it a weak definition, maybe you trimmed that directive off) then if you define you version as non-weak it will over-ride the weak definition. If you copied the weak definition directive into your code, then deending on the order the files are processed will control which definition gets used.
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/claudiorossi">claudiorossi</a> on November 19, 2018</div><div class="thread-post-content">Hi Richard
The weak attribute is defined at top of PortZynq7000.c file:
void vApplicationAssert( const char *pcFileName, uint32_t ulLine ) <strong>attribute</strong>((weak));
void vApplicationTickHook( void ) <strong>attribute</strong>((weak));
void vApplicationIdleHook( void ) <strong>attribute</strong>((weak));
void vApplicationMallocFailedHook( void ) <strong>attribute</strong>((weak));
void vApplicationStackOverflowHook( TaskHandle_t xTask, char *pcTaskName ) <strong>attribute</strong>((weak));
I only rewrite the function without add any directives. 
I tried to redefine the vApplicationIdleHook function too, but the standard function is always called.
In Xilinx SDK the FreeRTOS is compiled as a standalone library. May be this the problem?
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/claudiorossi">claudiorossi</a> on November 19, 2018</div><div class="thread-post-content">I have solved the problem. 
I need to insert the functions prototype (without weak attribute) in FreeRtosConfig.h file.
Unfortunately this file is automatically generated by Xilinx SDK tool so I need to modify
the tcl script file used by the tool.

</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on November 28, 2018</div><div class="thread-post-content">The symptoms sound like the need to mark the file as extern &#8220;C&#8221;. It may be that by putting the decleration in FreeRTOSConfig.h it is getting wrapped in the extern &#8220;C&#8221; automatically. It could be that the tool&#8217;s autogenerated header wraps most of FreeRTOSConfig.h in an extern &#8220;C&#8221; section, which could be it being helpful as you often end up declaring function there for use as call backs for FreeRTOS.
The solution to the regeneration is to not add the decleration to FreeRTOSConfig.h, but to add the extern &#8220;C&#8221; lines in the file where you define the function, either wrapping a pre-decleration or the definition.
I often have a &#8216;hooks&#8217; file for the various FreeRTOS hooks that has near the beginning
extern &#8220;C&#8221; {
then has the various hook functions for FreeRTOS
and then the section ends with 
}
Note, the functions in between are still C++ functions, but use the C linkage rules so they internally use the C linkage nameing rules, not the C++ rules that support overloading, so FreeRTOS can call them.
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationMallocFailedHook()  function redefinition problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/claudiorossi">claudiorossi</a> on November 30, 2018</div><div class="thread-post-content">Hi Richard
Your solution is correct.  Adding extern &#8220;C&#8221; {&#8230;declaration&#8230;} to the file where I have my functions solve the issue.
Thank you
