</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-TCP performance issues with LPC1768</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 6, 2018</div><div class="thread-post-content">Hi Andi,
<blockquote>
  Changing it to a <code>while(!empty)</code> and therefore processing all the data
</blockquote>
That&#8217;s indeed the usual way of working: the working task is woken-up from a MAC-interrupt ( either by a task notification or a semaphore ).
The working task checks both queues: reception and transmission, each in a <code>while(!empty)</code> loop.
While working on these queues, new notifications may come in.  That is no problem, the next <code>xTaskNotifyWait()</code> will return immediately without blocking.
<blockquote>
  seems to have got the ping response consistently down to 0.5ms
</blockquote>
Great! In case you have Linux: try <code>sudo ping -f &lt;address&gt;</code> to have a continuous flood of ICMP packets.
Here are some items that determine the performance of an Ethernet driver:
<ul>
<li>Filtering unwanted traffic using MAC filters and hash filters.</li>
<li>Early filtering: packets that are accepted by the MAC can be filtered by the driver: think of unwanted broadcast packets.  It is a waste of time to pass them to the IP-stack if they&#8217;re not used later on.</li>
<li>Consider using multi-casting in stead of broadcasting. I have seen networks that are littered with IPv4 broadcasts.</li>
<li>CRC offloading, unfortunately not available on a LPC1768</li>
<li>Use zero-copy methods wherever possible</li>
</ul>
Normal optimisations:
<ul>
<li>Disable stack checking</li>
<li>Use C optimisation level</li>
<li>Disable asserts ( if you dare )</li>
</ul>
You can also check the network performance with iperf3, see <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/e6c5bd5f/?limit=250#7bb5">this post</a>

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS-TCP performance issues with LPC1768</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 10, 2018</div><div class="thread-post-content">When the number of available Network Buffers is getting close to zero, you have a serious problem.
Here are some simple strategies to investigate it:
I would try not to block on the availability, and in stead just drop a packet.
Suppose your driver received a packet, you want to copy it to a Network Buffer, but none is available: I would increase some error-counter and drop the packet.
And for a zero-copy driver: a packet has arrived, but you do not have a new Network Buffer to replace it: leave the current Network Buffer assigned to DMA and drop the packet.
Suppose that <code>xNetworkInterfaceOutput()</code> is called and there is no DMA buffer available within e.g. 10 ms, I would increase a counter and drop it.
At every place where packets are dropped, please update some counter so that you can study the behaviour!
UDP packets are stored in Network Buffers. It is important to have those packets read/consumed by the task that owns the socket. If not, you loose valuable Network Buffers. If the CPU is very busy, it may happen that such a task doesn&#8217;t get enough CPU-time to process them.
( please note the macro <code>ipconfigUDP_MAX_RX_PACKETS</code>, that can help here )
In principle, the IP-task should never block on getting resources. One exception is <code>xNetworkInterfaceOutput()</code>, which may wait a few ms for an available DMA buffer. But if it waits for a Network Buffer, in most cases, it will be waiting for itself.
In the end, you do not want a TCP/IP stack  in which packets are dropped regularly. The above method is a way of studying the behaviour. Once all parameters are well tuned, packets are rarely dropped and there should always be enough Network Buffers.
