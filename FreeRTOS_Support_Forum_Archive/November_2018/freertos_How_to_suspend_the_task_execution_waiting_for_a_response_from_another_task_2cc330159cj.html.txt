  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">How to suspend the task execution  , waiting for a response from another task</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/b3nway">b3nway</a> on November 15, 2018</div><div class="thread-post-content">Hi all,
I&#8217;m a beginner to Freertos,  and I want to write a  function <strong>API<em>get</em>uart_data()</strong> designed as part of a library.
The basic idea is to introduce an abtraction layer architecture in my firmware project.
Summarizing :
<strong>API<em>get</em>uart_data()</strong>   returns NULL if no data is present on UART port 
If a data is present in the queue, **API<em>get</em>uart_data() **  returns a pointer to data. 
I have already implemented the task <strong>HAL<em>UART</em>task()</strong>  which stores in a DATA queue the incoming messages from  serial port.
This is a simple usecase:
my<em>application</em>task()
{
    while (1)
    {
        if (<strong>API<em>get</em>uart_data()</strong> != NULL )
        {
          /*do something with the data &#8230; */
        }
    }
}
Now my question: 
<strong>my<em>application</em>task()</strong> should be in [SUSPENDED] state until <strong>API<em>get</em>uart_data()</strong> returns a valid result
What could be the best way to implement this mechanism?
In other words, this is my current idea of a possible implementation:
UART<em>message*  <strong>API_get_UART_data(void)</strong>
{
    UART</em>message*  temp<em>message = NULL;
    current</em>task _handler =  <strong>xTaskGetCurrentTaskHandle()</strong>;
    /* send message to <strong>HAL_UART queue **  with (  tempmessage , currenttask _handler  )*/
  ** vTaskSuspend( current_task _handler);</strong>
/****************************/
/*  <strong>HAL<em>UART</em>task()</strong>  will ceck for a message in the DATA queue , changing temp_message if necessary.
/* now  <strong>HAL_UART_task()</strong> resumes using <strong>vTaskResume( current_task _handler);</strong> */
/****************************/
<pre><code>return tempmessage;
</code></pre>
}
any advice and suggestions will be greatly appreciated.
Thanks.
Giorgio.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to suspend the task execution  , waiting for a response from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on November 15, 2018</div><div class="thread-post-content">You have defined your API badly for this task, as your API doesn&#8217;t block, so it must be polled, forcing the application to work around this limitation.
Redefine your API<em>get</em>uart_data to have a parameter for how long to wait for data, and if the timeout expires, return the null, and if not return the pointer to the data. Then the consumer can make the blocking call and wait for the data. This timeout value can then be passed to the queue fetch operation that the UART task has put the data in.
Personallly, I tend to have the UART ISR do most of the packing work of assembly the low level message and putting it onto a FreeRTOS queue, and then the application level UART task takes that data, with no intermediate &#8216;uart driver&#8217; task in the middle. The receive side API is basically a simple call wrapper for that queue receive operation.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to suspend the task execution  , waiting for a response from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/b3nway">b3nway</a> on November 15, 2018</div><div class="thread-post-content">Hi Richard, thank you for the reply.
I agree with you about my not clever API definition,  but at this moment I&#8217;m focusing on  the possibilities provided  by FreeRTOS in order to Suspend/Resume a desired task.
Maybe a dedicated semaphore could be considered as a valid alternative.
In any case, trying to explain better my expectations:
when <strong>API<em>get</em>uart_data()</strong> is called by  <strong>my<em>application</em>task()</strong>
1) A query is sent to <strong>AL<em>UART</em>task()</strong>  , providing a pointer for the response
2) <strong>my<em>application</em>task()</strong> is  [SUSPENDED] by <strong>API<em>get</em>uart_data()</strong>
3) when <strong>AL<em>UART</em>task()</strong> intercepts the query, it updates the provided response pointer and resumes <strong>my<em>application</em>task()</strong>
4) updated response is returned by <strong>API<em>get</em>uart_data()</strong>
Is this a common architecture design in FreeRTOS?
What could be considered the most reasonable options in order to implement my idea? 
Thanks.
Best Regards.
Giorgio.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to suspend the task execution  , waiting for a response from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 15, 2018</div><div class="thread-post-content">I would not use suspend/resume here as there is a fundamental data race.
I would have API<em>get</em>uart_data() block on something, either a semaphore, queue or direct to task notification for the answer to be ready
</div></div><div class="thread-post"><h3 class="thread-post-title">How to suspend the task execution  , waiting for a response from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/b3nway">b3nway</a> on November 23, 2018</div><div class="thread-post-content">Hi Richard, thank you for your suggestion.
I changed my strategy, implementing  <strong>API<em>set</em>callback<em>uart</em>data( *void )</strong>  instead of <strong>API<em>get</em>uart_data()</strong>.
Briefly:
<strong>API<em>set</em>callback<em>uart</em>data (*function_ptr) ** starts a dedicated task , which  is triggered  by UART_DATA and calls  **function_ptr()</strong>  .
This approach seems  more efficient to me.
Regards.
Giorgio.
