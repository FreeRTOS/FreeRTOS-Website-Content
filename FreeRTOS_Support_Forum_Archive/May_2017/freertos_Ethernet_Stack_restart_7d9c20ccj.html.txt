The latest version of the STM32F4 driver is not on /Labs yet, but you can download <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/39bcfcfb/?limit=25#3ee0">it here</a>
<blockquote>
  I am receiving the &#8220;ETH<em>DMA</em>IT_RO&#8221; status in IRQ handler,
  even if I reset it, not helping. It toggles back to same.
   What are the possibilities for this and how can I resolve this ?
</blockquote>
You&#8217;re getting this error:
~~~
    /*
     * Bit 4 ROS: Receive overflow status
     * This bit indicates that the receive buffer had an
     * overflow during frame reception. If the partial 
     * frame is transferred to the application, the
     * overflow status is set in RDES0[11].
     <em>/
    #define ETH_DMA_IT_RO    ((uint32_t)0x00000010)  /</em>!&lt; Overflow interrupt */
~~~
My feeling says: that should never occur!
Are you supplying internal SRAM to the DMA, both for the descriptors as well as for the network buffers? Do you give proper memory, or have the descriptors been corrupted?
Are you using any external (S)DRAM at all?
Ethernet is fast, the DMA must transport data at 10 MByte per second. Do you have concurrent DMA transports? Can you play with their priorities?
I will answer your earlier question later on. Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">Ethernet Stack restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 9, 2017</div><div class="thread-post-content"><blockquote>
  I am in a scenario where I need to restart/reinit the Ethernet stack.
  I have STM32Fxx driver and code, Is there any built-in function to do
  the same ? I will be setting the new IP and related params before this
  reset. MAC ID will be same, so I believe I don&#8217;t have to recreate the
  IP task.
</blockquote>
That is right, both the IP-task as well as the EMAC task ( prvEMACHandlerTask ) will keep on running.
The EMAC does not need a reset. If you want to change the MAC-address ( which you do not want to ), you can write the new MAC address into some registers.
You could do that every time when <code>xNetworkInterfaceInitialise()</code> is called by calling <code>prvMACAddressConfig()</code>.
<blockquote>
  HAL<em>ETH</em>Start/Stop is not helping much there.
</blockquote>
Right, the EMAC settings haven&#8217;t change so the EMAC is not the problem.
<blockquote>
  I am able to get my required functionality done with just
  FreeRTOS<em>SetIPAddress() and others params, but not reliable, few times
  I get issue (for which I am thinking of reset now) as I have multiple
  tasks and control is sliced to other tasks also. The issue is after I
  try to set new IP, I see the timeout for ping requests (nothing from
  stack will be responsive), I don&#8217;t see any assert/hang. Is there any
  other way to read the device IP other than FreeRTOS</em>GetIPAddress()?.
  Any input on phy/stack reset related will be helpful.
</blockquote>
I think that you won&#8217;t be able to solve that problem <strong>on the embedded side</strong>. The problem is that you change a binding of a MAC-address with an IP-address. The host that you are working on is still using the old binding.
If my reasoning is true, the following should help within Windows: start a command prompt as an administrator. Enter the command <code>arp /d *</code> to clean the local ARP tables.
For Linux: <code>sudo ip -s -s neigh flush all</code>.
Beside that, you might see some time-outs, things might not work immediately.
Another issue that may occur is that the device does not connect through TCP after rebooting. That may be caused by the fact that your <code>ipconfigRAND32()</code> function does not get a unique seed after booting.
When a TCP socket is bound to port 0, a random port number will be assigned. After a reboot, these port numbers should start at a different number.
Another thing that should be random is the Initial Sequence Number in a TCP connection. When the device uses the same port and the same initial sequence number, the connection is bound to fail.
Hein
</div></div><div class="thread-post"><h3 class="thread-post-title">Ethernet Stack restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 9, 2017</div><div class="thread-post-content">Hi Shaank,
<blockquote>
  I use external SDRAM for my firmware.
</blockquote>
Are you providing SDRAM memory to DMA? Either as data buffer or as DMA descriptors?
If so, I would try to use internal SRAM for that purpose, and the DMA error <code>ETH_DMA_IT_RO</code> will disappear.
<blockquote>
  Anyway, its not the throughput/performance issue is problem for me
  it looks like, I have multiple threads being sliced(2ms) in my platform,
  doing different activities like write to flash/read/display/ etc.
  So when new config is being downloaded, I feel it takes the ticks away
  from emac task for a while. I have reduced the emac task priority and
  its been sliced by my task scheduler. Will that cause the problem for stack?
</blockquote>
The <code>ETH_DMA_IT_RO</code> error is not caused by tasks that are too late or too slow.
We advice the following scheme for priorities when using FreeRTOS+TCP:
Prio-4  High-priority tasks that do not use +TCP
Prio-3  prvEMACHandlerTask, deferred EMAC interrupt handler
Prio-2  IP-task ( ipconfigIP<em>TASK</em>PRIORITY )
Prio-1  Application tasks that do use +TCP
Regards.
