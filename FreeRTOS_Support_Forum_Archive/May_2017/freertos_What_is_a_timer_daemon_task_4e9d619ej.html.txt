</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 28, 2017</div><div class="thread-post-content">The timer daemon task deals with &#8216;Timers&#8217; (see http://www.freertos.org/FreeRTOS-Software-Timer-API-Functions.html ) not time delays like vTaskDelay. It is also used so an ISR can request the exectuion of a small piece code at the &#8216;Task Level&#8217; to avoid adding lattency at the interruupt level.
vTaskDelay is used to make the current task wait a bit, maybe a delay to let things happen, or to put a delay in a task loop so you only check something periodically.
A Timer lets setup a function to be called at a certain time in the future or at a defined rate. These functions should be short and fast, as all these functions will execute in the context of the Timer Daemon task, but can often be used to avoid the need to create a bunch of small periodic tasks. The also can be used as an asyncronous time out for an action. When you start an action, you start a timer. When you complete the action, youu stop and clear the timer. If the timer exprires, then the action didn&#8217;t complete in time, and the timer callback can initiate an abort for the action.
</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on May 28, 2017</div><div class="thread-post-content">Software timers are realized by FreeRTOS with the timer daemon task.
The timer daemon task does all the timer bookkeeping for you and eventually invokes the callback function specified on timer creation.
A (normal) task may start a number of such timers and just continues to run.
This timers can be seen as asynchrounous wrt. to the starting task.
vTaskDelay is a synchronous sleep of the calling task ie. the task is directly moved from running into blocked state.
The scheduler driven by the SysTick and wakes up the blocked/delayed task(s) after the number of ticks corresponding to the given delay.
These are different concepts.
In bare metal applications vTaskDelay is often implemented as a simple busy loop since there is no need to give up the CPU to allow other tasks to run.
Software timers require more effort to implement.
</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 28, 2017</div><div class="thread-post-content">The RTOS creates one or two system tasks &#8211; tasks that are created 
automatically when the scheduler is started for use by the RTOS itself. 
The first system task is the Idle task, which is always created.  The 
second system task is the timer <a 
href="https://en.wikipedia.org/wiki/Daemon_(computing)">daemon</a> task, 
which is also referred to by its older name as the timer service task. 
The timer daemon is created by the RTOS if configUSE_TIMERS is set to 1.
The RTOS uses the daemon to manage <a 
href="http://www.freertos.org/RTOS-software-timer.html">FreeRTOS 
software timers</a>, and nothing else.  FreeRTOS API functions that 
start &#8216;Timer&#8217; will somehow interact with the timer daemon task within 
their implementation (not seen by the application writer), and software 
timer callback functions execute in the context of the timer daemon 
task.  Users can also <a 
href="http://www.freertos.org/xTimerPendFunctionCall.html">send 
functions to the daemon task</a> so they execute in the context of the 
daemon task rather than the application task.
No other functions use the daemon task.  So, using your example, the 
daemon task has no role in the execution of functions such as 
vTaskDelay() &#8211; and those functions will work the same even when the 
timer daemon task is not created (which would be the case if 
configUSE_TIMERS was set to 0).
</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leesp">leesp</a> on May 29, 2017</div><div class="thread-post-content">I&#8217;ll try to explain what I understand, correct me if I am wrong:
Timer daemon task is a handler task to the tick interrupt handler (a.k.a &#8220;ISR&#8221;)
Say for example application programmer created and started a timer<em>1 with period 10ms. The Systick is 1ms (configTICK</em>RATE<em>Hz = 1000)
At each tick interrupt, the tick interrupt ISR would execute, and then give semaphore to the daemon task to make it Ready. If now the daemon task is of highest priority, it will execute. Part of what the daemon task is doing is, to decrement timer</em>1&#8217;s timer value. So after 1st tick interrupt, timer<em>1&#8217;s value becomes 9. Then the daemon task would block. When the next tick interrupt happens, daemon task Run again and decrement timer</em>1&#8217;s value.. so on and so forth. After 10 tick interrupt, daemon tasks finds that timer_1&#8217;s value is 0, and thus execute the callback function.
Correct?
</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on May 29, 2017</div><div class="thread-post-content">In principle you are right but the implementation is different.
In fact the timer daemon task is just doing kind of vTaskDelay waiting for the next due timer to expire or another timer related request arrives (start, cancel, etc.).
The SysTick ISR handler is the scheduler itself.
If you&#8217;re really interested in all the gory details see timers.c.
On the other hand you could just use it. It works 🙂

</div></div><div class="thread-post"><h3 class="thread-post-title">What is a &#8220;timer daemon task&#8221;?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 30, 2017</div><div class="thread-post-content"><blockquote>
  Q1. Does it mean that, at every tick interrupt, timer1&#8217;s tick will 
  decrement by 1?
</blockquote>
No, processing each timer on each tick interrupt would be extremely 
inefficient.  The timer daemon/service task enters the Blocked state 
until the timer is due to expire.  Blocked tasks use no processing time 
at all, be that in the tick interrupt or elsewhere.
