  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kostas2010">kostas2010</a> on May 17, 2017</div><div class="thread-post-content">Raising BASEPRI on M7 port (v9.0.0) is done as below:
~~~
<h1>define portDISABLE_INTERRUPTS()                vPortRaiseBASEPRI()</h1>
static portFORCE_INLINE void vPortRaiseBASEPRI( void )
{
uint32<em>t ulNewBASEPRI = configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY;
<pre><code>__asm
{
    /* Set BASEPRI to the max syscall priority to effect a critical
    section. */
    cpsid i
    msr basepri, ulNewBASEPRI
    dsb
    isb
    cpsie i
}
</code></pre>
}
~~~
Could you explain the need for a DSB?
Additionally,  I understand that ISB is used to ensure that when this function returns, the BASEPRI change is observed. However this makes sense only if ISB is placed after &#8220;cpsie i&#8221; instruction so that the PRIMASK clear is also observed. 
I have also looked into this (http://infocenter.arm.com/help/topic/com.arm.doc.dai0321a/DAI0321A<em>programming</em>guide<em>memory</em>barriers<em>for</em>m_profile.pdf) but I could not find the exact case in the guidelines.
</div></div><div class="thread-post"><h3 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 17, 2017</div><div class="thread-post-content">The cpsid/cpsie instructions are a workaround to a silicon errata and 
are only required if the revision of the core is r01p, otherwise use the 
Cortex-M4F port layer.  I imagine the errata docs will be the only place 
they are mentioned.
</div></div><div class="thread-post"><h3 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kostas2010">kostas2010</a> on May 18, 2017</div><div class="thread-post-content">Thank you for your answer. 
What about the need for DSB? Is it required after the MSR instruction that sets BASEPRI?
(To help our discussion I am pasting the CM4F port that is suitable for our CM7 (non r0p1))
~~~
static portFORCE<em>INLINE void vPortRaiseBASEPRI( void )
{
uint32</em>t ulNewBASEPRI = configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY;
<pre><code>__asm
{
    /* Set BASEPRI to the max syscall priority to effect a critical
    section. */
    msr basepri, ulNewBASEPRI
    dsb
    isb
}
</code></pre>
}
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 18, 2017</div><div class="thread-post-content">On the M3 and M4 it is actually after the next instruction: &#8220;MSR 
side-effects are visible after one further instruction is executed&#8221;.  I 
believe it is different on the M7 though and will have to look it up. 
The M4F port was updated so it could also be used on an M7.
</div></div><div class="thread-post"><h3 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kostas2010">kostas2010</a> on May 19, 2017</div><div class="thread-post-content">So, for M3/4 at least, removing the DSB instruction means that the side-effects will be visible after the ISB instruction, which is what we want. So it looks that practically there is no need for a DSB. 
I will be waiting for your findings on M7 as well. Many thanks again for the help. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Use of barriers when setting BASEPRI on Cortex M7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kostas2010">kostas2010</a> on May 24, 2017</div><div class="thread-post-content">Any news on this?
