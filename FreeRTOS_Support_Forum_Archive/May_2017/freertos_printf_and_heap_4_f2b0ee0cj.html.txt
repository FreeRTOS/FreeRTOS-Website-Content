called.

</div></div><div class="thread-post"><h3 class="thread-post-title">printf and heap_4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 22, 2017</div><div class="thread-post-content">I think C should only attempt to pull undefined symbols from the library 
&#8211; that is &#8211; the symbol is not in the application so look for it in the 
library.  However GCC seems to want to complain when it seems the same 
symbol defined in both the application and the library unless you 
explicitly tell it not to, which you have to do using a command line 
option.  Search the GCC manual for something like &#8216;multiply defined&#8217; to 
find the necessary option.
</div></div><div class="thread-post"><h3 class="thread-post-title">printf and heap_4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 23, 2017</div><div class="thread-post-content">If your implementation uses newlib-nano, another option is to look to see if they are using the RTOS compatible versions which call a __malloc<em>lock() and __malloc</em>unlock(), which you can then define to call the FreeRTOS scheduler stop/restart functions like heap3.h does. Then malloc and family are as threadsafe as pvPortMalloc(). 
</div></div><div class="thread-post"><h3 class="thread-post-title">printf and heap_4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on May 23, 2017</div><div class="thread-post-content">You could also use the &#8216;&#8211;wrap&#8217; linker flag and provide the corresponding wrapper functions.
</div></div><div class="thread-post"><h3 class="thread-post-title">printf and heap_4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 23, 2017</div><div class="thread-post-content">Hi Massimiliano,
Like Richard, I also tend to avoid the clib or newlib heap functions ( and their reentrant equivalents <code>_r</code> ), by using the linker or a <code>configASSERT()</code>.
The FreeRTOS+ library has its own task-safe implementation of all <code>printf()</code> functions, which:
● Does not use the HEAP
● Has a low usage of the stack
● May be called from within an ISR as well
The module <code>printf-stdarg.c</code> needs two external functions, provided by you:
~~~
    /*
     * &#8216;aAddress&#8217; is a memory address.
     * Return 1 for readable, 2 for writeable, 3 for both.
     * Function must be provided by the application.
     */
    extern BaseType_t xApplicationMemoryPermissions( uint32_t aAddress );
<pre><code>/*
 * vOutputChar() shall output a character to "stdout"
 * It is called in case a sprintf() function is called with
 * the NULL pointer.
 */
extern void vOutputChar( const char cChar, const TickType_t xTicksToWait  );
</code></pre>
~~~
Note that this crash will be avoided if you implement <code>xApplicationMemoryPermissions()</code> :
~~~
    int iNumber = 12;
    /* In the printf call %s is used in stead of %d,
    which may lead to a crash.  The printf functions
    in printf-stdarg.c will print it as &#8220;INV_MEM&#8221; */
    printf( &#8220;The answer is %sn&#8221;, iNumber );
~~~
In case you do need a <code>realloc()</code> function, I attached a tested version in which it is called:
~~~
    void *pvPortRealloc( void *pvAddres, size_t uxNewSize );
~~~
It adds a new function <code>uxPortGetSize()</code> which returns the length of any pointer in the heap ( using heap<em>4 or heap</em>5 ). The length is rounded up to a multiple of e.g. 8 bytes, due to its allocation.
See attachment <code>realloc_and_printf.zip</code> for both source files.
Regards.
