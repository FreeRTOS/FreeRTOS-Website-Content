  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">wrong use of #defines in xQUEUE type, v9.0.0</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/odman">odman</a> on May 25, 2017</div><div class="thread-post-content">~~~
In queue.c, 
typedef struct QueueDefinition
    #if ( configUSE<em>TRACE</em>FACILITY == 1 )
        UBaseType<em>t uxQueueNumber;
        uint8</em>t ucQueueType;   //&lt;&#8211; Line 162
    #endif
} xQUEUE;
In xQueueGenericReceive(), line 1279
                    #if ( configUSE<em>MUTEXES == 1 )
                    {
                        if( pxQueue->uxQueueType == queueQUEUE</em>IS_MUTEX )
                        {
In my FreeRTOSConfig.h:
<h1>define configUSE_MUTEXES                         ( 1 )</h1>
<h1>define configUSE<em>TRACE</em>FACILITY                  ( 0 )</h1>
~~~
I&#8217;m not sure how this even compiles, but it does with GNU ARM 4.9.3. The result is that illegal memory is written with unpredictable consequences.
cheers
Knut
</div></div><div class="thread-post"><h3 class="thread-post-title">wrong use of #defines in xQUEUE type, v9.0.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 25, 2017</div><div class="thread-post-content">Please have a look at the large comment around line 97, and these defines :
~~~
<h1>define pxMutexHolder                   pcTail</h1>
<h1>define uxQueueType                     pcHead</h1>
~~~
In case a queue object is in fact a mutex, the two fields are not used in their normal way (head, tail).  These are pointers, not characters. <code>uxQueueType</code> will be set to NULL (<code>queueQUEUE_IS_MUTEX</code>).
It may look a bit confusing, but it is entirely local to <code>tasks.c</code>.  I&#8217;m sure it was done to save a few bytes of RAM.
In another C project a <code>union</code> could be used for this, but <code>union</code>&#8216;s are not supported by all compilers that are used to compile the FreeRTOS kernel.
The member used when tracing: <code>ucQueueType</code> is indeed an 8-bit field that holds a copy of &#8216;ucQueueType&#8217; that was used during creation.
In short: there is nothing wrong with it.
