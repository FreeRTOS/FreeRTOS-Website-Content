  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Scheduler problem writing to internal flash</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmp1104">cmp1104</a> on January 7, 2013</div><div class="thread-post-content">I am using FreeRTOS v. 7.02 and an EFM32 microcontroller with IAR.&nbsp; I have a task that executes periodically by timing out waiting for a semaphore.&nbsp; The task collects some data and writes it to the internal flash of the microcontroller.&nbsp; Without the write to flash functionality, I have confirmed that the task executes as expected &#40;correct timing, data collection, etc.&#41;.&nbsp; However when I put the flash functionality in place, the task executes once &#40;i.e., writes one set of data to flash&#41; and then appears to get lost in the scheduler.&nbsp; From the RTOS plugin I can see that when things get lost the scheduler lists the task as in the running state.&nbsp;   
I know that writting to flash means that the code needs to execute from RAM.&nbsp; The EFM32 memory module does this already.&nbsp; I am also disabling interrupts prior to writing to flash and re-enabling when done.&nbsp; Is it possible that by dissabling the interrupts that the RTOS RTC tick interrupt is not executing and therefore the scheduler gets confused?   
Any insight would be appreciated.  
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler problem writing to internal flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on January 7, 2013</div><div class="thread-post-content">The EFM32 is a Cortex-M3 so if interrupts are left disabled for a long time the SysTick will generate lots of tick interrupts but all of them except one will just be lost. That will have the effect of the time kept by the kernel slipping against actual time, but nothing else.  
I have had behavior like that before and it turned out that the task was stuck in a polling loop inside a third party driver library function. The plug in said the task was Running, and it was, it was sat in a loop waiting for a bit to get set that never got set.
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler problem writing to internal flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmp1104">cmp1104</a> on January 7, 2013</div><div class="thread-post-content">Thanks for the reply.&nbsp; So it sounds like missing a SysTick interrupt is not a big deal.  
The program is getting hung up in vListInsert at:<br />
for&#40; pxIterator = &#40; xListItem &#42; &#41; &amp;&#40; pxList-&gt;xListEnd &#41;; pxIterator-&gt;pxNext-&gt;xItemValue &lt;= xValueOfInsertion; pxIterator = pxIterator-&gt;pxNext &#41;  
This is within an else statement that warns this point could be reached if 1&#41; Stack overflow 2&#41; Incorrect interrupt priority assignment 3&#41; Calling an API function from within a critical section 4&#41; Using a queue or semaphore before it has been initialized or the scheduler started.   
I am pretty sure 2, 3, 4 are not the cause.&nbsp; After the one successful write to flash I used the xTaskGetSchedulerState function to verify that the scheduler was still running.&nbsp; I don&#8217;t think it is a stack overflow either.
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler problem writing to internal flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on January 7, 2013</div><div class="thread-post-content">If the tick interrupt was still executing, and you have stack overflow checking switched on &#40;<a href="http://www.freertos.org/Stacks-and-stack-overflow-checking.html%29">http://www.freertos.org/Stacks-and-stack-overflow-checking.html&#41;</a> then FreeRTOS would catch a stack overflow, but if the tick interrupt was not running you would have to manually check in the debugger. Manually checking is easy if you have the state viewer plug in because you can have the plug in show the stack high water mark. Do you know what the plug in is reporting as the high water mark for that task?  
xTaskGetSchedulerState&#40;&#41; is not going to help much here because it will just report what it thinks the state is, in this case, it has been started and is not suspended so it will report that it is running.  
How are you disabling interrupts? The proper way is to call taskENTER&#95;CRITICAL&#40;&#41; and taskEXIT&#95;CRITICAL&#40;&#41; because they will keep a nesting count, but if the flash write driver disables and enables interrupts itself the critical section nest count could get messed up. Do you know if the drivers that write to the flash enables interrupts even if they were disabled when the function is called.  
Do the drivers that write to the flash use any interrupts or try to configure the systick timer to generate delays?
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler problem writing to internal flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmp1104">cmp1104</a> on January 7, 2013</div><div class="thread-post-content">1.&nbsp; In my FreeRTOS Config file I have configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW = 2.&nbsp; I have a vApplicationStackOverflowHook function and I know I am not hitting that.&nbsp; With my plugin the &#8220;Min Free Stack&#8221; is reported as &gt;256.&nbsp;<br />
2&#46; To disable the interrupts I am using the EM defined function INT&#95;Disable&#40;&#41; &#40;and re-enabling them using INT&#95;Enable&#41;.&nbsp; The function is supposed to disable interrupts at the CPU level and protect critical sections of code.&nbsp; Like the taskENTER&#95;CRITICAL&#40;&#41; and taskEXIT&#95;CRITICAL&#40;&#41; functions the EM functions use a counter to track entering and exiting protected sections of code.&nbsp; I did a quick quick and placed taskENTER&#95;CRITICAL&#40;&#41; and taskEXIT&#95;CRITICAL&#40;&#41;&nbsp; before and after my call to the flash writing function and removed the EM interrupt disabling and enabling functions and got the same behavior.<br />
3&#46; The EM functions that write to flash do not have any interrupts enabled.&nbsp; In their flash manipulation functions I did not see any reference to using the systick.  
My plug-in also consistently reports that the &#8220;&#35; Waiting Rx&#8221;&nbsp; is 2 for the semaphore I am trying to block on after I write to flash.&nbsp; I am not sure how this fits in.&nbsp; It is as though the scheduler thinks there are two tasks waiting for this semaphore.&nbsp; &#40;There are not, only one task uses this particular semaphore.&#41;&nbsp;&nbsp;
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler problem writing to internal flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmp1104">cmp1104</a> on January 8, 2013</div><div class="thread-post-content">Ok, I think I found the issue though I do not understand why the problem occurred in first place.&nbsp; In my WriteToFlash function I start with INT&#95;Disable and then call after function to find an empty memory location in flash &#40;GetEmpty&#41;.&nbsp; Even though in GetEmpty I am just reading from flash I called Int&#95;Disable and Int&#95;Enable.&nbsp; When I return to my write function I call Int&#95;Enable just before exiting.&nbsp; If I remove the second use of Int&#95;Disable, Int&#95;Enable the code works as expected and the RTOS scheduler does not get &#8220;corrupted&#8221;.&nbsp;
