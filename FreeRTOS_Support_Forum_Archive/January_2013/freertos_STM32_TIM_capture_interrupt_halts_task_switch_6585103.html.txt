  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32 TIM capture interrupt halts task switch</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/guildernstern">guildernstern</a> on January 10, 2013</div><div class="thread-post-content">Hello all and thank you to whoever reads this.  
I&#8217;m experiencing a problem with FreeRTOS port for STM32, here&#8217;s the background:  
&#45; STM32F100RB on custom hardware<br />
&#45; Keil compiler<br />
&#45; FreeRTOS V 6.1.1<br />
&#45; Standard FreeRTOS provided demos execute correctly on hardware<br />
&#45; application uses start up code from startup&#95;stm32f10x&#95;md&#95;vl.s<br />
&#45; system task size is configured to 0x200 in startup&#95;stm32f10x&#95;md&#95;vl.s<br />
&#45; application uses heap&#95;1.c<br />
&#45; heap size is configured to 3 K bytes in FreeRTOSConfig.h<br />
&#45; application has 4 tasks:<br />
&nbsp; Task&#95;A, priority 3, 64 bytes stack<br />
&nbsp; Task&#95;d, priority 3, 32 bytes stack<br />
&nbsp; Task&#95;N, priority 2, 128 bytes stack<br />
&nbsp; Task&#95;T, priority 2, 64 bytes stack<br />
&#45; application has 4 interrupts:<br />
&nbsp; system tick &#40;FreeRTOS sys tick handler&#41;<br />
&nbsp; TIMER 2 &#40;same for both capture and overflow&#41;<br />
&nbsp; UART 1<br />
&nbsp; UART 2<br />
&#45; interrupt priorities:<br />
&nbsp; &#35;define configKERNEL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; 255<br />
&nbsp; &#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp; 191<br />
&nbsp; &#35;define configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY 15<br />
&#45; priority group:<br />
&nbsp; NVIC&#95;PriorityGroupConfig&#40;NVIC&#95;PriorityGroup&#95;4&#41;;<br />
&#45; all interrupts have been configured as:<br />
&nbsp; NVIC&#95;InitStructure.NVIC&#95;IRQChannelPreemptionPriority = configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY;<br />
&nbsp; NVIC&#95;InitStructure.NVIC&#95;IRQChannelSubPriority = 0;<br />
&#45; timer 2 is configured to trigger an interrupt on input capture events and counter overflows.<br />
&nbsp; timer 2 is used to measure duration of pulses on input signal<br />
&#45; UART 1 is used to communicate with a radiomodem @ 57600 bps<br />
&#45; UART 2 is used to communicate with a GPS @ 4800 bps<br />
&#45; I2C is used to read data from MEMS sensors &#40;no interrupt&#41;  
The problem:  
Task switch halts when the frequency of the input capture signal is high &#40;100 KHz ?&#41;.  
Findings:  
&#45; Hard fault handler is not called<br />
&#45; Enabling configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW to 1 or 2 doesn&#8217;t catch any stack overflow<br />
&#45; When halting the debugger, the code is always in the I2C routines.<br />
&nbsp; The code gets stuck in while &#40;&#33;I2C&#95;CheckEvent&#40;&#41;&#41;. This looks very similar to the problem mentioned here:<br />
&nbsp; <a href="http://www.freertos.org/FreeRTOS_Support_Forum_Archive/October_2012/freertos_FreeRTOS_task_is_not_running_though_Timer_ISR_6042937.html">http://www.freertos.org/FreeRTOS_Support_Forum_Archive/October_2012/freertos_FreeRTOS_task_is_not_running_though_Timer_ISR_6042937.html</a><br />
&nbsp; The I2C routines have been tested without FreeRTOS and work well.<br />
&#45; The system tick interrupt keeps working, xPortSysTickHandler is called.<br />
&#45; The running task is always the same, i.e. Task&#95;A.<br />
&#45; The input capture interrupt does not nest.<br />
&nbsp; This was tested with a global variable increased / decreased at every interrupt entry / exit.<br />
&#45; Nothing changes clearing the interrupt flags at the beginning or at the end of the interrupt routine.<br />
&#45; Nothing changes adding some instructions to read the interrupt register before extiting interrupt<br />
&nbsp; &#40;suspected issue with pipeline races exiting the interrupt&#41;.  
Question:  
Anybody has an idea what I could try ?  
Thank you.  
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 TIM capture interrupt halts task switch</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 13, 2013</div><div class="thread-post-content">Thanks for providing such good information.&nbsp; My apologies for not replying earlier, this one somehow passed me by.  
From your information I understand that your application is executing correctly until the frequency of the input capture interrupt increases to somewhere around 100 KHz.  
Can you provide more information what the capture interrupt is doing?&nbsp; You say it measures the width of pulses, is that quick to do or does it require a long calculate?&nbsp; What does it do with the measurement once it has calculated it?&nbsp; Does it use any FreeRTOS API functions?   
Do you have any way of measuring how much CPU time is taken servicing the interrupt?  
When you stop the debugger and find the I2C code is running, is it always the same line that is executing &#40;is is stuck in a polling loop, or is it apparently running normally&#41;?  
Regards.
