</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on December 1, 2005</div><div class="thread-post-content">Although I&#8217;m the one who asked the question, I think I can see the answer now &#40;I still lack some understanding of the task management queues&#41;
Looking in queue.c, if I used only one &quot;xTaskWoken&quot; variable for both Tx and Rx in the same ISR, it could mess things up.
For example, first I call &#96;xTaskWoken = xQueueSendFromISR&#40;xRxedChars, &amp;ucByte, pdFALSE&#41;&#96; which would still work as expected. It sets xTaskWoken and wake a task waiting to receive from that queue.
Next I call &#96;xQueueReceiveFromISR&#40; xCharsForTx, &amp;ucByte, &amp;xTaskWoken &#41;&#96;. I looks like in there it wakes the next task that is waiting to send to this queue if it was full. That task would never be wake on this event because I passed in pdTRUE after waking the task from the irrelevant queue.
So I do need to keep track of Tx and Rx in separate flags. Let me know if I missed something, though.
</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 2, 2005</div><div class="thread-post-content">This is exactly correct.
The xQueueReceiveFromISR&#40;&#41; mechanism is such to ensure only one task is woken by the ISR.&nbsp; If xTaskWoken is initially passed in as false and a task is woken it gets automatically set to true.&nbsp; The next call &#40;if there is one within the same interrupt which is possible in some drivers&#41; it is passed in as true, preventing any other tasks being woken.
Using just a single variables means it could be incorrectly set to true on the first call.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 2, 2005</div><div class="thread-post-content">Because there can be two events in one ISR &#40;i.e. Rx and Tx at the same time&#41;, then what happens when two tasks of the same priority were waiting, one for Tx and another for Rx? Which one will start first?
</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 2, 2005</div><div class="thread-post-content">As tasks are unblocked they are placed at the back of the queue of tasks that are ready to run at that priority.&nbsp; Therefore they will execute in the order they were unblocked.&nbsp; If you want one to be guaranteed to execute first then it requires a higher priority.
</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on December 2, 2005</div><div class="thread-post-content">I hope that&#8217;s correct, that the first one woken is the first one to executed.
In practice however, adding tasks is not working that way. When I add multiple tasks of the same priority, the &#42;last&#42; one added of highest priority runs first because pxCurrentTCB points to it when the scheduler starts. Is that intended?
</div></div><div class="thread-post"><h3 class="thread-post-title">TaskWoken flag in xQueueReceiveFromISR()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 2, 2005</div><div class="thread-post-content">Before starting the scheduler it is another matter.&nbsp; The lines:
if&#40; pxCurrentTCB-&gt;uxPriority &lt;= uxPriority &#41;
&#123;
&#95;&#95;&#95;&#95;pxCurrentTCB = &#40; volatile tskTCB &#42; volatile &#41; pxNewTCB;&nbsp;&nbsp;&nbsp; 
&#125;
mean that prior to the scheduler being started &#8211; if a task has a priority greater than OR EQUAL to the currently highest priority task, then it will be the &#8216;current&#8217; task when the scheduler is started.
Therefore if your highest priority is 3 &#8211; and you create two tasks of priority 3 &#8211; the task created second will be the task to execute first.
