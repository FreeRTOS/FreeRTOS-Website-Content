</div></div><div class="thread-post"><h3 class="thread-post-title">Task Suspend &#038; Resume</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 9, 2013</div><div class="thread-post-content"><blockquote>
  FreeRTOS plugin shows both tasks as suspended.
</blockquote>
Be careful how you interpret what the plug-in is telling you.&nbsp; The plug-in cannot tell the difference between a task that is actually suspended &#40;in the Suspended state&#41; and a task that is in the Blocked state with an infinite timeout.&nbsp; Therefore if you call a blocking function such as xQueueReceive&#40;&#41; and give it a block time of portMAX&#95;DELAY then, if INCLUDE&#95;vTaskSuspend is set to 1 in FreeRTOSConfig.h &#40;which it must be in your case&#41;, the plug-in will show the task as being in the Suspended state.  
It is almost certain that the task is actually in the Blocked state, not the Suspended state.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Task Suspend &#038; Resume</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 9, 2013</div><div class="thread-post-content">I&#8217;m not sure why you would be allocating a packet in one task for use by another task &#8211; but assume if I saw all your code rather than this snippet it would be more obvious.&nbsp; Also personally I would always try and avoid repeatedly allocating and freeing memory blocks in this way &#8211; although heap&#95;4.c would normally make this ok.  
There is no suspend with timeout function.&nbsp; For that you would need to use a delay, not a suspend, but then there is no way of another task &#8216;undelaying&#8217; as per your unsuspending &#40;resuming&#41;.&nbsp; You could probably make the functionality by having the task block on a semaphore with a delay &#8211; then the other task can &#8220;give&#8221; the semaphore to unblock the task if the delay has not expired.  
Task suspend and resume are not features I use very often myself.&nbsp; They can be dangerous to use as a synchronisation method because if a task tries to a resume another task that has not yet got to the point of suspending itself then the resume has no effect &#40;and is not latches, as it would be if a semaphore were used instead&#41;.  
Regards.
