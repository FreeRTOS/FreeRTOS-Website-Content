  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Pre-emptive mode starves task of exec time</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tomwbarclay">tomwbarclay</a> on May 24, 2013</div><div class="thread-post-content">Hi,<br />
I am using FreeRTOS 7.3.0 on an Atmel SAM4 chip using the ASF library.&nbsp; I have a task that executes 4 calls in sequence then blocks. Each one is an interrupt driven state machine that issues an event from the ISR at the end. Each call waits for such an event before exiting. Each call invokes some SPI traffic which I can monitor on an external logic analyzer. What I observe is  
Set the tick rate to 1ms and I see approx 1ms gaps between the calls.<br />
Set the tick rate to 5ms and I see approx 5ms gaps between the calls.   
Set the config&#95;USEPREEMPTIVE to 0  
And I see very small gaps between the calls.  
Clearly when &#8216;preemtive&#8217;, the RTOS is going off to do something else during these gaps.  
In my code all tasks block, either on input Qs or output Q&#8217;s or wait for events. The entire design is asynchronous<br />
and event driven.<br />
In my test setup I have no regular activity other than an LED flasher running at 100ms period.<br />
I start the test activity by a keypress.  
I had presumed that at the RTOS tick the kernel would go around the other tasks, find they were all blocked<br />
and come back pretty sharpish to continue executing the test task … but it appears not.  
Anyone have any ideas ??? …before I get down and dirty and start putting debug code into FreeRTOS itself.  
Any help appreciated.

Please post a little outline of the tasks, with a description of the behaviour you are seeing, and I may be able to explain why you are seeing that behaviour.

</div></div><div class="thread-post"><h3 class="thread-post-title">Pre-emptive mode starves task of exec time</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tomwbarclay">tomwbarclay</a> on May 25, 2013</div><div class="thread-post-content">OK…hope it all makes more sense after reading this….  
I have 14 tasks. Each task has the pattern  
task start<br />
forever loop<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; wait on event or message<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; do something<br />
loop end<br />
task end  
One of the tasks waits on a 200ms timer expiring &#40;using vTaskDelay&#41; which flashes an LED. All the other tasks block indefinitely.  
In my test task, the do something part,&nbsp; there are 4 methods executing sequentially, call them A,B,C,D  
Each method starts a sequence of SPI transactions that happens purely in the interrupt domain and then&nbsp; waits for the final interrupt to issue a xSemaphoreGiveFromISR. The sequence of actions in the interrupt domain is a state machine,<br />
each interrupt setting up the next SPI transfer and next state. The interrupts occur when an SPI transfer completes. The<br />
important point &#40;I think&#41; as its at the end of the interrupt sequence when an RTOS call is made.  
So basically once the test task runs it executes as<br />
&nbsp; methodA entry<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; start SPI transactions&nbsp; &#8212;-&gt; SPI transfers in sequence of&nbsp; interrupts &#8211;&gt; send event from ISR<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; wait for event from ISR<br />
methodA end  
methodB entry<br />
&nbsp;&nbsp;&nbsp; ditto.<br />
etc etc etc  
On the logic analyzer I observe the bursts of&nbsp; SPI data transfer &#40;shown below&#41;   
….&#33;&#33;&#33;&#33;&#33;……………………..&#33;&#33;&#33;&#33;&#33; ………………….&#33;&#33;&#33;&#33;………………………..&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;&#33;…….  
as each method executes.  
The odd thing is that the gap between the bursts correlates &#40;roughly&#41;&nbsp; to the tick period. There is virtually no gap when I switch of the pre-emptive mode of RTOS operation.   
Hope this helps … Tom
</div></div><div class="thread-post"><h3 class="thread-post-title">Pre-emptive mode starves task of exec time</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on May 25, 2013</div><div class="thread-post-content">Seems clear. Are you context switching in the interrupt using portEND&#95;SWITCHING&#95;ISR or portYILD&#95;FROM&#95;ISR &#40;depending on the port&#41; when the event is sent to the task? If not then the switch will only happen on the next tick and the next task wont initiate its SPI transfer until that time.

Just out of interest, in FreeRTOS 7.3.0 the &#8216;higher&#95;prio&#95;task&#95;woken&#8217; can be set to NULL.  
What would be the impact ?  
… Tom
