  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/smith84">smith84</a> on May 3, 2013</div><div class="thread-post-content">Hi everyone,  
I have a system which is running fine with 2 tasks and 2 timers with FreeRTOS 7.4.0 on a Cortex-M3 &#40;Energy Micro EFM32LG232&#41;. Compiler is GNU Tools ARM Embedded 4.7 2012q4. Tickless idle has been enabled and is implemented using the on-chip RTC.  
I have added new module which uses another timer, and now the system is beginning to Hard Fault straight away from OS start.  
I have commented out as much code as I can, but it appears to be the call to xTimerCreate &#40;which happens before OS Startup&#41; which makes all the difference. Even if the timer is never started, the micro will hit a hard fault after the OS is started. Commenting out the new call to xTimerCreate stops the hard fault from occurring.  
The HardFault handler from <a href="http://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html">http://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html</a> has been copied in.  
When the hard fault occurs,<br />
&#45; The &#8220;Tmr Svc&#8221; task is running &#40;according to the Task Table in Eclipse&#41;<br />
&#45; HFSR.FORCED = 1 &#40;all other bits 0&#41;<br />
&#45; CFSR.INVSTATE = 1 &#40;all other bits 0&#41;<br />
&#45; The stacks do not appear to have overflowed as there is plenty of space filled with the poison value.<br />
&#45; pulFaultStackAddress = 0x20007fc0<br />
&#45; stacked&#95;r0 = 0<br />
&#45; stacked&#95;r1 = 0<br />
&#45; stacked&#95;r2 = 0x10000000<br />
&#45; stacked&#95;r3 = 0xE000ED04<br />
&#45; stacked&#95;r12 = 0xA5A5A5A5<br />
&#45; stacked&#95;lr = 0xFFFFFFFD<br />
&#45; stacked&#95;pc = 0xbe00 &#40;no instructions here, it is all 0xFF&#41;<br />
&#45; stacked&#95;psr = 0x6000000E &#40;PendSV ISR active?&#41;  
I have analysed the memory contents before and after the call to xTimerCreate and nothing there appears to be writing anything where it shouldn&#8217;t.  
Not sure what is going on here. Funny thing is that the error that causes the hard fault looks like it is coming from the SVC Handler ISR.  
I hope that someone else here who has used the CM3 with Timers on FreeRTOS can make some suggestions. Many thanks&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 3, 2013</div><div class="thread-post-content">You say the code was running fine, and that this problem started when you added more modules.&nbsp; Could it be that the added modules have exhausted your FreeRTOS heap, and that something you have attempted to create has not been created resulting in a null pointer reference.  
If that is a possibility then you can check the return value of each API call used to create a task, queue, timer, semaphore or mutex to trap any allocation failures &#8211; but as a more blunt but simple method you can define a Malloc failed hook to see if the hook function ever gets called &#40;set configUSE&#95;MALLOC&#95;FAILED&#95;HOOK to 1 in FreeRTOSConfig.h, then define a function with prototype 
<pre><code>void vApplicationMallocFailedHook( void )
</code></pre>
&#45; put a break point in the function and see if it ever gets called.  
If the error come from within the tickless implementation then I&#8217;m afraid I can&#8217;t help as you provided that yourself, but there are two example implementations in the V7.4.1 download that you can use as a template &#40;and presumably have already used as a template&#41;.&nbsp; Note there was an error in the SAM4L and RX100 tickless code in the line:  
<pre><code>    ulAlarmValue = ( ulAlarmValueForOneTick * ( xExpectedIdleTime - 1UL ) );
</code></pre>
which should have been simply:  
<pre><code>    ulAlarmValue = ulAlarmValueForOneTick * xExpectedIdleTime;
</code></pre>
Otherwise the partially complete tick period is compensated for twice.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/smith84">smith84</a> on May 3, 2013</div><div class="thread-post-content">The malloc failure hook is currently implemented with an endless loop. I am therefore quite sure that lack of heap is not the issue. Oddly I have been able to call xTimerCreate in another place before OS start and it seems to be fine &#40;probably should have mentioned that&#33;&#41;  
I probably should try disabling tickless idle to see if that makes a difference. I will do that after the Bank Holiday and post results. You are correct that the tickless idle functionality is custom, but it was done based on the documentation &#40;before 7.4.1 was released&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 7, 2013</div><div class="thread-post-content">Ok &#8211; it is good that the tickless idle implementation has been eliminated as a cause.&nbsp; From your original post it appears that the new module you added is key, either because there is something in the implementation of the module itself that is causing some kind of corruption, or because the act of adding the code into your build is shifting code in flash or ram around, and that is highlighting a problem.  
Are you 100% sure your linker script is correct for the device being programmed.  
Before delving into the new module, have you checked that removing the new module again gets you back to a working state.  
How big is the new module?&nbsp; Are you able to post its code here?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/smith84">smith84</a> on May 7, 2013</div><div class="thread-post-content">I have just double-checked the linker script and all appears well, certainly the memory sizes are correct. &#40;I have used the unmodified EFM32LGxxx series linker file from Energy Micro.&#41;  
I am now not certain that all is well when the new timer call is not included after doing some more detailed analysis. At this stage I have commented out the offending module&#8217;s Init function so there may be a memory size influence, but there should certainly be no new code running.  
I have done some step-by-step debugging to try and understand what is going on during the OS startup through the prvPortStartFirstTask and vPortSVCHandler calls, and would like to ask the following &#40;possibly silly&#41; question:<br />
Should the port.c code initialise the priority of the SVCall Exception? I see that it sets the priority of the PendSV and SysTick &#40;though it probably shouldn&#8217;t do SysTick if tickless idle is active&#41;, but could not see anything for SVCall and so its priority remains at 0 &#40;highest&#41;. Although I guess if my reading is correct it is only used to set up the first task and so would probably not make a difference.
</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex M3 Hard Faults &#8211; xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 7, 2013</div><div class="thread-post-content">In that port SVC is only used to start the scheduler, so its priority does not matter.
