  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Suspended sheduler (vTaskSuspendAll), usage</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on September 2, 2012</div><div class="thread-post-content">Quote from API reference: 
<blockquote>
  API functions that have the potential to cause a context switch &#40;for example, vTaskDelayUntil&#40;&#41;, xQueueSend&#40;&#41;, etc.&#41; must not be called while the scheduler is suspended.
</blockquote>
Is it strictly prohibited or just warning that most of them will cause unexpected behavior &#40;task will block itself&#41;. I examined freertos sources and it seems to me that it is allowed, but I&#8217;m not sure… Is it allowed to perform non-blocking freertos calls &#40;such as xSemaphoreGive&#40;&#41;&#41; while sheduler is suspended ?
</div></div><div class="thread-post"><h3 class="thread-post-title">Suspended sheduler (vTaskSuspendAll), usage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 2, 2012</div><div class="thread-post-content">It is a blanket statement, made because to analyse each API function in turn and determine exactly when it is ok and when it is not, and then document that for end users, would be unworkable and confusing.&nbsp; However, any call that attempts to place the calling task into the blocked state must definitely not be used.&nbsp; This is because if the logic says the task should be in the Blocked state, but because the scheduler is suspended it doesn&#8217;t transition to the Blocked state, the whole application logic will be broken &#40;if a task blocks to wait for something on a queue, but returns before either that something has arrived or a timeout has expired, then the application cannot work correctly&#41;.  
<blockquote>
  Is it allowed to perform non-blocking freertos calls
</blockquote>
In some cases, probably, given the caveat above.  
<blockquote>
  such as xSemaphoreGive&#40;&#41;&#41;
</blockquote>
In that specific case, if giving the semaphore should cause a context switch, then you will end up with the wrong task running until such time that the scheduler is unsuspected.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Suspended sheduler (vTaskSuspendAll), usage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on September 2, 2012</div><div class="thread-post-content">I don&#8217;t understand clearly what you mean under &#8220;wrong tasking&#8221;. If it doesn&#8217;t break kernel logic &#40;state machine ?&#41; and just influences application-level logic then it&#8217;s ok. Because it is only application developer who decides whether application logic correct or not, taking into account all tasks, their states and synchronization between them. If he suspends sheduler then he must understand consequences.<br />
To be more specific, I&#8217;m just searching alternative critical region implementation for use by user-mode tasks in FreeRTOS-MPU. Just before deciding to use global mutex it showed to me that suspending sheduler would be faster implementation &#40;correct me if I wrong&#41;. I&#8217;m aware of that both implementations will not be protected against interrupts, it&#8217;s ok for my case.
</div></div><div class="thread-post"><h3 class="thread-post-title">Suspended sheduler (vTaskSuspendAll), usage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 2, 2012</div><div class="thread-post-content">If you attempt to block when the scheduler is suspended, then the &#40;implied&#41; state machine will break, and your application cannot determine what is going on.  
For example, if you call xSemaphoreTake&#40;&#41; with a block time on a semaphore that is not available, and the scheduler is suspended, then calling task will be placed into the Blocked state &#40;internally within the scheduler&#41;, but the task will carry on running until the scheduler is resume.&nbsp; That means it will leave the xSemaphoreTake&#40;&#41; function, and the calling task has no idea if it obtained the semaphore or not.&nbsp; Worse, when the scheduler is unsuspended, the task will immediately enter the Blocked state to wait for the semaphore, but it is not even in the xSemaphoreTake&#40;&#41; function any more &#8211; so when the semaphore is given and the task unblocked it will just carry on from where ever it happened to be when the scheduler was unsuspended and the semaphore will remain available.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Suspended sheduler (vTaskSuspendAll), usage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on September 3, 2012</div><div class="thread-post-content">I understand it clearly. Of course, it will be stupid trying to waiting for receive something with a single task running while knowing that nobody will be able to send. &#40;However… it makes good sense when waiting from ISR… But given your warning that it&#8217;s not intended for such usage, this case could solved by just using global variable being polled from single running task not caring about processor time.&#41;  
Anyway, I&#8217;ve just wanted to make sure. Thanks for explanation, Richard.  
P.S. I just got that there are same restrictions as ones exist for critical region, even more relaxed &#40;maybe&#41;. So suspending will be correct method for my purposes.
