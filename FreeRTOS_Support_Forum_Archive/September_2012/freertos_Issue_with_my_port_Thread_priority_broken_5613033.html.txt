</div></div><div class="thread-post"><h3 class="thread-post-title">Issue with my port? Thread priority broken?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 3, 2012</div><div class="thread-post-content">One idea having looked at your code.  
Currently the implementation does not expect mutexes to be given from an interrupt, and there is a potential issue with doing this.&nbsp; As you are not the first person I have noted using mutexes in this way &#40;in fact, I do to, but know what to watch for&#41;, I will ensure future versions allow for this usage scenario too.  
This is perhaps a long shot, as the symptom you describe is not really what I would expect, but it is possible that giving a mutex in an interrupt while the queue is locked, and immediately before the task trying to take the mutex updates the mutex holder variable, that the mutex holder variable can be null.&nbsp; .  
To allow interrupts to use mutexes in this way you would have to make a small change in tasks.c.&nbsp; Currently you will see a function:  
<pre><code>    void vTaskPriorityInherit( xTaskHandle * const pxMutexHolder )
    {
    tskTCB * const pxTCB = ( tskTCB * ) pxMutexHolder;
        configASSERT( pxMutexHolder );
        if( pxTCB-&gt;uxPriority &lt; pxCurrentTCB-&gt;uxPriority )
        {
            /* Adjust the mutex holder state to account for its new priority. */
            listSET_LIST_ITEM_VALUE( &amp;( pxTCB-&gt;xEventListItem ), configMAX_PRIORITIES - ( portTickType ) pxCurrentTCB-&gt;uxPriority );
            /* If the task being modified is in the ready state it will need to
            be moved in to a new list. */
            if( listIS_CONTAINED_WITHIN( &amp;( pxReadyTasksLists[ pxTCB-&gt;uxPriority ] ), &amp;( pxTCB-&gt;xGenericListItem ) ) != pdFALSE )
            {
                vListRemove( &amp;( pxTCB-&gt;xGenericListItem ) );
                /* Inherit the priority before being moved into the new list. */
                pxTCB-&gt;uxPriority = pxCurrentTCB-&gt;uxPriority;
                prvAddTaskToReadyQueue( pxTCB );
            }
            else
            {
                /* Just inherit the priority. */
                pxTCB-&gt;uxPriority = pxCurrentTCB-&gt;uxPriority;
            }
            traceTASK_PRIORITY_INHERIT( pxTCB, pxCurrentTCB-&gt;uxPriority );
        }
    }
</code></pre>
That can be changed to:  
<pre><code>    void vTaskPriorityInherit( xTaskHandle * const pxMutexHolder )
    {
    tskTCB * const pxTCB = ( tskTCB * ) pxMutexHolder;
        /* If the mutex was given back by an interrupt while the queue was
        locked then the mutex holder might now be NULL. */
        if( pxMutexHolder != NULL )  // &lt;&lt;&lt;&lt;&lt;&lt;&lt;&lt;&lt;&lt;&lt;&lt; ADDED if() statement
        {
            if( pxTCB-&gt;uxPriority &lt; pxCurrentTCB-&gt;uxPriority )
            {
                /* Adjust the mutex holder state to account for its new priority. */
                listSET_LIST_ITEM_VALUE( &amp;( pxTCB-&gt;xEventListItem ), configMAX_PRIORITIES - ( portTickType ) pxCurrentTCB-&gt;uxPriority );
                /* If the task being modified is in the ready state it will need to
                be moved in to a new list. */
                if( listIS_CONTAINED_WITHIN( &amp;( pxReadyTasksLists[ pxTCB-&gt;uxPriority ] ), &amp;( pxTCB-&gt;xGenericListItem ) ) != pdFALSE )
                {
                    vListRemove( &amp;( pxTCB-&gt;xGenericListItem ) );
                    /* Inherit the priority before being moved into the new list. */
                    pxTCB-&gt;uxPriority = pxCurrentTCB-&gt;uxPriority;
                    prvAddTaskToReadyQueue( pxTCB );
                }
                else
                {
                    /* Just inherit the priority. */
                    pxTCB-&gt;uxPriority = pxCurrentTCB-&gt;uxPriority;
                }
                traceTASK_PRIORITY_INHERIT( pxTCB, pxCurrentTCB-&gt;uxPriority );
            }
        }
    }
</code></pre>
Alternatively, and breaking the FreeRTOS coding standard, you could just add:  
<pre><code>if( pxMutexHolder == NULL ) return;
</code></pre>
to the top of the function.

</div></div><div class="thread-post"><h3 class="thread-post-title">Issue with my port? Thread priority broken?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 11, 2012</div><div class="thread-post-content">One point, as Richard alludes to, is that Mutexes, unlike Semaphores, are meant to be taken by a tasks, and then later given BY THE SAME TASK to release it. Then another task can take the Mutex. By definition, an ISR isn&#8217;t part of a task, so can not give a mutex. This &#8220;ownership&#8221; of the mutex is one part of the reason that it can due priority inheritance to avoid priority inversion. In contrast, a Semaphore isn&#8217;t &#8220;owned&#8221; by anyone&nbsp; and can naturally be set and cleared by different entities.  
In your case, you are guarding a mailbox holding a message pointer and character count, but once a task gets the mailbox, and starts up the message, it does&#8217;t really act like it &#8220;owns&#8221; that mailbox, the mailbox is just busy. This sounds more like a semaphore, not a mutex. In fact, if the same task comes around and tries to send a second message before the first is done, if the mutex was defined as recursive, it would still be the owner of it, and proceed on and effectively abort the previous message. If the mutex isn&#8217;t recursive, then the code will check if the task should be bumped up in priority by inheriting from itself???  
As I said, this is much more a semaphore activity, since once you start the action, the task no longer really has any control over it. One way that a mutex might make sense is that when a task want to start sending a message, it grabs the mutex for that channel, and within this mutex protected region, it might make multiple calls to send pieces of the message, and at the end gie the mutex so another task can send a message, This allows you to keep the message &#8220;atomic&#8221; even though it isn&#8217;t all sent with one call. This mutex arbitrates task to task relationships. The actually sending of each block, might use a semaphore to let the task know that it is ok to start another piece of the message.
