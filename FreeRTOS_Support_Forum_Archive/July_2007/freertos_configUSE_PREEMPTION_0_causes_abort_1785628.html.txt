Why would using configUSE&#95;PREEMPTION &#35;defined as 0 cause a prefetch abort even before FreeRTOS&#8217;s scheduler is started &#40;which means that FreeRTOS isn&#8217;t even actively being used&#41;? I get a prefetch abort even when setting something simple like a global variable to an integer &#40;like 0&#41;. However, if I &#35;define configUSE&#95;PREEMPTION as 1 then FreeRTOS runs okay.
Any ideas?
Darrik
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on July 24, 2007</div><div class="thread-post-content">Very odd.&nbsp; Is it possible that in interrupt that makes use of a FreeRTOS API function is being executed prior to the scheduler being started?
Dave.
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dspaude">dspaude</a> on July 24, 2007</div><div class="thread-post-content">I would think that if this were true then the preempted version would have the same problem. Have any of the FreeRTOS examples been tried in cooperative mode?
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 25, 2007</div><div class="thread-post-content">&gt;Have any of the FreeRTOS examples been tried in cooperative mode? 
Yes definitely, although I may occasionally forget to re-test the cooperative version when making changes.&nbsp; Some of the examples may result in errors being reported when run in cooperative mode &#40;i.e. the &#8216;check&#8217; task reporting that one particular test task has not executed as expected&#41; but not a crash.
Which port are you using?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dspaude">dspaude</a> on July 25, 2007</div><div class="thread-post-content">I am using the GCC SAM7S port as the base, but of course with many changes for my application. I may try a debugger to see if there is something else that happens that I am not seeing, but the last time I used the debugger it literally indicated that the failure was on a variable assignment before the OS even started &#40;and no interrupts should have happened before that point in the code&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dspaude">dspaude</a> on July 26, 2007</div><div class="thread-post-content">The main difference I see in the FreeRTOS code between configUSE&#95;PREEMPTION == 0 and configUSE&#95;PREEMPTION == 1 is that configUSE&#95;PREEMPTION == 0 uses attribute &quot;IRQ&quot; for the tick handler while configUSE&#95;PREEMPTION == 1 uses attribute &quot;naked&quot;. I recall seeing some note that attribute &quot;IRQ&quot; for GCC didn&#8217;t work very well &#40;for some &quot;current version of GCC&quot;&#8211;whatever version that was&#41;. Could this be related?
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on July 26, 2007</div><div class="thread-post-content">If you are using a V4.n.n version of GCC and you are compiling it to ARM mode &#40;as its an IRQ&#41; you should be ok, but you could try writing your own entry code to be sure.&nbsp; To do this you would simply have to declare the function naked and call the save/restore context macros as per the preemptive example.&nbsp; This would be somewhat wasteful in a real application but would make a good test.
I think I recall you saying the crash happened before the scheduler was started though?&nbsp; Which demo are you basing your test on?
</div></div><div class="thread-post"><h3 class="thread-post-title">configUSE_PREEMPTION == 0 causes abort</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dspaude">dspaude</a> on September 27, 2007</div><div class="thread-post-content">I finally got back to trying to resolve this problem. I modified the vNonPreemptiveTick&#40;&#41; function prototype in portISR.c to use the &quot;naked&quot; attribute instead of &quot;IRQ&quot; and that allowed the code to power up. There are other issues related to this change, but at least it powered up. Before this change it would just crash when switching to any task except the IDLE task. However, if the IDLE task is the only one, then the system still crashes. Again, this is based on the SAM7S port and using GCC 4.2.1 &#40;YAGARTO&#41;.
