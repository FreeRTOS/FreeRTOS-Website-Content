  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leesp">leesp</a> on August 28, 2018</div><div class="thread-post-content">Hi,
Can someone explain to me in a simple manner, what does it mean by &#8220;FreeRTOS message queue are thread safe&#8221;? And how to use message queue for mutual exclusion to shared resources?
I know that message queue can be used by Task1, or ISR to send information to Task2, signalling Task2 that an event has happened. But use in thread safe, mutual exclusion, I am not sure
Thank you
</div></div><div class="thread-post"><h3 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 28, 2018</div><div class="thread-post-content"><blockquote>
  Can someone explain to me in a simple manner, what does it mean by 
  &#8220;FreeRTOS message queue are thread safe&#8221;?
</blockquote>
FreeRTOS allows your application to be organised as a set of independent 
threads of execution (tasks) &#8211; if something is thread safe then it means 
it can be used from more than one thread of execution as it is (without 
the application writer needing to do anything special).
<blockquote>
   And how to use message queue 
  for mutual exclusion to shared resources?
</blockquote>
While you could use a message queue for mutual exclusion of a resource, 
it would be better to use a mutex.  Rather than explain that here I 
recommend reading about them in the texts already available to you on 
the FreeRTOS.org website, and the relevant chapter in the FreeRTOS book 
https://www.freertos.org/Documentation/RTOS_book.html
</div></div><div class="thread-post"><h3 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 28, 2018</div><div class="thread-post-content">Queues are thread safe in that multiple  tasks can try to concurrently write to or read from a given queue, and the queue will handle the syncronization so that each message gets put in as a unique message and each message gets sent to a single task.
(This is as opposed to Stream Buffers and Message Buffers which require that only a single task attempt write to or read from at any given time)
This means that Task1 and Task2 and ISR1 and ISR2 can all send messages using the same queue to Task3 and Task4, and neither the senders of the receivers need to worry about conflicts in access (just that the queue might be full).
</div></div><div class="thread-post"><h3 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leesp">leesp</a> on August 29, 2018</div><div class="thread-post-content"><blockquote>
  This means that Task1 and Task2 and ISR1 and ISR2 can all send messages using the same queue to Task3 and Task4, and neither the senders of the receivers need to worry about conflicts in access (just that the queue might be full).
</blockquote>
Q1. Correct me if I am wrong: so sending msg to a queue is thread safe because, for example, Task1 sends Msg1, Task2 sends Msg2. While interleaving may happen (which means while Task1 is sending, it might be interrupted or pre-empted by Task2, who is sending to the same queue), data integrity would be guaranteed (which means Msg1, Msg2 would not be corrupted). Because of this, queue is thread-safe
Q2. Reading from a queue would not post a concurrency or data corruption problem, right?
<blockquote>
   and each message gets sent to a single task.
</blockquote>
Q3. How to ensure Task3, not Task4, gets Msg1?
</div></div><div class="thread-post"><h3 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 29, 2018</div><div class="thread-post-content"><blockquote>
<pre><code>This means that Task1 and Task2 and ISR1 and ISR2 can all send
messages using the same queue to Task3 and Task4, and neither the
senders of the receivers need to worry about conflicts in access
(just that the queue might be full).
</code></pre>
</blockquote>
Yes &#8211; note the ISRs need to use the &#8216;FromISR&#8217; version of the queue APIs.
<blockquote>
<pre><code>1. Correct me if I am wrong: so sending msg to a queue is thread
safe because, for example, Task1 sends Msg1, Task2 sends Msg2. While
interleaving may happen (which means while Task1 is sending, it
might be interrupted or pre-empted by Task2, who is sending to the
same queue), data integrity would be guaranteed (which means Msg1,
Msg2 would not be corrupted). Because of this, queue is thread-safe
</code></pre>
</blockquote>
Yes.
<blockquote>
<pre><code>2. Reading from a queue would not post a concurrency or data
corruption problem, right?
</code></pre>
</blockquote>
Right.
<blockquote>
<pre><code>and each message gets sent to a single task.
3. How to ensure Task3, not Task4, gets Msg1?
</code></pre>
</blockquote>
A single queue can have multiple readers and multiple writers.  If more 
than one task is blocked on a queue waiting to receive when a message 
arrives then it is the highest priority task of the two that will 
receive it &#8211; or if the tasks have the same priority &#8211; it is the task 
that has been waiting the longest that will receive it.
This is in the book you know &#8211; please invest time in reading it so we 
don&#8217;t have to repeat writing stuff here.
</div></div><div class="thread-post"><h3 class="thread-post-title">Queues &#8211; thread safe? Mutual exclusion? </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on August 29, 2018</div><div class="thread-post-content">How to make sure the right Task gets a given message, basically you can&#8217;t. Normally having multiple readers on a queue is a way to implement a &#8216;Task Pool&#8217; to handle concurent requests (likely running the same code, just with different stacks). If you care, you should have a dedicated queue for each task (so that would be used if after starting a request, it needs to get more information to complete the request).
