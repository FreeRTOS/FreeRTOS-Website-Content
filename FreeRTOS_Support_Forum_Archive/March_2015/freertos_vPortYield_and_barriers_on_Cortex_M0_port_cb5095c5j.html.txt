</div></div><div class="thread-post"><h3 class="thread-post-title">vPortYield and barriers on Cortex M0 port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/evading">evading</a> on March 10, 2015</div><div class="thread-post-content">Yes, as I understand it (from this source for example http://www.ethernut.de/en/documents/arm-inline-asm.html) that is only for the asm instructions in that asm statement, without a memory barrier the setting of portNVIC<em>INT</em>CTRL could actually be moved (by the compiler) to after the asm instructions. Unless the compiler implicitly see the hardware barriers as a software barrier as well.
</div></div><div class="thread-post"><h3 class="thread-post-title">vPortYield and barriers on Cortex M0 port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/andymcc0">andymcc0</a> on March 10, 2015</div><div class="thread-post-content">No, that is <strong>not</strong> what the <code>volatile</code> storage class qualifier <em>explicitly</em> does.  It tells the compiler that it cannot assume that a previously read value of the <code>volatile</code> variable is still valid, and so it must be re-read, so the second or subsequent read in the code must <strong>not</strong> be optimised out.  An obvious example is when the variable is a hardware status register that is being polled for a bit to change state.  It does not guarantee that &#8216;out of order execution&#8217; will not occur.
The <code>dsb</code> and <code>dmb</code> ARM assembler instructions will guarantee that all memory accesses will happen before any subsequent memory accesses or instructions, respectively.  The <code>isb</code> instruction will guarantee that the subsequent instructions will be re-fetched, bypassing any pipeline.  None makes any guarantee about the order before or after.  The use of these instructions in relation to the <code>volatile</code> keyword is entirely compiler dependent, so if this is important for your application, you will have to include these instructions as required in your code.
I clearly (even painfully) remember having to scatter <code>EIEIO</code>* instructions all over some PowerPC code that was heavily interractive with hardware via a bus-bridge with a posted write capability.  I have had no such problems (yet) with ARM Cortex-M based processors, but I&#8217;ve only used M3/4.

So basically, unless the &#8220;dsb&#8221; and &#8220;isb&#8221; instructions imply a software barrier, the vPortYield code:
<pre><code>/* Set a PendSV to request a context switch. */                                                       
*( portNVIC_INT_CTRL ) = portNVIC_PENDSVSET;                                                          
/* Barriers are normally not required but do ensure the code is completely                            
within the specified behaviour for the architecture. */                                               
__asm volatile( "dsb" );                                                                                                     
__asm volatile( "isb" );   
</code></pre>
could potentially be rearanged by the optimizer to be equivalent to
<pre><code>/* Barriers are normally not required but do ensure the code is completely                            
within the specified behaviour for the architecture. */                                               
__asm volatile( "dsb" );                                                                              
__asm volatile( "isb" );
/* Set a PendSV to request a context switch. */                                                       
*( portNVIC_INT_CTRL ) = portNVIC_PENDSVSET;                                                          
</code></pre>
Or could it?
A barrier like:
    asm volatile(&#8220;&#8221;:::&#8221;memory&#8221;);
would guarantee it, but I don&#8217;t know enough about GCC to say for sure that it is needed.
