</div></div><div class="thread-post"><h3 class="thread-post-title">How to configure the Total Heap Size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 12, 2015</div><div class="thread-post-content">Hi Jean,
Which heap_x.c are you using?
You will find this declaration in versions 1, 2 and 4:
<pre><code>static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
</code></pre>
That is the heap space.
You can make this <code>configTOTAL_HEAP_SIZE</code> as big as you want, the linker will issue an error when you&#8217;re running out of RAM.
Another possibility is to use heap_5.c. Right after starting-up, and before the first call to pvPortMalloc(), you will have to call:
<pre><code>void vPortDefineHeapRegions( const HeapRegion_t * const pxHeapRegions );
</code></pre>
to add the heap regions. Depending on the compiler used, you can calculate the amount of RAM memory dynamically.
Note that, depending on the compiler you&#8217;re using, some standard functions may still call the the malloc/free couple.
Often I declare these functions, making sure that they have a C-linking (and not a C++ linking):
~~~~~
extern void non<em>existent</em>function( void );
void *malloc( size_t size )
{
    ( void ) size;
    non_existent_function();
    return NULL;
}
void free( void *pvMemory )
{
    ( void ) pvMemory;
    non_existent_function();
}
~~~~~
Now if I call e.g. gmtime(), there will be a linking error because <code>non_existent_function</code> could not be found.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">How to configure the Total Heap Size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 13, 2015</div><div class="thread-post-content">FreeRTOS itself uses very approximately 200 to 300 bytes.  Task stacks 
come from the heap.
You would have to ask your compiler where the rest of the RAM is going. 
  The easiest way of doing that it to look at the map file &#8211; it will 
tell you how much RAM each section is taking (.bss, .data, etc.) and 
what in those sections is using RAM.  That is a C question though, not a 
FreeRTOS question &#8211; the things that take up RAM in a non-RTOS 
application (static variables, statically allocated DMA or network 
buffers, etc.) will be the same things taking up RAM when you add 
FreeRTOS into the build.

</div></div><div class="thread-post"><h3 class="thread-post-title">How to configure the Total Heap Size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 13, 2015</div><div class="thread-post-content">Hello Jean,
<blockquote>
  I have another question: which use the rest of memory space?
  The rest of the memory should be 192000-(180*1024) = 7280 bytes.
  Is it freeRTOS?
</blockquote>
Yes partly. FreeRTOS has some static declarations.
The RAM is normally divided among these:
<ul>
<li>Static and global variables</li>
<li>Any code located in RAM</li>
<li>A heap to be accessed by the standard malloc()/free()</li>
<li>A stack which is used until the scheduler will start</li>
</ul>
In your project you will probably find a file describing the layout for the linker, e.g. &#8220;stm32F40.ld&#8221;.
It describes all memories and it tells were to put the stack and heap (if any).
The linker file defines symbols like e.g. &#8216;_ebss&#8217; which you can declare in your code:
<pre><code>extern char _ebss;
</code></pre>
The address of &#8216;<em>ebss&#8217; can be used within your code to dynamically determine how much free RAM is actually left. That would be useful if you use &#8220;heap</em>5.c&#8221;.
But the following is much simpler and it is also safe:
<pre><code>#define configTOTAL_HEAP_SIZE  ( 180 * 1024 )
</code></pre>
because the linker will fail when it doesn&#8217;t fit any more.
Regards, Hein
