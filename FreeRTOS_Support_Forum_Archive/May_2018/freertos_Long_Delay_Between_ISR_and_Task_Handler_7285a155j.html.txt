  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Long Delay Between ISR and Task Handler</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrobert">mrobert</a> on May 7, 2018</div><div class="thread-post-content">I am trying to handle an ISR in a task. To do so, I call vTaskNotifyGiveFromISR() to a task that is wait on ulTaskNotifyTake(). E.g. In the ISR,
~~~
            /* Notification variable for Task */
            BaseType_t xHigherPriorityTaskWoken = pdFALSE;
<pre><code>        /* Set the Task to Highest Priority */
        vTaskNotifyGiveFromISR( sLINTaskUART, &amp;xHigherPriorityTaskWoken);
        /* Force a scheduler call on exit */
        if( xHigherPriorityTaskWoken == pdTRUE )
        {
            portYIELD_FROM_ISR();
        }
</code></pre>
~~~
in the Task
~~~
    while(1)
    {
        /* Wait forever for Notification */
        notified = ulTaskNotifyTake( pdTRUE,0xFFFFFFFF );
<pre><code>    if( notified == 0 )
    {
        // We've been idle for a loooong time. Go back to waiting I guess...
        continue;
    }
    /* Task do stuff */
 }
</code></pre>
~~~
I did some timing measurements and I found that there is about a 6 millisecond delay from the ISR to the task executing. I thought this could either be
1.  Context switching just takes that long ( I don&#8217;t believe it does )
2.  I wasn&#8217;t switching into the task right away (The handler task is the highest priority).
However, when I increased my configTICK<em>RATE</em>HZ from 100Hz to 1kHz, the delay between the ISR went down dramatically&#8230;
I don&#8217;t understand. I have preemption enabled. Shouldn&#8217;t that mean that the task is entered immediately from the ISR in either case? If that&#8217;s true, then the Tick Rate shouldn&#8217;t impact the delay between the ISR and the task.
Can someone clarify for me? I&#8217;ve read &#8220;Mastering the FreeRTOS Real Time Kernel&#8221; but this behavior doesn&#8217;t seem to match the behavior there. 
I am on an ESP32 and using the ESP-IDF&#8217;s version of FreeRTOS, but that shouldn&#8217;t change this behavior.
</div></div><div class="thread-post"><h3 class="thread-post-title">Long Delay Between ISR and Task Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 8, 2018</div><div class="thread-post-content">It doesn&#8217;t look like you are doing anything from just from the code you 
posted.  However I&#8217;m not familiar with the port in use as it was not 
created by us.  Can you check how portYIELD<em>FROM</em>ISR() is implemented, 
and perhaps post its implementation here.
</div></div><div class="thread-post"><h3 class="thread-post-title">Long Delay Between ISR and Task Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 8, 2018</div><div class="thread-post-content"><blockquote>
  However, when I increased my configTICK<em>RATE</em>HZ from 100Hz to 1kHz,
  the delay between the ISR went down dramatically&#8230;
</blockquote>
It looks like <code>portYIELD_FROM_ISR()</code> isn&#8217;t doing what it should do. I guess that you see the same timings with or without this yield, don&#8217;t you?
I think that in your case, the task is only activated after the kernel has seen (from the clock-tick) that your task is runnable. That is not the usual path.
If your task has become the highest-priority-runnable-task, the task should become active without the intervention of the kernel or clock-tick.
<code>portYIELD_FROM_ISR()</code> will have <code>vTaskSwitchContext()</code> called in <code>_frxt_dispatch</code>, and it should cause an immediate task switch. May you can debug that function?
But as Richard said, the ESP port was not created by FreeRTOS. Neither I have much experience with the port or with the part.
</div></div><div class="thread-post"><h3 class="thread-post-title">Long Delay Between ISR and Task Handler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrobert">mrobert</a> on May 8, 2018</div><div class="thread-post-content">Richard and Hein,
Thank you for your replies. After reading your replies, I checked the port, and it looked correct; portYIELD<em>FROM</em>ISR looked like it was doing what it was suppsed to. I eventually decided that my code was correct as well. 
As with many problems, the solution was simple, and makes me look dumb. I checked our config settings and found that a flag was set that changed the behavior of portYIELD<em>FROM</em>ISR; It didn&#8217;t occur to me that my config was bad before. Once I corrected the flag, the transition from ISR to the task fell to 11 microseconds. Much Better! 
You guys did help, and I appreciate your quick replies. Sorry for wasting your time!
