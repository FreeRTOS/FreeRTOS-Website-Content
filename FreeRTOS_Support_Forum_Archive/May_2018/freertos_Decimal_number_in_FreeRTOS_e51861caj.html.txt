</div></div><div class="thread-post"><h3 class="thread-post-title">Decimal number in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 13, 2018</div><div class="thread-post-content"><blockquote>
  What kind of variable to represent decimal number?
</blockquote>
Isn&#8217;t this more like a general C question?
The simple answer would be that it should be big enough to hold the maximum value.
Also decide if the variable becomes signed or unsigned. Can it become negative? If it can, you <strong>must</strong> use a signed type. If it is always positive, you <strong>may</strong> still use a signed type, depending on the width needed.
You can decide to use a char, an short, an int or a long ( or the unsigned versions of these ).
Note that when you mix the usage of <code>char</code>s, <code>short</code>s and <code>int</code>s ( often seen in small embedded projects ), the compiler needs to insert lots of extra code to make things working.
Function parameters are often passed in single registers, there is no need to downscale the size of parameters to save memory:
~~~
    /* Calling the first function may result in more code
    than calling the second function: <em>/
    void foo(char count);
    /</em> Here &#8216;count&#8217; will get the width of a CPU register. */
    void foo(int count);
~~~
Also care must be taken when signed-ness is mixed: the outcome of the expression <code>if( value_1 &gt; value_2 )</code> depends on the the values and on the signed-ness of the two variables. You would ask for trouble if you compare signed with unsigned values.
In practice, the <strong>int</strong> type has many advantages: it normally has the size of a CPU register ( 16, 32, or 64 bits ), and therefore, code using ( unsigned ) <code>int</code> is very efficient. If all your variables can be stored in <code>int</code>s, you can keep your code really simple. The compiler won&#8217;t have to insert any (hidden) transformation of signed-ness or width.
Types with a known width:
~~~
<h1>include &lt;stdint.h></h1>
/* defining types width a known width: */
int8<em>t
int16</em>t
int32<em>t
uint8</em>t
uint16<em>t
uint32</em>t
~~~
Within the +TCP library, you will see an extensive usage of <code>uint32_t</code>, because that corresponds to the fields in the Internet packets.
And finally, consider using of <code>size_t</code> as often as applicable.

</div></div><div class="thread-post"><h3 class="thread-post-title">Decimal number in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 13, 2018</div><div class="thread-post-content">I think this is only a FreeRTOS question if the behaviour is different 
when performing the calculation before the scheduler has started (i.e. 
from main()) and after the scheduler has started.
I&#8217;ve never known there to be a difference with integer usage, but there 
can be a difference in floating point usage if either:
1) The FreeRTOS port you are using does not give each FreeRTOS task 
unless the application code explicitly requests one.  This is not the 
normal case though.
2) There is a stack alignment issue inside the FreeRTOS task.  That was 
once a problem with ARM ports, but fixed a very long time ago by 
increasing the stack alignment to 8 (which is what it should have been), 
and more recently on PIC32MZ ports, but that has been fixed too.

</div></div><div class="thread-post"><h3 class="thread-post-title">Decimal number in FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 13, 2018</div><div class="thread-post-content">This looks like a fundamental misunderstanding of C.
You have all sorts of extra spaces, but %d is a format that need to be given an int value (not a float),  to print a float value, you generally would use a %f format. Sending a float value to the %d format will give you strange numbers.
In C, when you divide and integer by another interger, the fractional part will be discarded, so the expression (valueLoad/1024)*1030 will give you possibe values of 0, 1030, 2060, 3090 and so on.
if you did instead valueLoad * 1030L ./ 1024  you will get closer to the value you expect (the L is added to the end of the number to make sure the multiplication doesn&#8217;t overlow the range of an int).
I would actually tend to use(valueLoad * 1030L + 512)/1024 to round the value if I knew that valueLoad was always positive.
