I&#8217;ve created an application with two firmware slots. Bootloader works fine, it properly starts firmware from particular slot based on sequencer number saved on FLASH. 
By default, firmware is compiled for the first slot, which starts from address 0x08008000 in memory. Second slot is mapped to address 0x08104000. 
When  my device starts firmware from the second slot, FreeRTOS in booting time starts its first task  from address located in the first slot and then entire application jumps to the first slot. I thought addresses in binaries after compilation are relative, but in that case it&#8217;s somehow hardcoded with an absolute value.
Running firmware from the first slot has nothing problems.
What should I change? Some FreeRTOS params in config? I don&#8217;t think so&#8230; 
</div></div><div class="thread-post"><h3 class="thread-post-title">Two firmware slots application, FreeRTOS jumps to the first slot while executing first task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on May 28, 2018</div><div class="thread-post-content">Assuming you&#8217;re using e.g. ARM-CM3 you maybe missed to adjust SCB->VTOR (vector table start address) accordingly i.e. pointing to the exception table linked into the actual app binary.
Starting the app binary from bootloader needs to be done right and is not related to FreeRTOS. 
In short I&#8217;m using this sequence in my bootloader:
<ul>
<li>disable all IRQs</li>
<li>get app(1 or 2) image vector table <code>pVec</code> starting at app image base address</li>
<li>set main stack pointer and activate (privileged) thread mode using main stack
~~~
__set<em>MSP( (uint32</em>t)pVec->pvStack );
__set_CONTROL( 0 );
__sync();
~~~</li>
<li>invoke pVec->pfnReset_Handler function of the app image to start the app</li>
<li>in (app image) <code>Reset_Handler()</code> after optional relocation of init data and clearing BSS adjust VTOR with the (new) app image exception table
<code>SCB-&gt;VTOR = (uint32_t)&amp;exception_table;</code>
<ul>
<li>branch to app main() after CRT init <code>__libc_init_array();</code></li>
</ul></li>
</ul>
Good luck, HS2
</div></div><div class="thread-post"><h3 class="thread-post-title">Two firmware slots application, FreeRTOS jumps to the first slot while executing first task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/vipperdev">vipperdev</a> on May 30, 2018</div><div class="thread-post-content">Hey, thanks for your reply. In this project ARM-CM4 is used.
So my flow during switching from bootloader to main application is as follows:
1. Check which firmware slot should be used.
2. Disable IRQs.
2. Copy vector table to RAM. That part of RAM is the same for both slots. During copying process I&#8217;m changing offset  for each address, so they will be compatible with particular firmware slot. By default addresses don&#8217;t have offset, it&#8217;s removed in post-compiling stage.
3. Set stack pointer, according to the first word in vector table in RAM. That addresses is not changed while copying vector table to RAM.
4. Set SCB->VTOR.
5. Execute Data Sync Barrier DSB().
6. Jump to the Reset Handler from vector table copied to RAM.
Vector table is copied with correct offset for each firmware slot.
When RTOS starts its first task in prvPortStartFirstTask, and then jumps to vPortSVCHandler it switches to the task in the first slot. It fail while returning from vPortSVCHandler called by that first dummy task.

</div></div><div class="thread-post"><h3 class="thread-post-title">Two firmware slots application, FreeRTOS jumps to the first slot while executing first task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 1, 2018</div><div class="thread-post-content">Fundammentally, programs generally need to run from the address they were compiled to run at, as there are some absolute address values in the code. One solution is to design the code to always copy itself into ram (at a fixed address) and run there, then just the &#8216;bootloader&#8217; that does the copy needs to understand the changing address.
On some processors, with some compilers, there is a flag to compile the code a &#8216;Position Independent&#8217;, and when this is done right, the program can be stored at any address and it will run there, GCC for ARM has a pic (Position Independant Code) option that I beleive can do this, but that question does bring up one of the issues that it sounds like you only want to relocate the &#8216;flash&#8217;  memory but keep ram references absolute.

</div></div><div class="thread-post"><h3 class="thread-post-title">Two firmware slots application, FreeRTOS jumps to the first slot while executing first task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 1, 2018</div><div class="thread-post-content">I beleive the topic you reference dealt with one issue with PIC, that by default is also relocates the ram references (It was originally developed to allow the code of a shared library be loaded at any address, and in this case you wanted to move the data section too. </div></div><div class="thread-post"><h3 class="thread-post-title">Two firmware slots application, FreeRTOS jumps to the first slot while executing first task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on June 2, 2018</div><div class="thread-post-content">As Richard mentioned PIC is for shared libs and requires dynamic linking, I think. I wouldn&#8217;t go this way. It&#8217;s way more complicated than it seems at the first place.
If  I got you right you want to implement a safe update of the application binary by keeping the previous image in place and and activate the new image once successfully installed.
Since you can&#8217;t run the complete app from RAM (after relocation) you&#8217;ve to run (parts) of the code from flash. This code can&#8217;t be relocated anyway.
So I&#8217;d prepare an update package containing 2 app binaries properly linked to their (flash) slots and deal with updating the &#8216;next free&#8217; slot by the update protocol. The currently running app knows it&#8217;s slot and also the bootloader. So regardless which program actually does the update both are able to select the &#8216;next free&#8217; slot and tell it to the update tool, which in turn sends the selected app binary 1 or 2  to the device.
I&#8217;m just guessing that you want to update a device via an external interface using an update tool.
