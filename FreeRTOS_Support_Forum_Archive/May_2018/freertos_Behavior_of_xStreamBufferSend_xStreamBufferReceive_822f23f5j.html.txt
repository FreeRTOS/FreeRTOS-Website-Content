</div></div><div class="thread-post"><h3 class="thread-post-title">Behavior of xStreamBufferSend / xStreamBufferReceive</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hubpav">hubpav</a> on May 20, 2018</div><div class="thread-post-content">Hi Richard, thank you!
Apparently <strong>xStreamBufferSend</strong> handles that for you inside the <strong>do { } while</strong> loop, so no wrapper is necessary there.
With <strong>xStreamBufferReceive</strong>, the situation is different though&#8230; the call can return without having the desired length available under normal circumstances (as task can get notified from various reasons) &#8211; even if <strong>portMAX_DELAY</strong> has been specified. 
This is the wrapper (with timeout support) I have been using for reference (feedback is welcome):
&#8220;`c
size<em>t os</em>stream<em>timed</em>read(os<em>stream</em>t *stream, void *buffer, size_t length, uint32_t milliseconds)
{
    if (milliseconds == 0)
    {
        return xStreamBufferReceive(stream->_handle, buffer, length, 0);
    }
<pre><code>size_t bytes_read = 0;
uint64_t now = os_time_get();
uint64_t timeout = now + milliseconds;
while (now &lt; timeout)
{
    size_t chunk_length = xStreamBufferReceive(stream-&gt;_handle, buffer, length, pdMS_TO_TICKS(timeout - now));
    bytes_read += chunk_length;
    length -= chunk_length;
    if (length == 0)
    {
        break;
    }
    buffer = (uint8_t *) buffer + chunk_length;
    now = os_time_get();
}
return bytes_read;
</code></pre>
}
&#8220;`
Thank you. Cheers, Pavel
</div></div><div class="thread-post"><h3 class="thread-post-title">Behavior of xStreamBufferSend / xStreamBufferReceive</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on May 20, 2018</div><div class="thread-post-content">Correct, in xStreamBufferReceive() the second parameter is the size of 
the buffer into which data is to be copied, not the number of bytes to 
receive, so xSteamBufferRecevie() will return as soon as it has &#8216;some&#8217; 
data, the length of the data it receives in one go being capped to the 
buffer length.  See the xBufferLengthBytes description here: 
https://www.freertos.org/xStreamBufferReceive.html
Ref your implementation of os<em>stream</em>timed<em>read() &#8211; from a brief look it 
seems you have have an issue if the tick count overflows, the likelihood 
of which you have avoided by using a uint64</em>t &#8211; access to which will 
probably not be atomic.  It may be easier to use code similar to that 
shown on this page:  https://www.freertos.org/xTaskCheckForTimeOut.html 
which uses FreeRTOS API calls to take possible overflows into account 
for you.
</div></div><div class="thread-post"><h3 class="thread-post-title">Behavior of xStreamBufferSend / xStreamBufferReceive</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hubpav">hubpav</a> on May 20, 2018</div><div class="thread-post-content">Thank you, Richard. I was not aware of the <strong>xTaskCheckForTimeout</strong> function and I will look into it.
You are correct &#8211; I use <strong>uint64_t</strong> for my application ticks as it will &#8220;never&#8221; overflow&#8230; 🙂
However, I have been trying to make the access to this variable safe. Here is the snippet including the <strong>vApplicationTickHook</strong> callback implementation:
&#8220;`c
static uint64<em>t _os</em>time = 0;
uint64<em>t os</em>time<em>get(void)
{
    taskENTER</em>CRITICAL();
<pre><code>uint64_t ret = _os_time;
taskEXIT_CRITICAL();
return ret;
</code></pre>
}
void vApplicationTickHook(void)
{
    static TickType_t xTickLast = 0;
<pre><code>TickType_t xTickNow = xTaskGetTickCountFromISR();
_os_time += xTickNow - xTickLast;
xTickLast = xTickNow;
</code></pre>
}
&#8220;`
I hope this is sufficient for safe tick counter operation.
Thanks! Regards, Pavel
