</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS software timer stops without turning it of </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 7, 2018</div><div class="thread-post-content">You have called <code>xTimerCreateTimerTask()</code>, which will start-up the timer task. Your timer functions will be called from this task <strong>sequentially</strong>. The call-back takes place in <code>prvProcessReceivedCommands()</code>, by calling the user function <code>pxCallbackFunction</code>.
The timer task is sleeping most of the time. It runs at a configurable task priority of <code>configTIMER_TASK_PRIORITY</code>.
<blockquote>
  It runs alot of code, no sleep stuf that I know of.
</blockquote>
&#8220;no sleep stuf&#8221; ? It should have sleeps!
Roughly spoken in a multitasking system, a task-switch will only take place if:
<pre><code>- Another task has a higher priority
- Another task has the same priority and time-slicing is enabled
</code></pre>
Pre-emption is also important: if enabled a task can loose the CPU at any moment, also before it yields.
Sleeping means that a task doesn&#8217;t eat up CPU time. Sleeping is very important, except for tasks that have the lowest priority.
Now suppose that you have a task that spins without sleeping, and suppose that <code>configTIMER_TASK_PRIORITY</code> is low, then the timer-task wil starve, it won&#8217;t get CPU time anymore.
<blockquote>
  So a timer has always a higher priority as a task?
</blockquote>
Do you mean the timer task <code>prvTimerTask</code> in <code>timers.c</code> ?
That is your design decision, you may or you may not.
<blockquote>
  What happens when a second timer calls the CPU?
</blockquote>
As you have seen, the timer task will call your handlers in a sequential way. I would advice to keep the code short and not have it block.
<blockquote>
  Will it first finish the earlier timer task?
</blockquote>
It is not really a task but a application hook. And yes, hook 2 will only be called once hook 1 has returned.
