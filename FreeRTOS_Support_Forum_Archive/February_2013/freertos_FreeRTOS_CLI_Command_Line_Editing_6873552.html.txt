  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rrosier">rrosier</a> on February 28, 2013</div><div class="thread-post-content">Hello all,  
Could I ask if anyone knows of a CLI for FreeRTOS which includes some form of Command Line Editing.  
By this I mean that if someone types control characters like the &#8220;Backspace&#8221; button, that this is processed correctly by the Command Line.  
I suspect that I would need at a bare minimum the ability to use Backspace on a Command Line.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jdurand">jdurand</a> on February 28, 2013</div><div class="thread-post-content">I&#8217;ve wrote my own long ago and just cut, paste, and modify as needed for each new project.&nbsp; Some projects need to respond to special characters so I normally need to change at least something &#40;ex: one project uses &#8216;&#42;&#8217; to clear the buffer and abort any ongoing operation and &#8216;~&#8217; to send binary data to a background task&#41;.&nbsp; One thing in common with mine is when I receive a RETURN &#8216;r&#8217; that locks the buffer and begins whatever parsing is needed for the application.&nbsp; All editing like backspace and other special characters is done between my incoming ring buffer and the command buffer.  
It&#8217;s not really that hard, just decide what you need it to do and write it to your satisfaction.&nbsp;
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jdurand">jdurand</a> on February 28, 2013</div><div class="thread-post-content">Slight correction, the special characters for abort and binary data are done in the interrupt so they&#8217;re pulled from the data stream as soon as they come in.&nbsp; They are never even put into the buffer.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 28, 2013</div><div class="thread-post-content">What I have often done for cases like this is have &#40;small&#41; pool of buffers, and the serial interrupt builds up the line being typed into one of them &#40;processing backspaces and clear line commands, etc&#41; , and on the end of line character, sends the pointer to that buffer to the waiting task, and get the next buffer. When the task is done processing the buffer, it returns it to the list of available buffers. This way there isn&#8217;t a &#8220;dead time&#8221; for receiving characters after the End of Line &#40;unless you get so far ahead that you run out of buffers&#41;. This allows the command line processor to spawn copies of itself if needed to run a long command without killing the command input stream.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 28, 2013</div><div class="thread-post-content">I think most, if not actually &#42;all&#42; FreeRTOS+CLI examples process the backsapce character, but that is the only special character that is processed.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + CLI: Command Line Editing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rrosier">rrosier</a> on March 12, 2013</div><div class="thread-post-content">Thank you all for your replies.  
For information I found out what the issue was; the FreeRTOS CLI as used by the Atmel A.S.F. 3.5.1 does not fully handle backspace as sent by all potential terminal emulators.  
My Windows 7 Terminal Emulator is PuTTY.&nbsp; When I press Backspace &#40;&#8217;b&#8217; or 0x08&#41;, PuTTY sends Erase &#40;0x7F&#41;.  
The Atmel A.S.F. 3.5.1 does not respond to 0x7F in any special way; it only responds to &#8216;b&#8217; in a special way and for all other characters it echoes it back to the terminal.  
PuTTY responds to receiving the echoed 0x7F by performing a destructive backspace.&nbsp; So it looks as though everything is fine and working.  
Sadly when return is pressed, the 0x7F characters in the command string are passed through to FreeRTOS CLI and mess up the command string matching.  
As a result, it appears that Backspace doesn&#8217;t work when FreeRTOS CLI is asked to parse the command.
