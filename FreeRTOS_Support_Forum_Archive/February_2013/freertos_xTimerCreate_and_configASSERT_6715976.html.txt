  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTimerCreate() and configASSERT( )</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friedl">friedl</a> on February 3, 2013</div><div class="thread-post-content">Hello&#33;  
In timers.c in function xTimerCreate&#40;&#41; the term &#8220;xTimerPeriodInTicks &gt; 0&#8221;<br />
always evaluates to ZERO/FALSE:  
<pre><code>xTimerHandle xTimerCreate(...)
{
xTIMER *pxNewTimer;
    /* Allocate the timer structure. */
    if( xTimerPeriodInTicks == ( portTickType ) 0U )
    {
        pxNewTimer = NULL;
        configASSERT( ( xTimerPeriodInTicks &gt; 0 ) );
    }
</code></pre>
Therefore one will always see a compiler warning similar to:  
<pre><code>["..FreeRTOS_Sourcetimers.c" 236/3] condition is always true
</code></pre>
What is the sense of this assert when timers.h documents:  
<blockquote>
  If the timer cannot be created &#40;because , or <strong>the<br />
  timer period was set to 0</strong>&#41; then 0 is returned.  
</blockquote>
In my view this assert should be removed as this code does not do<br />
what is documented. I suggest:  
<pre><code>xTimerHandle xTimerCreate(...)
{
xTIMER *pxNewTimer = NULL;
    /* Allocate the timer structure. */
    if( xTimerPeriodInTicks &gt; ( portTickType ) 0U )
    {
</code></pre>
Regards<br />
Friedl  
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate() and configASSERT( )</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 3, 2013</div><div class="thread-post-content"><blockquote>
  Therefore one will always see a compiler warning similar to:
</blockquote>
I&#8217;m not sure I have ever seen that warning, which is curious, although software timers are a new&#40;ish&#41; features and most of the demos don&#8217;t include them because they are too old.&nbsp; Still, I have used timers with IAR, Keil, GCC, etc…  
The assertion is valid, but will be moved to outside of the &#8216;if&#8217; statement to remove the possibility of a warning.  
<blockquote>
  If the timer cannot be created &#40;because , or the<br />
  timer period was set to 0&#41; then 0 is returned.  
  In my view this assert should be removed as this code does not do<br />
  what is documented
</blockquote>
Well, the code returns NULL, which is 0 cast to a pointer, so it does behave as documented, although the documentation is somewhat imprecise.&nbsp; I have change the documentation to instead say &#8220;then NULL is returned&#8221;.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate() and configASSERT( )</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friedl">friedl</a> on February 3, 2013</div><div class="thread-post-content"><blockquote>
  <em>richardbarry</em><br />
  Still, I have used timers with IAR, Keil, GCC, etc…   
</blockquote>
This is a TASKING compiler and it sees that &#8220;xTimerPeriodInTicks &gt; 0&#8221; is always false and therefore the assert always true inside &#8220;xTimerPeriodInTicks == &#40; portTickType &#41; 0U&#8221;.  
<blockquote>
  <em>richardbarry</em><br />
  The assertion is valid, but will be moved to outside of the &#8216;if&#8217; statement to remove the possibility of a warning.  
</blockquote>
You can&#8217;t have a   
<pre><code>configASSERT( ( xTimerPeriodInTicks &gt; 0 ) )
</code></pre>
there as well or the function will NEVER return 0 nor NULL in case of xTimerPeriodInTicks == 0.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate() and configASSERT( )</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 4, 2013</div><div class="thread-post-content">I can see that the original position of the assert can only be reached when &#40; xTimerPeriodInTicks == 0 &#41;, and therefore the assert will always be evaluated to false, because if &#40; xTimerPeriodInTicks == 0 &#41; it cannot simultaneously be &gt; 0.&nbsp; The assert is useful to keep, but should not be placed in a position where it could cause a compiler warning to be generated, so I have moved it outside of the if&#40;&#41; statement….but you say:  
<blockquote>
  You can&#8217;t have a   
</blockquote>
configASSERT&#40; &#40; xTimerPeriodInTicks &gt; 0 &#41; &#41;  
there as well or the function will NEVER return 0 nor NULL in case of xTimerPeriodInTicks == 0.
The assert is a debugging statement only, it can be defined however the user wants and in production code &#40;where it will presumably not be defined&#41; its position will not change the logic of a function as it won&#8217;t generate any code.&nbsp; Setting the timer period to 0 is an error.&nbsp; The C code protects against that eventuality by trapping the error and exiting the function returning NULL.&nbsp; The assert&#40;&#41; gives people an opportunity to catch that happening while they are developing their application.&nbsp; I think I disagree with your statement that the function will never return NULL &#8211; it will if xTimerPeriodInTicks == 0 if configASSERT is not defined, or configASSERT&#40;&#41; is defined to something that does not prevent the application from continuing executing.&nbsp; The assert is not a logic statement that effects the flow of the code, just provided for the convenience of users while they are creating their applications.  
Regards.
