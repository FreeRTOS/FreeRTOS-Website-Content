  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Timer stack overflow problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/moh-hakam">moh-hakam</a> on February 6, 2013</div><div class="thread-post-content">I&#8217;m new to FreeRTOS, I got a timer stack overflow caught by <em>vApplicationStackOverflowHook</em> when <em>xTimerChangePeriod</em> called, what could be the reason<br />
I create a stopwatch timer as follows:  
<pre><code>stopwatchTimer = xTimerCreate(flshTmrStr,DUMMY_TIME_PERIOD,pdFALSE,
                    (void*)STOPWATCH_TIMER_ID, stopwatchCallback);
</code></pre>
and in the task function:  
<pre><code>stopwatchTimeExpired= pdFALSE;
xTimerChangePeriod(stopwatchTimer,delay*1000/portTICK_RATE_MS,0);
xTimerStart(stopwatchTimer,0);
while(stopwatchTimeExpired == pdFALSE)
{
    //do some stuff till time expired (flag set true in timer callback)
}
</code></pre>
in FreeRTOSConfig.h file:  
<pre><code>#define configUSE_TIMERS                    1
#define configTIMER_TASK_PRIORITY           3
#define configTIMER_QUEUE_LENGTH            10  
#define configTIMER_TASK_STACK_DEPTH        configMINIMAL_STACK_SIZE
</code></pre>
I&#8217;m using ATMEGA32 in WinAVR GCC compiler, thanks for your help…
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer stack overflow problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 6, 2013</div><div class="thread-post-content">The ATMega32 does not have much SRAM, but if a task that is calling xTimerChangePeriod&#40;&#41; is experiencing a stack overflow you will most likely have to increase the stack allocated to that task when the task is created.  
You can also try reducing the stack used by the task by reducing the size of any arrays allocated on the stack, or by moving variables from the stack to instead by static or global &#40;if your application allows&#41;.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer stack overflow problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/moh-hakam">moh-hakam</a> on February 6, 2013</div><div class="thread-post-content">Dear Richard,<br />
the overflow is not caused by the task, but by the timer service; when monitoring the task name in vApplicationStackOverflowHook it was &#8216;Tmr Scv&#8217;. I checked the remaining byte left for that task by using<br />
leftMem=uxTaskGetStackHighWaterMark&#40;NULL&#41;;<br />
and it was 91 byte &#40;out of 200&#41;<br />
in fact the application run fine despite that overflow,
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer stack overflow problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 6, 2013</div><div class="thread-post-content">It is possible that on AVR devices the timer stack size needs to be greater than the configMINIMAL&#95;STACK&#95;SIZE setting.&nbsp; configMINIMAL&#95;STACK&#95;SIZE is set for the idle task, which &#40;unless an idle task hook function is defined&#41; does nothing more than call some very small functions.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer stack overflow problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/moh-hakam">moh-hakam</a> on February 6, 2013</div><div class="thread-post-content">Yes, we&#8217;re right, increasing the timer stack size from 100 to 120 solved the problem.<br />
I think I may consider counting ticks instead &#40;and taking care of 0xFFFF~0 rollover&#41;….  
Thank you A lot…
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer stack overflow problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/moh-hakam">moh-hakam</a> on February 6, 2013</div><div class="thread-post-content">Yes, you&#8217;re right, increasing the timer stack size from 100 to 120 solved the problem. I think I may consider counting ticks instead &#40;and taking care of 0xFFFF~0 rollover&#41;…. Thank you A lot…
