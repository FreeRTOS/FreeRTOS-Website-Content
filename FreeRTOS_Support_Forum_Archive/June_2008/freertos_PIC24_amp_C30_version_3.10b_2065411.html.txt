  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC24 &#038; C30 version 3.10b</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jaumerc">jaumerc</a> on June 4, 2008</div><div class="thread-post-content">Hi,
I tried to use the demo application of FreeRTOS for PIC24 and I couldn&#8217;t get it worked.
I am using the Explorer 16 board with the PIC24FJ128GA010 PIM. I think this is the scenario used in the demo application. The difference is that I am using the MPLAB version 8.10 &amp; the compiler C30 version 3.10. 
I can compile the whole project without errors, programming the board, starting the application and then nothing happens &#40;no leds activity, no LCD messages and no UART activity&#41;. Debugging the application with ICD2 I see that the application is arriving at the following point &#40;program stack&#41;:
main.c vTaskStartScheduler&#40;&#41; Line 181
tasks.c xPortStartScheduler&#40;&#41; Line 1051
port.c asm volatile &#40; &quot;return&quot; &#41; Line 296 inside xPortStartScheduler function
After this, it seems target continues working &#40;I can do some &quot;step into&quot; instructions and program counters changes&#41; but after some of these steps, the program restarts.
Any idea of what can happen?
Jaume

</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 &#038; C30 version 3.10b</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 7, 2008</div><div class="thread-post-content">The first thing I found is that the -fomit-frame-pointer option no longer appears to omit the frame pointer.&nbsp; I&#8217;m not sure exactly why that would matter, but moved the vPortYield&#40;&#41; function to asm code from the existing C code implementation.&nbsp; This seemed to fix most things other than the serial port interrupt.
The serial port interrupt is crashing because the frame pointer saved to the stack by the LNK instruction is overwritten by a local variable that is allocated the same position on the stack.&nbsp; This in turn means the frame pointer that is restored at the end of the ISR is incorrect, and the interrupted function then crashes when it attempts to run its epilogue code.
I&#8217;m still looking at this to see if it is something in the kernel code or compiler that is causing this.&nbsp; Although it would thus far seem to be in the compiler I would like to make triple sure before I place the blame any where else&#33;
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 &#038; C30 version 3.10b</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richpainter">richpainter</a> on June 16, 2008</div><div class="thread-post-content">I was successful at using C30 3.10 and FreeRTOS 5.0.0 with -O3 optimization and ONLY module port.c having -fomit-frame-pointer. So, this worked as far as i can tell.
Specifically I used:
C30 gcc settings
Project:
&nbsp;&nbsp;&nbsp; Use Alternate:
&nbsp;&nbsp;&nbsp; -O3 -g -Wall -Wwrite-strings -fverbose-asm -dp -save-temps
&nbsp;&nbsp;&nbsp; -mconst-in-code -mlarge-data -merrata=exch
port.c:
&nbsp;&nbsp;&nbsp; Use Alternate:
&nbsp;&nbsp;&nbsp; -O3 -g -Wall -Wwrite-strings -fverbose-asm -dp -save-temps
&nbsp;&nbsp;&nbsp; -mconst-in-code -mlarge-data -fomit-frame-pointer -merrata=exch
Today I loaded FreeRTOS 5.0.2 and did the same thing with C30 3.10.
This doesn&#8217;t run correctly in that it does a reset as others have reported. I have not tracked back to see what is wrong.
So, this same problem exists on C30 3.10 as is being reported on C30 3.10b BOTH with FreeRTOS 5.0.2
rich
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 &#038; C30 version 3.10b</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 17, 2008</div><div class="thread-post-content">I think the complier is mis-optimizing some pieces of the code. I found I needed to use low levels of optimization to get things to work. The generated object code looked wrong, but I haven&#8217;t had time to dig into it in more detail.
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC24 &#038; C30 version 3.10b</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 17, 2008</div><div class="thread-post-content">There is definitely a code generation problem with the 3.10b compiler &#8211; I have had this confirmed and a solution should not be far away.
In the mean time I have a workaround whereby I have moved the portYIELD&#40;&#41; function to an assembly file &#40;from its current C implementation&#41;.&nbsp; This makes the code work provided no optimisation is used.&nbsp; I think I will actually keep the code in this form for the next release as it has two other benefits:
1&#41; The -fomit-frame-pointer options is no longer required as the prologue and epilogue code is now fixed in the asm file.
2&#41; It uses less stack space.
If you want a copy of the new .asm file then send me an email to r &#95;dot&#95; barry &#42;at&#42; freertos.org.
Regards.
