  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">task stops</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on August 17, 2006</div><div class="thread-post-content">I have an application runnign with about 8 taks in it now.&nbsp; most of them are very small tasks that do simple IO monitoring and hence have nice small stacks.&nbsp; The problem occurs that my debug serial port works absolutely fine until the main control thread hits a certain point at which the serial thread stops running &#40; the queue from the ISR is still having bytes pushed in, but the main worker thread seems to not to pull them out any more&#41;.&nbsp; The code in the main control code is nothing special, just doing some IO related functions.&nbsp; when it gets back out of that code, the serial task starts up again straight away.&nbsp; I realise that this a rather vague posting, but i am getting really frustrated as to why its not working.&nbsp; i&#8217;m really after things to check etc &#8211; stack sizes? heap size? things getting over written?&nbsp; the code is running on an ARM AT91Sam7S64.&nbsp; if i change the way the controller code runs so it is very simple &#40; but no longer properly functional &#41;, the problem does not occur.
thanks in advance for any thoughts or suggestions of ideas to help.
regards
Andy
</div></div><div class="thread-post"><h3 class="thread-post-title">task stops</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on August 17, 2006</div><div class="thread-post-content">To try and understand what you are saying.
Out of your eight tasks there are two that communicate on a particular queue.&nbsp; These tasks work fine unless the control task is operating.
When the control task operates the two tasks using the queue seem to stop &#40;at least the task taking data from the queue, seems to stop&#41;, but starts again when the control task blocks.
Presumably the control task is lower priority than the task that stops, otherwise the behavior you describe would be expected.
I don&#8217;t think it will be a heap problem as the heap is only used when tasks or queues are actually created.
Stack problem is probably not the issue either as this normally causes a crash &#8211; but check this first.
Is your control task using a critical section that is too long?&nbsp; Or is it locking the scheduler for too long?
</div></div><div class="thread-post"><h3 class="thread-post-title">task stops</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on August 30, 2006</div><div class="thread-post-content">not quite, the debug serial thread simply has a queue to the ISR routine that pushes newly received bytes to the thread via the thread.&nbsp; The control thread reads ADC channels and looks at IO pins for a lot of what it does.&nbsp; is it possible that TCB sections overlap in memory or something such that the TCB / thread data for the debug port gets somehow stomped over?&nbsp; i&#8217;ve tried jugglign stack sizes and have used the tasklist function to prove that the tasks have more than enough free stack space.&nbsp; once all the tasks have started, there is no dynamic variable allocation within my processes so feel confident that the inital stack free values would be constant over the life of the thread running &#40; for ever &#41;.&nbsp; Andy
