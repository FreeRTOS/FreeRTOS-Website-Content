  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Scheduler behavior in non-preemptive mode</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tzuchien_chiu">tzuchien_chiu</a> on August 29, 2006</div><div class="thread-post-content">I have a non-preemptive port of FreeRTOS and there there are totally three tasks:
tskIDLE&#95;PRIORITY = 0
Idle,&nbsp;&nbsp; tskIDLE&#95;PRIORITY
Task 1, tskIDLE&#95;PRIORITY + 1
Task 2, tskIDLE&#95;PRIORITY + 2
Task 1 and 2 is created using the same function:
&nbsp; portTASK&#95;FUNCTION&#40;task&#95;proc, params&#41;
&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; unsigned id = &#42;&#40;unsigned&#42;&#41; params;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; while &#40;1&#41; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; printf&#40;&quot;&#42;%d&#42; &quot;, id&#41;;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; taskYIELD&#40;&#41;;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#125;
&nbsp; &#125;
But Task 1 &#42;never&#42; gets a chance to run. After reading vTaskSwitchContext&#40;&#41;, I found that Task 1 is starved because Task 2 is &#42;always&#42; in the ready list, and uxTopReadyPriority is always 2.
Is this behavior expected?
&#45;- 
Tzu-Chien Chiu &#8211; SMedia Technology Corp.
URL: http://www.csie.nctu.edu.tw/~jwchiu/
</div></div><div class="thread-post"><h3 class="thread-post-title">Scheduler behavior in non-preemptive mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on August 29, 2006</div><div class="thread-post-content">Yes, this would be expected because task 2 never blocks.&nbsp; It is always the highest priority task that is able to run.
If you replaced taskYIELD&#40;&#41; with vTaskDelay&#40; 2 &#41;, then task 2 would block for 2 ticks, allowing task 1 to execute.
