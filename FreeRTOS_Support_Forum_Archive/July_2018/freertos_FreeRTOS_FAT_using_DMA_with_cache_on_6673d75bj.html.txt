</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+FAT  using DMA with cache on</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on July 30, 2018</div><div class="thread-post-content">Hi Mateusz, as you have seen, you can provide special functions for memory allocation in <code>FreeRTOSFATConfig.h</code>:
~~~
    #define ffconfigMALLOC( aSize )     uncached<em>malloc( aSize )
    #define ffconfigFREE( apPtr )       uncached</em>free( apPtr )
~~~
I am not an expert on CPU and caching, but here are my thoughts and recommendations:
Cached memories work fine, until you access that memory with a DMA controller, either for reading or writing.
A DMA controller bypasses the caching mechanism and writes and reads directly from the physical memory.
Before DMA reads memory, make sure that any changes to the memory regions involved are being flushed ( clean the cache ).
After DMA has written to memory, make sure that the regions are being invalidated. This will force the CPU to update the data cache.
While DMA works with memory, do not access that memory ( region ) from the CPU.
Make sure that the size of the memory passed to DMA is always a multiple of a cache-line ( e.g. 32 bytes ).
Even if only 16 bytes are being used, make sure that the other 16 bytes won&#8217;t be accessed by the CPU.
I once made an error with this: I declared network buffers in a FreeRTOS+TCP driver, and gave these buffers a 16-byte alignment. As a consequence, Buffer-2 got changed unwillingly because it had cache overlap with Buffer-1.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+FAT  using DMA with cache on</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on July 30, 2018</div><div class="thread-post-content"><blockquote>
  I am managing cache coherency exacly the same as you proposed. 
</blockquote>
Good to hear that.
FreeRTOS+FAT uses buffers of 512 bytes each. The application provides one big buffer as <code>FF_CreationParameters_t::pucCacheMemory</code>, which is interpreted as an array of 512-byte blocks.
So if you make sure that <code>pucCacheMemory</code> is well-aligned, all other blocks will be well-aligned as well.
In most cases, <code>ff_fwrite()</code> and <code>ff_fread()</code> will be called with a +FAT buffer as a parameter, and thus cached-memory in your case.
But there are two exceptions:
<ul>
<li>if you read or write &#8220;entire aligned sectors&#8221;: the user buffer will be passed directly to the access functions, thus bypassing the +FAT buffers.</li>
<li>If you use <code>ffconfigOPTIMISE_UNALIGNED_ACCESS</code>, a file buffer <code>pxFile-&gt;pucBuffer</code> will be passed to the access functions. <code>pucBuffer</code> was created with <code>ffconfigMALLOC()</code>.</li>
</ul>
In the +TCP driver for Zynq, I called the cache code conditionally:
~~~
    if( ucIsCachedMemory( pucEthernetBuffer ) != 0 )
    {
        Xil<em>DCacheFlushRange( pucEthernetBuffer, xDataLength );
    }
    &#8230;
    if( ucIsCachedMemory( pucEthernetBuffer ) != 0 )
    {
        Xil</em>DCacheInvalidateRange( pucEthernetBuffer,xDataLength );
    }
~~~
Maybe you could test the memory types in your <code>ff_fwrite()</code> and <code>ff_fread()</code> as here-above?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+FAT  using DMA with cache on</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on July 31, 2018</div><div class="thread-post-content">Hi Mateusz,
In my previous post I made a typo. Where I wrote:
~~~
    ff<em>fwrite() and ff</em>fread()
~~~
I actually meant the implementation in the driver, often called:
~~~
    prvFFRead() and prvFFWrite()
~~~
I&#8217;m sorry if that confused any one.
<blockquote>
  Ah okay if I understand you correctly I can pass aligned buffer placed in non cacheable region to:
  pxParameters->pucCacheMemory = &#8216;AlignedNonCacheableBuffer of size xIOManagerCacheSize&#8217;
  and everything should be fine cause +FAT executed read/write operations through this cache buffer?
</blockquote>
If the memory that you supply is non-cacheable, it must have an alignment that DMA can work with.
If the memory is cacheable, its alignment must fit both with DMA and the D-CACHE.
And also: when the first block is well-aligned, the subsequent blocks will also have a proper alignment because the block-size is 512 bytes.
<blockquote>
  Will it be possible to use cached_malloc/free then ? I see that +FAT allocated
  some memory for different structures but they are not used with read/write operation directly.
</blockquote>
With the exception of <code>pxFile-&gt;pucBuffer</code> ( which you do not use for now ).
<blockquote>
  Unfortunately I don&#8217;t understand first case that you&#8217;ve mentioned.
  What you mean by &#8220;entire aligned sectors&#8221; ? You mean writing 4KB of aligned data ?
</blockquote>
I mean for instance this kind of access:
~~~
<strong>attribute</strong> ((aligned (32))) uint8_t pucBuffer[ 16 * 512 ];
<pre><code>FF_Read( pxFile, 1, n * 512, pucBuffer );
FF_Write( pxFile, 1, n * 512, pucBuffer );
</code></pre>
~~~
In these cases, the +FAT caching buffers will be by-passed, and <code>pucBuffer</code> will be passed directly to the driver functions <code>prvFFRead()</code> and <code>prvFFWrite()</code>.
<blockquote>
  For now <code>ffconfigOPTIMISE_UNALIGNED_ACCESS</code> is set 0 so no problem in this case but I will test in future.
</blockquote>
As you can guess, the fastest file i/o is done when you read or write in multiple blocks of 512 bytes. This is also favourable for memory cards: contiguous reads and writes are a lot faster.
The <code>ffconfigOPTIMISE_UNALIGNED_ACCESS</code> option is only useful if you plan to read or write in small quantities.
<blockquote>
  I think that your solution with testing for cached/non-cached buffer operation will do the trick,
  I just need confirmation if it safe to use cached_malloc/free in this scenario 🙂
</blockquote>
In case you have doubts, there is some good testing software in the <a href="https://freertos.org/FreeRTOS-Labs/downloads/160919_FreeRTOS_Labs.zip?dl=0">original +FAT release</a>
It is in the old <code>160919_FreeRTOS_Labs.zip</code>:
~~~
    FreeRTOS-PlusDemoCommonFreeRTOS<em>Plus</em>FAT<em>DemosCreateAndVerifyExampleFiles.c
    FreeRTOS-PlusDemoCommonFreeRTOS</em>Plus<em>FAT</em>Demostestff<em>stdio</em>tests<em>with</em>cwd.c
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+FAT  using DMA with cache on</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/swichu91">swichu91</a> on July 31, 2018</div><div class="thread-post-content">Looks like it works, below are steps I performed:
&#8211; switched +FAT to use cacheable<em>malloc/free
&#8211; made sure that cacheable</em>malloc/free buffers are 32-bytes aligned. I&#8217;m using custom memory allocator based on heap<em>4.c so it&#8217;s actually easy to align buffers allocated with malloc
&#8211; I created +FAT pucCacheMemory non-cached segment which is 32-bytes aligned and used it instead of malloced one
&#8211; added simple isCachedMem function which cheks if address passed to prvRead/Write functions is withing cached-memory or not
&#8211; in prvRead if memory is cached I perform DCache</em>Invalidate AFTER  DMA transfer completed
&#8211; in prvWrite if memory is cached I perform DCache_Clean/Flush BEFORE starting DMA transfer 
&#8211; finally turn on cache 😀
I also noticed that when using ff<em>fwrite function pointer to memory buffer is passed straight into to prvWrite function. Therefore you have to make sure that if memory block passed to ff</em>fwrite function is allocated dynamically you have to make sure that it is  32-bytes aligned and manage cache coherency.
I hope someone find it useful and Hein thank you very much for meaningful discussion. As always you are very helpful 🙂
Best Regards
Mateusz Piesta
