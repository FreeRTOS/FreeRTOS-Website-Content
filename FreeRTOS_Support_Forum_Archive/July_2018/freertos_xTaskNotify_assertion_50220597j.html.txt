  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTaskNotify assertion</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fly135">fly135</a> on July 30, 2018</div><div class="thread-post-content">My application failed an assertion in the tasks.c xTaskNotify function.  I&#8217;m calling xTaskNotify with the handle of the task. Now my app has been calling this function since it booted maybe 20 hours ago. I just happened to notice it has rebooted as a result of the assertion. The only clue is the comment&#8230;.
&#8220;The task should not have been on an event list&#8221;
Anyone know what this means?
~~~
/* The task should not have been on an event list. */
configASSERT( listLIST_ITEM_CONTAINER( &amp;( pxTCB->xEventListItem ) ) == NULL );
~~~
John A
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 30, 2018</div><div class="thread-post-content">A task can be blocked on a task notification, or an RTOS object such as 
a queue, semaphore, stream buffer, event group etc. &#8230;. but it can&#8217;t be 
blocked on both a the same time.  The assert has detected an 
inconsistent state, because if the xEventListItem is not NULL, then it 
would appear that the task was blocked on an RTOS object too (which 
would not be possible).
A simple explanation for this would be a simple old data corruption &#8211; 
maybe the xEventListItem has been overwritten?
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fly135">fly135</a> on July 30, 2018</div><div class="thread-post-content">My task has this statement so that it doesn&#8217;t wait when notified&#8230;.
int ret = ulTaskNotifyTake(pdTRUE, msDelay(200));
But if it times out the task could be doing a lot of other things.  So for example if the task is sending and reading data from a socket it might be waiting for a socket related event.  So ruling out data corruption for the time being&#8230; if the task was waiting on a socket and the xTaskNotify was called (by another task) to signal this one would that potentially cause this assertion?
John A
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 30, 2018</div><div class="thread-post-content">The line with the assertion should not execute unless the task was 
waiting for a notification.  So if your 200ms block time (from you last 
post) has expired, and the task is no longer waiting for the 
notification, then the assert should not get hit as that line of code 
would never execute, see:
<pre>
/* If the task is in the blocked state specifically to wait for a
notification then unblock it now. */
if( ucOriginalNotifyState == taskWAITING_NOTIFICATION )
{
     ( void ) uxListRemove( &( pxTCB->xStateListItem ) );
     prvAddTaskToReadyList( pxTCB );
     /* The task should not have been on an event list. */
     configASSERT( listLIST_ITEM_CONTAINER( &( pxTCB->xEventListItem ) ) 
== NULL );
</pre>
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fly135">fly135</a> on July 31, 2018</div><div class="thread-post-content">Thanks for that explanation.  So that means maybe I should consider data corruption.  
edit: So for some reason it appears that my task was waiting for some event at the same time it was waiting for notification.
Thank you for your help.
John A
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 31, 2018</div><div class="thread-post-content">I&#8217;m afraid I&#8217;m not familiar with the way Espressif have integrated lwIP 
&#8211; but it is the case that if you have nested functions that unknowingly 
(so unmanaged) both use task notifications for different purposes you 
can get into a twist &#8211; however I don&#8217;t think even that would explain 
what you are reporting for the reason as per my previous email.
Try setting configUSE<em>LIST</em>DATA<em>INTEGRITY</em>CHECK_BYTES to 1 in 
FreeRTOSConfig.h &#8211; assuming you have configASSERT() defined then that 
can help confirm a data corruption, although it unfortunately can&#8217;t 
prove there isn&#8217;t one.
(actually, I know you have configASSERT() defined, as that is how this 
thread started ;o)
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotify assertion</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fly135">fly135</a> on July 31, 2018</div><div class="thread-post-content">Thanks, I&#8217;ll look into that.
