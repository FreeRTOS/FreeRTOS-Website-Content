  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS+TCP ATSAM4E receive not working</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/zetter">zetter</a> on July 21, 2018</div><div class="thread-post-content">Hi,
I&#8217;m just getting started with FreeRTOS and FreeRTOS+TCP in preparation for a switch we&#8217;re making to ARM from Atxmegas. We&#8217;re basing our new board on the ATSAM4E with a KSZ8051MNL phy, so we&#8217;ve bought a SAM4E-EK to get started with the software while the design team is working on the new board.
We started off with the ASF example project for the SAM4E to demonstrate FreeRTOS with LwIP. It works really well, but we figured we might start using the FreeRTOS+TCP right away, since it seems better integrated with FreeRTOS. However, we can&#8217;t really get it working. Send packets seems to be working fine, but we can&#8217;t recieve anything. It&#8217;s probably some stupid beginners mistake we&#8217;ve made, but we can&#8217;t figure out what it is.
We created the porject in Atmel Studio to select the appropriate ASF (3.4) modules (GMAC, GMAC_RAW&#8230;). We copied the whole ASF folder from that project into our project where we&#8217;re using our own makefiles and the GNU ARM GCC toolchain (we&#8217;re mostyly using OSX and Ubuntu for development and don&#8217;t really like the IDE). 
We also downloaded the latest FreeRTOS (10.0.1) and FreeRTOS+TCP and added that to the project.
We&#8217;re loading the GMAC, GMAC_RAW and PHY modules from the ASF files instead of the supplied FreeRTOS versions to be get the latest ones. 
We&#8217;ve copied the NetworkInterface.c template from the ATSAM4E example in FreeRTOS+TCP and the ethernet<em>phy.c from ASF to make some minor modifications so that they&#8217;ll play together. Basically an extra include and declaring ethernet</em>phy_addr a global.
So, transmission seems to be working. Atleast so well that a DCHP DISCOVER is sent. If we remove the &#8220;#define ipconfigDRIVER<em>INCLUDED</em>TX<em>IP</em>CHECKSUM 1&#8243; we can even see the DHCP server responding with an DHCP OFFER in Wireshark. Our code does however not seem to pick it up. In fact, it doesn&#8217;t seem to pick anything up from the network. We&#8217;ve added some debug statements throughout the code, and we can see that some receive stuff is called when the DHCP server responds. The same happens if we set a fixed IP and ping the card. The packets does however seem to get lost on the way to the higher levels of the code, and we can&#8217;t really figure out why.
Here&#8217;s a log with the debug statements:

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP ATSAM4E receive not working</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/zetter">zetter</a> on July 21, 2018</div><div class="thread-post-content">We&#8217;ve kept adding debug statements and can see that even prvProcessEthernetPacket in FreeRTOS<em>IP.c is beeing called. However, printing pxEthernetHeader->usFrameType there gives only the values 69 when we ping it, and sometimes 256 (I guess stuff from the DHCP server). None of those match ipARP</em>FRAME<em>TYPE or ipIPv4</em>FRAME_TYPE.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP ATSAM4E receive not working</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/zetter">zetter</a> on July 21, 2018</div><div class="thread-post-content">Ahh, found it. For anyone who might have similar problems in the future:
FreeRTOS defines a two byte offset as a default config option in FreeRTOSIPConfigDefaults.h. (#define ipconfigPACKET<em>FILLER</em>SIZE 2). The GMAC has to be configured accordingly. For instance, we call gmac<em>set</em>rx<em>buffer</em>offset(GMAC, ipconfigPACKET<em>FILLER</em>SIZE); in prvGMACInit in the network interface.
