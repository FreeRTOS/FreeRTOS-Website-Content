  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS &#8211; long time stability?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/grunfalan">grunfalan</a> on November 2, 2008</div><div class="thread-post-content">Hello friends,
For some time now, I am trying to find a good RTOS that I am going to use in my future projects with AVR microcontrollers. FreeRTOS is one of my favorites now, but as I don&#8217;t have any experience with RTOS, some questions started to emerge.
I found information &#40;on SafeRTOS FAQ&#41; that SafeRTOS uses static memory allocation for RTOS data instead of dynamic, which is used in FreeRTOS &#8211; and therefore it is more safe and stable. 
Also, on this forum, somebody mentioned memory leakage, as if it is something usual and inevitable with FreeRTOS. 
Does it mean that application with FreeRTOS can not be made for long time stability and 24/7/365 work? If that&#8217;s the case, could it be avoided with some careful programming technique? How big is this problem in practice?
I want to use it in a device that is placed on distance location, and should work for a long time without &quot;freezing&quot;. 
I already built the device without RTOS &#40;foreground/background system&#41;, and it works very stable on several locations, but now I am considering using RTOS because of easier upgrade/mantaining. 
Does use of FreeRTOS increase possibility of fallouts?
As I said, I am a complete newbie concerning RTOS, and any comment or experience will be valuable to me.
Thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS &#8211; long time stability?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 2, 2008</div><div class="thread-post-content">I suppose it depend what you do. From my inspection of the code, the only dynamic memory that is used is for the creation of tasks, queue and related objects. If you program creates all of these that are needed at start up, then the dynamic nature of the allocation isn&#8217;t an issue for long term operation. 
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS &#8211; long time stability?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 2, 2008</div><div class="thread-post-content">This is correct &#8211; memory is required each time a task, queue or semaphore is created, and freed when the same task/queue/semaphore is deleted.&nbsp; 
In FreeRTOS.org the memory is obtained from the &#91;pseudo&#93; heap, whereas in SafeRTOS the memory is provided by the application.&nbsp; Although the SafeRTOS application is free to obtain this memory in any way it wants, in a safety critical application normally only statically declared buffers would be used as generally dynamic allocation has problems regarding non-deterministic allocation/free times and with fragmentation &#40;memory pools can be used to fix some of these issues but these are complex to use and tune, so are not safer&#41;.
If you never delete a task, queue or semaphore then memory is never freed so you have no issues to worry about in that regard.&nbsp; Also the schemes used in FreeRTOS.org are very simplistic, and the way memory is allocated so restricted, that generally you would not have any problems in any case.&nbsp; The one thing to watch out for in FreeRTOS.org is that you always allow the idle task some processing time if you are wanting to delete resources as it is the idle task that does the final clean up.&nbsp; Also, never write an application that uses dynamic memory allocation to allocate and free &#8216;random&#8217; sized blocks as this is where you can get into fragmentation problems &#8211; but this is true for any embedded system be it FreeRTOS.org based or not.
Regards.
