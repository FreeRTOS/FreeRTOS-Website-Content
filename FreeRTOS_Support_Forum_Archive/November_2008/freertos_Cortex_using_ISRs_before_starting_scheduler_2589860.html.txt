</div></div><div class="thread-post"><h3 class="thread-post-title">[Cortex] using ISRs before starting scheduler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 21, 2008</div><div class="thread-post-content">The kernel will leave interrupts up to the configKERNEL&#95;INTERRUPT&#95;PRIORITY disabled following most API calls that are made before the scheduler is started. I think this is to ensure that interrupts don&#8217;t attempt to cause a context switch before the scheduler has been configured and started. You could probably call taskENABLE&#95;INTERRUPTS&#40;&#41; after an API call to set the interrupt mask level back to zero.

</div></div><div class="thread-post"><h3 class="thread-post-title">[Cortex] using ISRs before starting scheduler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 21, 2008</div><div class="thread-post-content">Did you see this page: http://www.freertos.org/a00110.html&#35;kernel&#95;priority ?
Be very careful enabling interrupts again after installing an interrupt handler IF that interrupt handler makes any API calls that could cause a context switch to be attempted.&nbsp; Any attempt to context switch before the scheduler is started will be hazardous for your application.

&#40;changing basepri register&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">[Cortex] using ISRs before starting scheduler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bodev">bodev</a> on November 21, 2008</div><div class="thread-post-content">I have found some more info.
STM32 implements only the 4 MSB bits of the PRIMASK.
&#40;i.e. see http://www.st.com/mcu/forums-cat-6944-23.html&#41;
So the line 
&#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp; 191 /&#42; equivalent to 0xa0, or priority 5. &#42;/
i think should be
&#35;define configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY&nbsp;&nbsp;&nbsp;&nbsp; 191 /&#42; equivalent to 0x0A, or priority 11. &#42;/
I am not sure if the assumption &#40;191 map to 5&#41; caused other indesired bahaviors in FreeRTOS
Furthermore, NVIC controller can be set up with the 4 bits splitted in two groups: priority and subpriority.
I think FreeRTOS consider all 4 bits as priority and no bits for sub priority.
I am not sure what can happen if someone use different schemes.
Bo
</div></div><div class="thread-post"><h3 class="thread-post-title">[Cortex] using ISRs before starting scheduler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 21, 2008</div><div class="thread-post-content">Yes &#8211; the STM32 implements 4 bits of priority, these four bits being the top 4 bits of an 8 bit number.&nbsp; So 0xff &#40;255, 0xf0, or &#40;0x0f&lt;&lt;4&#41; are all equivalent as the bottom 4 bits are ignored&#41; is the lowest priority and 0x0f &#40;31, or 0, or &#40;0&lt;&lt;4&#41;&#41; the highest priority.
191 is &#40;0x0b&lt;&lt;4&#41;, which as you point out is effectively 11, not 5.
This is a cut and paste error from the Luminary Micro ports, where only 3 bits are implemented, so 5 is the correct value.
Sorry for any confusion caused and thanks for pointing it out.&nbsp; I have corrected the comments in the SVN repository to ensure they get included in the next release.
Regards.
