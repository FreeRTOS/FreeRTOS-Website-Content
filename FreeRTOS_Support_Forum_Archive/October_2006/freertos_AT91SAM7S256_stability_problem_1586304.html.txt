  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AT91SAM7S256 stability problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 5, 2006</div><div class="thread-post-content">Hello , 
we have a serious problem with the AT91SAM7S256. 
We have realized a project with AT91SAM7S256 and FreeRTOS 4.05. 
We use 3 tasks with the same priority an idle task and a tick rate of 1 ms &#40;PREEMPTION = YES&#41;. 
We use the watchdog. It works.If we place a while&#40;1&#41;; command for testing in the Main task the system restarts without any problems. 
It works fine. 
On some boards the systems stops after a short while. 
All outputs are redefined as inputs and the xtal &#8211; oszilator stops working. 
The time between startup and the problem varies from board to board &#40;some minutes up to some days&#41;. 
We are not able to debug the problem with JTAG / Jlink. 
A connected Jlink changes the timing and the problem doesn&#96;t occured. 
In the past we noticed that the problem happend when we transfered and received data on UART 0 with DMA. After we have disabeled the DMA transmission it seemed to be fixed . 
In the current project we use DMA only for receiving data. 
We also use SPI &#40;without DMA and Interrrupt&#41; and TWI/I2C with Interrupt. 
Does anybody has an idea or a posible reason for this strange behaviour? 
Does anybody has an idea why the conroller doesn&#96;t restart in this error case? 
Thanks a lot
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 stability problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 5, 2006</div><div class="thread-post-content">&gt; Hello , 
&gt; we have a serious problem with the AT91SAM7S256. 
&gt; 
&gt; We have realized a project with AT91SAM7S256 and FreeRTOS 4.05. 
&gt; We use 3 tasks with the same priority an idle task and a tick rate of 1
&gt; ms &#40;PREEMPTION = YES&#41;.
&gt; We use the watchdog. It works.If we place a while&#40;1&#41;; command for testing in
&gt; the Main task the system restarts without any problems.
&gt; It works fine. 
So your saying that the watchdog does not work when the scheduler is running?&nbsp; By default the scheduler uses the PIT to generate the tick interrupt.&nbsp; The PIT uses the system interrupt.&nbsp; Does the watchdog also use the system interrupt?&nbsp; If so you might want to use a different timer to generate the tick interrupt.
&gt; 
&gt; On some boards the systems stops after a short while. 
&gt; All outputs are redefined as inputs and the xtal &#8211; oszilator stops working. 
Sounds like the problem is the oscillator ???&nbsp; If the oscillator is not working the SAM7 will be a dead dog.
&gt; We are not able to debug the problem with JTAG / Jlink. 
&gt; A connected Jlink changes the timing and the problem doesn&#96;t occured. 
This is a big clue to your problem.&nbsp; The Jlink does not effect the timing.&nbsp; Do you use different build options in the code when building for debug?&nbsp; If so then this is what is causing the different timing.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7S256 stability problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on October 6, 2006</div><div class="thread-post-content">Hello,
thanks for your answer.
The watchdog is working very well and it is tested
and resets the system &#40;core &amp; peripheral&#41; correct.
When the problem occured, we see these:
&gt; no xtal function, no dc at these contacts &#40;switched off by controller like when starting up&#41;
&gt; all ports were inputs &#40;we tried with a resistor to VCC and VSS, no significant current flows&#41;
&#40;like when starting up when power is applied&#41;
&gt; no reaction on the reset pin &#40;seemed to be switched off by the controller&#41;
&gt; no JLink control possible
The power supply is ok, 1,8V from internal regulator are ok, too.
There is no possibility to restart the system without cutting the power line.
regards
Rudi
