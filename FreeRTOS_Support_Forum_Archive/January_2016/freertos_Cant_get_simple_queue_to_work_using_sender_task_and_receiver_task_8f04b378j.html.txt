</div></div><div class="thread-post"><h3 class="thread-post-title">Can&#8217;t get simple queue to work using sender task and receiver task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 23, 2016</div><div class="thread-post-content">It is not clear what you are asking.  If I were to rephrase it as the following, would I be correct?
&#8220;I have two low priority tasks that constantly write to a queue without blocking, and a high priority task that blocks reading from the queue with a 100 tick time out.  As the low priority tasks are running continuously without blocking I would never expect the 100 tick time out to expire, but it does, what could be the reason for this&#8221;?
A brief look at your code shows two potential issues.
First you are declaring a block scope variable sender<em>one (same goes for sender</em>two), then passing the address of this variable into the task.  The task then uses the address of a block scope variable &#8211; so the address of a variable that doesn&#8217;t really exist any more.  On the AVR that may be ok, as I don&#8217;t think the memory used by main() is then re-used, but on something like a Cortex-M this will definitely cause you a problem as the memory used by main() is then re-used by interrupts.
The other potential issue is more subtle, and that is how you are using pointers.  This can can get quite confusing, but really is a C issue, rather than a FreeRTOS issue.  In the task you have a local varaible msg, and you pass the address of msg into the queue send function.  That means the queue will copy 1 byte (as the queue item size is one) from the address of the variable (which is an address on the task stack) rather than from the address msg is pointing to.  msg is pointing to the variable that you have set with your buzzer on/off code.
It might be easier then to copy the buzzer on/off value into the task using the task parameter, rather than the address of a variable that is set to the value.  For example:
In main:
~~~~
char sender_one = 1;
/* Cast the value 1 to a void *, so it can get passed into 
the xTaskCreate() function, rather than passing in the 
address of the variable. <em>/
xTaskCreate(task_sender, NULL, 50, (void</em>)sender_one, 1, NULL);
~~~~
In your task:
~~~~
void task_receiver(void *pvParameters)
{
    /* Cast the value back from a void * to an integer (char). */
    char msg = (char) pvParameter;
<pre><code>/* This time, msg holds the value 1, not the address of 
another variable, so now it IS valid to pass the address of
msg into the xQueueSendToBack() function. */
xQueueSendToBack(my_queue, &amp;msg, 0);
</code></pre>
~~~~
This should fix both the potential issues highlighted above, and simplify the code.

</div></div><div class="thread-post"><h3 class="thread-post-title">Can&#8217;t get simple queue to work using sender task and receiver task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 23, 2016</div><div class="thread-post-content">A couple of notes, although I&#8217;m not sure which FreeRTOS version you are 
using.  Note after fixing the first point below, I was able to run your 
code (using a different FreeRTOS port) without any problems &#8211; it behaved 
as expected and the queue was never empty:
<ul>
<li>You can&#8217;t use NULL as the text name for the tasks being created 
(second parameter to xTaskCreate()).  That will cause a NULL pointer to 
be dereferenced.</li>
<li>Did you check the return values of xTaskCreate() to check the tasks 
are being created, or step through the code to check the tasks are being 
created as expected?</li>
<li>Do you have configASSERT() defined, the stack overflow checks turned 
on, the malloc failed hook defined, etc?</li>
<li>portTickType was deprecated some time ago, it is recommended to use 
TickType_t instead.</li>
<li>portBASE<em>TYPE was deprecated some time ago, it is recommended to use 
BaseType</em>t instead.</li>
</ul>
