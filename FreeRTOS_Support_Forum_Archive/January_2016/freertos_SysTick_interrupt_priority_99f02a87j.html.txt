  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">SysTick interrupt priority</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/samfpetersen">samfpetersen</a> on January 6, 2016</div><div class="thread-post-content">I&#8217;m using FreeRTOS V8.2.1 on STM32F4 and my question is about the SysTick interrupt priority. The FreeRTOS source says that it should be the &#8220;lowest priority interrupt&#8221;, and it explicitly sets it to the lowest priority in xPortStartScheduler(). This seems backwards to me, shouldn&#8217;t it be the highest? 
Further complicating things is the STM32&#8217;s HAL libraries, which have their own systick implementation&#8230; It specifies that you should set the systick interrupt to the highest priority.
By the way, I&#8217;m referring to logically highest not numerically highest, and I&#8217;m aware that they are inverted
Thanks,
Sam
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 6, 2016</div><div class="thread-post-content">The interrupt that absolutely must be the lowest priority is the PendSV interrupt.  The SysTick interrupt could be higher, but could interfer with application interrupts if it is.
When the ST HAL is used with FreeRTOS, like it can be with the STM32 Cube software supplied by ST, then ST call the FreeRTOS tick handler from their HAL tick handler.  That means you must not install the FreeRTOS handler.  However, I do it the other way around &#8211; installing the FreeRTOS handler as normal, then calling the HAL tick handler from the FreeRTOS tick hook function.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 7, 2016</div><div class="thread-post-content">Actually &#8211; I would like to correct my previous post.  The SysTick handler does need to run at the lowest priority.  This is because the critical section within the handler itself assumes it is running at the lowest priority, so saves time by not saving the old priority mask and then restoring the previous priority mask.
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/samfpetersen">samfpetersen</a> on January 8, 2016</div><div class="thread-post-content">The conflict I encounter is that the ST HAL SysTick must be at the highest priority, since there are HAL layer ISRs that wait on a timeout (which is bad, but it is what it is). So to fix this, I&#8217;m setting the SysTick interrupt to the highest priority, and in that ISR I&#8217;m calling the ST HAL tick function and setting another interrupt at the lowest priority. In the ISR of that interrupt, I&#8217;m calling the FreeRTOS tick function.
Seems hacky, but I can&#8217;t think of a better way to do this at the moment. Thoughts?
Thanks,
Sam
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/janoshnosh">janoshnosh</a> on November 9, 2016</div><div class="thread-post-content">@Sam Petersen
I totally agree with that strategy. I have no understanding for why the SysTick interrupt should be of lowest priority. In my opinion, FreeRTOS wouldn&#8217;t have anything to do with a real-time system anymore, if it doesn&#8217;t keep counting milliseconds.
We have the same issue here, that the HAL-ISR-delays make all time calculations based on the FreeRTOS tick invalid. And ridiculous.
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/owainkopin">owainkopin</a> on December 22, 2017</div><div class="thread-post-content">@Richard Barry
what is logic of having systick as lowest priority isr?
Surely systick is used for driving timers on various semaphore/mailbox operations that may time out; and also scheduler is run off the back of the systick. Is not systick kind of the God process controlling just about everything?
I can also see the view that we may have processes run off the back of ISR&#8217;s that must be serviced in a timely fashion independent of the RTOS; they may be higher priority than systick. But ISR&#8217;s that are posting semapores etc; should they not run lower  than systick?
I am working on a system with around 10 isr sources; these are currently all higher priority than systick and I regularly see the systick being preempted. As a general rule of thumb is it not better to let systick run; do its stuff and then process other isrs?
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on December 22, 2017</div><div class="thread-post-content">I think it is only the PenSV that needs to run at the lowest priority, 
it is just recommended to run SysTick at the lowest too to leave a lot 
of higher priority interrupts available for applications that require 
them to be more real time (deterministic).  Some libraries (STM32Cube?) 
poll the tick inside an ISR (not good practice in my humble opinion) in 
which cases having the tick at the lowest priority can actually cause a 
deadlock.  It is also generally more efficient if the tick is only 
incremented after other interrupts have completed, rather than intermix 
ISRs that are using the time and having the time changing.
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/karltsai">karltsai</a> on April 23, 2018</div><div class="thread-post-content">I&#8217;m new to this and here is my strategy:
<ol>
<li>install the FreeRTOS systick handler and bump it to higher priority that HAL requires</li>
<li>make sure the priority mask and whatever house-keeping necessary are done properly in tje systick handler</li>
<li>rewrite/overwrite HAL<em>Delay and HAL</em>GetTick functions to use FreeRTOS version. Both of them are <strong>weak</strong> so not a problem. There is no need to keep 2 sets of system ticks </li>
</ol>
Can someone see any problem of this approach?
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 23, 2018</div><div class="thread-post-content">First, I&#8217;m guessing you are using STM32.  Is that correct?
Second &#8211; what is it you are trying to do?  If you want to use both the 
ST drivers and FreeRTOS at the same time then the ST way of doing that 
is to call the FreeRTOS tick handler from their tick handler.  The 
FreeRTOS way of doing it is to install its own tick handler (SysTick) 
then call the ST handler from the FreeRTOS tick hook function.  Either 
way, if you are using the ST driver, it is likely you are going to need 
both to execute.
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/karltsai">karltsai</a> on April 23, 2018</div><div class="thread-post-content"><ol>
<li>yes that is the case</li>
<li>I understand both approaches. calling from HAL leaves FRTOS vounerable as it didn&#8217;t have enough protection running in higher priority. calling from FRTOS breaks the HAL when it is expecting tick count to increment which never does unless the FRTOS priority is bumped.</li>
<li>I&#8217;m trying to address both problems in a seamless  way. i.e.: with minimal impact to HAL as well as FreeRTOS code base.</li>
</ol>
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 23, 2018</div><div class="thread-post-content">Unfortunately I think it is necessary to bump the SysTick priority up 
when using the HAL drivers as some wait for the tick count to change 
from within HAL interrupts themselves (not something that would normally 
be recommended).
</div></div><div class="thread-post"><h3 class="thread-post-title">SysTick interrupt priority</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/karltsai">karltsai</a> on April 23, 2018</div><div class="thread-post-content">this is the rewrite to break the barrier between HAL and FRTOS
<h1>include &lt;FreeRTOS.h></h1>
<h1>include &lt;task.h></h1>
// HAL<em>Delay is used mostly in device init and config
void HAL</em>Delay(uint32_t Delay)
{
    vTaskDelay(Delay);
}
uint32<em>t HAL</em>GetTick(void)
{
    return xTaskGetTickCount();
}
