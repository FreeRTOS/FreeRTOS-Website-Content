  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">How to get a list of all task handles?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/helliwell_cj">helliwell_cj</a> on January 4, 2016</div><div class="thread-post-content">I&#8217;m implementing a watchdog function, whereby each task &#8216;checks in&#8217; (to indicate it is still alive) by setting a flag/variable; the watchdog monitor periodically makes sure all the current tasks have checked in and, if so, resets the cpu watchdog time and clears the flags.
I&#8217;ve got the mechanism basically working, but the monitor needs to know how many and/or which tasks it should expect to hear from. Currently I&#8217;ve used uxTaskGetSystemState(), but it&#8217;s causing me to miss some UART interrupts [yes, I&#8217;m aware that this function is only recommended for debugging].
So is there a neater/faster way to get a list of task handles? I don&#8217;t need much of the stuff that uxTaskGetSystemState() does (and which presumably cause the lengthy scheduler suspension) &#8211; I just need to be able to walk through the list and examine a couple of variables of each TCB.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to get a list of all task handles?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on January 4, 2016</div><div class="thread-post-content">uxTaskGetSystemState() is the normal way, but if it is causing a problem, then how about having your tasks register with the watchdog management task when they are create? That can be done manually by the task implementer or automatically using the trace macros that execute when a task is created and deleted.
</div></div><div class="thread-post"><h3 class="thread-post-title">How to get a list of all task handles?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/helliwell_cj">helliwell_cj</a> on January 4, 2016</div><div class="thread-post-content">Yes, I&#8217;d starting wondering &#8211; if there&#8217;s no other mechanism already there to use &#8211; about patching into the create/delete. I am using Trace functionality too though, so I&#8217;d need to wrap <em>extra</em> into the trace macros. Doing it &#8216;manually&#8217; could be a bit too much of a risk [of forgetting].
I did also wonder about simply adding my own function to tasks.c  &#8211; not ideal but, given that I&#8217;d need to modify the trace macros anyway, may be just as clean a solution? Bit of a headache to keep re-patching into future updates, though we won&#8217;t be upgrading the RTOS too often. 
</div></div><div class="thread-post"><h3 class="thread-post-title">How to get a list of all task handles?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/helliwell_cj">helliwell_cj</a> on January 4, 2016</div><div class="thread-post-content">Just for potentially useful info for others: 
uxTaskGetSystemState() is taking about ~2ms to execute on my system; with 10 tasks running. The bulk of this time is in finding the stacks&#8217; high water marks (prvTaskCheckFreeStackSpace) &#8211; commenting this out drops the execution time to ~20us.
