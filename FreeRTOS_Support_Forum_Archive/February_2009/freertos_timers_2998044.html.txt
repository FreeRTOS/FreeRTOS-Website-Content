</div></div><div class="thread-post"><h3 class="thread-post-title">timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 6, 2010</div><div class="thread-post-content">I should have provided some explanation as to why timers are not there currently..  
The primary reason is that they are very difficult to implement in a deterministic and most importantly efficient way. There are on the other had very easy to implement indeed if you are not concerned with those kernel attributes in an particular application, but core code has to be more generically applicable.  
Most dynamic timer implementations &#40;where a timer can be created and destroyed at run time&#41; require such timers to be stored in a linked list of one form or another &#8211; and accessing the timers from both interrupt code and task code means that their data structures have to be protected with a critical section. Also, timer lists by their nature are normally traversed within the tick interrupt. For the reasons mentioned above &#40;interrupt responsiveness and determinism&#41; there is nowhere in the FreeRTOS code where linked lists are traversed while interrupts are disabled.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/larytet">larytet</a> on December 7, 2010</div><div class="thread-post-content">I appreciate the feedback. I am not going to implement POSIX timers. Not in this development cycle.  
Regarding performance I will avoid any not O&#40;1&#41; operations. Definitely no per tick traversing of the list of running timers is going to happen. Timer task&#40;s&#41; is going to sleep until the next timer expires. The suggested API will cover some rather large segment of application which require<br />
&#45; multilple coexisting timers<br />
&#45; timeout&#40;s&#41; known at compilation time<br />
&#45; set of different timers &#40;different timeouts&#41; is relatively small  
See below application notes<br />
&#42;&nbsp;&nbsp; The system requires multiple &#40;more than one&#41; started timers with the same timeout. If your<br />
&#42;&nbsp;&nbsp; system needs only one or two timers at any moment it is easier to use tick hook. Typical<br />
&#42;&nbsp;&nbsp; application &#8211; data transfer timers serving multiple connections &#40;sockets&#41;.<br />
&#42;<br />
&#42;&nbsp;&nbsp; In the system run one or more timers tasks handling different timer sets. Every timer<br />
&#42;&nbsp;&nbsp; set contains one or more timer lists.<br />
&#42;<br />
&#42;&nbsp;&nbsp; Function StartTimer allocates free entry from the stack of free timers and places<br />
&#42;&nbsp;&nbsp; the timer in the end of the timer list &#40;FIFO&#41;. Complexity ~O&#40;1&#41;<br />
&#42;<br />
&#42;&nbsp;&nbsp; Timer task waits for the expiration of the nearest timer, calls application handler<br />
&#42;&nbsp;&nbsp; TimerExpired, find the next timer to be expired using sequential search in the<br />
&#42;&nbsp;&nbsp; set &#40;always the first entry in a timer list&#41;. Timer task removes stopped timers from<br />
&#42;&nbsp;&nbsp; the list of running timers and returns the timers to the pool of free timers.<br />
&#42;&nbsp;&nbsp; Complexity ~ O&#40;size of set&#41;<br />
&#42;<br />
&#42;&nbsp;&nbsp; Function stop timer marks a running timer as stopped. Complexity ~O&#40;1&#41;  
Thank you, Arkady.
</div></div><div class="thread-post"><h3 class="thread-post-title">timers</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/larytet">larytet</a> on December 7, 2010</div><div class="thread-post-content">Part II.  
For some reason my previous reply failed to appear here.   
I am trying to cover as many different scenarios as possible. For example, I let the application to avoid interrupt/task scheduler disable/enable operations by allowing to handle timers expiration and start/stop in the some context. Not every application will be designed this way, but this is definitely a good alternative to consider. The API allows to use a dedicated timer task or a timer interrupt.  
I am investing significant effort in compilation time configuration.   
Definitely this API is not for each and every case.   
It is not generic enough if the application demands timers with precise&nbsp; &#40;no rounding is possible&#41;&nbsp; and arbitrary timeout. Such application requires some form of ordered by expiration time list of timers. Complexity of the start timer will likely not be O&#40;1&#41;.  
The API is not simple and small if the application requires only one or two timers which always expire &#40;I think that there is a clever solution for this, but I need more time&#41;.  
I need your help with the system requirements, different application designs &#40;link task or interrupt&#41; and so on.  
Thank you, Arkady
