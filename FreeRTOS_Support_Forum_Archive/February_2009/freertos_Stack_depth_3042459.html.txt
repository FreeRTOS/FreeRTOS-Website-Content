  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Stack depth</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on February 25, 2009</div><div class="thread-post-content">Are there any metrics to know the maximum stack depth of freeRTOS, provided that all the parameters are passed on the stack and not in registers?
I mean, which is the maximum stack usage of the longest call chain of the freeRTOS functions?
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack depth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on February 25, 2009</div><div class="thread-post-content">The configMINIMAL&#95;STACK&#95;SIZE setting is a good indication. This is the stack size allocated to the idle task &#40;which does not use much stack at all&#41; but also most of the demo tasks. The demo tasks exercise all the FreeRTOS functions.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack depth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on February 26, 2009</div><div class="thread-post-content">Ok, but the idle task does not use much of the freeRTOS services, so it is unlikely that it will use the maximum stack size needed by the most task consuming kernel service.
So, if all the parameters to the freeRTOS service functions are passed on the stack, and further, all the parameters from the service to internal functions are again passed on the stack, which, in turn, allocate local variables on the stack&#8230; Is there any way to know which is the longest or the most stack-consuming call chain given these hypotheses?
My compiler is capable of passing some of the parameters in registers&#40;up to 8 bytes&#41;, but due to the need of interfacing user-mode application with the system-mode kernel through a trap I cannot use register calling convention, but instead I need to use the stack.
So, for example, I call xTaskCreate, passing its parameters on the stack. This function stores local variables on the stack but it also calls other functions, which will further load the stack.
Of course, the size of the return addresses are architecture dependent, so there is practically no way to include them in the stack usage estimation. All I&#8217;m interested in is the size taken by the parameters and local variables.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack depth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 26, 2009</div><div class="thread-post-content">&gt; Ok, but the idle task does not use much of the freeRTOS 
&gt; services, so it is unlikely that it will use the maximum 
&gt; stack size needed by the most task consuming kernel service.
Agreed, but I think the main point of edwards3 post is that the demo app tasks also use this as the stack size and these use all the FreeRTOS services.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack depth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on February 26, 2009</div><div class="thread-post-content">Ok, so I&#8217;ll just have to look for the configMINIMAL&#95;STACK&#95;SIZE of an architecture similar to mine&#40;NXP 51XA&#41; and then do some probabilistic/statistic/estimatory math.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack depth</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/incrediball">incrediball</a> on February 26, 2009</div><div class="thread-post-content">Alternatively you could create stack sizes that are easily large enough, run the program with the stack highwater function enabled, throw everything imaginable at your program and after you&#8217;re satisfied that the program has run long enough, look at how much stack has been used. Using these results you can then fine tune the stack sizes.
I know this approach is not 100% sure but there are problems with calculating it out on a theoretical basis:
1&#46; Mistakes are easily made and certain factors &#40;e.g. interrupts&#41; can be overlooked. I wouldn&#8217;t trust a calculation unless I can perform such a test run and get comparable results.
2&#46; You cannot make any changes to your program, or ever upgrade to a new version of FreeRTOS, without having to recalculate everything.
