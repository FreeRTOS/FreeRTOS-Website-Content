  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">+ TCP uxNxWinSize</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on June 14, 2018</div><div class="thread-post-content">Could I get a bit an explanation on WinProperties_t Rx and Tx WinSize?
Coming from a different IP stack, I&#8217;m having a hard time following why this is specified in MSS.
For example, I have a socket that I want the rx buffer size at 1,048,576, or 1mb.  This would translate to a window scale of 4 in tcp language.  However, 1048576 / 1460 = 718, so I&#8217;m not following exactly how this number is being used, as the examples don&#8217;t use numbers this high.
</div></div><div class="thread-post"><h3 class="thread-post-title">+ TCP uxNxWinSize</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 14, 2018</div><div class="thread-post-content">A TCP conversation is parametrised by a few variables:
<ul>
<li>MSS, Maximum Segment Size, which is the size of the TCP payload. Often this is 1460 bytes long</li>
<li>TCP window sizes</li>
<li>TCP buffer sizes ( which is an internal thing )</li>
</ul>
When you communicate through a LAN, it does not make much sense to have a window size longer than 8 to 12 times MSS ( 11680 to 17520 bytes ).
Your question is why the TCP window size is defined as a multiple of MSS: the answer is efficiency.
Suppose that there is a constant stream of data, and that the window size is 4 KB, then you will often see half-filled Ethernet packets. If the window size is 3 x MSS ( 4380 bytes ), than you will see that all packets are 100% filled.
Buffer sizes are expressed in bytes, so you have total freedom.
If you make a big TCP window like 1 MB, a scale factor will be used, and the window size will not be an exact multiple of MSS, due to rounding.
Why do you choose 1 MB? Do you expect a better performance compared to a size of e.g. 12 times MSS ?
</div></div><div class="thread-post"><h3 class="thread-post-title">+ TCP uxNxWinSize</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on June 15, 2018</div><div class="thread-post-content">My communication is not on a lan, it is a streaming audio device, and really needs to work without skips where internet isn&#8217;t so great.  A larger tcp window combined with other internal buffering really helps.  Perhaps 1mb is overkill, but it has worked.
I think I follow now, so really window scaling happens depending on the WinSize.  The microchip stack I have been using has it that the tcp buffer size is the same as the window size, thus this seemed confusing that the window size is smaller than the buffer size.
</div></div><div class="thread-post"><h3 class="thread-post-title">+ TCP uxNxWinSize</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 15, 2018</div><div class="thread-post-content">You don&#8217;t need a TCP window as big as your buffering time. You could buffer a couple of seconds of video in your application, while the TCP layer uses a smaller window. This might actually improve performance as if an earlier packet was lost you want to re-request it before you actually need it, so you can have it (you don&#8217;t need much more buffer than the round trip delay time). The additional application buffer smooths out the varying quality of the connection, No amount of buffering (except down load the whole stream then play it) will get you skipless streaming if the connection can&#8217;t handle the needed rate, at least on average.
</div></div><div class="thread-post"><h3 class="thread-post-title">+ TCP uxNxWinSize</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 15, 2018</div><div class="thread-post-content"><blockquote>
   The microchip stack &#8230; the tcp buffer size is the same as the window size
</blockquote>
That is probably where your confusion comes from.  In +TCP, these parameters are separated.
Richard Damon is right: it is more advantageous to have a reasonable sized TCP window, and keep audio data buffered.
It is up to you how much data must be in the buffer before you start the player.
The FreeRTOS+TCP stack can buffer TCP data for you.  You can poll how much data is available in the buffer with this function:
~~~
    BaseType<em>t FreeRTOS</em>rx<em>size( Socket</em>t xSocket );
~~~
My advice for your streaming client would be the following:
~~~
    xWinProperties.lRxBufSize = 1024 * 1024;  /* 1 MB, or more <em>/
    xWinProperties.lRxWinSize = 12;           /</em> 12 packets <em>/
    xWinProperties.lTxBufSize = 6 * 1024;     /</em> 6 KB <em>/
    xWinProperties.lTxWinSize = 2;            /</em> 2 packets */
~~~
You may want to wait until the RX buffer is filled 80% and start playing the sound.
If your Internet connection is not so good, the IP stack may decide to decrease the size of the advertised TCP window.  Using a large TCP window may lead to a chaotic conversation with many retransmissions and Selective Acknowledgements ( SACK&#8217;s ).  If there are many dropped packets, a window size of 4 x MSS or less would be better.
