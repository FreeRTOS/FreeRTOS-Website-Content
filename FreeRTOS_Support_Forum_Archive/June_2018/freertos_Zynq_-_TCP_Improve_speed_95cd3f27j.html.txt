  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Zynq &#8211; TCP: Improve speed </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hannes23">hannes23</a> on June 20, 2018</div><div class="thread-post-content">Hello,
herewith I&#8217;d like to share my experience with improving the TCP communication.
In my case I could get more than 20 % gain in TCP speed at 1000 Mbps.
Following things are necessay: 
1st: Re-map the OCM (on-chip-memory) from bottom to top of address-space.
2nd: Force the linker to place the ucNetworkPackets &#8211; buffers into the OCM space.
The remapping is done by a macro calling some certain assembler code directly
after starting in main().
My code is :
int main( void )
{
    xil<em>printf( &#8220;Hello from FreeRTOS mainrn&#8221; );
        configASSERT( configUSE</em>TASK<em>FPU</em>SUPPORT == 2 );
    xil<em>printf( &#8220;configUSE</em>TASK<em>FPU</em>SUPPORT (FreeRTOS.h) is set to %drn&#8221;, configUSE<em>TASK</em>FPU_SUPPORT );
<pre><code>    // Remap all 4 64KB blocks of OCM to top of memory and enable DDR address filtering
    MY_REMAP();
...
...
</code></pre>
The configUSE<em>TASK</em>FPU_SUPPORT &#8211; part could of course be omitted if not used.
The code (found somewhere in the Xilinx forum)  for the MY_REMAP() define is:
<h1>define MY_REMAP()   <strong>asm</strong> <strong>volatile</strong>(</h1>
<pre><code>"mov  r5, #0x03                                           n"
"mov  r6, #0                                              n"
"LDR  r7, =0xF8000000  /* SLCR base address    */         n"
"LDR  r8, =0xF8F00000  /* MPCORE base address  */         n"
"LDR  r9, =0x0000767B  /* SLCR lock key        */         n"
"mov  r10,#0x1F                                           n"
"LDR  r11,=0x0000DF0D  /* SLCR unlock key                 n"
"dsb                                                      n"
"isb                   /* make sure it completes */       n"
"pli  do_remap     /* preload the instruction cache */    n"
"pli  do_remap+32                                         n"
"pli  do_remap+64                                         n"
"pli  do_remap+96                                         n"
"pli  do_remap+128                                        n"
"pli  do_remap+160                                        n"
"pli  do_remap+192                                        n"
"isb                   /* make sure it completes */       n"
"b    do_remap                                            n"
".align 5, 0xFF         /* forces the next block to a cache line alignment */ n"
"do_remap:              /* Unlock SLCR                         */ n"
"str  r11, [r7, #0x8]   /* Configuring OCM remap value         */ n"
"str  r10, [r7, #0x910] /* Lock SLCR                           */ n"
"str  r9,  [r7, #0x4]   /* Disable SCU &amp; address filtering     */ n"
"str  r6,  [r8, #0x0]   /* Set filter start addr to 0x00000000 */ n"
"str  r6,  [r8, #0x40]  /* Enable SCU &amp; address filtering      */ n"
"str  r5,  [r8, #0x0]                                             n"
"dmb                                                              n"
</code></pre>
   );
Next step is to create a memory section &#8220;.ocm&#8221; by changing the linker-desciption file.
Following changes are to be done:
In the memory section add:
   ps7_ocm  : ORIGIN = 0xfffc0000, LENGTH = 0x3fe00
In the section description add:
.ocm (NOLOAD) : {
   __ocm<em>start = .;
   *(.ocm)
   __ocm</em>end = .;
} > ps7_ocm
Final step is to inform the buffer definition, that the buffers should be placed into the ocm.
In file: NetworkInterface.c add the ocm-section attribute. It then should be:
static uint8<em>t ucNetworkPackets[ ipconfigNUM</em>NETWORK<em>BUFFER</em>DESCRIPTORS * niBUFFER<em>1</em>PACKET_SIZE ] <strong>attribute</strong> ( ( aligned( 32 
) ) ) <strong>attribute</strong> ((section (&#8220;.ocm&#8221;)));
After compile and link one could inspect the map-file to see, if the ocm section is successful generated and populated.
It looks like:
.ocm            0x00000000fffc0000    0x30000
                0x00000000fffc0000                __ocm<em>start = .
 *(.ocm)
 .ocm           0x00000000fffc0000    0x30000 ./src/Ethernet/FreeRTOS-Plus-TCP/portable/NetworkInterface/Zynq/NetworkInterface.o
                0x00000000ffff0000                __ocm</em>end = .
All hints and changes are of course without my responsibility and warrenty
If anybody has other or additional changes or hints to improve the speed in TCP communication let me please know.
Especially someone could comment, if it makes sense to push other buffers or variables into the ocm.
Greetings to all.

here are the results of the iperf3 tests I&#8217;ve done at my Zynq7000, running at 666MHz.
First I had to change the ip-address and port-number according to needs of our firewall.
Then I got a stack-fault. Maybe that some other tasks wich are running on my system caused this.
These other tasks don&#8217;t use much CPU time, I believe, so I didn&#8217;t change the software for the iperf tests.
After setting the stack-size to 1000 everything was fine.
Next I changed the window- and buffer settings to those values I used at my HTTP-server work.
The code after change is:
<h1>ifndef ipconfigIPERF<em>TX</em>BUFSIZE</h1>
<h1>define mySETTINGS</h1>
<h1>ifdef mySETTINGS</h1>
<pre><code>#define ipconfigIPERF_TX_BUFSIZE                ( 128 * 1024 )
#define ipconfigIPERF_TX_WINSIZE                ( 48 )
#define ipconfigIPERF_RX_BUFSIZE                ( ( 80 * 1024 ) - 1 )
#define ipconfigIPERF_RX_WINSIZE                ( 24 )
</code></pre>
<h1>else</h1>
<pre><code>#define ipconfigIPERF_TX_BUFSIZE                ( 65 * 1024 )   /* Units of bytes. */
#define ipconfigIPERF_TX_WINSIZE                ( 4 )           /* Size in units of MSS */
#define ipconfigIPERF_RX_BUFSIZE                ( ( 65 * 1024 ) - 1 )   /* Units of bytes. */
#define ipconfigIPERF_RX_WINSIZE                ( 8 )           /* Size in units of MSS */
</code></pre>
<h1>endif</h1>
<h1>endif</h1>
By the way: Why should or must the RX_BUFSIZE be uneven?
I&#8217;ve done tests with original bufsizes with and without -R, and also tests with my settings, also both variants.
Finally I did the concurrent test as you supposed and saw that indeed the performance of the one without -R really

</div></div><div class="thread-post"><h3 class="thread-post-title">Zynq &#8211; TCP: Improve speed </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 2, 2019</div><div class="thread-post-content">HI Johannes, I finally solved the problem of the lost packets during concurrent transmissions.
See [this post] (https://sourceforge.net/p/freertos/feature-requests/126/)
See x<em>emacpsif</em>dma.c in the function <code>emacps_send_message(()</code>, it is very essential to read back the register that was just set:
~~~
    XEmacPs<em>WriteReg( ulBaseAddress, XEMACPS</em>NWCTRL<em>OFFSET, xxx );
+    /* Reading it back is important compiler is optimised. */
+    XEmacPs</em>ReadReg( ulBaseAddress, XEMACPS<em>NWCTRL</em>OFFSET );
~~~
Now I started two concurrent sessions with iperf3, and both transported an equal amount of data.
This is <a href="https://sourceforge.net/p/freertos/feature-requests/_discuss/thread/1db9fcdb13/dc97/attachment/Zynq_2019_march_01.7z">the new Zynq driver</a>
