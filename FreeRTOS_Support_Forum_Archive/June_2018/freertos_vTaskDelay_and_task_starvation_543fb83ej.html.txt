  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vTaskDelay and task starvation</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nndpkz">nndpkz</a> on June 5, 2018</div><div class="thread-post-content">Hi, 
I have rather simple question which is probably due to my misunderstanding of basic RTOS scheduling. If 2 tasks like this:
~~~
void task1()
{
    while(1) {
        xil<em>printf(&#8220;1&#8221;);
        vTaskDelay( pdMS</em>TO_TICKS( 1000UL ) );
    }
}
void task2()
{
    while(1) {
        xil_printf(&#8220;2&#8221;);
    }
}
~~~
are run with same priorites, I&#8217;ve noticed that task1 will never be executed due to delay. Once I remove delay, the processing time between tasks is divided as expected. 
Can anyone explain me this? 
Best regards,
Nenad
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelay and task starvation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcrocker">dcrocker</a> on June 5, 2018</div><div class="thread-post-content">Richard will probably provide a detailed explanation of what is going on. However, it looks to me that you are relying solely on the tick interrupt to share CPU time between the two tasks. This is rarely a good idea. If the printf function includes a mutex to prevent the output getting garbled, then most times the tick interrupt occurs, task2 will own that mutex so task1 can&#8217;t be scheduled.
I would try one or both of the following to resolve the problem:
<ol>
<li>Increase the priority of task 1. It spends most of its time delaying, so you can do this without starving task 2 of CPU time.</li>
<li>Add a taskYIELD call at the bottom of the task2 loop, so that you are not relying solely on the tick interrupt to schedule CPU time between it and other tasks of equal priority.</li>
</ol>
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelay and task starvation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 5, 2018</div><div class="thread-post-content">As per David&#8217;s reply &#8211; a lot will depend on how the xil<em>printf() is 
implemented.  Is it thread safe?  If so, how is it made thread safe (see 
David&#8217;s reply).  If it&#8217;s not thread safe, then what you are doing is 
dangerous as any state inside xil</em>printf() (like its access to whichever 
console you are writing to) could get corrupted &#8211; even if no data gets 
corrupted you could get strings interleaved at the output as you are 
printing from two tasks simultaneously.  Does xil_printf() block (not 
return until all data has been output)?  If so, then your application 
will be running extremely slowly.  Etc.  A good proportion of support 
requests that have a call to printf() in them are caused by the printf() 
call itself.  You can serialise print output by having a logging task &#8211; 
when a task wants to print something it writes the message it wants to 
print to a queue and the logging task reads the data from the queue and 
writes it to the output port at a very low task priority.
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelay and task starvation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nndpkz">nndpkz</a> on June 6, 2018</div><div class="thread-post-content">Hi guys,
thank you for your help. It seems indeed that this was the problem with xil<em>printf() after all. I made another quick test such as: 
~~~
void task1()
{
    while(1) {
        xil</em>printf(&#8220;1&#8221;);
        vTaskDelay( pdMS<em>TO</em>TICKS( 1000UL ) );
    }
}
void task2()
{
    int i = 0;
    while(1) {
        i++;
    }
}
~~~
and both tasks were executing expected (I checked task2 in debug mode). Also, if there isn&#8217;t any call to xil_printf in task1 neither, than it also executes as expected. 
Best regards,
Nenad
