</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 10, 2018</div><div class="thread-post-content">The TimerCallback function is given the handle to the Timer that fired, and that handle has a void* pointer that the application can use to store information for its use. You could set that to the task handle when creating the timer, and then the timer callback could get that.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michaeln32">michaeln32</a> on June 11, 2018</div><div class="thread-post-content">Thanks Richard.

</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 11, 2018</div><div class="thread-post-content">My comment is that you don&#8217;t need to add a new item to the struct, it already has a void* pointer in it that is for the use of the user. YOU just need to make sure that when you create a timer you assign it to the creating tasks handle, then the timer call back can get that handle.
The create timer functions prototype is:
TimerHandle<em>t xTimerCreate
                 ( const char * const pcTimerName,
                   const TickType</em>t xTimerPeriod,
                   const UBaseType<em>t uxAutoReload,
                   void * const pvTimerID,
                   TimerCallbackFunction</em>t pxCallbackFunction );
 That pvTimerID parameter is for YOU to use, it sounds like you want to make it the handle of the task creating the timer.
 The timer callback function then just needs to call pvTimerGetID() on the timer handle it was passed to itself to get that value.

</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 12, 2018</div><div class="thread-post-content">xTimerCreate doesn&#8217;t end in FromISR, so it shouldn&#8217;t be called from an ISR.
Since creating a timer will allocate memory for the timer, this really isn&#8217;t something to be done in an ISR.
xTimerCreate() can (and I often do) be called before the scheduler starts, so before tasks start to run.
Deleting a task does NOT delete anything that it created, because FreeRTOS doesn&#8217;t track that sort of thing, and more importatly because it is quite possible for one task to create various resources that other tasks may use. There is not any natural connection of the creator of a timer and the timer itself. If it creates a timer, the timer will continue to operate even after the task is gone.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michaeln32">michaeln32</a> on June 13, 2018</div><div class="thread-post-content">Thank you Richard for your good and helpful answers.
The timer service task will run (be in running state) when a timer expired.
The timer greated by a task or by main (before scheduler run) using the API xTimerCreate().
Are there more resons that causes the timer service task to run that are not retelted to xTimerCreate() ?
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerCreate</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 13, 2018</div><div class="thread-post-content">The Timer Service Tasks needs to run (for a very short time) everytime you adjust the state of a timer (start, stop, restart, etc) as these operations put a command on the Timer Queue for the Timer Service Task to perform these operationss.
The Timer Service Task also handles requests from xTimerPendFunctionCall and xTimerPendFunctionCallFromISR, and those pended function run just like timer callback in the context of the Timer Service Task.
The Timer Service Task will run any time a timer callback is needed to run, and that callback is run in the contex of the Timer Service Task.
One way to think of the Timer Service Task is that it waits on  the Timer Request Queue for commands (Start/Stop /Change requests on Timers and Pend Function requests) with a timeout value such that it also wakes up to call timers callbacks as their time expires.
