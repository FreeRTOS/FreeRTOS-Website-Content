</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on June 3, 2018</div><div class="thread-post-content">Sure, the handle can be <code>static</code>. It&#8217;s just a (pointer) variable.
Alternatively you could use <code>xSemaphoreCreateMutexStatic</code> defining  the mutex itself with static resp. provided storage.
I don&#8217;t understand your intention of declaring a handle <code>volatile</code>. It&#8217;s usually not needed.
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michaeln32">michaeln32</a> on June 3, 2018</div><div class="thread-post-content">Thank you HS2.
I want to define SEMA static becase I want to use this semaphore only in one file (the file it is defined).

Can you please give your opinion on the thinks above ?
thank you 
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 3, 2018</div><div class="thread-post-content">The volatile protects against optimization of changes to the SEMA variable, which likely should only change once, when the semaphore is created. If it is created after the scheduler is started, and a task other than the one that creates the semaphore is looking at the handle to see if the semaphore has been created before it has been created, then you want the volatile. 
I personally try to create all my semaphores (and similar objects) before I start the scheduler, or at least before any task that want to use them to avoid the need to check and wait/skip on their existance, at which point I don&#8217;t need the volatile, since it never changes on anything that can&#8217;t see the creation directly.
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on June 3, 2018</div><div class="thread-post-content">Declaring a variable  <code>volatile</code> tells the compiler, that this variable might get  changed from outside the current flow of execution as visible to the compiler.
This is especially needed for memory mapped hardware (e.g. registers) which might get changed without notice of the software but by external hardware. Hence the compiler must generate code to do a full &#8216;memory&#8217;  i.e. hardware access (to a register) and shouldn&#8217;t optimize this access by caching it&#8217;s value into a processor register and just use it later on.
Don&#8217;t use <code>volatile</code> for inter-task synchronisation as it&#8217;s simply not intended for that purpose !
As Richard said, ensure that globally used or shared resources like semaphores used by different tasks or a task and an ISR are created before getting used.
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michaeln32">michaeln32</a> on June 3, 2018</div><div class="thread-post-content">Thank you Richard

</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 3, 2018</div><div class="thread-post-content">I would disagree with &#8216;Don&#8217;t use volatile for inter-task synchronisation as it&#8217;s simply not intended for that purpose!&#8217;. In the Standard, volatile means the variable needs to be treated as if it might change by means outside of the local code, which would include another task. so it can be useful for this. (on multi-core processors, which aren&#8217;t the targer for FreeRTOS it might not be sufficient, as you may also need some hardware memory barriers, but those aren&#8217;t needed for a single core processor). One common use for something like this would be to set an &#8216;alert&#8217; variable for a task, that it periodially checks while it is doing some long operaton to see if it needs to do something else. This can be a very light weight test.  You do need to be a bit careful that the other code has &#8216;observable&#8217; behavior to avoid some possible optimizations, but in &#8216;real&#8217; code I find this isn&#8217;t normally a problem.
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hs2sf">hs2sf</a> on June 3, 2018</div><div class="thread-post-content">Sure, with a number of constraints you mentioned (single core, no caches ?, &#8230;) it is possible to (mis)use a  volatile variable for this simple kind of IPC. However, even for this purpose on this kind of system I&#8217;d use an atomic variable. Because it&#8217;standard since a while and I prefer and recommend writing portable code. Which will still work properly even if FreeRTOS get&#8217;s ported to multicore processors or if one ports such code to an other system.
I just tried to give a more general, good advise to avoid a pretty common pitfall or  misunderstanding  of <code>volatile</code>
</div></div><div class="thread-post"><h3 class="thread-post-title">static and volatile declaration of  xSemaphoreCreateMutex()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 4, 2018</div><div class="thread-post-content">Yes, atomics are now the perfered method of this IF (and big if for these sort of machines) you have a modern compiler that supports it. (and single processor machines with caches will still work with just volatile for IPC, it is only multi-processor that gives issues, data caches actually give you more problems with hardware I/O, where you imply volatile works).
I suspect I am much more likely to want to port my FreeRTOS code to a compiler that doesn&#8217;t support atomics than to a machine where volatile doesn&#8217;t work (and the latter is much more likely to require a major restruturing anyway). I will note that the FreeRTOS code base includes work arounds for compilers that don&#8217;t fully support the C90 standard. This is why it invokes technically undefined behavior with violation of the One Definition Rule with handles being pointer to void in the user code but being pointer to structs in the kernal code, making almost every FreeRTOS system call a violation of that rule. This not only invokes technical undefined behavior, but increases the chance of error as user code can mix up handle usage.
