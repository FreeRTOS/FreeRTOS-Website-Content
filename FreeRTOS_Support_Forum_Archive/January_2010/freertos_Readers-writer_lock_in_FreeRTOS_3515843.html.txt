  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Readers-writer lock in FreeRTOS?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lopatcbs">lopatcbs</a> on January 12, 2010</div><div class="thread-post-content">Hi support forum&#33;  
Any recommendations on how to create a readers-writer lock in FreeRTOS?  
Basically, I have two threads reading from a datastructure and another thread writing to it occasionally. I want the two reader threads to be able to read simultaneously, while ensuring the writer thread can only write when the readers are not reading.  
The solution I&#8217;m about to implement is to use a counting semaphore with the max-value equalling the number of readers:  
<pre><code>init()
{
   rw_sem = 3
}
start_read()
{
   rw_sem--
}
stop_read()
{
   rw_sem++
}
start_write()
{
   rw_sem--
   rw_sem--
   rw_sem--
}
stop_write()
{
   rw_sem++
   rw_sem++
   rw_sem++
}
</code></pre>
However, this will not give me the benefits of a recursive mutex &#40;priority inheritance and that it can be taken multiple times by same thread&#41; and start/stop writing will be pretty slow.  
Any other suggestions?  
Best regards  
Lars
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tgarner">tgarner</a> on January 12, 2010</div><div class="thread-post-content">Why don&#8217;t you just use a separate mutex for each read task ?<br />
The write task would have to obtain both before it could write.
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lopatcbs">lopatcbs</a> on January 13, 2010</div><div class="thread-post-content">Yes, that would solve the problem, and it may be the best way to go.   
But I was hoping for a more generic and lightweight solution to the problem. I have several chunks of data that would benefit from R/W locking and potentially making a mutex for each task for each resource is tedious and might take up quite a bit of ram…
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 13, 2010</div><div class="thread-post-content">If one task is writing, and all other tasks are reading, do you need any protection at all?  
If the writer is updating multiple members of a structure, and it is essential that the update is effectively atomic &#8211; in other words a reader must only read when all the structure members have been updated and are in a consistent state &#8211; then protection &#42;is&#42; required.  
Likewise, if the variables being updated are larger than the natural word size of the CPU &#8211; for example updating 32bit variables on a 16bit CPU &#8211; then protection &#42;is&#42; required.  
If the updates are only on single variables, AND the variables are the same size as the natural word size on the CPU, AND there is only one writer, then protection probably isn&#8217;t required.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/lopatcbs">lopatcbs</a> on January 13, 2010</div><div class="thread-post-content">The data chunks are structs with configuration and structs with data, and yes the updates must be atomic. So far in the development I got away with a single mutex for each struct to give one actor exclusive access.   
But now I have a situation where I really need more than one task to have read access. Having learned about the readers/writer lock: <a href="http://en.wikipedia.org/wiki/Readers-writer_lock">http://en.wikipedia.org/wiki/Readers-writer_lock</a>&nbsp; I realise that it would solve the present problem, and it would also make my code more elegant and better performing if I could use start/stop-read and start/stop-write for the other structs.  
But niceness is not always free and it seems that an ideal R/W lock does cost some resources…
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tgarner">tgarner</a> on January 13, 2010</div><div class="thread-post-content">If the structs are small and they are read and written by essentially a quick copy operation,<br />
you could just put a critical section &#40; or suspend all/resume all &#41; around all reads and writes.<br />
That&#8217;s about zero resource usage.
</div></div><div class="thread-post"><h3 class="thread-post-title">Readers-writer lock in FreeRTOS?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 13, 2010</div><div class="thread-post-content">While FreeRTOS doesn&#8217;t currently have a read/write lock primitive, one of the advantages of open-source code is that someone can write one and submit it to the code base.
