  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTaskGetTickCount on 32bit  is inefficient</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/helarsen">helarsen</a> on May 24, 2009</div><div class="thread-post-content">Hello,
xTaskGetTickCount in Task.c does more work than needed when implemented on 32bit processors so should&#8217;nt the function be written somewhat like the following where it is assumed the configUSE&#95;16&#95;BIT&#95;TICKS&#33;=1 on 32b cores?
portTickType xTaskGetTickCount&#40; void &#41;
&#123;
&#35;if &#40;configUSE&#95;16&#95;BIT&#95;TICKS==1&#41;
portTickType xTicks;
&nbsp;&nbsp;&nbsp; /&#42; Critical section required if running on a 16 bit processor. &#42;/
&nbsp;&nbsp;&nbsp; taskENTER&#95;CRITICAL&#40;&#41;;
&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; xTicks = xTickCount;
&nbsp;&nbsp;&nbsp; &#125;
&nbsp;&nbsp;&nbsp; taskEXIT&#95;CRITICAL&#40;&#41;;
&nbsp;&nbsp;&nbsp; return xTicks;
&#35;else //&#40;configUSE&#95;16&#95;BIT&#95;TICKS==0&#41;
&nbsp;&nbsp;&nbsp; return &#40;xTickCount&#41;;//Allready atomic
&#35;endif
&#125;
The reason for the critical section on 16b processors is that grabbing of the xTickCOunt copy must be atomic. On 32b this is inherent, so with 32b there is no need to add the overhead of the critical section. Right?
regards
henning
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount on 32bit  is inefficient</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 24, 2009</div><div class="thread-post-content">I think what you are saying&#8230;.is that the critical section is not required on all processors, and you would be correct.&nbsp; It has been discussed here before.
xTaskGetTickCount&#40;&#41; is not called by the kernel itself anywhere, only applications.&nbsp; My preference it to keep it as it is to prevent yet another conditional compilation, which would be ugly.
You could optimise it completely, and make it an inline access to a global variable for the occasions where the critical section is not needed.
Ideally you could use something like
&#35;if&#40; sizeof&#40; portTickType &#41; &#33;= sizeof&#40; portBASE&#95;TYPE &#41; &#41;
&#123;
&#125;
&#35;else
&#123;
&#125;
&#35;endif
I think also it has been suggested previously that there could be another type of critical section, one that only has an effect when the data types are not compatable..
Regards.

portTickType xTaskGetTickCount&#40; void &#41;;

</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount on 32bit  is inefficient</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 25, 2009</div><div class="thread-post-content">The big problem is that is illegal code. sizeof is not allowed in &#35;if statements as the preprocesor doesn&#8217;t know the size of types &#40;or even what is a type&#41;.
You would need a config parameter which indicates that portTickType is an atomic type.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount on 32bit  is inefficient</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/helarsen">helarsen</a> on May 27, 2009</div><div class="thread-post-content">I am in doubt if xTaskGetTickCount&#40;&#41; may be called from an ISR when implemented as it currently is &#8211; using a critical section which esentially means that IRQ is disabled then re-enabled again. Is this ok to do inside an ISR? On the ARM ADuC702x which I use it boils down to &#95;&#95;disable&#95;interrupt&#40;&#41; then &#95;&#95;enable&#95;interrupt.
I ask because xTaskGetTickCount&#40;&#41; is actually very useful to call from the ISR in order to add time stamps to the acquisition data. 
In fact such practical use pattern is another argument for optimizing the xTaskGetTickCount&#40;&#41; in order to conserve the precious ISR time to a minimum.
I acknowledge the desire to keep the number of &#35;if&#40;&#41;/&#35;endif&#8217;s down, in particular in such a multidimensional project &#40;processor vs. compiler&#41; as FreeRTOS. But in the case of xTaskGetTickCount&#40;&#41; an exception is justified &#8211; at least so I think.
regards
Henning
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount on 32bit  is inefficient</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 27, 2009</div><div class="thread-post-content">A better solution to getting the tick count in an ISR is to make a xTaskGetTickCountFromISR function, to follow the mold of ISRs only use FromISR entry points, That entry would be a simple fetch of the tick counter, since it is in an interrupt, there is the built in critical section for the access if it is needed &#40;since ISRs that access the kernel don&#8217;t nest&#41;.
