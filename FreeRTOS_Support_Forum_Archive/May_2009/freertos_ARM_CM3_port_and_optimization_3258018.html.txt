</div></div><div class="thread-post"><h3 class="thread-post-title">ARM_CM3 port and optimization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/spacewrench">spacewrench</a> on May 2, 2009</div><div class="thread-post-content">CM3 automatically pushes a set of registers on exception, and the LR of 0xfffffffc is a magic value indicating something like the exception-return requirements.&nbsp; You can find the actual return address &#40;or exception address&#41; by looking on the stack &#40;which is pointed to by SP&#41;.&nbsp; IIRC, the automatically-pushed registers are R0-R3 and LR.
I can&#8217;t help you with your compiler optimization problem, though.&nbsp; Perhaps you&#8217;re running out of memory and/or stack if the compiler doesn&#8217;t optimize its usage?
d.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARM_CM3 port and optimization</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 2, 2009</div><div class="thread-post-content">I&#8217;ve never heard of CodeWord, but presume this is a GCC build?&nbsp; If so then I would also assume it is based on the CodeSourcery as that is the only source of CM3 GCC that I am aware of.
Is your startup code written in C or ASM?&nbsp; If C then can you ascertain whether or not main&#40;&#41; is ever called.&nbsp; If the code crashed before main is called on a CM3 then the most likely cause is a loop that clears the RAM being corrupted.&nbsp; If the loop is written in C then without optimisation the loop variables will be read from and written back to RAM on each iteration of the loop &#8211; and the loop will most likely zero out these variables.&nbsp; When optimisation is on the loop variables will be held in registers so zeroing out the RAM does not corrupt the loop variables.
One easy solution to this is to keep optimisation on just for the startup code, even when the rest of the code uses zero optimisation.
Regards.

There is no easy &#40;and generic&#41; way to restore the stack modified when entering the scheduler.
