</div></div><div class="thread-post"><h3 class="thread-post-title">Real Time Timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 4, 2006</div><div class="thread-post-content">The SAM7X demo does very little in the ISR&#8217;s as the DMA on the SAM7X fills and clears the buffers automatically, and most processing is done at the task level with interrupt enabled.
The WEB server demo creates a table of all the tasks running in the system for display on the &#8216;home&#8217; page.&nbsp; This table uses a lot of string handling functions &#42;and&#42; walks the stack of each task to find the respective stack high water marks for display.&nbsp; This function can therefor take a long time to complete and executes with interrupt disabled.&nbsp; I suspect that this is the source of your measurement.
From the FreeRTOS.org site: &quot;The RTOS CGI file generates a table containing information on each task executing within the demo.&nbsp; This table is interesting for demonstration purposes, but as it is necessary to leave interrupts disabled for an extended period during its creation it is not recommended for use in applications with strict real time requirements&quot;.
Try removing this to see if things improve.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Real Time Timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dmwilliams66">dmwilliams66</a> on April 4, 2006</div><div class="thread-post-content">Hi,
Since I&#8217;m dealing with servo&#8217;s and stepper motors, I need hard realtime processor responses.
To test out the response time of FreeRTOS I created a regular interrupt &#40;using Timer0&#41; which interrupts 100&#8217;s of times a second.&nbsp; Helpfully, the hardware clears the counter used at the point of the interrupt, so since I know how long each counter increment takes &#40;approx 1/24,000,000s&#41;, if I examine the value of the counter in my interrupt handler, I can see how long it took to get to the interrupt.
There are two mechanisms that might cause this time to exceed the normal IRQ dispatch time.&nbsp; One is that there are other interrupts that occur.&nbsp; FreeRTOS only serves one interrupt at a time. The other is that FreeRTOS regularly switches IRQ&#8217;s off while it does critical OS-related things.
What I find is that while the average interrupt latency is around 100/24000000 = 4uS &#40;which is excellent&#41;, the maximum latency can be as much as&nbsp;&nbsp; 2819/24000000 = 120us even with the &#40;vTaskList&#40; &#41; commented out&#41; which is almost three times the resolution I need. &#40;Note that this more careful finding is much better than the 2.5ms I said earlier&#41;
Note that this is not a flaw with FreeRTOS.&nbsp; Sub 1ms responses are excellent for most purposes.&nbsp; There is however a class of problem that requires much more accurate timing.&nbsp; Hence my interest in creating a FIQ-based interrupt scheme orthogonal to the rest of the OS.
So &#8211; does anyone have FreeRTOS + GCC-based FIQ Handler experience on the SAM7 processors?
D.
</div></div><div class="thread-post"><h3 class="thread-post-title">Real Time Timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dmwilliams66">dmwilliams66</a> on April 5, 2006</div><div class="thread-post-content">OK.&nbsp; I got the Fast Forcing Timer interrupt to work.&nbsp; I mostly had it right, but I wasn&#8217;t setting the FIQ stack up correctly.
I created a Timer interrupt, setting the Fast Forced flag so it came in as an FIQ.&nbsp; The FIQ mode has its own stack, etc. so it can run independently of the rest of user / irq mode.&nbsp; The stock FreeRTOS ARM implementation sets and clears both the IRQ and the FIQ, I modified this to only modify the IRQ flag.&nbsp; Now the FIQ is enabled at all times permitting the Timer0 interrupt to interrupt FreeRTOS any time &#8211; including during vTaskList calls.
Now I can get interrupts with latency of maximum 4us &#8211; all the time.
Care will need to be taken to protect any data modified by these routines with very short Disable FIQ / Enable FIQ segments, and naturally no kernel&nbsp; data can be touched.
I hope this is useful to someone else needing hard real time performance from FreeRTOS/ARM

</div></div><div class="thread-post"><h3 class="thread-post-title">Real Time Timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dmwilliams66">dmwilliams66</a> on April 13, 2006</div><div class="thread-post-content">The mechanism I outline in this thread does give hard-real time responses.&nbsp; It relies on the ARM&#8217;s FIQ which is a separately maskable interrupt from the normal IRQ.&nbsp; You can get very quick responses &#8211; as fast as the processor is capable of &#8211; but because it&#8217;s unclear what FreeRTOS is doing when its interrupted, you can&#8217;t safely manipulate any of the FreeRTOS structures.&nbsp; As such, it couldn&#8217;t really be said to be part of FreeRTOS.&nbsp; In my application, I have some data that I protect with Enable / Disable FIQ calls which permits me to communicate with this &quot;system on the side&quot;.&nbsp; I now get maximum delays of about 4us from IRQ event to my RT code running.
Richard has spoken about a more elegant scheme where we change the way interrupts are handled on the ARM port slightly so that the regular ARM interrupts themselves can be interrupted by higher priority IRQ&#8217;s.&nbsp; This would go a long way towards make FreeRTOS a more real time OS, but would still exhibit the problem that any task anywhere could disable IRQ&#8217;s for potentially unbounded lengths of time.&nbsp; So all tasks would need to co-operate &#8211; and the OS would need to be examined very carefully to find out what the longest IRQ diabled period is and reduce it if necessary. Ultimately the slowest responses possible from this kind of system would be in the low 100&#8217;s of microseconds, I suspect based on my research.
I chose to do the &quot;system on the side&quot; because the solution I chose needed to work regardless of what else was going on in the system.&nbsp; I am creating an environment for other people to use, so I didn&#8217;t want to impose any restrictions on them.&nbsp; It also turned out to be a lot easier&#33;&nbsp; I&#8217;m not a super ARM coder by any means.
It is interesting to note that these two kinds of solutions &#40;&quot;system on the side&quot; and the more integrated one&#41; are also the same two solutions commonly used to improve Linux&#8217;s realtime abilities.&nbsp; Linux&#8217;s pre-emptable kernel gets you a long way towards lower response times, but if you really want response times in the microseconds, you need to do something like the &quot;system on the side&quot;.
