</div></div><div class="thread-post"><h3 class="thread-post-title">different prototypes to AT91F_AIC_ConfigureIt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 23, 2006</div><div class="thread-post-content">&gt; &#8211; forgive my n00bishness: what&#8217;s it that isn&#8217;t portable about the &#40;atmel&#41; headers?
&gt; and what&#8217;s the
&gt; rationale behind using macros vs inlines?
I forget exactly as it was some time ago, but the headers:
&#43; Use inlines, which is not portable to many embedded C compilers, although I think GCC could cope quite easily.&nbsp; I think there was some header file inclusion ordering problem though.&nbsp; Try using one of the inline header file function in your GCC project and see what errors/warnings are generated.
&#43; Overlays structures onto peripheral register memory addresses.&nbsp; Again this is not guaranteed to be portable, but may still work ok.&nbsp; It depends on structure alignment and padding, etc. introducted by the compiler.
&gt; &#8211; fully ported headers for gcc &#40;or even better, uniform headers for all compilers,
&gt; as far as possible&#41; would be a great thing. as is, it&#8217;s quite difficult to port
&gt; a demo for the same board to another compiler when one doesn&#8217;t know all the
&gt; reasoning behind the header differences etc.
If you are volunteering ;-&#41;
These headers are massive, some of the largest files within the zip download.
&gt; &#8211; right now, lib&#95;AT91SAM7X256.h is not usable in the gcc version, be it only
&gt; because of that AT91F&#95;AIC&#95;ConfigureIt argument stuff. &#40;and actually, the lwIP
&gt; demo for rowley/gcc doesn&#8217;t use it, while the uIP demo for IAR does&#41;.
&gt; 
&gt; &#8211; about the redundancy of the first argument: is that gcc-specific or is it
&gt; also redundant in iar? would there be a problem in removing it from the iar
&gt; version as well or leaving it in the gcc version so as to have the same
&gt; prototype?
The first parameter is a pointer to the emac peripheral.&nbsp; As there is only one emac peripheral the pointer can just be a constant, it can never be anywhere else.&nbsp; This is the same for all compilers but not all peripherals.&nbsp; For example if there are two UARTs then you have to pass a pointer to the UART you want to use, but as there is only a single EMAC it is not necessary.
&gt; If i want to build the uip demo with gcc, should i&nbsp; ditch the 1st argument from
&gt; the calls to AT91F&#95;AIC&#95;ConfigureIt?
Try using the same headers as included with the IAR demo and see what happens.&nbsp; Other than that, the choice is yours.
&gt; &#8211; no, i&#8217;m not the one you sent the alternative iar/uip demo to. &#40;actually, i
&gt; don&#8217;t have iar&#41;
The demo will work with the free 32K KickStart version that you can download from the IAR WEB site, but you would also need the J-Link interface.&nbsp; It might be useful just as a reference during your porting.
&gt; &#8211; my aim is to port the uIP demo from iar to plain gcc. now just in order to
&gt; not reinvent the wheel &#40;as you write &quot;I&#8217;m using Rowley&quot; in an other post&#41;: do
&gt; you by any chance have the uIP demo for rowley too? cause that would be much
&gt; easier to get&nbsp; to build with gcc than the iar version.
I only have:
&#43; lwIP demo for plain GCC targeted at SAM7X, or
&#43; uIP demo using GCC targeted at LPC2000.
Other than the library thing, porting from IAR to GCC should be fairly straight forward &#40;?&#41;.&nbsp; Its just a matter of getting the functions defined in the Atmel headers to compiler and run under GCC, or rewriting the parts that you want in a GCC friendly way, as per the inlines that have been changed to &#35;defines.
