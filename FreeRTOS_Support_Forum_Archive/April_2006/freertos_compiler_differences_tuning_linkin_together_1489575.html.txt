Richard pointed out that plain arm-elf-gcc uses more stack than rowley, which in turn uses more than iar. so i&#8217;m looking at ways to reduce the stack size used with gcc and optimize it as far as possible.
&#45; do you have any suggestion about what configuration parameters or other ways might tuning arm-elf-gcc? &#40;and how does rowley do it, if it&#8217;s based on gcc?&#41;
&#45; do i understand it right that the amount of stack size eaten up &#40;i&#8217;m not talking about the amount allocated&#41; depends on the compiled code in a way that the optimization is to be searched for in the compiling stage, not at the linking stage?
&#45; last time i used iar was a while ago with msp430 , and it seemed to be 100% gui-bound. is there also a command-line compiler included? 
&#45; is it practically feasible to link together stuff compiled separately with iar and gcc?
&#45; as it&#8217;s openly available for a multitude of host OSes &#40;including linux&#41; and target architectures and since i feel at home with gcc, make etc &#40;and like the way it&#8217;s all open&#41;, i have pretty much standardized all i could on gcc and feel reluctant about changing to a proprietary compiler suite. right now, apart from the bigger stack size &#40;which isn&#8217;t so problematic&#41;, i&#8217;m quite happy with gcc. I &#8216;m still a little fresh with arm and FreeRTOS though, so is there any other problem about arm-elf-gcc that i should know about? 
&#45; any other ideas or comments related to optimizations of gcc or how to get them to work together?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">compiler differences, tuning, linkin together</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 29, 2006</div><div class="thread-post-content">GCC is a generic compiler targeted at a whole multitude of processors and systems.&nbsp; The compiler itself is very good at optimising &#40;IMHO&#41; and therefore good for microcontroller use, but the libraries that come with it were no written with small microcontrollers in mind.
From what I have read regarding &#40;non bias&#41; comparisons between ARM compilers the libraries that come with GCC are its major downfall due to the stack they consume.&nbsp; In most embedded applications this is not really an issue, but when you start doing lots of string manipulation for serving html then you are going to start using strcat, strlen, strcpy, etc, etc.
If you can, isolate all the code that uses these libraries into one or two tasks, then just allocate more stack to these tasks.
There may be other libraries around you can use targeted specifically at smaller devices.
In the past, if I have just required a few library functions, I have written them myself rather than include the versions that come with the compiler.&nbsp; For example, I did this in the WIZnet WEB server demo.
As far as IAR goes, you can call the compiler from the command line just like GCC, but I would not attempt to link IAR and GCC code together.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">compiler differences, tuning, linkin together</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rainer32">rainer32</a> on April 29, 2006</div><div class="thread-post-content">thanks for the information.
there&#8217;s just one thing i&#8217;m not sure about concerning the libraries: most every arm-elf-gcc toolchain out there doesn&#8217;t use the gnu libc &#40;glibc&#41; as the standard c library, but newlib &#40;which pretends to be programmed specifically for embedded stuff and smaller resources&#41;. i thought the c string functions and others of the kind were in there. obviously, newlib &#40;as a general, platform-independent libc&#41; is still not at the highest level of optimization.
for atmel&#8217;s smaller avr family, there&#8217;s a specially optimized open source libc &#40;avrlibc&#41;. i guess that&#8217;s missing for the arm family.
thanks for the info
