I got&nbsp; a couple of boards in their original pre-release configuration, which was RMII.&nbsp; I modified one myself to use MII, so I could support both, although as you say RMII is not longer recommended.&nbsp; My MII board is used for the online demo, so generally when testing I use the RMII board.&nbsp; The configuration works for the most part but is not as robust as MII.
&gt; anyways, i tested the uip demo, and it looks good. there&#8217;s still a couple problems
&gt; though:
&gt; &#8211; The stack values do go down: 
&gt; initial values &#40;shown at first page load&#41;:
&gt; uIP: 192, IDLE: 122, each LEDx: 118
&gt; in the second page load, i already have uIP at 7 &#40;seven&#33;&#41;. i have to refresh
&gt; manually, as the page doesn&#8217;t have an auto-refresh &#40;i might add one to look&#41;.
&gt; anyways, i tried my wget loop script on /cgi/rtos and after 40000 page hits,
&gt; IDLE stays at 122, each LEDx settled to an apparently stable 108, uIP is still
&gt; at 7. damn that looks low&#33; but the thing is, it runs stably anyways &#40;i didn&#8217;t
&gt; go beyond 40000, though&#41;
Wow 7 is too low.&nbsp; The stack used by the uIP task is set at 250 by default I think.&nbsp; This value comes from the IAR demo.&nbsp; GCC uses &#40;much&#41; more stack for library function, and command line GCC even more than the Rowley configuration.&nbsp; This needs to be raised.&nbsp; It is good that it does not shrink further though, which would indicate that it is executing correctly.
&gt; so now for the real problem: /cgi/tcp. when i load that page, i&#8217;ve occasionally
&gt; seen the uIP stack size drop to 4 before crashing. sometimes it crashes even
&gt; before displaying the /cgi/tcp page. when i leave plenty times between manual
&gt; refreshes of that page, i get about 40 or so done before the crash. with a wget
&gt; loop, it crashes immediately after the first. actually, if i wget /cgi/rtos
&gt; and then /cgi/tcp inside the same loop, it crashes on the first attempt of getting
&gt; /cgi/tcp.
&gt; unlike the lwip demo, where the leds kept blinking while the tcp stack froze,
&gt; i&#8217;m talking of a real crash with leds freeze here.
Does this also happen with a bigger stack?
&gt; 
&gt; so that leaves me with the following questions:
&gt; &#8211; while the end stack size of 108 &#40;down from 118&#41; for LEDx still looks comfy,
&gt; the stack size of uIP going down from 192 to 7 seems abnormal &#40;/cgi/rtos still
&gt; loads correctly though, 40000 times and on&#41;. is that a problem? if so, do you
&gt; have a clue about where it could be?
The cgi/rtos uses a lot of string handling functions to generate the table of tasks.&nbsp; This under GCC will eat your stack.&nbsp; Also note the comments on the WEB site that this function is good for debug and demonstration, but not good for production code as it leaves interrupts disabled for the entire time the table is being generated which can cause problems for your real time performance, missing interrupts, etc.

Just try with a larger stack.&nbsp; If you still have the problem I will send over some binaries.
