  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">different idea for xTaskCreate()</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on April 14, 2006</div><div class="thread-post-content">I&#8217;ve been thinking about a different way that xTaskCreate&#40;&#41; could work easier and be more portable. I wonder if others have given it much thought.
We can see that each task typically has it&#8217;s own initialization code first, and then begins it&#8217;s infinite loop for the real task code. So that code before the loop is always executed once, the first time.
What makes sense to me is if a function for the same purpose as xTaskCreate&#40;&#41; were defined which is meant to be called from &#42;within&#42; the task function itself. That means it would not have to pass the parameter that tells where that task needs to run when called again later, because it can be taken from context.
It would help in HCS12 and GCC because it would be easier to start tasks which begin in a different memory banks, without the wierd trampoline stuff that GCC does.
Basically in GCC-m68hc1x if a start address of the func is 31:80A0, there is no way to pass the whole address in a pointer &#40;only have 16-bit ptr&#41;. Instead, it gives a 16-bit addr to a trampoline func which manually tweaks the stack, sets the mem ory bank, then jumps to the real func. It seems more straight forward if xTaskCreate&#40;&#41; could just look at the current stack to see the full addr it was called from. I realize however that would be one more function that would have to be in port.c instead of task.c, so maybe not so convenient for everyone.
</div></div><div class="thread-post"><h3 class="thread-post-title">different idea for xTaskCreate()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 16, 2006</div><div class="thread-post-content">Anything that would reduce the number of parameters passed to xTaskCreate&#40;&#41; would be good as this takes more stack than would otherwise be desirable.
I have in the past attempted something similar where a function was introduced to turn main&#40;&#41; into a task.&nbsp; This was done to try and recover the stack used by main&#40;&#41; itself.&nbsp; main&#40;&#41; would start all the other tasks in the system, then call the new function, before entering a for&#40;ever&#41; infinite loop and be called under the control of the scheduler.
I would still like to do this, but it requires some fairly major work in each port which is not easy and somewhat time consuming.&nbsp; I can&#8217;t remember exactly what the issues where but I remember there were some difficulties.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">different idea for xTaskCreate()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nuncio">nuncio</a> on April 16, 2006</div><div class="thread-post-content">The best way to turn a bunch of parameters into just one is to create a structure and pass a pointer to the structure into the routine.
</div></div><div class="thread-post"><h3 class="thread-post-title">different idea for xTaskCreate()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on April 18, 2006</div><div class="thread-post-content">Interresting that recovering the stack from main&#40;&#41; with my HCS12 is automatic. Because the stack is at the end of the memory heap, all I have to do is setup the heap to overlap the initial stack at the high end of RAM. I don&#8217;t allocate that much memory from heap until vTaskStartScheduler&#40;&#41;. Since that never returns &#40;which is mostly because it&#8217;s a small system&#8211;less RAM&#41;, the main&#40;&#41; stack can simply be overwritten when the space is needed.
In otherwords, turning main&#40;&#41; into a task won&#8217;t be of value to me. Making each task require less stack&#8230; now that&#8217;s important.
