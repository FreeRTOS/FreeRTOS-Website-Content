  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problems with Task Timing.</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/billdenbeste">billdenbeste</a> on April 19, 2006</div><div class="thread-post-content">I have a FreeRTOS application with three tasks which exhibits funny timing behavior.&nbsp; My first task is derived from the flashing LED task in the demo &#40;some changes to use vTaskDelayUntil&#41;.&nbsp; This task makes a good visual indication that I haven&#8217;t broken anything.
My other two tasks implement a Queued LCD driver and a test task that sends it strings to be displayed.&nbsp; The queue is similar to the pollQ demo task.&nbsp; Functionally, both tasks seem to be OK by themselves.
I am using pre-emptive mode and no co-tasks.&nbsp; I am running on a Silabs C8051F120 using the Silabs IDE and the SDCC compiler.
When I run only the flashing LED task, the timing looks just as I would expect.&nbsp; When I add the LCD driver and test task, the LED task speeds up.&nbsp; Not just a little, but a lot.&nbsp; It also becomes very irregular.&nbsp; It looks as though some ticks are happening very much faster than others.
Obviously this is more likely to be a problem I have caused than a bug in the FreeRTOS code, but at this point I don&#8217;t know where to look next.&nbsp; Any suggestions would be welcome.
&#45; Bill
</div></div><div class="thread-post"><h3 class="thread-post-title">Problems with Task Timing.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 19, 2006</div><div class="thread-post-content">People that read this regularly will guess what I&#8217;m going to say ;-&#41;&nbsp; Have you checked the stacks used by your tasks?&nbsp; Maybe the LCD driver requires more than the minimal stack and is causing some corruption.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problems with Task Timing.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/billdenbeste">billdenbeste</a> on April 19, 2006</div><div class="thread-post-content">Richard,
Thanks for the quick reply.&nbsp; I am a regular reader, and I already thought of that.&nbsp; I can&#8217;t say for sure, as I don&#8217;t know how to test this inside the guts of FreeRTOS, but I don&#8217;t think so.&nbsp; 
I have a very small queue &#40;10 bytes&#41;. I have the task stack set as large as I think I can &#40;256 &#8211; start address&#41;.&nbsp; I don&#8217;t see any other evidence of corruption.&nbsp; I have re-ordered large blocks of code to change the adjacency of various blocks in memory, with no changes in behavior.&nbsp; I have re-written the task code to minimize stack usage with no change in behavior.
How would you go about checking for stack overflow?
 &#45; Bill
</div></div><div class="thread-post"><h3 class="thread-post-title">Problems with Task Timing.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on April 19, 2006</div><div class="thread-post-content">Each task stack is filled with 0xa5.&nbsp; I don&#8217;t know which debugger you are using, but you should be able to find the stack in memory.&nbsp; Either make note of where the stack is when the task is created, or stop the task on a breakpoint and check the tack pointer.&nbsp; You will hopefully see lots of 0xa5&#8217;s.&nbsp; Let the code run for a while, then check again to see how many are left.&nbsp; There is also a function in task.c that can be optionally included to walk the stack and tell you how much is left &#40;can&#8217;t rememeber the name off the top of my head&#41;.
It is very odd that you seem to get the tasks going faster.&nbsp; On the assumption you have not changed the timer setup by mistake some sort of corruption is most likely but normally this would lead to a complete failure.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problems with Task Timing.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/billdenbeste">billdenbeste</a> on April 20, 2006</div><div class="thread-post-content">Well,&nbsp; as i suspected, the task stack is not being corrupted.&nbsp; In fact, it is very lightly used.&nbsp; At the deepest my subroutines have pushed it down by about 20 bytes or so.&nbsp; Still lost on this one, so I will press ahead on other issues for a few days.
&#45; Bill
