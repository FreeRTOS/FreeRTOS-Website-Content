  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Solving an INTERRUPTing puzzle</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ammaree">ammaree</a> on September 5, 2015</div><div class="thread-post-content">In an application I am developing I have come across a puzzling situation. The background is as follows:
Hardware is standard CC3200 LaunchPad 
Software using CC3200 SDK v1.1.0 and FreeRTOS 8.2.2, 
Environment using latest Code Composer Studio (CCS) v6.1.0.104
ASSERT is enabled for all my code as well as the SDK driverlib, simplelink and oslib components and tested to trigger everywhere.
configASSERT is enabled for FreeRTOS and tested to trigger if I on purpose change (to an invalid value) configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY.
Although the CC3200 is M4 architecture (without FPU) the official SDK ships with an older version of FreeRTOS (8.0.1) and provides a ARM<em>CM3 port as opposed to an ARM</em>CM4 port.
In order to overcome some challenges with the CM3 implementation I adapted the latest official FreeRTOS CCS ARM_CM4F port by simply removing the VFP related code, nothing else.
Originally I only used taskENABLE<em>INTERRUPT() and taskDISABLE</em>INTERRUPT() function and everything worked perfectly
I then decided to change all references to taskENTER<em>CRITICAL() and taskEXIT</em>CRITICAL() and that is where the mystery started&#8230;..
The application now fails in various places, stages and modes, but always in a way where debugging is impossible, no debug exception handler triggering, no stack trace, nothing.
<ul>
<li>Stack size is not a problem, all tasks have at all times a minimum of 972 to 2848 bytes unused.</li>
<li>I have tried module by module to determine if the problem only occurs in s certain function, no luck.</li>
<li>If I use tasKENTER/EXIT_CRITICAL() anywhere it crashes.</li>
<li>Change all references to taskEN/DISABLE_INTERRUPTS and it runs rock solid.</li>
<li>Only xTaskNotifyFromISR and portYIELD<em>FROM</em>ISR is used in 1 routine, no other API calls from ISRs</li>
</ul>
What am I missing since I did not touch any of the related code in the port&#8230;
All help appreciated.
Andre
</div></div><div class="thread-post"><h3 class="thread-post-title">Solving an INTERRUPTing puzzle</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 5, 2015</div><div class="thread-post-content">Thanks for proving information on what you have already tried &#8211; it would be nice if more people did that.
First &#8211; we don&#8217;t have an official ARM<em>CM3 port for CCS, so originally you are using third party and unsupported code.  We do have an official ARM</em>CM4F port for CCS, so guess the code you adapted is from the official code base &#8211; altbeit that you have made the ataptions yourself so we can&#8217;t discount that being a potential source of error.
<blockquote>
  Although the CC3200 is M4 architecture (without FPU) the official SDK ships with an older version of FreeRTOS (8.0.1) and provides a ARM<em>CM3 port as opposed to an ARM</em>CM4 port.
</blockquote>
It is correct to use the ARM_CM3 port if the part does not have an FPU, but as mentioned about, there isn&#8217;t official for for CM3 and CCS.  With the other supported compilers the only difference between the CM3 and CM4F ports is the FPU support.
<blockquote>
  Originally I only used taskENABLE<em>INTERRUPT() and taskDISABLE</em>INTERRUPT() function and everything worked perfectly
</blockquote>
Normally we would advice against using those macros directly, in favour of using the taskENTER<em>CRITICAL() and taskEXIT</em>CRITICAL() macros as the latter count the nesting depth&#8230;
&#8230;and maybe this could be a clue to what your problem is?
When you call taskENABLE<em>INTERRUPTS() interrupts will get fully enabled no matter what.  When you call taskEXIT</em>CRITICAL() interrupts will only get fully enabled if the critical section nesting count is zero.  Although I can&#8217;t say why that would prevent you from being able to debug &#8211; you should be able to debug easily even when in a critical section.
How long does it take for this issue to occur?  Does it occurr immediately, or after a while.
&#8230;. if it occurs immediately can you inspect the value of uxCriticalNesting in FreeRTOSSourceportableCCSARM_CM4F.  To start with, when main() is called, it should be 0xaaaaaaaa.  If it is not that value then it is not being initialised correctly.  When the first task starts running (on entry to the first task, which could be the timer task created by FreeRTOS itself) it should be 0.
&#8230;. if it occurs after some time, is it always after a particual function is called, or after a particular event occurs (interrupt executes, etc.)?  If so, could it be something inside one of the libraries is accessing interrupt masks in a way that is not compatible with FreeRTOS?  FreeRTOS uses the BASEPRI register, so it is ok for libraries to globally enable/disable interrupts in the processor itself (provided they are enabled again), but there could be problems if a libary leaves BASEPRI in an unexpected state, or enables all interrupts when FreeRTOS expects them to be partially masked.
Regards.
