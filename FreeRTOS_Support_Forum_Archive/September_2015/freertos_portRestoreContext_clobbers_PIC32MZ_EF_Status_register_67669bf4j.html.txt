  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">portRestoreContext clobbers PIC32MZ EF Status register</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbjork">pbjork</a> on September 8, 2015</div><div class="thread-post-content">At the end of xPortStartScheduler(), the portRestoreContext is botching the stack frame for the first task to run.  Somehow it is pulling a bad value for the CP0 Status register off the stack and corrupting several important bits including the CU1 fpu coprocessor enable bit.  I don&#8217;t observe any other problems with the first task; it starts up well and continues on to several other tasks, seemingly without a hitch.  It does seem, though, if I restore the Status register manually after corruption, that it gets corrupted again at each call of portRestoreContext.
Here&#8217;s what&#8217;s at the ( UBaseType_t * ) pxCurrentTCB: a nice address = 0x80004F2C.
The contents of this is, according to the memory view, is 0xA5A5A5A5.  I know, not a valid value.  The saved stack pointer, just before the call to portRestoreContext, is a different kind of invalid, I think:
uxSavedTaskStackPointer = *( UBaseType_t * ) pxCurrentTCB = 0x00000000 !
I don&#8217;t know why this doesn&#8217;t come up as the value 0xA5A5A5A5 that the memory view shows.  But neither value seems valid as a stack pointer.
Any ideas as to the cause of this?
I&#8217;ve raised the configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY and configMAX</em>PRIORITIES to relatively high levels.  I&#8217;m trying to see whether any FreeRTOS API gets called before xPortStartScheduler().  Any other diagnostics?
Setup: the latest FreeRTOS v 8.x.x, shipping with MHC 1.06 for PIC32MZ EF family processors.

I also see that when the first task is actually called, it is NOT the highest priority task.

</div></div><div class="thread-post"><h3 class="thread-post-title">portRestoreContext clobbers PIC32MZ EF Status register</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iberoxarxa">iberoxarxa</a> on September 17, 2015</div><div class="thread-post-content">From Iberoxarxa we got the first results with Lua 5.3.1 running on FreeRTOS on PIC32MZ2048EFH064. MZ ports have been modified to achieve this:
<ul>
<li>CP0 status is initialized in pxPortInitialiseStack. portINITIAL<em>SR is invalid for this silicon, because it sets CU1 to 0 disabling the FPU. It is mandatory to apply 0x20000000 mask to portINITIAL</em>SR for enabling FPU.</li>
<li>FPU registers are 64 bit wide. There are 32 registers ($f0 to $f31). This registers must saved and restore in portSAVE<em>CONTEXT, portRESTORE</em>CONTEXT and vPortYieldISR. For this use sdc1 / ldc1 MIPS instruction. Be careful with that, so sdc1 / ldc1 requires a 8 word alignment stack. Changes in pxPortInitialiseStack are required for this.</li>
<li>FPU has 4 control registers. Register FCSR must be saved / restored in portSAVE<em>CONTEXT, portRESTORE</em>CONTEXT and vPortYieldISR.</li>
</ul>
Doing this our project: FreeRTOS + Lua 5.3.1 + Lwip runs.
Attached you have the modified port files. Probably all is not fine with our work. More tests are needed. We hope that this modifications will be useful for FreeRTOS team.
You must put &#8220;#define configUSE_FPU 1&#8221; in your FreeRTOSConfig.h file.
</div></div><div class="thread-post"><h3 class="thread-post-title">portRestoreContext clobbers PIC32MZ EF Status register</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iberoxarxa">iberoxarxa</a> on September 17, 2015</div><div class="thread-post-content">isr stack must be 8 byte alignment. This is done putting this in port.c:
<h1>if( configUSE_FPU == 1 )</h1>
const StackType<em>t * const xISRStackTop = &amp;( xISRStack[ configISR</em>STACK_SIZE &#8211; 8 ] );
<h1>else</h1>
const StackType<em>t * const xISRStackTop = &amp;( xISRStack[ configISR</em>STACK_SIZE &#8211; 7 ] );
<h1>endif</h1>
With this (and previous post) FreeRTOS inour project is stable. 3 hours running, responding to ping, and executing Lua scripts without any problem.
