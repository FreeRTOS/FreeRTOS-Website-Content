  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">The empty for loop in list.c</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/fraza077">fraza077</a> on September 11, 2015</div><div class="thread-post-content">I guess a lot of you have seen this your code get stuck here before:
<hr />
for( pxIterator = ( ListItem_t * ) &amp;( pxList->xListEnd ); pxIterator->pxNext->xItemValue &lt;= xValueOfInsertion; pxIterator = pxIterator->pxNext ) /*lint !e826 !e740 The mini list structure is used as the list end to save RAM.  This is checked and valid. */
    {
        /* There is nothing to do here, just iterating to the wanted
        insertion position. */
    }
<hr />
After having bundled through all this once again today, I found my problem (I was in a critical section due to an accidental Find/Replace having greater scope than I thought), but it struck me that there really weren&#8217;t enough checks in this section, despite the comment claim that &#8220;There is nothing to do here&#8221;.
In my case, for whatever reason, it was adding a duplicate element to the list. Is this something one could use an assert for? 
Inside the for loop:
<hr />
<h2>configASSERT(pxNewListItem != pxIterator);</h2>
Also, in case anything else goes wrong, why not ensure the list only gets run through once?
For example:
<hr />
volatile xListItem *start = ( xListItem * ) &amp;( pxList->xListEnd );
volatile uint32 RunThroughCnt = 0;
for( pxIterator = ( xListItem * ) &amp;( pxList->xListEnd ); pxIterator->pxNext->xItemValue &lt;= xValueOfInsertion; pxIterator = pxIterator->pxNext )
{
    if (pxIterator == start)
    {
        RunThroughCnt++;
        configASSERT(RunThroughCnt &lt;= 1);
    }
    configASSERT(pxNewListItem != pxIterator);
<h2>}</h2>
I imagine those of you who know the inner workings of FreeRTOS better than I do might know some reasons why these wouldn&#8217;t work? If not, is there anything else that can be done to make this safer?
Just staying in the for loop forever is annoying, all the info I get is that the watchdog kicked in, And I don&#8217;t have a clue where the code was when that happened.
Cheers,
Zac
</div></div><div class="thread-post"><h3 class="thread-post-title">The empty for loop in list.c</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 11, 2015</div><div class="thread-post-content">Things inside the kernel are kept as lean as possible, especially code that runs frequently, and especially especially code that is in a loop.  Adding these checks would be useful, I agree, but aren&#8217;t done because it would make the code slower.  Instead we have added asserts at the points in the code that can lead to you getting stuck in the loop.  For example, the most common cause (bar far) is people setting incorrect interrupt priorities &#8211; that is &#8211; using FreeRTOS API functions from an interrupt that has a priority higher than the priority masked by critical sections &#8211; so we have an assert that traps that happening.  That way the assert should be hit before the code ever reaches the loop, and it is hit at the point the cause is detected, rather than the symptom.
Regards.
