  Now the question becomes linguistic

As you say, I think this is a linguistic thing.  Let me explain how it is intended to work, then if you don&#8217;t think this is how it is working, please let me know and I will investigate.
If you <strong>peek</strong> a queue then you return the first item in the queue (assuming there is data in the queue) without modifying the queue.  That is, the item remains in the queue.  Remember semaphores are macros that use the queues, so like many other queue API functions, you can also call <a href="http://www.freertos.org/xQueuePeek.html">xQueuePeek() </a> on a semaphore.
If you <strong>read</strong> from a queue then you actually remove the item from the queue.  If you <strong>take</strong> a semaphore, then you make the semaphore unavailable to any other task.  When you read a queue, or take a semaphore, you can specify a block time, and the block time can be 0.  If the call specifies a non-zero block time then it is a <strong>blocking</strong> call &#8211; if the queue is empty, or the semaphore is not available, the calling task will wait in the Blocked state until it either times out or data becomes available.  If the call specifies a zero block time then it is a <strong>pollilng</strong> call because the function will return immediately to the calling task.  If you make a polling (zero block time) call to take a semaphore, and the semaphore is available, then you will obtain the semaphore &#8211; as you called a function that is intended to take the semaphore you just specified a block time of 0.
I think this terminology is in common use.  For example, if I am waiting for a bit to become set in a register then I can <strong>poll</strong> the register by sitting in a loop continuously reading the register, until the bit is set &#8211; or I can make a blocking call in which case I wait for an interrupt to tell me the bit is set.  If I poll a semaphore, then I can sit in a loop continuously trying to take the semaphore with a zero block time, until the semaphore becomes available.
<blockquote>
  The behavior of a semaphore in this example, and a queue are different, yet the semaphore is a one unit queue. Using xSemaphoreTake with a duration of 0 does affect the semaphore, and to me, it should not.
</blockquote>
I don&#8217;t understand this.  If you read a queue with a block time of zero, and there is data in the queue, then you <strong>will</strong> modify the queue too.
<blockquote>
  I will maintain that xSemaphoreTake with a time of zero should not affect the semaphore, 
</blockquote>
Is it not legitimate for somebody to want to take a semaphore with a block time of 0?  In your scheme, how would that work?
<blockquote>
  It was intended to work differently, and does not.
</blockquote>
As I said, I think this is purely a linguistic issue.  You want to be using the xQueuePeek() function, not the xSemaphoreTake() function.
Regards.

True, but in some cases there is only 1 possible taker of a semaphore (or receiver of a queue). For instance the IP-task in the +TCP stack: it may safely check the length of the queue to see if there is an API call. Nobody else will consume these messages.
Harvey wrote:
<blockquote>
  different task priorities do not seem to work well,

</blockquote>
True: in a RTOS the highest-priority task(s) that are runnable get all CPU time. As soon as a task goes in a blocked state, lower-priority tasks get attention. That is a choice-by-design.
You can:
<ul>
<li>either give your tasks the same priority and make sure that <code>configUSE_PREEMPTION</code> is defined as &#8216;1&#8217; (time-slicing)</li>
<li>combine several jobs within a single task and decide yourself how much time should be spent to each of the jobs.</li>

The functions <code>vTaskDelay()</code> and <code>vTaskDelayUntil()</code> are not interruptable. If you want an event to interrupt a blocking call, the cheapest way is probably to use the Notify fuctions mentioned in task.h :
~~~~~
/* Unblocking from a normal task: */
BaseType_t xTaskNotify( TaskHandle_t xTaskToNotify, uint32_t ulValue,
    eNotifyAction eAction );
/* Unblocking when called from an interrupt: */
BaseType_t xTaskNotifyFromISR( TaskHandle_t xTaskToNotify, uint32_t ulValue,
    eNotifyAction eAction, BaseType_t *pxHigherPriorityTaskWoken );
/* Wait to be notified: */
BaseType_t xTaskNotifyWait( uint32_t ulBitsToClearOnEntry,
    uint32_t ulBitsToClearOnExit, uint32_t *pulNotificationValue,
    TickType_t xTicksToWait );
~~~~~
These functions can be used to replace a semaphore in case it has only 1 taker. Note that you&#8217;ll have to store a copy of the task&#8217;s <code>TaskHandle_t</code>, and pass that to the task which will call <code>xTaskNotify()</code>.
Earlier you wrote:
<blockquote>
  the higher priority task gets all the processor time. Still working on that one, though.
</blockquote>
I&#8217;m still wondering: isn&#8217;t the workload just too high for your CPU? And is that work which must be done within a certain time?
If not, you could also assign a very low (or IDLE) priority: that task will receive all remaining CPU time not used by other tasks.
Example: for the FreeRTOS +FAT testing there are 6 tasks continuously accessing the same disk: create, write, seek, read, and close files. The only time when such a task will block is when waiting for disk access. Among the 6 tasks there is time-slicing, each one tends to get 16.7 % CPU time.
The application is still <strong>responsive</strong>: a telnet session is running at a normal priority and it will respond immediatelyto every request.
