</div></div><div class="thread-post"><h3 class="thread-post-title">How should xQueueSendFromISR and xQueueReceive be used?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 15, 2015</div><div class="thread-post-content">From your previous post:
<blockquote>
   So it has something to do with usart->ier = AVR32<em>USART</em>IER<em>RXRDY</em>MASK
   When I delete that line in the code above, it always works (two LEDs blinking)
</blockquote>
When you delete that line there won&#8217;t be any RX interrupt.
Your ISR is indeed masking off bits that have not been enabled:
~~~~~
    /* What caused the interrupt? */
    ulStatus = usart->csr &amp; usart->imr;
~~~~~
<blockquote>
  Because FreeRTOS is not supposed to run with nested interrupts,
  put all OS calls in a critical section
         portENTER<em>CRITICAL();
         if (xQueueSendFromISR(xRxedChars, &amp;cChar, &amp;xHigherPriorityTaskWoken))
         portEXIT</em>CRITICAL();
</blockquote>
I don&#8217;t think the critical section is necessary. Interrupts are not enabled (by the global flag) until you enable them.
And ask your self: will there be another ISR that will try to access your <code>xRxedChars</code>? That shouldn&#8217;t be.
Note that if you expect lots of data (kilobytes), you better look at other methods like using PDC (DMA) channels.
My guess is that taking away the critical sections will solve the problem.
From <code>trvUART_CLI_RX()</code> you will call <code>xQueueReceive()</code> (without the FromISR), and <code>xQueueReceive()</code> will use critical sections when necessary.
Regards.
