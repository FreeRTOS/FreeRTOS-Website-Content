  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title"> same Queue Receive in two different tasks</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joe_her">joe_her</a> on September 24, 2015</div><div class="thread-post-content">Can I wait for the same queue msg in two different tasks? That is one task sends a msg, which shuold be recieved by two or more then one task. How can this be done? the main concern is who will clear the queue, and how can one make sure that the queue is cleard only after all &#8220;clients&#8221; got the messege?
I am a bit confused on this.
Thnaks
</div></div><div class="thread-post"><h3 class="thread-post-title"> same Queue Receive in two different tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 24, 2015</div><div class="thread-post-content">Maybe each task could use <a href="http://www.freertos.org/xQueuePeek.html">xQueuePeek()</a> to read the message from the queue without removing the message from the queue, and then <a href="http://www.freertos.org/xEventGroupSetBits.html">set a bit in an event group</a> to indicate that that task had obtained the message.  When the value returned from xEventGroupSetBits() indicates that all the tasks had read the message then the message can be removed from the queue.
Just one suggestion &#8211; there are probably other methods that could be used too.
</div></div><div class="thread-post"><h3 class="thread-post-title"> same Queue Receive in two different tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joe_her">joe_her</a> on September 24, 2015</div><div class="thread-post-content">Thanks, but isnt there a racing risk? it looks like taskENTER_CRITICAL should be used between Peek and setting the bit. So I wonder if there is a better, more elegant,  way.
</div></div><div class="thread-post"><h3 class="thread-post-title"> same Queue Receive in two different tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 24, 2015</div><div class="thread-post-content">You should not call the peek function from a critical section, at least, 
not if a block time is specified.
I would need to know more about the use case to know if a race condition 
existed, as it would depend on what the tasks that had read from the 
queue did next.  If they were to immediately try reading again then they 
too would have to check the event group to ensure all the tasks had read 
the message before they tried reading again.
It also depends on the characteristics of how the queue is used.  If 
there is only one item available then you might implement a scheme where 
by tasks subscribe to the message, then when a message arrives on the 
queue it is sent to the tasks individually, maybe even using a task 
notification.
</div></div><div class="thread-post"><h3 class="thread-post-title"> same Queue Receive in two different tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joe_her">joe_her</a> on September 24, 2015</div><div class="thread-post-content">Thnaks.
Will try that.  As each event bit will be set by a different task, I think there is no risk of a race condition, assuming that setting the event bit is atomic, and this read-modify-write can not be interrupted by another task.
Johanan
</div></div><div class="thread-post"><h3 class="thread-post-title"> same Queue Receive in two different tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 24, 2015</div><div class="thread-post-content">My general feeling is that if it is only two tasks, and they don&#8217;t need to keep &#8216;in sync&#8217; while processing messages from the queue, that it would be much simpler to just create two queues and have the sender place the message on both.
If it is something more complicated, then maybe a better description would help.
