  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Coroutine Scheduling</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tcwden">tcwden</a> on January 26, 2007</div><div class="thread-post-content">Hi all,
I&#8217;m new to freeRTOS and coroutine. 
I have a question about the function of coroutine scheduler in the documentation, which says:
&quot;vCoRoutineSchedule&#40;&#41; executes the highest priority co-routine that is able to run. The co-routine will execute until it either blocks, yields or is preempted by a task. Co-routines execute cooperatively so one co-routine cannot be preempted by another, but can be preempted by a task.&quot;
The above paragraph seems a little bit contradicting to me. 
If the scheduler always schedules the highest priority co-routine first &#40;presumably, at every system clock tick&#41;, then I would think that a higher priority coroutine can preempt a lower priority coroutine. 
However, what it continues to say is that a coroutine will keep running until it blocks itself &#40;by crDELAY, crQUEUE&#95;SEND, or crQUEUE&#95;RECEIVE&#41;. In that case, what is the use of priority for coroutine?
Also, assuming no tasks are running, when coroutine A &#40;higher priority&#41; blocks itself for t ms, and coroutine B &#40;lower priority&#41; starts running, will coroutine B stops and let A to run after t ms?
Thanks in advance&#33;
Dennis
</div></div><div class="thread-post"><h3 class="thread-post-title">Coroutine Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 26, 2007</div><div class="thread-post-content">Co-routines will not preempt each other.&nbsp; Therefore when a co-routine is selected to run it will continue to be the selected co-routine until such a time that it blocks or calls yield.&nbsp; When a co-routine blocks the scheduler then re-evaluates which co-routine should be selected to run and will at that time choose the highest priority co-routine that is able to run &#40;i.e. is not blocked&#41;.
Co-routines use a cooperative system, whereas tasks can be configured to be wither cooperative or preemptive.&nbsp; The priority is used to select the next co-routine to run at each decision point.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Coroutine Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on January 27, 2007</div><div class="thread-post-content">Hi Dennis,
You&#8217;ve got to be sure what &quot;preempt&quot; means. richard already said it but maybe my simple explanation will help: Coroutines are only cooperative &#40;in your example cr A blocks itself by crDELAY, etc. therefore cr B can run while A is blocked&#41;
Of course priorities are important each time vCoRoutineSchedule&#40;&#41; determines which task should run next.
</div></div><div class="thread-post"><h3 class="thread-post-title">Coroutine Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tcwden">tcwden</a> on January 29, 2007</div><div class="thread-post-content">Thank you Richard and Jeff&#33;
From your description, can I say that when my coroutine executes
&nbsp; crDELAY&#40; xHandle, xDelayTime &#41;;
there is no gurantee that the coroutine will run after xDelayTime &#40;or even close to it&#41; because some other coroutine might be running and not blocking itself?
Cheers.
Dennis
</div></div><div class="thread-post"><h3 class="thread-post-title">Coroutine Scheduling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 29, 2007</div><div class="thread-post-content">That is correct.&nbsp; It is the nature of cooperative scheduling.&nbsp; If you need preemption then tasks are the only choice.&nbsp; Using cooperative scheduling you have to ensure your low priority co-routines call yield often enough to ensure your high priority co-routines meet their real time deadlines.
Regards.
