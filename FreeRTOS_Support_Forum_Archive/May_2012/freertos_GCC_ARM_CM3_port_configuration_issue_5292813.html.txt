  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">GCC ARM CM3 port configuration issue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/darrenjenkins">darrenjenkins</a> on May 22, 2012</div><div class="thread-post-content">I have noticed that &#40;due to the way that interrupt masking uses configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY to set basepri&#41; it is not valid to have an ISR containing freeRTOS interfaces at priority level 0 &#40;highest&#41;.<br />
This has bitten me, and may bite other users of this port.<br />
Is the port maintainer likely to want to clean this up him/herself? or would it be more suitable for me to submit a change to clean this configuration dificulty up ? and if so how and where can I do this ?  
Thanks for your attention.  
</div></div><div class="thread-post"><h3 class="thread-post-title">GCC ARM CM3 port configuration issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 22, 2012</div><div class="thread-post-content">As you elude to in your email, only interrupts at or below configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY can call interrupt safe FreeRTOS functions &#40;those that end in FromISR&#41;.&nbsp; The port never completely disables interrupts, and interrupts above configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY are never disabled.&nbsp;   
Interrupts at or below configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY get masked in critical sections using a bit mask in basepri.&nbsp; To allow interrupts of priority 0 to call interrupt safe FreeRTOS functions it would be required to have a bit mask that masks off interrupts at priority 0, and you cannot have a 0 bitmask on a Cortex-M core because the core itself &#40;i.e. there is nothing the software can do about it&#41; treats 0 as a special case that means all interrupts are enabled.&nbsp; This is a quirk of the backwards interrupt priorities on Cortex-M cores &#40;where low values mean high priority&#41;, because there has to be a mask which means enable everything, and that mask cannot be 0xff because 0xff means mask all but the very lowest priority.  
I would personally be very interested in any alternative you had for this, because I don&#8217;t think there is one other than globally disabling interrupts &#40;not desirable&#41;, but if you come up with something I&#8217;m afraid it is unlikely to make it into the main line code because it would probably result in more lines of code for a result with less functionality.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">GCC ARM CM3 port configuration issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/darrenjenkins">darrenjenkins</a> on May 22, 2012</div><div class="thread-post-content">if configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY is 0 you want to mask &#95;all&#95; interrupts, which is equivalent to disabling them.<br />
I was thinking of something like  
<pre><code>#if (configMAX_SYSCALL_INTERRUPT_PRIORITY != 0 )
#define portSET_INTERRUPT_MASK()                        
    __asm volatile                                      
    (                                                   
        "   mov r0, %0                              n" 
        "   msr basepri, r0                         n" 
        ::"i"(configMAX_SYSCALL_INTERRUPT_PRIORITY):"r0"    
    )
#else
#define portSET_INTERRUPT_MASK() asm volatile ("cpsie i");
#endif
</code></pre>
with something similar for portCLEAR&#95;INTERRUPT&#95;MASK and xPortPendSVHandler.  
Which is just some simple code to make it work, in that specific configuration.  
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">GCC ARM CM3 port configuration issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 23, 2012</div><div class="thread-post-content">Yes &#8211; I think that would work without adding more code.&nbsp; I was thinking about having an &#8216;if&#8217; in the asm code, but doing it with the pre-processor is better.&nbsp; I had to think for a moment if this would break the interrupt nesting code &#40;where the current mask level is stored and then restored as you enter/exit critical sections in ISRs&#41;, but I think because the NVIC is intelligent on the CM3 it will be ok.&nbsp; That is why the macros for the interrupt same critical sections don&#8217;t even store the mask and just restore it to 0 &#40;saves time/space and has the same effect&#41;.  
Could you do me a favor and add this to the &#8220;feature request&#8221; tracker.  
Thanks.
