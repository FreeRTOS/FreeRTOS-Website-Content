  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vTaskDelete</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jdurand">jdurand</a> on May 23, 2012</div><div class="thread-post-content">I&#8217;m in the process of moving all my projects from another RTOS to FreeRTOS and have a question on deleting  
In the old RTOS if I tried to delete a task that had already been deleted, then it would just return a FAIL.&nbsp; Looking at the code here, I can&#8217;t really tell what will happen if I delete the same task more than once &#40;ie: if the handle is no longer valid&#41;.  
I have a work-around but want to know if there&#8217;s a clean way of handling this.  
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelete</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 24, 2012</div><div class="thread-post-content">In FreeRTOS a task handle is really a pointer to the TCB for the task. When you delete the task, that TCB is freed, and any subsequent access invokes &#8220;undefined behavior&#8221;. If you delete it again, it will be freed again, which for many libraries will corrupt the free store, so not a good idea.   
I would suggest that you store the handle in a variable that you can zero after you delete the task, and that way you can check if the task has already been deleted.
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelete</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kpettit1">kpettit1</a> on May 24, 2012</div><div class="thread-post-content">Hi jdurand,  
Richard is of course the expert on FreeRTOS, but I can say that deleting a task more than once with vTaskDelete would be a bad thing for the following reasons:  
1.&nbsp; The vTaskDelete routine performs linked list manipulation that would cause corruption during the 2nd &#40;or 3rd, etc.&#41; call to vTaskDelete, even if the task were still valid.<br />
2.&nbsp; You don&#8217;t know when the task is actually deleted as this occurs in the idle task as a &#8220;clean-up operation&#8221;.&nbsp; This means the task handle may be invalid the 2nd time you call it.<br />
3.&nbsp; When the task is deleted, the TCB and stack are both freed, thus putting their memory regions back into the heap.&nbsp; That memory could have been reallocated and over-written before the 2nd vTaskDelete is called, so it isn&#8217;t possible to track valid / invalid task status in the TCB.  
The way I usually handle deletion of tasks is probably a bit different that usual.&nbsp; In my port layer, I always initialize my task&#8217;s initial stack frames with a valid return address to a &#8220;catch function&#8221; that performs a &#8220;vTaskDelete&#8221; followed by a for &#40;;;&#41; loop.&nbsp; Then when I want my task to end, I send it via a mutex or global variable, and the task simply &#8216;returns&#8217;.&nbsp; Note that is ONLY works because I modify the port layer for my applications &#40;I use mostly ARM processors, so this mean setting the LR &#40;Link Register&#41; in the initial stack frame&#41;.  
If you &#42;absolutely&#42; had to have a way of support multiple deletes from within the OS, it probably wouldn&#8217;t be too hard to extend task.c to add a new xList to track valid xTaskHandles and modify vTaskDelete to first search that new list before attempting to delete the task.&nbsp; You would also need to add a new xListItem to the TCB and be sure to remove the xTaskHandle from the list from the prvDeleteTCB function.  
Ken
