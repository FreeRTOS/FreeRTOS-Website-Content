  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">What happens if a isr is too long.</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/leverett">leverett</a> on May 4, 2012</div><div class="thread-post-content">Hello, I am using FreeRTOS on a PIC32. I have an ISR that &#8220;I think&#8221; works fine. It has an interrupt priority above the maximum set for the RTOS and disables interrupts on entry, enables on exit. I therefore believe it can be written in C with no wrapper.  
In the documentation I read that the ISR should be kept as short as possible. I understand and I am doing that.   
However, what if I didn&#8217;t? What will happen if the ISR gets too long. Suppose it takes longer than the RTOS tick. Since interrupts are disabled, the tick cannot stop it can it? Will the scheduler simply wait until the ISR finishes or will there be some nasty consequence?  
I understand this is a stupid question because one would never have an ISR that long but I&#8217;m just trying to understand how the RTOS functions.  
Thanks.  
</div></div><div class="thread-post"><h3 class="thread-post-title">What happens if a isr is too long.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nathanwiebe">nathanwiebe</a> on May 4, 2012</div><div class="thread-post-content">Even a short ISR has the possibility of being in-process when other ISRs become signalled.&nbsp; What happens in a nested interrupt controller is that lower priority &#40;or same priority&#41; interrupts set a hardware flag in the processor that remains set until the you service that particular interrupt.&nbsp; If the tick timer fires, it will just run that ISR when yours is done.&nbsp; The same is true of an ISR that is within the acceptable range to make kernel calls &#8211; the tick ISR has to wait.&nbsp; If, on the other hand, your higher priority interrupt fires while the MCU is in the tick ISR, it will jump into yours and come back to the tick ISR later.&nbsp; If your ISR is too slow, then it will just mean other interrupts have bad latency &#40;time from event to ISR action&#41;.&nbsp; Your worst case latency on a given ISR is the sum of the worst case run times of the longest ISR in each priority level you are using.&nbsp; In the case of the tick, you would have to have a really slow ISR to overlap two ticks events, thus potentially dropping a tick and throwing out the OS&#8217;s delays.
</div></div><div class="thread-post"><h3 class="thread-post-title">What happens if a isr is too long.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 4, 2012</div><div class="thread-post-content">An ISR taking too long won&#8217;t &#8220;break&#8221; the RTOS in the sense of it crashing or something like that. It may well &#8220;break&#8221; your program in that it no longer meets your real time requirements. Interrupts taking so long that you might miss a timer tick interrupt will cause your program&#8217;s sense of time to be disturbed, more time has really passed than the program knows about.  
Interrupts, by their nature are limited in their flexability to schedule their control routines, They may have a nesting, but they can&#8217;t &#8220;defer&#8221; and then resume like a task. Tasks on the other hand are very flexible in execution control.  
When NOT using an OS, the ISR needs to do everything needed to service the device, as it has no other way to get something to execute. When using an OS that isn&#8217;t an RTOS, it might be able to hand off &#8220;low priority&#8221; operations to a task, but the hallmark of a RTOS is that you can setup a &#8220;real time&#8221; task to get high priority work done on time.<br />
With an RTOS, you typically do very little in the ISR, normally not more than &#40;maybe&#41; grabbing the data and clearing the interrupt, and any more complicated work is left for a task. Think of it as the ISR handles things that need to be done in microseconds, while the task handles stuff that is more on the order of milliseconds, or so. There isn&#8217;t THAT much of a cost in time to transition to the task to process, as if that task is the highest priority available, it should run as soon as the ISR exits.  
For this to work this way, the Interrupt should NOT be &#8220;above the max set for FreeRTOS&#8221;, as such an interrupt WILL need to interact with FreeRTOS.&nbsp; The only real reason I can think of to have an interrupt above the FreeRTOS max level is something that handles activity that REALLY needs microsecond level response or you get failure, so the interrupt can&#8217;t be temporarily masked for some FreeRTOS operations in critical sections. FreeRTOS has been designed with the goal of these periods being as short as possible &#40;and of a knowable limited length&#41;. Having this type of routine around normally requires very definite care and planning.
