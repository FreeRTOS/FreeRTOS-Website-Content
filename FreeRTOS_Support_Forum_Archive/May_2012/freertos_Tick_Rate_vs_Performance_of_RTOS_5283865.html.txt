  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Tick Rate vs Performance of RTOS</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/toddatm">toddatm</a> on May 17, 2012</div><div class="thread-post-content">I will be running an Arm Cortex M3 at 156 Mhz. I have a need for an accurate timer with a resolution of 250 usecs both for implementing delays and for keeping time, as well as perhaps scheduling some action to be performed.  
I&#8217;m trying to decide whether to increase the OS tick timer to this resolution, or to use another hardware timer at my disposal. I have other hardware timers available which run at 25 Mhz that can cause periodic interrupts and I can/could build a utility outside the OS to implement these functions. In fact, this code is all available from an earlier non-RTOS design.  
The issues I&#8217;m concerned about as I think this over are:  
1&#41; How does increasing the tick timer from something like 200 Hz to 4 Khz effect the overall throughput of the processor? Does this vary with CPU frequency? I&#8217;m guessing that it&#8217;s less important on a processor running at 156 Mhz than one running at 25 Mhz. Is this assumption valid?  
2&#41; The OS Tick Timer is usually placed at a low priority, which means it could be quite jittery depending on the interrupt loading of higher priority interrupts and code which masks interrupts. To get an accurate delay timer/scheduling/timer I may want to consider raising the priority of the scheduler. Are there problems with having the scheduler be the highest priority interrupt instead of the lowest? I suppose this question depends on my real-time requirements for my other interrupts.  
Has anybody had experience with this kind of a question?   
Thanks for any feedback.  
Todd
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick Rate vs Performance of RTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 18, 2012</div><div class="thread-post-content">First, the affect of high rick rates is a function of how much time a task switch takes vs how often you are going to force it to happen via a tick. A faster processor makes executes more instructions per unit time than the slower one, so a tick will us up a lower percentage of the time.  
Raising the priority of the OS Tick isn&#8217;t going to help the jitter, if it is caused by long interrupt execution time, as interrupt delay ALL task level processing, so doing the tick interrupt sooner in the interrupt nest isn&#8217;t going to get you to the task waiting for the time mark any faster, the other interrupt still need to be executed first. Note that if interrupt routines are taking significant time, that is a sign that there may not be an appropriate partition, with a RTOS, the interrupts should be doing the minimum needed to handle the interrupt, and any longer operations deferred to a task.  
My first feeling is that if you really have a need for a lot of 250usec resolution timing, something isn&#8217;t being specified right. I don&#8217;t find much call for the need to be that accurate in specifying time out values. Occasionally&nbsp; I will have a need to a task to have an occational short delay like this, in which case I will not set the tick rate that fast &#40;in part because tick based delays tend to have a jitter of 1 tick in them as you don&#8217;t know when in the current tick you are&#41; so if i need an occational precise short delay, I will use a timer interrupt as a one shot timer, and wait on a semaphore that the timer interrupt gives. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick Rate vs Performance of RTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 18, 2012</div><div class="thread-post-content">Just to add to richard&#95;damon&#8217;s reply:  
<blockquote>
  1&#41; How does increasing the tick timer from something like 200 Hz to 4 Khz effect the overall throughput of the processor? Does this vary with CPU frequency? I&#8217;m guessing that it&#8217;s less important on a processor running at 156 Mhz than one running at 25 Mhz. Is this assumption valid?
</blockquote>
The frequency at which the tick happens is fixed, no matter how fast the CPU is.&nbsp; The time taken to execute the tick will get longer the lower the CPU frequency, so the lower the frequency of the CPU, the higher the percentage of CPU time will be spent processing ticks &#40;and every other line of code will take longer to execute too&#41;.  
A 1KHz tick is already very fast.&nbsp; Most production systems will use a much slower tick frequency, and I would very rarely recommend going above 1KHz.&nbsp; If you want 4KHz then use a timer peripheral instead.&nbsp; If you want little jitter in the interrupt, then set its priority above configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY &#40;i.e. a lower numerical value on a Cortex-M3&#41; and don&#8217;t call any FreeRTOS API function.&nbsp; That will give you a jitter equal to the CPU&#8217;s own jitter time caused by the difference between entering an interrupt from a task, and entering an interrupt from another interrupt &#40;tail chaining and late arrival features of the Cortex-M3 allow you to get into an interrupt faster at the expense of jitter&#41;.&nbsp; On a Cortex-M3 running at 50MHz, this will be a jitter of about 70ns &#40;and measuring it shows it to be almost exactly equal the this theoretical value&#41;.  
With regards to changing the priority of the kernel interrupt.&nbsp; My advice is simply, don&#8217;t do that.&nbsp; It will break the interrupt nesting model of the Cortex-M3, and make your application extremely complex because you will have a set of lower priority tasks that cannot call the FreeRTOS API too.&nbsp; It also will not gain you anything anyway because you will end up calling more context switch functions that you need &#40;multiple obsolete calls in a single interrupt nest&#41;.  
Regards.

Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Tick Rate vs Performance of RTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/toddatm">toddatm</a> on May 18, 2012</div><div class="thread-post-content">Your input was very helpful. After reading your advice and thinking it over and talking to our other developers, I decided to leave the tick at a lower rate like 200 Hz, and use the hardware timers for those few cases we need a shorter, precise delay or need to measure something. We had no reason to schedule anything on such a fine time scale. After thinking it over, I realized that. And we&#8217;ll leave the OS tick timer at the lower priority as it is. Thanks.
