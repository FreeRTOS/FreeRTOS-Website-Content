</div></div><div class="thread-post"><h3 class="thread-post-title">What is the best way to organise the source?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 4, 2012</div><div class="thread-post-content">In short, you can organise the source code however it best works for you.  
My preference is to keep any code that is common across multiple projects in a single location on my computer, and then have all projects reference that.&nbsp; That is why the FreeRTOS distribution has two root directories, one to hold a single copy of the code, and one to hold x number of projects that all reference the single copy.&nbsp; If you are using Eclipse however, that kind of directory structure is nearly impossible to use, distribute or maintain unless you use it with standard makefiles &#40;because Eclipse doesn&#8217;t include a proper project management/build system&#41;.  
FreeRTOS configuration is done at the application level, using FreeRTOSConfig.h, which should be somewhere in your application directory structure, not in your FreeRTOS source tree.&nbsp; That way, the FreeRTOS code can remain unchanged across all applications that are using it.&nbsp; Building FreeRTOS to a library is ok, and quite common, but if you have a single library for all applications you loose that flexibility in configuration.  
A lot of people will have FreeRTOS as a directory in their project directory structure.&nbsp; That can be flat, or, maintain the same directory structure as the FreeRTOS distribution.&nbsp; The benefit of the latter is that you can drop updated FreeRTOS versions in without having to move any files around first.  
Generally, the only source files you need are:  
tasks.c<br />
list.c<br />
queue.c<br />
timers.c &#40;optional&#41;<br />
portable///portable.c &#40;and maybe an asm file from the same directory, depending on the port&#41;  
and the include path required is  
source/include<br />
portable//  
That is not many, and easy to manage.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">What is the best way to organise the source?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stephman">stephman</a> on May 5, 2012</div><div class="thread-post-content">Hello  
From my side, without saying this is the best method :  
&#45; I prefer to copy the FreeRTOS in my project directory that I can thus have several projects not using the same version.<br />
If you keep FreeRTOS in a single directory it becomes impossible to maintain your projects &#40;old projects will not compile anymore when you will update freertos&#41;. This is indeed mandatory to keep the source files of your projects that you can compile them at anytime without touching the code, especially in the industry  
&#45; For the project, I like this organisation in layers :<br />
&nbsp;&nbsp;&nbsp;&nbsp; HAL &#40;Hardware Abstratction Level&#41;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; adc.c, gpio.c, spi.c, and any very low level drivers &#40;register drivers&#41;<br />
&nbsp;&nbsp;&nbsp;&nbsp; HIL &#40;Hardware Independent Layer&#41;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; high level driver<br />
&nbsp;&nbsp;&nbsp;&nbsp; Services<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; FreeRTOS,&nbsp; ethenet stack, usb stack, modbus, FAT system, terminal, ….<br />
&nbsp;&nbsp;&nbsp;&nbsp; Application<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; My user code  
THis is the same organisation than Freescale does in its demo projects I guess…  
it has the benefit to organise well, to be easier to port on a new platform &#40;just change the HAL layers&#41;  
Regards<br />
Stephane
