  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">pcStatusString size</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/casper0">casper0</a> on May 17, 2012</div><div class="thread-post-content">Maybe I am the only one who likes to use long task names &#40;&gt;22 chars&#41;, or I am doing something wrong, but when I tried printing status for tasks with long names I ended writing beyond the end of available string space and corrupting other data.  
It appears that giving room for 30 characters for the variables ought to be enough and then add space for the longest possible task name.  
Current&gt;&gt;&gt; PRIVILEGED&#95;DATA static char pcStatusString; // Not enough space for long task names.<br />
Proposed&gt;&gt;&gt; PRIVILEGED&#95;DATA static char pcStatusString;  
I am also thinking of changing the &#8220;sprintf&#8221; to a &#8220;snprintf&#8221;, and limiting the string size to the available memory.  
Noticed this in FreeRTOS 7.1.0 and 7.1.1  
</div></div><div class="thread-post"><h3 class="thread-post-title">pcStatusString size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xz8987f">xz8987f</a> on May 18, 2012</div><div class="thread-post-content">Yes, any usage of sprintf&#40;&#41; in the FreeRTOS kernel is a source of buffer overflow. That&#8217;s why in my port/version for Processor Expert and CodeWarrior &#40;<a href="http://www.steinerberg.com/EmbeddedComponents/FreeRTOS%29">http://www.steinerberg.com/EmbeddedComponents/FreeRTOS&#41;</a> all calls have been replaced with save string routines which do not write beyond the buffers.<br />
I think a similar thing needs to be done for the Kernel base sources.  
Erich
</div></div><div class="thread-post"><h3 class="thread-post-title">pcStatusString size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 18, 2012</div><div class="thread-post-content">Ideally there would be no limit on the length of a task&#8217;s name, and the TCB would just contain a pointer to the string.&nbsp; However, that is dangerous because it is assumed that the string is persistent in memory, and not in a temporary buffer or on the stack.&nbsp; Therefore the name is instead copied into an array using the following code:  
<pre><code>strncpy( ( char * ) pxTCB-&gt;pcTaskName, ( const char * ) pcName, ( unsigned short ) configMAX_TASK_NAME_LEN );
</code></pre>
That should in theory prevent the array from overflowing, presuming strncpy&#40;&#41; is implemented correctly.&nbsp; The line of code that follows then ensures the string is terminated correctly, in case the entire array was filled.  
<strong>However</strong>, many C libraries that come with compilers require a large ROM footprint and huge stacks, so many FreeRTOS demos come with a cut down version of sprintf&#40;&#41; that has limited functionality, but requires very little ROM or RAM.&nbsp; To ensure projects still link, the file that contains the sprintf&#40;&#41; function also contains an snprintf&#40;&#41; function, but it is <strong>not</strong> implemented correctly and just blindly calls sprintf&#40;&#41;.&nbsp; If you project contains the file &#40;third party&#41; file named printf-stdarg.c, then this is most likely the cause of your problem.  
This has been discussed a few times here, and I think, although it is a third party file, I need to do something about it for the next release.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">pcStatusString size</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 18, 2012</div><div class="thread-post-content">Sorry guys, for the second time this morning I have provided an incorrect answer.&nbsp; Scrub my last reply above.&nbsp; It is not strncpy&#40;&#41; that is not implemented, it is snprintf&#40;&#41; that is not implemented in printf-stdarg.c.&nbsp; strncpy&#40;&#41; is not even mentioned in printf-stdarg.c.&nbsp; I mis-read your original post.  
See if I can do better this time….  
The reason snprintf&#40;&#41; is not used in prvListTaskWithinSingleList&#40;&#41; is for the reason I mentioned in my previous post, so maybe there was some accidental relevance to that post after all.  
I take your point that the arbitrary 50 in the code is a very bad thing.&nbsp; In fact, I&#8217;m surprised it is there as it breaks the coding standard for it not to use a define.&nbsp; I have just changed it to:  
<pre><code>PRIVILEGED_DATA static char pcStatusString[ configMAX_TASK_NAME_LEN + 30 ];
</code></pre>
Although that leaves a magic number, it is more than adequately sized.  
Regards.
