Is sam == 0? If so, that first xSemaphoreTake&#40;sam, 0&#41; may corrupt your system at which poin all bets are off on&nbsp; behavior.   
Note that one danger of creating a semaphore in a task, is that the other users of the semaphore need to check that the semaphore has been created before using it. I tend to create all my queues and semaphores in the startup code before any tasks start to run or interrupts are enabled, so that I don&#8217;t have this issue.

</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore Problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 31, 2012</div><div class="thread-post-content">In nearly every case in use today, portTASK&#95;FUNCTION does nothing, and the line of code   
<pre><code>portTASK_FUNCTION(thisTask, pvParameters)
</code></pre>
just expands to the following  
<pre><code>void thisTask( void *pvParameters )
</code></pre>
so it is just a standard C function.  
If you create the task using the xTaskCreate&#40;&#41; API function, then the task does not execute until the scheduler has been started using the vTaskStartScheduler&#40;&#41; API function.&nbsp;   
<strong>DO NOT</strong> call the function, it must only run as a separate task.  
You are going to have to single step through the code in your debugger to find out what the problem is.&nbsp; Concentrate on the environment &#40;linker script, etc.&#41; causing corruption and your own use of the API &#40;<a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>&#41; rather than looking for something in the FreeRTOS source code &#8211; if you are using an official FreeRTOS port it is highly unlikely that you will find a problem in the FreeRTOS source itself &#8211; although obviously not impossible.  
Regards.
