<h3 class="thread-post-title">uart interrupts lost with at91sam7x512</h3>
<div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 14, 2009</div>
<div class="thread-post-content">&gt; I&#8217;m using FreeRTOS 5.0.2 with GCC on an AT91sam7x512.<br />
&gt; Many characters are lost when receiving under interrupt on<br />
&gt; uart1 (38400 bauds), depending on what happens on other<br />
&gt; ports( ethernet, uart0).
<p>How is the ISR passing data to the tasks?  Circual buffer?<br />
Are you using the DMA?  The SAM7 has a really nice DMA on the UART.</p>
<p>&gt; I think that there is a lot of time spent between<br />
&gt; vPortEnterCritical and vPortExitCritical, while which<br />
&gt; interrupts are disabled : I have measured (using<br />
&gt; timer1 as counter) approximately 1ms when sending some html<br />
&gt; pages to the webserver task, sometimes it can go up to 3.5<br />
&gt; ms, sometimes more.</p>
<p>Unfortunately using a timer in this way is not going to give you the correct result &#8211; this is because each task maintains its own interrupt status state.  A task can yield from a point within critical section to a task that has interrupts enabled (I know this sounds odd but its all in the design, and intended behaviour), this will not show in your measurement.  The measurement will only stop when the critical section is exited, even if loads of other tasks have executed in between.</p>
<p>Regards.</p>

<h3 class="thread-post-title">uart interrupts lost with at91sam7x512</h3>
<div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 14, 2009</div>
<div class="thread-post-content">
<p>Its been a while since I looked at the SAM7 Ethernet driver (although coincidentally I will be doing some work on the SAM7 very shortly) but cannot recall any reason my sending should need interrupts to be disabled for any length of time.</p>
<p>The demo that comes with FreeRTOS serves a WEB page that shows the state of all the tasks in the system, their stack high water mark, etc.  Generating this page does leave interrupts disabled for a long time but only because it is traversing all the task lists and stacks and needs to generate a consistent snapshot of the system status.</p>
<p>It looks like your interrupt is buffering the data, then only sending on the queue when the buffer needs processing.  This is good and as intended (and not as per the demo drivers that send every character on the queue as its received &#8211; a very wasteful scheme).</p>
<p>Regards.</p>
</div>
