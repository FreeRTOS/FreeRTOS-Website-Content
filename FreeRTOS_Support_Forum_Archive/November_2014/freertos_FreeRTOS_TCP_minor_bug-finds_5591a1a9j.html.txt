Maybe we should make a check-list for &#8220;Writing a NIC driver for FreeRTOS+TCP&#8221;.
I&#8217;m thinking of these options, I&#8217;m sure you&#8217;ve seen them all:
<ul>
<li>The choice between BufferManagement_1 / 2
Version 1 is indeed preferred if your system has enough memory
Provide an allocation function for version 1.</li>
<li>Optional: ipconfigUSE_LLMNR : add the LLMNR multicast MAC address 01:00:5E:00:00:FC
to the list of MAC-addresses.
LLMNR is <strong>very useful</strong> for name resolution on a LAN, especially when using DHCP.
All browsers use LLMNR as a preferred way to find names (without a dot)</li>
<li>Optional: ipconfigDRIVER<em>INCLUDED</em>TX<em>IP</em>CHECKSUM</li>
<li>Optional: ipconfigDRIVER<em>INCLUDED</em>RX<em>IP</em>CHECKSUM
The NIC driver calculates the TX and/or RX checksum, either automatically within the
EMAC peripheral, in which case it is called &#8220;checksum offloading&#8221;.
Or by calling usGenerateChecksum().</li>
<li>Optional: ipconfigETHERNET<em>DRIVER</em>FILTERS<em>PACKETS
If you want to filter incoming messages within the NIC driver, enable this option.
The advantage: you might want to stop many UDP broadcast messages as early as
possible. W32, discovery protocols, PnP, simple network maintenance and other inventions
can occupy quite some resources: allocate a buffer, send it to the IP-task, which
will analyse and drop it.
See FreeRTOS</em>Sockets.c:</li>
</ul>
~~~~~<br />
        /* Function returns true if there is a UDP socket bound to
        the given port number. */
    BaseType_t xPortHasUdpSocket( uint16_t usPortNr )
~~~~~
<ul>
<li>Optional: ipconfigPACKET<em>FILLER</em>SIZE
This option is a bit tricky: it makes sure that all 32-bit fields in the network
packets are 32-bit aligned. This means that the 14-byte Ethernet header should
start at a 16-bit offset. Therefore ipconfigPACKET<em>FILLER</em>SIZE is defined a 2 (bytes).
I think that most EMAC&#8217;s have an option to set this 2-byte offset for
both incoming and outgoing packets.</li>
<li>Optional: ipconfigUSE<em>LINKED</em>RX_MESSAGES
An optimisation: Collect received packets in a loop and link them through a pointer
called &#8216;pxNextBuffer&#8217;. Several messages will be forwarded to the IP-stack within
a single &#8216;eNetworkRxEvent&#8217; message to the IP-stack</li>
<li>Optional: what I would do is check the Link-Status continuously. As long as the LS is
low, it doesn&#8217;t make sense to send messages. Check the PHY frequently, to have a quick
response once it gets connected.
As long as LS is high, check it e.g. every 15 seconds, unless packets are received,
which already proves that the Link-Status is high.</li>
</ul>
I&#8217;m repeating the word &#8220;Optional&#8221;. All these points aren&#8217;t necessary, but they can all improve the performance.
I will come back on the &#8220;8-byte alignment&#8221; issue, thanks for reporting that.
&#8216;configASSERT_VOID&#8217; was my not-so-useful invention, the idea was:
<pre><code>#define configASSERT_VOID(statement)    if( ( statement ) == pdFALSE ) return
</code></pre>
used in functions returning &#8216;void&#8217;.
Regards,
Hein

If you like you send what you have now to info at freertos point org. Then we can have a look at it (without revealing any code).
Or maybe this text will contain a hint:
The &#8216;ipconfigPACKET<em>FILLER</em>SIZE&#8217; may indeed be a bit confusing. It corresponds to what is named &#8216;ETH<em>PAD</em>SIZE&#8217; in lwIP.
~~~~~
    uint8_t *pucBuffer;
~~~~~
What is <code>sizeof( pucBuffer )</code> on your platform ? If it is 64-bits then indeed the (internal) function like &#8216;pxUDPPayloadBuffer<em>to</em>NetworkBuffer&#8217; will only work with 8-byte aligned buffers.
At the other hand, the library is not yet prepared for 64-bit pointers.
Every network buffer descriptor has this memory:
~~~~~
    0x00 4 bytes  pointer to the network buffer descriptor
    0x04 4 bytes  reserved for flags
    0x08 2 bytes  Alignment filler (ipconfigPACKET<em>FILLER</em>SIZEbytes)
    0x0a &#8216;ipTOTAL<em>ETHERNET</em>FRAME_SIZE&#8217; bytes
                  Here the packet begins with &#8216;xDestinationAddress&#8217;
<pre><code>#define ipTOTAL_ETHERNET_FRAME_SIZE  ( ipconfigNETWORK_MTU + 
    ipSIZE_OF_ETH_HEADER + ipSIZE_OF_ETH_CRC_BYTES + 
    ipSIZE_OF_ETH_OPTIONAL_802_1Q_TAG_BYTES )
</code></pre>
~~~~~
Please note that the packet data:
~~~~~
    uint8_t *pucEthernetBuffer
~~~~~
points to offset 0x0a (== ipBUFFER_PADDING) in the allocated space.
In your NetworkInterface.c you should allocate &#8216;ipTOTAL<em>ETHERNET</em>FRAME<em>SIZE + ipBUFFER</em>PADDING&#8217; bytes per network buffer. 
~~~~~
    #define UNIT<em>SIZE ( ipTOTAL</em>ETHERNET<em>FRAME</em>SIZE + ipBUFFER<em>PADDING )
    /* Here the aligned(8) attribute is used because DMA likes it. */
    static unsigned char network</em>packets[ ipconfigNUM<em>NETWORK</em>BUFFER<em>DESCRIPTORS * UNIT</em>SIZE ] <strong>attribute</strong> ((aligned (8)));
<pre><code>void vNetworkInterfaceAllocateRAMToBuffers( pxNetworkBuffers[ ] )
{
unsigned char *ucRamBuffer = network_packets;
int x;
    for (x = 0; x &lt; ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS; x++) {
        /* Add the 10 bytes */
        pxNetworkBuffers[ x ].pucEthernetBuffer = ucRamBuffer + ipBUFFER_PADDING;
        /* Set the pointer to the network buffer descriptor */
        *((unsigned*)ucRamBuffer) = (unsigned)(&amp;pxNetworkBuffers[x]);
        /* and point to the next space to assign. */
        ucRamBuffer += UNIT_SIZE;
    }
}
</code></pre>
}
~~~~~
Regards,
Hein

Note that sending messages always happens from the IP-task.
FreeRTOS+TCP is 100% thread-safe, not interrupt-safe. As you most probably know, there is a very small delay between calling xSemaphoreGiveFromISR() and the waking up from xSemaphoreTake().
The above approach has the advantage that the configured priorities govern the processing, and not the hardware 🙂
Personally, I tend to give the highest priority to the NIC task. We don't want to miss packets due to an RX overflow. The above routine emacps<em>check</em>rx() will only put received messages in a queue, and free the DMA buffers.
The second highest priority is for the IP-task, and all other tasks get a lower priority.
