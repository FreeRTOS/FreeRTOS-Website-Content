</div></div><div class="thread-post"><h3 class="thread-post-title">How do I access TCP Flags for a received packet in the FreeRTOS stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 21, 2014</div><div class="thread-post-content">The TCP flags are used by the low level TCP protocol to ensure the application is presented with a reliable and correct stream of data. So the application does not need to see the flags at all, it just sees the data.
The API provides a way of connecting and closing sockets and sending and receiving data. The implementation of the API will use the flags internally, there is no visibility to the application. Can you give an example of what you are doing that needs visibility to the internal implementation?

</div></div><div class="thread-post"><h3 class="thread-post-title">How do I access TCP Flags for a received packet in the FreeRTOS stack?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 21, 2014</div><div class="thread-post-content">Hi Rob,
You did a good job in short time!
Or maybe it proves that +TCP is not too difficult to adopt 🙂
<blockquote>
  Packet 2 has the FIN, ACK flags set, so how does my HTTP thread know
  that second packet is the end of the config.txt file? Or, indeed, any
  other file that it will be requesting? 
</blockquote>
You can inspect the contents and know how many bytes are expected:
<pre><code>Content-Type: multipart/form-data; uploadData.boundary=---------------------------114782935826962
Content-Length: 2241
-----------------------------114782935826962
</code></pre>
Or without the special token:
<pre><code>Content-Length: 2092
Keep-Alive: timeout=5
Connection: Keep-Alive
Content-Type: text/html; charset=utf-8
This is the contents consisting of 2092 bytes...
</code></pre>
At the lower level it is also possible: keep on reading from the socket until 
you see an error:
<pre><code>xResult = FreeRTOS_recv( xSocket, pcBuf, sizeof pcBuf, cFlags = 0 );
if( ( xResult &lt; 0 ) &amp;&amp; (xResult != -FREERTOS_ERRNO_EAGAIN ) )
{
    /* The peer has gone, socket may be closed */
}
</code></pre>
Where EAGAIN is not an error.
Normally you will see ENOTCONN, or ENOMEM in case a pvPortMalloc() has failed.
The TCP protocol is robust, the sender (Apache server) will not allow the connection to be closed until every byte has been confirmed.
+TCP guarantees that recv() will return a value >= 0, until the last byte has been read from the RX buffer.
The flags you pass to recv() :
At this moment the value of &#8216;flags&#8217; is ignored and it should be passed as zero. There are values (MSG<em>DONTWAIT, MSG</em>PEEK) that could be handy in some situations (and can be added soon).
In case of UDP, the value of flags is meaningfull: with FREERTOS<em>ZERO</em>COPY, frames can
be sent in a way that memcpy() isn&#8217;t called.
As Dave wrote: the TCP status is nothing to worry about, you only see streams of data.
For debugging however, see FreeRTOS_socket.h:
<pre><code>/* returns pdTRUE if TCP socket is connected */
BaseType_t FreeRTOS_issocketconnected( xSocket_t xSocket );
/* for internal use only: return the connection status */
/* See 'enum eTCP_STATE' in FreeRTOS_TCP_IP.h for the meaning of the
values. */
BaseType_t FreeRTOS_connstatus( xSocket_t xSocket );
</code></pre>
Regards,
Hein
