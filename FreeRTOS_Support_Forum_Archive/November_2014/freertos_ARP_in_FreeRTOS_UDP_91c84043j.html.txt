It&#8217;s mostly there but I have a suspicion there&#8217;s something strange going on with the Address Resolution Protocol.
Watching packets with Wireshark, I see that the echo clients send out echo request messages that appear to be properly formatted, but never get a reply. I know the echo server is working because I connected to it from my virtual Linux machine.
Both network ports are broadcasting ARP requests to find out who 192.168.1.2 is (that&#8217;s my FreeRTOS simulation), but apparently aren&#8217;t getting a response. Also I can&#8217;t get to the CLI from YAT, again probably because address resolution hasn&#8217;t completed properly.
Any hints? Clues? Has anyone else seen similar behavior?
TIA

Sorry, I&#8217;m confused.  If 192.168.1.2 is the FreeRTOS node, which are the other two network ports&#8230;and I thought FreeRTOS was now running on an LPCXpresso?

Is that what your LPCXpresso project is attempting to do too?  If so I don&#8217;t think that would work on real hardware, with a real network MAC and PHY because it won&#8217;t see its own traffic &#8211; whereas the simulator does see its own traffic.

</div></div><div class="thread-post"><h3 class="thread-post-title">ARP in FreeRTOS+UDP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/digitalwiz">digitalwiz</a> on November 5, 2014</div><div class="thread-post-content">Yes, it is the FreeRTOS Win32 simulator. I&#8217;m using the LPCXpresso Eclipse IDE to build and run the program.
The client/server pair works fine. Then there are two clients (one zero-copy, the other not) that talk to a standard echo server. The server is running on my Windows 7 workstation. As I said previously, I know the server is working because I can telnet to it either from a Windows shell or my virtual Linux machine.
The workstation itself has two network ports: Ethernet at 192.168.1.191 and WiFi at 192.168.1.192. I&#8217;m connecting FreeRTOS to the Ethernet port with address 192.168.1.2. The echo clients attempt to access the server at 192.168.1.191. It just occurred to me that maybe the problem is trying to talk to another node using the same interface, so I tried changing the server location to 192.168.1.192 and got the same thing.
In either case FreeRTOS appears to correctly resolve the MAC address for the server. The reverse does not seem to be true. Both 192.168.1.191 and 192 are continually broadcasting ARP requests inquiring about 192.168.1.2, but apparently getting no response.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARP in FreeRTOS+UDP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 6, 2014</div><div class="thread-post-content">Hi Doug,
It can be confusing to have two NIC&#8217;s with an address in the same range.
What you could try is, e.g. assign:
<pre><code>- 192.168.2.192 to Wifi
- 192.168.1.191 to Ethernet / LAN
</code></pre>
both with a netmask of 255.255.255.0.
I&#8217;m not sure about your W32, but Linux might receive a packet on the ETH and send a reply through WiFi, because they belong logically to the same network.
If the networks are different (192.168.1.x versus 192.168.2.x), the routing becomes very predictable.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARP in FreeRTOS+UDP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/digitalwiz">digitalwiz</a> on November 11, 2014</div><div class="thread-post-content">Turns out the header structures weren&#8217;t being packed properly. pack<em>struct</em>end.h for GCC looks like this:
    <strong>attribute</strong>( (packed) )
So as a shot in the dark I added a space after <strong>attribute</strong> and lo and behold the structures are now properly packed. There&#8217;s still something funny going on with the Sender and Target addresses that I have to sort out, but I&#8217;m making progress.
</div></div><div class="thread-post"><h3 class="thread-post-title">ARP in FreeRTOS+UDP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 12, 2014</div><div class="thread-post-content">I just checked the file and found it to contain the following:
<pre>__attribute__( (packed) );</pre>
That looks valid, and I&#8217;m not sure that changing it to:
<pre>__attribute__ ( (packed) );</pre>
makes any difference?
Regards.
