</div></div><div class="thread-post"><h3 class="thread-post-title">Need more detail of the uxPriority parameter in xCreateTask function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on October 28, 2015</div><div class="thread-post-content">What is portTICK<em>RATE</em>MS set to? </div></div><div class="thread-post"><h3 class="thread-post-title">Need more detail of the uxPriority parameter in xCreateTask function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 28, 2015</div><div class="thread-post-content">A few minor details before getting to the main point of your post:
<blockquote>
  s<em>LEDPeriod / portTICK</em>RATE_MS
</blockquote>
The recommended way of doing this now is to use the code &#8220;pdMS<em>TO</em>TICKS( s_LEDPeriod )&#8221; &#8211; although both will still work.
<blockquote>
  xTaskCreate( &#8230;, (signed char *)&#8221;Blink1&#8243;, &#8230;);
</blockquote>
be careful as to where the string passed in as the task parameter is allocated.  It will probably change with the compiler optimisation.  If it is allocated in const memory then there will be problem, but if it is allocated on the stack of the function that creates the tasks then there could be a problem as you will end up with one task referencing the stack of another function &#8211; maybe the main() function or maybe another task &#8211; and that memory is likely to change.
The easiest thing to do is declare the strings as file scope constants, such as:
static const char *pcString1 = &#8220;Blink1&#8221;;
and then pass in the pcString1 variable as the task parameter.
&#8230;.now onto your question, in addition to Richard Damon&#8217;s reply:
How is printf() implemented?  Where is it sending its output?  
printf() will often take a long time to execute, so may not be able to execute in time, and it is rarely re-entrant, which can cause corruption if two tasks try using it at the same time.  For example, if the output goes to a UART and one task starts to print &#8220;hello&#8221;, but half way through there is a switch to the other task, and that task prints &#8220;world&#8221;, then the output may look something like &#8220;helworldlo&#8221; (a context switch occurred between the two &#8216;l&#8217; characters.
You can protect printf from this type of problem using a mutex, or scheduler locking, etc.
