  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">freeRTOS hangs on bx r14 only during debug mode</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mamarina">mamarina</a> on October 27, 2015</div><div class="thread-post-content">freertos hangs during execution of prvPortStartFirstTask. Specifically, it hangs during the svc handler, when it tries to jump to r14 (via bx r14). r14 before the jump contains 0xFFFF FFFD. I am using lpc1768, with gcc on eclipse.
This only happens on debug, and runs fine otherwise (i have 2 tasks running). i am suspecting it has something to do with my debug configurations (ie startup commands), but I have no idea how to fix it. any pointer is appreciated.
</div></div><div class="thread-post"><h3 class="thread-post-title">freeRTOS hangs on bx r14 only during debug mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 27, 2015</div><div class="thread-post-content">It is most likely something to do with the interrupt vector table.  See the red text in FAQ 1 on this page: http://www.freertos.org/FAQHelp.html
Is it possible that the debugger is running a scrip that changes the vector table base address, but when you run without the debugger the change doesn&#8217;t happen? 
</div></div><div class="thread-post"><h3 class="thread-post-title">freeRTOS hangs on bx r14 only during debug mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mamarina">mamarina</a> on October 28, 2015</div><div class="thread-post-content">hi. thanks for the pointers. but still cant get it to work.
i have the 3 interrupt vectors mentioned on the faq. They&#8217;re defined in the freertosconfig.h
I am running from flash, so I didnt relocate the vector table to somewhere else. 
i have these lines in my startup:
monitor writeu32 0xE000ED08 = 0x00000000
monitor reg r13 = (0x00000000)
monitor reg pc = (0x00000004)
any more idea?
thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">freeRTOS hangs on bx r14 only during debug mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on October 28, 2015</div><div class="thread-post-content">0xFFFF FFFD is the return code, not the address it is returning too, and looks right. The address it returns to comes off the stack. The return code just tells the LPC the state being returned too.
</div></div><div class="thread-post"><h3 class="thread-post-title">freeRTOS hangs on bx r14 only during debug mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mamarina">mamarina</a> on October 29, 2015</div><div class="thread-post-content">Hi Dave, thanks for replying&#8230; 
But I thought that bx r14 would cause the processor to jump to the address in r14, which in this case is 0xFFFF &#8230;.. 
The arm website says so&#8230;
    http://infocenter.arm.com/help/index.jsp?topic=/com.arm.doc.dui0040d/Cabdcdci.html &#8230;
Or did i misunderstood something? 
Anyway, here is the full function:
~~~~
    __asm volatile (
                    &#8221;   ldr r3, pxCurrentTCBConst2      n&#8221; /* Restore the context. <em>/
                    &#8221;   ldr r1, [r3]                    n&#8221; /</em> Use pxCurrentTCBConst to get the pxCurrentTCB address. <em>/
                    &#8221;   ldr r0, [r1]                    n&#8221; /</em> The first item in pxCurrentTCB is the task top of stack. <em>/
                    &#8221;   ldmia r0!, {r4-r11}             n&#8221; /</em> Pop the registers that are not automatically saved on exception entry and the critical nesting count. <em>/
                    &#8221;   msr psp, r0                     n&#8221; /</em> Restore the task stack pointer. */
                    &#8221;   isb                             n&#8221;
                    &#8221;   mov r0, #0                      n&#8221;
                    &#8221;   msr basepri, r0                 n&#8221;
                    &#8221;   orr r14, #0xd                   n&#8221;
                    &#8221;   bx r14                          n&#8221;
                    &#8221;                                   n&#8221;
                    &#8221;   .align 2                        n&#8221;
                    &#8220;pxCurrentTCBConst2: .word pxCurrentTCB             n&#8221;
                );
~~~~
I checked that the r3 (at the beginning of the function) points to 1000 xxxx, so that looks correct since thats where my stack is.  Any other pointers how I can debug this?
