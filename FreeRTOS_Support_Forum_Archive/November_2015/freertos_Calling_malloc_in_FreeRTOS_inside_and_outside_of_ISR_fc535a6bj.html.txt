</div></div><div class="thread-post"><h3 class="thread-post-title">Calling malloc in FreeRTOS inside and outside of ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 23, 2015</div><div class="thread-post-content">Hi Pugglewuggle
<blockquote>
  I need to dynamically allocate some memory 1) from in a task, and 2) from in an ISR.
</blockquote>
Personally I would not recommend dynamically allocate memory from an ISR because:
<ul>
<li>Most allocators are not written to be called from an ISR.</li>
<li>ISR&#8217;s must be fast and most calls to [pvPort]malloc() have a variable processing time</li>
</ul>
Most people will use a queue and feed it with xQueueSendFromISR(). That will also wake-up a task which is waiting for data.
<strong>Volume data:</strong>
If the ISR produces bigger quantities of data, and if there is <strong>only one</strong> consumer-task of that data, then I would prefer to use a circular buffer, such as <code>FreeRTOS-Plus-TCPFreeRTOS_Stream_Buffer.c</code>. This can be accompanied with a call to <code>vTaskNotifyGiveFromISR()</code> (or <code>xSemaphoreGiveFromISR()</code> etc) which will wake-up the task.
<blockquote>
  Should I always use pvPortMalloc or is there any instance
  where I should used regular malloc from stdlib?
</blockquote>
I would not mix the use of both allocators. But if you want you can use the <code>malloc()</code> and <code>free()</code> from stdlib, and make those thread-aware with the wrap-arounds.
I tend to prefer using:
<ul>
<li>heap_4.c In case I have 1 block of contiguous RAM data available</li>
<li>heap_5.c In case there are several non-contiguous blocks of RAM</li>
</ul>
The algorithm used is safe and very fast.
<blockquote>
  Also, I need to dynamically allocate some memory in an ISR to create an item
  for a queue. Is it okay/a good idea to call some form of malloc/pvPortMalloc
  (depending on ths answer to my first question) inside an ISR? (is it
  thread-safe, too slow, etc?). I&#8217;m using heap_4 right now.
</blockquote>
Please have a look at:
<pre><code>FreeRTOS-Plus-TCPincludeFreeRTOS_Stream_Buffer.h
</code></pre>
As a simple example:
~~~~~
<h1>define    UART<em>DMA</em>BUFFER_SIZE    2048</h1>
StreamBuffer_t *pxBuffer;
void create<em>buffer()
{
size</em>t uxLength = UART<em>DMA</em>BUFFER<em>SIZE;
size</em>t uxSize;
<pre><code>/* Add an extra 4 (or 8) bytes. */
uxLength += sizeof( size_t );
/* And make the length a multiple of sizeof( size_t ). */
uxLength &amp;= ~( sizeof( size_t ) - 1u );
uxSize = sizeof( *pxBuffer ) - sizeof( pxBuffer-&gt;ucArray ) + uxLength;
pxBuffer = ( StreamBuffer_t * )pvPortMalloc( uxSize );
if( pxBuffer != NULL )
{
    /* Clear the header data. */
    memset( pxBuffer, ' ', sizeof( *pxBuffer ) - sizeof( pxBuffer-&gt;ucArray ) );
    /* Treat the 'LENGTH' member (all capitals) as a 'const member' */
    pxBuffer-&gt;LENGTH = uxLength;
}
</code></pre>
}
void uart<em>isr()
{
BaseType</em>t xHigherPriorityTaskWoken = pdFALSE;
<pre><code>reset__flags();
uxStreamBufferAdd( pxBuffer, 0, &amp;xDMA[ dma_index ], sizeof( xDMA[ dma_index ] ) );
vTaskNotifyGiveFromISR( xDMATask, &amp;xHigherPriorityTaskWoken );
portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
</code></pre>
}
void uart<em>task()
{
    create</em>buffer();
    install_isr();
<pre><code>for( ;; )
{
size_t uxCount;
    ulTaskNotifyTake( pdFALSE, ulMaxBlockTime );
    for( ;; )
    {
        uxCount = uxStreamBufferGet( pxBuffer, 0, uart_buffer, sizeof( uart_buffer ), pdFALSE );
        if( uxCount == 0 )
        {
            /* All data ave been read. */
            break;
        }
        /* Process uxCount bytes. */
    }
}
</code></pre>
}
~~~~~
I hope that the example is clear and useful.

</div></div><div class="thread-post"><h3 class="thread-post-title">Calling malloc in FreeRTOS inside and outside of ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 23, 2015</div><div class="thread-post-content">In addition to Hein&#8217;s post &#8211; when using an RTOS you can always defer the 
interrupt processing to a task.
Have a task block to wait for the interrupt, then unblock the task from 
the interrupt.  If the task has a high priority it will execute 
immediately after the interrupt &#8211; so processing occurs contiguous in 
time just as if it had all happened in the interrupt.  Once in the task 
you can call any API functions you like.
The fastest way of doing this is to use a direct to task notification. 
See 
http://www.freertos.org/RTOS<em>Task</em>Notification<em>As</em>Binary_Semaphore.html 
for a full example.
A more restricted method that requires fewer tasks is to use the 
centralised deferred interrupt processing feature:
http://www.freertos.org/xTimerPendFunctionCallFromISR.html

</div></div><div class="thread-post"><h3 class="thread-post-title">Calling malloc in FreeRTOS inside and outside of ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 23, 2015</div><div class="thread-post-content">If you REALLY want to use malloc in an ISR, you need to create a version of pvPortMalloc that uses a critical section (that disables interrupts) during the malloc/free call, and if interrupts nest, you need a pvPortMallocFromISR that blocks nesting during the call to malloc/free. Note, this has significant implicatons, and is really not recomended.
The alternative (and prefered method), is to use one of the methods provided in FreeRTOS to push the data allocation to a task. In my mind, whenever possible, I try to avoid using malloc once the system has completed its initialization phase, and our coding standards require this unless STRONG justification can be provided, as there are a lot of issues that need to be dealed with when you use dynamic memory in real time systems.
