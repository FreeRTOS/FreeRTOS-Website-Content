</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_recv always return 1</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on November 21, 2015</div><div class="thread-post-content">First some remarks that have nothing to do with your &#8220;FreeRTOS_recv always return 1&#8221; problem. I had another look at the <code>FreeRTOSIPConfig.h</code> that you posted earlier:
<pre><code>#define ipconfigARP_CACHE_ENTRIES                6
</code></pre>
That is may too little: it will only have 6 ARP entries. If you have many connections, there will often be unnecessary ARP lookup&#8217;s because ealier entries were overwritten.
<pre><code>#define ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS   96
</code></pre>
That is a lot. I would use that in a Xilinx Zynq, which has 1 GB of RAM available. In CPU&#8217;s with less RAM, 36 descriptors will be more than enough:
<pre><code>#define ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS   36
</code></pre>
While developing, it is always good to keep an eye on the actual usage of network buffer descriptors, such as in this code:
~~~~~
    {
        uxCurrentCount = uxGetMinimumFreeNetworkBuffers();
        if( uxLastMinBufferCount != uxCurrentCount )
        {
            /* The logging produced below may be helpful
            while tuning +TCP: see how many buffers are in use. */
            uxLastMinBufferCount = uxCurrentCount;
            FreeRTOS_printf( ( &#8220;Network buffers: %lu lowest %lun&#8221;,
                uxGetNumberOfFreeNetworkBuffers(), uxCurrentCount ) );
        }
    }
~~~~~
TCP stream buffer size:
<pre><code>/* Each TCP socket has a circular buffers for Rx and Tx, which have a fixed
maximum size.  Define the size of Rx buffer for TCP sockets. */
#define ipconfigTCP_RX_BUF_LEN            ( 0x4000 )
/* Define the size of Tx buffer for TCP sockets. */
#define ipconfigTCP_TX_BUF_LEN            ( 0x4000 )
</code></pre>
That gives a RX (and TX) stream buffer of 16384 bytes. If you would omit to call recv(), the socket will receive up to that amount of bytes.
Note that you can always overwrite these default buffer sizes for individual sockets.

FreeRTOS<em>recv() will only return a negative value ( usually -pdFREERTOS</em>ERRNO_ENOTCONN ) when the RX stream buffer is empty.
It is even possible that a TCP connection comes in, bytes are being received, and the connection is closed, <strong>before</strong> your application has had a chance to call FreeRTOS<em>accept(). This happens often in a FTP server when small files are being received.
In such cases, FreeRTOS</em>recv() will return a positive number as long as there is data to read.
<blockquote>
  socketclose.pcap
</blockquote>
This PCAP already looks better than ublaze.pcap: now therr is a normal and complete TCP conversation. There has been 1 retransmission.
<blockquote>
  TCPCommandServer.c
</blockquote>
Here above I posted some code. Why did not you try it out? It would have solved your problem.
Look at this code:
<pre><code>while (lBytes = FreeRTOS_recv( xSocket, ( void * ) cLocalBuffer, sizeof( cLocalBuffer ) /*RS returns 1 no matter how many chars are in the buffer*/, 0 )!= FREERTOS_SOCKET_ERROR)
{
}
</code></pre>
Doesn&#8217;t your compiler issue a warning about this expression? Think of the C priorities within expressions.
it says:
<pre><code>while( lBytes = ( FreeRTOS_recv() != FREERTOS_SOCKET_ERROR ) )
</code></pre>
And therefore lBytes can either become 0 or 1.
Could you try out the code that I posted here above?
