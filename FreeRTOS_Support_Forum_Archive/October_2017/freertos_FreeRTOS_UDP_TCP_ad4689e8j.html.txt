</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + UDP + TCP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 12, 2017</div><div class="thread-post-content">Hi Gerhard, once upon a time, there was <code>FreeRTOS_Plus_UDP</code>. This library could only do UDP, DHCP and ICMP(echo).
A couple of years ago, this stack was re-engineered and extended with a few more protocols, and it was called renamed to <code>FreeRTOS+TCP</code>.  The name <code>+TCP</code> is possibly misleading, it should have been called <code>FreeRTOS+UDP+TCP+DHCP+ICMP+FTP+HTTP+NBNS+LLMNR+etc</code> 🙂
In other words, what you should do is forget about the <code>FreeRTOS_Plus_UDP</code>, and work with <code>FreeRTOS+TCP</code>.
The two stack use the same principles, and they have the same kind of interface. Both stacks use a single IP-task that does all the work.
When working with <code>FreeRTOS+TCP</code>, start simple. Disable DHCP at first and give your device a fixed IP address. Try to ping it, and when that works, try DHCP and other protocols.
When you have questions, please post them here, in this thread.

  just replace-merge the FreeRTOS+TCP files into the LPC1830 example
</blockquote>
Right, remove the entire UDP stack, and include the +TCP stack.
I will attach the current driver for LPC18 here below ( see <code>LPC18xx_2017_oct.zip</code> )
It is a zero-copy driver, so please add the following to your <code>FreeRTOSIPConfig.h</code>
~~~
    #define ipconfigZERO<em>COPY</em>RX<em>DRIVER   1
    #define ipconfigZERO</em>COPY<em>TX</em>DRIVER   1
~~~
A few parameters to tune are the following:
~~~
    #define configNUM<em>RX</em>DESCRIPTORS                 6
    #define configNUM<em>TX</em>DESCRIPTORS                 4
    #define ipconfigNUM<em>NETWORK</em>BUFFER_DESCRIPTORS   15
~~~
And later on, you may want to tune some TCP parameters, <a href="http://www.freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/API/setsockopt.html">as describer here</a>
The &#8220;quad&#8221; flash in the LPC18 that I used was a bit slow, and I placed some frequently-used functions in RAM:
~~~
    #ifndef configPLACE<em>IN</em>SECTION<em>RAM
        #define configPLACE</em>IN<em>SECTION</em>RAM    <strong>attribute</strong> ((section(&#8220;.ramfunc&#8221;)))
    #endif
<pre><code>/* Move func() to RAM: */
configPLACE_IN_SECTION_RAM void func()
{
}
</code></pre>
~~~
The .LD file contains the <code>.ramfunc</code> entry, in the <code>RamLoc96</code> section:
~~~
    /* Main DATA section (RamLoc96) <em>/
    .data : ALIGN(4)
    {
       FILL(0xff)
       _data = . ;
       *(vtable)
       *(.ramfunc</em>)
       <em>(.data</em>)
       . = ALIGN(4) ;
       <em>edata = . ;
    } > RamLoc96 AT>SPIFI</em>4MB
~~~
If you have a fast flash, there is no need to move code to RAM.
Good luck!

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS + UDP + TCP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on October 15, 2017</div><div class="thread-post-content"><blockquote>
  From our UDP example it didn&#8217;t appear that we&#8217;re particularly CPU bound
</blockquote>
As you probably know, the Ethernet layer needs two components:
1) Ethernet Media Access Controller (EMAC)
2) Ethernet PHY
The EMAC is often an internal peripheral of the CPU. A PHY is an external component. The EMAC and PHY communicate through a high-speed bus, MDIO or a newer protocol.
Both FreeRTOS<em>Plus</em>UDP as well as FreeRTOS+TCP need a driver for these two components. This driver exists of a <code>xxx/NetworkInterface.c</code> file and some (modified) drivers provided by the chip manufacturer.
I recently started to split-up the PHY-driver and make a generic driver that should work on all boards. As soon as it is well-tested, I will publish it here on this forum.
