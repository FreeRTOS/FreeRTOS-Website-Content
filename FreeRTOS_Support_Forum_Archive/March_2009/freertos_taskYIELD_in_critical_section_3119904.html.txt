  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">taskYIELD() in critical section</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 19, 2009</div><div class="thread-post-content">In freeRTOS 5.1.12, there is a taskYIELD&#40;&#41; inside a critical section&#40;portENTER&#95;CRITICAL&#41; in function xTaskResumeAll. Is that ok? If disabling the interrupts before switching the context, who will preempt the new running task?
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 19, 2009</div><div class="thread-post-content">I really need to add this to the FAQ&#33;
Yes this is perfectly OK everywhere the scheduler does it, although i don&#8217;t recommend doing this in the application code unless you fully understand the consequences.
Each task maintains its own flags value so a task can yield from a critical section to a task that is not in a critical section &#8211; the original idea being that when the original task started to run again it would start from within a critical section and therefore have guaranteed access to the data structures.&nbsp; This reason has actually since disappeared but it is still safe.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 19, 2009</div><div class="thread-post-content">Maybe I&#8217;m missing the point here, but when you enter a critical section, uxCriticalNesting is incremented and the interrupts are disabled. The interrupts being disabled, no timer interrupt will give the kernel the tick. This means the current task&#40;the one becoming active after yield&#41; will run for an indefinite amount of time without being preempted.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 20, 2009</div><div class="thread-post-content">What you are missing is that as part of the context switch caused by the yield will re-enable the interrupts &#40;unless the new task was also in a critical section&#41; as uxCriticalNesting is stored on a per TASK basis.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 20, 2009</div><div class="thread-post-content">Well, first, I should say that my architecture won&#8217;t store the General Interrupt Flag in the Program Status Word, thus this flag will not be saved/restored at a context switch.
More, nowhere in the example ports did I see that uxCriticalNesting is stored on a per task basis. Could this feature be introduced later from the V5.1.2 or so? 
So I am still puzzled by this yield inside critical section.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 20, 2009</div><div class="thread-post-content">Ok, it is clear to me now, as I have inspected &#8216;tasks.c&#8217; and found this:
&nbsp;&nbsp;&nbsp; &#35;if &#40; portCRITICAL&#95;NESTING&#95;IN&#95;TCB == 1 &#41;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; unsigned portBASE&#95;TYPE uxCriticalNesting;
&nbsp;&nbsp;&nbsp; &#35;endif
So I&#8217;ll just have to redesign a little my context switch functions&#40;timer interrupt and yield &#8216;function&#8217;&#41; to use this feature.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 20, 2009</div><div class="thread-post-content">In most cases the critical nesting count is stored on the stack of the task, but in newer ports it is stored as part of the TCB.
Also, not wanting to add confusion to the discussion, but some ports now don&#8217;t actually yield until they leave the critical section.&nbsp; This part is very port specific.
Regards.

Which architecture are you using?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 22, 2009</div><div class="thread-post-content">Well, I am trying to port freeRTOS to NXP 51XA&#40;8051 eXtended Architecture&#41;. Upon interrupt, the stack contains the PSW&#40;program status word&#41;, PC&#40;program counter&#41;, and eventually, the CS&#40;Code segment&#41;, if using the non-page zero mode. Non-page zero mode means the controller will use more than 64KB of RAM and more that 64KB of code. I won&#8217;t go into much detail here, just for reference.
Anyway, if using the uxCriticalNesting inside the TCB, another problem arises: Who will set the member variable uxCriticalNesting to 0? Because, if it is not set to zero, the start count will not be consistent with the interrupts enable/disable state.

</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ringzro">ringzro</a> on March 28, 2009</div><div class="thread-post-content">Another problem found in xTaskCreate:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; portENTER&#95;CRITICAL&#40;&#41;;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; uxCurrentNumberOfTasks++;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if&#40; uxCurrentNumberOfTasks == &#40; unsigned portBASE&#95;TYPE &#41; 1 &#41;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; As this is the first task it must also be the current task. &#42;/
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; pxCurrentTCB =&nbsp; pxNewTCB;
well, my implementation of portENTER&#95;CRITICAL&#40;&#41; is on a per-task basis&#40;portCRITICAL&#95;NESTING&#95;IN&#95;TCB == 1&#41;, so uxCriticalNesting is contained within the TCB. Well, pxCurrentTCB is not initialized at the point portENTER&#95;CRITICAL&#40;&#41; is called here. So my implementation of portENTER&#95;CRITICAL&#40;&#41; will alter some RAM zone which is not a TCB.
I saw in the source code that there are two forms of entering critical: portENTER&#95;CRITICAL and taskENTER&#95;CRITICAL. Unfortunately, both refer to the same function/code snippet. Why not split them to have one of them&#40;taskENTER&#95;CRITICAL&#41; for tasks&#40;TCB based&#41; and the other&#40;portENTER&#95;CRITICAL&#41; for the whole system&#40;global uxCriticalNesting&#41;?
Of course, my implementation of portENTER&#95;CRITICAL could use both a global variable or the field from TCB, based on the scheduler state, but that would increase code size and timing.
</div></div><div class="thread-post"><h3 class="thread-post-title">taskYIELD() in critical section</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 28, 2009</div><div class="thread-post-content">The idea is &#40;was&#41; that user code does not call anything in the port layer directly, only the task and queue API.&nbsp; Therefore user code should call taskENTER&#95;CRITICAL&#40;&#41; not portENTER&#95;CRITICAL&#40;&#41;, although the two are mapped to the same code so in reality it makes no difference unless you switch code from one port to another.
When portCRITICAL&#95;NESTING&#95;IN&#95;TCB is set to 1 then the enter/exit critical section macros should map to vTaskEnterCritical&#40;&#41; and vTaskExitCritical&#40;&#41; &#91;defined in task.c&#93;.&nbsp; These functions will only attempt to access pxCurrentTCB if the scheduler is running to remove the risk of them accessing it before it have been set to point to a valid TCB structure.
Regards.
