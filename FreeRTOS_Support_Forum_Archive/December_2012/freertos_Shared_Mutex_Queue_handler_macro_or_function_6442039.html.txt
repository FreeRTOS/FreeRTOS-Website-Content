  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Shared Mutex/Queue handler macro or function?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jmmag">jmmag</a> on December 11, 2012</div><div class="thread-post-content">Hi, I am a little new to the RTOS game and have been writing some standard tasks that communicate with each other by using queues and an attached circular buffer &amp; mutex lock.&nbsp; I have not found any examples of this specific approach, and my current code blocks have become quite large, what with handling failure conditions &#40;&#33;= pdPASS, etc.&#41; and this has driven me to consider just putting the entire block into a function which can be shared by all the tasks, similar to:  
<pre><code>int queue_write(*queue, *mutex, *circularbuffer, *message_struct, *input_message_buffer, length){
take_mutex();
write_to_cbuff(circularbuffer, input_message, message_struct);
queue_send(message_struct);
give_mutex();
return pass_state;
}
</code></pre>
I just wanted to know if anyone saw any pitfalls to this approach, and if I should just put it into a big macro instead.  
Thanks&#33;<br />
Jon
</div></div><div class="thread-post"><h3 class="thread-post-title">Shared Mutex/Queue handler macro or function?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 12, 2012</div><div class="thread-post-content">Using a function may increase your stack usage a bit, using a macro will increase your program size a bit, that is the trade off.  
I often have an &#8220;encapsulation&#8221; function for a common sequence of operations.  
As to your example, while I know it is just a simplified version of your code, I wouldn&#8217;t expect your function to take the &#8220;message&#95;struct&#8221; parameter. It would take the input&#95;message, and the queue information &#40;queue, mutex, circularbuffer, perhaps wrapped into a single struct&#41;, and the write&#95;to&#95;cbuff function copies the message to the slot in the buffer and returns the pointer to the message struct it copied to, which is pushed onto the queue.  
I might be tempted to move the mutex into the circular buffer code, as long as it could handle message coming out in a slightly different order than they are enqueued if they come from different tasks.   
Also, rather than copying the data into a circular buffer, I often find it better to have a list of buffers, and tasks needing a buffer get one from the list, and pass the buffer address as &#40;part&#41; of the message, and the consuming task then puts the buffer back on the free list, this way I never need to copy the data from one buffer to another like your circular buffer seems to be doing.

I originally did that because the data going into the circular buffer are just byte arrays, and the message&#95;structs that go into the queue have other information about the message &#40;like message type, source task, etc&#41;, beyond just the message length and position in the circular buffer.&nbsp; That way I figured I could avoid dynamic arrays in structs.&nbsp; Though since the queue is really just a FIFO, having the start position in the message&#95;struct is somewhat redundant since I am only reading from the head of the circular buffer every time, anyway.&nbsp; You are probably right in that I should keep the queue stuff in one struct, it seems a bit messy my way.  
<blockquote>
  I might be tempted to move the mutex into the circular buffer code, as long as it could handle message coming out in a slightly different order than they are enqueued if they come from different tasks. 
</blockquote>
Yeah, I originally thought it would be nice to leave any RTOS code out of simple function like the circular buffer, and wasn&#8217;t quite sure the order in which the locking, circular buffer transfer, and queue transfer should take place.&nbsp; Suppose I could always add an extra layer…  
Also, what do you think about the potential synchronization issues between the queue and the circular buffer?&nbsp; The corresponding queue&#95;read&#40;&#41; function would ideally block on the queue rather than having to take the mutex every time before checking, but of course there is the chance that it could take the queue element and get interrupted by the write&#95;to&#95;cbuff&#40;&#41; before it is able to take the mutex.&nbsp; Since right now it&#8217;s strictly FIFO I don&#8217;t <em>think</em> it should be a problem, but once I start wanting to prioritize messages to the front of the queue, then I will have to consider the synchronization issues.  
<blockquote>
  Also, rather than copying the data into a circular buffer, I often find it better to have a list of buffers, and tasks needing a buffer get one from the list, and pass the buffer address as &#40;part&#41; of the message, and the consuming task then puts the buffer back on the free list, this way I never need to copy the data from one buffer to another like your circular buffer seems to be doing. 
</blockquote>
So it would essentially be a heap of fixed-length message arrays?&nbsp; Ideally, I wish I could just throw the message&#95;struct and the message array into the queue; that would definitely save me a lot of trouble.&nbsp; But my message arrays vary anywhere from a few bytes a hundred, so any fixed-length solution seemed inefficient to me.&nbsp; And I will probably end up with around 15 different tasks, each with their own message queue…  
Thanks again,<br />
Jon
</div></div><div class="thread-post"><h3 class="thread-post-title">Shared Mutex/Queue handler macro or function?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on December 12, 2012</div><div class="thread-post-content">My comment on moving the mutex into the buffer was dependent on the buffer being able to handle &#8220;out of order&#8221; retrieval operations which is beyond what a &#8220;normal&#8221; circular buffer would handle, unless it&#8217;s size was adequate so you didn&#8217;t need to worry about actually keeping track of the taking data out of the buffer.&nbsp; In this case there is no need for the read to do any synchronization, as the queue entry will provide a pointer into the buffer for the data, and this access is read only. Also, normally I have only one reader task for a queue, so there isn&#8217;t the same contention issue as the write side. You do need to put the data into the buffer before putting the request onto the queue, and if you want to support the out of order retrieval, the request needs to include the address in the circular buffer the data was placed in.   
My other comment was that rather than having each producer have a static buffer where it builds its request, to be then copied into the circular buffer, to then be copied out into a static buffer of the consumer, which is a lot of copying that isn&#8217;t really needed, you have the producer start by acquiring a buffer from some store, fill it with data, and then pass the address of that buffer via the queue to the consumer, which processes that data and when done, puts the buffer back into the store. This store COULD be the heap, if you are allowed to use it in the middle of processing. Normally dynamic allocations are not allowed in critical code unless there are fall backs for handling out of memory conditions &#40;like if the producer can hold off the request until more memory becomes available, or report upstream a failure/back off state&#41;. I find it is more often a fixed length list of maximum size buffers &#40;where the number of buffers is computed based on maximum system load and processing time&#41;. If the messages vary widely in size, it is also possible to have two &#40;or more&#41; stores based on the message size where small messages come from one store, and bigger from another. If you know the distribution of message sizes than this can save you memory. Note that you do NOT need a different buffer size for every size message, it could be a 10 byte buffer for 1-10 byte messages, a 100 byte buffer for 11-100 byte messages, and a 1k buffer for 101-1000 byte messages &#40;or what ever works best with your size distribution of messages and your knowledge of the number of messages of the various sizes you need to have being processed at any given time.
