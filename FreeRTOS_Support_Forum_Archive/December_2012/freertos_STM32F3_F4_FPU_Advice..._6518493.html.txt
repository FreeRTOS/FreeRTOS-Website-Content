  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32F3/F4 FPU Advice&#8230;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mudestinator">mudestinator</a> on December 25, 2012</div><div class="thread-post-content">I have a STM32F3 Discovery and I have ported FreeRTOS to it.&nbsp; My tool chain is GCC based.&nbsp; I used information from two separate supported ports.&nbsp; They were the CORTEX&#95;M4F&#95;Infineon&#95;XMC4500&#95;GCC&#95;Atollic and the second was the CORTEX&#95;M4F&#95;STM32F407ZG-SK.&nbsp; The first port had the correct tool chain, but wrong micro controller manufacturer.&nbsp; The second almost the correct micro controller, but the wrong tool chain.&nbsp; The port works and currently has two &#40;2&#41; components designed specifically to test the hardware FPU operation.&nbsp; The first component uses the eight &#40;8&#41; math tasks from the flop &#40;flop.c&#41; tests.&nbsp; These tasks have been modified for single precision operation, because the hardware FPU is single precision.&nbsp; The second component is a single instance of the register test task &#40;in assembly&#41;.&nbsp; The resulting demo runs with no errors.  
Both of the supported parent ports run with two &#40;2&#41; instances of the register test tasks &#40;in assembly&#41;.&nbsp; Unfortunately, I am only able to get one instance to run with the flops tests.&nbsp; It appear that one register test task causes the other to fail, but does not effect the flop tests.&nbsp;   
I believe that&nbsp; the FPU is fully operational and that FreeRTOS running properly.&nbsp; However, I am troubled that I can not get the&nbsp; second instance of the register test task running successfully.&nbsp; Any advice on how to proceed would be most appreciated.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F3/F4 FPU Advice&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 25, 2012</div><div class="thread-post-content"><blockquote>
  These tasks have been modified for single precision operation,
</blockquote>
There are a set of standard demo tasks that use single precision in FreeRTPS/demo/common/sp&#95;flop.c.  
<blockquote>
  It appear that one register test task causes the other to fail, but does not effect the flop tests.
</blockquote>
The flop tests only use a subset of the registers, whereas the reg test tasks use all the registers.  
To start with run just one register test task by itself &#40;comment out all the other tasks, including the check task, etc.&#41;.&nbsp; Run the register test task at priority 1 so even the idle task does not run.&nbsp; You can put a break point in the error loop within the register check task to let you know if it fails.  
Once that has run for a few minutes &#40;no point running it longer than that if nothing else is running&#41; then add in the second register test task also at priority 1 &#8211; now you will have just the two register test tasks and nothing else.&nbsp; Again put a break point in the error loop of the second register test task.  
Do the tasks run now?&nbsp; If not, determine which register is getting corrupted by looking at the registers in the debugger window, and if necessary stepping through the code &#40;you will have to manually set the program counter back to the top of the test loop to break out of the error loop.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F3/F4 FPU Advice&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mudestinator">mudestinator</a> on December 25, 2012</div><div class="thread-post-content">Thank you for the sage advice.&nbsp; All of the tasks are running properly.&nbsp; The error was a typo introduced while trying to make the GCC assembler happy with what was originally an IAR assembly file.&nbsp; I had further complicated the issue by converting the contents of the assembly file into inline assembly.&nbsp; I do not know what motivated me to add that complication.&nbsp; The assembly file should have modified only enough to make the GCC assembler happy.&nbsp; That would have minimized the chance of introducing an error.&nbsp; Changing the task priority to 1 was the key to solving the issue.&nbsp; Thank you again for your valuable assistance.  
Since the FPU is single precision, is the FPU utilized when double precision operations are performed?&nbsp; Essentially, should I ensure that all of the floating point operations in my project are single precision to get the most bang for my buck?&nbsp; Thank you for your advice.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F3/F4 FPU Advice&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 25, 2012</div><div class="thread-post-content">You will have to check the assembly code output by the compiler to know if the FPU is used for double precision operations, but in my experience I have found that double precision operations are emulated in software if you have a single precision FPU.  
I have also found you have to be extremely careful in how you write your C code.&nbsp; For example:  
float x = 1.1, y; /&#42; Define single precision floats. &#42;/<br />
y = x &#42; 2.0; /&#42; Multiple by a constant. &#42;/  
will result in x being promoted &#40;in line with the C promotion rules&#41; to a double, the calculation being done as a double precision emulated operation, then the result assigned to the single precision y.&nbsp; A lengthy operation.&nbsp; To avoid this you have to explicity state the type of constants as in:  
y = x &#42; 2.0F;  
Then that will be one hardware multiplication &#8211; many many times faster.  
Regards.  
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F3/F4 FPU Advice&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mudestinator">mudestinator</a> on December 25, 2012</div><div class="thread-post-content">Thank you again for awesome information/advice.&nbsp; As I stated earlier, my tool chain is GCC based.&nbsp; I was hoping the using the following optimization option would simplify things.&nbsp; I was also planning to test its effect by examining the assembly code output.&nbsp; A technique that I just recently learned &#40;i.e. last post&#41;.  
-fsingle-precision-constant<br />
Treat floating point constant as single precision constant instead of implicitly converting it to double precision constant.  
I will post my findings to the forum.
