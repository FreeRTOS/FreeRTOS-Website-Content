  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Suggested TICK_RATE_HZ and timing</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/znatok">znatok</a> on December 28, 2012</div><div class="thread-post-content">HI,<br />
I have a few questions:  
1&#46; I&#8217;m running on STM32 with 120MHz CPU clock what is acceptable range of configTICK&#95;RATE&#95;HZ for this case. I mean what is the max rate what will keep OS run time relatively small compared to processes run time.  
2&#46; What is an average process switch time? Based on this parameter I can answer question 1 as well.  
3&#46; I have an alphanumeric LCD on board and it&#8217;s working fine. But this type of LCD requires delays of about 100us after each character write. Currently I run with configTICK&#95;RATE&#95;HZ = 1000 and to implement 100us delay I busy loop.<br />
Do you have any suggestion on implementing sub TICK&#95;RATE&#95;HZ delays better then loop?  
Thanks.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Suggested TICK_RATE_HZ and timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 28, 2012</div><div class="thread-post-content"><blockquote>
  1&#46; I&#8217;m running on STM32 with 120MHz CPU clock what is acceptable range of configTICK&#95;RATE&#95;HZ for this case. I mean what is the max rate what will keep OS run time relatively small compared to processes run time.  
</blockquote>
Most applications use a tick of 10 to 100ms.&nbsp; I would not recommend going faster than 1ms.  
<blockquote>
  2&#46; What is an average process switch time? Based on this parameter I can answer question 1 as well.
</blockquote>
You have the hardware and compiler with your compiler settings in front of you so I suggest you just measure it.&nbsp; All context switches are performed by the PendSV handler, so you can time how long that takes to execute.&nbsp; If you are using FreeRTOS V7.3.0 then you can also define configUSE&#95;PORT&#95;OPTIMISED&#95;TASK&#95;SELECTION to 1 to save a few extra cycles at the cost of being limited to 32 different priority levels.  
<blockquote>
  3&#46; I have an alphanumeric LCD on board and it&#8217;s working fine. But this type of LCD requires delays of about 100us after each character write. Currently I run with configTICK&#95;RATE&#95;HZ = 1000 and to implement 100us delay I busy loop.<br />
  Do you have any suggestion on implementing sub TICK&#95;RATE&#95;HZ delays better then loop?
</blockquote>
If it is a small display that only holds a few characters you might be better off just using a delay of 1ms as it won&#8217;t be noticeable.&nbsp; If you have a large display, or are scrolling characters then the additional time would be noticeable.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Suggested TICK_RATE_HZ and timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/travfrog">travfrog</a> on December 29, 2012</div><div class="thread-post-content">We are also using the stm32 and several of the subsystems require usec timing. We run freertos at 1msec and use the chips HW timers for the usec timings. Set up the timer to interrupt at the time out value &#8211; in your case 100usec &#8211; and in the handler post a message to the LCD task &#8211; or have the LCD code block on a semaphore released in the interrupt handler. Use the macro portEND&#95;ISR&#95;SWITCHING &#40;true&#41; &#8211; I think that&#8217;s the macro &#8211; I don&#8217;t have the code in front of me at the moment. Returning true will ensure or LCD task executes immediately &#40;assuming it&#8217;s the highest priority task&#41;.  
We&#8217;ve examined this implementation on a scope and it&#8217;s pretty much dead on.  
Before this approach we actually ran the OS at 100usec &#8211; clearly too fast but it was a quick way to maintain the 100usec timings of the system while we converted it from a loop to FreeRtos. At 120MHz, the stm ran just fine. We then changed to 1msec and used HW timers &#40;about 5 timers being used in this manner&#41; and now the CPU spends most of its time doing nothing.  
Hope that helps.<br />
Richard
</div></div><div class="thread-post"><h3 class="thread-post-title">Suggested TICK_RATE_HZ and timing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/znatok">znatok</a> on December 29, 2012</div><div class="thread-post-content">I was thinking about running CPU timer and busy loop with taskYIELD checking the timer value advance. If no other process is ready to run I will catch delay period exactly at time otherwise I will be late but will let other process to run. Considering that LCD task priority is low it&#8217; s quite OK.
