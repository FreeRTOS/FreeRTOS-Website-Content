</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex-M0 LPC1114 port fails its testsuite</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 29, 2012</div><div class="thread-post-content">If the LEDs are still blinking then the kernel is still running &#8211; but &#40;as you say&#41; it indicates that one of the tasks has reported an error.&nbsp; I will need to know which task is reporting the error before making any conclusions.&nbsp; If it is one of the reg test tasks then that is likely to be a genuine problem &#8211; otherwise it is more likely to be a self checking margin being breached in one of the test tasks.  
The demo applications tend to load the CPU heavily.&nbsp; Several of the tasks will measure block times to ensure they fall within expected margins.&nbsp; If a block time is deemed to be too long then the task reports an error.&nbsp; However, the execution pattern depends on several things.&nbsp; For example, self checking tasks of this type have to be run at a high priority relative to other tasks to ensure they have a chance of running within their expected margin of error.  
If you are able to isolate which task is reporting a problem I can suggest ways of diagnosing the cause &#40;be it a genuine issue or otherwise&#41;.&nbsp; One way of doing that is to have each error condition in the check task &#40;or timer&#41; set a unique bit in a variable when it is triggered.&nbsp; Then put a break point on the line of code at the end of the check task &#40;or timer&#41; that increases the LED toggle rate when an error is detected.&nbsp; When the break point is hit inspect the variable used to log error bits to see test was the cause of the reported error.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Cortex-M0 LPC1114 port fails its testsuite</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 30, 2012</div><div class="thread-post-content"><blockquote>
  In the test suite for LPC1114 LPCXpresso port of FreeRTOS: &#8216;InterruptQueueTasks, BlockTimeTestTasks, RecursiveMutexTasks&#8217; all fails after few hours to days.
</blockquote>
Ok &#8211; more on that below.  
<blockquote>
  CountingSemaphoreTasks, Reg1TestTask and Reg2TestTask do not fail.
</blockquote>
That is good news.  
While the standard demo tasks predominantly test the scheduler, rather than the scheduler&#8217;s port to particular hardware, the RegxTestTasks very much test the hardware port itself.&nbsp; If these are not failing then it shows that the context switched in when a task starts to run exactly matches that switched out when it last ran.  
The InterruptQueueTasks and the BlockTimeTasks are always the most likely to fail, and I think these are false positives.&nbsp; The failure shows that the hardware is not keeping up with the tight demands of the test, rather than the port not working &#40;hopefully, nothing is ever guaranteed&#41;.  
The BlockTimeTasks are one of the task sets that measures a time before blocking on various events under different conditions, then measures the time again when it next runs &#40;unblocks&#41; before comparing the time after to the time before to see if it is within a reasonable bound.&nbsp; You can see that if the bounds are set to be marginal then things like higher priority tasks running, or additional interrupt loads can cause the bounds to be breached momentarily &#8211; and the error communicated to the check task.&nbsp; This is a standard test, so the bounds set are common to all hardware, and are therefore more marginal on the smaller CPUs like the M0s than the larger CPUs like the M3s.&nbsp; .  
The Int Queue tasks and interrupts inject a heavy&#40;ish&#41; interrupt load, but more importantly, a bit of pseudo randomness into the execution pattern.&nbsp; The two errors you are seeing are in fact related &#8211; one causes the other.&nbsp; The tests themselves are actually very convoluted and not easy to follow, but they do provide excellent test coverage.&nbsp; They too are really designed to run on ports with a full nesting model, whereas the M0 has &#40;if I recall correctly&#41; a slightly simpler nesting model due to the limitations in the hardware itself &#40;when compared to its larger M3 and M4 cousins&#41;.  
Regards.
