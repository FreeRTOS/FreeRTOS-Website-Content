</div></div><div class="thread-post"><h3 class="thread-post-title">is the function&#8221;eTaskGetStateFromISR&#8221;exist?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 21, 2015</div><div class="thread-post-content">Normally suspending/resuming a task like this is really the wrong thing to be doing. If the task wants to wait for a DMA interrupt then wait for a semaphore that is set by that interrupt. That way you can add a timeout on the wait and the task can handle its own cleanup. (You can also use the task notification system as a lightweight version of this).
Also killing and restarting a task is a good way to mess up your program enviroment. Maybe you know that task doesn&#8217;t hold any resources in this case, but in general it can be very bad. On &#8220;Big&#8221; OSes, you can kill a PROCESS and restart it, as the OS knows what resources a process owns and can clean those up. Tasks are much more light weight.
</div></div><div class="thread-post"><h3 class="thread-post-title">is the function&#8221;eTaskGetStateFromISR&#8221;exist?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 21, 2015</div><div class="thread-post-content">Just to re-iterate and emphasise Richard Damon&#8217;s point &#8211; using task suspend/resume as a synchronisation method in this way is <strong>dangerous</strong> and can lead to missed interrupts if there is a chance an interrupt arrived before the task has suspended.  Suspending and resuming had no method of latching that an interrupt occured.  I would also second the suggestion that the correct way to do this is with a semahore, because a semaphore does latch that an interrupt has occurred &#8211; better still use a <a href="http://www.freertos.org/RTOS-task-notifications.html">direct to task notification</a> as that is faster and has no RAM overhead.
