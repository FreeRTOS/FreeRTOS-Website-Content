  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ricardo_crudo">ricardo_crudo</a> on August 6, 2015</div><div class="thread-post-content">Hi.
I&#8217;m running FreeRTOS 7.4.2 over LPC1759. The problem was isolated creating a code to blink leds using timer0 and timer1. In this case I&#8217;m allocating memory before create any task or call vTaskStartSchedule. I holds the execution putting a while(1) just before the memory allocation and the leds blink as expected,  but if while(1) goes just after the memory allocation line, leds blinking period are affected. The period becomes <strong>quite bigger</strong> than before. Going into the freeRTOS code I found out this starts to happen afer call xTaskResumeAll function in pvPortMalloc.
I&#8217;m using a older FreeRTOS version because this code come from an already existing project. It used to work with 1788.
Any thought is appreciated.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 6, 2015</div><div class="thread-post-content">I&#8217;m a little confused by your post, but think you have the following scenario:
<ul>
<li>The scheduler has not been started yet.</li>
<li>You are using two hardware timers to blink LEDs, one LED per timer.</li>
<li>After a call to pvPortMalloc() the rate at which the LEDs are blinking changes.</li>
</ul>
Is that correct?
Are your timers using interrupts?  If so, then interrupts are deliberately left masked (up to configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY) once you start using the FreeRTOS API.  That is done to prevent any interrupts attempting to use the scheduler before the scheduler has been started.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ricardo_crudo">ricardo_crudo</a> on August 7, 2015</div><div class="thread-post-content"><blockquote>
  Is that correct?
</blockquote>
yes, that&#8217;s correct. 
<blockquote>
  Are your timers using interrupts?
  Are your timers using interrupts? If so, then interrupts are deliberately left masked (up to configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY) once you start using the FreeRTOS API. That is done to prevent any interrupts attempting to use the scheduler before the scheduler has been started.
</blockquote>
Yes, they&#8217;re using interrupts. This mean I can&#8217;t allocate memory before start the scheduler?
Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 7, 2015</div><div class="thread-post-content">If you allocate memory using pvPortMalloc then interrupts will get masked. You can re-enable them manually as long as you are careful that interrupts don&#8217;t use the scheduler beore it is started.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/e-christenson">e-christenson</a> on August 9, 2015</div><div class="thread-post-content">I disagree here.  My (speculative) diagnosis (based on a dsPIC30F CPU) is that freeRTOS has changed the period register of the timer the LED flasher is using, because freeRTOS is using the same timer for the scheduler.
Another possibility (based on freeRTOSv8.2.1 and the dsPIC) is that the critical section exit in the portMalloc code has enabled other interrupts which are causing the LED flasher to miss interrupts.
Beyond that, this is the point at which knowing exactly how your interrupt controller works and checking on its state (as well as the timer) with the debugger are your friend!  
&#8220;Use the source, Luke&#8230;use the source&#8221;  (lol)
</div></div><div class="thread-post"><h3 class="thread-post-title">Timers period are affected after allocate memory [LPC1759]</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 10, 2015</div><div class="thread-post-content">On a Cortex-M FreeRTOS only tinkers with the SysTick timer (the timer built into the core of the Cortex-M, rather than a periphral).  The SysTick timer is not configured until the scheduler is started.
