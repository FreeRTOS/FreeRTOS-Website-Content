  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">API resquest and idea &#8230;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/debugasm">debugasm</a> on August 28, 2015</div><div class="thread-post-content">Hello everyone,
I have used freeRTOS for many time, although the start was tragic now I get along pretty well. I use freeRTOS on Xilinx hardware with MicroBlaze CPU, one of these days I&#8217;ll try on Zynq.
In my projects I have never used an external CPU but I always all centralized 
around the FPGA. By working alone, I prefer use one device so a single development tool with which to do everything.
My last project was very complex with many Tasks that were created, deleted. These communicate with each other using different &#8220;Queue&#8221;, &#8220;Semaphore&#8221;, for using Custom Hardware on FPGA. I have used Lwip for Web Server, TFTP, Announce, Discovery.
I come to the question. After all this time I have had in mind a couple of APIs 
that may be added to freeRTOS. I wanted to try alone to implement them, just for fun, but because of the limited time, I ask the community developers if these APIs may be useful.
<strong>(1)</strong>
In the latest versions of freeRTOs there is the ability to use the &#8220;TaskNotify&#8221;, 
optimal solution. The only drawback using it is that you should always store 
the &#8220;TaskHandle<em>t&#8221; in global variable. You can implement an API that passing 
&#8220;pcName&#8221; of the TaskFunction to get the &#8220;TaskHandle</em>t&#8221; ?   
<pre><code>:::python
BaseType_t xTaskCreate( 
                        TaskFunction_t pvTaskCode, 
                        const char * const pcName, 
                        unsigned short usStackDepth, 
                        void *pvParameters, 
                        UBaseType_t uxPriority, 
                        TaskHandle_t *pvCreatedTask 
                      );
</code></pre>
&#8220;const char * const pcName&#8221;  : Give the name at &#8220;TaskFunction&#8221;
&#8220;TaskHandle_t pvCreatedTask&#8221; : &#8220;TaskHandle&#8221; that identifies the task, to be stored globally for access
Using an API like this:
TaskHandle_t xTaskGetTaskHandleByName( const char * const pcName ); 
I could get &#8220;TaskHandle&#8221; looking for the name given. If not assigned any name I can not find TaskHandle of interest. I would avoid so store it globally.
It could be useful ?    
P.S. At this point all API that use &#8220;TaskHandle_t&#8221; can be have Override with 
&#8220;&#8230;ByName&#8221; API version.
<strong>(2)</strong>    
In large project I always using a &#8220;malloc&#8221; and &#8220;free&#8221; routine with &#8220;heap_4.c&#8221; code. The memory region is very large (64 MByte) and for speed-up MicroBlaze init I have create separate section on memory with this :    
<pre><code>:::python
/* Allocate the memory for the heap. */
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ] __attribute__((section(".heap_noload")));
</code></pre>
With custom section in linker &#8220;lscript.ld&#8221;
<pre><code>:::python   
.heap_noload (NOLOAD) : {
    . = ALIGN(8);
    _heap_noload = .;
} &gt; memory_S1_AXI_BASEADDR
</code></pre>
So far no problem.
The most boring thing at this point is that memory once allocated must always be freed if no longer used. To avoid memory is then fully occupied if ever released. The most serious problem is the &#8220;vTaskDelete&#8221;. I can not delete a task that use memory with &#8220;malloc&#8221;. Therefore I must first send a signal with the &#8220;Queue&#8221;, &#8220;Semaphore&#8221; or &#8220;TaskNotify&#8221; to free up memory, and then &#8220;vTaskDelete&#8221; for terminate the task.
The code written in &#8220;heap<em>4.c&#8221; uses a proprietary algorithm, which works very well. I imagined that if you change the structure of block memory &#8220;BlockLink</em>t&#8221; :
<pre><code>:::python
/* Define the linked list structure.  This is used to link free blocks in order
of their memory address. */
typedef struct A_BLOCK_LINK
{
    struct A_BLOCK_LINK *pxNextFreeBlock;   /*&lt;&lt; The next free block in the list. */
    size_t xBlockSize;                      /*&lt;&lt; The size of the free block. */
} BlockLink_t;
</code></pre>
With inserting a &#8220;TaskHandle_t&#8221; of the Task that uses the memory block. The structure of memory block could become:
<pre><code>:::python
/* Define the linked list structure.  This is used to link free blocks in order
of their memory address. */
typedef struct A_BLOCK_LINK
{
    struct A_BLOCK_LINK *pxNextFreeBlock;   /*&lt;&lt; The next free block in the list. */
    size_t xBlockSize;                      /*&lt;&lt; The size of the free block. */
    TaskHandle_t vCreatedTask; 
} BlockLink_t;  
</code></pre>
On call of &#8220;malloc&#8221; function the routine add &#8220;TaskHandle_t&#8221; of the task that calling. With &#8220;vTaskDelete&#8221; I can free memory in an automatic way, freeing up all the memory used by the Task.
It could be useful ?    
P.S. : I know the memory allocated to each task, free it completely in one shot, even if you use a store nested type.
debugasm
</div></div><div class="thread-post"><h3 class="thread-post-title">API resquest and idea &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 28, 2015</div><div class="thread-post-content">A short answer to a long email :o)
I think both of these are very good ideas.  A couple of notes of caution though:
1) Using at task name
Obtaining the handle of a task from its name would be quite a lengthy operation as it would require string comparison.  It may be possible to speed that up using caching, or hashing, or both (as per the directory name hashing using in FreeRTOS+FAT).
2) Freeing the memory used by a task
It might be dangerous to automatically free all the memory allocated by a task itself if, for example, the task created a queue and other tasks were still using the queue. There are other examples too, for example if a task created a persistant buffer etc..  So there would have to be a means of a task somehow noting which memory should be left unfreed.
Another possibility might be to have a task register which blocks of RAM should be freed when the task was deleted.  The function called from the Idle task that frees the task&#8217;s stack and TCB could then also free the memory the task had specifically said should be freed.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">API resquest and idea &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 28, 2015</div><div class="thread-post-content">One comment on the idea of trying to free memory allocated to a task. This is really only an issue if you are trying to &#8220;remote kill&#8221; a task asyncronously. Tasks are NOT a &#8216;Process&#8217; which are kept distinct with well defined and limited interfaces to other Tasks/Processes and that the OS can keep track of resources and clean up when the process is killed.
Tasks are part of a cooperative enviroment, and can share resources between tasks without the OS needing to keep track of things. They are much more &#8220;entangled&#8221; than processes (and in fact are basically threads in a classical OS)
This means that the method used on some &#8220;heavy&#8221; OSes of monitoring a process and killing it if it looks hung just isn&#8217;t normally appropriate for a system eeded data/signals not being rnlike FreeRTOS. If a task isn&#8217;t responding properly, you really don&#8217;t know how big the issue is, and really the only true solution would be to reset the system.
Rather than trying to build a watchdog on a processes poised to kill it and restart it, write the process defensively so it can&#8217;t get locked up, and error checks on not getting data/signals that it needs and reports the errors &#8220;upline&#8221;. Such a task won&#8217;t need to be killed and restarted. Having done that, if things &#8216;hang&#8217; then it is clear that you do need to restart to clear things (perhaps with an opertunity to go to a debugger first to analyse the system to debug way things hung).
