~~~~~

        ( ( TickType<em>t ) 1000 / configTICK</em>RATE_HZ )

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+UDP: Reasons behind TICK_RATE limit</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on August 23, 2015</div><div class="thread-post-content">Hi François,
Because it is Sunday, a little more about the tick- or clock-rate:
For a UDP stack, the clock-rate isn&#8217;t very important. The ARP tables and DHCP have relatively slow timers, in units of seconds.
For TCP however, time must be accurate: ACK&#8217;s are sometimes sent after a 200 ms delay, and retransmissions are also well-timed.
FreeRTOS+TCP has been tested mostly with a <code>configTICK_RATE_HZ</code> of 1000 Hz, but I assume that higher clock rates (including 1024) should work equally well.
( As you probably know&#8230; ) all FreeRTOS blocking functions have a parameter of type <code>TickType_t</code>. It defines the <em>maximum</em> number of clock ticks that a function should block.
In the TCP and UDP source code, you might find code like this:
~~~~~
    uint32<em>t ulDelayMs = 2;
    TickType</em>t xTickCount = pdMS<em>TO</em>TICKS( ulDelayMs );
    xSemaphoreTake( xSemaphore, xTickCount );
~~~~~
Waiting for 1 clock tick is tricky: the function might return within a few uS if the clock tick is about to come.
The above code will not work well with a 500 Hz clock, because <code>pdMS_TO_TICKS(2)</code> would return 1.
On a lower clock rate, <code>pdMS_TO_TICKS(2)</code> will even return 0, hence the API won&#8217;t block at all.
( NB. the prefix &#8220;pd&#8221; is an abbreviation of the source file name &#8220;projdefs.h&#8221; )
If you want to write portable code that runs with every clock speed, you might want to use the following <code>pdMS_TO_MIN_TICKS()</code> :
~~~~~
    #define pdMIN<em>TICKS( xTimeInTicks ) 
        ( ( ( xTimeInTicks ) &lt; ( TickType</em>t ) 2 ) ? ( ( TickType<em>t ) 2 ) : xTimeInTicks )
    #define pdMS</em>TO<em>MIN</em>TICKS( xTimeInMs ) 
        pdMIN<em>TICKS( ( ( ( TickType</em>t ) ( xTimeInMs ) * configTICK<em>RATE</em>HZ ) + 500 ) / ( TickType_t ) 1000 )
~~~~~
It rounds up and it returns a minimum value of 2. Sorry for the use of a &#8220;ternary conditional operator&#8221;, the &#8220;<code>a?b:c</code>&#8221; expression.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+UDP: Reasons behind TICK_RATE limit</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 23, 2015</div><div class="thread-post-content">Actually, you get the same problem at higher ticks, If you want to be sure you delay at least 2 tick periods, you need to delay for 3, as a delay of 2 might return after a delay of only 1.0001 ticks. For bigger values the error is still there, it just isn&#8217;t as noticable.
Also, your routine doesn&#8217;t &#8220;Round Up&#8221; but Rounds, so with a 100 Hz tick, a request for 22ms delay will give you a 2 tick, or 20ms delay (actually a 10.0001 &#8211; 20 ms delay). If you want to be absolutely sure that you never delay less than the spec you need to really round up (add +999 and then divide by 1000) and then add 1 to account for the short first tick.
