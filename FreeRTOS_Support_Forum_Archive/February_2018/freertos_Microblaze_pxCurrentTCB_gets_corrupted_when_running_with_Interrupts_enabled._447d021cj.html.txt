  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Microblaze : pxCurrentTCB gets corrupted when running with Interrupts enabled.</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardd">richardd</a> on February 5, 2018</div><div class="thread-post-content">Hi,
We are running a multi-thread application on a Xilinx Microblaze softcore and we are seeing that after approximately 15hours of running that the pxCurrentTCB which is returned from taskSELECT<em>HIGHEST</em>PRIORITY<em>TASK is corrupt.
The system is running with 3 interrupts enabled:
1. System Timer Interrupt (10ms)
2. I2C Interrupt (random, but usually every second or so)
3. Video Interrupt (approximately every 16mS).
All the threads run at the same priority of &#8220;tskIDLE</em>PRIORITY + 1&#8243;. And two of the threads  are woken up by Interrupts from the I2C and Video Interrupt. 
We have enabled the integrity checking on the task list, using configUSE<em>LIST</em>DATA<em>INTEGRITY</em>CHECK<em>BYTES, and when we do this we see pxCurrentTCB is being set to pdINTEGRITY</em>CHECK_VALUE (0x5a5a5a5a). So we are pretty sure that we are not overwriting memory and corrupting the lists.
We are also running with configCHECK<em>FOR</em>STACK<em>OVERFLOW=2 and portSTACK</em>GROWTH=-1, and the stack checking has not fired so again we don&#8217;t think we are corrupting memory.
The Xilinx toolchain is XSDK 2017.3.
We have searched the forum and have seen that other people have reported similar issues on the Cortex M3, but don&#8217;t think this is relevant as the microblaze only has a single interrupt priority?
Any help in resolving this issue would be much appreciated!
Thanks in advance,
Richard
</div></div><div class="thread-post"><h3 class="thread-post-title">Microblaze : pxCurrentTCB gets corrupted when running with Interrupts enabled.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 5, 2018</div><div class="thread-post-content">Are your interrupt priorities at or below configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY? (Might be a different name in the Cortex-A port &#8211; Google FreeRTOS on Corex-A to find it.
Also do you have configASSERT() defined?
</div></div><div class="thread-post"><h3 class="thread-post-title">Microblaze : pxCurrentTCB gets corrupted when running with Interrupts enabled.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardd">richardd</a> on February 6, 2018</div><div class="thread-post-content">Hi Richard,
We certainly have been concerned about the documentation surrounding the configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY. Searching through the Xilinx BSP for freeRTOS 9.01 v1.1, we see no reference to this define. We also checked for the following and none are defined or used in the BSP, configKERNEL</em>INTERRUPT<em>PRIORITY configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY and configMAX<em>API</em>CALL<em>INTERRUPT</em>PRIORITY.
So it seems that there are no INTERRUPT Priorities setup with the Microblaze port of freeRTOS?
The microblaze has a single interrupt pin which is driven from an external interrupt controller which has 5 interrupts attached:
 Video interrupt = 0 (We see the configAssert on a thread which is woken buy this interrupt)
 I2C interrupt = 1 (Used)
 UART Interrupt = 2 (Not used)
 System Timer Interrupt = 3 (Used for thread switching)
 SPI Interrupt = 4 (Not Used)
Looking at the Xilinx ISR handler if multiple interrupts occur at the same time then they would be service starting at ID = 0.
Yes, configAssert is assigned, I have attached a stack trace for a capture of the error condition. 
It seems that while attempting to wait on a semaphore the pxCurrentTCB get corrupted. This is after approximately 15 hours, with the semaphore wait occuring about every 16ms, it is signalled by the Video Interrupt ISR.
Thanks for your support!
Richard
