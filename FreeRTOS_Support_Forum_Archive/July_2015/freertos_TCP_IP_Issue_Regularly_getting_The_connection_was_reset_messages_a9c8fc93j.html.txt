We handled the issue directly through email. Now for the readers of this forum, here below is a summary of the things that we have found:
Your HTML server replied with data, but you had forgotten to include a &#8216;Content-Length&#8217;, as in:
<pre><code>HTTP/1.1 200 OK
Date: Sun, 9 Aug 2015 22:27:48 GMT
Content-Length: 10&lt;CR&gt;&lt;LF&gt;
&lt;CR&gt;&lt;LF&gt;
contents&lt;CR&gt;&lt;LF&gt;
</code></pre>
The browser didn&#8217;t like the answers it was receiving and it kept on creating new connections. At your site, the half-closed sockets weren&#8217;t properly removed (closed) and after a while all TCP resources were exhausted.
Also I wrote that in a HTML server, sockets must only be closed after a function returns a negative value (normally <code>FreeRTOS_recv()</code> returning <code>-pdFREERTOS_ERRNO_ENOTCONN</code>). In principle, the browser is responsible for shutting down unused connections.
Later you asked me why it takes so much time for your bootloader to download its firmware. I answered with the following text:
If you have very little RAM, try at least to make &#8216;<code>Win</code>&#8216; double as large as &#8216;<code>MSS</code>&#8216;. See:
http://www.freertos.org/FreeRTOS-Plus/FreeRTOS<em>Plus</em>TCP/API/setsockopt.html
with the option <code>FREERTOS_SO_WIN_PROPERTIES</code>.
(
With &#8216;<code>Win</code>&#8216; I mean the Window size of the TCP-slicing-windows. It is the maximum amount of data that can be outstanding before receiving an ACK. The RX buffer size must always be <strong>at least</strong> as big as &#8216;<code>Win</code>&#8216;, preferably double the size of &#8216;<code>Win</code>&#8216;.
&#8216;<code>MSS</code>&#8216; stands for Maximum Segment Size: it is the amount of nett TCP-data (or payload) that will fit in a single Ethernet packet. In the source-code it may be defined as:
<pre><code>#define ipconfigTCP_MSS (ipconfigNETWORK_MTU - ipSIZE_OF_IP_HEADER - ipSIZE_OF_TCP_HEADER)
</code></pre>
)
TCP performance is greatly enhanced if there can be at least 1 outstanding packet.
In the following example you will get &#8216;<code>Win = 2 * MSS</code>&#8216; for both directions:
<pre><code>/* Declare an xWinProperties structure. */
xWinProperties_t  xWinProps;
/* Clear the struct, just in case it will
get extended in the future. */
memset( &amp;xWinProps, ' ', sizeof( xWinProps ) );
/* Fill in the required buffer and window sizes. */
/* Unit: bytes */
xWinProps.lTxBufSize = 2 * ipconfigTCP_MSS;
/* Unit: MSS */
xWinProps.lTxWinSize = 2;
/* Unit: bytes */
xWinProps.lRxBufSize = 2 * ipconfigTCP_MSS; // two or more
/* Unit: MSS */
xWinProps.lRxWinSize = 2;
</code></pre>
If your MCU has very little RAM you might want to try a smaller MSS:
<pre><code>#define  ipconfigTCP_MSS        536
</code></pre>
and get an RX buffer size of at least 2 * 536 = 1072.
If you have enough RAM, you may want to use the maximum of:
<pre><code>#define  ipconfigTCP_MSS       1460
</code></pre>
Note that you do not set <code>ipconfigTCP_MSS</code> directly, it will be derived from what you define for MTU:
<pre><code>#define ipconfigNETWORK_MTU    1500
</code></pre>
So in order to get an MSS of 536, you&#8217;ll define MTU as 536 + 40 = 576:
<pre><code>#define ipconfigNETWORK_MTU     576
</code></pre>
After changing the TCP buffer sizes, you wrote: &#8220;The speed of the bootloader is staggering now. It programs it faster than a JTAG interface&#8221;.
Thanks for that,
Regards.

About <code>[v]s[n]printf()</code> :
You can use <code>printf-stdarg.c</code> if you define:
~~~~~
    BaseType<em>t xApplicationMemoryPermissions( uint32</em>t aAddress )
    {
        return 3;
    }
<pre><code>void vOutputChar( const char cChar, const TickType_t xTicksToWait )
{
}
</code></pre>
~~~~~
In the earlier (antique) version of <code>printf-stdarg.c</code>, <code>sprintf()</code> could be called with a NULL pointer, and then all characters would be forwarded to <code>vOutputChar()</code>, which is very slow.
If you do provide a pointer, vOutputChar() will never be called.
About <code>xApplicationMemoryPermissions()</code> : sometimes you are debugging code and by mistake you write:
~~~~~
    /* By mistake you put a %s in stead of %d */
    sprintf(buf, &#8220;Result = %s&#8221;, iValue);
~~~~~
The integer value of &#8216;iValue&#8217; (-1) probably points to non-existent memory and the debugging code itself will cause your application to crash. which is frustrating.
The mentioned function can prevent this by telling if the memory referred to has RD and/or WR permissions. It will print out: <code>"Result = INV_MEM"</code>
Why not simply use the standard provided family of <code>[v]s[n]printf()</code> ?
<ul>
<li>Because it uses a huge amount of stack space > 1000 bytes</li>
<li>Because it doesn&#8217;t seem to thread-safe, at least in Xilinx</li>
<li>Because it may omit to put a nul character if the result doesn&#8217;t fit</li>
</ul>
~~~~~
    char buffer[ 5 ];
    snprintf( buffer, sizeof( buffer ), &#8220;%s&#8221;, &#8220;Hello world&#8221; );
<pre><code>/* Now buffer will contain a non-terminated string 'hello',
whereas the 'printf-stdarg.c' version will print 'hell' */
</code></pre>
~~~~~
