</div></div><div class="thread-post"><h3 class="thread-post-title">New mutex crashing application!</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 30, 2011</div><div class="thread-post-content">Do you have stack overflow checking switched on?  
As this is an STM32, are you <strong>absolutely</strong> sure you have the interrupt priorities set correctly. Take care especially with the way the interrupt priority is split into preemption bits as the STM32 libraries default differently to all the other Cortex base chips. Item number 3 here is often quoted in this forum <a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>  
Consider also using a malloc failure hook function although your check for null should catch that in your case.

</div></div><div class="thread-post"><h3 class="thread-post-title">New mutex crashing application!</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 30, 2011</div><div class="thread-post-content"><blockquote>
  as the scheduler starts I am just falling through to:   
</blockquote>
DEFAULT&#95;ISR&#95;HANDLER HardFaultException 
Is xTaskStartScheduler&#40;&#41; returning? If so you are running out of heap when the idle task is being created. If xTaskStartScheduler&#40;&#41; is not returning, step through the code to find where the exception is happening. If you can&#8217;t do that then you can inspect the stack in the exception handler to find the PC value when the exception happened, but that is fiddly.  
If xTaskStartScheduler&#40;&#41; is not returning, does the first task ever start?  
<blockquote>
  xLEDSemaphore = xSemaphoreCreateMutex&#40;&#41;;<br />
  &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if &#40;xLEDSemaphore == NULL&#41;<br />
  &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; i = 6;  
</blockquote>
However, it does not drop to the i = 6 line. 
But it is returning from xSemaphoreCreateMutex&#40;&#41;?  
<blockquote>
  don&#8217;t have stack overflow checking, no. Do I understand correctly that each task would need to do its own checking? If I did switch this on I would still need to use uxTaskGetStackHighWaterMark in each task? 
</blockquote>
Overflow trapping will only work during a context switch, so when the scheduler is running. It might not help then if you have a problem starting the scheduler.  
<a href="http://www.freertos.org/Stacks-and-stack-overflow-checking.html">http://www.freertos.org/Stacks-and-stack-overflow-checking.html</a>  
<blockquote>
  If I understand correctly, the tasks have their own stacks and anything else is done from the heap. So, if you have an initialisation routine that is called once and never again, that would use the heap? As an aside, Is it bad practice to do the latter? Should all initialisations be done in the task itself before the infinite loop is reached?&nbsp;   
</blockquote>
main&#40;&#41; uses the stack from the linker script. Tasks have stacks allocated from the heap. Semaphores are allocated from the heap.  
Are you using heap&#95;1.c or heap&#95;2.c, or a different heap manager? If you are using heap&#95;1.c or heap&#95;2.c then the heap is statically allocated so the linker should take care of it. If you are using something else then it could be that the heap is being overflowed, or a linker script problem.

I am guessing that FreeRTOS doesn&#8217;t check to see whether the tasks hae asked for more than the available memory for its tasks and that Crossworks only complains if the amount of stack space claimed by FreeRTOS is more than the memory available.

I don&#8217;t really buy&nbsp; the latter, all of which would more suggest the heap is being&nbsp; overstretched.&nbsp; I&#8217;ll see if I can make the heap bigger.

<blockquote>
  OK, I have changed the&nbsp; configMINIMAL&#95;STACK&#95;SIZE to be 100
</blockquote>
That figure is in words, not bytes, so 100 will be 400 bytes of stack on a Cortex-M3.  
<blockquote>
  That would indicate my tasks are taking too much RAM I assume.
</blockquote>
?  
<blockquote>
  In fact, having counted, I have 18 tasks, most of which are allocated minimum task size<br />
  …<br />
  In fact, having counted, I have 18 tasks, most of which are allocated minimum task size, I am estimating my tasks are using around 3k. 
</blockquote>
If configMINIMAL&#95;STACK&#95;SIZE is 100, and you have 18 tasks, then that is 18 &#42; 400 = 7.2K bytes.&nbsp;   
<blockquote>
  Some of the initialisation routines that are run once take several hundred bytes. I assume that the system uses memory from the heap for this and it&#8217;s then freed up so they shouldn&#8217;t be the issue
</blockquote>
? That would be a strange assumption, unless malloc&#40;&#41; is being called anywhere.&nbsp; I would assume that, if you are talking about stack usage during initialisation, then that memory would come from the stack.  
Again, I strongly suggest reading about memory management in FreeRTOS.
