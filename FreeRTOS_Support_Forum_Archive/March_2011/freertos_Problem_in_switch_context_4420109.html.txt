  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem in switch context</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/naomihochberg">naomihochberg</a> on March 20, 2011</div><div class="thread-post-content">I use FreeRTOS with PIC24F15KA102. My application includes only one task &#40;except the idle task&#41; and I work with&nbsp; non nested interrupts and total disable interrupts for portDISABLE&#95;INTERRUPTS&#40;&#41;. In ISRs messages are entered to Q. Messages are received and&nbsp; handled by the task. Sometimes I reach the point where msg Q is full,but&nbsp; the task is not running although it is ready.  
Problem is caused by the fact that in vTaksSwitchContext&nbsp; scanning the ready lists and decrementing the global variable uxTopReadyPriority is not protected from interrupts.&nbsp; It may be changed by ISR that enters the message to Q during the following loop and than be&nbsp; overwritten in the loop.  
/&#42; Find the highest priority queue that contains ready tasks. &#42;/<br />
while&#40; listLIST&#95;IS&#95;EMPTY&#40; &amp;&#40; pxReadyTasksLists &#41; &#41; &#41;<br />
&#123;<br />
-uxTopReadyPriority;<br />
&#125;  
When I put the scanning loop under disable interrupts&nbsp; problem is solved.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on March 20, 2011</div><div class="thread-post-content">It sounds like you are doing something very wrong. Are you calling API functions that do not end in FromISR from inside an ISR? Are you enabling interrupts in the ISR in the wrong way, etc, etc. If it is being used correctly, the problem you describe will not happen.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/naomihochberg">naomihochberg</a> on March 24, 2011</div><div class="thread-post-content">I call xQueueSendToBackFromISR&#40;&#41; that calls xTaskRemoveFromEventList&#40;&#41; that calls prvAddTaskToReadyQueue&#40;&#41;<br />
that modifies uxTopReadyPriority&nbsp; &#40;in ISR&#41;.   
vTaskSwitchContext&#40;&#41;&nbsp; is call by&nbsp; portYIELD&#40;&#41;&nbsp;&nbsp; called by the Idle task.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on March 24, 2011</div><div class="thread-post-content">In that port, portYIELD&#40;&#41; disables interrupts up to the priority set by configKERNEL&#95;INTERRUPT&#95;PRIORITY, and there is a documented restriction that interrupts that call ISR safe API functions cannot use a priority above configKERNEL&#95;INTERRUPT&#95;PRIORITY &#8211; therefore, if the usage instructions are being followed, it should not be possible for the two code sections you highlight &#40;one inside an interrupt, and one outside of the interrupt&#41; to interfere with each other.  
That is the intention anyway &#8211; I&#8217;m always happy to be proven wrong.  
Regards
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/naomihochberg">naomihochberg</a> on March 27, 2011</div><div class="thread-post-content">In&nbsp; PIC24F15KA102 none nested interrupt mode it is impossible to write to IPL bits of SR register.&nbsp; ISR will always run in higher priority than none ISR routines.<br />
Does that mean that it is impossible to use FreeRTOS in none nested interrupts mode ?
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/naomihochberg">naomihochberg</a> on March 31, 2011</div><div class="thread-post-content">I use nested interrupts and configure all interrupts to configKERNEL&#95;INTERRUPT&#95;PRIORITY. It is actually the same as working in none nested interrupts mode. This way portYIELD&#40;&#41;&nbsp; disable interrupts before vTaskSwitchContext&#40;&#41; is called<br />
and my application is working OK.  
Thanks to richarfbarry for the explanation. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem in switch context</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on April 12, 2011</div><div class="thread-post-content">Hello naomihochberg,<br />
I had the same problem on my LPC2468 &#40;ARM7TDMI-S&#41; and FreeRTOS 6.1.1. I have implemented nested interrupts by re-enabling all IRQs on entrance in a wrapper ISR. I mask out from configKERNEL&#95;INTERRUPT&#95;PRIORITY to configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY and I have to mask out before calling <em>vTaksSwitchContext</em>.  
Your denoted loop in <em>vTaksSwitchContext</em> isn&#8217;t safe using xFromISR functions if the CSW can be preempted by that syscall-level IRQs with xfromISR calls. If using any other traps that cannot interrupt IRQs everything is safe again .   
I think this behavior should be considered in one of the next releases or should be mentioned correctly in the documentation as it only denotes   
<blockquote>
  To utilize this scheme your application design must adhere to the following rule: Any interrupt that uses the FreeRTOS API must be set to the same priority as the kernel &#40;as configured by the configKERNEL&#95;INTERRUPT&#95;PRIORITY macro&#41;, or at or below** configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY** for ports that include this functionality
</blockquote>
Regards,<br />
Roman
