  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STR912 issue (eclipse + gcc + hitex)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cpelissi">cpelissi</a> on December 4, 2007</div><div class="thread-post-content">Hello everybody,
I have trouble in using SRT912 and FreeRTOS. I am using the STR9 USB stick coming from Hitex. Normally, it should be quite straightforward to run freeRTOS on the stick due to the already existing port for the STR912 dev board on IAR dev tools. But for me it doesn’t.
The Hitex USB stick is coming with the GNU cross-compiler and the hitex IDE and debugger. Due to some stability issues in using the Hitex tools. I am not sure to still use the Hitex debugger in the future. For this reason, i try to set up my configuration right now using eclipse + mingw make + gnu compiler provide by hitex. For sure I still use Hitex debugger to flash and make bug tracking.
I have rewritten the asm file of the STR912 demo from IAR asm to GNU asm. And wrote a make file with an application which do nothing except launching the idle task. I was hopping to be able see this task running alone.
To avoid ARM-thumb switching issue all the code is compiled for ARM code today.
Stepping in my application seems to be OK until vTaskStartScheduler&#40;&#41;-&gt;xPortStartScheduler&#40;&#41;-&gt;vPortStartFirstTask&#40;&#41;;&nbsp;&nbsp;&nbsp; 
As it has been designed this function is just a call to the macro portRESTORE&#95;CONTEXT
At the end of this macro, just before jumping, every thing seems to be OK&#8230;
the registers are correctly initialized &#40;R1=0101&#8230;, R2=0202&#8230; and so on&#41;
The LR register has the address of the idle task + 4&#8230;
We are in supervisor mode&#8230;
But stepping the &quot;subs&quot; instruction is issuing an Undefined instruction exception. I do not understand why.
If someone has already faced with this problem I greatly seek its support.
Regards,
Christophe
</div></div><div class="thread-post"><h3 class="thread-post-title">STR912 issue (eclipse + gcc + hitex)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on December 5, 2007</div><div class="thread-post-content">It sounds like you have everything in the expected state.&nbsp; Particularly the Supervisor mode, I thought this was going to be your problem until I got to the bottom of your email.
Can you check that you don&#8217;t have THUMB&#95;INTERWORK defined in your makefile &#40;as -DTHUMB&#95;INTERWORK&#41;.&nbsp; Also, is the address in the LR on a four byte boundary?
</div></div><div class="thread-post"><h3 class="thread-post-title">STR912 issue (eclipse + gcc + hitex)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cpelissi">cpelissi</a> on December 5, 2007</div><div class="thread-post-content">Thanks Dave for your message&#33;
i have double checked. i am sure that :
 &#45; i am in supervisor mode, 
 &#45; i am not using the THUMB&#95;INTERWORK define 
 &#45; the address in the LR register is clearly on a 4 byte boundary and this address is the prvIdleTask function + 4
I have made several searches on this forum and on the web. i have seen that there is a pending issue on GCC compiler which gives unsafe behaviour to the portSAVE&#95;CONTEXT function. but i think &#40;maybe i am wrong&#41; that my problem is not in relation with this issue.
To be sure i have transformed the C definition portSAVE&#95;CONTEXT portRESTORE&#95;CONTEXT into assembleur macro. This will avoid the compiler to perform unsafe coding.
the opcode i have on my debugger is exactly the one written in the macro file
I still searching&#8230;
Regards,
Christophe
