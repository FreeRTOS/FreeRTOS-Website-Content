</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate problem on Atmega128</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcraw101">dcraw101</a> on December 8, 2007</div><div class="thread-post-content">I am using the FreeRTOS queue to hold incoming serial bytes.&nbsp; The RX ISR adds to the queue every time it receives a byte.&nbsp; We have a requirement to hold at least 1500 bytes in the queue as the remote transmitter sends out huge chunks of data periodically.&nbsp; My application does not need preemption so I was considering using coroutines for everything to save memory.&nbsp; Actually, I don&#8217;t even need to use FreeRTOS for my application, but I was hoping it would help structure and separate the different threads of my code.
I guess I could create my own global array of 1500 bytes and implement my own RX buffer.&nbsp; Then I would create a FreeRTOS queue of zero length and use that to essentially semaphore my coroutine when a new byte arrives.
Doug
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate problem on Atmega128</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sotd">sotd</a> on December 8, 2007</div><div class="thread-post-content">As far as I know the Mega128 had 4K bytes of RAM so you would never be able to create a buffer of 30K even if queues could be that big.
To get over the 255 you can either just change the type used in the functions or define portBASE&#95;TYPE to be a 16bit type.&nbsp; The latter would be inefficient in some cases.
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate problem on Atmega128</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcraw101">dcraw101</a> on December 8, 2007</div><div class="thread-post-content">If I did increase portBASE&#95;TYPE to a 16 bit type would it affect stability?&nbsp; Do any atomic operations on the Atmega128 depend on working with 8 bit types.&nbsp; Does portBASE&#95;TYPE need to be a signed value?
</div></div><div class="thread-post"><h3 class="thread-post-title">xQueueCreate problem on Atmega128</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/boozle">boozle</a> on December 10, 2007</div><div class="thread-post-content">Given the large blocks to be received, and the likely need to prevent overflow, I would create a standard interrupt driven serial handler which manages its own buffers.&nbsp; 
This interrupt handler should run at a higher priority than the clock tick and have no interaction with the RTOS.&nbsp; The RTOS should not totally disable interrupts in its critical regions, except for the time required to mask off all interrupts associated with the RTOS, after which the serial interrupt will be re-enabled. I know the 8051 interrupt system hardware is structured to enable this type of operation but others may not. 
Set up like this the serial interrupt code can then break into the RTOS at any time, run to completion, return from interrupt leaving the stack unchanged as viewed by the RTOS.&nbsp; A standard task can then monitor the buffer status extracting and inserting blocks of characters.&nbsp; 
In a similar situation I have used multiple RX buffers which are acquired and released via a state machine associated with each buffer, Rx buffer states are:&#40;created &amp; free&#41;, &#40;receiving&nbsp;&nbsp; characters&#41;, &#40;full &amp; ready for processing&#41;&#41;, &#40;being processed&#41;, then back to &#40;created &amp; free&#41;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;
