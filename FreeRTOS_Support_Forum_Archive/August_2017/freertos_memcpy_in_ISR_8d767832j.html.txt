</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on August 22, 2017</div><div class="thread-post-content">The execution time might be unknown to <em>you</em>, but it is certainly clear and deterministic.  A simple memcpy() implementation will copy the given number of characters, one by one.  You have the call overhead, and you have the loop for each character &#8211; the loop count is known when you call memcpy().  With strcpy(), the loop count is the length of the string, which may or may not be known by you.
If you have a more sophisticated compiler and enable optimisations, then memcpy is often inlined.  If the count is known at compile time, and alignments are known to the compiler, then it can use larger moves than characters, unroll the loop, and in some cases it can omit the memcpy altogether if it can see it is unnecessary.
</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on August 22, 2017</div><div class="thread-post-content">memcpy/strcpyy for small buffers shouldn&#8217;t be a time issue, if you need to move the data, it is probably the fast option. 
The one issue is that on some processors and some compilers, memcpy might be placed inline with code that uses some floating point registers. There exists a few corner cases where the FP registers in the ABI are considered &#8216;caller save&#8217; (normally called functions are allowed to trash these registers), but the standard interrupt prolog doesn&#8217;t save them, as it isn&#8217;t expected for ISRs to use floating point. (I beleive this is the case with the Cortex M4F). There tends to be an option to prevent this optimization.

</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on August 22, 2017</div><div class="thread-post-content">This is an interesting one &#8211; and the answer is not as straight forward as some of the posts in this thread make out.  It is something we have often considered ourselves and concluded that, as you don&#8217;t know in advance how many bytes are to be copied, the best and most efficient in the general case way of doing this is to call the standard C memcpy() function.
memcpy() needs to be efficient, so their implementations are normally intricate, but optimised for moving large amounts of data.  That means they are not necessarily optimised for moving small amounts of data &#8211; where a byte by byte copy would be the most efficient.  The need to be efficient and intricacy means assembly language is used (even required) with an excellent knowledge of the hardware architecture and characteristics.  That means that, unless you know in advance what the maximum number of bytes that are to be copied are, it is extremely unlikely you will come up with a more efficient general memcpy() algroithm.
memcpy will typically perform byte copies to get the to/from addresses word aligned, then word copies until the to/from addresses are aligned to the requirements of any other more efficient move implementation that might be available on the architecture in question.  That might be moving instructions by using push multiple and pop multiple instructions, or, as David B noted in this thread already, using wide floating point registers.
Using floating point registers is where it gets interesting, and gets back to Michael&#8217;s original question about if it is ok to use memcpy() in an ISR.
Some FreeRTOS ports require the application writer to specify which FreeRTOS tasks use flop registers, and FreeRTOS will then only store a flop context for those tasks (because flop context&#8217;s can be very expensive in memory and time).  However, if the standard C library uses flop registers for memory operations then every task will need a flop context, and if flop registers are used in an ISR, then each ISR will need to save/restore flop registers too.  Luckily I have only seen this be a problem once, and never on a Cortex-M.

In case you do encounter problems, you might want to try the attached module <code>memcpy.c</code> ( see below ). It is pretty well optimised and it is absolutely ISR-safe.

There is the &#8220;automatic inlining&#8221; of <code>memcpy()</code>, in case the actual length is small and known at compile time. Please be aware that compilers sometimes make erroneous assumptions about the alignment:
This <code>memcpy()</code> :
~~~~
    memcpy( target, source, 4 );

~~~~

A <code>memcpy()</code> function is smart about alignment. It will test the memory locations of both source and target.
GCC has the <code>-fno-builtin-memcpy</code> option which will avoid automatic in-lining. I tend to use it ( and also <code>-fno-builtin-memset</code> ) in all of my projects.

</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on August 24, 2017</div><div class="thread-post-content">The large memcpy implementation here is unlikely to be inlined automatically on many compilers, even when the actual length and alignements are known at compile time.  More sophisticated compilers (like later versions of gcc) will do the constant propagation first, then see that the resulting function is short enough to inline &#8211; with less sophisticated automatic inlining, the compiler will see the size of the full memcpy() function and decide it is too big to inline.  And inlining will not occur anyway if the compiler does not have the source of memcpy() on hand when it is used.
gcc&#8217;s builtin memcpy <em>will</em> inline correctly and optimally when information is known at compile time.  It will do a better job than you will get with this memcpy() implementation.
Additionally, gcc&#8217;s builtin (and library) memcpy is <em>correct</em>.  Your one here has a fundamental error.  It is not defined behaviour to access data via pointers of incompatible types.  If this memcpy is called with sources or destinations that are, say, 16-bit types, then you are not allowed to access the data as 32-bit types.  A union like this does not give you that ability &#8211; the compiler knows that the pointers involved cannot alias, and it can assume that the 16-bit data is not affected by any 32-bit writes.  Moreover, it can make the same assumption about incompatible types that are the same size &#8211; if &#8220;uint32_t&#8221; is a typedef for &#8220;unsigned long&#8221;, then it is incompatible with &#8220;unsigned int&#8221; even if that also is 32 bits.
As long as the function is compiled and called as a separate function, this type-based aliasing information will be lost and thus the compiler will do the copying.  But if it is inlined (or you have link-time optimisation enabled), then the compiler can use this aliasing information to skip memory accesses that it knows cannot legally happen.
So how do you <em>reliably</em> and <em>correctly</em> copy chunks of data in C?  There are three ways.  One is to use character pointers and do it byte for byte &#8211; such accesses are always allowed to alias.  Another is to use implementation-specific techniques, such as gcc&#8217;s &#8220;may_alias&#8221; type attribute.  The standard method is to use &#8220;memcpy&#8221;.
Remember, the memcpy that comes with the implementation is guaranteed to be correct for that implementation &#8211; it can use whatever tricks needed to avoid any aliasing issues even if it copies in larger lumps.
Note that when you use memcpy on gcc without the -fno-builtin-memcpy flag, gcc will generate inline code when appropriate.  This inlining can be so efficient that it is removed entirely, or done as simple register-to-register movement.  It means that memcpy() can be used to make code clear, correct and safe, without worrying about efficiency, rather than using unions or pointer casts that often are not fully safe (like in your code here).
Finally, remember that even if you implement your own memcpy(), and even if you use the -fno-builtin-memcpy flag, the compiler is free to assume that memcpy works exactly according to the standards.  If you write this:
static uint32_t memcpyBytes;
void *memcpy( void *pvDest, const void *pvSource, size_t ulBytes ) {
    memcpyBytes += ulBytes;
    // rest of implementation
}
static uint8<em>t d[100];
static uint8</em>t s[100];
uint32<em>t test(size</em>t n) {
    memcpyBytes = 123;
    memcpy(d, s, n);
    return memcpyBytes;
}
then the compiler is free to return the fixed value 123 from this test() function.  It knows memcpy cannot affect the value of memcpyBytes.
(As a side issue, the correct signature for memcpy() has &#8220;restrict&#8221; in the pointers.)
</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on August 24, 2017</div><div class="thread-post-content">The summary here is use the compiler&#8217;s memcpy.  It is safe and efficient.
Do not disable its useful and safe optimisations.  Do not mess with defining your own versions of such standard library functions &#8211; they will not be better than the implementations versions, and they may have subtle risks.  It may be a different matter if you are using a poor quality or limited compiler, but that is not the case here.

There was another case where the standard GCC implementation of <code>memcpy()</code> causing head-aches: on Cortex-A9 ( Richard mentioned it briefly here above).  That implementation uses 64-bit floating point registers.  But by default, the FPU registers are not stored on stack as part of the task context ( because storing FPU registers on stack is very expensive ).  At that point we decided to supply a <code>memcpy.c</code>, that only uses standard registers.
( before writing <code>memcpy.c</code>, I did study the assembler sources of many GCC implementations )
I was not suggesting that the generic /Labs implementation in <code>memcpy.c</code> is &#8220;better&#8221;, or &#8220;to be preferred&#8221;. I wrote that <strong>if</strong> the standard <code>memcpy()</code> is suspect, give it a try with this hand-made <code>memcpy()</code>, to see if the problem gets solved.

</div></div><div class="thread-post"><h3 class="thread-post-title">memcpy in ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on August 25, 2017</div><div class="thread-post-content">Yes, I understand what you mean about compiler bugs and perfect worlds.  Compiler bugs can be a real pain!  It is particularly difficult for you folks writing something like FreeRTOS where you need to have code that works on a wide range of platforms &#8211; it is a lot easier for the user who only needs it to work on their particular compiler version and target.  I make a point of consider the exact toolchain version as part of the build for a project &#8211; once I have used a version of gcc + libraries (or whatever other compiler), that is archived along with the project.  Clearly that is a luxury you don&#8217;t have for the FreeRTOS source that works on dozens of targets and many more toolchains and versions.
Correctness always trumps speed.  (Of course I am generalising here, and speed may also be part of making the device run correctly according to requirements.)  It is better to have a simple but known safe solution, than a complex one that might be faster, but may have problems.
It is also not easy writing optimal code, and not easy writing portable code &#8211; and pretty much impossible to write optimal portable code!  On gcc, memcpy() is usually very efficient, especially when it can use the builtin version.  But messing with casted pointers to move data in larger chunks can easily fall foul of aliasing rules and end up with code that the compiler happily accepts but the results don&#8217;t match expectations.  On other platforms, such manual casting might be the fastest method while memcpy() gives slow library calls.  There really is no easy answer.
When considering compiler options, you might like to recommend &#8220;-fno-strict-alias&#8221; in gcc.  That makes it safe to use pointers of different sizes and types to access other data, at the cost of some optimisations.
(Regarding attribute((packed)) &#8211; I am not a fan of this, and prefer to avoid it, partly because compiler bugs have been known with packed structs.  I&#8217;d rather add any padding manually with &#8220;dummy&#8221; fields, check none are missing with &#8220;-Wpadded&#8221;, and check the size of types using static assertions.  Again, this is easier when you don&#8217;t need to try to be portable on a range of targets.)

As for using things like floating point registers, that is a more tricky area.  I can well appreciate that it can be a headache &#8211; but it is not a compiler bug as such.  The compiler&#8217;s job is to generate code for the cpu.  If that cpu has floating point registers, then it can use them.  You might be able to control things to some extent, such as with compiler options, but it very difficult to try to say &#8220;I want to use floating point registers for <em>these</em> things but not <em>those</em> things.&#8221;  That should usually be a choice left to the compiler.  Sometimes non-floating point code can be made more efficient using floating point registers.  Similar issues can apply to other bits of hardware &#8211; the msp430&#8217;s hardware multiplier peripheral springs to mind.
For the ARM devices, lazy context switching of the floating point registers can be an answer.  (Yes, I know that&#8217;s easy for me to say, and far from easy to implement &#8211; especially in a way that avoids too much wasted ram space.)
