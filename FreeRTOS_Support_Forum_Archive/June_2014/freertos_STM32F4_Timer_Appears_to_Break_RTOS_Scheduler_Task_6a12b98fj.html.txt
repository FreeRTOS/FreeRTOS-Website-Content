</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 Timer Appears to Break RTOS Scheduler &#038; Task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 12, 2014</div><div class="thread-post-content">Which timer are you using?
If you are using the SysTick (the timer built into the Cortex-M core) then yes, that will definitely mess up FreeRTOS.  You can however hook into the timer interrupt using the vApplicationTickHook() <a href="http://www.freertos.org/a00016.html">hook function</a> &#8211; and use the RTOS tick count as a time base using the xTaskGetTickCount() <a href="http://www.freertos.org/a00021.html#xTaskGetTickCount">API function</a>.
On the other hand if you are using a peripheral timer then it should have no impact on FreeRTOS &#8211; unless you don&#8217;t configure the interrupt priorities correctly.  If you are using a recent version of FreeRTOS (V7.6.0 or later I think) and have <a href="http://www.freertos.org/a00110.html#configASSERT">configASSERT()</a> defined then it will automatically check the interrupt configuration for you for compatibility with FreeRTOS.
Regards.

Secondly, what about the priority of your timer interrupt?
When an interrupt has a higher priority than configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY, you will run into problems: &#8220;ISR safe FreeRTOS API functions must <strong>only</strong> be called from interrupts that have been assigned a priority at or below configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY&#8221;
And normally: the lower the priority value, the higher its priority.

I <i>guess</i> (as I am not familiar with ST&#8217;s code yet) that they have defined their own SysTick handler for use by their drivers, and that they call the FreeRTOS SysTick handler from inside that [which maybe a bit backward as normally you would let FreeRTOS handle SysTick then hook code into that using vApplicationTickHook() &#8211; but maybe it is done that way so the drivers can run without FreeRTOS too?].
In any case, this should not have any baring on using a peripheral timer, which it seems is what you are doing.
FreeRTOS should not affect the use of a peripheral timer, provided you have the interrupt priorities set correction &#8211; did you try the think mentioned in my previous post (setting configASSERT())?
There is seemingly a contradiction in your post however.  The comment you referred to in the FreeRTOSConfig.h file is above a line that maps FreeRTOS&#8217;s SysTick handler to the CMSIS name for that handler.  Doing that allows you to use an unmodified CMSIS compliant vector table, in which the name of the handler is SysTick_Handler.  However the vector table you have posted installs the FreeRTOS name directly, which given what the comment says I think must be a mistake.  I think there is a mismatch between your application code and your start up/vector table code.  Did you get them both from the same place?

Try to verify your code pattern (initialization and tasks running + interruptions) usage/conventions from FreeRtos page.
If you are using freertos system, then freertos encapsulates all exutable code/task management.
Probably it is not recommended executing not managed code when freertos scheduler is active. 
1.init system and pin configuration, execute some code not freertos managed
2.exit any running code, free resources
3.allocate freertos (task creation etc.)
4.run scheduler.
5.task is scheduled. and global communication is under freertos queues/generics
!! any interuption can be activated with framework specific drivers in task code, but it`s necessary to verify implementation of priority settings and passed values. freertos has configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY and configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY.
configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY is shifted , but configLIBRARY</em>MAX<em>SYSCALL</em>INTERRUPT_PRIORITY can be equivalent with platform specific, but it is not condition.
So, any interuption that is activated under the freertos cannot have higher priority than  configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY. However, the interrupt subroutine(Timer ISR) communicates with freertos task, there have to be used &#8212;&#8212;&#8212;FromISR(qHandle,w)  freertos  functions only.
If the ISR subroutine has higher priority than MAX<em>SYSCALL</em>INTERRUPT_PRIORITY, the configASSRT() blocks the next code running in &#8212;&#8212;&#8212;FromISR(qHandle,w) call.
