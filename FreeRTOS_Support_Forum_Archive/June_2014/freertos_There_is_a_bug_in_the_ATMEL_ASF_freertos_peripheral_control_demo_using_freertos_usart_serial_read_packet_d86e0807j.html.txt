  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">There is a bug in the ATMEL  ASF freertos peripheral control demo
 using  freertos_usart_serial_read_packet()</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wlauer">wlauer</a> on June 6, 2014</div><div class="thread-post-content">Hello,
There is a bug in the freertos peripheral control demo available on ASF.
http://asf.atmel.com/docs/latest/sam3x/html/group<strong>freertos</strong>service__group.html
In particular there is a software architecture issue with management of 
the circular buffer for the USART demo.
The function, freertos<em>usart</em>serial<em>read</em>packet(), under certain 
circumstances mishandles the read and write pointers and concludes the 
circular buffer is empty when it is actually full.
The bug involves the function, freertos<em>usart</em>serial<em>read</em>packet() (line 
491),  and the ISR Handler (line 658) in file freertos<em>usart</em>serial.c.
<pre><code>freertos_usart_serial_read_packet()  calls:
     freertos_copy_bytes_from_pdc_circular_buffer() in file
freertos_peripheral_control.c line 181 which manipulates
p_rx_buffer_details-&gt;next_byte_to_read (the read ptr) @ lines 243
and 252
     configure_rx_dma(usart_index, data_removed)    which
manipulates rx_pdc_parameters.ul_size (the size for dma transfer) @
lines  609, 611, 618, and 623
and the ISR Handler which calls:
     configure_rx_dma(usart_index, data_added); which manipulates
rx_pdc_parameters.ul_addr (the write ptr) @ lines 704 and 711
</code></pre>
The function, freertos<em>copy</em>bytes<em>from</em>pdc<em>circular</em>buffer(), determines 
how much data is available in the dma buffer. If data is available, it 
copies it from the dma buffer to the user buffer and then updates 
p<em>rx</em>buffer<em>details->next</em>byte<em>to</em>read. Then, if data was copied from 
the buffer and the DMA controller is stopped, it calls 
configure<em>rx</em>dma(usart<em>index, data</em>removed) to restart the dma 
controller to fill in the area in the dma buffer that was opened up by 
the copy from the dma buffer (the read).
When the DMA transfer (started by the read above) is complete, the 
Handler is called @ line 694. The Handler then manipulates 
rx<em>pdc</em>parameters.ul<em>addr (the write ptr) to set up the next write into 
the dma buffer and calls configure</em>rx<em>dma(usart</em>index, data_added) line 
717 to restart the dma engine if there is space available to fill in the 
dma buffer.
This works unless a call to freertos<em>usart</em>serial<em>read</em>packet() is 
interrupted between the update of p<em>rx</em>buffer<em>details->next</em>byte<em>to</em>read 
and the subsequent call to configure<em>rx</em>dma(usart<em>index, *data</em>removed<em>) 
by a dma transfer completion interrupt which updates 
rx_buffer_definition->rx_pdc_parameters.ul_addr  and calls 
configure_rx_dma(usart_index, *data_added</em>). The logic in<br />
configure<em>rx</em>dma to decide whether the buffer is empty or full line 601 
becomes confused and makes the wrong choice.
<ol>
<li>By example if we start out with the buffer full (i.e. both the read 
and write pointers are equal and the DMA controller is stopped).</li>
<li>Then a call to freertos<em>usart</em>serial<em>read</em>packet reads one byte which 
starts the dma engine with a size of 1 to fill in the byte we read.
     The read pointer is 1 byte ahead of the write pointer and the 
dma controller is running.</li>
<li>Then another call to freertos<em>usart</em>serial<em>read</em>packet reads one 
byte. Because the dma controller is still running 
configure<em>rx</em>dma(usart<em>index, data</em>removed) is not called.
     The read pointer is 2 bytes  ahead of the write pointer.</li>
<li>Then another call to freertos<em>usart</em>serial<em>read</em>packet read one byte 
occurs.  The read occurs but after line 256 in 
freertos<em>copy</em>bytes<em>from</em>pdc<em>circular</em>buffer() and  before**executing 
line 561 the dma controller receives the byte started in step 2 and 
triggers an interrupt.</li>
<li>The interrupt runs and immediately restarts the dma controller via a 
call to configure<em>rx</em>dma(usart<em>index, data</em>added) to fill in the two 
bytes from steps 3 and step 4.</li>
<li>Before execution can resume at line 561 (other interrupt processing 
and such) the dma controller completes the transfer of the two bytes in 
step 5 and generates an interrupt.</li>
<li>The interrupt handler advances the write ptr by 2 and  the read and 
write ptr are now equal and calls configure<em>rx</em>dma(usart<em>index, 
data</em>added). This call correctly identifies the buffer as full and stops 
the dma controller by setting size to 0 line 609.
     The read and write pointer are equal and the dma controller is 
stopped because the buffer is full.</li>
<li>Finally execution resumes at line 561 (from step 4) and subsequent 
call to configure<em>rx</em>dma(usart<em>index, data</em>removed). Seeing that the 
read and write pointers are equal and assuming the cause was the read in 
step 4 incorrectly determines the buffer was empty  and at line 612 
starts the action to refill the entire buffer destroying the valid data 
in the dma buffer.</li>
</ol>
The bug in the freertos<em>read</em>packet() function occurs because between 
updating the p<em>rx</em>buffer<em>details->next</em>byte<em>to</em>read and the call to 
configure<em>rx</em>dma(usart<em>index, data</em>removed) a previous dma transfer<br />
completes. After the interrupt service routine completes the subsequent 
call to configure<em>rx</em>dma(usart<em>index, data</em>removed) resumes execution it 
can misinterpret the state of the full buffer as empty. The update of 
p<em>rx</em>buffer<em>details->next</em>byte<em>to</em>read and the call to 
configure<em>rx</em>dma(usart<em>index, data</em>removed) cannot be interrupted and 
hence need to execute in the *same *critical section.
Additionally line 627 of   configure<em>rx</em>dma() incorrectly performs a 
sanity check to make sure the dma controller is not programmed to write 
beyond the dma buffer length.
configASSERT((rx<em>buffer</em>definition->rx<em>pdc</em>parameters.ul<em>size +
             rx</em>buffer<em>definition->rx</em>pdc<em>parameters.ul</em>size) &lt;=
             rx<em>buffer</em>definition->past<em>rx</em>buffer<em>end</em>address);
should read
configASSERT((rx<em>buffer</em>definition->rx<em>pdc</em>parameters.ul<em>addr +
             rx</em>buffer<em>definition->rx</em>pdc<em>parameters.ul</em>size) &lt;=
             rx<em>buffer</em>definition->past<em>rx</em>buffer<em>end</em>address);

</div></div><div class="thread-post"><h3 class="thread-post-title">There is a bug in the ATMEL  ASF freertos peripheral control demo
 using  freertos_usart_serial_read_packet()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 20, 2014</div><div class="thread-post-content">I want to ensure my report to Atmel is correct, so see if you agree with the following.  The existing code in freertos<em>uart</em>serial<em>read</em>packet() is like this:
~~~~
/* Copy as much data as is available, up to however much
a maximum of the total number of requested bytes. */
bytes_read += freertos_copy_bytes_from_pdc_circular_buffer(
    &amp;(rx_buffer_definitions[usart_index]),
    all_usart_definitions[usart_index].pdc_base_address->PERIPH_RPR,
    &amp;(data[bytes_read]),
    (len &#8211; bytes_read));
/* The Rx DMA will have stopped if the Rx buffer had become
full before this read operation.  If bytes were removed by
this read then there is guaranteed to be space in the Rx
buffer and the Rx DMA can be restarted. */
if (bytes_read > 0) {
  taskENTER_CRITICAL();
  {
    if(rx_buffer_definitions[usart_index].rx_pdc_parameters.ul_size == 0UL) {
      configure_rx_dma(usart_index, data_removed);
    }
  }
  taskEXIT_CRITICAL();
}
~~~~
<br>
and the fix would change it to be:
~~~~
taskENTER<em>CRITICAL();
{
  /* Copy as much data as is available, up to however much
  a maximum of the total number of requested bytes. */
  bytes</em>read += freertos<em>copy</em>bytes<em>from</em>pdc<em>circular</em>buffer(
      &amp;(rx<em>buffer</em>definitions[usart<em>index]),
      all</em>usart<em>definitions[usart</em>index].pdc<em>base</em>address->PERIPH<em>RPR,
      &amp;(data[bytes</em>read]),
      (len &#8211; bytes_read));
  /* The Rx DMA will have stopped if the Rx buffer had become
  full before this read operation.  If bytes were removed by
  this read then there is guaranteed to be space in the Rx
  buffer and the Rx DMA can be restarted. */
  if (bytes_read > 0) {
    if(rx_buffer_definitions[usart_index].rx_pdc_parameters.ul_size == 0UL) {
      configure_rx_dma(usart_index, data_removed);
    }
  }
}
taskEXIT_CRITICAL();
~~~~
So the critical section has been removed from inside the if() to around the entire code section.
Do you agree?
Regards.
