  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Changing configTOTAL_HEAP_SIZE</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kkelkar">kkelkar</a> on August 3, 2007</div><div class="thread-post-content">I am trying to allocate a buffer to write an event log file to. I can do so without issue within the current configTOTAL&#95;HEAP&#95;SIZE size limit. However, when I try to increase my configTOTAL&#95;HEAP&#95;SIZE by even 1000, FreeRTOS seems to stop running.
I am running on a SAM7S256 with 64K of memory and my configTOTAL&#95;HEAP&#95;SIZE is set to 14200. It seems like I should have the RAM to use. Does anyone have any suggestions on what else I need to change or look at to figure out why I cannot increase my heap size?
</div></div><div class="thread-post"><h3 class="thread-post-title">Changing configTOTAL_HEAP_SIZE</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 3, 2007</div><div class="thread-post-content">Take a look in your map file, this will tell you how much RAM you have available and where it is being used up.&nbsp; I would have thought though that you would get a linker error if configTOTAL&#95;HEAP&#95;SIZE was too large.&nbsp; Do you have the correct linker script for the S256? 
Are you allocating the buffer before starting the scheduler or afterwards.&nbsp; If afterwards then maybe you don&#8217;t have enough heap left to create the idle task.&nbsp; Check whether or not vTaskStartScheduler&#40;&#41; is returning &#40;the idle task is created automatically when you start the scheduler&#41;.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Changing configTOTAL_HEAP_SIZE</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jcwren">jcwren</a> on August 3, 2007</div><div class="thread-post-content">I don&#8217;t know what compiler and library you&#8217;re using, but I can tell you this: With GCC and newlib, the sbrk&#40;&#41; function in newlib/syscalls.c &#40;which is tailored to your system&#41; performs a check to see if the end of heap pointer is greater than the stack pointer, and if it is, it fails.&nbsp; This is a very primitive but effective method of determining if the heap and stack will collide.
When running FreeRTOS, the stack is in the static memory area, which is in low memory.&nbsp; This implicitly means that the stack pointer will appear to be below the end of the heap, and cause sbrk&#40;&#41; to fail.&nbsp; 
If you&#8217;re not running GCC + newlib, then this may well not be applicable.&nbsp;&nbsp; I do know I was getting weird behavior with FreeRTOS appearing to lock up, or certain tasks failing &#40;and others still running&#41; until I nailed this down.
In the LPC2148&#95;V130 demo package &#40;which I should be releasing this weekend after a couple more checks&#41;, I&#8217;ve implemented this fix.
&#45;-jc
</div></div><div class="thread-post"><h3 class="thread-post-title">Changing configTOTAL_HEAP_SIZE</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/kkelkar">kkelkar</a> on August 3, 2007</div><div class="thread-post-content">Sorry &#8211; I should have included the fact that I am using IAR in my original post.
That said, after the useful responses, I went back and checked the linker file. I found out that I had started this project based on the IAR SAM7s64 demo and had changed all the board configs and target processor, but not the linker files.
Thanks for the quick and helpful responses.
Kris
