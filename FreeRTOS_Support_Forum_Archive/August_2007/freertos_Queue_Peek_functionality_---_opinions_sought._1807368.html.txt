  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Queue Peek functionality &#8212; opinions sought.</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 22, 2007</div><div class="thread-post-content">Hypothetical scenario 1:
There is a queue on which 1 task is blocked waiting for data to arrive.&nbsp; Data arrives and the task unblocks.&nbsp; The task was just wanting to peek the data &#40;not remove it&#41; so takes a copy of the data and leaves the queue peek function.&nbsp; Now presumably it will perform some action, then later go back to the queue again where it will immediately find the data it just peeked.&nbsp; I think this behaviour is logical and ok, and is how the GenQTest.c demo tasks work.
Hypothetical scenario 2:
There is a queue on which 2 tasks are blocked waiting for data to arrive.&nbsp; Both tasks are the same priority.&nbsp; Data arrives and unblocks one of the tasks, this task was just peeking so takes a copy of the data and leaves.&nbsp; Now what should happen?&nbsp; There is another task blocked on the queue waiting for data, and there is already data in the queue &#8211; should this second task be unblocked after the first task has peeked the data?&nbsp; What would be the logical thing to do, or how would you expect this scenario to work?
Hypothetical scenario 3:
Same as 2, but this time the two tasks that are blocked on the queue are of different priority.&nbsp; The higher priority task wakes and peeks the data &#8211; should the second task then be unblocked because there is data in the queue that was not removed?&nbsp; The second task is of lower priority so will not execute until the first task blocks again &#40;it is ok if the first task removes the data before the second task executes, FreeRTOS.org already handles this situation&#41;.
Provided the behaviour is documented, does it matter which implementation is chosen &#40;wake the second task, not wake the second task&#41;?
Maybe it should be a compile time option &#8211; but this would add complexity and more preprocessor macros, plus more code to test.
Maybe there should be a rule that tasks can not block on a queue when they are just peeking?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Queue Peek functionality &#8212; opinions sought.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jorick23">jorick23</a> on August 22, 2007</div><div class="thread-post-content">I think that once a task peeks at a queue, it shouldn&#8217;t reawaken until new data is posted.&nbsp; Seems to me if a task just peeks the data but doesn&#8217;t use it, it means it didn&#8217;t want the data.&nbsp; Here are the three examples posted by Richard using my No Reawaken criteria:
Scenario 1 &#40;amplified&#41;:
The task is receiving a packet from the outside world and is waiting on the End-of-Packet character.&nbsp; The task peeks the queue, finds that it isn&#8217;t the right character, and goes back to sleep.&nbsp; When the End-of-Packet character finally comes in, it reads the entire packet from the queue and stores it.&nbsp; Sure there are other, maybe better ways of doing this but this is just an example.
Scenario 2:
Task 1 wakes, peeks at the data, and doesn&#8217;t want it.&nbsp; It goes back to sleep.&nbsp; Task 2 wakes up, gets the data from the queue, and goes back to sleep.&nbsp; If task 2 woke first, it would get the data from the queue and task 1 would never wake &#40;it didn&#8217;t want the data anyway&#41;.&nbsp; If neither task wants the data, they both go back to sleep until more data comes in.
Scenario 3:
Task 1 &#40;high priority&#41; wakes and peeks the queue.&nbsp; It doesn&#8217;t want it so it goes back to sleep.&nbsp; Task 2 wakes and gets the data.&nbsp; If task 1 got the data, task 2 would never wake up.
Scenarios 2 and 3 assume that only one task can use the data.&nbsp; If both tasks need the data then perhaps one task should block on the queue and then send the data to the second task.
It should be okay for a task to block on a queue if just peeking, as shown by the scenarios above.

</div></div><div class="thread-post"><h3 class="thread-post-title">Queue Peek functionality &#8212; opinions sought.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 22, 2007</div><div class="thread-post-content">jorick23 &#8211; with respect to your feedback.&nbsp; I agree in an ideal case a task would peek at the queue, then have the ability to go back to sleep until more data arrives.&nbsp; I&#8217;m not sure if this is possible though.
Say the task unblocks, peeks the data, decides it does not want it, then goes back to block on the queue.&nbsp; The queue data was left in the queue but the task does not know if it is still there or not &#8211; another task may have executed in between and removed it.&nbsp; 
The task must leave the queue function in order to decide whether or not it wants the data, then re-enter the function to block again.&nbsp; Unless this is all done in a critical section it does not know what the queue state is on the second entry.
The documentation on this new functionality is going to have to be very explicit to ensure people know the ins and outs of its use.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Queue Peek functionality &#8212; opinions sought.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sashiono">sashiono</a> on August 23, 2007</div><div class="thread-post-content">I&#8217;m thinking how I would use peek. 
I think that I would use it to have several tasks blocked on the same queue. 
I would have all the tasks receiving data only use peek to get the data. 
And the lowest priority actually remove the data. &#40;or even a dummy reader in the idle task clean out the queues&#41; 
This would work well if multiple tasks needed the same data. 
If this is how I used it then Hypothetical scenario 3 would be the most useful. 
Another possible, but similar situation would also be several tasks blocked on the same queue. but instead of all of them only using peek to get the data, peek would only be used to block and see if it wants the data, and xQueueReceive would actually be used to get the data. 
This would be used if data is only useful for one task, but you don&#8217;t know who actually needs it. Again though the lowest priority task needs to clear out the queue no matter what. 
again this fits Hypothetical scenario 3
One issue with this setup is what to do with a task of a higher priority where it peeks and doesn&#8217;t want that data. How do you block again on the same queue, yet still have lower priority tasks get the queue. 
Would you need to implement a queue skip function? Or would calling task yield be good enough to let a lower priority task get to the data? Or would calling peek again allow a lower priority task to check?
if peek was able to return the number of messages stored in the queue, rather than true false, then I can come up with some more situations where Hypothetical scenario 2 would be useful. For example waiting for several chunks of messages to build up before processing. 
If only true false is returned, I don&#8217;t see how useful it would be. maybe I&#8217;m missing a situation. 
-Sashi

</div></div><div class="thread-post"><h3 class="thread-post-title">Queue Peek functionality &#8212; opinions sought.</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 23, 2007</div><div class="thread-post-content">Thanks for all your thoughts.&nbsp; I am going to update so that when you have peeked from a queue but leave data in the queue the next task that is blocked on the same queue will be unblocked.&nbsp; If this task is of lower priority it will not actually run until the originally unblocked task blocks again &#8211; at which time, if the queue has been emptied again, it will simply automatically return to block on the queue for the remains of its block period as if nothing had happened.&nbsp; This all happens internally to FreeRTOS.org.
This seems to be the most flexible way.&nbsp; The application writer will have to be aware of the implications of peeking a queue.&nbsp; Without this change it would be possible for tasks to be blocked on a queue even when there was data available, which does not seem right.&nbsp; I think this is just a 1 line change, but also need to update the new demo/test task to test the behaviour.&nbsp; I might not get this done until this evening.
It is in fact &#40;I think&#41; rare in small embedded systems to have more than one task read from the same queue in any case, whereas the opposite is not true as it is common to have multiple tasks write to the same queue.&nbsp; At least this is the case in the software that I write.
Regards.
