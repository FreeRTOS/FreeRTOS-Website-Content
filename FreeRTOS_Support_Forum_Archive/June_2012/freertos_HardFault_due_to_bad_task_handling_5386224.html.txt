I am implementing an Application using FreeRTOSv7.1.1 on a stm32f2xx.<br />
My main&#95;Task is set at <strong>tskIDLE&#95;PRIORITY + 1</strong> and uses a binsemaphore to wait for an interrupt.<br />
After a random runtime, the system Hardfaults. It is due to pxCurrentTask go to 0x0.  
I wandered why and found that for a still unknown reason, my <strong>pxReadyTasksLists-&gt;pxIndex</strong> is still set to ** &amp;&#40;pxReadyTasksLists-&gt;xListEnd&#41;** after the task being resumed from the ISR.  
I use for this <strong>xSemaphoreGiveFromISR</strong> and the isr priority is configured between <strong>configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY</strong> and <strong>configLIBRARY&#95;KERNEL&#95;INTERRUPT&#95;PRIORITY</strong>.  
Could someone help me find some new trails to the solution ?  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">HardFault due to bad task handling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 27, 2012</div><div class="thread-post-content">So, if I follow what you are saying, a task at priority 1 is being signaled by an interrupt via a semaphore, and this is working ok for some time before the system crashes.&nbsp; When the system crashes, pxCurrentTCB is NULL, and the ready tasks list for tasks of priority 1 is empty.  
Even with the task not referenced from the ready list, the scheduler should at least select the idle task to run, so pxCurrentTCB should never be zero.&nbsp; This points to a corruption of the data structures somewhere.  
It sound like you have debugged this quite deeply, and are familiar with the interrupt priority settings configuration parameters etc. already &#8211; so my usual reply of &#8220;its probably the interrupt priority settings&#8221; might not be the case here.&nbsp; However, it is still worth double checking that the interrupts are running at the priority you think, and that no interrupts you are not aware of are running.&nbsp; These are the items documented on the <a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a> and <a href="http://www.freertos.org/RTOS-Cortex-M3-M4.html">http://www.freertos.org/RTOS-Cortex-M3-M4.html</a> web pages.  
After that it is a matter of looking at any other potential source of corruption in your code, where are buffers being used, is any shared memory being used, are resources being used by multiple tasks, etc.  
Can you keep cutting bits out of the code until the problem stops happening, so you have the smallest amount of code left to look at.  
It is also possible to look at the task&#8217;s TCB itself, and see if you can work out where the task is.&nbsp; If it is not in its ready list, is it referenced from another list somewhere?&nbsp; You can do this by obtaining the tasks TCB from its handle, then looking at the generic list item&#8217;s container value.&nbsp; It should always be one of the &#8216;state&#8217; lists &#8211; be that one of the ready lists, the blocked list, etc. etc. &#8211; but in this case that is probably the last resort option as learning where you task is after the problem is not necessarily going to lead you directly to the actual cause of the problem.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">HardFault due to bad task handling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on June 28, 2012</div><div class="thread-post-content">As I dont need IT without Kernel Calls my kernel intterupt priority is set to the lowest &#40;15 on cortex m3&#41; and I allow all interrupts to use syscall and therefore being masked while in kernel calls.  
In fact, when the system crashes, the task is in the ready tasks list for priority 1.<br />
But the pxIndex of the list point to the ListEnd item. That&#8217;s why -&gt;pxOwner is NULL and pxCurrentTCB gets the NULL pointer.<br />
This gives me the idea to test with a dummy&#95;task just to have a task always being pointed by pxIndex.<br />
So I suspect that somewhere pxIndex is not updated correctly but it seems too big to be this.  
i will investigate on this today.<br />
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">HardFault due to bad task handling</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on June 28, 2012</div><div class="thread-post-content">Hi,  
As everything looked fine in the list managment &#40;as i wasn&#8217;t doubting&#41;, I reviewed the FreeRTOS interrupt priority settings.<br />
As mentionned in my previous post i had :  
<pre><code>#define configKERNEL_INTERRUPT_PRIORITY     0xFF    /* Priority 15 */
#define configMAX_SYSCALL_INTERRUPT_PRIORITY    0x00        /* Priority 0 */
</code></pre>
<strong>configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY</strong> is set in BASEPRI on cortex-m3, I read the programming manual for this reg and saw that I quote :  
<blockquote>
  BASEPRI Priority mask bits&#40;1&#41;<br />
  0x00: no effect<br />
  Nonzero: defines the base priority for exception processing.  
</blockquote>
…<br />
I switch to 0x10 and everything seems to be fine now.  
Thank you very much for you answer.<br />
I&#8217;m sorry for the disturbance.  
Regards
