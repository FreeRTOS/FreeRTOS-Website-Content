  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">comment on serial.h</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on June 10, 2012</div><div class="thread-post-content">I&#8217;m implementing the interface defined in Demo/Common/include/serial.h.&nbsp; I also see hints in things like FreeRTOS-Plus and other forum posts that a refactoring of FreeRTOS may be underway.&nbsp; If that&#8217;s so, please consider:  
&#42; Adding documentation to interface declarations so ports know what the function is supposed to do.&nbsp; For example, various ports appear to have chosen to have the return values of xSerialGetChar and xSerialPutChar be either pdFAIL or pdPASS, although the return type would support just about anything, and my initial assumption is it would be like putchar&#40;3&#41;.  
&#42; Consistently using either xPort or pxPort as the parameter name for the xComPortHandle.&nbsp; I think the pxPort uses are inconsistent with the coding standard, since the value is an instance of the type even though what the type hides is the fact that it&#8217;s a pointer to something which might be a structure.&nbsp; But I suppose that&#8217;s a grey area.  
Peter
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 10, 2012</div><div class="thread-post-content">The code in FreeRTOS/Demo is not part of the FreeRTOS kernel code, and is provided as a working starting point only.&nbsp; Where the code is common to lots of demos for lots of ports it is documented, where the code is non-portable, for UARTs etc, there is less documentation.&nbsp; Things like FreeRTOS+IO is official code, and &#42;extensively&#42; documented.  
Note that the UART drivers found in FreeRTOS/Demo are &#42;not&#42; intended to be examples of efficient implementations.&nbsp; They are primarily designed almost with the opposite intention of stress testing a port and the FreeRTOS implementation by generating as many interrupts as possible by passing single characters through queue and causing lots of context switches.&nbsp; The example transfer modes in FreeRTOS+IO are much better &#8211; and DMA best of all &#40;but that does not test much outside of the hardware&#41;.  
Yes &#8211; there is some inconsistency in the naming &#8211; apologies for that.&nbsp; Most if not all the core kernel code should not suffer from that.&nbsp; The inconsistency arises from a knowledge of the underlying implementation, where really pointers are passed around &#8211; but the names should be used form the point of view of somebody who is just using an API without knowledge of its inner workings.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on June 11, 2012</div><div class="thread-post-content">Thanks.&nbsp; I&#8217;m really looking to re-use existing standard interfaces for common capabilities rather than create my own.&nbsp; When will FreeRTOS+IO be released independently of the LPC1769 demo?&nbsp; Will there be a repository for it and other parts of FreeRTOS-Products that can be mirrored and maintained locally as with FreeRTOS itself?&nbsp; Or does that exist and I&#8217;m not finding it?
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 11, 2012</div><div class="thread-post-content">The FreeRTOS+IO code is a bit like the main FreeRTOS code in that a lot of it is generic, and some specific to a port.&nbsp; The port layer if fatter than for the FreeRTOS code though as it deals with individual peripherals, not just the core.  
The code will make it into the repository at some point, but I would not like to say exactly when.&nbsp; I think there is already a link to the download on the FreeRTOS+IO demo project page &#8211; but you might be right in that the download also includes the NXP port layer.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on June 11, 2012</div><div class="thread-post-content">Yes; I had downloaded that, but it appeared to be a work-in-progress since that demo package was the recommended location to obtain the code.&nbsp; FreeRTOS+CLI was in the repository and got pulled out, and I figured that other components of FreeRTOS-Products would similarly be separated out.&nbsp; If that was the case, my preference was to try to locate existing interfaces to implement, but on the whole serial.h does not meet my needs so I&#8217;m looking for alternatives.  
Do you feel that the interface in FreeRTOS&#95;DriverInterface.h is essentially final?&nbsp; If not, I can start another thread with some comments on it.&nbsp; E.g., the use of character strings to identify devices is perhaps too expensive for lower-end MSP430 devices.&nbsp; If the names of available devices are meant to encode the Peripheral&#95;Type&#95;t and an instance number, it&#8217;d be better to pass those as integers.&nbsp; &#40;And why is it eSSP&#95;TYPE when the example pcPath is /SPI2/?&nbsp; And why do the example paths end with what appears to be a directory separator&#8211;will names be used to identify device components or capabilities at some point, e.g. /UART0/TXBUF?&nbsp; Questions start arising very quickly.&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 11, 2012</div><div class="thread-post-content">The interface will get extended, but the use of strings to identify the devices is not going to change because it follows the POSIX convention &#40;although not 100% the POSIX standard, as the FreeRTOS+IO implementation is leaner&#41;.&nbsp; If you use const strings then they should remain in flash.  
On the LPC, the SSP port is used for SPI communications.&nbsp;   
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pabigot">pabigot</a> on June 11, 2012</div><div class="thread-post-content">OK.&nbsp; Since most MCUs are not LPCs, it would have been less confusing to me if the generic peripheral type were eSPI&#95;TYPE, and the spelling of the path were /SSP on the LPC&#8217;s instances of those devices.  
Sure the strings go in flash.&nbsp; Still, if an MCU has four UARTS named /UART0 through /UART3, that&#8217;s two instances &#40;device table and open command parameter&#41; of four device strings of six characters each taking up 48 bytes of flash unless the linker detects and merges string constants.&nbsp; Hard to justify on an 16 kB MCU.
</div></div><div class="thread-post"><h3 class="thread-post-title">comment on serial.h</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on June 11, 2012</div><div class="thread-post-content">I think the names of the devices are not part of the IO core code, but the board support package, so you could call them whatever you like. That would save a few bytes &#40;&#8221;u1&#8243;, &#8220;u2&#8221;, etc.&#41;
