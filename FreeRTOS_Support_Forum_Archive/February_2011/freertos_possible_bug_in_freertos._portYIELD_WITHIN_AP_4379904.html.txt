There is an example of one possible scenario to reveal what may happen.  
Suppose, application has created 3 independent tasks- task1, task2, and task3 and two binary semaphores m2 for IPC between task1 and task2, and m3 for IPC between task2 and task3. Lets list the priorities in the ascending order:<br />
task1 &#8211; 1<br />
task2 -2<br />
task3 -3<br />
The scheduler is started. Both semaphores are taken during initialization.<br />
Task1 is running. Task 2 is blocked on m2 and task 3 is blocked on m3&#40;waiting when semaphore will be given&#41;.<br />
Suddenly task1code invokes xSemaphoreGive that is covered by xQueueGenericSend. Inside xQueueGenericSend function current task1 enters critical section&#40;macro taskENTER&#95;CRITICAL&#41;. <br />
In a vast majority of existed ports for FREERTOS increment nesting counter is provided to keep track of how many times portENTER&#95;CRITICAL was called. It increments every time program comes across with portENTER&#95;CRITICAL and decrements on every portEXIT&#95;CRITICAL. Now the nesting counter is incremented.  
Then task copies data to the queue &#40;lines 465-468, file queue.c&#41; and finally checks whether any task is blocked waiting for a data on this queue&#40;lines 472-473 file queue.c&#41;. According to a given scenario&nbsp; precondition task2 is blocked currently on the m1. Since task1 gives mutex and task 2 is higher priority task, then task1 will call portYIELD&#95;WITHIN&#95;API macro&#40;line 480&#41;. This macro will consequently perform a context switch.  
Now task1 is inside critical section and tick interrupts are disabled.<br />
Lets assume that on the next step task2 does a few things like sending some information via uart for argument&#8217;s sake. And after that, within 1 ms period, it gives mutex- m3 and task3 is waiting for it.<br />
Now task2 invokes&nbsp; xQueueGenericSend where the first thing it does – it&nbsp; enters critical section and nesting counter for a crittical section is incremented again, finally its value is 2.&nbsp; Then it checks whether any tasks are already waiting for this mutex. According to our scenario task3 is waiting.&nbsp; Now task3 is gonna be run, where tick interrupts are enabled.   
Lets assume at some point context switch inside tick interrupt handler will point to a task1.<br />
Now the task1 is at the point where portYIELD&#95;WITHIN&#95;API was called. The next instruction is portEXIT&#95;CRITICAL. Most realizations of this macro&#40;for a vast majority of existing ports&#41; rely on &#8220;increment nesting counter&#8221; by comparison it with 0, and if its value is 0, then tick interrupt is enabled again, otherwise only a nesting counter is decremented. In our scenario nesting counter currently holds 2. So task1 will decrement nesting counter by one and return with the state when tick interrupts are disabled. Normally it should be in the state when tick interrupts are enabled, but now it is not &#33;&#33;&#33;&#33;&#33;.   
It is not normal?. Am I correct.   
I suppose that portYIELD&#95;WITHIN&#95;API &#40;line 480 queue.c&#41; must be preceded with taskEXIT&#95;CRITICAL if taskENTER&#95;CRITICAL was called above. And taskEXIT&#95;CRITICAL that is called below should be excluded from the code. See example below. The same thing may be done in function xTaskResumeAll&#40;file tasks.c&#41; and function xQueueGenericReceive&#40;file queue.c&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">possible bug in freertos. portYIELD_WITHIN_AP</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 22, 2011</div><div class="thread-post-content">Sorry &#8211; only time for a very quick answer.  
The kernel code is designed specifically to yield in a critical section &#8211; but application code should never do this.  
richard&#95;damon is right that the critical section count is per task.&nbsp; The critical section variable is saved as part of the task context., either in the TCB or on the stack depending on the port.  
A task that yields in a critical section yields with interrupts disabled, but if it yields to a task that has a critical section count of zero interrupt will be re-enabled prior to the new task running.&nbsp; When the original task starts executing again, when it is restored it is noted that the critical section count is not zero &#40;either from the stack or from the TCB&#41; and it is restarted with interrupts disabled.  
It is actually more complex then that because behaviour depends on the port too, but in essence, that is how the code is designed to work and it is not a bug &#40;unless you can show otherwise&#41;.&nbsp; This really needs to be an FAQ because I spend a lot of my life explaining it.  
Regards.
