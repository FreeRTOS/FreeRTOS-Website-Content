</div></div><div class="thread-post"><h3 class="thread-post-title">Trace Hook Macros</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jwestmoreland">jwestmoreland</a> on July 10, 2009</div><div class="thread-post-content">ZouYong,
Sounds like you need to spend more time in the debugger &#8211; no reason to make release builds if you don&#8217;t know that your debug version is working or not.
Set breakpoints in your TIMER IRQ and see if that is working.
Get a scope, program some I/O&#8217;s and create a couple of tasks that toggle the I/O&#8217;s &#8211; or even toggle the I/O&#8217;s in your timer IRQ.
HTH,
John
</div></div><div class="thread-post"><h3 class="thread-post-title">Trace Hook Macros</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/zy015240">zy015240</a> on July 10, 2009</div><div class="thread-post-content">Hi John,
&nbsp;&nbsp; I already create three tasks in my test main&#40;&#41;, each one flash one LED at different frequency using Taskdelayuntil&#40;&#41; function, and it work ok. But I really need to know if the kernel mechanism such as switchcontext work correct. so I think I can use trace macro to confirm. But I do know how to use them. Thank you for faster replay.
</div></div><div class="thread-post"><h3 class="thread-post-title">Trace Hook Macros</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jwestmoreland">jwestmoreland</a> on July 10, 2009</div><div class="thread-post-content">ZouYong,
Move one of your tasks to be &gt; 0x10000 &#40;above 64K&#41; &#8211; this will check if your port is OK running in 430X mode.&nbsp; You define this in your linker command file.&nbsp; Maybe you don&#8217;t want to run in 430X mode initially until you get your port stable.
Put a taskYield&#40;&#41; in your LED tasks forcing them to do a context switch.
Put a breakpoint range on 0xFFFE-0xFFFF to make sure the board isn&#8217;t constantly resetting &#8211; I&#8217;ve seen small projects do this when they are unstable &#8211; and it isn&#8217;t always apparent.
Check values in tasks.c like xTickCount and uxCurrentNumberOfTasks &#8211; xTickCount should increment until it rolls and uxCurrentNumberOfTasks should reflect the &#35; of tasks that are running.
If you do the above you will prove the kernel is correct.&nbsp; This way you don&#8217;t have to worry about trace hook macros.&nbsp; I think when you have the system stable and you want to do some fine tuning &#8211; the the trace hook macros may be more appropriate.
