RTOS V4.2.1 Built with the same configuration shown above runs with a max jitter of 
-23895ns. If I build it on MPLAB V8.0 with pic32-gcc V1.0 it runs with max jitter of +486ns. 
Note: the later versions of MPLAB V8.15a and fwd upgrade the firmware in the ICD 2. If I plug the ICD 2 into an earlier version of MPLAB &#40;V8.00 specifically&#41; and reflash the ICD 2 to the old firmware, FreeRTOS V4.2.1 works fine. I can&#8217;t build V5.4.0 in MPLAB 8.00 because it say the format of the workspace has changed &#40;i.e. I can&#8217;t open the project&#41;.
What version of MPLAB, Pic32-gcc and ICD firmware was FreeRTOS V5.4.0 built under?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V5.4.0 &#8211; Pic32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rjbelgau">rjbelgau</a> on July 25, 2009</div><div class="thread-post-content">Your website says that V5.0.2 was built on the Explorer 16 board so I pulled down that version and it seems to be working. Being a newbee, I think I will start here. It would be interesting if you could try V5.4.0 on the Explorer 16 board.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V5.4.0 &#8211; Pic32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 25, 2009</div><div class="thread-post-content">I have just tired V5.4.0 and you are correct in that the demo does not run as is.&nbsp; The problem has arisen because of some modifications that were made to the byte alignment, causing just&nbsp; a few more bytes per task stack to be allocated.&nbsp; This in turn meant there was not enough heap left for the idle task to be created.
To fix, open up FreeRTOSConfig.h and change the configMINIMAL&#95;STACK&#95;SIZE setting from 200 to 190.&nbsp; The demo will then execute with no problems.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V5.4.0 &#8211; Pic32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rjbelgau">rjbelgau</a> on July 26, 2009</div><div class="thread-post-content">That fixed it. Thanks
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V5.4.0 &#8211; Pic32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rjbelgau">rjbelgau</a> on August 5, 2009</div><div class="thread-post-content">Can you use vTaskDelayUntil&#40;&#41; API function to delay for say 60 minutes?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS V5.4.0 &#8211; Pic32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 5, 2009</div><div class="thread-post-content">The maximum delay period depends on the type used to hold the tick count and the tick frequency.&nbsp; Assuming the tick count is held in a 32 bit variable &#40;configUSE&#95;16&#95;BIT&#95;TICKS is set to 0&#41; and the tick frequency is 100Hz &#40;configTICK&#95;RATE&#95;HZ is set to 100&#41; then the maximum delay that can be achieved using vTaskDelayUntil&#40;&#41; is 0xffffffff ticks, 
which equals 0xffffffff one hundredths of a second, 
which equals 42949672.95 seconds, 
which equals 715827.8825 minutes, 
which equals 11930.46470833 hours, 
which equals 497 days 
:o&#41;
Note that block times sent to queue and semaphore functions can specify an indefinite wait by setting the block time to portMAX&#95;DELAY and having INCLUDE&#95;vTaskSuspend set to 1.
Regards.
