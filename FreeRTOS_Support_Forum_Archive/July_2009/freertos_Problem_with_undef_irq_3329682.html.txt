  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem with undef irq</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nixw">nixw</a> on July 10, 2009</div><div class="thread-post-content">Hello All, 
I&#8217;m using the V4.2.0 ARM7&#95;LPC2000 port of the FreeRTOS and have a almost working system with 5 tasks &#40;including the Idle task&#41; using cooperative task switching.&nbsp; My problem is I consistently get an undef irq occurring which resets the system.&nbsp; If I break the system at the point the undef handler is executed the call stack is only one function deep.&nbsp; The position it seems to have jumped from to the undef handler is consistent but not meaningful. &#40;Possibly looks like the stack has been corrupted?&#41;&nbsp; This position in the code normally executes fine and is very simple.
I&#8217;ve looked for stack overflows for the tasks and cannot seem to see any.&nbsp; I&#8217;ve also tried to reduce my use of pointers to the bare minimum and the ones I must use I&#8217;ve checked over very carefully.&nbsp; Does anyone have any ideas to what this bug might be?
Thanks in advance. 
Nick 
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with undef irq</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jwestmoreland">jwestmoreland</a> on July 10, 2009</div><div class="thread-post-content">Nick,
Make sure your minimal stack size and heap are set correctly &#8211; meaning those are not being exhausted &#8211; and also &#8211; check to see if an IRQ has been enabled that does not have an IRQ handler installed.
I have written some code &#8211; not for your part &#8211; sorry &#8211; I call &#8216;interrupt&#95;grabber.c&#8217; for this very purpose &#8211; it is helpful during bring-up of suspect boards &#8211; if an IRQ goes off that &#8216;shouldn&#8217;t&#8217; &#8211; the respective simplistic handler will just spin &#8211; so it is easy to identify the source of the IRQ in the debugger.&nbsp; On a lot of processors &#8211; if an IRQ goes off that doesn&#8217;t have a handler &#8211; it usually hits the reset vector.&nbsp; Not sure if that is your problem but you may want to bang out your own interrupt&#95;grabber.c just in case.
HTH,
John
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with undef irq</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on July 10, 2009</div><div class="thread-post-content">The IRQ link register will hold the return address, not the stack, but I&#8217;m not sure that is helpful. You need to determine which IRQ is executing.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with undef irq</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nixw">nixw</a> on July 14, 2009</div><div class="thread-post-content">I have had some success by changing the compilation of the functions the undefined IRQ seemed to have jumped from to ARM code &#40;previously the files the function were in were compiled as Thumb&#41;.&nbsp; Although I haven&#8217;t been able to find an explanation as to why this helps.&nbsp; The undef IRQ is called when a unknown instruction is attempted to be executed by the CPU.&nbsp; I&#8217;m aware that the IRQ handlers must be compiled in ARM and I understand the the CPU can switch back and forth between ARM and Thumb modes relatively easily so I&#8217;m unsure why this would help.&nbsp; Can anyone shed any light on this?
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with undef irq</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nixw">nixw</a> on July 14, 2009</div><div class="thread-post-content">Cheers John and Dave for your suggestions.&nbsp; John the interrupt is a specific one for ARM, the undef IRQ happens when a instruction not recognised by the CPU or it&#8217;s coprocessor&#40;s&#41; is attempted to be executed.&nbsp; Dave you are right, the IRQ link register &#40;R14&#95;undef&#41; contained the return address which was the same as the stack view.&nbsp;&nbsp; This is what I was seeing as &#8216;the functions the undefined IRQ had seemed to jump from&#8217;.&nbsp; Thanks for both your help.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem with undef irq</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nixw">nixw</a> on July 15, 2009</div><div class="thread-post-content">Cheers John and Dave for your suggestions.&nbsp; John the interrupt is a specific one for ARM, the undef IRQ happens when a instruction not recognised by the CPU or it&#8217;s coprocessor&#40;s&#41; is attempted to be executed.&nbsp; Dave you are right, the IRQ link register &#40;R14&#95;undef&#41; contained the return address which was the same as the stack view.&nbsp;&nbsp; This is what I was seeing as &#8216;the functions the undefined IRQ had seemed to jump from&#8217;.&nbsp; Thanks for both your help.
