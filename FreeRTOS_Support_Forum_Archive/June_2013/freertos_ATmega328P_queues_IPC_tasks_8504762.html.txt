  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">ATmega328P queues + IPC + tasks</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jgordo32">jgordo32</a> on June 23, 2013</div><div class="thread-post-content">I&#8217;m struggling with my first real freeRTOS project. I am basically using an ATmega328P microcontroller and an nRF24L01+ radio as a &#8220;node&#8221;. I have two of these nodes and I am using them to talk to each other. I have successfully ported freeRTOS to my microcontroller so that I can use tasks to blink LEDs and to do very basic send/receive of data using my radio driver which I also wrote. The part that I&#8217;m struggling with is how to best structure my code and tasks to create something like a network layer on top of my radio driver.  
Here were my initial thoughts:  
When the radio&#8217;s data ready interrupt fired, I would set a global boolean variable to signal to my &#8220;radio&#95;task&#40;&#41;&#8221; function to read data from the radios FIFO.<br />
I would have a function called &#8220;radio&#95;task&#40;&#41;&#8221;, which would NOT actually be a freeRTOS task, which would check the outgoing queue and use my radio driver &#40;in combination with freeRTOS receiveFromQueue&#40;&#41;&#41; to send the front packet on the queue if there is one. This function would also check the global boolean and read a packet from the radio&#8217;s FIFO if there was one. It would then sendToQueue&#40;&#41; this read packet onto the incoming queue.<br />
I would then have an actual freeRTOS called nwk&#95;task&#40;&#41; which would have a state machine to do various network maintenance and upkeep etc. Inside the state machine there would be some calls to a nwk&#95;send&#40;&#41; function which would sendToQueue&#40;&#41; for the outgoing queue. Likewise there would have to be some receiveFromQueue&#40;&#41; calls on the incoming queue which would process whatever packets I receive. Then lastly this freeRTOS task would call my function radio&#95;task&#40;&#41;<br />
I would potentially have other tasks running which would monitor sensor data and perhaps also call nwk&#95;send&#40;&#41; when certain events occur based on sensor data etc.<br />
I feel like that is not a terrible approach, but I&#8217;m running into a few difficulties that I thought I would ask about. Questions:  
I&#8217;ve created a typedef for my nwk&#95;packet&#95;t which is a struct consisting of an address, a statically defined array which is the maximum size for a radio packet, and a data&#95;length which says how much of the array is actually used for this packet. How do I make a freeRTOS queue which holds my nwk&#95;packet&#95;t &#8216;s?? Also is there a better way to make my nwk&#95;packet&#95;t than using the statically sized array? I thought about using a pointer but then I have to make sure the array that I&#8217;m sending isn&#8217;t overwritten until it&#8217;s actually pulled off the queue right?<br />
I&#8217;m confused about where blocking would/needs to occur. By using the global boolean flag in my data ready ISR I allow interrupts to occur more frequently, but does that mean I need to use portENTER&#95;CRITICAL&#40;&#41; when I actually push/pull data from the queues?<br />
How would a more experienced embedded programmer structure the tasks and queues to allow for a network layer on top of my basic radio driver?<br />
Sorry for my severe lack of understanding on some of these topics, this is my first venture into OS level programming. Everything else I&#8217;ve done has been very low level and basic C. Thanks for your help&#33;  
EDIT: One thing I forgot to mention is that my radio has some hardware provisions for acking. You can set a message to be auto acknowledged with a certain number of retries and the hardware will handle all of that. However, a message can still fail which you can read from the radio or have the radio trigger an interrupt when this happens. So I would like to have some notion of a message success and a message failure that does some type of callback but I have no idea how to work that into my structure. Any ideas on that would fit in with removing stuff from the queues etc.?  
Thanks again.
</div></div><div class="thread-post"><h3 class="thread-post-title">ATmega328P queues + IPC + tasks</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 24, 2013</div><div class="thread-post-content">Well there is a lot to take in in your post, so a step at a time:  
<blockquote>
  When the radio&#8217;s data ready interrupt fired, I would set a global boolean variable to signal to my &#8220;radio&#95;task&#40;&#41;&#8221; function to read data from the radios FIFO.
</blockquote>
Is radio&#95;task&#40;&#41; &#40;the function, rather than task&#41; called periodically to ensure the responsiveness of your radio, and to ensure the receive FIFO does not get full?&nbsp; Common design patterns would be:  
1&#41; Have the interrupt handle some of the faster top level protocol management, then signal a task when a complete packet is ready for parsing.  
2&#41; Have the interrupt do nothing more than save the received data into a buffer then signal a task that there is data available for processing.&nbsp; The task then does all the protocol management.  
In both cases the task would remain in the Blocked state until signaled from the interrupt, and the signally from interrupt to task would be performed using a semaphore.&nbsp; Whether approach 1 or 2 was best would be completely dependent on the protocol and what else the system was doing.  
The problem with a global variable is that it has no event signalling capability &#8211; meaning a task cannot Block on a global variable changing, and be automatically removed form the Blocked state when it does change, as it can be using a semaphore.  
<blockquote>
  It would then sendToQueue&#40;&#41; this read packet onto the incoming queue
</blockquote>
It may be possible to do that from the interrupt, depending on the packet.&nbsp; It might be that you want to buffer the packet in RAM, then send a pointer to the buffer on a queue to unblock a task that was blocked waiting for something to arrive on the queue.&nbsp; The receiving task would then own the buffer, and free it &#40;return it for re-use&#41; when it has finished processing its contents.  
<blockquote>
  I would then have an actual freeRTOS called nwk&#95;task&#40;&#41; which would have a state machine to do various network maintenance and upkeep etc. I
</blockquote>
Sounds reasonable.  
I&#8217;m not sure if I&#8217;m answering your question, but hopefully giving some food for thought.  
I solution might be something like:  
for&#40; ;; &#41;<br />
&#123;<br />
&nbsp;&nbsp;&nbsp; /&#42; Wait to be told there is new data. &#42;/<br />
&nbsp;&nbsp;&nbsp; xSemaphoreTake&#40; .. &#41;;  
&nbsp;&nbsp;&nbsp; /&#42; Process the received data. &#42;/<br />
&nbsp;&nbsp;&nbsp; if&#40; xProcessData&#40;&#41; == pdTRUE &#41;<br />
&nbsp;&nbsp;&nbsp; &#123;<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; If processing the received data resulted in a packet to be returned. &#42;/<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; vSendReply&#40;&#41;;<br />
&nbsp;&nbsp;&nbsp; &#125;<br />
&#125;  
…being careful that the hardware is only accessed from a single task, or when protected by something like a mutex.
