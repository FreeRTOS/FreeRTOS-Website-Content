My problem is that sometimes my RTOS + blinking light task demo starts up and runs fine.&nbsp; Other times, I have to restart it a few times &#40;from 1 to 7 so far&#41; and then it runs fine.&nbsp;&nbsp; Fine, meaning for days without a restart.  
I&#8217;m guessing I have a race condition somewhere.&nbsp; It crashes after running vTaskStartScheduler&#40;&#41; and a few tasks.&nbsp; I&#8217;ve been stepping along looking for clues.&nbsp; I&#8217;m out of ideas for targeting my search.&nbsp; I plan to do a few stepping marathons soon looking for clues.  
Do you have any suggestions off the top of your head.  
Thanks  
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on June 20, 2013</div><div class="thread-post-content">If the original port does not have the same problem then look through <a href="http://www.freertos.org/History.txt">http://www.freertos.org/History.txt</a> for changes between V5.x x and V6.x.x, then between V6.x.x and v7.x.x.  
I din&#8217;t think there should be anything significant there. The only major compatibility change was between 4.x.x and 5.x.x, but worth looking.
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/markwrichardson">markwrichardson</a> on June 26, 2013</div><div class="thread-post-content">I finally narrowed down the issue to this simple stub:  
<pre><code>void vApplicationIdleHook( void )
{
//    vCoRoutineSchedule();
    if (ulIdleCycleCountL == 0L)
    {
        ulIdleCycleCountH++;
        ulIdleCycleCountL++;
    }
    else
    {
        ulIdleCycleCountL++;
    }
}
</code></pre>
By commenting out vCoRoutineSchedule&#40;&#41;, RTOS will run days with out a restart.&nbsp; With this line active I can sometimes get the code to run after a few restarts as I mentioned above.  
I&#8217;ve been looking at the 2 PDF docs and online and haven&#8217;t seen any mention of prerequisite initialization.&nbsp; In this demo app, there are no coroutinesregistered.&nbsp; The only reference to coroutine is this one.  
The demo app is basically the one present in the eZ80 user contributed port except for my own LED port assignments.
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on June 26, 2013</div><div class="thread-post-content">If you are not using coroutines then the line should not be there anyway, so just leave it commented out.
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/markwrichardson">markwrichardson</a> on June 26, 2013</div><div class="thread-post-content">I do plan to use them for my project.&nbsp; I&#8217;m evaluating a non-supported port of RTOS for the Zilog eZ80.&nbsp; There was a customer contribution file for this port on the website as of version 5.0.0.&nbsp; I&#8217;m starting small evaluating the stability and correctness of the user supplied port code.&nbsp; I will continue enhancing the demo with simple uses of the features I plan to use and retain it as a baseline.&nbsp; When I reach my project testing phase, I plan to offer that baseline as a user contribution.
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/markwrichardson">markwrichardson</a> on June 27, 2013</div><div class="thread-post-content">Judging by Example 7 on pg 38 of the <strong>Using the FreeRTOS guide</strong> it seems that vApplicationIdleHook&#40;&#41; won&#8217;t be multithreaded.&nbsp; However, in my spartan sample unless the simple increment is atomic the addition is erratic.&nbsp; My processor can&#8217;t do atomic long addition, only 3-byte int.&nbsp; So by surrounding my increment code with DI/EI I&#8217;m able to get predictable responses.  
Does vApplicationHook&#40;&#41; have the potential to be called by each distinct occurrence of vTaskDelay&#40;&#41; being used in each seperately running task when preemption is enabled ?
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on June 28, 2013</div><div class="thread-post-content">vApplicationIdleHook&#40;&#41; is only ever called from the Idle task. I think the Z80 is 8 bits, so 32 bit additions will probably be done in four or more steps, with intermediate results held in registers or on the stack &#40;I don&#8217;t know how many registers the Z80 has but guess not many&#41;. If the addition is sometimes getting the wrong answer then it is likely that the intermediate values are being corrupted. If the values are on the stack then it could be a simple RAM corruption. If the intermediate values are in registers then it seems the context switch is not working properly.
</div></div><div class="thread-post"><h3 class="thread-post-title">RTOS port crash and restart</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/markwrichardson">markwrichardson</a> on June 28, 2013</div><div class="thread-post-content">I had wondered about the context switch and will check that again next.  
The eZ80 is an &#8216;enhanced&#8217; Z80.&nbsp; Just some background for you . .&nbsp; a Z180 was created from the Z80 with 16 bit registers and a paged memory manager.&nbsp; It was a proper superset of the Z80 and invited binary porting to a 1MB memory space. . .&nbsp; the eZ80 was another derivative of the Z80 with 24 bit registers and a full 16MB memory space with no paging required.&nbsp; It was also a superset of the Z80.  
My last post was because I had added a single byte increment during entry and decrement at exit.&nbsp; Both are a single instruction opcode.&nbsp; The code below, before I added the DI / EI, led me to the conclusion of a multi thread issue.&nbsp;   
<pre><code>unsigned long AIDtotal = 0;
unsigned int ulIdleCycleCountL = 0;
unsigned int ulIdleCycleCountH = 0;
unsigned char AIDcnt = 0;   
void vApplicationIdleHook( void )
{
//  vCoRoutineSchedule();
    asm( "DI" );
    AIDcnt ++;
    if (AIDcnt &gt; 2)
    {
        asm("nop");
        asm("nop");
        asm("nop");
        asm("nop");  // breakpoint
        asm("nop");
        asm("nop");
        asm("nop");
        AIDtotal ++;
    }
    if ( ulIdleCycleCountL == (unsigned int)0xFFFFFF )
    {
        asm("nop");
        asm("nop");
        asm("nop");
        ulIdleCycleCountH++;   // original was breakpoint here 
        asm("nop");
        asm("nop");
        asm("nop");
        ulIdleCycleCountL = (unsigned int)0 ;
    }
    else
    {
        ulIdleCycleCountL =  ulIdleCycleCountL + 1;
    }
    AIDcnt --;
    asm( "EI" );
}
</code></pre>
Thanks for the reminder to double check the context switch.&nbsp; I&#8217;ll do that again.&nbsp;   
My question in response 6 was because I didn&#8217;t think that AIDcnt could become more than &#8216;1&#8217; unless preemption occurs and another instance of thread through this function has occurred.&nbsp;
