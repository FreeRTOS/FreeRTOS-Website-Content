  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">UDP: Calls to FromISR with enabled interrupts</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michalmn">michalmn</a> on June 4, 2013</div><div class="thread-post-content">When running my own application that uses UDP transport layer on an LPC3250 board I experienced some issues with corrupted xPendingReadyList. With &#8220;corrupted&#8221; I mean weird links &#40;more than one cycle&#41; between list items, wrong number of contained items, etc. This problem puzzled me for quite a while until I finally looked on the implementation of xProcessReceivedUDPPacket. It calls  
<pre><code>xSemaphoreGiveFromISR( pxSocket-&gt;xWaitingPacketSemaphore, &amp;xHigherPriorityTaskWoken );
</code></pre>
outside of any critical section. After I replaced it by xSemaphoreGive&#40;&#41; all problems were gone.  
My understanding is that the FromISR&#40;&#41; functions are only to be used where the interrupts are disabled. This assumption is also supported by the fact that using the &#40;from my point of view&#41; correct function without FromISR fixed the problem.  
Could anyone tell me please whether this is a bug? And, in the event that this is considered correct, give me a short explanation why it is ok to call FromISR functions with enabled interrupts?  
Thanks,  
Michal
</div></div><div class="thread-post"><h3 class="thread-post-title">UDP: Calls to FromISR with enabled interrupts</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 5, 2013</div><div class="thread-post-content">The point of the &#8220;FromISR&#8221; functions is that they are safe to use from interrupts, so no, they should not need to be called from critical sections &#40;caveat being, I think, the oddball and old UC3 port&#41;.&nbsp; The implementation of the functions takes care of critical sections with interrupt safe critical section macros.&nbsp; The normal critical section macros, as used by task code, should not be used in an interrupt &#40;nothing that does not end in &#8220;FromISR&#8221; should be used in an interrupt &#8211; the interrupt safe API is kept separate from the task API to allow the kernel implementation to be smaller, simpler and faster&#41;.  
That said however, the critical sections inside the FromISR functions are only necessary for ports that support interrupt nesting &#8211; which most new ports do, but the 3250 port does not.&nbsp; In the 3250 port the preprocessor will remove the calls to the interrupt safe critical nesting macros because interrupts should not be enabled anyway, making the macros obsolete.  
If you find adding your own critical section makes a difference then I would guess the problem lies in your interrupt entry code.&nbsp; Are you re-enabling interrupts before calling the handler?  
Regards.  
</div></div><div class="thread-post"><h3 class="thread-post-title">UDP: Calls to FromISR with enabled interrupts</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michalmn">michalmn</a> on June 5, 2013</div><div class="thread-post-content">Thanks for the clarification. The interrupt handler runs with disabled interrupts. At least I do not intentionally enable them. But I will check again whether this might be the case.  
Just to give you some more information, I have &#40;among others&#41; a simple task that collects data from memory. The body is just:  
<pre><code>f(); vTaskDelayUntil(&amp;lastWakeTime, portMS_TO_TICKS(1));
</code></pre>
As long as f&#40;&#41; takes less than 1 ms, anything is fine. I wanted to see what happens under high load and if f&#40;&#41; has to collect more data, it runs for about 1.5 ms. In this case, after a couple of seconds I end up in an infinite loop in xTaskResumeAll where  
<pre><code>while( listLIST_IS_EMPTY( ( xList * ) &amp;xPendingReadyList ) == pdFALSE )
</code></pre>
loops forever because the list contain corrupted items. Then I added checks around the code that manipulates xPendingTaskList. and found that after calling vListInsertEnd in xTaskRemoveFromEventList the number of elements has not increased. So I suspect that there is a race condition where two tasks access the list at the same time.  
Regards,  
Michal  
</div></div><div class="thread-post"><h3 class="thread-post-title">UDP: Calls to FromISR with enabled interrupts</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 5, 2013</div><div class="thread-post-content">It sounds like you have looked in this in detail already, so I suspect you have read the following link already, but in case not it contains a list of things to check for:  
<a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>  
Normally when somebody reports that type of corruption it is because they are using a port that does support a full interrupt nesting model, and they have set their interrupt priorities incorrectly, which causes the kernel data structures to be accessed without the appropriate protection.&nbsp; For that reason it is probably a good idea to look at the interrupt implementation first.  
You can tell in interrupts are enabled on an ARM9 by looking at the I bit in the CPSR while inside the interrupt.  
How are you entering the interrupt?&nbsp; The normal way would be using a naked function or asm wrapper that uses the portSAVE&#95;CONTEXT macro.  
Do you autovector to the interrupt handlers individually, or do you have a single interrupt entry point for all interrupts?  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">UDP: Calls to FromISR with enabled interrupts</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/michalmn">michalmn</a> on June 5, 2013</div><div class="thread-post-content">Hi Richard,  
Finally, your precise hint pointed me to the bug. As you suggested I really enabled the high speed time interrupt &#40;that I&#8217;m using to trigger the system tick&#41; far too soon. This caused the interrupt handler to run under certain circumstances partially with enabled interrupts. Thanks for your great help.  
Regards,  
Michal
