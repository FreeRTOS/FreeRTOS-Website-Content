The emWin task is the only task running.

</div></div><div class="thread-post"><h3 class="thread-post-title">Hard Fault within vPortYield</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on June 21, 2013</div><div class="thread-post-content">I don&#8217;t know emwin at all, but the first place to look is always stack overflow. I expect graphics takes a lot of stack. Do you have stack overflow checking switched on? The auto stack checking will only check the task stack, so also manually check the interrupt stack &#40;which is the stack configured in the linker and used by main&#40;&#41;&#41;.  
A long shot, but I think portNVIC&#95;INT&#95;CTRL&#95;REG = portNVIC&#95;PENDSVSET&#95;BIT will fault if it is called from unprivileged code. Could it be that your application or emwin is switching out of privileged mode?
</div></div><div class="thread-post"><h3 class="thread-post-title">Hard Fault within vPortYield</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pcalton">pcalton</a> on June 21, 2013</div><div class="thread-post-content">I had some task stack issues when I first started the migration into FreeRTOS, but the task is now provided with ample stack &#40;1024 words&#41; and I am monitoring how much of that is used. Following your suggestions, I tried making the interrupt stack larger and monitoring how much of that is used. Again, the stack high water mark is well within its bounds.   
Finally, the processor remains in privileged mode, so the portNVIC&#95;INT&#95;CTRL&#95;REG = portNVIC&#95;PENDSVSET&#95;BIT line should be ok.  
The fact that the code runs fine for a while &#40;5 minutes at times&#41; without issue makes me think that it faults when the vPortYield coincides with something else.  
There is only one task, so I would have thought the only asynchronous code would be the SystemTick interrupt for the scheduler, a UART interrupt for my debug printf and the LCD interrupt.  
Once the system is running, the only printf used is in the hardfault handler.<br />
The LCD interrupt changes the frame buffer base address to show the most recently rendered screen
