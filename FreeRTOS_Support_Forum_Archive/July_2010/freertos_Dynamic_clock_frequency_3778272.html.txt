  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Dynamic clock frequency</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jakbird">jakbird</a> on July 20, 2010</div><div class="thread-post-content">While working on some power saving routines I ran into a problem with FreeRTOS.&nbsp; The OS assumes the clock stays at a fixed frequency, set by configCPU&#95;CLOCK&#95;HZ.&nbsp;&nbsp; For the STM32 the system tick timer uses this value to calculate the timer reload.&nbsp; However the STM32 can vary the instruction clock &#40;SYSCLK&#41;&nbsp; anywhere from 4MHZ to 72MHZ with substantial power savings at lower frequencies, significant when running on batteries or off the USB Vbus power.  
I&#8217;d like to suggest changing configCPU&#95;CLOCK&#95;HZ into a RAM location instead of a compile time option.&nbsp; And for the STM32 it would be nice if the SysTick timer load routine in port.c was exposed so that the clock frequency changes would affect the SysTick timer in one routine, instead of replacing the one in port.c.  
The other question is where best to vary the frequency?&nbsp; My inclination is to post a change request, and then switch the CPU clock during the tick hook routine, so that &#40;on the STM32&#41; the Systick timer can be modified to keep to the expected tick rate with a minimal loss from resetting the timer.<br />
&nbsp; Jack Peacock
</div></div><div class="thread-post"><h3 class="thread-post-title">Dynamic clock frequency</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 20, 2010</div><div class="thread-post-content">One thing to note, is the as far as I know, the only thing that the FreeRTOS kernel does with the value of configCPU&#95;CLOCK&#95;HZ is us it with the tick rate parameter to set up the tick timer. If you want to change the cpu frequency on the fly, you are free to adjust the clock rate &#40;as well as any other perpetual that also need timing adjusted&#41;. Another point to consider is that FreeRTOS itself doesn&#8217;t need the timer tick to be at any given or constant rate. It is the requirements of the user program that control how accurate you need to keep the tick rate.&nbsp;
</div></div><div class="thread-post"><h3 class="thread-post-title">Dynamic clock frequency</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 21, 2010</div><div class="thread-post-content">When a task blocks on a temporal event &#40;calls something like vTaskDelayUntil&#40;&#41;, vTaskDelay&#40;&#41;, or a queue or semaphore function with a time out&#41; then the kernel will calculate the time at which the task should unblock.&nbsp; If you then change the tick frequency the calculated time will be wrong, and an error will occur &#40;the consequence of which could be significant or insignificant, depending on your application&#41;.  
You can remove this problem by only every blocking for 0 ticks &#40;not blocking&#41; or blocking indefinitely &#40;using portMAX&#95;DELAY if configINCLUDE&#95;vTaskSuspend is also set to 1&#41;, but that severely restricts how you can write your code.  
Another technique I believe is often used is to manually adjust how many times the tick value is incremented during each timer tick.&nbsp; For example, if you slow the timer down by a factor of ten, then you have to call vTaskIncrementTick&#40;&#41; ten times during each timer tick &#40;could potentially be lengthy&#33;&#41; until the timer is set back to its original frequency.  
There are a few people doing interesting work on this issue at the moment and hopefully the results will be published soon.&nbsp; This often includes using special hardware though, with an external low frequency clock in addition to the main timer.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Dynamic clock frequency</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jakbird">jakbird</a> on July 21, 2010</div><div class="thread-post-content">Maintaining a constant rate for the system tick isn&#8217;t an issue per se, since the timer reload count can be adjusted at the same time the CPU frequency is changed &#40;with the assumption that the SysTick timer is tied to the CPU frequency&#41;.&nbsp; There is an issue of exactly when to change the frequency in order to keep the SysTick constant.&nbsp; I&#8217;m guessing that the system tick hook in FreeRTOS occurs soon after the SysTick timer generates an interrupt, so this would be the best place to change CPU speed and the SysTick counter/reload register.&nbsp; The question is, how soon is the hook called after the tick interrupt?&nbsp; Does the task rundown and context switching take place first?  
Unfortunately ARM did miss on the design decision to make the SysTick timer dependent on the CPU instruction clock rather than the base oscillator.&nbsp; Not a big deal but it makes it harder to dynamically control clock rate and power consumption.
