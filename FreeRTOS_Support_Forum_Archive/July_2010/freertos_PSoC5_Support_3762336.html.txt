</div></div><div class="thread-post"><h3 class="thread-post-title">PSoC5 Support</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/psocsensei">psocsensei</a> on July 7, 2010</div><div class="thread-post-content">Joe &#8211;   
I&#8217;m doubtful that the initial stack pointer or reset vector are an issue.&nbsp; Neither of these locations should ever be used from the RAM vector table.  
The initial stack pointer is only ever referenced from a reset condition to set the initial stack pointer.&nbsp; After that it is never used.&nbsp; The reset vector is only referenced from a reset.&nbsp; If a reset happens, then the NVIC is reset to using the ROM vector table.&nbsp; The space for these two locations needs to be present &#40;and is&#41; in order that the other vectors are in the correct place, but the values in these two locations shouldn&#8217;t be needed.  
&#45; Brad  
</div></div><div class="thread-post"><h3 class="thread-post-title">PSoC5 Support</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/psocsensei">psocsensei</a> on July 7, 2010</div><div class="thread-post-content">The PSoC Creator generated startup code will turn off global interrupts as part of the startup process.&nbsp; By the time that main&#40;&#41; is hit the interrupts are disabled.&nbsp; That was done with CyGlobalIntDisable during the configuration process.<br />

I&#8217;m not sure where the enabling of interrupts should be placed in your FreeRTOS port, but they will need to be enabled as you&#8217;ve found:<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#35;define CYGlobalIntEnable&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;&#95;&#95;asm&#40;&#8221;CPSIE&nbsp;&nbsp; i&#8221;&#41;;&#125;

</div></div><div class="thread-post"><h3 class="thread-post-title">PSoC5 Support</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 7, 2010</div><div class="thread-post-content">The FreeRTOS code itself does not use global interrupt flags, but instead uses the basepri register to effectively set a mask level.&nbsp; It would therefore seem most appropriate to re-enable global interrupts from the start up code as part of the individual application code.&nbsp; This could be done just before main is called.&nbsp; Alternatively&nbsp; global interrupts could be re-enabled from anywhere in main&#40;&#41;, or even the official FreeRTOS CM3 port code could be altered to ensure interrupts are globally enabled prior to SVC 0 being called to start the scheduler.&nbsp; Although this latter option involves changing the port code it should make no difference to anything that has gone before as evidently this issue has not arisen in any other CM3 projects &#40;at least its never been reported before&#41;.  
With regard to the value stored in the first position in the RAM vector table.&nbsp; While the CPU itself might not use that location the FreeRTOS code does, as prior to starting the scheduler the system stack is set back to its original &#40;starting&#41; value, and the value is obtained from the vector table.&nbsp; This is done to ensure no RAM is wasted as some of the system stack will have been consumed by the C code used to start the scheduler.&nbsp; The full code is shown below:  
<pre><code>void vPortStartFirstTask( void )
{
    __asm volatile(
    " ldr r0, =0xE000ED08 n" /* Use the NVIC offset register to locate the stack. */
    " ldr r0, [r0]          n"
    " ldr r0, [r0]          n"
    " msr msp, r0       n" /* Set the msp back to the start of the stack. */
    " svc 0             n" /* System call to start first task. */
    );
}
</code></pre>
Regards.
