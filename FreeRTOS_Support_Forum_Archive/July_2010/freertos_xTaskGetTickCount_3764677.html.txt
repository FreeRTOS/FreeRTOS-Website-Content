  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTaskGetTickCount</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/incrediball">incrediball</a> on July 9, 2010</div><div class="thread-post-content">I repeatedly run into the problem of trying to use xTaskGetTickCount within an interrupt &#40;actually I&#8217;m trying to use some other code that sets up a timer&#41; but this crashes the system because of the critical section. Rather than writing an interrupt safe version that does not use a critical section, would this be a possible solution?  
Instead of:  
portTickType xTaskGetTickCount&#40; void &#41;<br />
&#123;<br />
portTickType xTicks;  
/&#42; Critical section required if running on a 16 bit processor. &#42;/<br />
taskENTER&#95;CRITICAL&#40;&#41;;<br />
&#123;<br />
xTicks = xTickCount;<br />
&#125;<br />
taskEXIT&#95;CRITICAL&#40;&#41;;  
return xTicks;<br />
&#125;  
do:  
portTickType xTaskGetTickCount&#40; void &#41;<br />
&#123;<br />
portTickType xTicks;  
do &#123;<br />
xTicks = xTickCount;<br />
&#125; while &#40;xTicks &#33;= xTickCount&#41;;  
return xTicks;<br />
&#125;  
The loop will repeat if xTickCount is updated while it is being read. Since xTickCount is declared as volatile, the loop condition should not be optimised away by the compiler.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/incrediball">incrediball</a> on July 13, 2010</div><div class="thread-post-content">I&#8217;m surprised that no one else seems to have run into the problem with not being able to use xTaskGetTickCount in interrupts. For example what if you want to put a timestamp on some received data? Or what if you want to record the last time a particular interrupt was raised? At present it is not possible.  
I imagine that fixing this issue would stop one or two &#8220;why does my project keep crashing&#8221; posts in this forum because it is not immediately obvious that this function cannot be used in an interrupt.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on July 14, 2010</div><div class="thread-post-content">There are two simple mods to get around the problem, one is to add a function xTaskGetTickCountFromISR function that just return xTickCount, the second is remove the static qualifier on the declaration of xTickCount and just access the variable in the ISR.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on July 14, 2010</div><div class="thread-post-content">Calling vTaskSetTimeOutState&#40;&#41; will also allow you access to the tick count, but indirectly.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskGetTickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/incrediball">incrediball</a> on July 14, 2010</div><div class="thread-post-content">richard&#95;damon: sure, it&#8217;s easy to get to the information if one patches the FreeRTOS source. However I prefer not to do this sort of thing for a number of reasons, e.g. it makes upgrading more difficult. It would be better if the original FreeRTOS source would provide a function that works in both cases &#40;no patches necessary and no &#8220;interrupt version&#8221; that must be used in interrupts otherwise a crash results&#41;. I believe my version of the function would be one way to achieve this and using a loop to check if an update occurred while reading might even be more efficient than the critical section. It is also a method not seldomly used in embedded systems for checking if updates occur while reading peripherals &#40;e.g. when reading a 16 bit running timer on an 8 bit processor&#41;.  
davedoors: interesting tip but this does not appear to be part of the FreeRTOS API so might not be available in this form in future versions.
