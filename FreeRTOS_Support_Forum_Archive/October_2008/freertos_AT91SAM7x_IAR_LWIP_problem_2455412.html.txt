  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AT91SAM7x IAR LWIP problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbeamtn">pbeamtn</a> on October 28, 2008</div><div class="thread-post-content">I&#8217;v been working on porting LWIP to FreeRTOS for the AT91SAM7x with IAR EWARM 5.1.&nbsp; I now have it compiling fine, but LWIP seems to &quot;run away&quot; whenever it receives a packet.&nbsp; For example, if I send it an ARP request, it continues to send ARP responses.&nbsp; It seems to not clear the old receive buffer, so it interprets the buffer over and over as a new packet.
The offending code seems to be in ethernetif.c:
&nbsp;&nbsp;&nbsp; for&#40; ;; &#41;
&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; do
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ethernetif = xNetIf-&gt;state;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; move received packet into a new pbuf &#42;/
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; p = low&#95;level&#95;input&#40; xNetIf &#41;;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if&#40; p == NULL &#41;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; No packet could be read.&nbsp; Wait a for an interrupt to tell us 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; there is more data available. &#42;/
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; vEMACWaitForInput&#40;&#41;;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#125;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#125; while&#40; p == NULL &#41;;
vEMACWaitForInput&#40;&#41; is only run if low&#95;level&#95;input&#40;&#41; returns null.&nbsp; I don&#8217;t fully understand what low&#95;level&#95;input&#40;&#41; does, but it calls ulEMACInputLength&#40;&#41; which always returns a length even if a new packet has not been received.
I don&#8217;t understand the initial do loop, since it seems to me you would want to do vEMACWaitForInput&#40;&#41; and then process what was received instead of trying to receive and only calling vEMACWaitForInput&#40;&#41; if that &quot;fails&quot; &#8212; which it never does for me after I receive the first packet.
I am hesitant to start changing this code since it seems to work for someone.&nbsp; This is the stock Rowley AT91SAM7x logic in the demo distribution.&nbsp; If someone can explain how this is supposed to work and how it determines whether the data is the buffer is new or not, I would certainly appreciate it.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7x IAR LWIP problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 29, 2008</div><div class="thread-post-content">I would have to read the data sheet again to remember exactly, but from memory&#8230;.
Each descriptor has an &#8216;ownership&#8217; bit that says whether the buffer is owned by the software or hardware.&nbsp; When it is owned by the hardware the MAC peripheral can write data into the buffer pointed to by the descriptor, when it is owned by the software the buffer already contains data that has not yet been processed.
The software maintains an index that indicates which descriptor it is going to read next.&nbsp; When it reads data from a descriptor it has to first set &#40;or maybe clear&#41; the ownership bit to pass the buffer back to the hardware, and increment the index so it knows which buffer to read next.
It sounds like your setup if failing to do one or other of these.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7x IAR LWIP problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbeamtn">pbeamtn</a> on October 29, 2008</div><div class="thread-post-content">I think I know more about what is going on, but I&#8217;m not yet sure how to fix it.
I had to set ETH&#95;PAD&#95;SIZE to 2 to get data aligned properly &#8212; otherwise, I get data aborts on address checks.&nbsp; This increases the len returned by ulEMACInputLength&#40;&#41; by 2.&nbsp; This adversely affects vEMACRead&#40;&#41; such that the ownership bit is never reset &#8212; ulSectionLength is 60 but ulTotalFrameLength is 62 in my case.&nbsp; It would seem that the length I need to read should be reduced by ETH&#95;PAD&#95;SIZE.
</div></div><div class="thread-post"><h3 class="thread-post-title">AT91SAM7x IAR LWIP problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/pbeamtn">pbeamtn</a> on October 29, 2008</div><div class="thread-post-content">This is what I had to do to get the demo project to at least respond to pings:
In ethernetif.c, I modified low&#95;level&#95;input&#40;&#41; to look like this:
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if&#40; xSemaphoreTake&#40; xRxSemaphore, netifGUARD&#95;BLOCK&#95;TIME &#41; &#41;
&nbsp;&nbsp;&nbsp; &#123;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; Obtain the size of the packet. &#42;/
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; len = ulEMACInputLength&#40;&#41;;
&nbsp;&nbsp;&nbsp; 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; if&#40; len &#41;
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#123;
//&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#35;if ETH&#95;PAD&#95;SIZE
//&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; len += ETH&#95;PAD&#95;SIZE;&nbsp;&nbsp;&nbsp; /&#42; allow room for Ethernet padding &#42;/
//&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; &#35;endif
&nbsp;&nbsp;&nbsp; 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; /&#42; We allocate a pbuf chain of pbufs from the pool. &#42;/
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; p = pbuf&#95;alloc&#40; PBUF&#95;RAW, len + ETH&#95;PAD&#95;SIZE, PBUF&#95;POOL &#41;;
Instead of modifying len by adding the size of ETH&#95;PAD&#95;SIZE, I leave it alone and just allocate len + ETH&#95;PAD&#95;SIZE.
I don&#8217;t have Rowley CrossStudio to see how the stock demo works, but it worries me to make this kind of change just to convert to IAR.
If someone wants the IAR/lwip AT91SAM7 project I&#8217;m working on, then let me know &#8212; pbeam at windrock dot com.&nbsp; I would love to have another set of eyes look at what I did to get this to work.
