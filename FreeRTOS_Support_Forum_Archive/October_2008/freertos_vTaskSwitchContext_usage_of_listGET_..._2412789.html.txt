  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">vTaskSwitchContext() usage of listGET_&#8230;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/em1ssnuke">em1ssnuke</a> on October 22, 2008</div><div class="thread-post-content">vPreemptiveTick&#40;&#41; calls vTaskSwitchContext&#40;&#41; usage of listGET&#95;OWNER&#95;OF&#95;NEXT&#95;ENTRY&#40;&#41; causes &#95;&#95;dabt&#40;&#41;.&nbsp; Unfortunately there is no task at this point to execute.&nbsp; 
This appears to be a race condition of letting the tick counter generate ticks while tasks are just getting initialized.&nbsp; I assume the tick generation should not occur until after the tasks have been initialized and prior to vTaskStartScheduler&#40;&#41;.&nbsp;&nbsp; Now locating where the tick generation has been initiated.
</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskSwitchContext() usage of listGET_&#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on October 22, 2008</div><div class="thread-post-content">You have not mentioned which port you are using. If using Cortex M3 then this can happen if you attempt to block from within a critical section. It can also happen on any port if you have your interrupt priorities wrong, that is you are using API calls from an interrupt priority about the maximum allowable system call interrupt priority.
