I`ve installed 8.0.0 according to instructions, including changing all types to match those in the FreeRTOS.h header file. These are the only changes I have made from 7.5. I also set the flag in FreeRTOS.h &#8211; configENABLE<em>BACKWARD</em>COMPATIBILITY to 0. Program compiles with no errors or warnings.
After loading and running the software, it`s hanging up, and the processor being reset by the WDT as prescribed intervals. At this point unable to ascertain where the issue is.
What would have changed that could be causing this &#8211; recalling that everything in 7.5 was working just fine?
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange Behaviour in FreeRTOS 8.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 26, 2014</div><div class="thread-post-content">I am not aware of anything that would cause this when upgrading from V7.6.x to V8, however as you have come from V7.5 it may be related to additional error traps included in V7.6.x.
7.6.x includes some additional configASSERTS() statements to trap common misconfigurations on some architectures (you don&#8217;t mention which architecture you are using) and it is possible you are hitting one of those.  Have you tried placing a break point in your assert handler to see if it gets hit before the watchdog resets the system?
Regards.

I did not have an assert defined so I added that. Also created a function to handle the assert calls, but it never gets called &#8211; includes a DBG output and breakpoint.

Thanks for any other suggestions as to what I could try.

It works with no issues at all under IAR/EWARM 7. So it looks like a possible bug in FreeRTOS v8.0 with this device, and/or EWARM 7?
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange Behaviour in FreeRTOS 8.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 28, 2014</div><div class="thread-post-content">Hmm.  I presume as you are updating a previous project to V8.0.0 you are not using any of the new features in V8.0.0, so there must be something in the pre-existing features that is causing your application to behave differently.  Other than the changes in the type names there are not too many differences in the pre V8 features so that will help narrow this down.
So one step at a time &#8211; in your original post you noted you had changed your application to use the new type names, then turned off the backward compatibility.  Did you try compiling and running your application before you did this &#8211; so with your application completely unmodified and only FreeRTOS source files changed (so the old type names in your application were #defined to the new type names by the macros at the bottom of FreeRTOSConfig.h which are removed when configENABLE<em>BACKWARD</em>COMPATIBILITY is set to 0)?
If that does make a difference then we can concentrate on that line of enquiry, if that doesn&#8217;t make a difference (i.e. the issue still exists) then the next thing to look at is the code that should be kicking the watchdog to determine why it is not being kicked&#8230;Is your application kicking the watchdog from several locations, or do you have one task/function/whatever that is monitoring the whole system before the watchdog is kicked.  If you have a central watchdog function then we need to determine why it is deciding not to kick the watchdog &#8211; is the task/function deciding not to kick the watchdog because a test is failing or it the task/function failing to kick the watchdog in time simply because it is never being called?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Strange Behaviour in FreeRTOS 8.0</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/groufosse">groufosse</a> on February 28, 2014</div><div class="thread-post-content">To start, I deleted and reinstalled FreeRTOS v8. Then, on IAR, I started from a working copy of the project, and made incremental changes to go from v7.6 to v8.0. That includes changing all defines in code and setting the #define configENABLE<em>BACKWARD</em>COMPATIBILITY to 0. It&#8217;s now operating with no issues.
Still a bit of a mystery as to how it compiled before &#8211; including a clean and build &#8211; and yet still crashed while running. 
Thanks for your patience and help as I worked through this.  8&#8211;)
