  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">MSP430 &#8211; ISRs unable to call TaskYield()?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alunz">alunz</a> on January 20, 2005</div><div class="thread-post-content">G&#8217;day,
The following is a lengthy-ish explanation of a problem encountered with a
port to the MSP430F149.&nbsp; There seems to be a problem with an ISR calling
TaskYield&#40;&#41; which causes other interrupts to be disabled.&nbsp; If anyone has
encountered something like this would appreciate any pointers.
Am attempting to port FreeRTOS onto the EasyWeb2 dev board from Olimex using
the demo MSP430 port &#40;originally for the MSP430F449&#41; as a base.&nbsp; 
The EasyWeb2 has only one LED but does have a 16&#215;2 LCD.&nbsp; Therefore, have
modded the demo apps so that the LED flashing routines will toggle a char
that is to be displayed &#40;there is a new task that periodically redraws the
LCD every 50ms&#41;.&nbsp; The single main LED is used by the vErrorChecks&#40;&#41; routine
to report on the status of the tasks.
So far so good and the program seems to work.
However there is a problem where vErrorChecks&#40;&#41; will report that there is a
problem &#40;the LED flashes faster&#41; after the demo routine has been running for
a while.&nbsp; Poking around in the code reveals that the problem is with
ComTest.
What is happening is that after a while the Tx ISR stops working.&nbsp; That is,
characters are not being pulled from the xCharsForTx queue and then sent to
the UART.
Further poking around reveals that the problem goes away if the call to
TaskYield&#40;&#41; within the vRxISR&#40;&#41; routine is commented out.
Am a bit of a loss to immediately see why this is a problem, so would
appreciate any pointers that people may have.
Thanks for your time,
aLUNZ
</div></div><div class="thread-post"><h3 class="thread-post-title">MSP430 &#8211; ISRs unable to call TaskYield()?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on January 20, 2005</div><div class="thread-post-content">I think the 149 and 449 are pretty well compatable regarding memory layout.&nbsp; Are you using the demo application exactly as downloaded &#8211; but for the addition of the extra task?
</div></div><div class="thread-post"><h3 class="thread-post-title">MSP430 &#8211; ISRs unable to call TaskYield()?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alunz">alunz</a> on January 21, 2005</div><div class="thread-post-content">Thanks for the very prompt reply.&nbsp; It turned out that the problem as originally reported was caused by creating more threads/tasks than there was memory to support them.
Trimming back the number of threads has mostly got things behaving as they should.&nbsp; Have only got one remaining problem &#40;with the polled queue test&#41; that needs to be investigated.&nbsp; That problem is proving to be very intractable and seems to be defying most physical laws &#40;including causality&#41;.&nbsp; May have to ask some more questions on that one if am unable to nut out what is going wrong there.
For the record, the EasyWeb2 port is very much the original Demo port with changes to:
&#45; setting up the hardware &#40;different ports for LED / LCD, different CLK, Timer ISR setup&#41;
&#45; removing one of the LED tasks from Flash.c
and of course the code to use the LCD to simulate LEDs.
Again, thanks for the reply and thanks for FreeRTOS, it is proving to be fun and useful.
aLUNZ
</div></div><div class="thread-post"><h3 class="thread-post-title">MSP430 &#8211; ISRs unable to call TaskYield()?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 21, 2005</div><div class="thread-post-content">With the demo apps I basically just add tasks until all the memory is used.&nbsp; Perhaps I should make this a little clearer in the docs.
The demo tasks are more for testing the kernel and are each written in isolation which is not memory efficient.&nbsp; I have just added a new section to the FreeRTOS.org WEB site about how applications can be written to use less RAM.&nbsp; You might like to take a look.
Regards.
