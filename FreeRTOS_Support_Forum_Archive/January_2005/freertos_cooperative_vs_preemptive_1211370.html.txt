</div></div><div class="thread-post"><h3 class="thread-post-title">cooperative vs preemptive</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on January 15, 2005</div><div class="thread-post-content">See the page:
http://www.FreeRTOS.org/a00132.html
Also, most ports have a macro portUSE&#95;PREEMPTION.&nbsp; This can be found near the top of the portmacro.h file for the port you are using &#40;described on the port documentation page&#41;.&nbsp; It is best to set portUSE&#95;PREEMPTION to either 1 or 0 &#40;to use preemptive or cooperative respectively&#41;, and then pass this macro to vTaskStartScheduler&#40;&#41;.&nbsp; For example:
&#91;in portmacro.h&#93;
&#35;define portUSE&#95;PREEMPTION 1
&#91;in your application source code&#93;
vTaskStartScheduler&#40; portUSE&#95;PREEMPTION &#41;;
The amount of RAM and ROM used depends on how many tasks you create, not which scheduler is used.&nbsp; However, the scheduler processing overhead is less with the cooperative scheduler.&nbsp; 
If RAM usage is important then consider how you create tasks.&nbsp; Each task requires its own stack so the fewer tasks the less RAM is required.
For example, if your application has one periodic function that must run with very regular frequency, and a few other functions that can be considered &#8216;background&#8217; then:
Option 1:
You can create one task for each function and use preemptive scheduling.&nbsp; The periodic task has the highest priority to ensure it meets its timing requirements.&nbsp; This gives the simplest design but uses the most RAM.
Option 2:
You can create a high priority task for the periodic function, and a single low priority task for the other functions and use the preemptive scheduler.&nbsp; The low priority task would contain some kind of loop that loops through all the background functions.&nbsp; Whenever the periodic function needed to execute the background function task would be preempted.&nbsp; This option uses less RAM as there are less tasks, but still maintains the timing requirements of the periodic task.&nbsp; Provided your background functions never block you could even add them to the Idle task &#8211; saving even more RAM.
Option 3:
This is a hybrid option.&nbsp; It is the same as option 2, but using the cooperative scheduler.&nbsp; If the periodic task can be signalled by an interrupt then you can perform a context switch to the periodic task from the interrupt handler even though the cooperative scheduler is being used.
There will be some more WEB documentation on this very subject appearing in the next week or so.
Regards.
