</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on January 11, 2005</div><div class="thread-post-content">I was told that since you can&#8217;t access the stack in Hi-Tech, you can&#8217;t use a pre-emptive RTOS.
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on January 11, 2005</div><div class="thread-post-content">I&#8217;m not familiar with this compiler but if it does not allow you to access the stack then portions of the port would have to be written in assembly.&nbsp; The IAR ARM7 port is similar.&nbsp; Here the inline assembly cannot access the required C variables so wrappers are written in assembly, and these just call the C functions.&nbsp; The stack management is handled by asm macros.&nbsp; The other ports don&#8217;t have assembly files.
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on January 11, 2005</div><div class="thread-post-content">They use what they call a &quot;Compiled Stack.&quot;&nbsp; I think that means that there is no stack.&nbsp; There is a fixed call tree instead.&nbsp;&nbsp;&nbsp; But I&#8217;m not sure exactly what that means.
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 18, 2005</div><div class="thread-post-content">I&#8217;m actually working on a port to the HT-Soft PICC18 compiler for FreeRTOS.&nbsp; I&#8217;ve gotten it to a point where I&#8217;ve run into an issue with the software stack.&nbsp; I don&#8217;t understand how the MPLAB C18 compiler would work here either.
What I see is that the linker script provided looks like it assigns the firxt 0x60 bytes at the top of the BIG&#95;BLOCK &#40;Heap&#41; to be a stack.&nbsp; Then, in the code &#40;demo&#35;1&#41; the first mention or access of the stack is in the xSerialPortInitMinimal-&gt; xQueueCreate-&gt; pvPortMalloc-&gt; vTaskSuspendAll-&gt; portENTER&#95;CRITICAL function/macro at the first queue creation.&nbsp; This macro assigns INTCON to POSTINC1 without initializing FSR1 in any visible way.&nbsp; 
I don&#8217;t see how this could work at all.&nbsp; Does the MPLAB C18 assign FSR1 magically and permanently to the stack based on the linker request?&nbsp; Wouldn&#8217;t a section of the heap need to ba allocated as a software stack, and the FSR pointed to the right location before access?&nbsp; Otherwise, how can one be sure the compiler hasn&#8217;t hijacked the FSR for some other purpose in the compiled code since last access?
Can someone help?
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ken_l">ken_l</a> on December 18, 2005</div><div class="thread-post-content">I wrote the previous message.&nbsp; Created an account to facilitate further messages.&nbsp; This message is sent with said account.
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 18, 2005</div><div class="thread-post-content">It has been some time since I looked at the PIC port, but I recall that the port code just uses the same programmers model as the compiler.&nbsp; You would have to check the C18 documentation but I&#8217;m petty sure that this register is used as the stack pointer by the compiler and therefore setup by the C init routines before main&#40;&#41; is called.&nbsp; The compiler always expects this to point to the stack from that point on and never uses the register for anything else.
</div></div><div class="thread-post"><h3 class="thread-post-title">HT-TECH picc18</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ken_l">ken_l</a> on December 19, 2005</div><div class="thread-post-content">I have looked and what you describe is correct, although I&#8217;m somewhat suprised by the convention.&nbsp; I&#8217;ve also found that the PICC18 uses a hybrid of the internal hardware stack &#40;for function return addresses&#41; and a compiled stack &#40;for data params&#41;.&nbsp; I&#8217;m not sure how to account for that in FreeRTOS yet.&nbsp; This comparison of PICC18 and C18 may also be useful: http://www.xargs.com/pic/picc18-vs-c18.html.
