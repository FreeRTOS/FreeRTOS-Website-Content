</div></div><div class="thread-post"><h3 class="thread-post-title">Need general advice on debugging a crashing application</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 30, 2015</div><div class="thread-post-content">Hi Aiden,
There is always a bit of guessing what someone&#8217;s program is supposed to do before understanding what might go wrong.
<blockquote>
  accidentally using xSemaphoreGive instead of
  xSemaphoreGiveFromISR within an ISR
</blockquote>
These things must be absolutely clear and correct 🙂
Note that calling &#8216;<code>xSemaphoreGiveFromISR()</code>&#8216; from a ISR does not cause a task switch. The interrupt should end with code like this:
<pre><code>portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
</code></pre>
<blockquote>
  having an interrupt priority level set higher
  than configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY.
</blockquote>
I suppose that you&#8217;ve noticed that a higher priority is often expressed in a lower number?
When debugging with configASSERT() enabled, the priorities may be checked for you in port.c:
<pre><code>configASSERT( ucCurrentPriority &gt;= ucMaxSysCallPriority );
</code></pre>
Beside checking for stack overflows: make sure that your interrupts do not cause any corruption, protect the tasks against your interrupts.
<blockquote>
  as for now I am very confused
</blockquote>
As a general rule: try systematic exclusion of parts of code.
Maybe you want to show what happens in your ISR&#8217;s? Can you show some literal code?
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Need general advice on debugging a crashing application</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on May 30, 2015</div><div class="thread-post-content">Hi Aiden,
Something that comes to mind immediately is the following:
<pre><code>for( ;; )
{
    //Wait for the next frame of AFE data
    xSemaphoreTake(xSemaphoreAFEFrameReady, portMAX_DELAY);
    /* Now 1 frame will be handled */
}
</code></pre>
How did you create this semaphore? Could it happen that two or more interrupts have occurred before the task is waking up?
A <code>SemaphoreHandle_t</code> is actually a <code>QueueHandle_t</code> with a queue length of 1 (and an item size of 0).
What happens if your CPU is very busy and interrupts come too fast?
Can it happen that it takes a while before <code>xMutexTimestampCPUT</code> is available in:
~~~~~
    // Lock the PPS table before proceeding
    xSemaphoreTake(xMutexTimestampCPUT, portMAX_DELAY);
~~~~~
If your CPU is fast enough to handle the stream of frames, you can do the following, use <code>xQueueCreate()</code> in stead of <code>xSemaphoreCreateBinary()</code> :
~~~~
&#8211;    xSemaphoreAFEFrameReady = xSemaphoreCreateBinary();
+    xSemaphoreAFEFrameReady = xQueueCreate( numAFEframes,
+        semSEMAPHORE<em>QUEUE</em>ITEM_LENGTH );
~~~~
( make sure that <code>numAFEframes</code> has been initialised before creating the semaphore as above )
In this way there will be much more elastic, the consuming task may run a bit behind.
Regards, Hein
