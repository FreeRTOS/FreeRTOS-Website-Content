</div></div><div class="thread-post"><h3 class="thread-post-title">Thread-local storage?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mikehitekp">mikehitekp</a> on April 15, 2011</div><div class="thread-post-content">As far as I can see, although GCC doesn&#8217;t barf about &#8216;&#95;&#95;thread&#8217;, it may well just ignore it, as it is not supported everywhere.  
At a conceptual level, I cannot see how just declaring a variable as &#95;&#95;thread helps the compiler know which thread the variable is attached to, nor which variable is intended to be read.  
The only way I have found is to pass a pointer to the task, and by sufficient dereferencing, make it point to some data local to the task. You need to ensure it is dereferenced before the task finishes, and that no-one is using it when this happens.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread-local storage?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rwilder">rwilder</a> on April 15, 2011</div><div class="thread-post-content">Thanks for your reply.  
It isn&#8217;t ignored. GCC adds a bunch of code variables declared with &#95;&#95;thread &#40;I looked at the disassembler listing&#41;. But I think you&#8217;re right, FreeRTOS would have to cooperate somehow &#8211; to tell the GCC libraries that it has performed a context switch. It would also have to cooperate on task creation, to create a new instance of thread-local storage.   
BTW: I know about casting the void-pointer argument to the task. It&#8217;s just ugly if you want the task to call any helper functions. You have to pass the pointer to each helper.The helpers become dependent on the task and that takes away abstraction and re-use. I wish it were hidden, like the &#8220;this&#8221; pointer in C++  
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread-local storage?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on April 16, 2011</div><div class="thread-post-content">The way the compiler would handle Thread Local Storage is to create a structure&nbsp; with an entry for each separate variable. A pointer to the &#8220;current&#8221; thread&#8217;s structure is kept some place handy &#40;either a dedicated register, or a global variable&#41;. The task system &#40;like FreeRTOS&#41; then needs to create a copy of this for each task created, and then change the pointer with each task swap,  
To implement this in FreeRTOS would probably require adding a pointer in the TCB &#40;or maybe just extra space at the base of the stack frame&#41;, code to create the memory &#40;which would need to be in the portable layer as determining how much is needed is implementation specific&#41; and code to change the pointer &#40;which would also need to be in the portable layer, but the state save/restore code that would use it is already there.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread-local storage?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on April 16, 2011</div><div class="thread-post-content">There is a structure used by newlib that does this. I think it was quite a long time ago and this forum is not very search friendly, but it is there somewhere.
