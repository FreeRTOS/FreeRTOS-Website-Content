</div></div><div class="thread-post"><h3 class="thread-post-title">FaultISR on Mutex useage</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 24, 2011</div><div class="thread-post-content">The normal source of problems on Cortex-M3 devices is the interrupt priorities.&nbsp; There is some info here on that:<br />
<a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a> &#40;check item 3&#41;.&nbsp; I presume, as you are calling xSemaphoreTake&#40;&#41;, that the code is not in an interrupt routine, but are there any interrupts firing in the background &#40;other than the kernel tick&#41;?&nbsp; If so, try stopping the interrupts then running the code.  
From what you say, it sounds like the problem is caused in xSemaphoreTake&#40;&#41; itself.&nbsp; Is it possible that the lcd&#95;keypad&#95;shared&#95;pins&#95;mutex variable has got corrupted?&nbsp; Or that the structure to which it points has got corrupted?&nbsp; Do you have run time stack checking switched on &#40;does not look like it form the configuration options settings in your post&#41;, and the malloc&#40;&#41; failed hook defined?&nbsp; It would be worth switching these on as a first step.  
If that does not help find the problem, can you step into the xSemaphoreTake&#40;&#41; function and see exactly where the problem is happening?&nbsp; Is the task blocking when it attempts to take the semaphore, or is the semaphore already available?  
Regards.
