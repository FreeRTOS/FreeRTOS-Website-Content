  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Nesting of critical regions</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on February 4, 2005</div><div class="thread-post-content">I&#8217;m working on a port for the pic18 using wizC as development environment.
It looks like &quot;enter&#95;critical&quot;/&quot;exit&#95;critical&quot; should be able to be nested. The current MCC18 port for the pic18 uses the softwarestack to do this.
Because wizC does not use a framepointer, I cannot use this technique. I looked through some other ports and found an alternative in the &quot;GCCMSP430F449&quot;-port. But I was wondering: Can the pic&#8217;s hardwarestack be used for this? This stack is used by wizC as call/return-stack but is modifiable from software. I think it can be done IF all combinations of enter/exit are at the same level. What I mean is: An enter&#95;critical and it&#8217;s counterpart should always be in the same functioncall-depth. Can anyone tell me if this is guaranteed the case? Now and in the future?
</div></div><div class="thread-post"><h3 class="thread-post-title">Nesting of critical regions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on February 5, 2005</div><div class="thread-post-content">Because my first tests run succefully, I think the answer to the above question is &#8216;yes&#8217;, but confirmation is still appreciated.
</div></div><div class="thread-post"><h3 class="thread-post-title">Nesting of critical regions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 5, 2005</div><div class="thread-post-content">I&#8217;m not sure I quite follow this one.
The msp430 port uses the method for systems that cannot modify the stack without crashing the program &#8211; typically systems that don&#8217;t use a frame pointer as you say.
It works by simply maintaining a count of the depth of critical section nesting.&nbsp; Each task must have it&#8217;s own count, so the count is saved and restored as part of the tasks context.
As far as I can remember the hardware stack on the PIC is used by the processor itself when jumps are made.&nbsp; It might be that you can use values on the stack yourself, provided no function calls are made while the stack has been modified.&nbsp; The bit width of the stack may be odd.&nbsp; I suggest that this has potential to be a dangerous approach &#8230; but I&#8217;m always willing to be proved wrong.
</div></div><div class="thread-post"><h3 class="thread-post-title">Nesting of critical regions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on February 5, 2005</div><div class="thread-post-content">Indeed, I don&#8217;t have a framepointer and therefore cannot modify the software-stack.
The pic hardwarestack is mostly used as a implicit call/return-stack, but it&#8217;s use is not limited to that. It can also be used as a datastack by using the push/pop instructions.
Functioncalling between the push/pop combinations is no problem as long as the pop is done after returning from these functions &#40;stack must be the same before the pop as it was just after the push&#41;.
Basically what I am asking is: Are the enter&#95;critical and the exit&#95;critical always in the same function? 
So, this is no problem:
&#8230;
enter&#95;critical
call func
&nbsp;&nbsp;&nbsp; return from func
exit&#95;critical
&#8230;
But this is a problem:
&#8230;
enter&#95;critical
call func
&nbsp; exit&#95;critical
&nbsp; return from func
&#8230;
Perhaps it&#8217;s easier to simply use the msp430 way. 
It&#8217;s part of my personality: when I dive into something, I want to get to the bottom&#8230; :-&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">Nesting of critical regions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 5, 2005</div><div class="thread-post-content">Things are a little complicated.
The enter/exit routines are always in the same function &#40;function calls can exist between them however&#41; &#8230; BUT &#8230;
It is possible for a context switch to occur within a critical region.&nbsp; This sounds odd but there are places where a portYIELD is called within a critical section.&nbsp; This is ok as each task maintains it&#8217;s own interrupt flags so the next task will start with interrupt enabled.&nbsp; When the task that called yield from within the critical section starts again it will start with interrupts disabled.
I&#8217;m not sure how this affects your idea.&nbsp; When a yield is performed the hardware stack is swapped out &#40;presumably&#41; so any modifications may just get saved as part of the task context and then not affect any other tasks.&nbsp; I think the only way to get confidence in this is to step through a few switches in the simulator.&nbsp; You could try adding:
portENTER&#95;CRITICAL&#40;&#41;;
&nbsp;&nbsp;&nbsp; taskYIELD&#40;&#41;;
portEXIT&#95;CRITICAL&#40;&#41;;
within a simple task and see what happens&#33;
</div></div><div class="thread-post"><h3 class="thread-post-title">Nesting of critical regions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hermarcel">hermarcel</a> on February 5, 2005</div><div class="thread-post-content">Tested it with no problems&#33; Even with multiple tasks sharing their code using different values for pvParameters.
But I have decided to go the MSP430-way because I don&#8217;t see &#40;m&#41;any advantages in my approach. Besides, adding a new concept could possibly interfere with future modifications/additions of FreeRtos.
Thanks anyway, I&#8217;m really learning a lot&#33;
