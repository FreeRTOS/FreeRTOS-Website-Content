</div></div><div class="thread-post"><h3 class="thread-post-title">binary semaphore, ISR not yielding to switch</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on February 4, 2008</div><div class="thread-post-content">Do I understand correctly that the problem is you are not running proper &quot;startup code&quot; in order to initialize global variables on powerup? </div></div><div class="thread-post"><h3 class="thread-post-title">binary semaphore, ISR not yielding to switch</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cjb2002">cjb2002</a> on February 5, 2008</div><div class="thread-post-content">Not actually. GCC is doing right and the startup code is too.
By declaring
&nbsp;&nbsp; static portBASE&#95;TYPE xTaskWoken = pdFALSE; 
it means that at startup it will contain pdFALSE, but as for the ISR routine implies, it will see it just as:
&nbsp;&nbsp; static portBASE&#95;TYPE xTaskWoken;
only that it will be initialized to pdFALSE at startup.
Since I never do a xTaskWoken = pdFALSE; statement in the ISR, it will never get back to pdFALSE except when calling xSemaphoreGiveFromISR, which never returned false in my current implementation.
it&#8217;s amazing how a single statement-splitting changes meanings:
static portBASE&#95;TYPE xTaskWoken;
xTaskWoken = pdFALSE;
but it&#8217;s the way it is meant to be, as what C regards.
hope I made it clear,
Carlos
