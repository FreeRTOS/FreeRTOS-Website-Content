  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Atomicity and `volatile`</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrkline">mrkline</a> on March 17, 2016</div><div class="thread-post-content">FreeRTOS seems to take an&#8230; interesting approach to atomicity. Code in <code>tasks.c</code> and <code>list.h</code> use <code>volatile</code> in an apparent attempt to make some code safe from compiler optimizations that would &#8220;break&#8221; said code during inopportune context switches (either to another task or to an interrupt &#8220;beneath&#8221; the OS). The smoking gun is the existence of <code>configLIST_VOLATILE</code> and its comment,
<blockquote>
  The list structure members are modified from within interrupts, and therefore by rights should be declared volatile.  However, they are only modified in a functionally atomic way (within critical sections of with [sic] the scheduler suspended) and are either passed by reference into a function or indexed via a volatile variable.  Therefore, in all use cases tested so far, the volatile qualifier can be omitted in order to provide a moderate performance improvement without adversely affecting functional behaviour.  The assembly instructions generated by the IAR, ARM and GCC compilers when the respective compiler&#8217;s options were set for maximum optimisation has been inspected and deemed to be as intended.  That said, as compiler technology advances[&#8230;] it is feasible that the volatile qualifier will be needed for correct optimisation[&#8230;] If this is ever experienced then the volatile qualifier can be inserted in the relevant places within the list structures by simply defining configLIST&#95;VOLATILE to volatile in FreeRTOSConfig.h (as per the example at the bottom of this comment block).
</blockquote>
This, along with a linter note in <code>tasks.c</code> that, &#8220;A manual analysis and inspection has been used to determine which static variables must be declared volatile.&#8221;, gives the impression that FreeRTOS authors believe declaring a variable <code>volatile</code> makes it safe to use in multiple, concurrent contexts. This misconception is as dangerous as it is old. <code>volatile</code> only guarantees that the compiler will not optimize away reads and writes to a given value, nor perform speculative reads ahead of time. It is only useful for accessing &#8220;special&#8221; addresses, such as MMIO. For lockless interaction between different contexts of execution, a set of ordering guarantees are also required, which <code>volatile</code> simply does not provide.
This is so crucial to systems programming that the 2011 ISO standards for C and C++ spend great effort to define atomic semantics and the orderings needed (see <a href="http://en.cppreference.com/w/c/atomic">http://en.cppreference.com/w/c/atomic</a>). Unless I am mistaken, the only reason FreeRTOS doesn&#8217;t fall apart during untimely context switches is because most platforms which run it are single-core microprocessors where a write to an address is not buffered or cached in some way. In these cases, <code>volatile</code> has been &#8220;good enough&#8221; to stop breaking optimizations. However, this is a very poor safety net. Some architectures supported by FreeRTOS have instructions needed to properly order lockless code. (see <a href="http://infocenter.arm.com/help/index.jsp?topic=/com.arm.doc.dui0489c/CIHGHHIE.html">ARM&#8217;s <code>DSB</code></a>). These are emitted by C11 atomic reads and writes, but not by <code>volatile</code>. And as the comments for <code>configLIST_VOLATILE</code> note, optimizers could quickly ruin the assumptions FreeRTOS makes about these accesses.
The obvious solution would be to use the C11 facilities for variables shared locklessly across several contexts of execution, but given that FreeRTOS supports many compilers (several of which can be charitably described as &#8220;stable&#8221; and uncharitably described as &#8220;archaic&#8221;), a different approach may be needed. One pre-C11 approach is to create port-specific inline functions or macros that perform various atomic operations (load, store, increment, decrement, compare and swap, etc.). This is the approach taken by Linux. At any rate, why is <code>volatile</code> being used in these places?
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomicity and `volatile`</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on March 17, 2016</div><div class="thread-post-content"><blockquote>
  At any rate, why is volatile being used in these places?
</blockquote>
?
To ensure variables that are accessed and updated from more than one thread of execution are updated and written back to memory atomically as seen from other threads and so are always in a consistent state before another thread of execution accesses the same variable. The atomic behavior is achieved by the fact of having the updates performed in one form of critical section or another which is portable for every compiler and architecture.
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomicity and `volatile`</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrkline">mrkline</a> on March 18, 2016</div><div class="thread-post-content"><blockquote>
  The atomic behavior is achieved by the fact of having the updates performed in one form of critical section or another which is portable for every compiler and architecture.
</blockquote>
Okay, and looking at the ports for architectures with multiple cores or out-of-order execution, I can see that critical sections are guarded with memory fences (<code>DSB</code> on ARM, to continue using that example). But if the memory barriers ensure that writes are &#8220;seen&#8221; by other threads of execution once leaving the critical section, what is the use of <code>volatile</code>? For reads on said values?
If so,
<ol>
<li>Reading a <code>volatile</code> value doesn&#8217;t perform an <em>acquire</em> operation to ensure writes happened before the load from the persepctive of the current thread. (see <a href="http://en.cppreference.com/w/c/atomic/memory_order#Release-Acquire_ordering">http://en.cppreference.com/w/c/atomic/memory_order#Release-Acquire_ordering</a>)</li>
<li><code>volatile</code> does not necessarily guarantee a &#8220;correct&#8221; ordering when reading a value outside a critical section. (One reading of the standard is that ordinary loads can move across a volatile load/store in either direction, but ordinary stores can’t. &#8211; see sources below)</li>
<li><code>voltaile</code> can cause pessimizations unneded by correct lockless code.</li>
</ol>
Additionally, memory fences are quite pessimal on architectures that have loads and stores with built-in acquire and release semantics, such as ARMv8&#8217;s <code>LDRA</code> and <code>STRL</code>. (FreeRTOS supports several such chips.)
In short, <code>volatile</code> is the wrong tool for atomicity and concurrent memory access.
See:
&#8211; Herb Sutter&#8217;s <em><code>atomic&lt;&gt;</code> Weapons</em> talk (<a href="https://channel9.msdn.com/Shows/Going+Deep/Cpp-and-Beyond-2012-Herb-Sutter-atomic-Weapons-1-of-2">Part 1</a>, <a href="https://channel9.msdn.com/Shows/Going+Deep/Cpp-and-Beyond-2012-Herb-Sutter-atomic-Weapons-2-of-2">Part 2</a>. While the talk is on C++, C has the same semantics (the ISO C people lifted it from the C++11 standard, more or less.)
&#8211; http://en.cppreference.com/w/c/atomic
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomicity and `volatile`</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 18, 2016</div><div class="thread-post-content">This has been debated a lot, but not for a long time.  The discussions are always interesting, and thanks for the links, I will read through them.  We have also taken opinions from compiler vendors.
The first thing to do is limit the discussion to the FreeRTOS use cases, as follows, it is very different to Linux!:
1) Single core.  FreeRTOS is used more and more in multi-core, but predominantly in AMP mode, where any shared memory is treated specifically (cache flushes, etc.).  The SMP version of FreeRTOS was created by a third party, so not discussed here.
2) Historically, and still predominantly, on cores that do not perform out of order operations.  This is changing quickly though, and as you point out, where appropriate memory barriers are used in the portable layer, rather than in the core code, where necessary.
3) Supporting some 20+ &#8216;compilers&#8217;, where in many cases a 90&#8217;s version of C is a big ask, let alone C11, some aren&#8217;t really C compilers at all.  Add into the mix that on at least one occasion a premium compiler has required a volatile as a fix to an optimisation bug even when there was no conceivable &#8216;normal&#8217; reason for volatile to be used.
4) Supporting some very basic processor architectures.
5) Kernel data structures can change at any time, including <em>directly</em> from inside interrupts.
6) The functions are genrally very short.
The sequence:
~~~~
Enter<em>critical</em>section();
Update<em>volatile</em>variable();
Exit<em>critical</em>section();
~~~~
is taken as a &#8216;best compromise&#8217; approach that meets all the above constraints in a very portable way.  The variable is volatile to ensure it gets writen back to memory given the constaints above (especially point 5), and barriers can be added to the Exit<em>critical</em>section() function on architectures that need it without upsetting ports that have no equivalent.
Now the disadvantage of the above is that all accesses to the variable within the critical section should be written back to memory, which is sub-optimal, as it is only absolutely necessary when the critical section is exited.  In most cases this not deemed an issue as the variable may only be accessed once where reading it from memory modifying it and writing it back to memory is exactly what is wanted, and generally critical sections are very small.  Some optimisations have been included where this is not the case &#8211; for example where the tick count is read more than once a local const version is created (it cannot be updated in the critical section, or when the scheduler is locked) so the compiler only takes a single bite at it.
On architectures that support special atomic instructions, or using compilers that support the latest and greatest standard (?), some of the volatiles could be removed safely, and perhaps it is time to refactor accordingly, but to do so would require the introduction of a port specific volatile keyword so volatile and port specific volatiles could be mixed and matched within the same code.  However, performance gain would be minimal given the short function lengths (the data still has to be read from memory, modified, then written back to memory, then fenced if required).
This page has been referenced a few times&#8230;
https://www.kernel.org/doc/Documentation/volatile-considered-harmful.txt
&#8230;which gives the example:
~~~~
    spin<em>lock(&amp;the</em>lock);
    do<em>something</em>on(&amp;shared<em>data);
    do</em>something<em>else</em>with(&amp;shared<em>data);
    spin</em>unlock(&amp;the_lock);
~~~~
&#8230;but this is not something that is going to happen in a system where only one thing can be executing at a time.  Spinning in that situation is not going to work if the thing you are waiting for to unlock a resource cannot execute because you are spinning.  In FreeRTOS, and other similar systems, if a resource is locked then the currently executing thread must tell the scheduler it cannot proceed until the lock is released or a timeout occurs, at which time the scheduler will stop executing it.
Thoughts?

</div></div><div class="thread-post"><h3 class="thread-post-title">Atomicity and `volatile`</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mrkline">mrkline</a> on March 21, 2016</div><div class="thread-post-content"><blockquote>
  This page has been referenced a few times&#8230;
  https://www.kernel.org/doc/Documentation/volatile-considered-harmful.txt
  &#8230;which gives the example:
</blockquote>
<pre><code>spin_lock(&amp;the_lock);
do_something_on(&amp;shared_data);
do_something_else_with(&amp;shared_data);
spin_unlock(&amp;the_lock);
</code></pre>
<blockquote>
  &#8230;but this is not something that is going to happen in a system where only one thing can be executing at a time.
</blockquote>
The important point here is not that the code is surrounded by spinlocks (which as you correctly point out, are useless&#42; in a single-core machine with interrupts disabled), but that the spinlocks act as memory barriers. If you follow <code>spin_lock</code> through a few layers of macros, you find it calls <a href="http://lxr.free-electrons.com/ident?i=barrier"><code>barrier</code></a>, which tells the compiler not to make assumptions about the current values in memory. In GCC, this is done with <code>asm volatile("" ::: "memory");</code> (see <a href="https://gcc.gnu.org/onlinedocs/gcc/Extended-Asm.html#Clobbers">https://gcc.gnu.org/onlinedocs/gcc/Extended-Asm.html#Clobbers</a>). By doing this instead of making all variables in the critical section <code>volatile</code>, the compiler is free to perform its normal optimizations <em>within</em> the critical section, but not make assumptions about a memory location&#8217;s contents before or after. I haven&#8217;t read much of Linux&#8217;s internals myself (nor do I have an ARMv7 build of Linux sitting around to disassemble), but I assume <code>spin_lock</code> also provides hardware memory fences (i.e. special instructions, such as ARM&#8217;s <code>DSB</code>) on systems that need it.
Are variables modified inside critical sections accessed outside of one? If so, hardware memory fences may be needed on out-of-order or multiprocessor machines to ensure that all writes from thread <em>A</em> are &#8220;seen&#8221; by thread <em>B</em> when thread <em>B</em> performs its reads. This is where I am more concerned &#8211; using <code>volatile</code> variables inside the critical section is pessimal, but provides the needed ordering guarantees (by virtue of being in the critical section). Any reads outside the critical section, however, are not provided the needed ordering guarantees by virtue of being <code>volatile</code>.
Also, it seems the C++ article for the C11/C++11 memory model explains things a bit more; hopefully you find it helpful: <a href="http://en.cppreference.com/w/cpp/atomic/memory_order">http://en.cppreference.com/w/cpp/atomic/memory_order</a>
&#42; It&#8217;s also worth noting that <code>spin_lock</code> seems to expand to a critical section on single-processor machines: <a href="http://lxr.free-electrons.com/source/include/linux/spinlock_api_up.h#L58">http://lxr.free-electrons.com/source/include/linux/spinlock_api_up.h#L58</a>
