I didn&#8217;t find anything definite when I searched for an answer.
I was reading through http://www.freertos.org/RTOS-Cortex-M3-M4.html and if I understand correctly, the port for Cortex M4 (specifically using the Atmel sam4e8e) allows the use of taskENTER<em>CRITICAL/taskEXIT</em>CRITICAL in interrupts. Is this correct? I&#8217;m unsure because I have until recently used the arm7 port (at91sam7x) and I&#8217;m pretty sure that the use of taskENTER<em>CRITICAL/taskEXIT</em>CRITICAL in interrupts meant certain disaster. I&#8217;m asking because I have some situations where some general purpose code has sections that are protected by critical sections and I want to know if this code can be called from an interrupt or if I need to take special precautions like I needed to on the arm7 platform.
If they can be used in interrupts then what exactly do they do? The API documentation just states &#8220;Preemptive context switches cannot occur when in a critical region&#8221;, so if used within a regular task, then I expect that no other task can preempt and execute but also that no interrupt can preempt the executing code and execute. So if used in an interrupt then does this mean that no higher priority interrupt can preempt the currently executing interrupt?
</div></div><div class="thread-post"><h3 class="thread-post-title">taskENTER_CRITICAL/taskEXIT_CRITICAL on Cortex M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 5, 2014</div><div class="thread-post-content">Hi,
&#8220;taskENTER<em>CRITICAL/taskEXIT</em>CRITICAL&#8221; do nothing more than temporarily disabling interrupts.
vTaskSuspendAll/xTaskResumeAll is a &#8216;lighter&#8217;, it prevents that other competing tasks will become active, while still allowing interrupts.
In general I would advise not to use any critical section within an interrupts handler.
You have some &#8220;general purpose code&#8221; which must be called when an interrupt handler becomes active?
In stead of calling this code directly, I would set a flag and call for instance xSemaphoreGiveFromISR(), so that a regular task wakes up and call the general purpose code.
You don&#8217;t really gain performance by calling the code directly from the interrupt handler.
Regards,
Hein

I was really just wondering if anyone could answer the question of whether critical sections are safe to use on the Cortex m4 port or not.
On a similar theme, since the cortex port allows nested interrupts, how do functions such as xSemaphoreGiveFromISR() protect the semaphore&#8217;s internal contents against corruption if another higher priority interrupt suddenly executes and gives/takes the same semaphore? Are critical sections in use here or do we actually need to use critical sections to protect the semaphore?
</div></div><div class="thread-post"><h3 class="thread-post-title">taskENTER_CRITICAL/taskEXIT_CRITICAL on Cortex M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 5, 2014</div><div class="thread-post-content">Calling xSemaphoreGiveFromISR() from an interrupt should always be safe, as the kernel (xQueueGenericSendFromISR()) will mask interrupts when necessary.
For debugging purposes, sending logging during an interrupt is quite heavy. An alternative could be to use a circular buffer of events:
~~~~~
<h1>define LOG<em>EVENT</em>COUNT ( 100 )</h1>
struct xInterruptEvent {
    char cText[15];
    TickType_t xTimeStamp;
};
struct xInterruptEvent xEvents[ LOG<em>EVENT</em>COUNT ]
volatile BaseType<em>t xEventHead = 0;
BaseType</em>t xEventTail = 0;
void vEventAdd( const char <em>pcFormat, &#8230; )
{
    BaseType_t xIndex = xEventHead;
    xInterruptEvent *pxEvent = &amp;xEvents[xIndex];
    if( ++xEventHead >= LOG_EVENT_COUNT )
    {
        xEventHead = 0;
    }
    va_list args;
    va_start( args, pcFormat );
    /</em> Make sure your version of vsnprintf()
    is reentrant, otherwise use strncpy()
    and fixed text messages <em>/
    vsnprintf( pxEvent->cText,
        sizeof pxEvent->cText, pcFormat, args );
    va_end( args );
    /</em> read a high-resolution time */
    pxEvent->xTimeStamp = xGetHiresTime( );
}
~~~~~
The advantage is that the logging itself almost doesn&#8217;t influence the timing.
You can log all events recorded from a normal task.
Regards
</div></div><div class="thread-post"><h3 class="thread-post-title">taskENTER_CRITICAL/taskEXIT_CRITICAL on Cortex M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ilgitano">ilgitano</a> on September 5, 2014</div><div class="thread-post-content">If you&#8217;re prepared to have a modified local version of FreeRTOS (we&#8217;re not) then you can generalise the critical section handling for use in any context.

</div></div><div class="thread-post"><h3 class="thread-post-title">taskENTER_CRITICAL/taskEXIT_CRITICAL on Cortex M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 5, 2014</div><div class="thread-post-content">Ignoring the whys and wherefores of the advisability of using critical sections for a moment, some direct technical answers:
<blockquote>
  I was reading through http://www.freertos.org/RTOS-Cortex-M3-M4.html and 
  if I understand correctly, the port for Cortex M4 (specifically using the 
  Atmel sam4e8e) allows the use of taskENTER<em>CRITICAL/taskEXIT</em>CRITICAL in 
  interrupts. Is this correct?
</blockquote>
I will have to revisit the page, as if it says that it was not intentional.  As a general rule of thumb taskENTER<em>CRITICAL() and taskEXIT</em>CRITICAL() should not be used in interrupts (see an alternative below).  As it happens, however, and specifically only to the Cortex-M3/4 ports (and a just a hand full of other ports), because of a combination of the way the port works and the intelligence built into the NVIC it is probably ok to do so (note the word &#8216;probably&#8217; in that sentence, it is not something that is part of the testing).
Like other functions and macros though there is an alternative interrupt safe version that can be used.  The macros that can be used are portSET<em>INTERRUPT</em>MASK<em>FROM</em>ISR() &#8211; which returns the existing interrupt mask before setting the mask up, and portCLEAR<em>INTERRUPT</em>MASK<em>FROM</em>ISR() which sets the mask back to its previous value.  You can look at the implementation of xQueueGiveFromISR() to see how the macros are used.
These functions will also work from a task, so maybe your general code that gets called from both tasks and interrupts could use those macros instead of the ones that are intended to be used from tasks?
<blockquote>
  If they can be used in interrupts then what exactly do they do? The API 
  documentation just states &#8220;Preemptive context switches cannot occur when 
  in a critical region&#8221;, so if used within a regular task, then I expect that 
  no other task can preempt and execute but also that no interrupt can preempt 
  the executing code and execute
</blockquote>
Again this answer is specific to the Cortex-M3/4 ports:  Both the macros intended for use in tasks and those intended for use in interrupts set the interrupt priority to a level that will prevent any interrupt that is permitted to execute an interrupt safe FreeRTOS API function from firing.  They do not disable interrupts completely.  The version used in a task maintains a separate interrupt nesting count and clears the interrupt mask when the count reaches 0.  The versions that are intended for use in interrupts set the interrupt mask then clears the mask back to its value prior to being set.
<blockquote>
  So if used in an interrupt then does this mean that no higher priority 
  interrupt can preempt the currently executing interrupt?
</blockquote>
Not quite &#8211; priorities that are too high enough (above the defined maximum system call interrupt priority level) to be allowed to use the FreeRTOS API can still execute.
Regards.
