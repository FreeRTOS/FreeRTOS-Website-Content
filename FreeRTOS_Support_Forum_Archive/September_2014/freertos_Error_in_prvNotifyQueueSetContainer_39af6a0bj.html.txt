  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Error in prvNotifyQueueSetContainer</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ta8086">ta8086</a> on September 15, 2014</div><div class="thread-post-content">It seems there is a bug in queue.c/prvNotifyQueueSetContainer(). </div></div><div class="thread-post"><h3 class="thread-post-title">Error in prvNotifyQueueSetContainer</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on September 15, 2014</div><div class="thread-post-content">I don&#8217;t know it looks right to me. If it was &lt;= it would pass if the queue set way full but then still try to write to it.

</div></div><div class="thread-post"><h3 class="thread-post-title">Error in prvNotifyQueueSetContainer</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidlcamlin">davidlcamlin</a> on March 29, 2017</div><div class="thread-post-content">Have similar issue, set the queue to 160 elements, periodically call xQueueSendToBack and after a while it fails in the same configAssert, having pxQueueSetContainer->uxMessagesWaiting = pxQueueSetContainer->uxLength = 2. I&#8217;m using FreeRTOS 9.0.0 on ATSAME70Q21. This queue is added into a set using xQueueCreateSet(2), maybe is related? 
</div></div><div class="thread-post"><h3 class="thread-post-title">Error in prvNotifyQueueSetContainer</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 29, 2017</div><div class="thread-post-content">The test in the assert is valid.  As already pointed out in this thread, it is checking the line below it doesn&#8217;t fail, because if it did fail then the queue set would be in an inconsistent state.
When you are using a queue set you MUST ensure the number of spaces in the queue set is greater than or equal to the sum of all the spaces in the queues added to the set.  If that is not the case then you can add something to a queue that is a set without the set ever knowing.  That is what the assert is guarding against.
When you read from a queue set you MUST then also read from the queue.  That is, if you read queue handle X from a queue set you MUST then read the item from queue X &#8211; again otherwise the queue set will be in an inconsistent state.
</div></div><div class="thread-post"><h3 class="thread-post-title">Error in prvNotifyQueueSetContainer</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidlcamlin">davidlcamlin</a> on April 7, 2017</div><div class="thread-post-content">I created a set originally for 2 queues, one is receiving timer events (xQueueSendToBack) and the other from interrupt using xQueueSendToBackFromISR. I followed your suggestion and now the queue set is 3 (but no third queue added to the set). After about half a day of running, this assert is triggered again and pxQueueSetContainer->uxMessagesWaiting = pxQueueSetContainer->uxLength = 3. Am I doing something wrong? Maybe the timer (1st) queue isn&#8217;t processed quickly enough because the message from the 2nd queue is still being processed? But how is the set reporting 3 messages waiting when the third queue doesn&#8217;t exist in the set? Do I need to call anything after xQueueSelectFromSet?
