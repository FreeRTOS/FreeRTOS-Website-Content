</div></div><div class="thread-post"><h3 class="thread-post-title">Blocked Task &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 19, 2014</div><div class="thread-post-content">I think there are two ways of debugging in the SDK (at least, there are on the Zynq).  Using the system debugger interface, or using the GDB interface.  This is an option when you create the launch configuration.
If you are using the GDB interface then the <a href="http://www.highintegritysystems.com/down-loads/stateviewer-plug-in/">FreeRTOS Eclipse Plug-in</a> may work in the SDK.  That will show you the handle (or name, <a href="http://www.freertos.org/vQueueAddToRegistry.html">if it is registered</a> in the queue registry) of the object on which the task is blocked.
Actually, I just looked at the <a href="http://www.freertos.org/Free-RTOS-for-Xilinx-MicroBlaze-on-Spartan-6-FPGA.html">documentation page for the Microblaze port</a>, and it shows the Eclipse plug-in being used.  Search for &#8220;kernel aware&#8221; on that linked page.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Blocked Task &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 22, 2014</div><div class="thread-post-content">The plug-in should show you the queue or semaphore on which the task is blocked.  If no queue or semaphore is shown then it is probably blocked on a vTaskDelay() or vTaskDelayUntil().
There are some tools that do what you want (click on a task to see the stack frame for that task) but they are not supported for MicroBlaze (not yet, anyway).  You could do it by hand by obtaining the tasks stack pointer and working it out from the stack frame you can see in the portSAVE_CONTEXT macro which you will find defined in FreeRTOS/Source/Portable/GCC/MicroBlaze/portasm.s.
The stack pointer can be obtained from the tasks handle, which is a pointer to the tasks TCB &#8211; and the first item in the TCB is the task&#8217;s &#8216;top of stack&#8217;.  So the handle is in effect a pointer to the task&#8217;s top of stack.
Regards.
