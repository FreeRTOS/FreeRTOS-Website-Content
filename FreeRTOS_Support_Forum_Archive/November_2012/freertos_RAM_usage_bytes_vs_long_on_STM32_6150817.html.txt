</div></div><div class="thread-post"><h3 class="thread-post-title">RAM usage: bytes vs long on STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 10, 2012</div><div class="thread-post-content"><blockquote>
  If I have a queue that is ten chars long, is it really ten longs long?
</blockquote>
No, but neither is it ten chars long.&nbsp; The space taken is the size of the queue structure itself, and the size of the queue storage area.&nbsp; The size of the queue structure is fixed.&nbsp; In the case of this example, the queue storage area is 10 bytes &#40;the size that was requested&#41;.  
<blockquote>
  Also, that 76 byte overhead for the queue, is that really 76 longs? 
</blockquote>
No, otherwise it would be 304 bytes.  
What makes you think you are running out of RAM.&nbsp; RAM for queues comes from the FreeRTOS heap &#40;<a href="http://www.freertos.org/a00111.html%29.">http://www.freertos.org/a00111.html&#41;.</a>&nbsp; If you want to know if you are running out of FreeRTOS heap you can defined a malloc failed hook function &#40;<a href="http://www.freertos.org/a00016.html%29%2C">http://www.freertos.org/a00016.html&#41;,</a> or depending on the memory alloctor being use xPortGetFreeHeapSize&#40;&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">RAM usage: bytes vs long on STM32</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on November 12, 2012</div><div class="thread-post-content">Are you using stack overflow protection? <a href="http://www.freertos.org/Stacks-and-stack-overflow-checking.html">http://www.freertos.org/Stacks-and-stack-overflow-checking.html</a>   
Your problems sound to apparently random and like the linker script or the start up code is not configured correctly, unless it is just a plain old bug in your code.  
<blockquote>
  because reserving a byte on the STM32 seem to take up a long
</blockquote>
.   
The STM32 is a 32 bit machine and as such required 4 byte alignment. If you reserve a byte, it will place it in a 32 bit word. If you reserve a two byte array it will place it in two bytes of a 32 bit word. Byte bytes that are left over in the 32 bit word will not be used.  
<blockquote>
  I assume from what&#8217;s been said, FreeRTOS is very neat with how it uses memory and it somehow packs chars within a long for queues.
</blockquote>
FreeRTOS does nothing clever. It just expects the compilers being used to comply with the C standards. If you allocate 4 bytes it will give you 4 bytes, which happen to fit in a 32 bit word. If you allocate 5 bytes it will give you five bytes, which fit in two 32 bit words with 3 bytes left over &#40;to make up the second 32 bit word&#41;. If you allocate 400 bytes, it will give you 400 bytes. That is just C code behaving like C code.  
From Travfrog:  
<blockquote>
  What heap file are you using &#40;heap&#95;1,2 or 3&#41;.
</blockquote>
There is also heap&#95;4.c now.  
<blockquote>
  when you are defining a stack size of a heap size, the number is the number of ints so the number of bytes is 4x that
</blockquote>
That is right. When you define a stack size it is in stack units, and on the STM32 each stack variable is 32 bits. So specifying a stack depth of 100 will allocate 100 stack variables, which is 400 bytes. That is how the API is specified and not to be confused with normal memory allocation.
