  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">SAM4 USB</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tomwbarclay">tomwbarclay</a> on November 21, 2012</div><div class="thread-post-content">Hi,<br />
&nbsp;&nbsp;&nbsp; I am developing on Atmel SAM4&#95;Xplained board, with SAM4 processor and Atmel Studio6 GCC.&nbsp; I have Free RTOS working OK. The current application has serial ports running under PDC and interrupt control, with inter-task messages for internal communications. So far so good.   
Now the problem. I am trying to get USB running. Everything I have tried gets the same result, the program hangs. It seems as if the global interrupts are disabled.&nbsp;<br />
So far I have tried<br />
a&#41; make stack bigger for each task &#40;up to 512 bytes&#41; in Free RTOS config<br />
b&#41; change ISR priority from 5 &#40;as delivered by ASF&#41; to 11 to be less than the FreeRTOS max interrupt priority.<br />
&#40;even though I do not make any FreeRTOS calls in the USB stack&#41;<br />
c&#41; delay start up of the USB stack for 10secs by initializing from a delayed task.  
No good they all crash.   
I have built and&nbsp; loaded the demo applications USB-CDC and USB-MSC-RTOS.&nbsp; These seem to work OK and I cant see any code difference between those applications and mine.   
Tracing the crash seems to happen after the first interrupt to the USB handler. &#40;I break then continue&#41;. No other interrupt is then hit after that point.&nbsp; When I break the program manually I find it is then in the FreeRTOS &#8216;lists&#8217; and I presume that it<br />
will effectively loop forever as no tick or other stimulus is occurring.   
Given that the USB stack only runs from this one interrupt and uses callbacks to signal events then I believe it should run &#40;but do nothing&#41; if all the callbacks are do-nothing functions.  
I also find it difficult ton see what interactions there could be between FreeRTOS and the USB stack.  
Has any one successfully implemented the ASF&#40;3.4.1&#41; USB stack on and Atmel SAM 4 processor ?  
I would be grateful for any advice on what to do next ?   
</div></div><div class="thread-post"><h3 class="thread-post-title">SAM4 USB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 21, 2012</div><div class="thread-post-content">The latest ASF version &#40;if it is not already available, it will be in the next couple of days&#41; includes a direct FreeRTOS peripheral control integration.&nbsp; This is the <a href="http://www.atmel.com/images/doc42049.pdf">application note</a>.  
Although this ASF version does not include a FreeRTOS USB peripheral control integration, the example applications that are included do use the existing ASF USB functionality.&nbsp; For example, the USB is used in the SAM4S-EK peripheral control example as in interface to the command line interface &#40;CLI&#41;.  
I am, right now, working on a FreeRTOS integration along the lines of those outlined in the application note highlighted above.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">SAM4 USB</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tomwbarclay">tomwbarclay</a> on November 23, 2012</div><div class="thread-post-content">Hi,<br />
Thanks for the info. I will read the note with interest.  
I eventually found the fix by trawling line by line through a USB example that worked,&#40; but did use FreeRTOS.&#41;&nbsp;<br />
It boils down to adding this line at initialization time in main&#40;&#41;.&nbsp; Its part of the SAM NVIC support in ASF.  
<strong>irq&#95;initialize&#95;vectors&#40;&#41;;</strong>  
Also I placed some real code &#40;toggle a debug LED&#41; into each of the empty callbacks to prevent the compiler from optimizing them out. Now it all works.   
I don&#8217;t yet fully understand … given that if the interrupt system was not running correctly then none of my other comms stuff &#40;USARTS&#41; should have worked, but they clearly did.  
I have not yet removed the debug calls from the callbacks but I anticipate that it will all still work OK.  
Since I use a circular buffer between the FreeRTOS tasks and the USB interrupt stack process I get by by placing the task read functions between ENTER&#95;CRITICAL and EXIT&#95;CRITICAL sections. This seems to work fine and I can leave the USB ISR priority at 5 &#40;the default&#41; as this mechanism complies with FreeRTOS config rules.  
Best regards.
