  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">PIC32 Application hanging in vListInsert</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bull98">bull98</a> on November 7, 2012</div><div class="thread-post-content">Hello, I have an application running on a PIC32 and is hanging in the vListInsert, right by the big comment with suggestions for fixing issues :&#41;&nbsp;   
The application will run for a while, and work fine, until it seems to somewhat randomly hang in this function.  
Here is my summary:  
&#42; Micro: PIC32MX795F51L<br />
&#42; Compiler: C32<br />
&#42; Version: v7.1.1<br />
&#42; Standard Demos work  
Steps I have taken:<br />
&#42;Made sure configCHECK&#95;FOR&#95;STACK&#95;OVERFLOW&nbsp; = 2 and I have provided the vApplicationStackOverflowHook function, nothing ends up in there<br />
&#42; Checked the uxTaskGetStackHighWaterMark for all of the tasks, they seem to have plenty of stack space left<br />
&#42; Checked the interrupt priorities, as far as I understand, they look OK to me.&nbsp; Here is what they are set at:  
<pre><code>#define configMAX_SYSCALL_INTERRUPT_PRIORITY    0x03
#define configKERNEL_INTERRUPT_PRIORITY         0x01
</code></pre>
This application uses interrupts for CAN communication, here is their priority settings:  
<pre><code>INTSetVectorPriority(INT_CAN_1_VECTOR, INT_PRIORITY_LEVEL_4);
    INTSetVectorSubPriority(INT_CAN_1_VECTOR, INT_SUB_PRIORITY_LEVEL_0);
    INTEnable(INT_CAN1, INT_ENABLED);
</code></pre>
When it hangs, the call stack can be traced back out to this line:   
<pre><code>CANMessage_STR * message_PTR;
portBASE_TYPE status;
status = xQueueReceive(xQueueHandleCANSend, (const void *) &amp;message_PTR, (2/portTICK_RATE_MS));
</code></pre>
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Application hanging in vListInsert</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bull98">bull98</a> on November 7, 2012</div><div class="thread-post-content">Sorry I forgot to ask an actual question… Does the interrupt priority setting look OK?&nbsp; What would be my next thing to check?&nbsp; From reading other posts regarding this issue, it looks like some corruption of memory could be to blame somewhere in the application?
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Application hanging in vListInsert</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on November 7, 2012</div><div class="thread-post-content">I&#8217;m looking at serial.c in the standard demo as a reference. The function it calls to set the interrupt looks quite different to the one you are using so I guess the microchip API has changed since the demo was written. I would say though that if INT&#95;PRIORITY&#95;LEVEL&#95;4 sets the interrupt priority to 4 then that could be your problem. If the CAN interrupt calls FreeRTOS functions then the priority needs to be 3 or lower.&nbsp; I have no idea what the sub priority is.  
Also, are you entering the interrupt through the assembly code wrapper as described on the web page, and shown in the example I&#8217;m looking at?
</div></div><div class="thread-post"><h3 class="thread-post-title">PIC32 Application hanging in vListInsert</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bull98">bull98</a> on November 7, 2012</div><div class="thread-post-content">Thanks, that did the trick.&nbsp; I have read and re-read the page talking about the interrupt priority, but I somehow got my head turned around reading about the Cortex M3 inverted priority order and thought 4 was lower than 3….&nbsp;&nbsp; Thanks again&#33;
