</div></div><div class="thread-post"><h3 class="thread-post-title">GDB debugging and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/embeddedc">embeddedc</a> on June 1, 2007</div><div class="thread-post-content">You said previously that it was ok when not running the debugger.&nbsp; In the past I have experienced two problems when stepping through this part of the code, neither time with GDB though so I don&#8217;t know if it is relevant.&nbsp; The first was where stepping the debugger temporarily allowed interrupts to execute even when interrupts were globally disabled.&nbsp; This can corrupt your data structures.&nbsp; The second was where the timer that generated the interrupt was not halted when the debugger hit a break point, but kept running.
If neither of these are the problem then I would suggest a simple test.&nbsp; Write a task that sets all the registers to a known value, then calls yield, then checks to ensure the registers still contain the same values.&nbsp; Create two of these tasks, with each task setting the registers to a different known value.&nbsp; Then run the scheduler is cooperative mode.&nbsp; This way you know which value should be in each register of both of the two tasks and can step through the saving and restoring of each when yield is called, to see where the problem occurs.
There are some examples of this technique in the FreeRTOS download, but I cannot find one for the ARM7.&nbsp; Take a look at the function prvSetAndCheckRegisters&#40;&#41; in DemoCORTEX&#95;LM3S102&#95;GCCDemo1main.c, or vRegisterTest&#40;&#41; in the PIC24 or microblaze main&#40;&#41; files.
