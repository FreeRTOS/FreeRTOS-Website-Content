I am trying to run a LPC23xx &#40;an ARM7TDMI-S core&#41;port with CodeSourcery and FreeRTOS v6.0.0. My startup code setups stacks for each mode and ends with SVC mode.  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; MSR&nbsp;&nbsp;&nbsp;&nbsp; CPSR&#95;c, &#35;Mode&#95;SVC|I&#95;Bit|F&#95;Bit<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; MOV&nbsp;&nbsp;&nbsp;&nbsp; SP, R0<br />
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; SUB&nbsp;&nbsp;&nbsp;&nbsp; R0, R0, &#35;SVC&#95;Stack&#95;Size&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;   
&#43; an option to gcc -fomit-frame-pointer is set.  
However during startup FreeRTOS&#40;vTaskStartScheduler&#40;&#41;, no more tasks are created&#41; it always crashes in a PrefetchAbort ISR&#40;more explained below&#41;.<br />
During debugging I have discovered a strange behavior in pxPortInitialiseStack in prvIdleTask.<br />
As a last operation of vTaskStartScheduler is called a macro portRESTORE&#95;CONTEXT&#40;&#41;. The problem is in the instruction   
/&#42; Restore all system mode registers for the task. &#42;/  
&#8220;LDMFD LR, &#123;R0-R14&#125;^   
The register LR points on saved stack&#40;0x4000128C&#41; of prvIdleTask. Memory from debugger is:<br />
0x4000128C&nbsp; 00000000 01010101 02020202 03030303 04040404&nbsp;<br />
0x400012A0&nbsp; 05050505 06060606 07070707 08080808 09090909&nbsp;<br />
0x400012B4&nbsp; 10101010 11111111 12121212 400012C8 00000000&nbsp;<br />
0x400012C8&nbsp; 00005CDC A5A5A5A5 40009180 00007EA8 00000000&nbsp;   
The instruction loads to LR a 15th value, the zero. Next instruction will jump to the restored return address.<br />
LDR LR, .<br />
Because LR is zero, this jump is mostly to some abort ISR start address. No abort is generated. It seems like a one stack shift to the right.  
Please could someone help me with this issue?<br />
Thank you very much<br />
Martin  
</div></div><div class="thread-post"><h3 class="thread-post-title">LPC23xx port problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 25, 2009</div><div class="thread-post-content">I see what you say about Supervisor mode being the last stack to get set up so the CPU should be in Supervisor mode.&nbsp; Normally otherwise I would say that the most likely cause would be that the CPU was simply in the wrong mode.&nbsp; Its worth checking in the debugger all the same, at the point where the task context is resumed.  
Which memory allocation scheme is being used?&nbsp; Heap&#95;1.c, heap&#95;2.c, heap&#95;3.c or something else?&nbsp; Is it possible that the memory being allocated is clashing with something else?  
Are you running the standard demo from the FreeRTOS download?&nbsp; Has it been modified in any way?  
Can you also check that the task stack is truly 8 byte aligned, and not on an odd boundary in particular.  
Regards
</div></div><div class="thread-post"><h3 class="thread-post-title">LPC23xx port problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wella">wella</a> on November 26, 2009</div><div class="thread-post-content">Hi Richard,  
The scheme is heap2.c and I no am using a standard demo. The codesourcery is using CS3 and I cannot compile demo for gcc. I have adopted startup code, set paths and compiled without warnings as a new project.<br />
There is something wrong about this instruction.<br />
ldm&nbsp;&nbsp; lr, &#123;r0, r1, r2, r3, r4, r5, r6, r7, r8, r9, r10, r11, r12, sp, lr&#125;^<br />
If I understand it correctly, it will loads data to registers from address stored in lr to registers r0 &#8211; r14&#40;lr&#41;. We should be now in system&#40;1F&#41; mode due to instruction msr&nbsp;&nbsp; SPSR&#95;fc, r0&#40;0x1F&#41;. The lr contains value 0x4000128C and memory listing is the same like in my previous post.   
If I count correctly, the 15th&#40;lr value&#41; from 0x4000128C is 0x00000000, not<br />
00005CDC &#40;start address of pvrIdleTask&#41;.<br />
The stack is 8 byte aligned, adress is 0x400011E0 &#40;tskIDLE&#95;STACK&#95;SIZE == 60&#41;.  
Here must be some bad dwarf :&#41;. I do not understand at all why others can run examples….  
Martin

</div></div><div class="thread-post"><h3 class="thread-post-title">LPC23xx port problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 26, 2009</div><div class="thread-post-content"><a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a> .&nbsp; Its number 4 ;-&#41;  
The instruction you reference is the expanded version of ldm lr, &#123;r0-r14&#125;^ which loads r0 to r14 from the Supervisor mode link register into the System/User mode link register. Assuming the LPC is already in Supervisor mode.
</div></div><div class="thread-post"><h3 class="thread-post-title">LPC23xx port problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 26, 2009</div><div class="thread-post-content">Correction &#8211; it loads the bytes starting from the address held in the Supervisor mode link register into the System/User mode registers r0 to r14.
