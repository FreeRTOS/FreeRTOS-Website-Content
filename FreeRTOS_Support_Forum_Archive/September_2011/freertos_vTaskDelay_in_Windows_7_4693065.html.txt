</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelay in Windows 7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 5, 2011</div><div class="thread-post-content">The Windows port is a FreeRTOS &#8220;Simulator&#8221;.&nbsp; As it says on the documentation page for the port &#8220;The tick interrupt generation is simulated by a high priority Windows thread that will periodically pre-empt the low priority threads that are running tasks. The tick rate achievable is limited by the Windows system clock, which in normal FreeRTOS terms is very slow and has a very low precision. True real time behaviour cannot therefore be obtained.&#8221;  
While it is common to have ticks running at 100Hz or even 1KHz on a microcontroller, the Windows clock is in comparison extremely clunky.&nbsp; The resolution is dependent on your hardware, but often in the 40ms range &#40;with huge jitter too&#41;.&nbsp; Therefore, attempting to use this clock to get near real time performance would prevent any tasks being able to accurately block for any time that was not a multiple of this 40 &#40;ish&#41; ms, and the average accuracy would be 40/2 ms &#8211; not very good.  
For those reasons, the port simulates a real time system by making time run slowly, where it pretends every &#8216;n&#8217; ms is 1 ms.&nbsp; Asking for a 100ms delay should always result in approximately the same delay being achieved, but it will be nothing like 100ms.  
The simulator is a convenient place to develop code, that can then be moved relatively easy onto a real target, it is not in itself intended to be a real time system.  
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">vTaskDelay in Windows 7</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/arainho">arainho</a> on September 19, 2011</div><div class="thread-post-content">HI All,  
Actually windows can generate clock ticks of 1000 or more with no problems under windows. Windows does have special counters that can be used to generate these high tick clocks. For those interrested below is my version of the &#8220;prvSimulatedPeripheralTimer&#8221; routine which creates the clock ticks. Just substitute the current one in port.c and start ticking away.&nbsp; In my PC the reported max frequency is of about 2mhz&#33;&#33;&#33;  
I have not tested this on single core computers, but on twin core one core is used at 100% and the other is left free which gives the system good response.  
Regards,  
Alfredo  
//&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8212;&#8211;<br />
// Modification by: Alfredo Rainho Neves<br />
// This is an updated version that will actually responde a few thousand times<br />
// a second.<br />
// The CPU load will show very high, but the routine actualy yield<br />
// giving other tasks a chance. In a multicore CPU only one core will have<br />
// a 100% CPU usage<br />
static DWORD WINAPI prvSimulatedPeripheralTimer&#40; LPVOID lpParameter &#41;<br />
&#123;<br />
LARGE&#95;INTEGER lpFrequency;<br />
LARGE&#95;INTEGER startTime;<br />
LARGE&#95;INTEGER currentTime;<br />
unsigned long&nbsp; countPerTick;<br />
unsigned long&nbsp; elapsed;  
/&#42; Just to prevent compiler warnings. &#42;/<br />
&#40; void &#41; lpParameter;  
// Get the performance counter frequency<br />
QueryPerformanceFrequency&#40;&amp;lpFrequency&#41;;  
// Calculate the count per ticks<br />
countPerTick = lpFrequency.LowPart / configTICK&#95;RATE&#95;HZ;  
while&#40;1&#41;&nbsp; &#123;<br />
// Get the start time<br />
QueryPerformanceCounter&#40;&amp;startTime&#41;;  
// Wait for time period to elapse<br />
do &#123;<br />
// Yield to another task to make the system more responsive<br />
Sleep&#40;0&#41;;  
// Get the current time<br />
QueryPerformanceCounter&#40;&amp;currentTime&#41;;  
// Calculate the elpased time<br />
elapsed = currentTime.LowPart &#8211; startTime.LowPart;   
&#125; while &#40;elapsed &lt; countPerTick&#41;;  
WaitForSingleObject&#40; pvInterruptEventMutex, INFINITE &#41;;  
/&#42; The timer has expired, generate the simulated tick event. &#42;/<br />
ulPendingInterrupts |= &#40; 1 &lt;&lt; portINTERRUPT&#95;TICK &#41;;  
/&#42; The interrupt is now pending &#8211; notify the simulated interrupt<br />
handler thread. &#42;/<br />
SetEvent&#40; pvInterruptEvent &#41;;  
/&#42; Give back the mutex so the simulated interrupt handler unblocks<br />
and can access the interrupt handler variables. &#42;/<br />
ReleaseMutex&#40; pvInterruptEventMutex &#41;;<br />
&#125;  
&#35;ifdef &#95;&#95;GNUC&#95;&#95;<br />
/&#42; Should never reach here &#8211; MingW complains if you leave this line out,<br />
MSVC complains if you put it in. &#42;/<br />
return 0;<br />
&#35;endif<br />
