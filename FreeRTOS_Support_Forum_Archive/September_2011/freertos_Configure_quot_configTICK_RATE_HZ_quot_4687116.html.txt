  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Configure &#8220;configTICK_RATE_HZ&#8221;</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/anuradha123">anuradha123</a> on September 1, 2011</div><div class="thread-post-content">All,  
I am using FreeRTOS with STM32L.  
Currently I have configured &#8220;configTICK&#95;RATE&#95;HZ&#8221; parameter in FreeRTOSConfig.h to be 1000.<br />
I want to change this parameter to 250.  
There are&nbsp; vTaskDelay&#40;&#41;s and xTicksToWait defined in my code.<br />
Is it possible to achieve the same delay miliseconds I achieved with Tick rate 1000 in Tick rate 250,<br />
without changing the figures i used at vTaskDelay&#40;&#41;s and&nbsp; xTicksToWaits?  
Thank you.<br />
Anuradha
</div></div><div class="thread-post"><h3 class="thread-post-title">Configure &#8220;configTICK_RATE_HZ&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 1, 2011</div><div class="thread-post-content">If you wrote the delays as plain numbers, no. The key to making these delays &#8220;constant&#8221; over varying tick rates is to compute the value based on configTICK&#95;RATE&#95;HZ like&nbsp;&nbsp;&nbsp; vTaskDelay&#40;delayms &#42; configTICK&#95;RATE&#95;HZ/1000&#41;  
I tend to define a macro to do the conversion and use it on all delays that are specified in ticks, so that I can specify them in ms and not need to worry if I adjust the tick rate.  
There is one hack you could do if this is too much work to do it right, and that is change the tick interrupt to call the tick increment routine 4 times.
</div></div><div class="thread-post"><h3 class="thread-post-title">Configure &#8220;configTICK_RATE_HZ&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mikehitekp">mikehitekp</a> on September 1, 2011</div><div class="thread-post-content">If these are defined in terms of portTICK&#95;RATE&#95;MS, defined in portmacro.h, then timings will still be correct.  
If not they won&#8217;t, but it should be worth changing the definitions from &#40;say&#41; counts &#40;in ticks&#41; to delay&#95;ms / portTICK&#95;RATE&#95;MS. If these are all constants, the compiler will work them out.  
Regards
</div></div><div class="thread-post"><h3 class="thread-post-title">Configure &#8220;configTICK_RATE_HZ&#8221;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 1, 2011</div><div class="thread-post-content">Provided you keep configTICK&#95;RATE&#95;HZ at or below 1000, you can defined delays in milliseconds using:  
5000 / portTICK&#95;RATE&#95;MS &#40;for 5 seconds&#41;<br />
250 / portTICK&#95;RATE&#95;MS &#40;for 250 milliseconds&#41;<br />
etc.  
Then changing configTICK&#95;RATE&#95;HZ will not effect the delay period as portTICK&#95;RATE&#95;MS will be adjusted automatically.  
There are lots and lots and lots of examples of this in the set of standard demo tasks that are used in all the demo applications included in the FreeRTOS download.  
Regards.
