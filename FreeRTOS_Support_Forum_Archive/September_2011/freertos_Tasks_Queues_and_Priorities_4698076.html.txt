1&#46; Some ticket entered the queue and the consumer starts over immediately, bevause he hase the higher priority.<br />

3&#46; The producer starts again and throw in another ticket, that ok<br />

Ok, I run the sample for some time waiting for a crash because this behavior should lead to memory problems, but

</div></div><div class="thread-post"><h3 class="thread-post-title">Tasks, Queues and Priorities</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/sven-de">sven-de</a> on September 8, 2011</div><div class="thread-post-content">In other words: The second queue-event releases your task from the block-state to which it was send with a delay. If this is actually the case that would be a major bug in FreeRTOS. A task blocked by a delay may only be released after termination of the time constraint. The only way around this, I know of, is an example in the reference manual where the task is released earlier by calling vTaskSuspend&#40;&#41; and vTaskResume&#40;&#41; before the actual time limit is reached. Queue-events shouldn&#8217;t have any impact on delays.  
Since such a prominent bug would&#8217;ve been noticed, the problem is probably at your end. My best guess would be that the debugger somehow currupts the behaviour.
</div></div><div class="thread-post"><h3 class="thread-post-title">Tasks, Queues and Priorities</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 8, 2011</div><div class="thread-post-content">I need to get a better understanding of the question.  
<blockquote>
  1&#46; Some ticket entered the queue and the consumer starts over immediately, bevause he hase the higher priority.
</blockquote>
Ok, sounds good so far.&nbsp; A high priority task is blocked on a queue, waiting for data.&nbsp; Data is posted to the queue by a low priority task, causing the higher priority task to unblock &#40;data is in the queue&#41;, and, as it has the higher priority, preempt the task that posted to the queue.&nbsp; Now the high priority task is running.  
<blockquote>
  2&#46; Consumer reaches the first point of waiting
</blockquote>
The consumer, being the higher priority task, is blocked for a fixed period.&nbsp; It enters the Blocked state, which allows the lower priority producer task to execute again.  
<blockquote>
  3&#46; The producer starts again and throw in another ticket, that ok
</blockquote>
The low priority writes to the queue again, but this time there is nothing blocked on the queue as the higher priority consumer is just delaying for a fixed period &#40;not delayed on the queue, just delaying&#41;.&nbsp; Therefore the low priority task should be able to write to the queue, not get preempted as the write does not unblock anything, and just continue.  
This scenario of course could result in the queue becoming full &#8211; if tasks are writing to the queue but the only task that can read from the queue is blocked doing something else.  
<blockquote>
  4&#46; The consumer immediately starts at the beginnung again, not finishing the outstanding work, getting the new ticket and ….
</blockquote>
Up to now I have understood everything, but this bit does not make sense to me, or I have misunderstood what you are saying.&nbsp;   
What should happen is the consumer completes is delay, leaves the Blocked state, then continues with whatever the next thing in its implementation is &#8211; which might be to read from the queue again.  
What you seem to be saying is that the task just starts from the beginning of its implementation again?&nbsp; That can only point to a system crash/reset.&nbsp; The most likely cause for that would be a stack overflow.&nbsp; Do you have stack overflow checking switched on?  
This assumes you are using an official port.&nbsp; If not, I cannot really comment as there may be a bug in the &#40;unofficial&#41; port layer.&nbsp; All the official ports goes through fairly extensive testing that I would hope would highlight such a bug &#40;not that anything is 100% certain of course&#41;.  
Regards.

Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Tasks, Queues and Priorities</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 8, 2011</div><div class="thread-post-content">One thing to watch out for is that debuggers can get confused with task switches. It sounds like while the consumer was &#8220;paused&#8221; you traced through the producer, but during that time the consumer probably finished it&#8217;s delay and started back up, but no breakpoint was set for it any more &#40;the breakpoint following the producer&#41;, and then finished its operations.  
If you use a debugger to &#8220;step&#8221; through a task, you MUST avoid stepping into any function that might be called by multiple threads &#40;including most of FreeRTOS&#41; or you may &#8220;jump threads&#8221; in the stepping and the thread you are tracing runs on ahead. What happens with stepping is that you can &#40;normally will&#41; get a timer interrupt when you step &#40;which the stepping normally doesn&#8217;t follow&#41;, and if that task switches, that can bypass the debugger which put a breakpoint on the next instruction it thought would run, so other tasks run until you get back to task you started from &#40;or any other task that reaches that address&#41;. If you end up with a different task than the one you started with, if you ever follow it on a path the first task doesn&#8217;t take, the first task now run free.  
You can set breakpoints and watch it progress.
