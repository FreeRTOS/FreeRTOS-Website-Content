  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Simple test is ending up in WWDG_IRQHandler</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on September 23, 2011</div><div class="thread-post-content">I have a very basic piece of code that compiles and links without any errors:  
<pre><code>// FreeRTOS includes
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "semphr.h"
// STM32 Library includes
#include "stm32f10x_usart.h"
#include "stm32f10x_rcc.h"
#include "stm32f10x_gpio.h"
void configureUSART2();
void writebytesTask(void *params);
int main(void)
{
  configureUSART2();
  xTaskCreate(writebytesTask, (signed char *) "Task0", 100, (void *) 0, 1, NULL);
  xTaskCreate(writebytesTask, (signed char *) "Task1", 100, (void *) 1, 1, NULL);
  vTaskStartScheduler();
  while(1){}
}
void writebytesTask(void *params)
{
  long i = (long) params;
  while (1) {
    USART2-&gt;DR = i;
    while (!(USART2-&gt;SR &amp; USART_FLAG_TC)) {}
  }
}
</code></pre>
I have left out the definition of configureUSART2&#40;&#41;, but I have tested it and know it works properly.&nbsp; When I flash this to my board &#40;Olimex STM32-H107&#41;, I get no bytes sent out on USART2.&nbsp; When I run OpenOCD and gdb to see what is going on, I can step through each line, up to the call to vTaskStartScheduler&#40;&#41;.&nbsp; After that point, it doesn&#8217;t return &#40;as expected&#41;, but no data is sent out either.&nbsp; When I hit CTRL-C in gdb to halt it, I get this:  
<pre><code>Program received signal SIGINT, Interrupt.
WWDG_IRQHandler () at /home/luke/repos/roboticbicycle/MCP/src/startup_STM32F10X_CL.s:112
</code></pre>
I haven&#8217;t implemented WWDG&#95;IRQHandler&#40;&#41;, it is aliased to the Default&#95;Handler in the startup assembly code &#40;provided by STM and unmodified by me&#41;.&nbsp;   
&nbsp; If I remove all the FreeRTOS code and replace the tasks with a single simple while loop that simply writes to USART2-&gt;DR and waits for the transmission to complete, I receive a continuous stream of data on the machine that I have connected to the Olimex board, so I am confident that this isn&#8217;t merely some communication configuration problem.  
What might be going on here and what am I doing wrong?&nbsp; Any ideas on how to debug this?&nbsp; I&#8217;m new to FreeRTOS and am not sure exactly how to debug things once the scheduler has started &#40;any tips/pointers on this would be welcome&#41;.  
Thanks,<br />
~Luke

</div></div><div class="thread-post"><h3 class="thread-post-title">Simple test is ending up in WWDG_IRQHandler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jackpeacock">jackpeacock</a> on September 23, 2011</div><div class="thread-post-content">WWDG is the Windowed Watchdog timer for the STM32 series controllers.&nbsp; The IRQ is an early warning interrupt that the timer is about to cause a reset.&nbsp; If you don&#8217;t enable the interrupt in your code then most likely the error message is not reliable.
</div></div><div class="thread-post"><h3 class="thread-post-title">Simple test is ending up in WWDG_IRQHandler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on September 23, 2011</div><div class="thread-post-content">WWDG is the Watchdog.&nbsp; I have not enabled it.  
I think the reason it is jumping to that location may have to do with the fact that FreeRTOS needs a few of its functions put into the vector table of the startup code, and since I haven&#8217;t done that, it happens to be jumping to the WWDG handler &#40;aliased to Default&#95;Handler&#41; instead of the proper FreeRTOS handler.&nbsp; I will examine the startup files in the demos to make sure of this.

Try disabling it all the same.&nbsp; It might be enabled by default &#40;not uncommon&#41; or enabled in the start up code.  
<blockquote>
  I think the reason it is jumping to that location may have to do with the fact that FreeRTOS needs a few of its functions put into the vector table of the startup code, and since I haven&#8217;t done that, it happens to be jumping to the WWDG handler &#40;aliased to Default&#95;Handler&#41; instead of the proper FreeRTOS handler.&nbsp; I will examine the startup files in the demos to make sure of this.

You need the SysTick, PendSV and SVC handlers installed.&nbsp; If the vector table is CMSIS compliant you can install them simply by adding the following lines to FreeRTOSConfig.h:  
<pre><code>#define vPortSVCHandler SVC_Handler
#define xPortPendSVHandler PendSV_Handler
#define xPortSysTickHandler SysTick_Handler
</code></pre>
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Simple test is ending up in WWDG_IRQHandler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 23, 2011</div><div class="thread-post-content">Normally I don&#8217;t use semaphores to protect a device, but keep the device under the control of a single task, and only that task directly controls the device. For serial output like this, another option &#40;for many architectures&#41; is to define an output subroutine &#40;callable by any task&#41; that puts the data in a queue and if the serial channel is inactive, forces a serial interrupt. The interrupt routine then is what has exclusive control to the hardware, and it check if data is waiting, and the port is available, and if so, sends the character out. This keeps that tasks from going into a spin wait, waiting to send their character, but they instead block on the queue, letting other tasks have time.

</div></div><div class="thread-post"><h3 class="thread-post-title">Simple test is ending up in WWDG_IRQHandler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on September 24, 2011</div><div class="thread-post-content">A lot of details a processor specific, but here is a general outline:  
<pre><code>xQueueHandle txque; /* Init to a queue to hold  characters to send */
void putchar(char c){
    xQueueSendToBack(txque, &amp;c, portMAX_DELAY);
   if( __serial_tx_empty__){ /* test for transmitter possible stopped */
      __force_serial_tx_interrrupt__;
   }
}
void serial_tx_intterrupt_handler(){
  portBASE_TYPE woken = 0;
  portBASE_TYPE flag;
  char c;
  while(__tx_buffer_not_full__){
    flag = xQueueReceiveFromISR(txque, &amp;c, &amp;waswoken);
    if(flag){
      __tx_buffer__ = c;
    } else {
      break; /* no more to send */
    }
    portEND_SWITCHING_ISR(woken);
  }
</code></pre>
