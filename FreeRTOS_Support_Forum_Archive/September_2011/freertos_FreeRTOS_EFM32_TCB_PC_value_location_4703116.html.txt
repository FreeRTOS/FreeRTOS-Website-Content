</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS EFM32 TCB PC value location</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 11, 2011</div><div class="thread-post-content">Probably the best place to start is to use the FreeRTOS plug in for IAR.&nbsp; If you are using a recent version of IAR then it will already be installed.&nbsp; The plug in will tell you the state of every task, the location of the top of its stack, and which queue/semaphore the task is blocked of &#40;if it is in the Blocked state&#41;.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS EFM32 TCB PC value location</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gastaronum">gastaronum</a> on September 11, 2011</div><div class="thread-post-content">This solution is a bit complicated for me, because my problem does not occur periodically &#40;by accident&#41; with a long interval of time &#40;days&#41; and not in each of device, that my software is run.<br />
Therefore, I run a lot of devices, and if in any of device the problem is occurred, the device will send &#8220;dump&#8221; of debug info &#40;include PC value&#41; through UART..  
I prefer to determine address of the last instruction that is executed in the task in Run-Time and add it to the &#8220;dump&#8221; of my debug info.  
Thank you.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS EFM32 TCB PC value location</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 11, 2011</div><div class="thread-post-content">When the task that is &#8220;stuck&#8221; gets stuck, does the rest of the system continue executing?&nbsp; If so, then the stuck task cannot itself be in the Running state.&nbsp; You could then use the traceTASK&#95;SWITCHED&#95;OUT&#40;&#41; macro to log some data about each task as it is switched out of the Running state &#8211; how useful that is would be debatable though.&nbsp; For example:  
1&#41; If the task is switched out because it yields, the last instruction it executes will always be in the yield function, and that tells you nothing about why it was yielding.&nbsp; You could get around that by using more trace macros to also log data about why yield was called &#40;for example, was it a block on a queue, or because vTaskDelay&#40;&#41; was called, etc.&#41;.  
2&#41; If a task no longer runs it might be because a completely different task is using all the CPU time, and starving it of any time itself.  
Regards.
