  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Problem using vTaskDelayUntil and vListRemove</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alberto_lega">alberto_lega</a> on September 23, 2011</div><div class="thread-post-content">Hi,<br />
I tried to mout FreeRTOS V7.0.1 on a Fujitsu MB96F356RWB. The project is compiled using Softune &#40;F2MC-16 Family SOFTUNE Workbench V30L35&#41;. I started from FreeRTOS released for MB96340.  
I created a new Softune project using start.asm working on my system. I slightly modief it to be as close as possible to the one contained in the release for MB96340.  
I added all the files needed except croutine.c and I modified FreeRTOSConfig.h to exclude co-routines.<br />
I implemented memory model contained in heap&#95;3.c &#40;should be a wrapper for standard malloc and free&#41;.  
As first try, I created one task in main&#40;&#41; with the following code:  
<pre><code>#define CHA_VEH_STATE_MACHINE_TSK_TICK      ( (portTickType) (CHA_VEH_STATE_MACHINE_PERIOD_MS / portTICK_RATE_MS) )
void CHA_VEH_StateMachine(void* parParam){
    portTickType xLastWaitTime;
    for(;;){
        /* Wait until next execution */
        vTaskDelayUntil(&amp;xLastWaitTime,CHA_VEH_STATE_MACHINE_TSK_TICK);
    }
}
</code></pre>
The project was compiled and downloded into the micro, bur some problems raised. Micro&#8217;s Program Counter jumped to position 0x000000 and was impossible to continue execution or to take micro control via EUROScope &#40;debugger&#41;. This problem does not happen without the call to vTaskDelayUntil.  
Moreover, the problem does not raise if I create another task with a low priority which is kept running as a fake background task.  
With an empirical method of cut code and try I found that the problem is related to the call to vListRemove, in particular to its first lines:  
<pre><code>    pxItemToRemove-&gt;pxNext-&gt;pxPrevious = pxItemToRemove-&gt;pxPrevious;
    pxItemToRemove-&gt;pxPrevious-&gt;pxNext = pxItemToRemove-&gt;pxNext
;
</code></pre>
Actually, I do not know deeply FreeRTOS implementation, so I can only make a guess of what is happenning, but I am scared to make some pointer to point to something that does not exist &#40;the task is only one, so there is no next&#33;&#41;<br />
In vListRemove I cannot see any check on this possibility.  
Anyhow, this is only my guess. Because it is not possible to take micro control using the debugger &#40;it does not work&#41; I do not know if my gess is correct or not.  
So, if someone found similar problem, please tell me how to make a workaround to avoid micro crash.  
Bye.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem using vTaskDelayUntil and vListRemove</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 23, 2011</div><div class="thread-post-content">For expediency, the linked lists have items at their ends that are always there.&nbsp; That means you don&#8217;t have to check as you are always guaranteed to have one item in the list.  
Check that your start up code is performing the necessary initialisation of variables, including clearing the bss section to zero.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem using vTaskDelayUntil and vListRemove</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alberto_lega">alberto_lega</a> on September 27, 2011</div><div class="thread-post-content">Thank you very much for your help, richardbarry.  
I am sorry, but I was wrong about the descriptioon of the problem in the previous post . I say that because I found a way to get micro control: I have inserted a while&#40;&#33;Dummy&#41; before the execution of any OS-related function.<br />
This makes the micro stop execution until the variable Dummy is 0. When the micro is turned on and before EUROScope takes control, it remains stuck in the while&#40;&#41;.  
I ran the code lots of time, and I understand that my problem raises when exiting the following function:  
<pre><code>__nosavereg __interrupt void vPortYield( void )
{
    /* Save the context of the interrupted task. */
    portSAVE_CONTEXT();
    /* Switch to the highest priority task that is ready to run. */
    vTaskSwitchContext();
    /* Restore the context of the new task. */
    portRESTORE_CONTEXT();
}
</code></pre>
the macros portSAVE&#95;CONTEXT&#40;&#41; and portRESTORE&#95;CONTEXT&#40;&#41; are directly written in assembly, whereas the function vPortYield&#40;&#41; is compiled and a short header and tail are placed. Header and tail depends on how is defined the function call interface in the project properties. I am currently using &#8220;Stack argument passing&#8221;, which means that the header is simply the instruction  
<pre><code>LINK #$00
</code></pre>
whereas the tail is  
<pre><code>UNLINK
</code></pre>
The problem happens when executing ULINK, the assembly instruction before RETI. This instruction affects Stack Pointer &#40;SP&#41; and Register Word 3 &#40;RW3&#41; in this way:  
&#40;SP&#41; &lt;&#45; &#40;RW3&#41;<br />
&#40;RW3&#41; &lt;&#45; &#40;&#40;SP&#41;&#41;<br />
&#40;SP&#41; &lt;&#45; &#40;SP&#41;+2  
In particular, RW3 in the context of the new task in execution contains a value which cannot be used as SP because it points to 0 &#40;i.e.: &#40;&#40;RW3&#41;&#41;=0&#41;.<br />
This makes me loose the control over the micro and makes the PC be stuck to 0.  
This problem happens at the first context swich, when the task in execution calls for the very first time the function vTaskDelayUntil.   
What should I check or do to solve this problem?   
Thank you very much.<br />
Bye
