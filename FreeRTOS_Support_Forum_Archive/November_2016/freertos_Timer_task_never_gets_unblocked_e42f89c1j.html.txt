  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Timer task never gets unblocked</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/j99yu">j99yu</a> on November 1, 2016</div><div class="thread-post-content">Platform: ATSAMG55J19
FreeRTOS version: 8.0.1 (most recent version available in Atmel Studio 7)
I&#8217;m trying to defer function processing by calling <strong>xTimerPendFunctionCallFromISR()</strong> in a USB handler ISR.
I followed the example from http://www.freertos.org/xTimerPendFunctionCallFromISR.html and have something like the following in my function <strong>UHP_Handler()</strong>:
~~~
    &#8230;
    BaseType<em>t xHigherPriorityTaskWoken = pdFALSE;
    xTimerPendFunctionCallFromISR(ohci</em>bottomhalf, 
                                &amp;IntInfo,
                                NULL,
                                &amp;xHigherPriorityTaskWoken);
<pre><code>portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
...
</code></pre>
~~~
When the timer task runs, it gets blocked on <strong>portYIELD<em>WITHIN</em>API()</strong> when there are no messages in the queue and then it never seems to unblock even after messages get queued.
I have the task priorities set up such that the timer task priority has highest priority (largest numeric value) and have the USB interrupt priority set up as 11 (which is lower priority than <strong>configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY</strong>) .
Other relevant code :
~~~
<h1>define configMAX<em>PRIORITIES                            ( ( uint32</em>t ) 5 )</h1>
<h1>define configPRIO_BITS                                 4</h1>
<h1>define configLIBRARY<em>LOWEST</em>INTERRUPT_PRIORITY         0x0f</h1>
<h1>define configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY    10</h1>
<h1>define configKERNEL<em>INTERRUPT</em>PRIORITY         ( configLIBRARY<em>LOWEST</em>INTERRUPT<em>PRIORITY &lt;&lt; (8 &#8211; configPRIO</em>BITS) )</h1>
<h1>define configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY    ( configLIBRARY</em>MAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY &lt;&lt; (8 &#8211; configPRIO</em>BITS) )</h1>
~~~
I have three tasks running: idle task (priority 0), timer task (priority 4), and an application task (priority 1).
Question:
Why isn&#8217;t the timer task running after <strong>portYIELD<em>FROM</em>ISR()</strong> gets called in the interrupt handler? The first time that the interrupt handler executes, <strong>xHigherPriorityTaskWoken</strong> does get set to <strong>pdTRUE</strong>, but in every subsequent execution, this variable equals <strong>pdFALSE</strong>. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer task never gets unblocked</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 1, 2016</div><div class="thread-post-content">I cannot see anything obviously wrong in your code.
<blockquote>
  Why isn&#8217;t the timer task running after <em>portYIELD_FROM_ISR()</em> gets
  called in the interrupt handler? The first time that the interrupt
  handler executes, <em>xHigherPriorityTaskWoken</em> does get set to <em>pdTRUE</em>,
  but in every subsequent execution, this variable equals <em>pdFALSE</em>.
</blockquote>
This would seem to indicate that the first time it is called it 
successfully unblocks the timer task, but in subsequent calls the timer 
task was not found to be in the blocked state &#8211; maybe because it was:
1) Unblocked by the first ISR, but never executed.  That could be due to 
a memory corruption, perhaps.  Do you have configASSERT() defined? 
(Google it for the documentation page).  Do you have 
configCHECK<em>FOR</em>STACK_OVERFLOW set to 2?
2) The task was unblocked, and it executed, but the implementation of 
the function that was executed caused the timer task to enter the 
blocked state before the function had returned.  What is the function 
you are deferring to the timer task doing?  Is it blocking on anything 
else or does it just run to completion?
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer task never gets unblocked</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/j99yu">j99yu</a> on November 6, 2016</div><div class="thread-post-content">configASSERT is defined and I&#8217;ve changed configCHECK<em>FOR</em>STACK_OVERFLOW  from 1 to 2.
No difference.
The behaviour seems to be case 1) you mentioned. No context switching is happening after portEND<em>SWITCHING</em>ISR(); execution simply resumes in the task that was running prior to the interrupt. I assume that the correct behaviour is that vTaskSwitchContext() gets run at some point after portEND<em>SWITCHING</em>ISR(). However, this is not happening. 
What could be preventing a context switching from occuring? How does a context switch happen from within an ISR anyway?
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer task never gets unblocked</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 7, 2016</div><div class="thread-post-content"><blockquote>
  How does a
  context switch happen from within an ISR anyway?
</blockquote>
You are using an ARM Cortex-M, right?  If so then the context switch 
happens in the PendSV interrupt, and the interrupt that asks for the 
context switch simply sets the PendSV interrupt pending.  Once the 
PendSV is set pending it will execute immediately that all other higher 
priority interrupts have completed.
I assume you have the PendSV interrupt installed?  Are you seeing other 
context switches or is it always the same task that is running (perhaps 
re-reading the thread the answer to that would be obvious, but I&#8217;m 
replying via email).
I would recommend updating to the latest version of FreeRTOS as it will 
contain many more configASSERT() calls that might highlight your issue.. 
  You can do that by simply copying the latest source files (including 
the port layer) over the top of the source files you are currently using.
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer task never gets unblocked</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/j99yu">j99yu</a> on November 8, 2016</div><div class="thread-post-content">I can see context switches happening up until the point that the USB interrupt is enabled. Could it be that these interrupts are occuring at too high a frequency (every ms) and keep preempting the PendSV interrupt, never allowing it to run? 
</div></div><div class="thread-post"><h3 class="thread-post-title">Timer task never gets unblocked</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 8, 2016</div><div class="thread-post-content">Interrupts at 1ms is not going to be a problem.
<blockquote>
  I can see context switches happening up until the point that the USB
  interrupt is enabled.
</blockquote>
That is a big clue.  Have you posted the code of the USB ISR?  Is the 
USB working in an application that is not using FreeRTOS?

~~~
void UHP_Handler()
{
<pre><code>uint32_t int_status;

/**

IntInfo.int_status= int_status;

IntInfo.rh_status= rh_status;
BaseType_t xHigherPriorityTaskWoken = pdFALSE;
