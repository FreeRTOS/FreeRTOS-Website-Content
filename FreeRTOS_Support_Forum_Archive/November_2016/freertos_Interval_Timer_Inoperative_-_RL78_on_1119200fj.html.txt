</div></div><div class="thread-post"><h3 class="thread-post-title">Interval Timer Inoperative  &#8211; RL78 on </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on November 24, 2016</div><div class="thread-post-content"><blockquote>
  However the Timer fires in the IAR RL78 Async_Serial project (from the
  G13 tutorial projects)**!!??
  //#1 &#8211; Using IAR Debugger (/memory view/), have verified that the
  Interval Time vector (0x38) has been initialized and points to the ISR.
</blockquote>
Does the IAR debugger provide a peripheral view that shows how the 
timer&#8217;s registers are configured?  If the registers in the project that 
works are configured the same as the registers in the project that 
doesn&#8217;t work (and you are 100% sure that is the case), then I would 
assume it was something outside of the timer&#8217;s set up that was causing 
the problem.
Interrupts will deliberately be left disabled between the first call to 
a FreeRTOS API function and the first task starting to execute.  As a 
first step (to ensure the compiler syntax, project settings, start up 
code, etc. are correct &#8211; as the required syntax can change between 
compiler versions) I would recommend creating a dummy program that 
configures and uses the timer BEFORE any FreeRTOS functions are called. 
  If that works, then we can move forward bit by bit until we find the 
place where the timer stops working.
For example, you can add code like this to the start of main() &#8211; before 
any other functions are called &#8211; where the function names are 
descriptive of what the function should do:
<pre>
int main( void )
{
    SetupAnyClockesNeededByTheTimer();
    ConfigureTheTimerToCountAndAutoReload();
    // Sit here to make sure no other code runs.
    for(;;);
}
</pre>
In the above I&#8217;m suggesting configuring the timer into an auto reload 
mode, so it counts to a known value (or down to 0 if its a down 
counter), reloads itself, then counts again.  Watch the value of the 
timer in the debugger (or read it in the for(;;) loop if it can&#8217;t be 
viewed in the debugger).
Is the timer counting and reloading as expected?
If so, re-configure the timer so it not only counts, but generates an 
interrupt each time it reloads.  Put a break point in the interrupt handler.
Does the interrupt handler ever get hit?  If not, do any interrupt 
handlers get executed?

After changing the Options -> Debugger from Simulator to E1 <em>(for Renesas Emulator pod that connects to the Renesas Starter Kit)</em> that menu item is replaced with the wordd <strong>Emulator</strong>,  the Interval Timer interrupt worked.  Helps to interact with the hardware instead of a Simulator!!
