  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Best practice for determining busy status of a task processing a queue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/liteyear">liteyear</a> on November 7, 2016</div><div class="thread-post-content">In any multithreaded design I find myself often implementing this sort of pattern:
~~~
void my<em>task()
{
    while(1)
    {
        wait</em>on<em>queue(requestQ, &amp;theOperation);
        raise</em>flag(busy);
<pre><code>    process_queue_item(theOperation);
    lower_flag(busy);
}
</code></pre>
}
void request<em>operation(newOperation)
{
    add</em>to_queue(requestQ, newOperation);
}
~~~
This works pretty well when only one other task is requesting operations and waiting on the results. When you have multiple tasks doing the same however, you quickly run into edge cases where for example the task is between <code>wait_on_queue()</code> and <code>raise_flag()</code> or <code>lower_flag()</code> and <code>wait_on_queue()</code>. In both those cases, it is difficult to determine whether it is safe to assume the task is idle.
For example, imagine the implementation of a &#8220;<code>wait_for_operation_to_complete()</code>&#8221; function in another task. If you call <code>request_operation()</code> and then wait on <code>len(queue) == 0 &amp;&amp; !busy</code>, you could return early because the condition is true in between <code>wait_on_queue()</code> and <code>raise_flag()</code>.
In the pthreads world I&#8217;ve successfully modified this pattern to only pop the operation off the queue <strong>after</strong> processing it. That way <code>len(queue) == 0</code> is a good indication of idleness. If I were to replicate this in FreeRTOS it might look like this:
~~~
QueueHandle_t gOperationQueue = NULL;
void my_task(void *pvParameters)
{
    gOperationQueue = xQueueCreate(3, sizeof(sOperation));
<pre><code>while(1)
{
    xQueuePeek(gOperationQueue, &amp;theOp, portMAX_DELAY);
    process_operation(theOp);
    xQueueReceive(gOperationQueue, &amp;theOp, portMAX_DELAY);
}
</code></pre>
}
void request<em>operation(newOp)
{
    while(!gOperationQueue)
        vTaskDelay(5 / portTICK</em>PERIOD_MS);
<pre><code>xQueueSend(gOperationQueue, newOp, 10 / portTICK_PERIOD_MS);
</code></pre>
}
bool task<em>is</em>idle(void)
{
    return uxQueueMessagesWaiting(gOperationQueue) == 0;
}
~~~
This is neat because it removes the busy semaphore (although you&#8217;d still need to add a mutex if you want concurrent access to variables that the task can update), but I wonder if this is best practice, given that the xQueuePeek and xQueueReceive functions don&#8217;t seem to hint at this sort of usage (eg. the <code>&amp;theOp</code> argument is required for both, even though it is useless in the <code>xQueueReceive</code> call).
How do others tend to implement this sort of pattern? It seems like such a common paradigm with not a lot written about it (that I&#8217;ve seen).
</div></div><div class="thread-post"><h3 class="thread-post-title">Best practice for determining busy status of a task processing a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 7, 2016</div><div class="thread-post-content">My question is what do you need with the busy flag? If the task doing this processing should only have one request in it at a time, that sounds like you want a mutex guarding the access to the task. I would then use a pair of semaphores, one to trigger to that task that a request is pending (and using a shared memory buffer to send the request, alternatively you could use a queue to transfer it) and a second one the task uses to signal the results are ready.
More often, I see something sort of like what you are describing as part of a device driver, where the calling task is going to be held up until the operation is completed, in which case you don&#8217;t need a seperate task, but that it runs within the &#8216;calling task&#8217; (with a mutex so only one task can be actualy within the driver).
</div></div><div class="thread-post"><h3 class="thread-post-title">Best practice for determining busy status of a task processing a queue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/liteyear">liteyear</a> on November 8, 2016</div><div class="thread-post-content">Fair question. Let me be a bit clearer about the purpose of the busy flag. It&#8217;s different to the two scenarios you describe.
In a couple of recent examples the task was a file system task. Operations were load/save/delete/list type things. Imagine that periodically a few operations get queued up &#8211; mount disk, get free space, list files, etc, which keep the internal state up to date if anything changes. Then imagine there are two other tasks that occasionally want to know what the current file list is. They shouldn&#8217;t request their own &#8220;list file&#8221; operation and wait for that to finish because there will already be such an operation in the queue if necessary. It&#8217;s not enough to mutex the file list because the file system task could be busy doing other things first. What they need to know is that the file system task has finished all its operations &#8211; that is, it&#8217;s not busy and is up to date.
There are other scenarios &#8211; say the initialisation task asks the file system task to do a bunch of things nice and early during startup, and then launches tasks A and B. At some point both task A and B need some information about the state of the file system, but neither of them made the request for that initialisation to occur, so they can&#8217;t just check if their own operations have completed. What they should do is check if file system task is busy. If not, then they know the initialisation operations have completed and they&#8217;re right to extract the state details.
So it&#8217;s really a &#8220;have you got anything on your plate at the moment?&#8221; type flag.
