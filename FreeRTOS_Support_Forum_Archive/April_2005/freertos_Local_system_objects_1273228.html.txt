  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Local system objects?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on April 26, 2005</div><div class="thread-post-content">Is it a possible enhancement to store system objects &#40;tasks, semaphores, queues&#41; on stack/static instead of doing a memory allocation?
</div></div><div class="thread-post"><h3 class="thread-post-title">Local system objects?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 26, 2005</div><div class="thread-post-content">This is something that was considered when writing the first version.&nbsp; Like most things it has advantages and disadvantages.
The memory allocation is within the port layer, so you can replace this with anything you like&nbsp; but at the moment the allocation must be done here somehow.&nbsp; The supplied samples are very simple, and if the number of objects are known in advance and never deleted heap&#95;1.c can be used.
It would be too inflexible for all allocation to be done statically, but maybe the functions could have an options for static allocation?&nbsp; This is also true for the task stacks.
Another problem would be that in some cases the types are deliberately hidden, so static allocation would mean that this data hiding would have to be removed.
