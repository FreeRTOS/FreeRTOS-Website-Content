I&#8217;m running a test of the MQTT Client interface on a FreeRTOS/LWIP platform and IAR debugger on a device connected to the local LAN.  LWIP version is 2.1.2.
The problem is that after 1, 2,..15 hours of test the network hangs (no ping, apparently no interrupts) and after breaking with the debugger the stack (Tasks List) results corrupted as in the picture.
Apart from the network all the other tasks work correctly. There was no exception or ASSERT apparently fired. 
The test consists in publishing  2 values (SysTime and T<em>Ext)  every 2 seconds  on a public broker (cloudmqtt.com) and subscribing to 1 message (&#8216;LED&#8217;). The settings of mqtt</em>opts are left  default. The problem is more likely to happen  when MQTT tracing  is disabled, and expecially (but not only) upon receiving the message subscribed.
These are the last lines of output I got before network hangs:

i.e. in the function mqttoutputsend()
..
err = altcpwrite(tpcb, mqttringbufgetptr(rb), sendlen, TCPWRITEFLAGCOPY | (wrap ? TCPWRITEFLAGMORE : 0));

    mqttringbufadvancegetidx(rb, sendlen);
    / Flush /
    altcpoutput(tpcb);
  }*
altcp_output get stuck in this loop:
<em>/ useg should point to last segment on unacked queue /
useg = pcb->unacked;
if (useg != NULL) {
for (; useg->next != NULL; useg = useg->next);
}</em>
..due to corruption of the PCB as reported
If  so, I also wonder why the previos call to altcp<em>write() can pass the check
(tcp</em>write_checks) without entering in 
<em>LWIPASSERT(&#8220;tcpwrite: no pbufs on queue => both queues empty&#8221;,
                pcb->unacked == NULL &amp;&amp; pcb->unsent == NULL);</em>
If you have any ideas on where I could look or need some more info,  let me know.

</div></div><div class="thread-post"><h3 class="thread-post-title">Network hangs during MQTT test</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/iabra">iabra</a> on June 28, 2019</div><div class="thread-post-content">Maybe it is not the definitive solution and I&#8217;m asking you to recheck ,  but it seems to work better this way: 
Note:
The segment pointed by **useg ** was used in  comparations despite of a possible &#8211; and in my case verified &#8211; NULL value.
~~~
err<em>t tcp</em>output(struct tcp<em>pcb *pcb)
{
&#8230;
/* put segment on unacknowledged list if length > 0 */
if (TCP</em>TCPLEN(seg) > 0){
    seg->next = NULL;
    /* unacked list is empty? <em>/
    if (pcb->unacked == NULL)     {
        pcb->unacked = seg;
        useg = seg;
        /</em> unacked list is not empty? <em>/
    } 
    //else
    else if (useg)//<strong>(-IABR Jun 29, 2019 useg CAN be NULL )</strong>
    { 
     /</em> In the case of fast retransmit, the packet should not go to the tail
        * of the unacked queue, but rather somewhere before it. 
        * We need to check for this case. -STJ Jul 27, 2004 <em>/
        if (TCP_SEQ_LT(lwip_ntohl(seg->tcphdr->seqno), lwip_ntohl(useg->tcphdr->seqno))) {
     /</em> add segment to before tail of unacked list, keeping the list sorted */
            struct tcp_seg **cur_seg = &amp;(pcb->unacked);
            while (*cur_seg &amp;&amp;
            TCP_SEQ_LT(lwip_ntohl((*cur_seg)->tcphdr->seqno), lwip_ntohl(seg->tcphdr->seqno))) {
                cur_seg = &amp;((*cur_seg)->next );
            }
            seg->next = (*cur_seg);
            (*cur_seg) = seg;
        } 
        else {
            /* add segment to tail of unacked list */
            useg->next = seg;
            useg = useg->next;
        }
    }
    /* do not queue empty segments on the unacked list */
} 
&#8230;
}
~~~
