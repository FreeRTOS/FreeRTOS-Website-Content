  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">C++ BaseTask for setting up xTaskCreateStatic and calling a client implemented functions via a single static function</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nasher128">nasher128</a> on June 9, 2019</div><div class="thread-post-content">Hi all.
I&#8217;m currently making my own simple C++ wrapper around FreeRTOS and I&#8217;m trying to design it in such a way where I only need the client to implement a virtual function (I&#8217;ve called this runnable()) which is called by xTaskCreateStatic. Because
xTaskCreateStatic requires a static function to be passed in, if I create this function in my base task and pass in the &#8220;this&#8221; pointer to the function for casting to the derived class, everything works as expected. 
However, I have a problem where if I create two objects of the same (e.g. two SensorTasks objects which implement the virtual function I&#8217;ve described), only the second object&#8217;s virtual function is being called.  I think this is down to I&#8217;m passing the same static function address within my BaseClass to both xTaskCreateStatic() calls, making the second call overwrite the first. 
</div></div><div class="thread-post"><h3 class="thread-post-title">C++ BaseTask for setting up xTaskCreateStatic and calling a client implemented functions via a single static function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 9, 2019</div><div class="thread-post-content">I have a similar wrapper at https://github.com/richard-damon/FreeRTOScpp
What I did is use the void* pointer parameter for the create task function to point to the base object that implements the task. The static function then casts the void* parameter into the right object pointer type, and uses it to call the virtual function. Yes, this means that your task can&#8217;t use that parameter for itself, but it does have the object it was part of instead.
</div></div><div class="thread-post"><h3 class="thread-post-title">C++ BaseTask for setting up xTaskCreateStatic and calling a client implemented functions via a single static function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stackmaster">stackmaster</a> on June 22, 2019</div><div class="thread-post-content">That is precisely the same model that I use, on multiple OS&#8217;s, and it works well.
That said, I am a newbie to FreeeRTOS, and I am worried about how this C++ model interacts with <strong>xTaskCreate</strong>.  Does <strong>xTaskCreate</strong> have a &#8220;create suspended&#8221; flag?
Consider the following scenario:
<ol>
<li>We create a C++ wrapper for a thread class object that uses <a href="https://www.freertos.org/a00125.html">xTaskCreate</a> or <a href="https://www.freertos.org/xTaskCreateStatic.html">xTaskCreateStatic</a>.</li>
<li>When the thread starts to run, as stated by <strong>Richard Damon</strong>, the static function does a <strong>reinterpret_cast&lt;></strong> to convert the <strong>void</strong> pointer argument to the function to be a pointer to the  base class of the C++ thread wrapper.</li>
<li>The static function then invokes <strong>pCThreadObject->runnable</strong>, as implied by <strong>nasher</strong>. </li>
<li><strong>pCThreadObject->runnable</strong> starts immediately doing whatever it wants to do, right-away.</li>
<li>Some programmer derives a new class from <strong>CThreadObject</strong> and overrides <strong>CThreadObject::runnable</strong>.</li>
</ol>
Now we see a problem:
Upon construction of <strong>CThreadObject</strong>, the static running thread will attempt to invoke <strong>CDerivedObject::runnable</strong> instead of <strong>CThreadObject::runnable</strong> .  <strong>CDerivedObject::runnable</strong> will think that it is OK to operate against the portion of the aggregate object that pertains only to <strong>CDerivedObject</strong> . Yikes! Race-condition! The program will likely crash.
The most elegant solution to this problem is to allow <a href="https://www.freertos.org/a00125.html">xTaskCreate</a> or <a href="https://www.freertos.org/xTaskCreateStatic.html">xTaskCreateStatic</a> to specify that the new thread is to be created suspended. The new threaad should not be allowed to run at all until <a href="https://www.freertos.org/a00131.html">vTaskResume</a> is invoked. There are other work-arounds that can be done by the programmer, but this is the simplest solution.
Question:
Does FreeRTOS allow a thread to be created in a suspended state?
</div></div><div class="thread-post"><h3 class="thread-post-title">C++ BaseTask for setting up xTaskCreateStatic and calling a client implemented functions via a single static function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 22, 2019</div><div class="thread-post-content">Tasks can not be created in a suspended state, but you can create the task at a lower priority than yourself, suspend it, then move it to a higher priority if desired. My wrapper, if used when the scheduler is running, will make sure that the created task is of lower priority than the creating task, so that the constructor can finish before the task is called (this does require certain options to be enabled, if they aren&#8217;t then it assumes the caller has done what is needed to make sure things happen correctly),
If the task was told to be created at a higher priority than the task creating it, it will be created at a lower priority, and once it executes, it will move its priority to what is desired.
</div></div><div class="thread-post"><h3 class="thread-post-title">C++ BaseTask for setting up xTaskCreateStatic and calling a client implemented functions via a single static function</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stackmaster">stackmaster</a> on June 24, 2019</div><div class="thread-post-content">Just curious: Are you taking care of the new race-condition that could arise where:
1. Spawning thread extracts its priority P7.
2.  Spawning thread prepares to spawn spawned thread at lower priority than P6 &lt; P7..
3.  Spawning thread is preempted.
4.  Some other thread changes priority of spawning thread to, say, P4 &lt; P6.
5.  Spawning thread resumes and spawns spawned thread at priority P6.
6.  Spawned thread runs&#8230;etc&#8230;crash.
Yes, this is very inlikely, but&#8230;I was curious about what you thought about it.
