  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Blocking on Multiple RTOS Objects</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/stackmaster">stackmaster</a> on June 21, 2019</div><div class="thread-post-content">Regarding <a href="https://www.freertos.org/Pend-on-multiple-rtos-objects.html">xQueueSelectFromSet</a>, it is written:
<blockquote>
  NULL is returned if a call to xQueueSelectFromSet() times out. Otherwise xQueueSelectFromSet() returns the handle of the queue set member that is ready for reading, allowing the calling task to immediately call xQueueReceive() or xSemaphoreTake() (on a queue handle or semaphore handle respectively) with the guarantee that the operation will succeed
</blockquote>
In the world of synchronization, there exists analogues to xQueueSelectFromSet on other OS&#8217;s. On Windows, it is <a href="https://docs.microsoft.com/en-us/windows/desktop/api/synchapi/nf-synchapi-waitformultipleobjects">WaitForMultipleObjects</a>. On Linux , it is <a href="https://linux.die.net/man/4/epoll">epoll</a>. On FreeBSD/etc. , it is <a href="https://www.freebsd.org/cgi/man.cgi?query=kqueue&amp;sektion=2">kqueue</a>. 
There has been quite a bit of discussion regarding the theoretically-correct model for mutliple-object synchronization, and what is more pratically correct. IMHO,  of all of the synchronization frameworks, the Windows people found the &#8220;sweet spot&#8221;. In the context of this discussion, they made it so that if <a href="https://docs.microsoft.com/en-us/windows/desktop/api/synchapi/nf-synchapi-waitformultipleobjects">WaitForMultipleObjects</a> returns <strong>true</strong>, the side-effect(s) of having successfully waited against a waitable object occurs, automatically, before <a href="https://docs.microsoft.com/en-us/windows/desktop/api/synchapi/nf-synchapi-waitformultipleobjects">WaitForMultipleObjects</a> returns.
I would like to know how receptive the community would be toward tweaking xQueueSelectFromSet so that the semantics changed to be more inline with <a href="https://docs.microsoft.com/en-us/windows/desktop/api/synchapi/nf-synchapi-waitformultipleobjects">WaitForMultipleObjects</a>.
I was hoping not to get into a lengthy discussion regarding the merits of why the auto-side effect model is better before hearing what others thought.
Regards, SM

I guess I should reveal, upfront, what I have in mind, to avoid design-creep.
I would like a &#8220;full complement&#8221; of synchronization primitives. Of course, FreeRTOS already has a surprisingly rich model for synchronization. Here, I am talking more about the waiting functions. These are the enhancments that I would make:
1. Create a new function <strong>xWaitForOne</strong> that waits against a single synchronization object. This function would take a <strong>TickType_t</strong>  to specify time-out.
2. Create a new function <strong>xWaitForAny</strong> that waits against a multiple synchronization objects. This function would be able to wait for up to a <strong>#define</strong> specified number objects simultaneously. Microsoft calls their <strong>#define</strong> for this maximum <strong><a href="https://docs.microsoft.com/en-us/windows/desktop/api/synchapi/nf-synchapi-waitformultipleobjects">MAXIMUM<em>WAIT</em>OBJECTS</a></strong>. This function would take a <strong>TickType_t</strong>  to specify time-out.
3. Make <strong>timer</strong>, <strong>event</strong>, <strong>semaphore</strong>, <strong>mutex</strong>, all waitable using <strong>xWaitForOne</strong> and <strong>xWaitForAny</strong> , using handles to such objects as arguments.
4. My prefernce would have been to modify <a href="https://www.freertos.org/FreeRTOS-Software-Timer-API-Functions.html"> FreeRTOS&#8217;s existing timer primitive</a> to make it possible to insert its handle into <strong>xWaitForOne</strong> and <strong>xWaitForAny</strong>, but I am not sure whether that is desirable or possible. There is also the issue of FreeRTOS&#8217;s timer&#8217;s callback function, but that pointer argument could be set to NULL under the new model.
5. Coincidentally, in <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/e55d04fa72/">this thread</a>, Richard Damon mentions that he has a C++ wrapper for FreeRTOS&#8217;s thread framework. When one clicks to see <a href="https://github.com/richard-damon/FreeRTOScpp">his code on github</a>, it is clearly evident that he is heading in the same direction, as least for primitives.
6. For my personal use, &#8220;full complement&#8221; would mean adding shared-memory, but I realize that this is probably asking too much.

The UDP example is indeed very useful.  Mind you that the UDP library is now extended with many more protocols, like TCP, and it is now called <a href="https://freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/index.html">FreeRTOS+TCP</a>.
The principles are still the same: IP-task listens to a queue, and the messages (<code>IPStackEvent_t</code>) are simple and fixed-size.  They are treated in a first-in first-out order.
~~~
    /* Message type that is sent to the IP-task. */
    struct
    {
        eIPEvent_t eEventType;
        void *pvData;
    } IPStackEvent_t;
~~~
The task that handles the network interface (EMAC), works with two interrupts (RX/TX), and it is called &#8220;the EMAC deferred interrupt handler task&#8221;.  The ISR&#8217;s do a minimum: read and clear a status of the peripheral.  The high-priority task will be woken up (<code>vTaskNotifyGiveFromISR</code>), and take care of receiving and sending Ethernet data.
Recently, Richard wrote a good an interesting text about semaphores and task-notify <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/1e23c91fee/?limit=25#0d69">here</a>.  Don&#8217;t miss that.
When I have a complex task that works with many different objects ( queues, GPIO-status, TCP sockets, audio controllers, etc ), I will have it block in a simple call to <code>ulTaskNotifyTake()</code>.  All other tasks and drivers know the task handle, and they can ask for it&#8217;s immediate attention by calling either <code>xTaskNotifyGive()</code> or <code>vTaskNotifyGiveFromISR()</code>.

</div></div><div class="thread-post"><h3 class="thread-post-title">Blocking on Multiple RTOS Objects</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 25, 2019</div><div class="thread-post-content">While there is much similarity betseen an RTOS (especially a micro kernal like FreeRTOS) and a &#8216;Big OS&#8217;, there are also significant fundamental differences. A programmer who ignores these tends to write bad, if not broken code. One big difference is that with a &#8216;Big OS&#8217;, the OS has control of the machine, and parcels out access to the user programs, and those only have as much access as the OS gives them, and one of the key features is the OS is in control and is trying to protect one program from another. With an RTOS like FreeRTOS this is reversed. The program is in complete control over the machine, it owns it and controls it. The program gives the kernal usage of a few parts of it to get the services it needs. There is no fundamental concept of protecting the machine from the program.
One spot this distinction shows up is in the identities of the fundamental program units to each other. In FreeRTOS we have Tasks, that interact with each other through global variables and various syncronization primatives. For the &#8216;Big OS&#8217;, this is pretty much like the basic thread. But the Big OS adds to that Processes which are mostly isolated from each other, and these Processes are often grouped into Sessions, and these Sessions are well isolated from each other. People confusing these two sometimes ask how to kill a Task and clean up its resources, thinking of Processes, which FreeRTOS doesn&#8217;t have.
A second big spot where we see a difference is in I/O, in the Big OS, all I/O is provided by the OS and all communication needs to be done through well defined channels, it needs to be this way to protect differnet Processes and Sessions from each other. The OS needs to be in control. With FreeRTOS, it provides NO I/O, all I/O is provided by the user program, perhaps through standard library proceedures, but it is outside the kernel. This means there doesn&#8217;t need to be as uniform of an I/O interface, and the I/O drivers can be more customizable to the program needs.
If your larger application has built into it the concept that it is a unique Process from parts of the system, and that there are other parts running that are well isolated from it, then it may well NOT be suitable for conversion to something like FreeRTOS.

Or, if I use FreeRTOS to determine total available RAM at start-up, then the only porting issues, aside from the above, is  use of certain hardware-acceleration primitives (AES) that are different on the MCU&#8217;s and would have been necessary anyway.

<li>Wait on 1 <a href="https://docs.microsoft.com/en-us/windows/desktop/Sync/using-event-objects">Event</a>.</li>
<li>Wait on 3 Timers.</li>
</ul>
That is a total of 8 things to wait on simultaneously in an <a href="https://en.wikipedia.org/wiki/Event_loop">event loop</a>. 
Naturally, this begs the question: &#8220;Should a programmer even be doing that?&#8221;
I claim that the answer is &#8220;yes&#8221;.
The mental relief that an engineer experiences under an event-loop is greater than that under call-backs or whatever other mechanisms are employed, IMO. Once a programmer gets used to this model, it becomes easier than trying to get the the format specifiers right in <code>printf()</code>.
I do not believe that <strong>xWaitForAny</strong> wold be some whimsical nice-to-have that makes my job as a lazy programmer easier. I believe that it is fundamentally essential in the regular model for generalized multi-threading applications, in the same way that mutexes, themselves, are fundamental. I am saying that there is a reason that <a href="https://en.wikipedia.org/wiki/Dave_Cutler">Dave Cutler</a> and crew at Micosoft spent so much time crafting such a relative small number of OS functions (with huge salaries). I&#8217;m saying that <a href="https://en.wikipedia.org/wiki/Edsger_W._Dijkstra">Esdger Dijkstra</a>, original author of the mutex and pioneering thinker in the area of synchronization and distributed computing, in general, would probably bless <strong>xWaitForAny</strong> as not a nice-to-have, but &#8220;fundamentally regular&#8221;. Ironically, at the time <a href="https://en.wikipedia.org/wiki/Edsger_W._Dijkstra">Dijkstra</a>  proposed his mutex, he received considerable push-back from other leaders in computer science, because they felt that his concepts of multi-threading were ridiculous.
It often happens in engineering that some engineers will start insisting that certain things are fundamental, fiddling with them before they become widely accepted, while other engineers remain skeptical, because the extant model has been &#8220;good enough&#8221;. While the debate is ongoing, there will be a kind of &#8220;creeping&#8221; toward the truth. Eventually, it will be discovered that, indeed, the primitive is fundamental.  And then of course, 10 or 20 years later, we will all look back and think, &#8220;So..what  were we debating again?&#8221; For synchronization, this is happening, but is taking too long, IMO. 
Assuming that it is true that event loops are  fundamental primitives of generalized multi-threading engineering, which I admit is still under debate, one might ask, &#8220;Where is the creeping?&#8221; It is <a href="https://libevent.org/">libevent</a>. There is also <a href="https://en.wikipedia.org/wiki/Libuv">libuv</a>. One can see the stumbling that occurs while said creeping is ongoing. For example, <a href="https://idea.popcount.org/2017-02-20-epoll-is-fundamentally-broken-12/">there people who are agnry</a> with the design of the Linux equivalent of <strong>xWaitForAny</strong>, <a href="https://linux.die.net/man/4/epoll">epoll</a>. Their entire consternation can be traced back to a single design &#8220;flaw&#8221; which, unfortunately, is present in <a href="https://www.freertos.org/xQueueSelectFromSet.html">xQueueSelectFromSet()</a>:  The &#8220;flaw&#8221; is a counter-model to the following:
<em>If it is true that waiting for multiple objects simultaneously using a single function is a fundamental primitive in the realm of generalized synchronization, then that function must force the side-effect of the successfully-triggered object to occur before the function returns.</em>
Of course,  <a href="https://www.freertos.org/xQueueSelectFromSet.html">xQueueSelectFromSet()</a>, did not do this because it cannot, because not all elements in the queue can have their &#8220;side-effects&#8221; effected. This is true for <a href="https://linux.die.net/man/4/epoll">epoll</a> as well: Not all types of things that can be waited-on in <a href="https://linux.die.net/man/4/epoll">epoll</a> are amenable to being &#8220;side-effected&#8221;. This simple articulation of design choice has all kinds of ramifications for engineers trying to get their sychronization models right, hence the raging debate. For example, on Linux and FreeBSD, the number of waitable objecst can be on the order of 1000&#8217;s. The number of threads (Tasks) waiting can also be on the order of 10&#8217;s or 100&#8217;s. Then, when a waitable object (Semaphore/etc.) triggers, you&#8217;ll get 10&#8217;s or 100&#8217;s of threads suddenly coming awake, even though only one of them would have work to do, the so-called <a href="https://en.wikipedia.org/wiki/Thundering_herd_problem">thundering herd problem</a>. Not good.
You are right, however: one would need to be sensitive to the effect of grafting-on new primitives onto a kernel that many people are alredy happy with. There would be a minimal tolerance to the imposition of time and space of the new primitive on the kernel, and this cannot be taken lightly. This is why any attempt to add <strong>xWaitForAny</strong> / etc. would have to be done with a lot of discipline and understanding of context in which it would operate.

The key word  is &#8220;necessarily&#8221;. Given FreeRTOS&#8217;s architecture, it is no more &#8220;necessary&#8221; to regard it as a real-time OS than it is to regard, necessarily, a Ford F-350 Super Duty pick-up truck as a towing vehicle. Both, given their architectures, can be multi-purposed. 
The question then  becomes one of reasonableness:
Is it reasonable to take the wife and kids out on a date in a Ford F-350? Sure. No problem. Is that why Ford created the F-350? No. Is it reasonable to add side-steps to make it easier for the little ones to climb-up? Yes. Does that hurt the overall purpose of the vehicle if Ford were to add that side-steps to all F-350&#8217;s? No.
I do not see the &#8220;much harder to port to a smaller environment&#8221;. One might write the following code, then ask if it is portable:
<code>int x = 0;</code>
The answer had better be &#8220;yes&#8221;.
Then one might ask again for:
~~~
struct Foo
{
int x;
int y;
} ;
~~~
Again, the answer had better be yes.
One can play this game for the entirety of a codebase, where we eyeball each line of code, and ask ourselves, objectively, &#8220;Is this code truly portable?&#8221; If the code had been written with portability in mind from the outset, the answer will continue to be &#8220;yes&#8221;.
There will eventually come a point where the answer is not only &#8220;no&#8221;, but there is nothing that the programmer can do to make it portable, because the code under consideration is inherently non-portable. We then focus on those lines of code and ask:
* How much of this non-portable code is there in the entire application?
* What is its nature? I/O? Sychronization? IPC? Harware control? Machine identification?
In my case, the answers are, respectively:
* &lt;5%
*  synchronization
Sure, there are issues with C++ RTTI, exception handling, etc&#8230;but these are relatively trivial. <strong>xWaitForAny</strong> is not trivial, and cannot be circumvented in my model.
This gets us back to the sub-$10 MCU. The question becomes:
<em>Is there a market for a multi-tasking OS that can run Big Apps on a sub-$10 MCU.</em>
I claim that the answer is &#8220;yes&#8221;.
<em>Is there a multi-tasking OS that can run these Big Apps under a fully generalized multi-threading model on such an MCU?</em>
I claim that the answer is &#8220;no&#8221;.
<em>In light of what OS&#8217;s are available, does it make sense to write one from scratch?</em>
No.
<em>Why?</em>
Because FreeRTOS is already very close to what would be needed.
