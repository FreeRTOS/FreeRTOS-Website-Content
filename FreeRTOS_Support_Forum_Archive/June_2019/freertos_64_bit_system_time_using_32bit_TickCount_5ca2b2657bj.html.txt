  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">64 bit system time using 32bit TickCount</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jarni">jarni</a> on June 30, 2019</div><div class="thread-post-content">~~~
uint64<em>t GetSysTime64()
{
    static uint64</em>t systime = 0;
    static uint32<em>t maxticktime = 0;
    static uint32</em>t overflow = 0;
    uint32_t ticktime;
<pre><code>ticktime = xTaskGetTickCount();
if (ticktime &lt; maxticktime) overflow++;
maxticktime = ticktime;
systime = overflow;
systime &lt;&lt;= 32;
systime += ticktime;
return systime;
</code></pre>
}
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 30, 2019</div><div class="thread-post-content">&#8220;<code>systime</code>&#8221; doesn&#8217;t have to be static 🙂
If you do not call your function <code>GetSysTime64()</code> for a long time, you might miss an overflow.
With a 1000 Hz clock, the tick time overflows after 49 days, which is quiet a long time.
But mind you, there is a time tick hook, in which you can update your own tick counter:
~~~
<h1>if(  configUSE<em>TICK</em>HOOK != 0 )</h1>
<pre><code>volatile uint64_t tickCount64;
void vApplicationTickHook( void )
{
    tickCount64++;
}
</code></pre>
<h1>endif /* configUSE<em>TICK</em>HOOK */</h1>
~~~
The above code won&#8217;t miss a single clock tick
</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jarni">jarni</a> on June 30, 2019</div><div class="thread-post-content">I didn&#8217;t remember configUSE<em>TICK</em>HOOK&#8230;
Anyway you need a mutex to read/write tickCount64, or:
~~~
uint64<em>t GetTickCount64()
{
    uint64</em> tick;
    taskENTER<em>CRITICAL();
    tick = tickCount64;
    taskEXIT</em>CRITICAL();
    return tick;
}
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 30, 2019</div><div class="thread-post-content">In your example code, it would be more correct to use <code>TickType_t</code> in stead of <code>uint32_t</code>.
You&#8217;re right about the critical section, unless you have you&#8217;re on a 64-bit machine. And in that case, you wouldn&#8217;t need the extra code at all, because <code>xTaskGetTickCount()</code> will return a 64-bit count.
</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on June 30, 2019</div><div class="thread-post-content">Not sure what is trying to be achieved here, but the kernel code already

</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on June 30, 2019</div><div class="thread-post-content">One more addition about the atomical copy of <code>TickType_t</code>:
~~~
TickType<em>t xTaskGetTickCount( void )
{
TickType</em>t xTicks;
<pre><code>/* Critical section required if running on a 16 bit processor. */
portTICK_TYPE_ENTER_CRITICAL();
{
    xTicks = xTickCount;
}
portTICK_TYPE_EXIT_CRITICAL();
return xTicks;
</code></pre>
}
~~~
With the above code, a critical section will be entered only if needed.
</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jarni">jarni</a> on June 30, 2019</div><div class="thread-post-content">On 32bit systems reading/modifying TickType_t variables is atomic:
~~~
/* 32-bit tick type on a 32-bit architecture, so reads of the tick count do
not need to be guarded with a critical section. */
<h1>define portTICK<em>TYPE</em>IS_ATOMIC 1</h1>
<h1>endif</h1>
~~~
~~~
<h1>if (portTICK<em>TYPE</em>IS_ATOMIC == 0)</h1>
/* Either variables of tick type cannot be read atomically, or
portTICK<em>TYPE</em>IS_ATOMIC was not set &#8211; map the critical sections used when
the tick count is returned to the standard critical section macros. */
<h1>define portTICK<em>TYPE</em>ENTER<em>CRITICAL() portENTER</em>CRITICAL()</h1>
<h1>define portTICK<em>TYPE</em>EXIT<em>CRITICAL() portEXIT</em>CRITICAL()</h1>
<h1>define portTICK<em>TYPE</em>SET<em>INTERRUPT</em>MASK<em>FROM</em>ISR() portSET<em>INTERRUPT</em>MASK<em>FROM</em>ISR()</h1>
<h1>define portTICK<em>TYPE</em>CLEAR<em>INTERRUPT</em>MASK<em>FROM</em>ISR(x) portCLEAR<em>INTERRUPT</em>MASK<em>FROM</em>ISR((x))</h1>
<h1>else</h1>
/* The tick type can be read atomically, so critical sections used when the
tick count is returned can be defined away. */
<h1>define portTICK<em>TYPE</em>ENTER_CRITICAL()</h1>
<h1>define portTICK<em>TYPE</em>EXIT_CRITICAL()</h1>
<h1>define portTICK<em>TYPE</em>SET<em>INTERRUPT</em>MASK<em>FROM</em>ISR() 0</h1>
<h1>define portTICK<em>TYPE</em>CLEAR<em>INTERRUPT</em>MASK<em>FROM</em>ISR(x) (void)x</h1>
<h1>endif</h1>
~~~

</div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 30, 2019</div><div class="thread-post-content">FreeRTOS already keeps track of the number of times the tick has overflowed in xNumOfOverflows, and the vTaskSetTimeOutState function will fetch the current tick count and the current overflow state, so the data is already available. </div></div><div class="thread-post"><h3 class="thread-post-title">64 bit system time using 32bit TickCount</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 30, 2019</div><div class="thread-post-content">But the values returned by it can easily be converted into the 64 bit value you want. The xNumOfOverflows is exactly what you overflow counter is, and kept by FreeRTOS in a way to prevent races.
Your function has the issue that it isn&#8217;t thread safe, and has a data race (If the first task that is calling it gets preempted after detecting the roll over but before resetting the maxTickTime, or after getting the current tick count and before testing against maxTickCount, and a tick increment occurs before some preempting task calls the function.
