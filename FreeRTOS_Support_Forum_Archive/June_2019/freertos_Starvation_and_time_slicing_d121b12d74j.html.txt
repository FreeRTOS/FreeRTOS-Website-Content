</div></div><div class="thread-post"><h3 class="thread-post-title">Starvation and time slicing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 2, 2019</div><div class="thread-post-content">One big question, how does your &#8216;printf&#8217; function work. If it is based on &#8216;Semihosting&#8217;, then often it will interfere with how FreeRTOS wants to work.
The second question, do you have Preemtion enabled? If not then unless printf was is using an output designed for an RTOS, and has a block in it, once you get into one of the continous task, you have no &#8216;yield&#8217; point, and thus never allow the system to swtich tasks.
Last, you many need to make sure your printf is reentrant and usable in an RTOS enviornment, sometimes library functions aren&#8217;t.
</div></div><div class="thread-post"><h3 class="thread-post-title">Starvation and time slicing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/akimata">akimata</a> on June 2, 2019</div><div class="thread-post-content">Yeah printf is based on semihosting and seems like it&#8217;s blocking the execution or somehow is not reentrant. UART printf it&#8217;s working as intended.
</div></div><div class="thread-post"><h3 class="thread-post-title">Starvation and time slicing</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on June 2, 2019</div><div class="thread-post-content">Semihosting often doesn&#8217;t block but will spin in a tight idle loop, perhaps with interrupts being blocks.
If the UART driver has the proper blocking, that would allow the switching.
I would still double check that you have preemption enabled, as that still might be part of the issue, which has now been hidden by the fact that the tasks continully are blocking, providing context change points. If you change the continous tasks to do some other long running operation that doesn&#8217;t need blocking, you may find that you get the starving again without preemption.
Turning off preemption makes things &#8216;tactically&#8217; simpler, as you don&#8217;t need to worry about as many inter-task sharing concerns due to the limited context switch points. It does make things significantly more complicated in a &#8216;stratigic&#8217; sense, as now every task, even low prioirty ones, need to make allowance for the highest priority response time by frequently providing context switch points.
