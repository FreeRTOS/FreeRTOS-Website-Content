</div></div><div class="thread-post"><h3 class="thread-post-title">STM32 Interrupt Priorites</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 20, 2012</div><div class="thread-post-content">History, and the weird way the Cortex-M defines interrupts.  
The Cortex-M has eight priority bits, but different implementations use a different number of bits.&nbsp; Two things make this more confusing &#8211; first it is the most significant bits that are implemented and second high numeric values denote low logical priorities.  
Go right back to the beginning of the Cortex-M.&nbsp; To define an interrupt priority you had to use all eight bits, and shift the values into the correct position &#40;most significant bits&#41;.&nbsp; Bits that are not use are normally set as 1 rather than 0 for &#8220;future proofing&#8221;.  
The next step &#8211; libraries start appearing for the Cortex-M early adopters.&nbsp; These libraries want the priority specified as the raw value, that is the 8 bit shifted value.  
The next step &#8211; other libraries appear that want the priority defined as an eight bit value, but &#42;not&#42; shifted.&nbsp; Now you have three ways of defining priorities.  
Finally CMSIS appears.&nbsp; This wants priorities defined using just the implemented number of bits and not shifted.  
Therefore, the newer demos have more ways of defining the priorities than the older ports.  
configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY and configLIBRARY&#95;LOWEST&#95;INTERRUPT&#95;PRIORITY should always be equivalent, but the former is defined as if you are writing raw values to the Cortex-M3 NVIC registers and the latter is defined as if you are passing the value to a CMSIS &#40;or propitiatory&#41; library function that does the shifting for you.  
Confused.&nbsp; You should be.&nbsp; Stand on your head and half close your eyes, then Cortex-M interrupt priorities make sense.  
Regards.
