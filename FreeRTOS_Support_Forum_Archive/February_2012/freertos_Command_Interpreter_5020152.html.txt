  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Command Interpreter</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mdkendall">mdkendall</a> on February 15, 2012</div><div class="thread-post-content">I was very pleased recently to discover the Command Interpreter in Demo/Common/Utils. One often has to add some sort of command interface to products and having a standard framework to build from is a big time saver. I like the architecture of this one; it seems well thought-out.  
Having used it I have a couple of suggestions and comments:  
First, the semantics of the return value of xCmdIntProcessCommand surprised me. I was expecting the value to indicate &#8220;I did something&#8221; or &#8220;I did nothing&#8221;, so one would use it thus:  
<pre><code>while (xCmdIntProcessCommand(line, buf, size)) {
    printf(pcCmdIntGetOutputBuffer());
}
</code></pre>
Instead, the return value indicates whether there is anything further to do, hence:  
<pre><code>do {
    more = xCmdIntProcessCommand(line, buf, size);
    printf(pcCmdIntGetOutputBuffer());
} while (more);
</code></pre>
which seems less elegant.  
Second, the pcCmdIntGetParameter&#40;&#41; function is handy but I was surprised to see that when requesting parameter N I actually get a string that extends from the beginning of the Nth parameter all the way to the end of the line. I see that the pxParameterStringLength will tell me how many characters actually constitute the parameter. Interpreters I have used previously have had the tokeniser replace the delimiting characters in the command string with nulls, cutting the string in to chunks, so that when later fetching a particular parameter one gets a sub-string containing just that particular parameter. That seems a little more convenient.  
Lastly, and somewhat trivially, the long, mixed-case filename CommandInterpreter.c does not really match the style of the other FreeRTOS filenames. Can I suggest cmdint.c &#40;since CmdInt seems to be used as the &#8220;module prefix&#8221; for functions&#41;?  
Anyway, overall I&#8217;m very happy. Thanks for making this available.
</div></div><div class="thread-post"><h3 class="thread-post-title">Command Interpreter</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 15, 2012</div><div class="thread-post-content">The command interpreter is hiding in the code, but not yet formally announced or documented &#40;other than a news snippet to say it is there&#41;.&nbsp; It will be formally announced in a couple of weeks &#8211; and at the same time separated out of its current location to a separate download.&nbsp; It is now fully documented and has some example applications, and these will appear on the web site at the same time.  
Thanks for your feedback points:  
&#43; I can see the semantics may seem odd, to me they were ok and it didn&#8217;t occur to me until you pointed it out.&nbsp; The idea is that you keep calling the function until there is nothing left to do &#8211; the concept being to minimise RAM usage &#8211; and the semantics work from that perspective.&nbsp; I will consider that.  
&#43; The behaviour you are seeing for pcCmdIntGetParameter&#40;&#41; is not what it should do, and not behaviour I have ever seen myself.&nbsp; The string should be tokenised in exactly the way you are saying.&nbsp; That relies on the string being in writable memory though, were you passing the string in RAM?  
&#43; The file name has changed for the V1 release &#40;the one in a couple of weeks&#41;, as have the names of the functions it defines.&nbsp; They are documented now.&nbsp; They won&#8217;t change again after the formal release though.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Command Interpreter</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mdkendall">mdkendall</a> on February 15, 2012</div><div class="thread-post-content">I am definitely seeing the behaviour I described for pcCmdIntGetParameter&#40;&#41;. I register a command &#8220;foo&#8221; with 2 parameters. On the command line I enter &#8220;foo bar baz&#8221;. The callback gets called. Within it I have p = pcCmdIntGetParameter&#40;pcCommandString, 1, &amp;len&#41; and the result is that p is a pointer in to the original string, starting at the first &#8216;b&#8217;, i.e. &#42;p is &#8220;bar baz &#8221;. The space between the first and second params has not been replaced with a null. I see no code in xCmdIntProcessCommand&#40;&#41; or pcCmdIntGetParameter&#40;&#41; that would make such a substitution.  
I am using the version of CommandInterpreter.c from the 7.10 distribution. Perhaps there has been a change since then?
</div></div><div class="thread-post"><h3 class="thread-post-title">Command Interpreter</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 15, 2012</div><div class="thread-post-content">My apologies.&nbsp; It used to be done that the command was terminated, but to prevent the command string being altered as a side effect of calling the API function the API function was changed to instead return the length of the parameter string.&nbsp; You are quite correct.  
I just checked one of the demos and it looks like this:  
<pre><code>    /* Obtain the name of the first parameter, and the length of its name. */
    pcParameter1 = ( int8_t * ) FreeRTOS_CLIGetParameter( pcCommandString, uxFirstParameter, &amp;xParameter1StringLength );
    /* Terminate parameter string. */
    pcParameter1[ xParameter1StringLength ] = 0x00;
</code></pre>
This means the application terminates the string if it wants to, which was considered safer.  
Sorry for the confusion.  
Regards.
