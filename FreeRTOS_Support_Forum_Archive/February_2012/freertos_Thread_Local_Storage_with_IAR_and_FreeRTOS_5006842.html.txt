  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gregd29">gregd29</a> on February 8, 2012</div><div class="thread-post-content">I am using FreeRTOS on the LPC4350 using the IAR compiler.&nbsp; I am trying to decide the best way to handle thread local variables.&nbsp; I am going to be processing the same communications protocol over several serial ports, USB &amp; Ethernet.&nbsp; Each one of the communication tasks will require the same set of control variables to remember it&#8217;s &#8220;state&#8221;.&nbsp; Each task should have a separate instance of each thread local variable.&nbsp; What is the best way to handle this requirement?&nbsp; I see some of the thread local support is provided, or at least stubbed out in IAR.&nbsp; Is it recommended to integrate with IAR or roll your own?&nbsp; I don&#8217;t see where FreeRTOS has any built in support for thread local storage.&nbsp; Are there any examples available which integrate FreeRTOS with IARs TLS framework?
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 8, 2012</div><div class="thread-post-content">I don&#8217;t know what the IAR system does, but FreeRTOS does not attempt to provide any special mechanism for doing this.  
If the protocol is controlled in a task, can you have the state information as a stack variable in the task?&nbsp; You would have to make the stack big enough of course, but that would give each task its own copy very easily.&nbsp; If there is too much data, then have the task declare a pointer to the data on its stack, and then set the pointer to a block of RAM malloced by the task when the task starts to run.&nbsp; The result will be the same, but the RAM will be from the heap, not on the stack.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 8, 2012</div><div class="thread-post-content">As Richard said, FreeRTOS doesn&#8217;t provide Thread Local Storage which looks like globals, but have a unique value for each thread. Typically this is implemented with some global &#8220;variable&#8221; which is changed to point to a different block of memory for each task &#40;effectively a struct&#41;. You could add a field to the TCB storing this pointer, allocate a new block of memory of the size indicated by the compiler/linker for TLS in task create, and have the schedule change the appropriate variable on a task switch. Note that EVERY task will get the same set of TLS variables, so this doesn&#8217;t really work well for things lie communications protocol state, as it means that EVERY task will get allocated these variables.  
If you don&#8217;t need the &#8220;global&#8221; nature of TLS, then each task naturally has its own stack variables&nbsp; as Richard pointed out that can be either used directly or to store a pointer to an allocation if you need bigger buffers. Another option that can be used in part is to pass the task a pointer to a control block, and create several tasks using the exact same task function. I commonly do this if I have a unit with multiple serial ports that, at least at the task level, are treated similarly. This same pointer can be passed to any functions that need similar information about the serial port.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/gregd29">gregd29</a> on February 8, 2012</div><div class="thread-post-content">Yes, I have thought about doing just what you said.&nbsp; The only problem is getting access to the pointer on the data stack from all of the subroutine functions that are called from the main task function.&nbsp; You would have to pass the pointer to each subroutine, taking up additional stack area.&nbsp; With complicated tasks this can be many levels deep.&nbsp; The code becomes much more wordy when you have to include the pointer in each reference also.&nbsp; The IAR compiler has support for TLS &#40;thread local storage&#41; which the user has to implement the interface for.&nbsp; You basically place all of the thread local variables in a specific section &#40;&#95;&#95;DLIB&#95;PERTHREAD&#41; and then allocate a separate storage area for each thread.&nbsp; The context switch updates a pointer to the beginning of the thread local storage area.&nbsp; I believe that the IAR compiler will then call special handling routines when these variables are accessed.&nbsp; These handler routines are what has to be implemented by the user for the particular RTOS.&nbsp; If you search for Multithreaded in the IAR C/C++ Development Guide you will see a how section in the manual that describes the support.&nbsp; Anyway, this may be something worth looking into in the future.&nbsp; It seems like this would be a very valuable feature to support in an RTOS.&nbsp; It helps to make the task functionality much easier to write when you have multiple instances of the same task like with this communications example.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 8, 2012</div><div class="thread-post-content">From richard&#95;damon:  
<blockquote>
  Typically this is implemented with some global &#8220;variable&#8221; which is changed to point to a different block of memory for each task &#40;effectively a struct&#41;. 
</blockquote>
There is floating about somewhere a copy of FreeRTOS that was adapted in just this way for integration with NewLib, which has a pointer to structures, the name of which that escapes me, to hold thread local variables.  
<blockquote>
  The only problem is getting access to the pointer on the data stack from all of the subroutine functions that are called from the main task function.
</blockquote>
Set configUSE&#95;APPLICATION&#95;TASK&#95;TAG to 1, then use the pxTaskTag member of the task&#8217;s TCB.&nbsp; Look at the vTaskSetApplicationTaskTag&#40;&#41; and xTaskGetApplicationTaskTag&#40;&#41; functions.&nbsp; xTaskGetApplicationTaskTag&#40;&#41; lets you obtain a value from the TCB, from any function, so long as that task is running.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rwt33">rwt33</a> on February 8, 2012</div><div class="thread-post-content">I feel there are times where it&#8217;s appropriate to add thread-local storage variables, but in general I would &#95;only&#95; do this for lib-function variables, such as errno.<br />
Like the others have said, for general &#8220;state&#8221; values then stack variables are your best bet. After all, that&#8217;s what the stack is for&#33;

</div></div><div class="thread-post"><h3 class="thread-post-title">Thread Local Storage with IAR and FreeRTOS</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 8, 2012</div><div class="thread-post-content">Richard,<br />
It sounds like with the TASK TAG implantation, it would be possible to implement TLS by also defining a few of the trace hooks to set the TLS pointer as the TASK TAG when a task is created, and to switch the current TLS pointer to the current TASK TAG on a task switch.  
Gregd,<br />
I will say that I find adding sending the pointer on function calls to not be that intrusive. Using TLS for these variables mean that EVER task will get them, so that not only do your serial tasks have the serial variables, but also every other task. This can add up to a lot more of a loss than the few bits to pass the pointer to structure down the call chain.  
If you are writing C++ code, then it even makes sense to make these member functions of some protocol class that your task class is derived from and the passing is automatic.  
If you are writing C code, then passing a pointer to a device descriptor structure seems natural for an implementation that is expecting to have multiple similar devices to specify which device we are working on here. Think of it like the FILE&#42; parameter on all the file I/O functions. It would be a bit unusual to think of a fwrite function that used globals for per file information. Sometimes even seeing up this structure allows you to make some code more common, and use information in the structure to customize special cases out of the main code. To just use a global for the state hides the multiple instances and makes it to easy in my mind to get sloppy. Remember, you need to worry about access contention for &#8220;real&#8221; global variables, the these &#8220;pseudo&#8221; globals via TLS don&#8217;t need to worry &#40;normally&#41;, when you start to get used to accessing &#8220;globle&#8221; variables &#40;that are really TLS&#41; you might forget that something ISN&#8217;T TLS, and forget about access synchronization.
