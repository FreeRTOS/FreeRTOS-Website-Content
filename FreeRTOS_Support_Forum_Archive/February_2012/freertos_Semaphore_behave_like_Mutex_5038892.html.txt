</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore behave like Mutex?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 16, 2012</div><div class="thread-post-content">You can see the vSemphoreCreateBinary&#40;&#41; code in semphr.h.  
Mutexes are created to contain the mutex, so the first call to take the mutex succeeds, which is what you want when the presense of a mutex indicates the the resource it is protecting is available.  
Binary semaphores are create so the semphore is not available, so the first call to tkae <strong>fails</strong>. This means the task that creates the semaphore can immediately then block on the seamphore to wait for an event. If the semaphore is used to signal an event, then the event will not have happened when the semaphore is created.

</div></div><div class="thread-post"><h3 class="thread-post-title">Semaphore behave like Mutex?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on February 16, 2012</div><div class="thread-post-content">I don&#8217;t think there is a right or wrong way of doing it.&nbsp; Some applications want it created &#8220;empty&#8221; and others want it created &#8220;full&#8221;.&nbsp; It cannot be both.  
If you want it to be created empty then call create the semaphore, then immediately take it.&nbsp; You can take it with a block time of 0 as you know the semaphore will be there &#8211; it was just created.&nbsp; In that case, the code manually sets it to the state it wants it to be in.&nbsp; In the other case, where the code wants it to be available on creation, it does not have to manually do anything, just create it.  
Regards.
