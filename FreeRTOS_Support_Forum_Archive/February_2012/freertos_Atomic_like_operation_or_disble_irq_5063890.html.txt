  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Atomic like operation (or disble irq)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tjohansen">tjohansen</a> on February 24, 2012</div><div class="thread-post-content">Hi forum  
In my case, I have the classic example of task updating variables, that are used in a different task,<br />
I know the variable update is &#8220;atomic&#8221; if the variable can be updated in one instruction. &#40;8, 16 or 32 bit&#41;  
But in my system I do have 16 bit SDRAM interface, so updating a 32 bit variable, would require more then one instruction.<br />
Or am I wrong about that??  
I could, of course use the macros portENTER&#95;CRITICAL and&nbsp; portEXIT&#95;CRITICAL. I would like to avoid this because the variables are written and read often.  
When doing the the write and read operation on them I could also disable interrupts. But is that allowed by FreeRTOS? Wouldn&#8217;t that make the scheduler run unexpected?  
Thomas
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomic like operation (or disble irq)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davidbrown">davidbrown</a> on February 24, 2012</div><div class="thread-post-content">If your cpu is capable of reading and writing 32-bit at a time, then such accesses are atomic &#8211; regardless of the width of the memory &#40;unless you have multiple bus masters, and a DRAM controller that splits up such accesses, but that&#8217;s highly unlikely&#41;.  
Remember, of course, that only each read or write of each variable is atomic &#8211; read/modify/write operations are not atomic on most cpus &#40;though they /are/ atomic on some CISC cpus&#41;, and there is no guarantee of atomicity when accessing multiple variables.  
Look at the generated assembly code for the source code in question &#8211; then you can easily see what instructions are used.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomic like operation (or disble irq)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tjohansen">tjohansen</a> on February 24, 2012</div><div class="thread-post-content">Hi  
My CPU is 32 bit. Its a ARM Cortex M3,  
I could look at the ASM code generated. But if the used instruction doesn&#8217;t make the operation atomic?  
Also, If need to write variable &gt;32 bit &#40;Could be strings or structs, than I need to do something atomic.  
So is using portENTER&#95;CRITICAL and&nbsp; portEXIT&#95;CRITICAL the only way in FreeRTOS  
Im using the LPC1788 CPU  
Thomas
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomic like operation (or disble irq)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 24, 2012</div><div class="thread-post-content">If the task is updated in one task, and only used &#40;read, not written&#41; in the other task, then you don&#8217;t need any mutual exclusion provided the width of the variable is equal to the natural word size of the CPU. In this case the word size is 32 bits, so if your variable is 32 bits then you should be ok without anything.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomic like operation (or disble irq)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on February 24, 2012</div><div class="thread-post-content">Oops. Meant if the **variable ** is updated in one task.
</div></div><div class="thread-post"><h3 class="thread-post-title">Atomic like operation (or disble irq)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 24, 2012</div><div class="thread-post-content">As it has been said, bus cycle atomisity isn&#8217;t needed if you have instruction level atomisity unless you have something else that might access the memory &#40;like a multiprocessor system&#41;.  
If you have a 32 bit processor, and the memory signals that it is only 16 bits wide, it is quite possible that the processor will do the access atomically.  
portENTER/EXIT&#95;CRITICAL is the normal way of doing this and is fairly light weight, but if you need to be even faster you could use an interrupt disable/enable pair &#40;which is similar to what what the CRITICAL macros use&#41; if:  
1&#41;&nbsp; You know you are not inside a CRITICAL section, or you know that your method is not incompatible with nesting with the CRITICAL section macros &#40;they try to only mask interrupt that might interact with FreeRTOS so there MAY be another way to disable interrupts that can nest with the CRITICAL section macros&#41;  
2&#41; You disable interrupt time is short enough that you are not going to unacceptably impact interrupts that the critical section macros leave enabled.  
Disabling/Enabling the interrupts will not impact the tick interrupt/scheduler any more than the critical section macros will. The impact that is there is the reason you need to keep critical sections short.
