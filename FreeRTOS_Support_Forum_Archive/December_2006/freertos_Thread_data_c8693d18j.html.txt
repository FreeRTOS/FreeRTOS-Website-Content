</div></div><div class="thread-post"><h3 class="thread-post-title">Thread data</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on December 23, 2006</div><div class="thread-post-content">Generally, this would allow threads to have thread specific data that is accessible from service functions that are called from multiple threads. One use would be to make the task pvParameters usable by functions called by the task. When a task starts up, it it could set that pvParameters as it&#8217;s task data pointer. In fact, that might be an interesting &#8216;default&#8217; value for the task data pointer rather than NULL.
In my specific case, I have an C++ object oriented layer above FreeRTOS. There is an object for each thread/task. I would set the task data pointer to locate the object. That way, member functions of the &#8216;thread object&#8217; could be called from service functions that otherwise would have no way to find the thread object from the task handle.
Originally I maintained a lookup table that associated task handles with thread objects. A bit complex and costly to access the object.
Later I bacame braver and modified the context save/restore routines to push/pop the thread object pointer from/to a global variable. I pass the thread object pointer in to the task as pvParameters, and initialize the global variable with it. Then, from within service functions I get at the thread object via the global. This works well, but I think it is a bit heavy to burden each context switch with this cost when most &#8216;runs of a thread&#8217; &#40;context switch in to context switch out&#41; will not even use the global. In fact, timewise it may be more costly than the table lookup&#33;
Hence my request. This is not an original idea. It is a feature of other RTOS&#8217;s I have seen, although I couldn&#8217;t name one off the top of my head.
I don&#8217;t think there is a mutex problem because only the thread itself will access the pointer and its referenced data structure. In fact, I would ask that this restriction be enforced &#40;i.e., the accessor functions not take a task handle parameter&#41;. However, I was concerned about things like this and that is why I raised the issue in the forum rather than just do it myself. I thought your &#40;and others&#41; experience might save me from myself.
So I think it is trivial, but I am not sure&#8230; add &#40;but using the Hungarian naming convention&#41;:
&nbsp;&nbsp; void &#42; taskData;
to the TCB with accessor functions
void setTaskData&#40;void &#42; ptr&#41;
&#123;
&nbsp;&nbsp; &#8216;set tcb to locate the current TCB&#8217;
&nbsp;&nbsp; tcb-&gt;taskData = ptr;
&#125;
void &#42; getTaskData&#40;void&#41;
&#123;
&nbsp;&nbsp; &#8216;set tcb to locate the current TCB&#8217;
&nbsp;&nbsp; return tcb-&gt;taskData;
&#125;
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread data</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on December 23, 2006</div><div class="thread-post-content">An interesting idea.&nbsp; I&#8217;m not there would be enough call for the feature to include it in the standard TCB structure.&nbsp; There is actually a member of the TCB that is not used directly by the scheduler already &#8211; the uxTCBNumber member.&nbsp; This is only used to hold a number to facilitate debugging when printing out the task states.&nbsp; A bit ugly perhaps, but maybe this could have a dual purpose?
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Thread data</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on December 23, 2006</div><div class="thread-post-content">Yes, I had noticed uxTCBNumber and thought of using it when I was considering just implementing it myself. But really, I don&#8217;t think 4 bytes per TCB is all that much.
Do you see this as safe enough go ahead and do? Maybe I should just write the accessor functions and try it out, using uxTCBNumber. I could let you know how it works out, and if OK you could decide whether or not you want to include it.
I assume that after you set uxTCBNumber you never change it. Correct?

Seems to work fine. This requires that &#8216;unsigned portBASE&#95;TYPE&#8217; be safely convertible back and forth to &#8216;void &#42;&#8217; in the particular FreeRTOS port you are using. It is probably safer to at a new &#8216;void &#42;&#8217; field to the TCB structure.

void &#42; GetTaskData&#40;void&#41;
&#123;
&nbsp;&nbsp;&nbsp; tskTCB &#42;&nbsp;&nbsp;&nbsp; tcb = xTaskGetCurrentTaskHandle&#40;&#41;;

</div></div><div class="thread-post"><h3 class="thread-post-title">Thread data</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/imajeff">imajeff</a> on December 26, 2006</div><div class="thread-post-content">I agree that there&#8217;s no reason to change anything in FreeRTOS, and I would not like to increase overhead for the feature. There are many possibilities already.
I don&#8217;t think &#8216;unsigned portBASE&#95;TYPE&#8217; would easily cast to pointer in many small systems. I guess it could be a global array of pointers, using this value to index to this task.
Better Idea:
The pvParameters could pass an environment allocated for a particular task if it needs to already exist. Of course that is not saved in the TCB, so I could save the pointer at &#8216;&#42;pxStack&#8217; because that would not be written until the stack is full &#40;if portSTACK&#95;GROWTH &lt; 0&#41;. Now thinking more, I wouldn&#8217;t need point to it. I&#8217;d just have the data space be the region unused by stack. Increasing &#8216;usStackDepth&#8217; gives me more space for the task data block.
I think this would allow for any target to work, especially if Richard will write something into the docs to guarantee what we can expect in a portable way.
