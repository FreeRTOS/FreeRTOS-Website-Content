  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Generic ISR dispatch routine</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on December 24, 2006</div><div class="thread-post-content">In order to have a single generic ISR dispatch routine, I have added a function to tasks.c that returns the priority of the highest priority ready task.
unsigned portBASE&#95;TYPE TopPriority&#40;void&#41;
&#123;
&nbsp;&nbsp;&nbsp; return uxTopReadyPriority;
&#125;
My generic dispatch routine captures this priority before dispatching to the proper ISR. When the ISR returns, it tests whether the highest priority has changed. If so, it calls for a context switch, else it doesn&#8217;t.
void PortIRQDispatch&#40;void&#41;
&#123;
&nbsp;&nbsp;&nbsp; portENTER&#95;SWITCHING&#95;ISR&#40;&#41;;
&nbsp;&nbsp;&nbsp; 
&nbsp;&nbsp;&nbsp; unsigned&nbsp;&nbsp;&nbsp; portBASE&#95;TYPE prevTopPriority = TopPriority&#40;&#41;;
&nbsp;&nbsp;&nbsp; ISRDispatch&#40;&#41;;
&nbsp;&nbsp;&nbsp; portEXIT&#95;SWITCHING&#95;ISR&#40;prevTopPriority&lt;TopPriority&#40;&#41;&#41;;
&#125;
I wonder if anyone has any comments on issues/problems this may raise.
One point is that this subverts time slicing between tasks of equal priority. Using &lt;= rather than &lt; in the final test would be similar to time slicing, although not quite the same. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Generic ISR dispatch routine</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on December 24, 2006</div><div class="thread-post-content">I&#8217;m not sure I follow the object of this code, what you are trying to achieve?&nbsp; 
If you want to only cause a switch to another task when there is a task of higher priority than the running task then you could add the code to vTaskSwitchContext in tasks.c to only execute the while loop if the top ready priority is greater than the running priority.
If this is just to have commonality in your IRQs and to prevent the application writer having to use the ENTER/EXIT macros then I think the code is good.&nbsp; You of coarse have a few little expenses in an extra layer of indirection.&nbsp; Also you are going to save and restore the context even when the task does not need it saved and restored.&nbsp; Each IRQ in the system will save the context.
Different ports handle this in different ways.&nbsp; Some only save the context when a switch is actually required which is really nice as this is the most optimal.&nbsp; From the macros you quote I assume you are using the ARM port.&nbsp; This itself uses two different techniques.&nbsp; Looking at the STR750 &#40;and I think the ARM9&#41; ports you will see that there is an IRQ wrapper&nbsp; written in assembler that saves the context before calling the IRQ C function, then restores it again prior to exiting the ASM wrapper &#40;on completion of the interrupt&#41;.&nbsp; The portEND&#95;SWITCHING&#95;ISR macro then becomes a simple call to vTaskSwitchContext&#40;&#41; if a switch is required.&nbsp; Take a look at the port page for STR750/RIDE at the section &quot;Interrupt service routines&quot;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Generic ISR dispatch routine</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on December 24, 2006</div><div class="thread-post-content">I am using an LPC2xxx. The VIC priority vectored interrupts and the FIQ interrupt are handled separately and each in there own way. In my case, they all operate outside the realm of FreeRTOS, never triggering context switches.
My PortIRQDispatch&#40;&#41; is the common routine entered off of the VIC default IRQ. All of these have to go through such a common handler. So it can perform operations common to all of the default vector ISRs. I was looking for a common way of determining if a context switch was required on exiting the ISR.
I really don&#8217;t like to tamper with FreeRTOS, so I look for ways to work with it with as few changes as possible. My TopPriority&#40;&#41; function added into tasks.c seemed like a pretty inocuous change that gave me what I wanted. But I wonder if others might have tried a similar stunt and run into some subtle &#8216;gotcha&#8217;.
In this particular case, I&#8217;m not sure tampering vTaskSwitchContext&#40;&#41; would be a good thing to do. I think it would mean that taskYIELD&#40;&#41; wouldn&#8217;t perform as expected.
Thanks for the feedback.
