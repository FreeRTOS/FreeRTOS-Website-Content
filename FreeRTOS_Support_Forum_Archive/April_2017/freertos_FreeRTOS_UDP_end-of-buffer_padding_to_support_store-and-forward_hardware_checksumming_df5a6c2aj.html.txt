</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+UDP end-of-buffer padding to support store-and-forward hardware checksumming</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 23, 2017</div><div class="thread-post-content">Hi Sasha,
<blockquote>
  I&#8217;m writing a from-scratch STM32F7 zero-copy Ethernet driver for FreeRTOS+UDP 9.0.0.

Congratulations !
Do you really mean +UDP, or +TCP?
FreeRTOS+TCP started in the <a href="http://www.freertos.org/FreeRTOS-Labs/index.shtml">/Labs section</a>. It is the successor of +UDP. It is more complete, and more often used. If you want to use it UDP-only, that is still possible:
~~~
    #define ipconfigUSE_TCP    0
~~~
Moving from +UDP to +TCP shouldn&#8217;t be hard. The principles are all the same.
The drivers for both releases are 99% the same. FreeRTOS+TCP has an extra parameter when calling <code>xNetworkInterfaceOutput()</code>:
~~~
    BaseType<em>t xNetworkInterfaceOutput( NetworkBufferDescriptor</em>t * const pxDescriptor, BaseType_t bReleaseAfterSend );
~~~
When <code>bReleaseAfterSend</code> is true, the driver ( <code>NetworkInterface</code> ) is responsible for releasing <code>pxDescriptor</code>. When you have zero-copy transmissions:
~~~
    #define ipconfigZERO<em>COPY</em>TX_DRIVER    1
~~~
&#8230; then <code>bReleaseAfterSend</code> will always be true, so it is safe to pass the memory to a DMA descriptor. Once the transfer is ready, the original Network Buffer must be released.
I like to work with a counting semaphore that keeps track of the number of available DMA descriptors for transmission (<code>TX</code>).
In the current STM32F4 driver, it looks like this:
~~~
    /* As soon as the EMAC has sent a frame, the original Network Buffer must be released. */
    ucPayLoad = ( uint8_t * )DMATxDescToClear->Buffer1Addr;
<pre><code>/* Look-up the Network buffer that owns a certain payload. */
pxNetworkBuffer = pxPacketBuffer_to_NetworkBuffer( ucPayLoad );
/* Release the Network buffer. */
vReleaseNetworkBufferAndDescriptor( pxNetworkBuffer ) ;
/* Mark that it has been released already, just to be sure. */
DMATxDescToClear-&gt;Buffer1Addr = ( uint32_t )0u;
/* Tell the counting semaphore that one more TX descriptor is available. */
xSemaphoreGive( xTXDescriptorSemaphore );
</code></pre>
~~~
<blockquote>
  for ICMP-over-IPv4 packets, the checksum field in the ICMP packet must always be 0x0000 in both modes
</blockquote>
I also encountered this &#8216;feature&#8217; on STM32F4&#8217;s EMAC :
~~~
    if( pxPacket->xICMPPacket.xIPHeader.ucProtocol == ipPROTOCOL<em>ICMP )
    {
        pxPacket->xICMPPacket.xICMPHeader.usChecksum = ( uint16</em>t )0u;
    }
~~~
Just to summarise, for IPv4, the following check-sums exist:
1) IP-header has a checksum over a so-called pseudo header (16-bits)
2) Protocol-checksum (16-bits)
3) A 4-byte Frame Check Sequence (FCS) that we do not get to see in the library.
Checksums 1) and 2) can either be set and checked by the EMAC, or by the library.
The last checksum can only be added by the EMAC.
Now when a packet has 100 bytes, we send 100 bytes to the EMAC, and the EMAC will secretly add 4-byte frame-check.
But there is a minimum frame length of 60 + 4 bytes. That is needed for a proper collision detection on the LAN.
In FreeRTOS+TCP, you can define the following:
~~~
    #define ipconfigETHERNET<em>MINIMUM</em>PACKET_BYTES        ( 60 )
~~~
ARP and ICMP messages can be as short as 42 bytes. The 18 extra bytes will be set to zero. So 60 bytes will be sent to the EMAC.
<blockquote>
  But it doesn&#8217;t appear like FreeRTOS+UDP provides four unused bytes at the end of an Ethernet buffer.
</blockquote>
True because the EMAC adds 4 bytes on its own.
<blockquote>
  In order to get the checksum to be automatically inserted,
  I must tell the DMA peripheral that the frame is four bytes
  bigger than what FreeRTOS+UDP suggests
</blockquote>
That is new for me, I haven&#8217;t encountered that yet. But I haven&#8217;t used an STM32F7 either.
<blockquote>
  Have I missed something about the buffer allocation size that makes this OK?
</blockquote>
FreeRTOS+TCP will guarantee that all network buffers have a minimum size of <code>ipconfigETHERNET_MINIMUM_PACKET_BYTES</code>. That is particularly important when using <code>BufferAllocation_2.c</code>, which allocates just enough bytes for <code>pucEthernetBuffer</code>.
~~~
/* Adding pad bytes. */
<h1>if defined( ipconfigETHERNET<em>MINIMUM</em>PACKET_BYTES )</h1>
{
    if( pxNetworkBuffer->xDataLength &lt; ( size<em>t ) ipconfigETHERNET</em>MINIMUM<em>PACKET</em>BYTES )
    {
    BaseType_t xIndex;
<pre><code>    for( xIndex = ( BaseType_t ) pxNetworkBuffer-&gt;xDataLength;
         xIndex &lt; ( BaseType_t ) ipconfigETHERNET_MINIMUM_PACKET_BYTES;
         xIndex++ )
    {
        /* FreeRTOS+TCP guarantees that pucEthernetBuffer is long enough. */
        pxNetworkBuffer-&gt;pucEthernetBuffer[ xIndex ] = 0u;
    }
    pxNetworkBuffer-&gt;xDataLength = ( size_t ) ipconfigETHERNET_MINIMUM_PACKET_BYTES;
}
</code></pre>
}
<h1>endif</h1>
~~~
<blockquote>
  Or is there a way to specify end-of-buffer padding somewhere? I&#8217;ve noticed that this page is missing some details.
</blockquote>
An EMAC will understand the trailing zero&#8217;s at the end. They will be transmitted, followed by an FCS.
<a href="https://sourceforge.net/p/freertos/discussion/382005/thread/39bcfcfb/">Here</a> you find the latest <a href="https://sourceforge.net/p/freertos/discussion/382005/thread/39bcfcfb/3ee0/attachment/STM32Fxx_networkInterface_and_iperf.zip">NetworkInterface.c</a> for the STM32F4.
This and other drivers will (hopefully) soon appear in the official FreeRTOS+TCP release. Regards.

Thanks for pointing-out that defining <code>ipconfigHAS_INLINE_FUNCTIONS = 0</code> leads to compiler warnings. In fact some defines were missing. Here they are:
~~~
    #define FreeRTOS<em>max</em>BaseType(a, b)  ( ( ( BaseType<em>t  ) ( a ) ) >= ( ( BaseType</em>t  ) ( b ) ) ? ( ( BaseType<em>t  ) ( a ) ) : ( ( BaseType</em>t  ) ( b ) ) )
    #define FreeRTOS<em>max</em>UBaseType(a, b) ( ( ( UBaseType<em>t ) ( a ) ) >= ( ( UBaseType</em>t ) ( b ) ) ? ( ( UBaseType<em>t ) ( a ) ) : ( ( UBaseType</em>t ) ( b ) ) )
    #define FreeRTOS<em>min</em>BaseType(a, b)  ( ( ( BaseType<em>t  ) ( a ) ) &lt;= ( ( BaseType</em>t  ) ( b ) ) ? ( ( BaseType<em>t  ) ( a ) ) : ( ( BaseType</em>t  ) ( b ) ) )
    #define FreeRTOS<em>min</em>UBaseType(a, b) ( ( ( UBaseType<em>t ) ( a ) ) &lt;= ( ( UBaseType</em>t ) ( b ) ) ? ( ( UBaseType<em>t ) ( a ) ) : ( ( UBaseType</em>t ) ( b ) ) )
~~~
( the casts are necessary just in case these macro&#8217;s are being called with constant values ).
Something about &#8220;static inline&#8221;:
The FreeRTOS kernel has never used <code>static __inline</code> functions. The reason is that some compilers wouldn&#8217;t understand it.
When developing FreeRTOS+TCP, the need for static inline functions increased, The have several advantages compared to macro&#8217;s:
● they allow proper type-checking of the parameters
● the compiler will decide whether the functions will either be inlined or linked, depending on the generated code-size
● they avoid a possible multiple evaluation of it&#8217;s parameters
● The use of function-like macro&#8217;s can lead to hard-to-detect errors
An example of the last :
~~~
/* What if &#8216;ptr&#8217; is a number, in stead of a pointer? */
<h1>define  STORE<em>BYTE( ptr, value )    ( ( ( uint8</em>t *) ptr ) = ( value ) )</h1>
~~~
Note that an older compiler for TI parts did generate erroneous ( crashing ) code in case <code>static inline</code> functions were used in FreeRTOS+FAT, by defining <code>ffconfigINLINE_MEMORY_ACCESS = 1</code>.
TI solved that in a newer release of the compiler.
Regards.

( the following text is based on my experience with Xilinx Zynq, which has a zero-copy driver, and a lot of cached DRAM )
With <code>BufferAllocation_2.c</code>, memory will be obtained by calling <code>pvPortMalloc()</code>, which is normally cached memory. When using <code>BufferAllocation_1.c</code>, indeed you can choose where to allocate the memory, cached or uncached.
When using cached memory, before passing it to DMA, it must be flushed. And after receiving data, the memory area must be refreshed before it is up-to-date.
The mistake that I made ( I&#8217;ve had headaches about this ), was to flush or refresh parts of memory which had an overlap with other objects!
Lesson: you have to make sure that the starting offset and the length of the memory blocks occupied by <code>pucEthernet</code> are properly aligned with boundaries of the caching.
Using a length of 1536 ( 0x600 ) bytes worked wonderfully.
Later I decided to dedicate 1 MB of <strong>uncached</strong> DRAM to DMA, both for the MMC driver as well as ETH. Since then, the driver doesn&#8217;t worry about flushing and refreshing any more.  Regards.
