I want to use my FreeRTOS+TCP device as a L3 bridge  (living behind a router) 
That is to say, there are two boxes which are radio modems.
Each end runs freertos+TCP. I know the source code pretty well 
Now, the implementation is trivial but has anyone done this ?
Does anyone have any suggestions on WHERE to hook in the bridge logic and keep all the other stuff happy?
Essentially I have to pick it off 
some in
prvProcessEthernetPacket()  and check if the dst addr is our addr or &#8216;the other end&#8217;
and or prvProcessIPPacket()
on the send side, I need to do the reverse of course, inject up the stream&#8230;
In the usage case, the device (modem) will be connected to a router. .The router will route traffic to the device for traffic destined to the other subnets. IE its not actually used for bridging two networks,, but for routing between networks. I find the best way to do this sort of thing using microwave links is to put routers are each end of the link (like 192.168.1.0/24, the other end 192.168.2.0/24) , and run the link itself as a bridge (with its own subnet 172.16.1.0/29 ) etc etc
anyway, requirements are pretty much the same, I use the term bridge because that&#8217;s what it is doing.  something else will do the routing and handle the routing tables etc
glen.
</div></div><div class="thread-post"><h3 class="thread-post-title">+TCP used as L3 bridge</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 19, 2017</div><div class="thread-post-content">Hi Glen,
First some general information:
The IP-task sends all packets to Ethernet by calling this driver function:
~~~
    BaseType_t xNetworkInterfaceOutput( pxDescriptor, t bReleaseAfterSend );
~~~
The IP-task receives Ethernet packets by receiving <code>eNetworkRxEvent</code> messages in its queue ( <code>xNetworkEventQueue</code> ).  A driver can send network buffers to that queue by calling <code>xSendEventStructToIPTask()</code>.
Those are the two paths between +TCP and the Ethernet.
About &#8216;internal&#8217; routing: the current implementation is simple:
<ul>
<li>Every target that is within the netmask is contacted directly (using ARP look-up)</li>
<li>Packets to other IP-addresses will be sent to the gateway, if any.</li>
</ul>
But every packet will finally be sent by the same <code>xNetworkInterfaceOutput()</code>.
Now you want to route packets that come from your LAN, and forward them to a radio-connection and v.v., true?
<blockquote>
  <code>prvProcessEthernetPacket()</code> and check if the dst addr is our addr or &#8216;the other end&#8217;
</blockquote>
I think it&#8217;s a good place to forward packets!
<code>prvProcessEthernetPacket()</code> will handle every packet that has been received by <code>NetworkInterface.c</code> (i.e. from the LAN).
Something like the following ?
~~~
     void prvProcessEthernetPacket( NetworkBufferDescriptor<em>t * const pxNetworkBuffer )
     {
     EthernetHeader</em>t *pxEthernetHeader;
     volatile eFrameProcessingResult_t eReturned;
<pre><code>     configASSERT( pxNetworkBuffer );
</code></pre>
<ul>
<li>if( xToMyRouter( pxNetworkBuffer ) )</li>
<li>{</li>
<li>/* The packet has bee forwarded to a router. */</li>
<li>eReturned = eFrameConsumed;</li>
<li>}</li>
<li><pre><code> else
 {
     /* Interpret the Ethernet frame. */
     eReturned = ipCONSIDER_FRAME_FOR_PROCESSING( pxNetworkBuffer-&gt;pucEthernetBuffer );
     pxEthernetHeader = ( EthernetHeader_t * ) ( pxNetworkBuffer-&gt;pucEthernetBuffer );
 }
 if( eReturned == eProcessBuffer )
 ...
</code></pre>
 }
~~~</li>
</ul>
So if the function <code>xToMyRouter()</code> handles / forwards the packet, it gets ownership of the network buffer ( call <code>vReleaseNetworkBufferAndDescriptor()</code> after use ), and it must return a non-zero value.  Do not block, just queue the network buffer, in order not to hold-up the IP-task.
If this approach turns out to be useful, we could make some permanent application hook here.
I suppose that you will also create a task that monitors / receives packets from the radio-connection.
We miss something here.  You would like to call <code>xNetworkInterfaceOutput()</code> directly to forward the packet to the LAN, true? But the code in <code>NetworkInterface.c</code> <strong>assumes</strong> that the <code>xNetworkInterfaceOutput()</code> function is non re-entrant.
The IP-task does not have a message type to forward a packet to the LAN.  We could add that type of messages:
~~~
     eNetworkDownEvent,      /* 0: The network interface has been lost and/or needs [re]connecting. <em>/
     eNetworkRxEvent,        /</em> 1: The network interface has queued a received Ethernet frame. <em>/
     eARPTimerEvent,         /</em> 2: The ARP timer expired. <em>/
     eStackTxEvent,          /</em> 3: The software stack has queued a packet to transmit. <em>/
+    eForwardTxPacketEvent,  /</em> 4: Blindly forward a packet by passing it to xNetworkInterfaceOutput(). <em>/
     eDHCPEvent,             /</em> 5: Process the DHCP state machine. */
/* And in prvIPTask() in FreeRTOS_IP.c */
<pre><code> switch( xReceivedEvent.eEventType )
 {
     ...
     case eForwardTxPacketEvent:
         /* Set the `bReleaseAfterSend` parameter to true, to pass the ownership to the driver. */
         xNetworkInterfaceOutput( ( NetworkBufferDescriptor_t * ) xReceivedEvent.pvData, pdTRUE );
         break;
     ...
 }
</code></pre>
~~~
<code>eStackTxEvent</code> is a bit misleading, it will only handle UDP-packets.  It was added at the time when the library was still called +UDP 🙂
Or you could change the implementation of <code>xNetworkInterfaceOutput()</code> to become re-entrant.
I hope that I answered your question.  Regards.
