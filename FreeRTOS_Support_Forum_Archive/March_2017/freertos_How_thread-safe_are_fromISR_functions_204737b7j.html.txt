  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">How thread-safe are *fromISR() functions?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jeromecwright">jeromecwright</a> on March 8, 2017</div><div class="thread-post-content">Some of my team have been questioning how thread safe the &#42;fromISR() functions are.
Currently we use these lightweight API calls in some module interfaces in the case that they are called from high priority interrupts. 
They also referenced examples 1 and 2 from the lightweight API section here:
http://www.freertos.org/message<em>passing</em>performance.html#light
Although these examples seem to be legacy code (Version 4.8 ~ ). It does mention 
<em>&#8220;We have done nothing between Listing 1 and Listing 2 to ensure interrupt safety. This is therefore still not appropriate usage if the queue is also accessed from an ISR.&#8221;</em>
That said, the third example (using the return value to indicate an opportunity to yield) seems to be up to date. And a quick look into the functions save &amp; disable interrupts on entry then restore the register status on exit, which prevents further interrupts. However there is also a critical section in this example placed around the &#42;fromISR() function.
<strong>1. Is this third example thread safe? Can it be called from an ISR without the need to create a critical section or manage the thread interactions between queue resources?</strong>
I see no reason that the &#42;fromISR() functions cannot be called from tasks as well, just the yield behaviour needs to be managed by the application designer.
<strong>2. Is it true that the main difference between the &#42;fromISR() function and the normal API is the control over the yield?</strong>
The main reason I would like to do this is for the purpose of re-usability in application code. Having different functions based on whether the queue is being added to from an ISR or a low prio task adds to redundancy, or the need to create wrappers.
Thanks,
Jerome.
</div></div><div class="thread-post"><h3 class="thread-post-title">How thread-safe are *fromISR() functions?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 8, 2017</div><div class="thread-post-content"><blockquote>
  http://www.freertos.org/message<em>passing</em>performance.html#light
</blockquote>
Is that page still linked into the website?  Did you find it from a link 
on a different page?
Whether the &#8216;FromISR&#8217; functions are thread safe or not depends on the 
port you are using.  As general rule, if the port supports interrupt 
nesting then the functions are thread safe because they implement their 
own critical sections.  if the port doesn&#8217;t support interrupt nesting 
then the &#8216;FromISR&#8217; functions will not have critical sections and will 
not be thread safe.
</div></div><div class="thread-post"><h3 class="thread-post-title">How thread-safe are *fromISR() functions?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jeromecwright">jeromecwright</a> on March 15, 2017</div><div class="thread-post-content">I am afraid I don&#8217;t know if it is still linked to a website. Someone had sent me the link to check over as they had concerns about this. Our port is to SAMD20 ARM Cortex M0+. Which supports nested interrupts. 
But all the same it might be wise to protect our fromISR functions with critical sections for portability.
Do you think this might have any undesired behaviour?
</div></div><div class="thread-post"><h3 class="thread-post-title">How thread-safe are *fromISR() functions?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 15, 2017</div><div class="thread-post-content">The M0 port, unlike the M3, M4 and M7 ports, does not support interrupt nesting.  All the other &#8216;M&#8217; cores have a basepri reg, but the M0 does not.
