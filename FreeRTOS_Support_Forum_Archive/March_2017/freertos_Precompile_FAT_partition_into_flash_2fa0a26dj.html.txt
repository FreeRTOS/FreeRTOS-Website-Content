</div></div><div class="thread-post"><h3 class="thread-post-title">Precompile FAT partition into flash</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 18, 2017</div><div class="thread-post-content">Hi Michael, are you familiar with Linux tools?
In Linux you can create a so-called <a href="https://en.wikipedia.org/wiki/Loop_device">loop device</a>. You can format that as a small FAT16 partition (with the smallest possible cluster size), and fill it with your HTTP-files. When that is done, you can flush and close the loop device and transform the contents of a binary file into one big declaration in C:
~~~
    <strong>attribute</strong>((aligned( 4 )))
        const uint8<em>t ucHTTPDrive[ HTTP</em>SIZE ] = {
        /* here data. */
    };
~~~
The alignment helps <code>memcpy()</code>, which works much faster with aligned pointers.
It would need a simple read-only +FAT driver that reads sectors from that image in flash. Please look at <code>ff_ramdisk.c</code> for an example of such a driver.

<blockquote>

If your embedded web page is very simple, then you might just store a few HTTP files in flash and simulate the calls to <code>ff_fopen()</code>, <code>ff_fread()</code>, and <code>ff_fclose()</code>.
I have heard of uIP, but not &#8220;uip http-fs&#8221;.
<blockquote>
  The minimum FAT16 size is 4.1MB.
  Does this account for the +FAT implementation as well?
</blockquote>
+FAT uses <code>ffconfigMIN_CLUSTERS_FAT16</code> and <code>ffconfigMIN_CLUSTERS_FAT32</code> to decrease these boundaries. By default, their values are 4086 and 65525 (clusters).
<blockquote>
  Might FAT12 be a solution?
</blockquote>
+FAT also has FAT12 included, but to be honest, I don&#8217;t know user&#8217;s experiences with it. I rarely use it my self.
<blockquote>
  Also the limited 32kb RAM is a problem, regarding all the buffers used for caching.
</blockquote>
A HTTP server, a +FAT driver, and a small RAM disk?
To put it positively, that&#8217;s quite a challenge!
~~~
<pre><code>/* Some parameters to reduce the RAM foot-print of +TCP.
Settings are not yet tested. */
#define ipconfigNETWORK_MTU                    552  /* To get an MSS of 512 bytes. */
#define ipconfigUSE_TCP_WIN                      0  /* No TCP sliding windows. */
#define ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS   3
#define ipconfigTCP_RX_BUFFER_LENGTH            ( 2 * ipconfigTCP_MSS )
#define ipconfigTCP_TX_BUFFER_LENGTH            ( 2 * ipconfigTCP_MSS )
</code></pre>
~~~

I&#8217;m not following this.  You can provide your own implementation of 
ff<em>stdio.h and the ff</em> functions &#8211; that is how abstraction works &#8211; you 
provide a shim between the function being called and the function you 
want to map it too.  If you change the name of the functions then you 
will need to provide implementations of the new function names.  What 
has been gained?  Currently the API is &#8216;standard&#8217; in that it is what 
stdio expects, but with ff_ prefixed to the function names so they don&#8217;t 
clash with the standard C functions.  Changing it will make it harder to 
port to different file systems as in most cases the port is just a 
<h1>define from one to the other.</h1>

~~~
