  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Using Software Timers &#038; Tickless Idle Mode</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bryce78">bryce78</a> on March 10, 2017</div><div class="thread-post-content">Hello Community!
I am wondering about the compatibility of software timers and low-power tickless idle modes to sleep indefinitely.  I read in the version history that around v8.2.3 there were enhancements/fixes made **&#8221;to the software timer code that allows tickless low power applications to sleep indefinitely when software timers are used&#8221;. **
However, this does not appear to be working for me &#8212; the software timers still wake the RTOS, so I&#8217;m unsure I&#8217;ve configured things correctly.  I did not find any examples in &#8220;FreeRTOS/Demo&#8221; directory that illustrate tickless idle and software timers in use.
In my case:
 &#8211; FreeRTOS v9.0.0
 &#8211; (configOVERRIDE<em>DEFAULT</em>TICK<em>CONFIGURATION == 1) and (configUSE</em>TICKLESS_IDLE == 2) 
 and I&#8217;ve defined the RTOS tick generated by RTC module at 128Hz.
 &#8211; I have 3 tasks and 2 software timers (running at 32Hz and 4Hz).  
When my application has nothing to do the tasks enter the blocked state with portMAX<em>DELAY timeout and portSUPPRESS</em>TICKS<em>AND</em>SLEEP(xExpectedIdleTime) is called, where xExpectedIdleTime = 2.
(I have set configEXPECTED<em>IDLE</em>TIME<em>BEFORE</em>SLEEP == 2 so the RTOS will want to stop the ticks and enter sleep very quickly.)
With a short idle time &#8212; likely because of the software timers &#8212; the RTOS wakes after a short time, as one would expect.  I can&#8217;t realize the functionality described in the FreeRTOS version history (bold section above); logically it doesn&#8217;t seem possible, but apparently it&#8217;s implemented?  
Perhaps I misinterpret the comment or missunderstand how to configure the tickless idle to work in conjunction with software timers?  I did try disabling/enabling the software timers in the portPRE<em>SLEEP</em>PROCESSING/portPOST<em>SLEEP</em>PROCESSING but that was a bad idea!
Perhaps the comment in the version history is incorrect?  It seems to contradict 
<em>Software timers are not being used, so the scheduler is not due to execute a timer callback function at any time in the future.</em> written here http://www.freertos.org/low-power-tickless-rtos.html
Could someone clarify?
Thanks!
Bryce
</div></div><div class="thread-post"><h3 class="thread-post-title">Using Software Timers &#038; Tickless Idle Mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 11, 2017</div><div class="thread-post-content">I think the change history note you refer to was in relation to allowing 
the tickless idle mode to be entered indefinitely EVEN WHEN software 
timers were used (i.e. configUSE_TIMERS is set to 1 in 
FreeRTOSConfig.h).  Even when this is the case, software timers will 
still execute when they time out, even if tickless idle has activated 
and the MCU is in a low power state.  It does not mean that software 
timers top executing when the tickless mode is entered.  In other words 
the indefinite sleep will only be indefinite if there are no software 
timers due to expire, otherwise sleep mode will be exited when the 
software timer expires
Does that explanation help at all?
</div></div><div class="thread-post"><h3 class="thread-post-title">Using Software Timers &#038; Tickless Idle Mode</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/bryce78">bryce78</a> on March 13, 2017</div><div class="thread-post-content">Thanks!  This explanation helps a lot!
[I did not know how indefinite sleep (tickless idle) was impacted by configUSE_TIMERS == 1 in earlier versions.  Now I understand that the software enhancements were made to allow tickless idle even with this option set, but it doesn&#8217;t mean the software timers will stop executing when tickless mode is entered.]
