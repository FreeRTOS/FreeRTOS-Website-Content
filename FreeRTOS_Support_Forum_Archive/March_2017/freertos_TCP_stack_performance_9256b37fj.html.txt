</div></div><div class="thread-post"><h3 class="thread-post-title">TCP stack performance</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 30, 2017</div><div class="thread-post-content">Hi Joe, if I understand it well, in the PCAP that you emailed me, a host is sending a file to your +TCP device.
Your device advertised a TCP window size of 1320. The MSS is 660 bytes. All perfect.
But the big delays are found between the +TCP ACK and the reception of new data: about 87 ms. After that, two blocks of 660 bytes are received and an ACK is sent immediately.
You&#8217;re using these IP addresses: a private 192.168.1.21 and a public IP address 173.x.x.x
This connection goes through the Internet? If that is true, then a 90 ms delay is &#8216;normal&#8217; and only more buffer space can help you out. Unless you have a low bandwidth, then the case would be hopeless 🙂
But I guess that you have enough bandwitdth, it only has long delays.
Is your +TCP device mostly receiving large files, or also sending?
I assume you have seen the socket option <code>FREERTOS_SO_WIN_PROPERTIES</code> ?
It allows you to set 4 properties of a socket. These must be set before communication starts.
~~~
typedef struct xWIN<em>PROPS {
    /* Properties of the Tx buffer and Tx window */
    int32</em>t lTxBufSize; /* Unit: bytes <em>/
    int32_t lTxWinSize; /</em> Unit: MSS */
<pre><code>/* Properties of the Rx buffer and Rx window */
int32_t lRxBufSize; /* Unit: bytes */
int32_t lRxWinSize; /* Unit: MSS */
</code></pre>
} WinProperties_t;
~~~
As a test you could set them like this:
<pre><code>xProperties.lTxBufSize = 6 * ipconfigTCP_MSS;
xProperties.lTxWinSize = 4;
xProperties.lRxBufSize = 6 * ipconfigTCP_MSS;
xProperties.lRxWinSize = 4;
</code></pre>
or more, depending on how much RAM you have available.
Also augmenting the value of MTU would increase the performance, but that would be costly in terms of RAM usage. 
Regards, Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">TCP stack performance</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 1, 2017</div><div class="thread-post-content">Hi Joe,
( I am truly sorry to be lengthy again &#8230; )
<blockquote>
  My default setup (don&#8217;t know the the default xProperties of the socket)
</blockquote>
The defaults of the <code>xProperties</code> of a socket are indeed taken from these two macro&#8217;s:
~~~
    /* Defines the default size of the TX stream buffer. */
    #define ipconfigTCP_TX_BUFFER_LENGTH (4 * ipconfigTCP_MSS)
<pre><code>/* Defines the default size of the RX stream buffer. */
#define ipconfigTCP_RX_BUFFER_LENGTH (4 * ipconfigTCP_MSS)
</code></pre>
~~~
<code>ipconfigTCP_MSS</code> equals <code>ipconfigNETWORK_MTU</code>, minus the overhead of a TCP package.
These are the default values:
~~~
    xProperties.lTxBufSize = ipconfigTCP<em>TX</em>BUFFER<em>LENGTH;
    xProperties.lTxWinSize = ipconfigTCP</em>TX<em>BUFFER</em>LENGTH / ipconfigTCP<em>MSS;
    xProperties.lRxBufSize = ipconfigTCP</em>RX<em>BUFFER</em>LENGTH;
    xProperties.lRxWinSize = ipconfigTCP<em>RX</em>BUFFER<em>LENGTH / ipconfigTCP</em>MSS;
~~~
The driver will make sure that <code>lTxWinSize</code> and <code>lRxWinSize</code> are at least 1.
Also, <code>lTxBufSize</code> will always be a multiple of <code>MSS</code>, and if necessary, it will be rounded-up.
In case no TCP sliding windows are used ( <code>FREERTOS_SO_WIN_PROPERTIES = 0</code> ), the actual window size will be one MSS.
The following macro is something different:
<pre><code>#define ipconfigTCP_WIN_SEG_COUNT    12
</code></pre>
It says that all TCP sockets together ( at any time ) may have a total of 12 outstanding ( i.e. unconfirmed ) packets. It determines the number of buffers ( of type <code>TCPSegment_t</code> ) that are allocated in <code>FreeRTOS_TCP_WIN.c</code>.
<blockquote>
  <blockquote>
    I am downloading the file and writing it out to a SD card.
    Time to complete is 800 seconds.
    I can&#8217;t change the MSS size but I did change the following properties for THAT specific socket:
    xProperties.lRxBufSize = 20 * ipconfigTCP_MSS;
    xProperties.lRxWinSize = 20;
    Download time (and SD writing) was reduced to 110 seconds &#8212; so dare close to a times 8 improvement.
  </blockquote>
</blockquote>
That is good news! But maybe you get the same performance with 10. In a PCAP you can count the actual number of outstanding packets. It is indicated as:
~~~
    TCP -> [SEQ/ACK analysis] -> [Bytes in flight 16060]`.
~~~
In my example, there are at most 16060 bytes (11 times MSS) outstanding without an ACK.
About getting UDP faster using an application-hook :
Have you used <a href="http://www.freertos.org/FreeRTOS_Support_Forum_Archive/August_2016/freertos_TCP_UDP_multi-cast_support_658bdb52j.html"><code>FREERTOS_SO_UDP_RECV_HANDLER</code></a> already?
The UDP messages can be delivered to your application with this function:
<pre><code>BaseType_t xOnUDPReceive(
    Socket_t xSocket,
    void * pvData,
    size_t uxLength,
    const struct freertos_sockaddr * pxFrom,
    const struct freertos_sockaddr * pxDestination );
</code></pre>
The address of your function can be bound to a socket by calling <code>FreeRTOS_setsockopt()</code> with &#8216;FREERTOS<em>SO</em>UDP<em>RECV</em>HANDLER&#8217;.
The function must return non-zero to tell the stack that it may discard the packet.
When using this call-back, time is saved: your application task doesn&#8217;t not need to become active.
The call-back should be fast though (do not block or wait), because it is called from the IP-task.
Regards.
