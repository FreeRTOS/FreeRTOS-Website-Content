  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Atmel SAMG55 and USB MS Host  intermittend problem</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/przemekg">przemekg</a> on September 10, 2018</div><div class="thread-post-content">Hi , I am running freeRTOS 10.1 on Atmel SAMG55, using Atmel frame work and fatFS.
USB stack is interrupt driven.
I experienced lots of problems with intermittent system freeze during writing files to USB MS.
Writing to the USB MS works fine without RTOS enabled (a simple loop writing short text report file for testing purposes).  Once the loop is moved to the RTOS task, then the USB stack freezes during write operation after some iterations (3 &#8211; 100&#8230;). 
Ther is no difference if preemption is enabled or disabled (as only single task is created):
~~~
void board<em>task</em>usb<em>debug(void *pvParameters){
    UNUSED(pvParameters);
    for(;;) {<br />
        ct</em>ReportToFile();
        vTaskDelay (500);
    }
}
~~~
No other timers or or interrupt sources enabled. FreeRTOS and USB stack interrupt priories set as follow:
~~~
<h1>define configLIBRARY<em>LOWEST</em>INTERRUPT_PRIORITY 0x0f    /* Lowest on M4 */</h1>
<h1>define configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY 10</h1>
<h1>define UHD<em>USB</em>INT_LEVEL 0 /* Highest on M4 */</h1>
~~~
I&#8217;ve got impression that the USB write operation is somehow corrupted by the systick timer, but the USB interrupts are on the higher priority than freertos systick.<br />
Current systick is set to 1000Hz, and I can get  up to about 100 successful write operations (about 10 in most cases).  If systick is set to 100Hz (and vTaskDelay() set accordingly), then I can get couple of hundreds operations before it freezes.
Massive heap is allocated for that task.
I am missing something? (probably)
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel SAMG55 and USB MS Host  intermittend problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on September 10, 2018</div><div class="thread-post-content">Since you have the USB interrupt at a level higher than (lower value) than configLIBRARY<em>MAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY it can not use any FreeRTOS interfaces (the FromISR calls).
I would normally expect that a USB driver would use some sort or notification through the RTOS to tell tasks there is something to process so they don&#8217;t need to spin wait for a data flag.
Having ISRs at too high of a priority level cause this sort of problems.
If you have configASSERT setup to report these sorts of issues, it helps detect a lot of this klind of issue.
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel SAMG55 and USB MS Host  intermittend problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/przemekg">przemekg</a> on September 10, 2018</div><div class="thread-post-content">I can see your point. A the moment the USB driver is not aware of the RTOS and it is not using any of the FromISR calls.  
However, does it matter if there is only one task running and preemption is disabled ?
I do not have configASSERT setup,  but found that the USB stack is freezing waitng for the &#8220;uhi<em>msc</em>mem<em>command</em>ongoing&#8221; flag to be zeroed in the folowing function:
~~~
Ctrl<em>status uhi</em>msc<em>mem</em>write<em>10</em>ram(uint32<em>t addr, const void *ram)
{
   &#8230;
    uhi</em>msc<em>mem</em>command<em>ongoing = true;
    uhi</em>msc<em>scsi</em>write<em>10(uhi</em>msc<em>mem</em>lun, addr, ram, 1,
            uhi<em>msc</em>mem<em>stop</em>pooling);
    while (uhi<em>msc</em>mem<em>command</em>ongoing);   /* stuck here */ 
    if (!uhi_msc_mem_command_status) {
        return CTRL_FAIL;
    }
~~~
The program flow in that stack is quite complicated (for me ..) and I am not sure where to start with transforming it to RTOS friendly&#8230;
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel SAMG55 and USB MS Host  intermittend problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on September 11, 2018</div><div class="thread-post-content">One thing to check is that uhi<em>msc</em>mem<em>command</em>ongoing is actually being checked (looking at the assembly of the loop). If it hasn&#8217;t been made volatile, it is possible that the compiler generated code that doesn&#8217;t reload the value for memory for each check.
That code should be able to be replaced with a semaphore.
setting the flag to true, would be a take with a timeout of 0, to make sure the semaphore is taken.
The wait loop would be a take with a maximum delay.
The ISR would do a give from ISR to be the equivalent of setting it to zero.
It  could also use direct to task notifications.
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel SAMG55 and USB MS Host  intermittend problem</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/przemekg">przemekg</a> on September 11, 2018</div><div class="thread-post-content">All the flags are declared as volatile, bet there is quie a few of them , used as a callbacks. It is not easy to track the flow, as lot of dependencies are used in the Atmel ASF.
I added and tested the configASSERT, but it does not throw any hints so far. 
Trying to find an example of use Atmal SAM with USB host and FreeRTOS now.
