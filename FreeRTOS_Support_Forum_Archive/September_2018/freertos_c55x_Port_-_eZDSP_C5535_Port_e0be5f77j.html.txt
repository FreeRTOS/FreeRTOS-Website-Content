Some details:
 The workspace you want to grab is here:
eZDSP->eZDSP<em>5535</em>Files->ccsws2
Within that is dir->test &#8211; that is the project you want to run.
Note, since this is a 7zip file &#8211; you may have to fix some paths.  I have this running on the eZDSP 5535 USB Stick and my dev drive for this is f:&#46;
The debugger could croak a little if you break and it is in a lib routine &#8211; but hit continue and it should hit the next breakpoint &#8211; I think that could be another artifact of the DBSTAT issue.
The file also contains instructions on how to build a bootable SD image.
I started work on this awhile ago &#8211; CCS 7.4.0 is the current build tool for the archive plus the port is using v.6.0.5.  I have it running on the &#8216;C5545 Booster Pack board and will release that a little later.
For both boards &#8211; the demo blinks as many LEDs as possible and a few messages get written to the OLED screen.

</div></div><div class="thread-post"><h3 class="thread-post-title">c55x Port &#8211; eZDSP C5535 Port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/westmorelandeng">westmorelandeng</a> on September 9, 2018</div><div class="thread-post-content">Hello Again Everyone,
I&#8217;ve posted a new dir in the repository:
eZdsp<em>C55x</em>FreeRTOS<em>Port/eZdsp</em>DBG/
It has the kernel updated to v10.1.1 which was just released.<br />
I&#8217;ve also updated to the latest TI IDE &#8211; CCS v8.1.0 &#8211; and the workspace that&#8217;s in the commit is for this version of CCS (ccsw2).  Note, due to TI deprecating support for the &#8216;c55x modules and boards &#8211; the IDE won&#8217;t load everying quite automatically; and, when you make an SD image, you have to make sure and use the x-standalone.x files &#8211; there&#8217;s a dir for those you&#8217;ll find.  I&#8217;ve also posted an SD bootimage that will boot both the ezDSP &#8216;c5535 and the &#8216;c5545 BP boards.   So that can be used as a diagnostic if needed.
    When you get things running in the debugger &#8211; depending on how much you may have to change directories, etc. &#8211; you may have to set up a new debug workspace &#8211; but you can still use the EZDSP5535.ccxml and ezdsp5535.gel files but you may have to set up loading the test.out file, etc. manually.  Hopefully the workspace loads OK.<br />
 And here&#8217;s another interesting part &#8211; tasks.c &#8211; I decided to rename that tasks<em>sysStk.c &#8211; and, the port sortof breaks the current porting convention; but that assumes there really is one and since this is a new target so-to-speak; and it has two stacks, one &#8216;regular&#8217; stack and a system stack; it was necessary to add the secondary system stack to tasks.c (tasks</em>sysStk.c).  The addition is fairly straight forward; and does use a litte unnecessary memory; but the port runs.  So, just blindly adding new kernel files and not making the necessary updates to tasks<em>sysStk.c and/or just taking tasks.c and not doing the necessary work for the system stack will result in the port not running. 
 So, officially though &#8211; this is for Richard:
 I humbly submit tasks</em>sysStk.c as an addition to the kernel files that enables the use of the system stack on the Texas Instruments &#8216;c55x Low Power DSP architecture.  I know we&#8217;ve talked about this in the past &#8211; but here it is, finally.
 I also do not claim this is the ONLY way to do this; it&#8217;s A way, and it works; and debugging that isn&#8217;t fast or easy.   I think we&#8217;ve all experienced how a debugger can completely lose it&#8217;s mind with the stack is blown &#8211; imagine now when two stacks are blown.<br />
 OK &#8211; have fun with this, and good luck everyone!
 John Westmoreland

The README.md has been updated:
Addendum: (9/25/18 &#8211; jcw) Before you go embarking on debugging this build (these builds now) &#8211; please be aware of the following document: http://www.ti.com/lit/ug/spru652g/spru652g.pdf Apparently CPU<em>119 hasn&#8217;t been fixed. It&#8217;s virtually impossible to tell if you have a stack issue and/or a DBSTAT issue right now. I&#8217;ve asked TI for the definition of DBSTAT more than once; just so I can check to see if valid values are on the stack. DBSTAT is basically in the &#8216;middle&#8217; of sysstack; so there&#8217;s really no good way to deal with it. Wanted to mention this since I imagine some will wonder why I&#8217;ve taken the approach I have taken. Note CPU</em>119 isn&#8217;t the only item that&#8217;s a possible issue still in the SPRU652 document.
Regards,
John W.
