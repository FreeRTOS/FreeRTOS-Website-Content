I am trying to measure the execution time of a function a FreeRTOS task with xTaskGetTickCount(). The code looks like the following example.
~~~
static void prvRxTask( void *pvParameters )
{
<pre><code>for( ;; )
{
    long start = xTaskGetTickCount();
    func_doing_something();
    long stop = xTaskGetTickCount() - start;
    vTaskDelay( pdMS_TO_TICKS( 1000UL ) );
}
</code></pre>
}
~~~
My result of stop is always  &#8220;0&#8221; because the xTaskGetTickCount() gets not incremented durring the tasks execution.  Why is that so? (I activated the timer in the FreeRTOSConfig.h) If it is relevant, I am using a Zedboard with a Zynq 7000 SoC.
</div></div><div class="thread-post"><h3 class="thread-post-title">Measure Time within a Task with xTaskGetTickCount()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xz8987f">xz8987f</a> on September 1, 2018</div><div class="thread-post-content">The tick count gets incremented at every tick interrupt. So the question is what is your tick frequency/period? If you have set it up to 1 ms, you won&#8217;t be able to measure something which is faster than that. Or in other words: Keep the Nyquist/Shannon theorem in mind (https://en.wikipedia.org/wiki/Nyquist%E2%80%93Shannon<em>sampling</em>theorem).
What I&#8217;m using instead for ARM Cortex-M3/M4/M7 (not sure what you are using) is the Cortex cycle counter (see https://mcuoneclipse.com/2017/01/30/cycle-counting-on-arm-cortex-m-with-dwt/).
I hope this helps,
Erich

</div></div><div class="thread-post"><h3 class="thread-post-title">Measure Time within a Task with xTaskGetTickCount()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on September 2, 2018</div><div class="thread-post-content">No &#8211; provided you are not in a critical section, the tick count gets incremented on every tick interrupt, no matter which task is running.
Are you sure the tick count is incrementing at all?  If not, then the call to vTaskDelay() will never return &#8211; if vTaskDelay() does return then the tick interrupt is executing [probably] correctly &#8211; in which case the next thing to do would be to mearsure the time to check the frequency is as you expect.
</div></div><div class="thread-post"><h3 class="thread-post-title">Measure Time within a Task with xTaskGetTickCount()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 2, 2018</div><div class="thread-post-content">A few additional remarks:
<blockquote>
  long start = xTaskGetTickCount();
</blockquote>
The type <code>long</code> is <code>signed</code>.  The result of <code>xTaskGetTickCount()</code> has the type <code>TickType_t</code>, which is always <code>unsigned</code>.  In the Zynq port it is 32 bits in portmacro.h:
~~~
    typedef uint32<em>t TickType</em>t;
~~~
Now when you calculate a difference in time, you can use unsigned arithmetic as here below:
~~~
    TickType<em>t xStart, xEnd, xDifference;
    for( ;; )
    {
        xStart = xTaskGetTickCount();
        vTaskDelay( pdMS</em>TO_TICKS( 1000UL ) );
        xEnd = xTaskGetTickCount();
        xDifference = xEnd &#8211; xStart;
        printf( &#8220;Time diff: %lu ticksn&#8221;, xDifference );
    }
~~~
In the above case, one would expect to see: &#8220;Time diff: 1000 ticks&#8221;.   Can you please verify that?
~~~
    long start = xTaskGetTickCount();
    func<em>doing</em>something();
    long stop = xTaskGetTickCount() &#8211; start;
~~~
The variables here above are never being read, so why would the compiler assign a value to them?
When you inspect local variables from within a debugger, you better switch off compiler optimisations (<code>-O0</code> ).
The tick count is incremented from within an interrupt, and that happens independently from what your application is doing.
So unless you use an endless critical section ( which disables interrupts ), the tick count should always get updated.
When I work with Xilinx/Zynq, I often use a function from their Xilinx library to measure time in micro-seconds:
~~~
<h1>define COUNTS<em>PER</em>USECOND  ( XPAR<em>CPU</em>CORTEXA9<em>CORE</em>CLOCK<em>FREQ</em>HZ / ( 2 * 1000000u ) )</h1>
uint64_t ullGetHighResolutionTime( void )
{
XTime tCur;
<pre><code>XTime_GetTime( &amp;tCur );
tCur /= COUNTS_PER_USECOND;
/* Return the time in micro-seconds. */
return tCur;
</code></pre>
}
~~~
My core frequency was 666 MHz.
The functions store the time as 64-bits so they won&#8217;t overflow quickly.
