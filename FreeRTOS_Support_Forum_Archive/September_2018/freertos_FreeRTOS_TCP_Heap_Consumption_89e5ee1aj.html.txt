I have both ipconfigZERO<em>COPY</em>TX<em>DRIVER and ipconfigZERO</em>COPY<em>RX</em>DRIVER set to 1, and I&#8217;m using BufferAllocation_1 and, of course, heap4.
At present, the +TCP stack seems to be working well on the surface as I&#8217;m able to send and receive UDP packets, and I&#8217;ve also implemented and tested a simple HTTP server &#8230; thus TCP is working as well.
For diagnostic purposes, I have a console readout that lets me inspect the heap using xPortGetFreeHeapSize() and xPortGetMinimumEverFreeHeapSize().

When I retrieve a simple web page using a browser,  however, the heap consumption rises to ~45K (expected) &#8230; but then never goes back down again.  After the HTTP transactions, I&#8217;m properly closing all involved sockets.  I can retrieve the web page a 2nd time and it doesn&#8217;t climb any higher than the ~45K, so there&#8217;s no memory leak.
The last time I had +TCP diagnostic messages enabled, I didn&#8217;t notice any unusual consumption (leaks) in the buffer descriptors.  The count rises with activity, as expected, but remains stable.

In general, I need help with a bit deeper dive into the inner workings of the +TCP memory management so I can use more than superficial &#8220;appearance&#8221; for verifying my code integrity.  I don&#8217;t want to create code that may be configured wrong or unnecessarily impacts TCP performance. **

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP Heap Consumption</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on September 5, 2018</div><div class="thread-post-content">Roughly spoken, there are two phases during which heap memory is allocated and that memory is never released.
1) During <code>FreeRTOS_IPInit()</code>, several system resources are allocated. 
2) When the first TCP connection is established, some buffers are allocated in <code>FreeRTOS_TCP_WIN.c</code>:
~~~
    xTCPSegments = ( TCPSegment<em>t * ) pvPortMallocLarge( ipconfigTCP</em>WIN<em>SEG</em>COUNT * sizeof( xTCPSegments[ 0 ] ) );
~~~
Please check the value of <code>ipconfigTCP_WIN_SEG_COUNT</code>. It defines the maximum number of outstanding packets ( both RX and TX ) at any moment in time.  The default of 256 is a bit high, 32 would be OK for a small device with few &#8220;concurrent&#8221; TCP connections.
One <code>TCPSegment_t</code> is about 64 bytes, so by default about 16 KB is being allocated.
A TCP socket will allocate heap memory when created. Beside that, stream buffers will be created when the first bytes are being sent or received.
An UDP socket doesn&#8217;t need a stream buffer. It will store the receive packets in buffers of the type <code>NetworkBufferDescriptor_t</code>.
All memory allocated by a socket will be released when <code>FreeRTOS_closesocket()</code> is called.
When using the <strong>copy</strong> method, both for RX and TX, a number of buffers are usually declared as static space.
So the linker will reserve for instance:
~~~
   For RX : 10 x 1536 bytes
   For TX :  2 x 1536 bytes
<hr />
<pre><code>        12 x 1536 = 18432 bytes
</code></pre>
~~~
When using the <strong>zero-copy</strong> method, the memory costs are about the same:
~~~
   For RX : 10 Network buffers
   For TX :  0
<hr />
<pre><code>        10 Network buffers
</code></pre>
~~~
When receiving packets, DMA will write directly into Network buffer. When sending packets, DMA will read from a Network buffer.
As you probably know:
<code>BufferAllocation_1.c</code> declares the space for Network buffers in static arrays.
<code>BufferAllocation_2.c</code> is more suitable for small memory: it allocates the space dynamically.
