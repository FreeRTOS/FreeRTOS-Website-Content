  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">High priority interrupts on pic24 port</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hucker233">hucker233</a> on June 3, 2010</div><div class="thread-post-content">I have just isolated a bug in some code I&#8217;m debugging on a PIC24 project.&nbsp; The code is using an API function in an ISR that runs at a priority higher than the kernel priority &#40;1&#41;.&nbsp;   
The priorities were setup because our AD has a very tight timing requirement for clocking the data in &#40;if we take an interrupt in the middle we loose data&#41;.&nbsp; The problem is the code right now is queuing up the data &#40;a fair bit&#41; from the ISR for external task processing and saving to an SD card.&nbsp; This mechanism eventually crashes.  
So now I&#8217;m in a quandary, how best to handle this from an architectural standpoint?&nbsp; Implementation as a queue was natural &#40;as was a semaphore&#41; but it appears that none of the OS centric solutions will work here since I can&#8217;t call them.&nbsp; Valid assumption?&nbsp; Am I stuck writing to a circular buffer I manage in the ISR and then having a task poll to see if new data has arrived?&nbsp; Seems to defeat some of the reason I&#8217;m using an OS&#33;  
Any help greatly appreciated, this has been quite a wild goose chase&#33;  
Chuck
</div></div><div class="thread-post"><h3 class="thread-post-title">High priority interrupts on pic24 port</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on June 3, 2010</div><div class="thread-post-content">Since the interrupt is above configKERNEL&#95;INTERRUPT&#95;PRIORITY then the ISR can not user any FreeRTOS functions, so no queue to send data from ISR to task. You will need to fill a buffer in ram, and somehow signal the task the data is there, one trick would be to take some unused device, and have the A/D interrupt manually trigger it with the IF register, and have that interrupt set a semaphore, etc.  
Another option, if your processor supports it, is to use DMA to read the A/D and take an interrupt on buffer full, which would be less critical. &#40;This may not be an option on your processor, I know some of the dsPIC33 have this, I don&#8217;t know if any of the PIC24s do.
