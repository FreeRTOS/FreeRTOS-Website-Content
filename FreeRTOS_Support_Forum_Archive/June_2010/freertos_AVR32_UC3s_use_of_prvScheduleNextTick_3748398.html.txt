  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">AVR32_UC3&#8217;s use of prvScheduleNextTick()</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rgrover1">rgrover1</a> on June 22, 2010</div><div class="thread-post-content">Hello,  
I&#8217;m working with AVR32&#95;UC3 and GCC. I&#8217;ve got a FreeRTOS port from Atmel at version 6.0.0; and it seems to work fine for a simple app which blinks LEDs.<br />
I want to upgrade to 6.0.5; but my led-blinker app fails.<br />
The problem is caused by the changes in port.c to the mechanism used to generate ticks.<br />
It has to do with prvScheduleNextTick&#40;&#41;; which replaces the previous scheme implemented by prvClearCcInt&#40;&#41;.  
I&#8217;ll include the code from the two:  
<pre><code>    __attribute__((__noinline__)) static void prvClearCcInt(void)
    {
        Set_system_register(AVR32_COMPARE, Get_system_register(AVR32_COMPARE));
    }
</code></pre>
Vs.  
<pre><code>    __attribute__((__noinline__)) static void prvScheduleNextTick(void)
    {
        unsigned long lCycles, lCount;
        lCycles = Get_system_register(AVR32_COMPARE);
        lCycles += (configCPU_CLOCK_HZ/configTICK_RATE_HZ);
        // If lCycles ends up to be 0, make it 1 so that the COMPARE and exception
        // generation feature does not get disabled.
        if(0 == lCycles)
        {
            lCycles++;
        }
        lCount = Get_system_register(AVR32_COUNT);
        if( lCycles &lt; lCount )
        {       // We missed a tick, recover for the next.
            lCycles += (configCPU_CLOCK_HZ/configTICK_RATE_HZ);
        }
        Set_system_register(AVR32_COMPARE, lCycles);
    }
</code></pre>
Reverting port.c in 6.0.5 to use prvClearCcInt&#40;&#41; makes everything work like normal.  
On the surface, it seems that prvScheduleNextTick&#40;&#41; certainly has a minor bug about not taking counter wrap-around into consideration-when the COMPARE register value wraps around due to the increment we might end up generating the next tick TWO ticks later. But I can&#8217;t figure out why my app completely fails to work with the new scheme.  
Can someone please help? Thanks.
</div></div><div class="thread-post"><h3 class="thread-post-title">AVR32_UC3&#8217;s use of prvScheduleNextTick()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rgrover1">rgrover1</a> on June 22, 2010</div><div class="thread-post-content">And could someone please explain to me how the previous scheme worked &#40;i.e. the one using prvClearCcInt&#41;. Does setting the COMPARE register to itself reset the COUNT register?
</div></div><div class="thread-post"><h3 class="thread-post-title">AVR32_UC3&#8217;s use of prvScheduleNextTick()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on June 22, 2010</div><div class="thread-post-content">The files in the FreeRTOS download are designed for the original ES version of the AVR32, whereas the files in the AVR32 Atmel Software Framework &#40;available from atmel.com&#41; are designed for the latest AVR32 chips.&nbsp; The ES versions are now somewhat obsolete, and my advice is to use the files from Software Framework V1.7.0.&nbsp; The AVR32 files have not been updated between V6.0.0 and V6.0.5 so I don&#8217;t think you will have any problems there.  
There is actually a new AVR32 port being created at the moment to add a bit of extra functionality, and the original files have actually been removed from the FreeRTOS SVN repository already.&nbsp; I can&#8217;t promise a completion date yet &#8211; but watch this space…  
Regards.
