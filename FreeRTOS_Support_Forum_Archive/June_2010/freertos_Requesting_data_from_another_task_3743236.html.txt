  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Requesting data from another task</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ljskinny">ljskinny</a> on June 16, 2010</div><div class="thread-post-content">Hello there,  
i&#8217;m new to the freertos and programmed avrs in a mainloop style so far. For a new project i want to learn more about the intertask communication and the best practises.  
So far no problem in the understanding of the RTOS but now i have the following problem.  
I have a GUI task which displays the status of other tasks &#40; UART active, temperatures, usb, …&#41; So i need some status information from the tasks. My goal is to make independed tasks, which in future could developed by seperate programmers. So they only need to know the messages how to communicate with each other.  
Solution 1:&nbsp; The Peripheral tasks sending continously the status data. For me this makes no sense.  
Solution 2:&nbsp; The Gui Task uses a shared memory variable from the other task protected by a semaphore. Advantage: No memory overhead, but the GUI task needs to know about the task and its member variables..  
Solution 3: The Gui Task requests the data by a Message through a Queue to the corresponding task. The Task will answer in a different queue with the requested data. So the advantage is, you only need to know the messages but not about the task. So different programmers could program independed tasks with only one defined interface &#40; Messages&#41;.  
So what are your suggestions about this problem regarding performance, reuse, simply and robustness?  
Best reagrds,  
Holger  
</div></div><div class="thread-post"><h3 class="thread-post-title">Requesting data from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on June 16, 2010</div><div class="thread-post-content"><blockquote>
  Solution 1:&nbsp; The Peripheral tasks sending continously the status data. For me this makes no sense.  
</blockquote>
I think it makes no sense to send the data unless it has changed, and the change is in some way significant.  
<blockquote>
  Solution 2:&nbsp; The Gui Task uses a shared memory variable from the other task protected by a semaphore. Advantage: No memory overhead, but the GUI task needs to know about the task and its member variables..  
</blockquote>
You could end up with a lot of semaphores which will not be efficient.  
<blockquote>
  Solution 3: The Gui Task requests the data by a Message through a Queue to the corresponding task. The Task will answer in a different queue with the requested data. So the advantage is, you only need to know the messages but not about the task. So different programmers could program independed tasks with only one defined interface &#40; Messages&#41;.  
</blockquote>
How about have a single queue that the GUI tasks reads. When other tasks post they post the data value and the meaning of the data. That way there is only one queue, everything is serialized, and your app will be efficient.
</div></div><div class="thread-post"><h3 class="thread-post-title">Requesting data from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ljskinny">ljskinny</a> on June 17, 2010</div><div class="thread-post-content">Hi Davedoors.  
In my GUI task, this is only one point of the menu. So this is a special case. My menu should also setup the parameters&nbsp; for each pheriperal. In this case i will send messages through a queue to each task. My Problem is getting the data from the other task on request.  
Best regards  
Holger  
</div></div><div class="thread-post"><h3 class="thread-post-title">Requesting data from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jkuusama">jkuusama</a> on June 18, 2010</div><div class="thread-post-content">I had&nbsp; the same problem. In my solution, a task sends out a message when the status changes, but only then. The message is sent to a message passing task, which then sends the message out the any task wanting to know about statuses. That is handy, since I don&#8217;t need to touch any any of the other tasks if I want to add a logger task, a serial port reporting task or whatever.  
By the way, I&#8217;m using shared memory for the status info. The task need to know either about the messages or the variables, and I don&#8217;t see a big difference either way. I have functions to read and write to the shared memory, and then the status messages are simply &#8220;task1 status changed&#8221; and the monitor task calls read status variable function; no need to make it any more complicated:-&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Requesting data from another task</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ljskinny">ljskinny</a> on June 22, 2010</div><div class="thread-post-content">Hi there,  
now i had another idea to solve this:  
I have two queues:  
<strong>1&#41; CommandQueue:</strong><br />
This queue will get events from other tasks. &#40;setting vars, execute functions,etc&#41; It also will receive a RequestEvent from another task. This request is not send to the CommandQueue from that task, but to the RequestQueue of that task.  
<strong>2&#41; RequestQueue:</strong><br />
In this queue we will receive requested data from other tasks. Since there is only data written on request of this task, there is no collision with other tasks.  
I find this system easy to use, because you can simple wrap this to the uart, spi, I2C to communicate with other peripherals.  
Best regards,  
Holger
