  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS+TCP : Why do sockets stay in the status eCLOSE_WAIT ?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 2, 2016</div><div class="thread-post-content">A user of FreeRTOS+TCP asked the following question:
<blockquote>
  Look at the output of FreeRTOS_netstat(). It was recorded on a K63F
  machine:
</blockquote>
~~~~ 
    Prot Port IP-Remote       : Port  R/T Status       Alive  tmout Child
    TCP  3123 0.0.0.0         :     0 0/0 eTCP<em>LISTEN      0      0 0/2
    TCP    80 0.0.0.0         :     0 0/0 eTCP</em>LISTEN      0      0 3/3
    TCP    80 192.168.180.111 : 55940 1/0 eCLOSE<em>WAIT      0  19973
    TCP    80 192.168.180.111 : 55942 1/0 eCLOSE</em>WAIT      0  19975
    TCP    80 192.168.180.111 : 55944 1/0 eCLOSE<em>WAIT      0  20000
    FreeRTOS</em>netstat: 5 sockets 2 &lt; 3 &lt; 3 buffers free
~~~~
<blockquote>
  192.168.180.111 is the PC running several wget instances in parallel,
  all connecting to K63F. Port 80 has a listen limit of 3 clients. After
  1000-4000 seconds no new HTTP connections can be initiated, since there
  are no free &#8220;slots&#8221;.
  I don&#8217;t understand why those closed sockets (all wgets are killed on
  the PC) in eCLOSE_WAIT state remain there; they should disappear,
  shouldn&#8217;t they? There&#8217;s a &#8216;tmout&#8217; field, which reaches zero, but then
  the countdown start from 20000 again.
  What could be the reason for these persistent, non-closing sockets?
</blockquote>
From <a href="https://en.wikipedia.org/wiki/Transmission_Control_Protocol">WiKiPedia</a>:
<pre><code>CLOSE-WAIT
    (both server and client) represents waiting for a connection
    termination request from the local user.
</code></pre>
A socket in the status &#8220;<code>eCLOSE_WAIT</code>&#8221; is waiting for you! It has done
all it could and it may be closed by calling <code>FreeRTOS_closesocket()</code>.
How can you prevent this?
1) Check the return code of all API&#8217;s :
~~~~
    // Same for FreeRTOS<em>send()
    xRc = FreeRTOS</em>recv(s, b, sizeof b, 0);
    if( ( xRc &lt; 0 ) &amp;&amp; ( xRc != -pdFREERTOS<em>ERRNO</em>EWOULDBLOCK ) )
    {
        FreeRTOS_closesocket( s );
        s = NULL;
        return -1;
    }
~~~~
Note: if a socket&#8217;s connection is closed but it still has RX data, <code>FreeRTOS_recv()</code> will return positive values until all data have been read.
2) After your socket is connected, you may call <code>FreeRTOS_issocketconnected()</code> to see if it is still connected. If it returns false you can close the socket.
3)  You can call <code>FreeRTOS_connstatus()</code> to check the status, but that is only recommended for debugging.
4) Always try to close sockets gracefully. Also under other operating systems that communicate with your embedded systems. If your program decides to close a TCP connection, follow this procedure (symbolically):
~~~~
    FreeRTOS<em>shutdown(s, 0);
    /* A FIN will be sent. Wait up to a few seconds for the other
    party to ACK our FIN.
    If the other party still had data to sent, it will do so.
    Keep on calling FreeRTOS</em>recv() for this socket until it returns
    a negative value (not equal to -EWOULDBLOCK) */
<pre><code>for( ;; )
{
    /* Only do this if reading from 's' will block. */
    xRc = FreeRTOS_recv(s, buf, sizeof buf, 0);
    if( xRc &gt; 0 )
    {
        /* Use the received data in 'buf'. */
    }
    else if( ( xRc &lt; 0 ) &amp;&amp; ( xRc != -pdFREERTOS_ERRNO_EWOULDBLOCK ) )
    {
        FreeRTOS_closesocket( s );
        s = NULL;
        break;
    }
}
</code></pre>
~~~~
The flag for <code>shutdown()</code> (RD, WR, and RDWR)  has not been implemented in +TCP.
PS about <code>FreeRTOS_issocketconnected()</code>:
For an active connection, using <code>FreeRTOS_connect()</code>, you can call <code>FreeRTOS_issocketconnected()</code> as well. It will return false until the socket gets connected. Once it is connected, it will return true until the connection is closed.
For passive connections (using <code>FreeRTOS_accept()</code>), the socket will start in a connected state.
