I am noticing that xTxLock is accessed both from ISR and task code &#40;same for xRxLock&#41;.  
Wouldn&#8217;t it need to be declared volatile to ensure that neither the task called function does not cache the value in a register?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Why isn&#8217;t xTxLock in xQueueHandle volatile</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on August 1, 2012</div><div class="thread-post-content">Forgot to add that is is similar to this post <a href="http://www.freertos.org/FreeRTOS_Support_Forum_Archive/September_2006/freertos_Queues_and_compiler_optimization_GCC_1582595.html">http://www.freertos.org/FreeRTOS_Support_Forum_Archive/September_2006/freertos_Queues_and_compiler_optimization_GCC_1582595.html</a>  
But there did not appear to be a definitive answer.   
</div></div><div class="thread-post"><h3 class="thread-post-title">Why isn&#8217;t xTxLock in xQueueHandle volatile</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 2, 2012</div><div class="thread-post-content">Interesting question. I think volatile is often used to often in FreeRTOS and could be speeded up with less but I&#8217;m not sure in this case.  
Looking at xTxLock,  
It is used in xQueueGenericSendFromISR&#40;&#41; where the function tests and sets a value in a structure passed in as a pointer. The optimizer cannot determine how the value is used so should not optimize the code away.  
It is used in prvUnlockQueue&#40;&#41; where the same logic applies but in this case the function is quite short so the optimizer could potentially try and inline it.  
It is used in the macro prvLockQueue&#40;&#41; which is used in xQueueGenericSend&#40;&#41; and xQueueGenericReceive&#40;&#41; which are also the functions that call prvUnlockQueue&#40;&#41;, so if prvUnlockQueue&#40;&#41; is inlined the compiler can see xTxLock is being used but might not see why as it is never tested.  
Comments Richard?
</div></div><div class="thread-post"><h3 class="thread-post-title">Why isn&#8217;t xTxLock in xQueueHandle volatile</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 2, 2012</div><div class="thread-post-content">There might be something in this, as the compiler does not know the value is being tested in an interrupt, I&#8217;m looking into it.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Why isn&#8217;t xTxLock in xQueueHandle volatile</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 2, 2012</div><div class="thread-post-content">Having looked at this, my conclusion is that the xTxLock and xRxLock variables should probably be made volatile, for absolute certainty, although it is probably not necessary.  
My reasoning is that the locking and unlocking is not performed in the same function.&nbsp; While the locking is inline, the unlocking is performed by a separate function &#40;prvUnlockQueue&#40;&#41;&#41;, therefore the compiler will probably not see an increment then decrement of the lock count without the incremented value ever being used unless prvUnlockQueue&#40;&#41; was itself inlined &#8211; which is unlikely &#8211; or cross function optimisation was used.  
However, as the word &#8220;probably&#8221; appears in that sentence, it makes sense to make them volatile.&nbsp; Thanks for pointing this out.  
Interestingly the uxMessagesWaiting value is volatile, but probably does not need to be, as it is incremented and decremented in completely different functions, with completely different execution patterns.&nbsp; Dare I take that out though :o&#41;  
Regards.
