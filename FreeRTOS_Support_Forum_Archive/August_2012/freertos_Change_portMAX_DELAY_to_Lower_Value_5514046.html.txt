  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Change portMAX_DELAY to Lower Value</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on August 10, 2012</div><div class="thread-post-content">Is portMAX&#95;DELAY required to be 0xFFFFFFFF for a 32-bit tick?&nbsp; What happens if this timeout is actually reached for an xQueueReceive&#40;&#41; call?  
Here&#8217;s the background:  
I have several tasks that call xQueueRecieve on a queue with a timeout of portMAX&#95;DELAY.&nbsp; One task &#40;a console processor&#41; is expected to routinely reach the 32-bit timeout, others are expected to never reach it.&nbsp; I was testing that the one that is routinely supposed to reach the portMAX&#95;DELAY timeout work correctly.&nbsp; A portMAX&#95;DELAY of 0xFFFFFFFF is 49.7 days for me.&nbsp; I didn&#8217;t want to wait that long for my test, so I set it to 10 minutes &#40;600000 ticks&#41;.&nbsp; When I ran my app, ALL of my tasks that call xQueueReceive&#40;&#41; with portMAX&#95;DELAY locked up, even the ones that were successfully receiving from the queue for the entire 10 minutes.&nbsp; The one task that I was testing &#40;the one that was blocked for the entire 10 minutes&#41; is stuck in vListInsert&#40;&#41; in the iteration loop.&nbsp; I&#8217;m guessing that&#8217;s why the other tasks stopped working, and I&#8217;m also assuming all my other tasks have stopped working too.&nbsp; The only thing I can see running are raw console messages from within ISRs saying that none of my ISTs are running…&nbsp; I have a lot of experience with causing tasks to get stuck in vListInsert&#40;&#41;, but not like this.  
Thanks,<br />
Andy
</div></div><div class="thread-post"><h3 class="thread-post-title">Change portMAX_DELAY to Lower Value</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 10, 2012</div><div class="thread-post-content">The behaviour of a block time of portMAX&#95;DELAY depends on the setting of INCLUDE&#95;vTaskSuspend&#40;&#41; in FreeRTOSConfig.h.&nbsp; If the configuration constant is set to 1, then portMAX&#95;DELAY will cause the task to block indefinitely.&nbsp; This means a function call that uses a block time of portMAX&#95;DELAY need not check the return type of the blocking function call, because if the call returns, the task is guaranteed that the event it was waiting for has occurred.&nbsp; For examples:  
<pre><code>xQueueReceive( xQueue, &amp;buffer, portMAX_DELAY );
ProceessReceivedData( buffer );
</code></pre>
is guaranteed to have something in buffer when ProcessReceivedData&#40;&#41; is called.  
If INCLUDE&#95;vTaskSuspend is set to 0, then portMAX&#95;DELAY is just a delay as any other.&nbsp; That means you have to check the return type of the blocking function call to determine if the function returned because the event occurred, or because the timeout occurred.&nbsp; Therefore you would write you code as follows:  
<pre><code>while( xQueueReceive( xQueue, &amp;buffer, portMAX_DELAY ) != pdPASS );
ProcessReceivedData( buffer );
</code></pre>
if you wanted to wait indefinitely, or  
<pre><code>xReturned = xQueueReceive( xQueue, &amp;buffer, portMAX_DELAY );
if( xReturned == pdTRUE )
{
    ProcessReceivedData( buffer );
}
</code></pre>
if you didn&#8217;t want to wait indefinitely.  
<blockquote>
  he one task that I was testing &#40;the one that was blocked for the entire 10 minutes&#41; is stuck in vListInsert&#40;&#41; 
</blockquote>
Have you checked the items on the following FAQ page:<br />
<a href="http://www.freertos.org/FAQHelp.html">http://www.freertos.org/FAQHelp.html</a>  
<blockquote>
  I&#8217;m guessing that&#8217;s why the other tasks stopped working, and I&#8217;m also assuming all my other tasks have stopped working too.&nbsp;
</blockquote>
It depends on which vListInsert&#40;&#41; you are talking about, but if it is one of the ones in tasks.c, if a task was spinning in it, then other tasks would not execute.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Change portMAX_DELAY to Lower Value</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/*anonymous">*anonymous</a> on August 13, 2012</div><div class="thread-post-content">I understand how the portMAX&#95;DELAY is supposed to work.&nbsp; My question is more related to choosing a different value for it, instead of 0xFFFFFFFF.&nbsp; Is this allowed?&nbsp; What impact will it have on how timeouts are handled?  
I&#8217;m mostly interested in verifying the FreeRTOS kernel behavior at the boundary condition where portMAX&#95;DELAY is reached.&nbsp; Are there test cases already written that verify this?&nbsp; If not, how would the test cases go about testing it, waiting for 50 days or modifying the portMAX&#95;DELAY value?  
I know that xQueueReceive&#40;&#41; is _supposed _ to be guaranteed not to return if you use portMAX&#95;DELAY, but I would like to see it with my own eyes &#40;preferably without waiting for 50 days&#41;.
</div></div><div class="thread-post"><h3 class="thread-post-title">Change portMAX_DELAY to Lower Value</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 13, 2012</div><div class="thread-post-content">This was tested and analysed quite extensively when SafeRTOS was created.&nbsp; Although that was some time ago the details of that part of the code has not changed.&nbsp; If you look back through the change history &#40;several years&#41; you may be able to identify the two version numbers where a change was made to correct a corner case that was not handled quite correctly &#40;that had about a one in several billion billion chance of occurring because it only happened when the tick count overflowed&#41;.&nbsp;&nbsp; The change history is <a href="http://www.FreeRTOS.org/History.txt.">http://www.FreeRTOS.org/History.txt.</a>  
With regards to manually modifying the tick count/delay periods:&nbsp; Static module tests are much easier because you can manually crank the tick count over at the fastest speed your computer can run, rather than having to wait the actual amount of time &#40;this is how most testing is done&#41;.&nbsp; If you want to manually change the tick count value then do it before you make the blocking call, so the wake time is relative to the &#40;manually&#41; modified tick count.&nbsp; I don&#8217;t see any reason why the tick count value could not be initialised to a high number rather than 0 in the first place &#40;writing without actually trying it&#41;.  
Regards.
