  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Exiting the Kernel </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wdawson61">wdawson61</a> on August 3, 2012</div><div class="thread-post-content">Hi.&nbsp; I have an arm cortex m3 &#40;lpc1758&#41; freeRTOS application that is a bootloader,&nbsp; It lives in low memory, runs on a FreeRTOS task , gets pristine hw out of reset then either programs some other memory in the system from a USB flash drive and drives a nifty LCD display OR executes a completely separate image with its own kernel and views on how things should be done.&nbsp; This OTHER body of code attempts to kill-off&nbsp; FreeRTOS&#8217;s ISRs &#40;PendSV, Systick, SVCALL&#41;, then installs it&#8217;s own set of handlers by moving the vector table, etc.&nbsp; This has been working until recently.&nbsp; Now I&#8217;m getting an InvPC Usage fault from the Cortex M3 when the other kernel tries to its context switching magic.&nbsp; If I trace the UsageFault via the stack frame, it points to FreeRTOS&#8217;s <strong>vPortYieldFromISR</strong>.&nbsp; Even though the OTHER body of code attempts to clear the <strong>pendsv</strong> and <strong>svcall</strong> pending bits the NVIC.&nbsp; My question is:  
How can I ensure that FreeRTOS is indeed done and will not have stacked exceptions to return to / from&nbsp; or any other other pending exceptions before I yank the exception vector table out from under it?  
Any help would be greatly appreciated as this is a difficult issue &#40;for me&#41; to debug&#33;&#33;  
-Wade
</div></div><div class="thread-post"><h3 class="thread-post-title">Exiting the Kernel </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on August 3, 2012</div><div class="thread-post-content">If you have actually moved the interrupt vector table, then the only way a FreeRTOS interrupt handler could execute after would be if you had copied the FreeRTOS handlers into your new vector table, or you moved the vector table from an interrupt that had nested with an already existing FreeRTOS handler.
