</div></div><div class="thread-post"><h3 class="thread-post-title">Richard:Bug in the LPC2000 port of FreeRTOS ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on August 24, 2012</div><div class="thread-post-content">Before Cortex-M took over, ARM7 was one of the most popular FreeRTOS targets, and this used to come up frequently &#40;eg <a href="http://www.freertos.org/FreeRTOS_Support_Forum_Archive/March_2009/freertos_taskYIELD_in_critical_section_3119904.html%29.">http://www.freertos.org/FreeRTOS&#95;Support&#95;Forum&#95;Archive/March&#95;2009/freertos&#95;taskYIELD&#95;in&#95;critical&#95;section&#95;3119904.html&#41;.</a>&nbsp; It is a long time since I have had to explain it, but needless to say this is not a bug but an essential part of the design for processor cores that perform yields using synchronous unmaskable software interrupts/yields.  
Each task has its own interrupt nesting count.&nbsp; Switching to a task that was not in a critical section will result in interrupts becoming enabled again while that task is running.&nbsp; Switching back to the task that was in a critical section when it yielded will result in interrupts becoming disabled again until the task exits the critical section it originally entered.&nbsp; This is essential because it is &#40;possibly&#41; going to need atomic access to the queue &#40;semaphore, mutex, whatever&#41; when it starts running and already assumes it is in a critical section.&nbsp; Were it to resume with interrupts disabled &#8211; it would have been a bug.  
Generally it is best not to mess with the core kernel code without asking first &#8211; the code is extremely robust &#8211; although obviously not infallible.

When you are in the office, look at the file Source/portable/RVDS/ARM7&#95;LPC21xx/portmacro.inc.&nbsp; It contains the portRESTORE&#95;CONTEXT macro that runs at the end of the yield function.&nbsp;   
In that macro, note the line that has the comment &#8220;Get the SPSR from the stack.&#8221; &#45; the interrupt enable bit is set in the PSR &#40;bit 7&#41;.&nbsp; When the task is created, the initial PSR that is put on the task&#8217;s stack is set to 0x1f &#40;System mode, with interrupts enabled&#41;.&nbsp; Step through the end of the yield function in the debugger when the task starts for the first time.&nbsp; When the instruction &#8220;LDMFD LR&#33;, &#123;R0&#125;&#8221; &#40;on the same line as the comment&#41; executes it should load this 0x1f from the task&#8217;s clean stack into R0, then executing the the following line &#8220;MSR SPSR&#95;cxsf, R0&#8221; should load this into the PSR register &#8211; ensuring interrupts are enabled the first time the task runs.&nbsp;   
If you are seeing any value other than 0x1f coming from the stack at that point then the task stack is corrupt before it even starts, and I suspect this is what is happening if the task really is empty.&nbsp;   
Calling any function that enters then exits a critical section, such as the queue function you mention, will cause interrupts to become enabled, so this is explainable.&nbsp; This is because the critical nesting count will be incremented when the critical section is entered and decremented when the critical section is exited &#8211; and having a zero nesting count will result in interrupts becoming enabled.  
Please let me know what you find.
