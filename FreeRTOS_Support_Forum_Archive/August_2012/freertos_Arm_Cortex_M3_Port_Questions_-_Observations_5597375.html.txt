  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Arm Cortex M3 Port Questions &#8211; Observations</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/toddatm">toddatm</a> on August 30, 2012</div><div class="thread-post-content">I&#8217;m fairly new to the Cortex M3 assembly language, but also new to FreeRTOS and was having a look at the function:  
void vPortStartFirstTask&#40; void &#41;<br />
&#123;<br />
&#95;&#95;asm volatile&#40;<br />
&#8221; ldr r0, =0xE000ED08 n&#8221; /&#42; Use the NVIC offset register to locate the stack. &#42;/<br />
&#8221; ldr r0,&nbsp; n&#8221;<br />
&#8221; ldr r0,&nbsp; n&#8221;<br />
&#8221; msr msp, r0 n&#8221; /&#42; Set the msp back to the start of the stack. &#42;/<br />
&#8221; cpsie i n&#8221; /&#42; Globally enable interrupts. &#42;/<br />
&#8221; svc 0 n&#8221; /&#42; System call to start first task. &#42;/<br />
&#8221; nop n&#8221;<br />
&#41;;<br />
&#125;  
I liked the idea of using the vector table location to grab the original stack location &#40;and plan to use this in my fault handlers to try and set the stack back to something useful&#41;.  
I&#8217;m wondering why&nbsp; is read twice in this function. Is that a typo? Or was there a purpose? Because I&#8217;m learning the assembly language and processor, this line confused me and I&#8217;m just wondering if there&#8217;s a subtle point about the processor I&#8217;m missing that might require the memory to be read twice &#40;or some timing thing going on&#41;.  
Second question &#40;or maybe this is just a comment&#41; is about the &#8220;cpsie i&#8221; instruction. I was surprised to find out that the default for this bit is that interrupts are enabled. &#40;Most processors come up with interrupts blocked, and it surprised me that i and f are both unmasked&#41;. All the ports I took a look at set this even though it appears the power-on default is enabled for this bit and it&#8217;s not needed &#40;unless, I suppose, some user code might have disabled it early on&#41;.  
Finally, the comments that goes along with the functions &#95;&#95;enable&#95;fault&#95;irq&#40;&#41; and &#95;&#95;disable&#95;fault&#95;irq&#40;&#41; &#40;which enable/disable the FAULTMASK&#41; I found are probably cut/paste errors from another Arm port perhaps? The comments mention FIQ, which the Cortex doesn&#8217;t have but as I remember other Arm processors do have.  
Minor issues, but as I&#8217;m new and learning, I was interested in seeing if I have something wrong.  
Thanks.

</div></div><div class="thread-post"><h3 class="thread-post-title">Arm Cortex M3 Port Questions &#8211; Observations</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on August 31, 2012</div><div class="thread-post-content">Calling FreeRTOS API functions before the scheduler has started will deliberately leave interrupts disabled to make sure interrupts don&#8217;t use the scheduler functionality before it is ready. It does not use the global interrupt mask though, only basepri. Calling SVC with global interrupts disabled will cause a fault though, so I guess the cpsie instruction just ensures the application or start up code has not disabled interrupts before it calls svc.
