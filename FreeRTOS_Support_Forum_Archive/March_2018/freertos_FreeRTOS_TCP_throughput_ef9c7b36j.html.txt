The values look good.
I suppose you have set the socket options before calling accept()?
All settings will be inherited by the child sockets.
Could you post a (well zipped) PCAP file that show the TCP conversation?
You may want to try out an <strong>iperf3 server</strong> ( see here below ).
I would recommend to add these IPERF settings to your FreeRTOSIPConfig.h :
~~~
<h1>define ipconfigIPERF_VERSION                   3</h1>
<h1>define ipconfigIPERF<em>STACK</em>SIZE<em>IPERF</em>TASK     680</h1>
<h1>define ipconfigIPERF<em>DOES</em>ECHO_UDP             0</h1>
<h1>define ipconfigIPERF<em>TX</em>BUFSIZE                ( 24 * ipconfigTCP_MSS )</h1>
<h1>define ipconfigIPERF<em>TX</em>WINSIZE                ( 12 )</h1>
<h1>define ipconfigIPERF<em>RX</em>BUFSIZE                ( 24 * ipconfigTCP_MSS )</h1>
<h1>define ipconfigIPERF<em>RX</em>WINSIZE                ( 12 )</h1>
/* The iperf module declares a character buffer to store its send data. */
<h1>define ipconfigIPERF<em>RECV</em>BUFFER<em>SIZE          ( 12 * ipconfigTCP</em>MSS )</h1>
~~~

Oops. I left that question unfinished: I wanted to ask you if your LAN is quiet enough to leave space for your iperf data? My own LAN was 99% available during the test.
About the PCAP that I attached: you will see that about every 10 packets receive an ACK. That is why I wrote that a TCP-Window size of 10 x 1.46 KB would be enough. Here is an example of a TCP Window size of 12 packets:
~~~
    #define ipconfigIPERF<em>TX</em>BUFSIZE   ( 24 * ipconfigTCP<em>MSS )  /* Units of bytes. */
    #define ipconfigIPERF</em>TX<em>WINSIZE   ( 12 )                    /* Size in units of MSS */
    #define ipconfigIPERF</em>RX<em>BUFSIZE   ( 24 * ipconfigTCP</em>MSS )  /* Units of bytes. <em>/
    #define ipconfigIPERF_RX_WINSIZE   ( 12 )                    /</em> Size in units of MSS */
~~~
No one can guarantee a constant high TCP throughput. If you write the application for both sides, I would consider using UDP in stead.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP throughput</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on April 13, 2018</div><div class="thread-post-content">When you use the -R option, it means that Zynq is sending data. That gives a good performance. If your application mostly sends from the device to the outside world, that is very good news.
When you omit the -R option, the Zynq receives data and it is more dependent on the speed of its partner. In your test you only get an average speeds of 260 Mbps:
[ 4] 0.00-1.00 sec 30.6 MBytes 257 Mbits/sec
[ 4] 1.00-2.00 sec 31.6 MBytes 265 Mbits/sec
If your embedded device mostly receives data, you may also want to optimise the software on your host&#8230; if that is possible.
Does your embedded application mostly send or mostly receive data?
There are many techniques to optimise TCP-communication. You can have a look in the iperf module, or the project under &#8220;protocols&#8221;, such as the FTP server.
If it is possible, can you post some code that sends/receives the &#8216;bulk&#8217; TCP data? You can also send it to the email address that I mentioned here above.
