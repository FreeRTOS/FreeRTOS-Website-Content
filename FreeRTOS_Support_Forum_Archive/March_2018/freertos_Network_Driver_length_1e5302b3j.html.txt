  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Network Driver length</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jeronimo479">jeronimo479</a> on March 9, 2018</div><div class="thread-post-content">On the webpage [(http://https://www.freertos.org/FreeRTOS-Plus/FreeRTOS<em>Plus</em>TCP/Embedded<em>Ethernet</em>Porting.html#creating<em>a</em>simple<em>network</em>interface<em>port</em>layer)]
The porting instructions for moving a packet from the MAC receive bufer and pushing it onto the IP stack shows:
~~~
&#8230;
if( xBytesReceived > 0 ){
        pxBufferDescriptor = pxGetNetworkBufferWithDescriptor( xBytesReceived, 0 );
        if( pxBufferDescriptor != NULL ){<br />
                ReceiveData( pxBufferDescriptor->pucEthernetBuffer );
                pxBufferDescriptor->xDataLength = xBytesReceived;
&#8230;<br />
~~~
I don&#8217;t understand why I would include  &#8220;pxBufferDescriptor->xDataLength = xBytesReceived;&#8221;. 
When I call pxGetNetworkBufferWithDescriptor(), it allocates memory and writes the actual packet length. If I set it myself after calling pxGetNetworkBufferWithDescriptor(), it migth not be right.
Thoughts?
</div></div><div class="thread-post"><h3 class="thread-post-title">Network Driver length</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 9, 2018</div><div class="thread-post-content">I see what you mean.
Have you ever seen the first and second setting of ->xDataLength being 
different?
In the code you past ReceiveData() is use the length of the allocated 
buffer, which may not be the same as xBytesReceived (it should always be 
equal to or greater than xBytesReceived, never smaller).  ->xDataLength 
might then be set to xBytesReceived so the TCP stack knows how many 
bytes within the allocated buffer actually contain data.
</div></div><div class="thread-post"><h3 class="thread-post-title">Network Driver length</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jeronimo479">jeronimo479</a> on March 9, 2018</div><div class="thread-post-content">The comments in the BufferAllocation_2.c code that supports pxGetNetworkBufferWithDescriptor(), show that in some outgoing packets, it accounts for ICMP packets getting replaced by ARP requests, and therefore, the packet minimum sisze is adjusted. But for incoming packets, I can&#8217;t see any reason for this, and I&#8217;m new to +TCP so I don&#8217;t have enough experience.
</div></div><div class="thread-post"><h3 class="thread-post-title">Network Driver length</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 10, 2018</div><div class="thread-post-content"><blockquote>
  The comments in the BufferAllocation_2.c code that supports
  pxGetNetworkBufferWithDescriptor(), show that in some outgoing
  packets, it accounts for ICMP packets getting replaced by ARP
  requests, and therefore, the packet minimum size is adjusted.
</blockquote>
ARP packets are the smallest packets with 42 bytes. So changing an ICMP into an ARP packet is OK, it is getting smaller. Only when an Ethernet buffer grows, it must be re-allocated (when <code>using BufferAllocation_2.c</code>).
<blockquote>
  But for incoming packets, I can&#8217;t see any reason for this, and I&#8217;m
  new to +TCP so I don&#8217;t have enough experience.
</blockquote>
If <code>ipconfigFTP_RX_ZERO_COPY</code> is non-zero: incoming packets are received in Ethernet buffers that have a maximum size of about MTU + 14.
When the Network Interface uses <code>memcpy()</code>, it has big DMA buffers, and for the Ethernet buffers, it allocates just enough bytes to hold a packet.  Still, <code>baMINIMAL_BUFFER_SIZE</code> is always respected as a minimum size.
Does this answer your question?
