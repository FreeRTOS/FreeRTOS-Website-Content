  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Counting semaphore sleep until a specific count</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/unknowcoder">unknowcoder</a> on March 5, 2018</div><div class="thread-post-content">Hello,
Is there anyway to have a counting semaphore block until a specific count is available? I can do this manually by implementing a timer to sleep and periodically wake to check the count.
I have a scenario where multiple task can process messages but each consumer has a special algorithm that looks for different data pattern. One of the task can only process the buffer when it&#8217;s completely full. Therefore I want to block on the counting semaphore at which point when the buffer is completely full only then can I take a look at the buffer and try to extrapolate data.
Also when the task which needs the entire buffer is processing it it needs to take every single semaphore in one go. If the task doesn&#8217;t do this then other task can try processing parts of the buffer but I don&#8217;t want this. If the algorithm that is looking at the entire buffer finds a pattern that pattern must be processed as it&#8217;s more critical.
<strong>A little background</strong>
The buffer isn&#8217;t really a single message it&#8217;s a machine learning algorithm that uses an FPGA that hands off information to a the GPP. The GPP has multiple consumer but one of the consumer can only make good prediction if all the data is there. There other consumer which uses variants of the same algorithm to predict special cases.
</div></div><div class="thread-post"><h3 class="thread-post-title">Counting semaphore sleep until a specific count</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 5, 2018</div><div class="thread-post-content">The short answer is no, there is no way of setting a &#8216;trigger level&#8217; on a counting semaphore.  
FreeRTOS V10 introduced stream buffers, which do have a trigger level, but are very light weight and can only have a single reader and a single writer (which could be an interrupt).  Perhaps you could refactor to use a stream buffer and a managemet task &#8211; the management task looking for whatever patterns are necessary and then unblocking which ever task needs to process the discovered pattern?
</div></div><div class="thread-post"><h3 class="thread-post-title">Counting semaphore sleep until a specific count</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/unknowcoder">unknowcoder</a> on March 8, 2018</div><div class="thread-post-content">Hi Richard, 
Would this cause any issue if I add the following feature to the counting semaphore
* Check the count if the count is exactly equal to max set the uxMessagesWaiting = 0
* The code will look very similiar to uxQueueMessagesWaiting()
* It will also have a method to set it back. 
* Thoughts on this?
Actually to be clear this is making the counting semaphore work as a binary semaphore in specific task.
~~~
    taskENTER<em>CRITICAL();
    {
        uxReturn = ( ( Queue</em>t * ) xQueue )->uxMessagesWaiting;
        if(MAX<em>COUNT == uxReturn)
        {
            ( ( Queue</em>t * ) xQueue )->uxMessagesWaiting = 0;
        }
    }
    taskEXIT_CRITICAL();
~~~
