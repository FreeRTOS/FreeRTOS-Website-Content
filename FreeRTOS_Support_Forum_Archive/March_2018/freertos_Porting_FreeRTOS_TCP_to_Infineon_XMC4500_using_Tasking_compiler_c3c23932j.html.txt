</div></div><div class="thread-post"><h3 class="thread-post-title">Porting FreeRTOS+TCP to Infineon XMC4500 using Tasking compiler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 26, 2018</div><div class="thread-post-content">Hi Mark,
<blockquote>
  When the task starts its sends out the ARP request with
  corrupted ARP packets.
  The IP address is 192.168.0.200. But when the processor sends an
  ARP request in wireshark its shows as 0.209.192.168.
</blockquote>
It looks to me like the PACKED attribute doesn&#8217;t work correctly for your compiler.
Have a look at <code>FreeRTOS_IP_Private.h</code> :
~~~
    #include &#8220;pack<em>struct</em>start.h&#8221;
    struct xARP<em>PACKET
    {
        EthernetHeader</em>t xEthernetHeader;  /*  0 + 14 = 14 <em>/
        ARPHeader_t xARPHeader;            /</em> 14 + 28 = 42 */
    }
    #include &#8220;pack_struct_end.h&#8221;
    typedef struct xARP_PACKET ARPPacket_t;
~~~
The above declaration should result in a struct that is 42 bytes long. It is being verified in FreeRTOS_IP.c, in case you have <code>configASSERT()</code> defined.
It looks to me like the compiler has increased the size of <code>xEthernetHeader</code> to 16 bytes.
Can you check that please?

</div></div><div class="thread-post"><h3 class="thread-post-title">Porting FreeRTOS+TCP to Infineon XMC4500 using Tasking compiler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 28, 2018</div><div class="thread-post-content">PS. Have you read <a href="https://www.freertos.org/FreeRTOS_Support_Forum_Archive/May_2016/freertos_About_ipBUFFER_PADDING_and_ipconfigPACKET_FILLER_SIZE_b762e48bj.html">this post</a> already? It talks about the +2 byte offset (<code>ipconfigPACKET_FILLER_SIZE</code>) of all Ethernet packets.
<blockquote>
  The data type changed from uint32<em>t to uint8</em>t array is the problem.
</blockquote>
We did that because <code>SenderProtocolAddress</code> was positioned at an unaligned address.
<blockquote>
  After changing back and fixing the packing now it works
</blockquote>
I think that many people are curious about the details: what did you change back and how did you fix the packing attribute for the Tasking compiler?
<blockquote>
  But its adding 2 bytes extra in the last. Instead of replying
  with 74 bytes it sends out 76 bytes now.
</blockquote>
And is the contents correct, or do you see a 2 bytes inserted at the beginning?
Do you have <code>ipconfigETHERNET_MINIMUM_PACKET_BYTES</code> defined?
Ethernet packets must be at least 60 bytes long. It would surprise me that the minimum in your CPU is set at 76 bytes.
</div></div><div class="thread-post"><h3 class="thread-post-title">Porting FreeRTOS+TCP to Infineon XMC4500 using Tasking compiler</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 29, 2018</div><div class="thread-post-content"><blockquote>
  I was thinking same and verified it before and the compiler packs to correct size:
  FreeRTOS<em>IPInit
  FreeRTOS</em>IPInit: EthernetHeader<em>t size: 14
  FreeRTOS</em>IPInit: ARPHeader<em>t size: 28
  FreeRTOS</em>IPInit: IPHeader_t size: 20
</blockquote>
And does <code>ARPPacket_t</code> get a correct size of 42 bytes?
Do you have <code>configASSERT()</code> defined?
Do you have logging enabled, using the following in <code>FreeRTOSIPConfig.h</code>:
~~~
<h1>define ipconfigHAS_PRINTF          1</h1>
<h1>define FreeRTOS_printf(X)          serialPrintf X</h1>
<h1>define ipconfigHAS<em>DEBUG</em>PRINTF    1</h1>
<h1>define FreeRTOS<em>debug</em>printf(X)    serialPrintf X</h1>
~~~
Where <code>serialPrintf()</code> is just an example and could look like this:
~~~
    extern void serialPrintf( const char *pcFormat, &#8230; );
~~~
<blockquote>
  One more think I noticed that in 10.1 the
  struct xARP<em>HEADER
  {
  &#8230;..
  uint8</em>t ucSenderProtocolAddress[ 4 ];
  &#8230;.
  }
  is changed from uint32_t to above data type. I think this may
  be making the compiler behave bad while doing the memcpy.
</blockquote>
We did see unexpected behaviour with the GCC compiler which were &#8216;solved&#8217; by either using the <code>-fno-builtin-memcpy</code> or the <code>-mno-unaligned-access</code> compiler option.
In what way is your compiler behaving &#8216;badly&#8217;?
<blockquote>
  Can you help me on the FreeRTOS 9 not sending reply to the ping
  command please.
</blockquote>
Try to follow what is happening. Does the PING arrive well? Without a 2-byte offset?
Is it analysed well in FreeRTPS_IP.c ? Does <code>prvProcessICMPPacket()</code> get called? Is an answer being sent?
Are the CRC&#8217;s calculated for outgoing packets, either in the library, or by the MAC peripheral?
Please check <code>ipconfigDRIVER_INCLUDED_TX_IP_CHECKSUM</code>
