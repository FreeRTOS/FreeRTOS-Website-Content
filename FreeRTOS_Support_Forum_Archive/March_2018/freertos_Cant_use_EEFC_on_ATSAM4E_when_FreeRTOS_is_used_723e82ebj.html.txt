I am using the ARM_CM4F port of FreeRTOS 10.0.0.0 and static memory allocation. To get started, I am creating a single task in FreeRTOS that does everything. So the only FreeRTOS API calls I make are one call to xTaskCreateStatic() followed by a call to vTaskStartScheduler(). I have conditional code in my application so that I can compile with or without FreeRTOS.
When I compile without FreeRTOS, the code works (and has done so for many months).
When I compile with FreeRTOS,  the code hangs when it tries to call Atmel Software Framework functions that access the EEFC (flash controller peripheral). For example, I have this code in the application startup sequence:
<pre><code>cpu_irq_disable();
const uint32_t rc = flash_read_unique_id(uniqueId, 4);
cpu_irq_enable();
</code></pre>
Function flash<em>read</em>unique<em>id calls a RAMFUNC that accesses the EEFC. Disabling interrupts is necessary to prevent code in flash being executed due to an interrupt (in particular, SysTick) while the call is in progress. With FreeRTOS enabled (so that the code executes in the task), it hangs in that code. If I replace the call to flash</em>read<em>unique</em>id by the constant 1 then the code doesn&#8217;t hang, the initialisation completes and the firmware runs normally &#8211; until I do something that makes it try to use the EEFC again.
Any ideas? I tried replacing cpu<em>irq</em>disable/enable calls  by taskENTER<em>CRITICAL/EXIT</em>CRITICAL but it made no difference. I also tried varying the stack size &#8211; but as the code runs perfectly as long as I don&#8217;t access the EEFC and the flash functions use very little stack, it can&#8217;t be due to stack overflow anyway.

that RAM is not recoverable after the scheduler has started &#8211; it does 
mean you loose any variables declared in main() though but there is no 
way of returning to main() anyway.

</div></div><div class="thread-post"><h3 class="thread-post-title">Can&#8217;t use EEFC on ATSAM4E when FreeRTOS is used</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/dcrocker">dcrocker</a> on March 27, 2018</div><div class="thread-post-content">I found a solution. I noticed that the corruption matched the last 3 parameters passed to  xTaskCreateStatic(). So it occurred to me that the compiler might be storing those parameters at the start of RAM instead of on the stack. I had declared the function that calls xTaskCreateStatic() and vTaskStartScheduler() with attribute &#8220;naked&#8221; on the grounds that it never returns, therefore it doesn&#8217;t need to save/restore any registers. I removed the &#8220;naked&#8221; attribute and the corruption is gone. I guess I don&#8217;t completely understand what that attribute does.
</div></div><div class="thread-post"><h3 class="thread-post-title">Can&#8217;t use EEFC on ATSAM4E when FreeRTOS is used</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 28, 2018</div><div class="thread-post-content">Thanks for reporting back.
Using the naked attribute will prevent the compiler from inserting any 
function prelude code &#8211; the asm code that executes to set up a stack 
from before any of the function&#8217;s C code executes.  That is definitely a 
bad thing if any stack is used at all, which is will be in the function, 
as stack accesses are then basically uninitialised.
