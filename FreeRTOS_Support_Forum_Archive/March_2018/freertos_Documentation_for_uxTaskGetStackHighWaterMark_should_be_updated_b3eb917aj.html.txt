  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jankok">jankok</a> on March 14, 2018</div><div class="thread-post-content">At https://www.freertos.org/uxTaskGetStackHighWaterMark.html it gives the return type as UBaseType<em>t, however, at least in Amazon&#8217;s portmacro.h, UBaseType</em>t is typedef&#8217;d as unsigned char. This caused me considerable puzzlement when I increased the initial stack size for a task and it caused the reported high water mark to <em>decrease</em>, as the high water mark number rolled over from 255 to 0.
Amazon&#8217;s portmacro.h for Arduino contains:
~~~
<h1>define portSTACK<em>TYPE  uint8</em>t</h1>
typedef portSTACK<em>TYPE StackType</em>t;
typedef signed char BaseType<em>t;
typedef unsigned char UBaseType</em>t;
~~~
and FreeRTOSconfig.h contains:
~~~
<h1>define configMINIMAL<em>STACK</em>SIZE            ( ( portSTACK_TYPE ) 192 )</h1>
<h1>define configSTACK<em>DEPTH</em>TYPE              uint16_t</h1>
~~~
Does this look correct? It looks odd to me since portSTACK<em>TYPE ends up defined as uint8</em>t, which might cause problems if one were to try to increase configMINIMAL<em>STACK</em>SIZE beyond 255.
In any case, it seems to me the documentation for uxTaskGetStackHighWaterMark should be updated to show some other return type.
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 14, 2018</div><div class="thread-post-content">This has been discussed multiple times, so you will find info in the 
forum.  Some changes were made in V10 to allow you to use a different 
data type &#8211; I think using vTaskGetInfo() rather than 
uxTaskGetStackHighWaterMark().
<blockquote>
  In any case, it seems to me the documentation for 
  uxTaskGetStackHighWaterMark should be updated to show some other return 
  type.
</blockquote>
As can be seen in the header file and the source file, the prototype for 
the function is:
UBaseType<em>t uxTaskGetStackHighWaterMark( TaskHandle</em>t xTask );
So the return type is shown correctly in the documentation.  The &#8216;base 
type&#8217; is the natural (most efficient) type for the architecture so is 
different in different ports &#8211; normally 32-bits &#8211; but not on an AVR.
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jankok">jankok</a> on March 14, 2018</div><div class="thread-post-content">Well, task.h shows
~~~
<h1>if configENABLE<em>BACKWARD</em>COMPATIBILITY == 1</h1>
UBaseType<em>t uxTaskGetStackHighWaterMark( TaskHandle</em>t xTask ) PRIVILEGED_FUNCTION;
<h1>else</h1>
configSTACK<em>DEPTH</em>TYPE uxTaskGetStackHighWaterMark( TaskHandle<em>t xTask ) PRIVILEGED</em>FUNCTION;
<h1>endif /* configENABLE<em>BACKWARD</em>COMPATIBILITY */</h1>
~~~
So the return type depends on whether configENABLE<em>BACKWARD</em>COMPATIBILITY == 1. In the Arduino FreeRTOS library, configENABLE<em>BACKWARD</em>COMPATIBILITY is not defined at all, so the return type is configSTACK<em>DEPTH</em>TYPE which is uint16_t. And indeed the function can return a value greater than 255. I&#8217;ve tested it.
The documentation says the return type is UBaseType_t, but that&#8217;s not true for the Arduino port, and that can lead users like me to get nonsensical values for the high water mark, when taking the usage example code for uxTaskGetStackHighWaterMark at face value.
Should portSTACK<em>TYPE , BaseType</em>t and UBaseType_t be defined as 16-bit types in the Arduino port? If not, I think the documentation for uxTaskGetStackHighWaterMark should be updated to warn about the confusing type issues.
In any case, thanks for the help, Richard, and thanks for making FreeRTOS available to the world &#8211; for free! 🙂
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 14, 2018</div><div class="thread-post-content"><blockquote>
  Well, task.h shows
  <h1>if configENABLE<em>BACKWARD</em>COMPATIBILITY == 1</h1>
  UBaseType<em>t uxTaskGetStackHighWaterMark( TaskHandle</em>t xTask ) PRIVILEGED_FUNCTION;
  <h1>else</h1>
  configSTACK<em>DEPTH</em>TYPE uxTaskGetStackHighWaterMark( TaskHandle<em>t xTask ) PRIVILEGED</em>FUNCTION;
  <h1>endif /* configENABLE<em>BACKWARD</em>COMPATIBILITY */</h1>
  So the return type depends on whether 
  configENABLE<em>BACKWARD</em>COMPATIBILITY == 1. In the Arduino FreeRTOS 
  library, configENABLE<em>BACKWARD</em>COMPATIBILITY is not defined at all, so 
  the return type is configSTACK<em>DEPTH</em>TYPE which is uint16_t. And indeed 
  the function can return a value greater than 255. I&#8217;ve tested it.
</blockquote>
Curious &#8211; I think if configENABLE<em>BACKWARD</em>COMPATIBILITY is not defined 
at all then it will default to 1.  We always try to ensure FreeRTOS 
versions default to being backward compatible to ensure upgrading is 
easy.  If that is the case then uxTaskGetStackHighwaterMark() should 
have a return type of UBaseType<em>t &#8211; are you 100% positive 
configENABLE</em>BACKWARD_COMPATIBILITY is not defined anywhere in your 
application?
<blockquote>
  Should portSTACK<em>TYPE , BaseType</em>t and UBaseType_t be defined as 16-bit 
  types in the Arduino port? 
</blockquote>
No &#8211; portSTACK_TYPE is dictated by the architecture, you can&#8217;t choose a 
value for it as if it is wrong the code just won&#8217;t work.
The base type is set to the &#8216;natural&#8217; size of the architecture to ensure 
it is as efficient as possible and is predominantly used for booleans, 
rather than holding values.  uxTaskGetStackHighWaterMark() returning 
such a value is a symptom of FreeRTOS being 15 years old.
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jankok">jankok</a> on March 14, 2018</div><div class="thread-post-content"><blockquote>
  Curious &#8211; I think if configENABLE<em>BACKWARD</em>COMPATIBILITY is not defined 
  at all then it will default to 1.
</blockquote>
Aparently not. According to http://gcc.gnu.org/onlinedocs/cpp/If.html#If , in the expression part of a #if, &#8220;Identifiers that are not macros &#8230; are all considered to be the number zero.&#8221;
I grepped for COMPATIBILITY in the Arduino library src directory and didn&#8217;t see any definitions of configENABLE<em>BACKWARD</em>COMPATIBILITY. So the #if is interpreting it as 0.
I think we can agree that in a processor that can have more than 255 words of stack space, the return type of the function should not be an 8-bit type. So, what should the return type of the function be?
My suggestion is to cut the Gordian knot, keep it simple, define it as just:
configSTACK<em>DEPTH</em>TYPE uxTaskGetStackHighWaterMark( TaskHandle<em>t xTask ) PRIVILEGED</em>FUNCTION;
Forget about configENABLE<em>BACKWARD</em>COMPATIBILITY. It seems to me the purpose of that is to avoid problems for users of ancient code <em>if they update to a newer version of the FreeRTOS library</em>. If they don&#8217;t update, there should be no problem. If they do update, having them define configSTACK<em>DEPTH</em>TYPE seems like a small price to pay. You could add code like this before the declaration of uxTaskGetStackHighWaterMark in task.h:
~~~
<h1>ifndef configSTACK<em>DEPTH</em>TYPE</h1>
<pre><code>#error Missing definition:  configMAX_STACK_DEPTH_TYPE must be defined in FreeRTOSConfig.h.  See the Configuration section of the FreeRTOS API documentation for details.
</code></pre>
<h1>endif</h1>
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 14, 2018</div><div class="thread-post-content">It should be defaulted in FreeRTOS.h &#8211; see line 867 (at the time of 
writing) here: 
https://sourceforge.net/p/freertos/code/HEAD/tree/trunk/FreeRTOS/Source/include/FreeRTOS.h#l4
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jankok">jankok</a> on March 15, 2018</div><div class="thread-post-content">All right, so I guess you&#8217;re saying that ports to processors, where UBaseType_t is not large enough to hold a stack size value, should include
~~~
<h1>define configENABLE<em>BACKWARD</em>COMPATIBILITY 0</h1>
<h1>define configSTACK<em>DEPTH</em>TYPE              uint16_t // or whatever</h1>
~~~
in FreeRTOSConfig.h. The latest Arduino FreeRTOS library FreeRTOSConfig.h contains the second line but not the first. Arduino<em>FreeRTOS.h is V10.0.0 and doesn&#8217;t contain the code to default configENABLE</em>BACKWARD_COMPATIBILITY to 1 if undefined.
I guess I can live with that. However, I still think  https://www.freertos.org/uxTaskGetStackHighWaterMark.html should be updated, because if someone copies the example usage code, while using an AVR or similar processor, the results won&#8217;t make sense if the high water mark is greater than 255. I got bitten by that, and that&#8217;s why I came here and started this thread!
(I was having problems that I thought might be due to some sort of memory corruption. I tried investigating stack space using the example code in that web page. I started going crazy because increasing the allocated stack space could sometimes <em>decrease</em>  the high water mark, and I never could get the high water mark very large. It was only when I tried seeing exactly how large I could make it, and I increased the stack space by 1 and saw the high water mark go from 255 to 0, that a light bulb turned on and I realized that the high water mark was somehow getting truncated to 8 bits.)
</div></div><div class="thread-post"><h3 class="thread-post-title">Documentation for uxTaskGetStackHighWaterMark should be updated?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/jankok">jankok</a> on March 20, 2018</div><div class="thread-post-content">Rick Richard ran into the same problem, see https://sourceforge.net/p/freertos/discussion/382005/thread/335d645d/
The problem occurs on processors where sizeof(UBaseType<em>t) != sizeof(configSTACK</em>DEPTH<em>TYPE). For example on an 8-bit AVR processor, the stack can grow one byte at a time, but the stack can have more than 255 elements, so UBaseType</em>t is defined as uint8<em>t and configSTACK</em>DEPTH<em>TYPE is defined as uint16</em>t.
I think the simplest solution that would maintain backward compatibility with existing user&#8217;s code, would be to change the return type of uxTaskGetStackHighWaterMark to be configSTACK<em>DEPTH</em>TYPE, and then default the value of configSTACK<em>DEPTH</em>TYPE to be UBaseType<em>t if configSTACK</em>DEPTH_TYPE is not defined in FreeRTOSConfig.h.
In any case, the documentation for uxTaskGetStackHighWaterMark should be updated to show the correct return type, so users don&#8217;t keep tripping over this problem. Would you like me to file this as a bug?
