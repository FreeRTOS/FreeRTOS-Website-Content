  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Analysing tasks management and priorities </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xavierpacheco">xavierpacheco</a> on March 11, 2018</div><div class="thread-post-content">A task has been created that reads a value of the ADC of a temperature sensor of a battery every 100 ms, calculate the value of it from the reading and update the value of a variable with it. My first iteration of the routine is as follows:
`#define DELAY<em>TICKS 100 // tick period 1 ms => 100 ms delay 
volatile float battery</em>temperature; 
void temperature_task(void* parameters) { 
TickType<em>t current</em>tick<em>count, expired</em>tick_count; 
while (1) { 
// Read ADC 
unsigned short adc<em>value = read</em>temperature_adc(); 
// Compute temperature 
float temperature = compute<em>temperature(adc</em>value); 
// Update variable 
battery_temperature = temperature; 
// Get current system tick count and compute expired count 
current<em>tick</em>count = xTaskGetTickCount(); 
expired<em>tick</em>count = current<em>tick</em>count + DELAY<em>TICKS; 
// Wait until the number of ticks has happen (100 ms) 
while (xTaskGetTickCount() &lt; expired</em>tick_count) {} } }`
Once incorporated into the system, other tasks have begun to have problems because they are receiving less processing time, and even one of them has stopped working completely.
The task has been created with &#8220;normal&#8221; priority and the tick of the system is 1 ms (time of change between concurrent tasks). And the function to read the ADC works waiting for the reading, but it only takes a few nanoseconds and is not considered to impact the system, like the routine that computes the temperature.
So these are my questions:
What happens with tasks that have been receiving less processing time, but still running? Specifically about their priority and the way they use their time.
What happened to the task that has stopped running completely?
What is the problem that I have caused with my routine and how can I solve it? 
P.D.:  I&#8217;m using FreeRTOS Cortex M3
</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 11, 2018</div><div class="thread-post-content">In this loop:
~~~
    while (xTaskGetTickCount() &lt; expired<em>tick</em>count) {
    }
~~~
your task consumes all CPU time, depending on it priority.
Please have a look at <a href="https://www.freertos.org/vtaskdelayuntil.html">vTaskDelayUntil()</a>
and <a href="https://www.freertos.org/a00127.html">vTaskDelay()</a>
</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xavierpacheco">xavierpacheco</a> on March 11, 2018</div><div class="thread-post-content">But, if that loop consumes all CPU time, how can other tasks still execute? 
</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 11, 2018</div><div class="thread-post-content">That is a very good question! I thought about it while I composed my answer here above.
The loop doesn&#8217;t block in any way, so that task is non-stop <strong>runnable</strong>.
As long as a task with priority P is runnable, only tasks of priority P and higher will run.
These three defines determine the behaviour of the FreeRTOS scheduler:
~~~
    configUSE<em>PREEMPTION
    configUSE</em>TIME<em>SLICING
    configIDLE</em>SHOULD_YIELD
~~~
I think you find good documentation <a href="https://freertos.org/Documentation/RTOS_book.html">here</a>. Although it might not be up-to-date with the latest newest 10.x release.  The principles of FreeRTOS scheduling have never changed.  &#8230; as far as I know.
I can answer your question, but then I&#8217;d have to see your code, most importantly <code>FreeRTOSConfig.h</code>, and also the priorities of the other tasks, and see if and how they block.
About timing: note that <code>TickType_t</code> is a 32-bit number. It will overflow, and also this calculation will, some day, overflow:
~~~
    expired<em>tick</em>count = current<em>tick</em>count + DELAY_TICKS; 
~~~
When it overflows, your timing will be incorrect.
<a href="https://www.freertos.org/xTaskCheckForTimeOut.html">Here</a> you find safe method, along with an example.
Regards,

</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 11, 2018</div><div class="thread-post-content"><blockquote>

It looks like the other tasks have an equal priority and thus there is time-slicing.
But before guessing more, I&#8217;d like to see your <code>FreeRTOSConfig.h</code>, and also the priorities of all tasks, and see if they block.
</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on March 11, 2018</div><div class="thread-post-content">Assuming you have the proper options enable in FreeRTOSConfig.H, task of the same priority will time share in a round robbin fashion, switching which ready task will run on each Tick interrupt. If the other task do something to block, then they will give up the processor, and this task will eventually get run, and continue until the next Tick.
</div></div><div class="thread-post"><h3 class="thread-post-title">Analysing tasks management and priorities </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/xavierpacheco">xavierpacheco</a> on March 11, 2018</div><div class="thread-post-content">The problem is about guessing, because the approach doesn&#8217;t give more information. That&#8217;s all it says. That&#8217;s a problem that I found in an article and I was interested in analysing it. So, we can guess what it sounds more reasonable. As you say, we can assume that other tasks have same priorities. But, as the problem says, there is a task that stopped executing, so it has to be the iddle task. So, as the ADC task doesn&#8217;t block, the only way that other tasks are able to execute, is either if they have higher priorities and they block or if they have the same priorities and don&#8217;t block, so there is time-slicing and that&#8217;s why they receive less time than the ADC task.  
Is it my approch good?
Now, the way to solve this is replacing the while loop with a TaskDelay or TaskDelayUntil function.
