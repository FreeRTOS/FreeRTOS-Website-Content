  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTimerStart API documentation weak point</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/phil-uulm">phil-uulm</a> on February 1, 2019</div><div class="thread-post-content">Hello Documentation Writers,
the API documentation of xTimerStart(&#8230;) says:
&#8220;&#8230; Starting a timer ensures the timer is in the active state. &#8230;&#8221;
This is really misleading because &#8220;ensures&#8221; wrongly insinuates the timer to have been started before the completion of the call  xTimerStart(&#8230;).
In the Return-Section it says:
&#8220;&#8230; When the command is actually processed will depend on the priority of the timer service/daemon task relative to other tasks in the system, although the timers expiry time is relative to when xTimerStart() is actually called.&#8221;
This is really contradicting.
Instead the above sentence should read somthing like:
&#8220;Starting a timer ensures the timer is in the active state only if the priority of the service/deamon task is the highest in the system.&#8221;
Other software timer related API documentation may be affected in the same way.
Could you consider making the documentation more explicit in that matter?
Thank you very much,
Philipp
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerStart API documentation weak point</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 1, 2019</div><div class="thread-post-content">Hi &#8211; sorry if you found this wording confusing.
<blockquote>
  &#8220;&#8230; Starting a timer ensures the timer is in the active state. &#8230;&#8221;
</blockquote>
I think this line is meant to indicate that when a timer is started, it 
will be in the active state, not necessarily that the timer is started 
immediately (as you point out, that depends on the priority of the timer 
task).  I will have a look to see if it can be clearer.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTimerStart API documentation weak point</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/phil-uulm">phil-uulm</a> on February 1, 2019</div><div class="thread-post-content">Hello Richard,
if there is a difference between &#8220;started&#8221; and &#8220;active&#8221; the naming of 
xTimerIsTimerActive(&#8230;)
is also misleading.
We were surprised to discover, that a xTimerIsTimerActive(&#8230;) might return pdFALSE directly after xTimerStart() completes succesfully. It took us a while to understand that the semantics of software timers is way more complicated than it looks at first glance &#8212; particularly with the priority of the timer-task beeing (too) low.
Our solution is to make sure the timer task has highest priority so we can be sure the timer is started by calling xTimerStart().
Thank you for looking into the issue.
Philipp
