</div></div><div class="thread-post"><h3 class="thread-post-title">TCP Communication</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 13, 2019</div><div class="thread-post-content">Wolfgang, thanks for reporting this.
I had to look this up: why is de WIN size reported as 1463 and not 1460?
It has to do with the TCP/IP stream buffers: The length of the buffer can be used minus on byte.
That has to do with the fact that a read and write index are being used.
So in stead of making a bufer N x 1460 bytes, an extra 4 bytes are reserved.
For example: 4 x 1460 + 4 = 5844 bytes, of which 5843 bytes can be used. There are the extra 3 bytes!
It does not hurt, the reported buffer space is really available!
I just tried to make a patch for this but the resulting code would be too ugly.
Regards, Hein
</div></div><div class="thread-post"><h3 class="thread-post-title">TCP Communication</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 13, 2019</div><div class="thread-post-content">I just wrote:
<blockquote>
  So in stead of making a buffer N x 1460 bytes, an extra 4 bytes are reserved.
</blockquote>
A next question could be: why not reserve <code>N x 1460 + 1</code> bytes?
That has to do with efficient copying. Calling <code>memcpy()</code> for aligned buffers is much more efficient than for unaligned buffers.
When the stream buffer has a length which is a multiple of 4 ( or <code>sizeof( size_t )</code> ), it is more likely that access in that buffer is always aligned.

</div></div><div class="thread-post"><h3 class="thread-post-title">TCP Communication</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 13, 2019</div><div class="thread-post-content"><blockquote>
  Could it be that reporting new winsize is not working correct when data are read out of socket?
</blockquote>
I am not aware of any problem with that. But let me explain how it works:
When receiving data, the driver has a definition of &#8220;low-water&#8221;. &#8220;low-water&#8221; means that the reception buffer has little space. 
The algorithm in<code>FreeRTOS_recv()</code> is simple: only in case of &#8220;low-water&#8221;, a signal will be sent to the IP-task, that will result in sending an update of the WIN size.
Could you try a simple thing: put the TCP window size (for reception) to 1460 (of 2920) bytes?
So like this:
~~~
    windowsProperties.lRxBufSize = 4 * ipconfigTCP_MSS;
    windowsProperties.lRxWinSize = 1; /* or 2 */
~~~
I think that the TCP server will send WIN updates more often because the TCP window is smaller.
