</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 20, 2019</div><div class="thread-post-content"><blockquote>
  Is there a way to make the call to FreeRTOSsendto blocking?
  When I returns I want to make sure that the data has been sent
  I am using UDP
</blockquote>
Yes sure that is possible. Please have a look <a href="https://www.freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/API/setsockopt.html">here</a>
See also the macro&#8217;s <code>ipconfigSOCK_DEFAULT_RECEIVE_BLOCK_TIME</code> and <code>ipconfigSOCK_DEFAULT_SEND_BLOCK_TIME</code> <a href="https://www.freertos.org/FreeRTOS-Plus/FreeRTOS_Plus_TCP/TCP_IP_Configuration.html#ipconfigSOCK_DEFAULT_SEND_BLOCK_TIME">here</a>
For many socket options, it is important to apply them to a socket just after its creation, but <code>FREERTOS_SO_SNDTIMEO</code> and <code>FREERTOS_SO_RCVTIMEO</code> may be changed any time.
The send() functions have a flag, in which you can pass <code>FREERTOS_MSG_DONTWAIT</code>, meaning to ignore the time-outs set on this socket.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/oneguyindc">oneguyindc</a> on February 20, 2019</div><div class="thread-post-content">Yes I read the documentation but it was not clear to me.
If FREERTOS<em>SO</em>SNDTIMEO is speficied to a <strong>non zero</strong> value &#8211; that means the call to FREERTOS<em>SO</em>SNDTIMEO will <strong>block</strong> attempting to send the packet via UDP and when it returns &#8211; if return is non zero &#8211; UDP sent sucessful
if return is zero &#8211; UDP unsucessful
Is that right ?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 20, 2019</div><div class="thread-post-content"><blockquote>
  will block attempting to send the packet via UDP and when it returns
  if return is non zero &#8211; UDP sent sucessful
  if return is zero &#8211; UDP unsucessful
</blockquote>
That is true: the length of the packet is returned in case of success, and zero is returned when either of these went wrong:
<ul>
<li>There was no network buffer available, even after waiting <code>SNDTIMEO</code> clock-ticks</li>
<li>The message buffer to the IP-task (<code>xNetworkEventQueue</code>) didn&#8217;t have space to accept a new message, also after waiting <code>SNDTIMEO</code> clock-ticks</li>
</ul>
So it is useful to call <code>sendto()</code> in a blocking way, although when an application is well tuned, the function will never block.
As you understand: a non-zero return code from <code>sendto()</code> only guarantees that a messages has been passed to the IP-task. When there is a Link Status with a switch or a router, I don&#8217;t see any reason why the UDP packet won&#8217;t be sent out through the PHY.
What happens after that is unknown: there are no guarantees that an Ethernet packet will arrive at the destination. To be sure, you will need some ACK-ing mechanism.
Although in practice, on a good quality LAN, the success rate for packet deliver is 100%. But don&#8217;t rely on it.
Hein

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 21, 2019</div><div class="thread-post-content">UDP packets are just sent onto the network and routed however the 
infrastructure between sender and receiver happens to route them.  There 
are no guarantees in the order in which they will be received, or even 
if they will be received at all.  If you need such guarantees then you 
either need to use TCP, or build these controls into the protocol that 
the UDP packets are carrying.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 21, 2019</div><div class="thread-post-content">I had prepared the text here below before reading Richard&#8217;s remarks. he was quicker than I am.
Here is my text, which is very similar to Richard&#8217;s view:
Formally, it is not guaranteed that Ethernet packets arrive in the same order as they have been sent.
But in practice, especially on a LAN, packets will arrive in the same order. The PHY will reattempt to deliver a packet in case it detects a collision.
The TCP protocol can handle all these exceptions perfectly well. UDP, on the contrary will deliver the raw packets. And at most, a packet may be dropped.
The order &#8220;1, 2, 3, 1, 2&#8221; sounds very strange to me. It means that packet 1 and 2 are transmitted 2 times. Why would that be and who does the retransmissions? I wouldn&#8217;t know.
The FreeRTO+TCP library will only transmit each UDP packet once, that is for sure. Even when the PHY sees (false) collisions, the order of arrival would have been &#8220;1, 1, 2, 2, 3&#8221;, and not &#8220;1, 2, 3, 1, 2&#8221;
I suppose that your application is not repeating messages?
I&#8217;m puzzled about your observations. Have you looked with WireShark already?

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_sendto &#8211; Is this a blocking call</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on February 22, 2019</div><div class="thread-post-content"><blockquote>
  <ol>
  <li>Is there a way that FreeRtos can block my call to FreeRtos_Send()
  until the bits are pushed out of the PHY</li>
  </ol>
</blockquote>
No there is not a (standard) way to do that.
The function that finally sends the packet is <code>xNetworkInterfaceOutput()</code>. As a test you could add some code there. When the function leaves, the packet may still be &#8220;in transfer&#8221;. But this should last less than a ms.
<blockquote>
  <ol>
  <li>I am assuming that FreeRtos has a Queue that queues up the UDP
  packets pushed by the App. Can this Queue be reduced to size 1</li>
  </ol>
</blockquote>
Yes and no, +TCP does not queue up outgoing packets. There is one queue though: the message queue to the IP-task, called <code>xNetworkEventQueue</code>.
But once the IP-task receives message <code>eStackTxEvent</code>, it will work on it untill it is passed to DMA for transfer.
<blockquote>
  <ol>
  <li>Will setting the Queue size to 1 effectively achieve what I am
  asking in my point #1</li>
  </ol>
</blockquote>
I&#8217;m afraid that you&#8217;ll have to make some code your self.
I must say that I have never heard of +TCP sending out UDP packets twice.
May you want to show the code that sends the UDP packets?
Can you attach a PCAP file that shows the double UDP packets?
Are you constantly creating new sockets ( as I understood from you first post ), or do you re-use the socket over and again?
Have you checked standard things like the heap and the stacks? Does <code>pvPortMalloc()</code> always succeed? Have you run the project with stack checking on?
