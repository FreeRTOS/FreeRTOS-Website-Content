  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">xTaskNotifyWait wake-up with  a delay</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yevpator75">yevpator75</a> on February 14, 2019</div><div class="thread-post-content">Hello,
I would like to ask about task notifications. 
I have a UART DMA transfer and when it is done, from the interrupt context I send a notification to a waiting  task :
~~~
uint32<em>t
sts = xTaskNotifyFromISR (gp</em>uartTxLogHandle,UART<em>TX</em>FREE<em>NOTIF</em>VAL, eSetBits, pdFALSE);
~~~
In the waiting task I have the following:
~~~
notifyRetVal = xTaskNotifyWait (0,TASK<em>NOTIF</em>BITS<em>TO</em>CLEAR,&amp;val, UART<em>TX</em>DMA<em>BUSY</em>TIMEOUT);
~~~
The problem is that the waiting task unblocks always with  a long latency. I see on the oscilloscope that the unblocking happens only after a new RTOS tick passes. The notifyRetVal , which I mentioned in the code above, is pdTRUE.
I checked in the User Manual and didn&#8217;t find there any mentioning that it should behave like I am observing now.  I expect that when I send a notification , the blocking task should unblock immediately, given there is no any other task with a higher priority.
Thanks in advance for any help!
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotifyWait wake-up with  a delay</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on February 14, 2019</div><div class="thread-post-content">The last paramater, which you are passing a pdFALSE, is normally supposed to be a pointer to a variable that the ISR passes in, that the notify will set true if something was woken. The ISR is then supposed to at its end, test this and cause the scheduler to run if needed, causing an immediate switch. pdFALSE, is 0, so it looks like a NULL pointer, which means the result isn&#8217;t returned, then the ISR never causes the scheduler to run, so until some other interrupt occures (like the timer) that does run the scheduler, the current running task doesn&#8217;t change.
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotifyWait wake-up with  a delay</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yevpator75">yevpator75</a> on February 14, 2019</div><div class="thread-post-content">Thank you Richard. 
Now I see I indeed improperly interpreted the last parameter, as you explained above.
Every time I call notifyFromISR , i should then call portYIELD<em>FROM</em>ISR( xHigherPriorityTaskWoken );
</div></div><div class="thread-post"><h3 class="thread-post-title">xTaskNotifyWait wake-up with  a delay</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on February 15, 2019</div><div class="thread-post-content">You don&#8217;txxxFROM need a portYIELD<em>FROM</em>ISR for each xxxFromISR call, but should have one at the end of every ISR that uses functions that might unblock a task. On some ports it doesn&#8217;t matter where the portYIED<em>FROM</em>ISR statement is, but on others it needs to be at the very end.
