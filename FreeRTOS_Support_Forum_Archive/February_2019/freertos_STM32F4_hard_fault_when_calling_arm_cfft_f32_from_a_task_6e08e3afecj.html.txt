  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">Hello. 
In a freeRT0S project created with Stm32cubemX (freeRTOS v. 9.0.0 CMSIS-RTOS v.1.02) my program gives a hardfault when the following line is called from my one and only task (created with priority osPriorityNormal:
arm<em>cfft</em>f32(&amp;arm<em>cfft</em>sR<em>f32</em>len2048, SampleBufferFloat, ifftFlag, doBitReverse);
However, if I call the exact same function with the same parameters before the task is started then it returns  normally.
The call stack only shows PendSV_Handler before the hard fault. 
I implemented the prvGetRegistersFromStack to copy the registers, but I&#8217;m struggling to understand what I&#8217;m looking at. $pc just gives the address of the line prvGetRegistersFromStack.
The project was generated with cubemx with mostly default values for freeRTOS. I have read the warning about interrupt levels and I don&#8217;t it applies here since I have only started one task and aren&#8217;t calling any freeRTOS functions from ISR.
There is also some SPI DMA going on in the background, but I don&#8217;t believe the issue is related to this. 
If I don&#8217;t call the arm<em>cfft</em>f32 funtion, the program appears to continue working just fine. 
I&#8217;d be grateful for any ideas of where to start looking. 
Many thanks. 
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">So just to eliminate any other cause, I created a new Cubemx project with only freeRTOS (so no DMA etc.) and addded in the FFT function to a single task. 
Again, the FFT function completes normally if called outside the task (before the task is started). If called inside the task then I again get a hard fault at xPortPendSVHandler. 
The timebase source is TIM7 this time. Last time it was TIM1.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 13, 2019</div><div class="thread-post-content">Starting with the basics &#8211; do you have configASSERT() defined (with the latest version of FreeRTOS, which contains many more asserts()), and do you have stack overflow detection turned on?    https://www.freertos.org/Stacks-and-stack-overflow-checking.html
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">Hi. Yes, I have the following defined:
<code>#define configASSERT( x ) if ((x) == 0) {taskDISABLE_INTERRUPTS(); for( ;; );}</code>
<code>#define configCHECK_FOR_STACK_OVERFLOW           1</code>
I&#8217;m using the latest available version of CubeMX. I see that there is a v10 of freeRTOS. I will attempt to install it over the CubeMx version.
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">I installed the latest version. No change other than now in the call stack I have a call to vTaskSwitchContext visible below PendSV_Handler.  
When I go to it, it&#8217;s taskCHECK<em>FOR</em>STACK_OVERFLOW();  I&#8217;m not sure how to interpret this. 
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">So I put a breakpoint in vApplicationStackOverflowHook() and I end up there. So it looks like I&#8217;ve got some stack overflow. Thanks for helping me narrow it down somewhat. I have no idea what&#8217;s causing the stack overflow, though!
~~~
__weak void vApplicationStackOverflowHook(xTaskHandle xTask, signed char <em>pcTaskName)
{
   /</em> Run time stack overflow checking is performed if
   configCHECK<em>FOR</em>STACK_OVERFLOW is defined to 1 or 2. This hook function is
   called if a stack overflow is detected. */
    asm(&#8220;bkpt 255&#8221;);
}
~~~
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/wonkowill">wonkowill</a> on February 13, 2019</div><div class="thread-post-content">Out of desperation I increased the configMINIMAL<em>STACK</em>SIZE from 128 to 2048 and I no longer get the hard fault. I&#8217;m confused, though. I thought this stack size was for the idle task which is doing nothing in my case. I wonder whether it&#8217;s just kicking the problem down the road, though. 
</div></div><div class="thread-post"><h3 class="thread-post-title">STM32F4 hard fault when calling arm_cfft_f32 from a task </h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on February 13, 2019</div><div class="thread-post-content">First, set configCHECK<em>FOR</em>STACK_OVERFLOW to 2, not 1, it is then much 
more reliable.
configMINIMAL<em>STACK</em>SIZE is only used <strong><em>by the kernel</em></strong> to dimension 
the size of the stack used by the Idle task, but lots of the standard 
demo tasks use the same constant to make them portable across multiple 
architectures.
