  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">portXYZ macro description</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hooverphonique">hooverphonique</a> on April 28, 2010</div><div class="thread-post-content">FreeRTOS uses several macros named &#8220;portXYZ&#8221;..  
For porting purposes, is there a detailed description of, what the exact functionality of these macros must be?<br />
Looking at the usage gives some clues, but also leads to guesswork..  
I&#8217;ve also noticed that queue.c makes uses of both &#8220;portENTER/EXIT&#95;CRITICAL&#40;&#41;&#8221; and &#8220;taskENTER/EXIT&#95;CRITICAL&#8221; even though &#8220;task.h&#8221; hardcodes the latter to be equivalent to the former. Is this a simple mistake or are there cases, where they differ in functionality?<br />
There is even a case where &#8220;portENTER/EXIT&#95;CRITICAL&#40;&#41;&#8221; is nested within &#8220;taskENTER/EXIT&#95;CRITICAL&#8221; which doesn&#8217;t really make sense to me…  
cheers..
</div></div><div class="thread-post"><h3 class="thread-post-title">portXYZ macro description</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 28, 2010</div><div class="thread-post-content">It is intended that application code does not &#40;in most cases&#41; call portXYZ macros directly, but instead calls the taskXYZ equivalents &#8211; as you point out in some cases the two are equivalent.&nbsp; With regard to the ENTER/EXIT&#95;CRITICAL&#40;&#41; macros they are indeed the same and you could use either, although it is still recommended that application code only uses the taskXYZ versions for reasons of future compatibility.  
It is possible that I have used both versions directly in the kernel code, and that is probably not a good thing to do, although the portXYZ versions are intended for use by the kernel itself.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">portXYZ macro description</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hooverphonique">hooverphonique</a> on April 28, 2010</div><div class="thread-post-content">right.. no comment on my first question rearding portXYZ functionality?  
I&#8217;m primarily looking for documentation of &#8220;portENABLE/DISABLE&#95;INTERRUPTS&#8221; and &#8220;portSET/CLEAR&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#8221;.. It&#8217;s not quite clear if these macros must disable/mask interrupt processing altogether or only the interrupts &#40;priorities&#41; that call API functions..  
and then there&#8217;s &#8220;portCRITICAL&#95;NESTING&#95;IN&#95;TCB&#8221;…  
cheers..
</div></div><div class="thread-post"><h3 class="thread-post-title">portXYZ macro description</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 28, 2010</div><div class="thread-post-content">There is no quick answer to these because the implementation of the macros is very dependent on the architecture you are using and your design decisions.  
ENABLE&#95;DISABLE&#95;INTERRUPTS&#40;&#41; should either disable/enable interrupt completely, up just up to the priority set by configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY &#8211; depending on whether you are implementing a port that allows interrupt nesting or not.  
SET/CLEAR&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#40;&#41; is only needed if you are implementing interrupt nesting.&nbsp; The SET part should return the current interrupt priority mask, and the CLEAR part should return the interrupt mask to whatever the SET part returned.&nbsp; Note however that the Cortex M3 port does something slightly different because the hardware allows a bit of a simplification.  
You also need to store the critical nesting count as part of the task context.&nbsp; This can be done either on the task stack, or in the task TCB.&nbsp; set portCRITICAL&#95;NESTING&#95;IN&#95;TCB to 0 for the former, and 1 for the latter.&nbsp; Again note that the Cortex M3 port is a bit different here too.  
Which architecture are you porting too?  
Regards.

sorry for not getting back to you earlier…  
I&#8217;m porting to AVR XMega, or more correctly, have already done so.. my plan is to contribute as soon as I&#8217;m confident everything works as expected..  
The reason for asking the questions is that I have an issue that causes the tick to stop and because of some residual doubts about what the mentioned macros are supposed to do, I wanted to make sure I understood what they have to do correctly. The tick issue has been tracked down to a TWI problem, which is good :-&#41;  
Regarding portCRITICAL&#95;NESTING&#95;IN&#95;TCB: If I understand correctly, I don&#8217;t have to implement anything related to this, but just &#8220;pick&#8221; a value of 0 or 1? 
</div></div><div class="thread-post"><h3 class="thread-post-title">portXYZ macro description</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hooverphonique">hooverphonique</a> on November 9, 2010</div><div class="thread-post-content">Another question about taskENTER&#95;EXIT&#95;CRITICAL/portENTER&#95;EXIT&#95;CRITICAL:  
does the kernel rely on the fact that these disable interrupts up to configMAX&#95;SYSCALL&#95;INTERRUPT&#95;PRIORITY &#40;for an implementation supporting interrupt nesting&#41; or is it ok if they only disable context switching? If they only disable switches, then what about the tick isr &#8211; must it be disabled as well?  
the documentation for these state that they &#40;only&#41; disable context switches, but the code for xQueueGenericReceive suggests that they also must disable &#40;some&#41; interrupts..  
I&#8217;m doing a port where all context switches happen through a soft-interrupt, which means that context switching may be disabled just by disabling that one isr instead of disabling whole priorities.
</div></div><div class="thread-post"><h3 class="thread-post-title">portXYZ macro description</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 9, 2010</div><div class="thread-post-content">I believe that the actual requirement on the CRITICAL macros is that once you ENTER&#95;CRITICAL you can not ENTER&#95;CRITICAL by another execution path until you have done all the EXIT&#95;CRITICAL &#40;or use FromISR code that assumes that you can&#8217;t be in a critical section&#41;. This means that the ENTER&#95;CRITICAL does need to disable interrupts that will call FreeRTOS API functions.
