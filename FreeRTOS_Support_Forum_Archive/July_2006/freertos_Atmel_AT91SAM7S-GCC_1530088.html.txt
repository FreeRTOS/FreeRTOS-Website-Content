  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Atmel AT91SAM7S-GCC</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/chris_koerber">chris_koerber</a> on July 4, 2006</div><div class="thread-post-content">Good day,
My colleagues and I are currently thinking about dumping our homebrew non-multitasking scheduler of our AT91SAM7sS design which happened to become rather complex during the lasts weeks. 
FreeRTOS seems to be the perfect replacement. However, I have the impression that the AT91SAM7 port is relativly new and thus not very well documented &#40;at least I couldn&#8217;t find any documentation&#41;.
Because of this I&#8217;d like to ask some questions here, any input is highly appreciated:
1&#46; Does the AT91SAM7-GCC port work with the GNUARM toolchain?
2&#46; What is the source of the &quot;Tick-Interrupt&quot;? Sorry I couldn&#8217;t phrase it better, this subject is actually a bit too low level for my taste. What I mean is this: On our board resides a real time clock, is this a possible source for this interrupt or will FreeRTOS automatically rely on the the MCU built-in signal?
best regrads,
Christian
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel AT91SAM7S-GCC</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 4, 2006</div><div class="thread-post-content">The SAM7S port was created using IAR tools.&nbsp; The SAM7X port with Rowley/GCC.&nbsp; A command line GCC &#40;rather than Rowley IDE&#41; makefile was also provided for the SAM7X demo a little later.&nbsp; This was created using GNUARM.&nbsp; There is little specific documentation for the command line GCC version as 95% of it is common with the Rowley port documentation.&nbsp; See here:
http://www.freertos.org/portsam7xlwIP.html&#35;CommandLineUsage
The X and S are very similar and compatible, just the peripherals are different &#40;I think&#41;, so using the X demo on an S part should just be a matter of cutting out the unwanted bits &#40;Ethernet driver mainly&#41;.&nbsp; Several people have done this.&nbsp; I have a project written using GNUARM that includes an SD card driver also, so people are using this successfully.
The Tick is generated by the PIT &#40;periodic interrupt timer&#41;, which according to the datasheet is provided exactly for this purpose.
Hope this answers your questions.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel AT91SAM7S-GCC</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on July 4, 2006</div><div class="thread-post-content">Thank you Richard,
this sounds promising. 
Please let me get back to the tick issue once more:
What our application basically does, is sampling a sensor with 200Hz, performing some signal processing for 1 millisecond and than disabling ALL interrupts and switching to low clock cycle, thus nearly shutting it down for 4 milliseconds &#40;in order to preserve battery charge&#41;. The only way to get back from this state is&nbsp; by a signal from the real time clock via an advanced interrupt controler. 
So my thoughts circle around the question whether there was a way to interface FreeRTOS with this signal.
best regards,
Christian
</div></div><div class="thread-post"><h3 class="thread-post-title">Atmel AT91SAM7S-GCC</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 4, 2006</div><div class="thread-post-content">Take a look at the function prvSetupTimerInterrupt&#40;&#41; in FreeRTOSSourceportableGCCARM7&#95;AT91SAM7Sportable.c.&nbsp; This is the function that installs the tick handler on the PIT interrupt &#40;as well as configuring the PIT frequency&#41;.
You can generate the tick from any interrupt source capable of providing a periodic interrupt.&nbsp; So you could modify prvSetupTimerInterrupt&#40;&#41; to use your external clock through an IRQ rather than using the clock on the processor.&nbsp; The kernel does not care where the interrpt comes from as long as it gets it at regular intervals.
You might want to consider using the idle task hook to place the CPU into power down mode.&nbsp; This way whenever there is no processing to perform &#40;all tasks are blocked other than the idle task, assuming no other tasks share the same priority as the idle task&#41; then the CPU will sleep automatically sleep until the next interrupt.
Regards.
