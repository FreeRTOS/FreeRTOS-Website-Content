I suspect that the root of the problem is &#8216;operator error&#8217; &#40;&#42;ahem&#42;&#41;, so I&#8217;ll list what I&#8217;ve been trying and perhaps someone can help me see what I&#8217;m doing wrong.
&#45;&#8212;-
I&#8217;m using the AT91SAM7x256-EK with the CrossConnect programmer. The way I understand it, this is the same hardware setup as the one Richard describes on the page for the lwIP demo. 
I connected the programmer&#8217;s USB cable from the board to a USB port on the back of my Windows PC and connected a crossover ethernet cable from the ethernet port on the board to the ethernet port on a second ethernet card installed in my PC.
I edited SAM7&#95;EMAC.h so that:
&#42; The ethernet address is the default address &#40;0, 0xbd, 0x33, 0x06, 0x68, and 0x22&#41; 
&#42; The IP address used by the board is 192.168.0.49
&#42; The gateway address is 192.168.0.3 &#40;this is a BS address, as I&#8217;m not interested in talking to different networks&#41;
&#42; The net mask is 255.255.255.0
In SAM7&#95;EMAC.c, I did not edit the value of USE&#95;RMII&#95;INTERFACE &#40;meaning that it is still 0&#41;.
As I alluded to earlier, my PC has two ethernet interfaces. One connects to the real network, and the other I use for projects like this. On that second ethernet card, I used the IP address 192.168.0.50, the subnet mask 255.255.255.0, and the gateway address 192.168.0.50 &#40;which shouldn&#8217;t signify anything special, if I understand correctly. I haven&#8217;t gone out of my way to set up the interface to forward traffic or anything&#41;.
I loaded the rtosdemo.hzp file in Rowley CrossStudio and built it. It built with no errors. Then, I connected to the target using the CrossConnect, and selected &#8216;build and run&#8217;. The code built &#40;again&#41;, was uploaded to the device, and verified, all with no errors.
I opened HyperTerminal and established a connection with the board &#40;it was COM3 for me&#41; and see the alphabet stream by like it should. The DS1-DS4 LEDs blinked as described on the page for the demo project. The DS6 LED &#40;&#8217;FULL DUPLEX&#8217;&#41; was orange, and the DS7 and DS8 LEDs &#40;&#8217;SPEED 100&#8242; and &#8216;LINK &amp; ACT&#8217;&#41; were solid green. When I entered &#8216;http://192.168.0.49&#8217; into my browser, the DS8 LED blinked once immmediately, and then began blinking rapidly shortly thereafter. The browser timed out and did not bring up a page at all.
I tried examining the &#8216;status&#8217; of the ethernet connection on the computer, and it &#40;the Windows dialog generated from clicking &#8216;View status of this connection&#8217;&#41; confirmed that packets were being sent and that none were being received. I checked the crossover cable to make sure it was wired correctly. It was. I tried disabling the primary ethernet address &#40;for the real network&#41;, and trying again. Still no luck. I tried changing the first segment of the ethernet address to 0x08, and had no success. I tried changing USE&#95;RMII&#95;INTERFACE to 1, but that just made DS6-8 blink simultaneously and intermittently, so I&#8217;m guessing that was the board&#8217;s way of telling me that I want USE&#95;RMII&#95;INTERFACE set to 0. 
The 192.168.x.x network is just the board and my PC, so there shouldn&#8217;t be any address conflicts. I also tried using a &#8216;straight&#8217; cable to connect the board to a hub and using another straight cable to connect the hub to the PC &#40;neither one in the &#8216;Uplink&#8217; port&#41;.
I&#8217;m sure that I&#8217;m just doing something stupid, or that I&#8217;ve overlooked something simple. Either way, I&#8217;m out of ideas and would appreciate any input.
Thanks a bunch&#33;
Mike Sheffler
</div></div><div class="thread-post"><h3 class="thread-post-title">Problem With lwIP Demo On AT91SAM7x256-EK</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on July 18, 2006</div><div class="thread-post-content">This is a tricky one as you have already tried nearly everything I would have suggested.
The fact that your USB connection and LED&#8217;s are functioning as expected show that the program is built and downloaded fine so it must just be a network configuration issue.
The setup you describe &#40;IP address, etc.&#41; sounds fine.&nbsp; I would stick with 00 being the first octet of the MAC address.
USE&#95;RMII&#95;INTERFACE should be zero, unless you are using one of the very early pre-production boards.
I would have postulated that it was a mix up somewhere between the two network cards, but the fact that you can see the LED&#8217;s blink when you expect them to would suggest otherwise.&nbsp; It might be worth however installing Ethereal &#40;if you have not already, http://www.ethereal.com/&#41;.&nbsp; This will allow you to sniff the traffic on each network interface individually so you can ensure the traffic is going via the correct card.
Some random thoughts, comments:
+Which browser are you using?&nbsp; I have tested with Internet Explorer and FireFox.
+Can you ping the SAM7X, or is there no response?
+Is it possible to place the card &#40;temporarily and with appropriate IP address&#41; on your primary network?
+Did you make any other changes to the code?&nbsp; If you created some other tasks for example it is possible that it ran out of heap space so could not create all the server tasks.
A couple of things to try in addition to pinging and Ethereal:
1&#41; In SAM7&#95;EMAC&#95;ISR.c, try setting a break point in vEMACISR&#40;&#41;.&nbsp; This will show us whether or not you are getting interrupts from the EMAC peripheral.
2&#41; In heap&#95;2.c, at the end of the function pvPortMalloc&#40;&#41; immediately before the return, add the following code:
if&#40; pvReturn == NULL &#41;
&#123;
&nbsp;&nbsp;&nbsp; asm volatile &#40;&quot;NOP&quot;&#41;;
&#125;
and set a break point on the NOP.&nbsp; If the break point is hit then you ran out of heap somewhere &#40;should not happen if the code is not modified&#41;.
Regards.

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem With lwIP Demo On AT91SAM7x256-EK</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on July 20, 2006</div><div class="thread-post-content">How are you connected to the board?&nbsp; With a crossover cable?
If not, make sure that you&#8217;re not connected through a switch, otherwise you wont see all the packets you&#8217;re interested in.
I wasted a day pulling my hair out while I was writing our TCP stack wondering why I couldn&#8217;t see packets and why it wasn&#8217;t working, of course it was, I just assumed it wasn&#8217;t because I couldn&#8217;t see some of packets on my host machine&#33;

</div></div><div class="thread-post"><h3 class="thread-post-title">Problem With lwIP Demo On AT91SAM7x256-EK</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/nobody">nobody</a> on July 21, 2006</div><div class="thread-post-content">I&#8217;m sure you will have tried this already but I will say it anyway.
Place a break point in the Tx complete interrupt in the same ISR.&nbsp; If you hit the break point then the sam things it has sent something which never made it onto the wire if you cannot see it with ethereal.
If the interrupt is never is never seen then set a break point in lEMACSend within sam7&#95;emac.c.&nbsp; You should see the arp response going to the dma if nothing else.
Some time back there was an issue with the mac address being sued where the sam would reply to the arp happily, but the router between the sam and pc did not let the repyly through.&nbsp; So depending on which side of the router ethereal was placed you would or would not see the arp response.
