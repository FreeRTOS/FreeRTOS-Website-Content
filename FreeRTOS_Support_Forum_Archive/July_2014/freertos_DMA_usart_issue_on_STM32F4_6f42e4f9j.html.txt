</div></div><div class="thread-post"><h3 class="thread-post-title">DMA usart issue on STM32F4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 11, 2014</div><div class="thread-post-content"><blockquote>
  With only one of these lines appears the problem.

Do you mean that including <b>any</b> of these lines will cause the problem, or that including one specific line will cause the problem (if so, which one?).
If including any of these lines causes the problem then it would seem unlikely but not impossible it was the line itself that was the problem.  I say not impossible because the lines are calling into the FreeRTOS kernel, which means critical sections will be being entered and exited &#8211; but that should definitely not cause a problem.
Are you 100% sure the start up code is initialising the system correctly?  Can you check the value of uxCriticalNesting both on entry into main() and immediately before starting the scheduler.  uxCriticalNesting is defined in port.c, but I&#8217;m not sure which compiler you are using.  You will find port.c in FreeRTOS/source/portable/[compiler]/ARM<em>CM3 (or ARM</em>CM4F).  It should be non zero (probably 0xaaaaaaaa) when you enter main, and close to the same value before the scheduler is started.  If the start up code was not executing properly you may find it had a different value.

</div></div><div class="thread-post"><h3 class="thread-post-title">DMA usart issue on STM32F4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on July 11, 2014</div><div class="thread-post-content"><blockquote>
   because the program loops in DMA_GetCurrDataCounter() under SendOnUsart1().
  Then it doesn&#8217;t reach vTaskStartScheduler().
</blockquote>
Ah!  So you are trying to use the UART DMA interrupts <em>before</em> the scheduler has been started.  That makes much more sense then.
FreeRTOS will deliberately leave interrupts at and below configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY masked until the scheduler has started.  This is done to ensure interrupts do not try to use a FreeRTOS API function while the scheduler is in an inconsistent state.  When you call the first FreeRTOS API function interrupts will be enabled, but when you come out they will be masked (still enabled, but masked to a certain priority level).  Hence the interrupt stops working.
The interrupts are automatically unmasked when the scheduler is started (when the tasks start running).
Regards.
