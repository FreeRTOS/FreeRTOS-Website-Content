</div></div><div class="thread-post"><h3 class="thread-post-title">Intermittent crashing on Cortex M4</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on October 31, 2014</div><div class="thread-post-content">Thank you for providing such detailed information.
What happens when the application crashes &#8211; do you end up in a hard fault, data abort, etc?  Did you attempt to debug that.  Not always possible, but sometimes very helpful &#8211; I suspect you have seen this page already: http://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html
Does the issue occur when configUSE<em>TICKLESS</em>IDLE is set to 0?
Regarding the interrupt enabling/disabling:
FreeRTOS never completely disables interrupts &#8211; its critical regions are implemented by setting the BASEPRI register to mask a subset of interrupt priorities, rather than setting the i bit in the CPSR to globally disable interrupts.  The only way you should disable or enable interrupts yourself is by calling taskENTER<em>CRITICAL and taskEXIT</em>CRITICAL if in a task, or portSET<em>INTERRUPT</em>MASK<em>FROM</em>ISR and portCLEAR<em>INTERRUPT</em>MASK<em>FROM</em>ISR if in an interrupt (the latter two there are actually intended for internal use, and you will see them being used in xQueueGenericSendFromISR() in queue.c, but there is nothing to stop you using them yourself).  The big exception to this is when implementing the &#8216;suppress ticks and sleep&#8217; function &#8211; where an global disable must be used for the reasons explained in the source code comments &#8211; that is kernel code rather than user code though.
I believe the ASF on the other hand effects critical sections by globally disabling interrupts using the i bit in the CPSR.  So provided it always enables it again there should be no conflict between its critical sections and FreeRTOS&#8217;s.
Regards.
