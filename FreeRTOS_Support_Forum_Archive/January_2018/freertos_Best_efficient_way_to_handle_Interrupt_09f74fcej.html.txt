</div></div><div class="thread-post"><h3 class="thread-post-title">Best efficient way to handle Interrupt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 27, 2018</div><div class="thread-post-content">Hi David,
To summarise your two approaches:
FIRST case :
~~~
void Interrupt<em>handler()
{
char cC;
    cC = LL</em>USART_ReceiveData(Instance);
    xQueueSendFromISR(xQueueUartRx, &amp;cC, NULL);
    vTaskNotifyGiveFromISR(uartExtTaskHandle, NULL);
}
void uartExt<em>task(void const* argument)
{
char cChar;
    while(true)
    {
        if (xQueueReceive(xQueueUartRx, &amp;cChar, 0))
        {
            // do somethings
        }
        ulTaskNotifyTake(pdTRUE, portMAX</em>DELAY);
    }
}
~~~
SECOND case :
~~~
void Interrupt<em>handler()
{
portCHAR cC;
    cC = LL</em>USART_ReceiveData8(USART6);
    xQueueSendFromISR(xQueueUartRx,&amp;cC, NULL);
}
void Task<em>for</em>receiving()
{
char Ccar;
    for (;;)
    {
        if (xQueueReceive( xQueueUartRx,&amp;Ccar, portMAX_DELAY ) == pdTRUE)
        {
            // do somethings
        }
    }
}
~~~
The second approach looks better to me.
In the first approach you are using two wake-up (or notify) mechanisms: both a message queue and a task notification. One method is enough.
Note that the second approach is ok for a terminal driver that receives key strokes or so.
When the USART is exchanging big amounts of data, it is worth using multiple DMA-buffers. Only when a buffer is full, or when no more data are expected, you send a buffer to the user.  After reading it, the user will have to pass back the buffer to the driver.
Personally, I like to use circular buffers (see stream_buffer.c), where the driver may write and the user (a single user only) may read from it. This can also be combined with the task-notify mechanism:
~~~
void Interrupt<em>handler()
{
char cC;
BaseType</em>t xSwitchRequired = pdFALSE;
<pre><code>cC = LL_USART_ReceiveData( Instance );
addByte (&amp;xCircularBuffer, cC);
vTaskNotifyGiveFromISR( uartExtTaskHandle, &amp;( xSwitchRequired ) );
/* Switch context if needed: */
portYIELD_FROM_ISR( xSwitchRequired );
</code></pre>
}
void Task<em>for</em>receiving(void const* argument)
{
char pcBuffer[ 128 ];
int iCount;
<pre><code>while(true)
{
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
    /* When waking up, 1 or more bytes have been placed in the
    circular buffer.  Read them in blocks: */
    for( ;; )
    {
        iCount = readBytes ( &amp;xCircularBuffer, pcBuffer, sizeof pcBuffer );
        if( iCount &lt;= 0 )
        {
            break;
        }
        // do somethings
    }
}
</code></pre>
}
~~~
Note also that I added a call to <code>portYIELD_FROM_ISR()</code>, to cause a context-switch.

</div></div><div class="thread-post"><h3 class="thread-post-title">Best efficient way to handle Interrupt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 27, 2018</div><div class="thread-post-content">The simplest way is to use a mutex for the task side. Normally the ISR side doesn&#8217;t have much to worry about, as only 1 ISR will be connected to a given buffer, so it just needs to make sure it updates things such that the task will always see something consistant, and the task need to make sure it keeps things clean for the ISR. One key for this is you move/take the data byte, THEN you update the data pointers.
Often I find the task side doesn&#8217;t need an explicit mutex for the curcular buffer, as there is a higner level aspect that makes it so that only one task has access to the buffer at any given time.

</div></div><div class="thread-post"><h3 class="thread-post-title">Best efficient way to handle Interrupt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 27, 2018</div><div class="thread-post-content">David wrote:
<blockquote>
  Thanks for your answer, how you guarantee your circular buffer is thread safe ?
</blockquote>
You&#8217;re welcome.
Richard Damon already answered your question.
The method is thread-safe as long as there is only one &#8220;giver&#8221; and one &#8220;taker&#8221;.  As Richard comments, this is a design thing.
If you want to read USART data from several threads (tasks), the circular buffer should be protected with a mutex.
</div></div><div class="thread-post"><h3 class="thread-post-title">Best efficient way to handle Interrupt</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 27, 2018</div><div class="thread-post-content">As Hein said, there is no reason that I see to use both a Queue, and then also a direct to task notification (or a semaphore), as you normally only need one interlocking primative. If the baud rate isn&#8217;t to high, or the protocal makes it hard for the ISR to figure out the message breaks, just using a Queue can be the simplest, though it does have the overhead of likely causing a task switch in and out for each character. If the data rate is high, the messages are somewhat long, and the ISR can detect message boundries, then having the ISR buffer up a full message and then notify the task can lower the processor load to receive the message. This might be done with a circular buffer, or you might have a group of buffers and indicate which buffer has the message (particularly useful for large messages, to avoid needing to copy it into and out of a circular queue.
