  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">BufferAllocation_1.c xFreeBuffersList memory corruption issue</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/tc-cadscan">tc-cadscan</a> on January 26, 2018</div><div class="thread-post-content">I&#8217;ve written a zero-copy network driver for FreeRTOS+TCP on STM32F4. For the most part it works well, but every once in a while I get an issue with pxGetNetworkBufferDescriptor returning NULL. I&#8217;m calling it with xBlockTimeTicks set to portMAX_DELAY, so in theory this should never happen. Looking through the source code, the buffer descriptors are kept in a list called xFreeBuffersList, and are fetched by this line:
~~~
pxReturn = ( NetworkBufferDescriptor<em>t * ) listGET</em>OWNER<em>OF</em>HEAD_ENTRY( &amp;xFreeBuffersList );
~~~
Following this, some validation is performed on pxReturn to make sure it is a valid descriptor, and if not, return NULL. This seems to be where it&#8217;s failing:
~~~
if( ( bIsValidNetworkDescriptor( pxReturn ) != pdFALSE<em>UNSIGNED ) &amp;&amp;
                    listIS</em>CONTAINED_WITHIN( &amp;xFreeBuffersList, &amp;( pxReturn->xBufferListItem ) ) )
~~~
So it&#8217;s basically looking up the ListItem<em>t associated with the network descriptor, and verifying that it is part of xFreeBuffersList. listIS</em>CONTAINED<em>WITHIN just compares the pvContainer field of the ListItem</em>t to the list pointer (xFreeBuffersList in this case). The problem seems to be that pvContainer is set to NULL. As this should get set when the descriptor is inserted into the list (i.e. when it was last released), and the descriptor is definitely getting inserted into the list correctly (it must be, given that we just got it from the list), this makes me think the list structure is getting corrupted in memory somehow.
A couple of times I&#8217;ve also seen a different issue, where listGET<em>OWNER</em>OF<em>HEAD</em>ENTRY returns some random value which isn&#8217;t a buffer descriptor. Whenever this happened, I tracked it down to fields in the list structure being invalid (sometimes NULL or sometimes random values), which also suggests memory corruption to me.
There are only 5 places in my code where I call into BufferAllocation_1.c:
<ul>
<li>During xNetworkInterfaceInitialise, I call pxGetNetworkBufferDescriptor multiple times to allocate buffers to the receive DMA descriptors.</li>
<li>During xNetworkInterfaceOutput, I assign the buffer passed in by the TCP/IP stack to a transmit DMA descriptor. If this fails (due to a DMA descriptor not being available within a given timeout), I call vReleaseNetworkBufferAndDescriptor to discard the buffer.</li>
<li>During the receive deferred interrupt processing task, I attempt to send the received buffer to the TCP/IP stack. If this fails, I call vReleaseNetworkBufferAndDescriptor to discard the buffer.</li>
<li>Also in the deferred processing task, I call pxGetNetworkBufferWithDescriptor to replace the receive buffer that was just used.</li>
<li>In the transmit complete interrupt handler. I call vNetworkBufferReleaseFromISR to release the transmit buffer.</li>
</ul>
In all of these cases, I&#8217;m calling the buffer allocation functions exactly as described in the documentation, so I don&#8217;t think this is the issue. Whenever I have to deal with a buffer in an ISR, I make sure to only call the interrupt-safe functions. Checking in BufferAllocation<em>1.c, all of the functions that interact with the descriptor list use ipconfigBUFFER</em>ALLOC<em>LOCK and ipconfigBUFFER</em>ALLOC_UNLOCK (or the interrupt-safe equivalents), so I&#8217;m not sure where the problem is happening.
I&#8217;ve written a simple test application to reproduce the issue &#8211; it basically just listens for UDP packets on port 10000 and echoes them back to the sender. I&#8217;m setting the FREERTOS<em>ZERO</em>COPY flag to reduce unnecessary buffer allocation/deallocation, to rule that out. This is the only task on the system which uses the TCP stack:
~~~
static void echoThread(void *pvParameters)
{
    const uint16_t port = 10000;
<pre><code>Socket_t sock = FreeRTOS_socket(FREERTOS_AF_INET, FREERTOS_SOCK_DGRAM, FREERTOS_IPPROTO_UDP);
CAD_ASSERT(sock != FREERTOS_INVALID_SOCKET);
struct freertos_sockaddr hostAddr;
hostAddr.sin_port = FreeRTOS_htons(port);
FreeRTOS_bind(sock, &amp;hostAddr, sizeof(hostAddr));
struct freertos_sockaddr clientAddr;
uint32_t clientAddrLength = sizeof(clientAddr);
uint8_t *buffer;
int32_t length;
while (1)
{
    length = FreeRTOS_recvfrom(sock, &amp;buffer, 0, FREERTOS_ZERO_COPY, &amp;clientAddr, &amp;clientAddrLength);
    if (length &gt; 0)
    {
        length = FreeRTOS_sendto(sock, buffer, length, FREERTOS_ZERO_COPY, &amp;clientAddr, clientAddrLength);
    }
    if (length &lt;= 0)
    {
        FreeRTOS_ReleaseUDPPayloadBuffer(buffer);
    }
}
</code></pre>
}
~~~
The issue only shows up very rarely &#8211; probably once in every 100,000 to a million packets. The only reliable way I&#8217;ve found to reproduce it is to flood the network interface with traffic, at a rate of several thousand packets/second. Even then it&#8217;s difficult to reproduce, sometimes taking several minutes. If it helps at all, I&#8217;ve found that it tends to show up most often just after starting to send packets &#8211; stopping and then restarting the packet generator is more likely to trigger it than just leaving it running.
I did find one other post on here (https://freertos.org/FreeRTOS<em>Support</em>Forum<em>Archive/August</em>2016/freertos<em>TCP</em>BufferAllocation<em>1</em>xFreeBuffersList<em>corruption</em>bab400aej.html) with a similar issue. In that case it was tracked down to stack overflow (identified by the 0xA5A5A5A5 sequence), but in my case I don&#8217;t see that sequence anywhere so I doubt it&#8217;s stack overflow. Also if it was stack overflow I&#8217;d expect it to happen a lot more frequently and less randomly than it is doing.
At this point I&#8217;m not sure how I can debug the issue any further, as the problem seems to be happening within the TCP stack itself. Any ideas?
Thanks,
Tom

</div></div><div class="thread-post"><h3 class="thread-post-title">BufferAllocation_1.c xFreeBuffersList memory corruption issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 29, 2018</div><div class="thread-post-content">Hi Tom,
<blockquote>
  I&#8217;ve written a zero-copy network driver for FreeRTOS+TCP on STM32F4
</blockquote>
That is very brave of you, but there was a zero-copy driver already.  It is not in the official distribution yet, but it was published in this list.  I will post it as an attachment here below (<code>STM32Fxx.zip</code>).
<blockquote>
  but every once in a while I get an issue with pxGetNetworkBufferDescriptor returning NULL.
</blockquote>
I solved this problem by dropping a packet.  When a packet has been received, then you need to provide a new empty network buffer.  If that is impossible, I would drop the received packet, and leave the buffer in place so it will be used to receive a next package.
<blockquote>
  I&#8217;m calling it with xBlockTimeTicks set to portMAX_DELAY
</blockquote>
Are you sure it is wise such a long time?  Does this happen from <code>prvEMACHandlerTask()</code> ?
When the function is called from the IP-task ( e.g. from <code>xNetworkInterfaceOutput()</code> ), you should use a time-out of zero. If not, the IP-task will probably be waiting for the IP-task to release some network buffer.
<blockquote>
     During xNetworkInterfaceInitialise, I call pxGetNetworkBufferDescriptor multiple
       times to allocate buffers to the receive DMA descriptors.
</blockquote>
Comment : during initialisation, there must be enough network buffers.  You can use <code>configASSERT()</code> for this.  If it is triggered, the is a configuration error.
<blockquote>
     During xNetworkInterfaceOutput, I assign the buffer passed in by the TCP/IP stack
       to a transmit DMA descriptor. If this fails (due to a DMA descriptor not being
       available within a given timeout), I call vReleaseNetworkBufferAndDescriptor to
       discard the buffer.
</blockquote>
This function has lead to some confusion in the past.
To summarise:
If <code>ipconfigZERO_COPY_TX_DRIVER = 1</code>, the parameter <code>bReleaseAfterSend</code> is always true
If <code>bReleaseAfterSend</code> is true, it means that the driver will own the <code>pxDescriptor</code>.
So yes, if sending fails, you must release the network buffer.
If sending succeeds, the releasing of the buffer is suspended.
In my zero-copy driver, the releasing is indeed done within <code>prvEMACHandlerTask()</code>.
I stop commenting here.
Please have a look at the attached driver.  It has been tested on both STM32F4 and STM32F7.
Regards.
