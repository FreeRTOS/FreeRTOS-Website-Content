  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">TCP: prvTCPWindowFastRetransmit: Requeue sequence number</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/hannes23">hannes23</a> on January 30, 2018</div><div class="thread-post-content">Hi everyone,

Relatively often I see the debug message:
prvTCPWindowFastRetransmit: Requeue sequence number xxxxx &lt; yyyyy
Could this be an indication, that any parameter should be trimmed in any way, or is this a normal situation
which occurs at heavy traffic?
By the way no error or missing a  packet happens though.
Greetings.
</div></div><div class="thread-post"><h3 class="thread-post-title">TCP: prvTCPWindowFastRetransmit: Requeue sequence number</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 30, 2018</div><div class="thread-post-content">Hi Johannes, 80 MByte of TCP data per sec is indeed heavy traffic.
<code>prvTCPWindowFastRetransmit()</code> is the routine that checks for fast retransmission. This will take place when A, B, C have been sent, but only B and C have been acknowledged by the peer.  At tha moment, the device assumes that packet &#8216;A&#8217; got dropped somewhere.
<blockquote>
  By the way no error or missing a packet happens though.
</blockquote>
Good. Neither it will affect the performance severely, because it is literally a &#8220;fast retransmission&#8221;.
If you want to avoid these retransmissions, there are several places to look:
<ul>
<li>Within the library: does the IP-stack every run out of Network Buffers?  You may want to check <code>uxGetMinimumFreeNetworkBuffers()</code>.</li>
<li>Within the driver: does <code>xNetworkInterfaceOutput()</code> ever result in a time-out?  Does <code>emacps_send_message()</code> ever fail?</li>
<li>On the LAN: are there more participants on the LAN, could there be an overflow within a switch or a router?</li>
<li>Can you find statistics about the LAN?  Collision counts?</li>
<li>Are you using any Ethernet hub?</li>
</ul>
Ps. there is an important patch to Zynq/NetworkInterface.c, around line 400:
~~~
         if( xResult > 0 )
         {
             /* A packet was received. No need to check for the PHY status now,
             but set a timer to check it later on. <em>/
             vTaskSetTimeOutState( &amp;xPhyTime );
             xPhyRemTime = pdMS_TO_TICKS( PHY_LS_HIGH_CHECK_TIME_MS );
             xResult = 0;
+            /</em> Indicate that the Link Status is high, so that
+            xNetworkInterfaceOutput() can send packets. */
+            ulPHYLinkStatus |= niBMSR_LINK_STATUS;
         }
         else if( xTaskCheckForTimeOut( &amp;xPhyTime, &amp;xPhyRemTime ) != pdFALSE )
         {
             xStatus = ulReadMDIO( PHY_REG_01_BMSR );
~~~
This has nothing to do with the fast retransmissions.  Ken Chang reported that in some cases, <code>xNetworkInterfaceOutput()</code> did not send packets, whereas the reception of packets was OK.  The above patch will fix that problem.
Please report about your findings about the fast retransmissions.
