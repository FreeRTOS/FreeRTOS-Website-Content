</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS+TCP for Renesas RX63N</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 22, 2018</div><div class="thread-post-content">Richard wrote:
<blockquote>
  The memory used by the stack is very configurable. You can run with
  small MSS and no TCP windowing for low memory consumption
</blockquote>
Those are the best methods to reduce memory usage of +TCP.
Adam Dunkels&#8217; earlier TCP/IP stack uIP, was indeed using a minimum of RAM.  I has a TCP window of 1 packet (MSS).  It wants an ACK after each packet sent.
FreeRTOS+TCP also has this &#8220;uIP&#8221; mode if you define:
~~~
    #define ipconfigUSE<em>TCP</em>WIN            ( 0 )
~~~
This will save lots of RAM, at the cost of some performance.
You also mentioned decreasing the size of the MTU.  That is indeed a very effective and compatible way of decreasing memory usage, for instance:
~~~
    #define ipconfigNETWORK_MTU            ( 512 )
~~~
When MTU equals 1500 bytes, the MSS equals 1460. So when you&#8217;re playing with MTU, use <code>ipconfigTCP_MSS</code> in stead of the constant <code>1460</code>:
~~~
    #define ipconfigTCP<em>RX</em>BUFFER<em>LENGTH     ( 3 * ipconfigTCP</em>MSS )
    #define ipconfigTCP<em>TX</em>BUFFER<em>LENGTH     ( 2 * ipconfigTCP</em>MSS )
~~~
The above defines the default buffer sizes for reception and transmission.
Do not define <code>ipconfigTCP_MSS</code> your self, it is already defined in <code>FreeRTOSIPConfigDefaults.h</code>.
If you are using TCP windows, you may want to reduce :
~~~
    #define ipconfigTCP<em>WIN</em>SEG_COUNT 64
~~~
FreeRTOS+TCP has a fixed amount of packet buffers.  Each buffer can hold a complete Ethernet packet.
You can choose to have all buffers allocated at start-up, or dynamically ( using <code>pvPortMalloc()</code> ).
Please check <code>BufferAllocation_1.c</code> versus <code>BufferAllocation_2.c</code>.
Regards, Hein

<blockquote>
  The RX62N I used has only 96KB of RAM, and my main application

Does that mean that 96 &#8211; 70 = 26 KB remains for TCP/IP ? That is well possible !
I just created a mini-project that creates a UDP port for logging, and a TCP port in listening mode.
In this case, I prefer to use <code>BufferAllocation_2.c</code>, because it will <code>malloc()</code> just enough bytes and only when needed.
The module <code>BufferAllocation_1.c</code> is preferable for high-performance systems, where there is plenty of RAM available.
A few parameters for <code>FreeRTOSIPConfig.h</code>  that help reducing the need for RAM:
~~~
/* The maximum number of network buffers: */
<h1>define ipconfigNUM<em>NETWORK</em>BUFFER_DESCRIPTORS    ( 10 )</h1>
/* The Maximum Transmission Unit: */
<h1>define ipconfigNETWORK_MTU                       (  512 + 40 )</h1>
/* Not using DHCP: */
<h1>define ipconfigUSE_DHCP                          0</h1>
/* Each TCP socket has a buffer for RX and one for TX.
Make them big enough to hold 1 packet: */
<h1>define ipconfigTCP<em>RX</em>BUFFER<em>LENGTH              ( 1 * ipconfigTCP</em>MSS )</h1>
<h1>define ipconfigTCP<em>TX</em>BUFFER<em>LENGTH              ( 1 * ipconfigTCP</em>MSS )</h1>
~~~
Measuring RAM/heap usage is always difficult. For my test, I was using an STM32F4.
The results below are just an estimate and <strong>may vary</strong> among different compilers and platforms:
Starting up the IP-task, creating lists and buffers: 17 KB
Creating a UDP socket: 100 bytes
Creating a TCP socket in listen mode: 376 bytes
Listening socket gets connected and creates buffers: 1088 bytes( 2 x MSS )
DATA and BSS, i.e. memory claimed at compile time: 900 bytes.
The listening socket was created with the socket option <code>FREERTOS_SO_REUSE_LISTEN_SOCKET</code>. That means that when a connection comes in, the listening socket <strong>turns into</strong> a connected socket.
Normally, the listening stays in the listening state and it will <code>accept()</code> many connections.
The amount of flash used by the +TCP and NetworkInterface.c : 21 KB.

Just a quick update about the code I posted on 2018-01-22. I found an error in it, in that it didn&#8217;t handle fragmented packets properly. In fact these packets weren&#8217;t cleared from the low level driver, resulting in clogged up buffers.
These problems started to show after reducing the MTU size. Some devices on our network were sending broadcasts every once in a while with packets greater than my MTU. And these packets are delivered to the software in fragments. 
Since these broadcast are not of interest to my device I can just ignore them, but I do have to make shure the buffers are cleared, which can be done by a small change in the function prvNetworkInterfaceInput( void ), in the file &#8220;FreeRTOS-Plus-TCPportableNetworkInterfaceRX63NNetworkInterface.c&#8221;:
Change the first if- statement to:
~~~
    if( ( pxDMARxDescriptor->status &amp; ACT )==0 )
    {
        /* Get the Frame Length of the received packet */
        xReceivedLength = pxDMARxDescriptor->RFL;
<pre><code>    pucTemp = (uint8_t *) pxDMARxDescriptor-&gt;buf_p;
    if( xReceivedLength==0 )
    {
        //When small buffers are used, segmented packets can be expected.
        //These are usually broadcasts which can be ignored.
        //if a packet is not marked with an end bit, these will have zero length
        //So we consume all zero-length packets here.
        EMAC_UpdateRxConsumeIndex();
    }
}
else
{
    xReceivedLength = 0;
}
</code></pre>
~~~
With this change I now have been running this driver for a couple of days now without a single problem, and the amount of RAM used is nothing to complain about.
So thanks Stephan for sharing the uip driver, but I will proceed with the FreeRTOS+TCP driver, as I highly appriciate the BSD style too.
