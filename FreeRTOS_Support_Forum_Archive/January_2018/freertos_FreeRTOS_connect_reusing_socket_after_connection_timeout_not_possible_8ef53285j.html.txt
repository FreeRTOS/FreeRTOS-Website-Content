</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_connect(): reusing socket after connection timeout not possible?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 17, 2018</div><div class="thread-post-content">Hi Ronald, I am not sure what the BSD rules say about this, but I would always create a new client socket for each attempt to <code>connect()</code> to a peer.  So once <code>connect()</code> has returned an error, close the socket, and start with a new one.
More in general: a socket only has one life cycle.
One exception is possibly a socket that listens and calls <code>accept()</code>: it can be used for ever as it always stays in the same listening state.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_connect(): reusing socket after connection timeout not possible?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 18, 2018</div><div class="thread-post-content">Here is some more information about the behaviour of <code>FreeRTOS_connect()</code> :
<code>FreeRTOS_connect()</code> starts by looking-up the MAC-address of the target.  If the IP-address has an entry in the ARP table, this happens very quickly.  When an ARP look-up is needed, it will take at least half a second.
The number of attempts ( sending a <code>SYN</code> ), and the time-outs between them are fixated in the library source code:
~~~
    0.000  sec  SYN-1
    3.000  sec  SYN-2
    9.000  sec  SYN-3
~~~
You can either <code>connect()</code> to a remote device in a blocking way, or by polling.
Blocking: the socket option <code>RCVTIMEO</code> determines the maximum time that <code>FreeRTOS_connect()</code> will wait for a connection:
~~~
    /* Wait at most 5 seconds. */
    TickType_t xTimeout = pdMS_TO_TICKS( 5000ul );
    FreeRTOS_setsockopt( xSocket, 0, FREERTOS_SO_RCVTIMEO, ( void * ) &amp;xTimeout, sizeof( BaseType_t ) );
~~~
Mind that a useful value for <code>RCVTIMEO</code> is either +/- 2, 5, or 11 seconds.
When using <code>FreeRTOS_select()</code>, a successful <code>FreeRTOS_connect()</code> will be notified as a <code>eSELECT_WRITE</code> event.  A successful acceptance of a new client triggers a <code>eSELECT_READ</code> event.
You can find complete examples of using <code>FreeRTOS_select()</code> in the &#8220;protocols&#8221; directory ( FTP and HTTP server ).
When using &#8220;non-blocking&#8221; ways to connect, you can call this function to see if a connection was established:
~~~
/* returns pdTRUE if TCP socket is connected */
BaseType_t FreeRTOS_issocketconnected( Socket_t xSocket );
~~~
You may also call <code>FreeRTOS_recv()</code> <strong>before</strong> the connection is established, to see any errors that might occurs.
If you do not want to block on <code>FreeRTOS_connect()</code>, and you don&#8217;t want to use <code>FreeRTOS_select()</code>, there is a third way.  Let your task block on a semaphore, and bind that semaphore to all sockets that it owns:
~~~
/* Define this in you FreeRTOSIPConfig.h */
<h1>define ipconfigSOCKET<em>HAS</em>USER_SEMAPHORE        1</h1>
<pre><code>/* Bind a semaphore to a socket. */
FreeRTOS_setsockopt( xSocket, 0, FREERTOS_SO_SET_SEMAPHORE, ( void * ) &amp;xMySemaphore, sizeof( xMySemaphore ) );
</code></pre>
~~~
The semaphore will be given to for every event of interest: RX, TX, connect succeeded, acceptance of a client.
The same semaphore can be &#8220;bound&#8221; to many sockets of all types.
I attached a working &#8220;hello world&#8221; example of this method: &#8220;socket<em>using</em>semaphore.c&#8221;

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_connect(): reusing socket after connection timeout not possible?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 29, 2018</div><div class="thread-post-content"><blockquote>
  I have a question that is related to the question above.
  When I use FreeRTOS_shutdown() to close a TCP connection but I don&#8217;t
  close the socket, can I use the same socket to reconnect?
</blockquote>
That is not possible.  I think that other OS&#8217;s have the same behaviour in this respect.
<blockquote>
  When I reboot the remote side, my device running FreeRTOS+TCP thinks
  it is still connected and +TCP refuse to reconnect. The only solution
  is closing the socket?
  I have solved the issue with ipconfigTCP<em>KEEP</em>ALIVE = 1.
  The connection will be closed automatically and I can reconnect again
  without closing the socket.
</blockquote>
Ah yes of course. I was assuming that your application is sending data continuously.  The peer only gets a chance to send a RST when it receives some data.
Personally I prefer to check the liveliness of a connection by sending AYA ( Are You Alive ) messages to the other application, as real TCP data.  In some rare cases, a low-level KEEP-ALIVE messages is understood and responded to, while the application is not able to send data for whatever reason.
But often we are only developing one side of the communication, the other side being a &#8220;black box&#8221;.  In those cases, the <code>ipconfigTCP_KEEP_ALIVE</code> option is very useful.
Regards.
