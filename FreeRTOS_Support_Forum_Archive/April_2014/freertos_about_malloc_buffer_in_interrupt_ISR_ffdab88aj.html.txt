</div></div><div class="thread-post"><h3 class="thread-post-title">about malloc buffer in interrupt ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/labelsr">labelsr</a> on April 13, 2014</div><div class="thread-post-content">Yes, it is true that malloc buffer in INT ISR is not a good idea. If malloc is not permitted, what should I do?
  Can I portDISABLE<em>INTERRUPTS() before malloc() and portENABLE</em>INTERRUPTS() after malloc()?
</div></div><div class="thread-post"><h3 class="thread-post-title">about malloc buffer in interrupt ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on April 13, 2014</div><div class="thread-post-content">If you really need to use malloc/free in interrupts, then you need to bracket all calls to them in something that keep you from reentering it. This could be a portDISABLE_INTERRUPTS() outside of interrupt routines.
A better solution, especially if your ISR just needs to free a buffer, is to create a queue that holds void* pointers, and have the ISR queue up the pointer, then a high priority task waits on the queue and frees it.
Even better could be to set up a pool of buffers that your application acquires one to fill, pass it around, and when done it is put back in the pool. This does require that you analysis your usage to set up the sizes of the pools.
The BIG problem with applications that use malloc/free in operation is that you really do need to test EVERY malloc call for failure and handle it in a reasonable manner, and this code is very hard to test as part of a full system. (malloc in startup is much more consistent, and thus testable) 
</div></div><div class="thread-post"><h3 class="thread-post-title">about malloc buffer in interrupt ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on April 13, 2014</div><div class="thread-post-content">You are going to have problems using the heap_n.c files that come with FreeRTOS as they (at least the one I just looked at) only suspend the scheduler when allocating memory &#8211; they don&#8217;t disable interrupts.  Therefore you could get data corruption if a task and interrupt call malloc at the same time.  You could write your own versions that disable interrupt instead of just disabling the scheduler, but if you get away with that or not will actually depend on the port you are using and the priority of the interrupt.
Better to use something like the mechanism described on the following page &#8211; make the priority of the timer task the highest priority in your system to ensure the pended function executed immediately that the interrupt has completed.
http://www.freertos.org/xTimerPendFunctionCallFromISR.html
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">about malloc buffer in interrupt ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/labelsr">labelsr</a> on April 15, 2014</div><div class="thread-post-content">Thank you for your reply.
I migrate mem-pool code to my platform,it is high-efficience. So I think disable INT before POOL<em>ALLOC() and re-enable INT after POOL</em>ALLOC() is OK in the ISR. In my opinion, if MALLOC is in ISR, I need to disable INT before MALLOC and re-enable INT after it. If it is in task, I need to suspend scheduler before it and resume scheduler after it. Am I right?
</div></div><div class="thread-post"><h3 class="thread-post-title">about malloc buffer in interrupt ISR</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on April 15, 2014</div><div class="thread-post-content">If you use malloc in an ISR, then <em>ALL</em> calls to malloc and free need to be bracketed by the equivalent of disable interrupt/enable interrupt. In the ISR itself you may need something a bit different, as you don&#8217;t want to totally reenable interrupts until the ISR is done.
