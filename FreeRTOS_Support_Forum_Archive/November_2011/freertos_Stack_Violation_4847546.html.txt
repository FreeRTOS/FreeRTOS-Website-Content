</div></div><div class="thread-post"><h3 class="thread-post-title">Stack Violation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/davedoors">davedoors</a> on November 28, 2011</div><div class="thread-post-content">The kernel creates at least one, and possibly two tasks, when you call vTaskStartScheduler&#40;&#41;. So tasks are being created, even if you don&#8217;t create them in your code.  
How does it know the stack has been violated? What check is it performing to determine that? If it is just checking that the stack pointer is in the stack segment as configured by your linker script then the warning message can probably be ignored. I know this is how the IAR compiler works, so it is likely to be the same in your ISE. When a task is running, the stack pointer will &#40;correctly&#41; point to the stack allocated to that task, which will come from a heap somewhere, and be outside of the memory region the tool expects it to point into.

</div></div><div class="thread-post"><h3 class="thread-post-title">Stack Violation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 28, 2011</div><div class="thread-post-content">As DaveDoors said, it might just be complaining that the stack pointer is outside of its .stack section.&nbsp; Looking at the print out above, your .stack section is between 0x2850 and 0x504f.&nbsp; That is nearly 11K of stack that will be used by main&#40;&#41;.&nbsp; The tasks themselves will use a stack from the FreeRTOS heap.&nbsp; When the warning is output, look at the stack pointer value to see where it is.&nbsp; If a task is running it will point somewhere in the FreeRTOS heap.&nbsp; If a task is not executing, it should be in this 11k section somewhere.  
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack Violation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/uecasm">uecasm</a> on April 16, 2012</div><div class="thread-post-content">I was having the same issue, and further noticed that if I enabled exceptions via Xil&#95;ExceptionsEnable&#40;&#41; then the processor halted on a stack violation when vTaskStartScheduler is called.  
The &#8220;quick&#8221; workaround would be to simply disable the stack protection exception in the IP core configuration for the CPU, and rely on FreeRTOS&#8217;s stack protection mechanism instead.  
However it&#8217;d be nice if FreeRTOS could be modified to support the CPU-based stack protection instead, as it provides instant feedback instead of detecting it only after-the-fact or on task switch &#40;with the possibility of missing it entirely depending on the nature of the error&#41;.  
I had a quick look at the code and what would be required to do it; the basics are pretty simple: portRESTORE&#95;CONTEXT &#40;and anything else which switches R1 to a different stack&#41; needs to set the SLR and SHR registers &#40;which only exist conditionally&#41; to the extent of the stack being restored prior to restoring R1 to that stack.&nbsp; Unfortunately I couldn&#8217;t find any easy way of determining the extent of the stack from there.&nbsp; The logical &#40;at least to me&#41; way to do it would be to include those as context registers as well, and initialise them from pxPortInitialiseStack, but unfortunately that isn&#8217;t passed the stack extents.&nbsp; The next most logical is to pull them out of the TCB, but that&#8217;s private to tasks.c, and in any case only includes one or other of the ends &#40;plus the current top&#41;, which isn&#8217;t sufficient to calculate the extent.&nbsp; &#40;Which in turn means that FreeRTOS&#8217; own stack checking can&#8217;t check for stack underflow.&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack Violation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/uecasm">uecasm</a> on April 17, 2012</div><div class="thread-post-content">Ok, I think I figured out a way to do it by using portUSING&#95;MPU&#95;WRAPPERS=1 and using xMPU&#95;SETTINGS to contain the stack info.&nbsp; &#40;Which is not entirely unreasonable, if you consider stack protection to be a limited MPU application.&#41;  
It&#8217;s a little bit messy though since it also forced me to define stubs for all the MPU&#95;&#42; functions, which at the moment all just call back to the normal implementation, and hack my LD script for the new sections it created.&nbsp; &#40;Though I suppose that since the Microblaze can have an MMU enabled, someone might eventually want to do a full implementation of that.&#41;
</div></div><div class="thread-post"><h3 class="thread-post-title">Stack Violation</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on April 17, 2012</div><div class="thread-post-content">A port of FreeRTOS that implements the MPU stubs is only available for the Cortex-M3, which is why the subs just point back to the original functions for the Microblaze.&nbsp; If you want the MPU functionality to protect the stack on a Microblaze you will have to implement the MPU changes yourself in the port layer.  
Regards.
