  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">XSemaphoreGiveFromISR takes forever sometimes</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cynergizer">cynergizer</a> on November 30, 2011</div><div class="thread-post-content">I am using xSemaphoreGiveFromISR, which normally takes just a few usecs to execute, but everyone once in a while it takes 54 ms to execute.&nbsp; I&#8217;ve tracked this down to prvAddTaskToReadyQueue in vTaskRemoveFromEventList in xQueueGenericSendFromISR.&nbsp; I&#8217;m using an LPC2378 running at max speed of 72Mhz.&nbsp; I do allow task preemption, but I do not nest interrupts.&nbsp; My timing measurements are from wiggling a pin and measuring it on scope, triggering via excessive pulse width.&nbsp; Searching through the forum, it looks like someone had a similar problem which Richard thought might be caused by a stack overflow?&nbsp;
</div></div><div class="thread-post"><h3 class="thread-post-title">XSemaphoreGiveFromISR takes forever sometimes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cynergizer">cynergizer</a> on November 30, 2011</div><div class="thread-post-content">This problem seems to go away when I turn off MAM.&nbsp; Bizarre.
</div></div><div class="thread-post"><h3 class="thread-post-title">XSemaphoreGiveFromISR takes forever sometimes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on December 1, 2011</div><div class="thread-post-content"><blockquote>
  I&#8217;ve tracked this down to prvAddTaskToReadyQueue in vTaskRemoveFromEventList 
</blockquote>
prvAddTaskToReadyQueue&#40;&#41; calls vListInsertEnd&#40;&#41;, which is a deterministic function &#40;it always takes the same time to execute&#41;.  
<pre><code>void vListInsertEnd( xList *pxList, xListItem *pxNewListItem )
{
volatile xListItem * pxIndex;
    /* Insert a new list item into pxList, but rather than sort the list,
    makes the new list item the last item to be removed by a call to
    pvListGetOwnerOfNextEntry.  This means it has to be the item pointed to by
    the pxIndex member. */
    pxIndex = pxList-&gt;pxIndex;
    pxNewListItem-&gt;pxNext = pxIndex-&gt;pxNext;
    pxNewListItem-&gt;pxPrevious = pxList-&gt;pxIndex;
    pxIndex-&gt;pxNext-&gt;pxPrevious = ( volatile xListItem * ) pxNewListItem;
    pxIndex-&gt;pxNext = ( volatile xListItem * ) pxNewListItem;
    pxList-&gt;pxIndex = ( volatile xListItem * ) pxNewListItem;
    /* Remember which list the item is in. */
    pxNewListItem-&gt;pvContainer = ( void * ) pxList;
    ( pxList-&gt;uxNumberOfItems )++;
}
</code></pre>
<blockquote>
  This problem seems to go away when I turn off MAM.&nbsp; Bizarre.
</blockquote>
Not really. The original 2368 and 2378 parts have known bugs in the MAM. Check the errata for your revision to see if the bug is still there. I think the FreeRTOS demo for the 2368 always turns the MAM off for that reason.
</div></div><div class="thread-post"><h3 class="thread-post-title">XSemaphoreGiveFromISR takes forever sometimes</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cynergizer">cynergizer</a> on December 5, 2011</div><div class="thread-post-content">Hi Edwards,<br />
