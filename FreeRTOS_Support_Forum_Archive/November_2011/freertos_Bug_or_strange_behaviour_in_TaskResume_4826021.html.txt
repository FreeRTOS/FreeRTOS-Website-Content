There are probably more complex scenarios where this deadlock can occur too, where preemptive context switches happen at various times, but basically I think you have a test where the correct behaviour would be for both tasks to end up in the suspended state.

</div></div><div class="thread-post"><h3 class="thread-post-title">Bug or strange behaviour in TaskResume ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 18, 2011</div><div class="thread-post-content">Part of the problem is that the definition of Resume is to be a hop if the task is already running, so a suspend-resume is different than a resume-suspend &#40;if the task is currently Ready. This means that your program has a race condition is the suspend and resume for a task are coming from different tasks, and they don&#8217;t have anything to make sure that they happen in the right order.  
Better to use a semaphore given by one task and taken by the other to do the suspension, as it doesn&#8217;t matter if the give happens before of after the take, you just one proceed from the take until both happen.  
Even better &#40;unless this is just a learning exercise&#41; if you have two operations at the same priority, that are to alternate operations, just put them in one task.and save resources.
</div></div><div class="thread-post"><h3 class="thread-post-title">Bug or strange behaviour in TaskResume ?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 18, 2011</div><div class="thread-post-content">Ok, I have run this and looked at it in detail, and cannot see anything wrong with the kernel, but can with your test code.  
Before showing you the scenario I observed, an explanation on the behaviour:&nbsp; When a task is removed from the suspended list, it is added to the end of the ready list for tasks of that priority.&nbsp; This is so it is the last task, of that priority, that is selected to run.&nbsp; It has to be this way to prevent a task from continuously being selected to run.&nbsp; That means, the scenario 2 I described above was not quite correct.&nbsp; When there are only two tasks of a given priority, and a start condition that has one task in the Running state and one task in the Suspended state, then the running task resuming the suspended task will not result in the resumed task running immediately.&nbsp; When it is resumed, it is added to the <strong>end</strong> of what was a list of 1 task, and the following yield therefore re-selects the task that was already Running.&nbsp; Below is the corrected scenario 2, which is what I observed, and at all times the number of items in each list was shown as I would expect:  
1&#41; Task 1 runs and suspends itself.  
2&#41; Task 2 runs and resumed Task 1.&nbsp; It continues running though, and suspends itself.  
3&#41; Task 1 is now the only task that can run, so runs, resumes task 2, carries on running, and suspends itself.  
4&#41; Task 2 is now the only task that can run, so runs, resumes task 1, carries on running, and suspends itself.  
5&#41; Task 1 runs, once again, loops back to the top of its for&#40; ;; &#41; loop, and suspends itself without ever resuming Task 2.  
Now both tasks are in the suspended state, although &#8216;a&#8217; has been incremented &#40;once by each task I think&#41;.  
I think this is quite simply an error in the logic of your code.  
Regards.
