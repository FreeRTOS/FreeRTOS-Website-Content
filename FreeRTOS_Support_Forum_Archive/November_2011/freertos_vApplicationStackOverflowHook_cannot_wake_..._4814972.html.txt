</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationStackOverflowHook cannot wake &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on November 14, 2011</div><div class="thread-post-content">If you are not running on a system with an MMU, once you have experienced a stack overflow, the system may well be now in an unstable state and not able to continue.  
I am also not sure what parts of the API are allowed to be called from the stack overflow routine, and I suspect trying to force a task switch may not be allowed there, as the stack check is happening within the task switch routine.  
Normally the overflow hook will be code to somehow output an error message somewhere if possible with primitive code, and then restart the processor.  
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationStackOverflowHook cannot wake &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 14, 2011</div><div class="thread-post-content">Generally, unless you are using an MPU port, you cannot recover from a stack overflow.&nbsp; When you have an MPU, you get notification of the stack overflow before any corruption happens as a trap is triggered as soon as a write outside of the region allocated to the stack is attempted.&nbsp; Most ports don&#8217;t use an MPU, and you only know a stack overflow has happened some time after it has happened &#8211; and at that point you don&#8217;t know what the system state is so all you know is you know nothing.&nbsp; Generally a stack overflow will corrupt a TCB, so the task you are trying to yield from is already corrupt.&nbsp; Even if you are lucky enough that something sensible happens, you will just re-enter the context switch and detect the stack overflow again.  
Regards.  
Also consider that the stack overflow is called from the context switch mechanism.&nbsp; You cannot attempt to re-enter the context switch by requesting a context switch when you are already in a context switch &#40;if that makes any sense at all ;o&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationStackOverflowHook cannot wake &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on October 26, 2012</div><div class="thread-post-content">The context that FreeRTOS calls the vApplicationStackOverflowHook is not suitable for making calls to most of the FreeRTOS API as you are in the middle of the scheduler.  
As I said before, at the point where you have detected that you have overflowed the stack, you are really in a state where you can not trust your system, so trying to continue is really not advised.
</div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationStackOverflowHook cannot wake &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/yuantuh">yuantuh</a> on October 28, 2012</div><div class="thread-post-content">Thank you very much. </div></div><div class="thread-post"><h3 class="thread-post-title">vApplicationStackOverflowHook cannot wake &#8230;</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on October 28, 2012</div><div class="thread-post-content">Yes. At the point that it has detected the problem, there is significant chance that your system memory is corrupted. Any code there should not depend on the rest of the system being operational.&nbsp; An infinite loop is one reasonable process &#40;possible blinking an led also&#41;, or rebooting the system. The reboot can possible pass on the information about why the reboot was caused and the new invocation of the system may be able to send out a message about it, hopefully before the problem reoccurs.
