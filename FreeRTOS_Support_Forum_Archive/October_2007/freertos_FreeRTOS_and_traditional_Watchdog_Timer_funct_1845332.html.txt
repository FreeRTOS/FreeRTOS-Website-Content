  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS and traditional Watchdog Timer funct</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joconnor37">joconnor37</a> on October 15, 2007</div><div class="thread-post-content">Could I broach the general subject of Watchdog Timer functionality when using FreeRTOS? I have completed a few modest real-time embedded systems projects with PIC 18Fxxxx MCUs over the last few years, always without a RTOS. I used the traditional &quot;super loop&quot;, switch statements controlled by system states etc, etc. I always implemented the Watchdog Timer &quot;liberally&quot; at portions of the code.
I think to similarly liberally implement the Watchdog Timer still in FreeRTOS based projects &#8211; e.g. start the Watchdog Timer at start of a &quot;potentially problematic&quot; function such as a read/write on the I2C bus, so that in event of &quot;failure&quot; the program gets kicked out of the function by a Watchdog Timer reset. This resets PC back to first executable. Any thoughts on the ramifications of this when using FreeRTOS? Should the Watchdog Timer functionality be at the &quot;task level&quot; or remain at the &quot;C function level&quot;, for example?
Kind Regards,
John O&#8217;Connor
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS and traditional Watchdog Timer funct</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on October 15, 2007</div><div class="thread-post-content">There are many different ways of using a watchdog timer in multi threaded applications.&nbsp; Some are quite complex, but unless you have a safety critical system I would suggest keeping things simple.&nbsp; 
Unlike your previous single threaded applications your watchdog should look for hangs or errors within individual functions, and within the scheduler itself &#40;not that the scheduler will ever go wrong of coarse :o&#41;.
One technique for this to have a watchdog variable within each task &#8211; this could be Boolean or a counter, I normally use the latter.&nbsp; For example, each task increments a counter at strategic places within the code, then a higher priority task &#40;or a tick hook&#41; periodically checks that all the counters within the system are still incrementing.&nbsp; If all counters are incrementing then the watchdog is kicked.&nbsp; If any counters unexpectedly retain their value for a period of time then it is assumed that the task is bad in some way, and the watchdog is stopped &#40;or the system &#91;or just the task&#93; manually reset in software, the watchdog then being a back for a total failure&#41;.&nbsp; If a task finds an error in its function it simply stops incrementing its counter.&nbsp; If a task hangs, then the counter will stop automatically.
This mechanism is implemented in a basic way by the demo applications that come with each FreeRTOS.org port.&nbsp; Most of these implement a &#8216;check&#8217; task, or &#8216;check&#8217; hook function.&nbsp; This looks at all the other tasks to ensure they are running as expected.&nbsp; In this case though, rather than using a watchdog to fix an error, the check task simply outputs some signal &#40;LED or LCD&#41; to indicate that an error has been found.
You could use the idle task to check the other task are still running.&nbsp; This will then also ensure that the system is not overloaded.&nbsp; If the idle task ever gets starved out then the watchdog will fire.
Hope this helps.
Regards.

I have implemented watchdog timer driver using freertos on <strong>LPC1114</strong> &#40;NGX Base Board&#41;. I have used the problem statement above and a task whose priority is set to be idle task priority is monitoring 4 tasks where a counter is incremented. If the counter in any of the tasks stops then the idle task doesn&#8217;t feed the watchdog timer and the system is reset by watchdog.We have implemented this as <strong><em>watchdog timer service</em></strong> as in the tasks which the developer thinks are very critical are the ones that feed idle task which further feeds watchdog timer counter.<br />
