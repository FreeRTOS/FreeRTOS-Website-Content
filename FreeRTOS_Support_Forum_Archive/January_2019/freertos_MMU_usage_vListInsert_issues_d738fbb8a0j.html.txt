  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">MMU usage vListInsert issues</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on January 17, 2019</div><div class="thread-post-content">I have been working on MMU support with task stack protection for the Cortex A5, and have the MMU working as intended on my part.  However, I am running into this issue, that the vListInsert(and probably more) create a list that writes into a different task space, which causes a permission fault.
~~~
    pxNewListItem->pxNext = pxIterator->pxNext;
    pxNewListItem->pxNext->pxPrevious = pxNewListItem;//<--- fault location
 pxnewlistitem->pxPrevious = pxIterator;
    pxIterator->pxNext = pxNewListItem;
~~~
It faults because pxNewListItem->pxNext->pxPrevious is in the other tasks space.
Any ideas what to do, or whether to just give this up entirely?
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 17, 2019</div><div class="thread-post-content">I don&#8217;t know how you have set up the MPU on the Cortex-A, but in the 
Cortex-M MPU port we run the kernel code in privileged mode, then it can 
access the memory allocated to unprivileged tasks.
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on January 17, 2019</div><div class="thread-post-content">When does it switch? Is the kernel code  started yet after you call vTaskDelay() which ends up calling vListInsert?
The Cortex A5 doesn&#8217;t have an MPU, rather an MMU, which takes a bit different thinking.  So the createtask allocates out of a page aligned pool, then each allocated pool is set to be protected from other asid&#8217;s.
On the A port, it would appear that tasks are running in SYS mode, I&#8217;m not sure about the thinking behind that.
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 17, 2019</div><div class="thread-post-content">I&#8217;m afraid it is not clear to me what you are trying to achieve.  Our 
MPU (noting that you have MMU, which in the past we have used as a kind 
of MPU just without virtual memory) port is used to enable different 
tasks to run at different privilege levels, and to isolate different 
memory regions.  A task can run unprivileged, with a switch to privilege 
being effected using an SVC instruction each time it calls a FreeRTOS 
API function.  I think in all memory protected cases the OS has to run 
with privileges (kernel mode) otherwise you are going to get the issue 
you are reporting &#8211; the kernel is isolated from the memory it needs to 
access.
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on January 17, 2019</div><div class="thread-post-content">I&#8217;m trying to achieve task memory protection.
It isn&#8217;t clear to me where to insert elevation, as the task calls vtaskdelay and there isn&#8217;t really a defined place to say it is no longer user mode.
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 17, 2019</div><div class="thread-post-content">Elevation should happen prior to calling vTaskDelay().  This is normally 
done by having the API function not a direct C subroutine call, but an 
SVC call, SVC being the only way to programmatically raise privilege. 
We take a slightly simpler approach though by wrapping vTaskDelay() in a 
function called MPU<em>vTaskDelay() that raises privilege then calls the 
standard vTaskDelay().  The standard vTaskDelay() must be in a memory 
areas that is marked as privileged execution only, and the raising of 
the privilege must check that the source of the SVC was one of the 
MPU</em>nnn() function wrappers.
</div></div><div class="thread-post"><h3 class="thread-post-title">MMU usage vListInsert issues</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/friesen">friesen</a> on January 18, 2019</div><div class="thread-post-content">Thank you, this is making sense now. I suppose MMU support is too outside of what average FreeRTOS applications need.  For me, it is more about developing a complex program and reducing development time.

<h1>else</h1>
<h1>define vPortResetPriviledge</h1>

<h1>endif</h1>
