  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS_recv returns pdFREERTOS_ERRNO_ENOTCONN but also all the data</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/joehinkle">joehinkle</a> on January 3, 2019</div><div class="thread-post-content">How do you delete a post?
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS_recv returns pdFREERTOS_ERRNO_ENOTCONN but also all the data</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on January 5, 2019</div><div class="thread-post-content">Just in case some readers are curious about the title of this post, here is an explanation:
It is not uncommon to shut down a TCP connection immediately after sending some data.
When your application runs on a laptop, it is usually safe to do the following:
<pre><code>send( socket, buffer, length, 0 );
shutdown( socket, SHUT_RDWR );
close( socket );
</code></pre>
When an application closes a socket, the OS will take care of the socket and make sure that the data will be delivered before the socket is destroyed.
Under FreeRTOS+TCP, when you close a socket (<code>FreeRTOS_closesocket()</code>), the socket will be destroyed immediately and the TCP connection will be aborted in a non-gracious way.
You will have to wait for the connection to get closed (<code>-pdFREERTOS_ERRNO_ENOTCONN</code>).
~~~
    FreeRTOS<em>send( xSocket, pcBuffer, uxLength, 0 );
    FreeRTOS</em>shutdown( xSocket, FREERTOS<em>SHUT</em>RDWR );
    for( ;; )
    {
    BaseType_t xResult;
<pre><code>    xResult = FreeRTOS_recv( xSocket, pcBuffer, sizeof( pcBuffer ), 0 );
    /* Testing for -pdFREERTOS_ERRNO_EAGAIN is actually not necessary
    because FreeRTOS_recv() will never return that pseudo error. */
    if( ( xResult &lt; 0 ) &amp;&amp; ( xResult != -pdFREERTOS_ERRNO_EAGAIN ) )
    {
        break;
    }
}
FreeRTOS_closesocket( xSocket );
</code></pre>
~~~
Calling <code>shutdown()</code> results in sending the FIN flag. But as long as the socket has data queued to be sent, the FIN flag will not be set. Only the TCP packet carrying the last bytes will have FIN set.
This mechanism can be seen when using the FTP server: files with an arbitrary length are being sent. The connection gets closed immediately and gracefully after the last byte.
At the <strong>receiving end</strong>, it may happen that the connection is closed while the socket <strong>still holds</strong> received data.
<code>FreeRTOS_recv()</code> will do 5 things:
<ul>
<li>If the socket is invalid, return <code>-pdFREERTOS_ERRNO_EINVAL</code></li>
<li>If the RX stream is not empty, return the number of bytes read</li>
<li>If the connection is closed, return <code>-pdFREERTOS_ERRNO_ENOTCONN</code></li>
<li>If the socket has a memory problem, <code>-pdFREERTOS_ERRNO_ENOMEM</code></li>
<li>Or else, if the receive time-out is non-zero: wait for data in a blocking way.
Return either 0 or the number of bytes</li>
</ul>
Finally, one thing about <code>send()</code> / <code>shutdown()</code>: when calling <code>send()</code>, the IP-task will be triggered to start sending the data immediately. It may happen that the packet carrying the last bytes does not have the FIN flag set.
That is not a real problem, it is just less efficient.
When you know that <code>send()</code> is called for the last time, you can set a flag in the socket:
~~~
    BaseType_t xTrueValue = 1;
<pre><code>FreeRTOS_setsockopt( xSocket,
                     0,
                     FREERTOS_SO_CLOSE_AFTER_SEND,
                     ( void * ) &amp;xTrueValue,
                     sizeof( xTrueValue ) );
FreeRTOS_send( xSocket, pcBuffer, uxLength, 0 );
/* shutdown() will be done automatically.
Just wait for the connection to close as described above. */
</code></pre>
~~~
This is a small optimisation found in FreeRTOS+TCP only.
