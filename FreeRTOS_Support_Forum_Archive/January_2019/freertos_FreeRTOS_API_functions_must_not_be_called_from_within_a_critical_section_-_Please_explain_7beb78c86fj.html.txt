  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">FreeRTOS API functions must not be called from within a critical section &#8211; Please explain</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ingamow">ingamow</a> on January 14, 2019</div><div class="thread-post-content">From the documentation of taskENTER_CRITICAL(), I&#8217;ve seen this info <strong>&#8220;FreeRTOS API functions must not be called from within a critical section&#8221;</strong>. In one of my projects using Cortex M0, I happen to use xQueueSendFromISR() from within a critical section in an ISR. I face no problems in using this, so just wanted to know the <strong>EXACT TECHNICAL REASON</strong> of why this is mentioned. 
*P.S : I could only find Answers like &#8220;As a general Rule of Thumb &#8230;&#8221; . Can anyone please explain it in detail ? *
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS API functions must not be called from within a critical section &#8211; Please explain</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on January 14, 2019</div><div class="thread-post-content">First, you should not be calling taskENTER<em>CRITICAL inside an ISR, as it doesn&#8217;t end in FromISR (there is on many port a taskENTER</em>CRITICAL<em>FROM</em>ISR routine that can be used if the port supports nested interrupts), and I don&#8217;t think that function has the same note. (I don&#8217;t know off hand if the M0 allows nested interurpts so it provides/needs a critical section in ISRs).
The big issue is that if you call a FreeRTOS function that blocks inside a critical section, you run into an issue that the taskENTER_CRITICAL call says no other task or ISR will be run during it, but the blocking says that some other task should be run, so the result will by necessity break some expectation. ISRs never block, so this can&#8217;t be an issue for a critical section in an ISR.
Many ports implement the scheduler call via a interrupt call, so it can&#8217;t be called in a critical section.
</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS API functions must not be called from within a critical section &#8211; Please explain</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on January 14, 2019</div><div class="thread-post-content">The Cortex-M0 does not have a basepri register, so critical sections 
don&#8217;t mask just a subset of interrupt priorities as per the 
Cortex-M3/4/7 ports, but all interrupts &#8211; so interrupt nesting isn&#8217;t 
supported directly by the kernel for that port.  Therefore a critical 
section inside an interrupt is not necessary, and the &#8220;From ISR&#8221; 
versions of those functions referred to by Richard D are just null macros.
The &#8216;rule of thumb&#8217; description is given because it is not only 
dependent of the API function in use, but also dependent on the FreeRTOS 
port in use.  For example, consider a port that uses a trap to perform a 
context switch synchronously &#8211; in a critical section the trap may just 
cause an exception (because of the state of the processor when you are 
in a critical section), whereas other architectures may not.  In any 
case, anything that is supposed to block of switch to a higher priority 
task that doesn&#8217;t because you are in a critical section can cause 
application logic errors.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS API functions must not be called from within a critical section &#8211; Please explain</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on January 15, 2019</div><div class="thread-post-content">If the port supports nested interrupts, then taskENTER<em>CRITICAL</em>FROM<em>ISR, which should be called something like:
uint32</em>t mask = taskENTER<em>CRITICAL</em>FROM<em>ISR();
will block interrupts up to the level that is allowed to use the FreeRTOS FromISR API, from occuring until the next occurance of
taskEXIT</em>CRITICAL<em>FROM</em>ISR(mask);
(note the additon of a parameter in the calls)
If it doesn&#8217;t support nested interrupts, then there is no need to do this, as nothing will be able to interfere.
If nesting IS possible (or was in an earlier version of the code) the Critical Section may have been needed if some other ISR might play with that Queue also.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS API functions must not be called from within a critical section &#8211; Please explain</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on January 17, 2019</div><div class="thread-post-content">A context switch can&#8217;t happen in a critical setion, thats why you have a critical section, so you can&#8217;t switch to some new context.
The issue comes if you want to test the status of something, and react appropriately, and not have to worry that something else might have changed the conditon. Note that xQueueSendFromISR internally uses a critical section for accessing the queue so it can test that there is room, and using it, without problems that someone else takes the space that it thought was available.
In the code you posted, which had to be incomplete as the critical section was only ended if the send succedded, perhaps the else clause to handle a failed send needed to assume that some other ISR wasn&#8217;t going to come along and make room in the queue during its recovery. That would require a critical section.
It could also be that at one point there was more code after the Send and before the end critical, that has since been removed, and now the critical section isn&#8217;t needed in this version.
