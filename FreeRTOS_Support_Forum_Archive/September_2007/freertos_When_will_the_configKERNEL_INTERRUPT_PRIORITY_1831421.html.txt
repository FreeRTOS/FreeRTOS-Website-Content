Best regards,
Frank Andersen
</div></div><div class="thread-post"><h3 class="thread-post-title">When will the configKERNEL_INTERRUPT_PRIORITY</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 25, 2007</div><div class="thread-post-content">The ARM7 is a pain on this front as the interrupt controller is not part of the core &#8211; so there is not one solution for all ARM7 devices.&nbsp; The normal way is to use the FIQ, but I think you have already indicated that this is not an option on your processor.
To implement the configKERNEL&#95;INTERRUPT&#95;PRIORITY feature you need to change the enable/disable interrupt macros to only enable/disable interrupts below the kernel priority.&nbsp; I think this should be straight forward.&nbsp; You can keep the kernel at the lowest priority to make it easier.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">When will the configKERNEL_INTERRUPT_PRIORITY</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/frankandersen">frankandersen</a> on September 27, 2007</div><div class="thread-post-content">Well, yes I agree that the ARM7 intrrupt controller is a pain. 
But if I get my USB bulk interrupt to run outside the FreeRTOS, it will still be delayed a bit by eg. the TimerTick interrupt, as interrupts still not are nested?
And then I would need a Task to monitor a global variable to signal form the interrupt, runing outside of FreeRTOS, right?
Best regards,
Frank Andersen
</div></div><div class="thread-post"><h3 class="thread-post-title">When will the configKERNEL_INTERRUPT_PRIORITY</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on September 27, 2007</div><div class="thread-post-content">If you define the disable interrupt/enter critical section macro to only disable interrupts below a certain priority, and your USB interrupt is above this priority, then the USB will not get delayed by the kernel activity.&nbsp; This is how the ports that use the configKERNEL&#95;INTERRUPT&#95;PRIORITY feature work.&nbsp; For example, on the Cortex-M3 demo I have a 20KHz interrupt running at a higher priority than the 1KHz RTOS tick &#8211; and measure the jitter in the timing.&nbsp; The jitter is no greater than can be calculated from the datasheet as the maximum due to the processor itself &#8211; a matter of a few instruction cycles.
Regards.
</div></div><div class="thread-post"><h3 class="thread-post-title">When will the configKERNEL_INTERRUPT_PRIORITY</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/frankandersen">frankandersen</a> on October 1, 2007</div><div class="thread-post-content">Hi Richard,
Well mabye the Cortex-M3 is different from the ARM7 interrupt controller. 
If the ARM7 is going to execute a interrupt of a higher priority, while executing another interupt, the mode has to change to system and interrupts to be enabled again. &#40;Nested Interrupts&#41;
But I think it might would help to let the USB bulk run outside the FreeRTOS, by changing the interrupt enable / disable functions.
Best regards, Frank Andersen
