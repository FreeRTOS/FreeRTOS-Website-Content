  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Program hangs with libopencm3 on STM32F103C8T6 (Blue-Pill)</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/victor-lamoine">victor-lamoine</a> on March 20, 2019</div><div class="thread-post-content">Hello,
I&#8217;m trying to learn / use FreeRTOS with libopencm3 on a STM32 thanks to <a href="https://www.amazon.com/Beginning-STM32-Developing-FreeRTOS-libopencm3/dp/1484236238">Warren
Gay&#8217;s book</a> the code examples used in his book are available <a href="https://github.com/ve3wwg/stm32f103c8t6">here</a>
I have already asked this question on <a href="https://stackoverflow.com/questions/55217781/why-is-the-xqueuesendtoback-call-blocking">StackOverflow</a> and on <a href="https://github.com/ve3wwg/stm32f103c8t6/issues/14">ve3wwg/stm32f103c8t6</a> but I did not get an answer that solved my problem.
<h1>Hardware</h1>
<ul>
<li>MCU: STM32F103C8T6 (also known as Blue Pill)</li>
<li>FT232RL breakout board</li>
<li>ST-Link V2</li>
</ul>
<h1>Software</h1>
<ul>
<li>Kubuntu 18.04</li>
<li>arm-none-eabi-gcc (15:6.3.1+svn253039-1build1) 6.3.1 20170620</li>
<li>gdb-multiarch &#8211; GNU gdb (Ubuntu 8.2-0ubuntu1~18.04) 8.2)</li>
<li>FreeRTOS 10.2.0</li>
<li>libopencm3 latest commit 0fd4f74ee301af5de4e9b036f391bf17c5a52f02</li>
</ul>
The following program creates two tasks and a queue. The queue is filled by the task &#8220;SEND&#8221; and the task &#8220;RECEIVE&#8221; receives from the same queue, the Blue Pill LED (GPIOC, GPIO13) is turned on by the &#8220;SEND&#8221; task every 1100 ms and the &#8220;RECEIVE&#8221; tasks turns it off when it receives a message (100 ms after it has been turned on).
~~~
<h1>include &lt;FreeRTOS.h></h1>
<h1>include &lt;libopencm3/stm32/gpio.h></h1>
<h1>include &lt;libopencm3/stm32/rcc.h></h1>
<h1>include &lt;queue.h></h1>
<h1>include &lt;task.h></h1>
static QueueHandle_t queue;
static void
task<em>receive(void *args <strong>attribute</strong>((unused)))
{
  bool nothing;
  while (1)
  {
    if (xQueueReceive(queue, &amp;nothing, 10) == pdPASS)
      gpio</em>set(GPIOC, GPIO13); // Turn off
  }
}
static void
task<em>send(void *args <strong>attribute</strong>((unused)))
{
  bool nothing = false;
  while (1)
  {
    gpio</em>clear(GPIOC, GPIO13); // Turn on
    vTaskDelay(pdMS<em>TO</em>TICKS(100));
    xQueueSendToBack(queue, &amp;nothing, portMAX<em>DELAY);
    vTaskDelay(pdMS</em>TO_TICKS(1000));
  }
}
int
main(void)
{
  rcc<em>clock</em>setup<em>in</em>hse<em>8mhz</em>out_72mhz();
  // Blue-Pill led
  rcc<em>periph</em>clock<em>enable(RCC</em>GPIOC);
  gpio<em>set</em>mode(
    GPIOC,
    GPIO<em>MODE</em>OUTPUT<em>2</em>MHZ,
    GPIO<em>CNF</em>OUTPUT<em>PUSHPULL,
    GPIO13);
  gpio</em>set(GPIOC, GPIO13); // Turn off (polarity of the led is inversed!)
  queue = xQueueCreate(32, sizeof(bool));
  if (queue == 0)
  {
    while (1)
    {
      gpio<em>toggle(GPIOC, GPIO13);
      for (uint32</em>t i = 0; i &lt; 80000; ++i)
        <strong>asm</strong>(&#8220;nop&#8221;);
    };
  }
  xTaskCreate(task<em>receive, &#8220;RECEIVE&#8221;, 200, NULL, configMAX</em>PRIORITIES-1, NULL);
  xTaskCreate(task<em>send, &#8220;SEND&#8221;, 200, NULL, configMAX</em>PRIORITIES-2, NULL);
  vTaskStartScheduler();
  while(1);
  return 0;
}
~~~
This program does not work when I flash it on a Blue Pill, the led stays on and never turns off, I think the execution is blocking at the xQueueSendToBack call (it never exits).
I am using the configuration files from the <a href="https://github.com/ve3wwg/stm32f103c8t6/blob/master/rtos/uart2">rtos/uart2</a> example of the book.
I have tried debugging this with the ST-Link V2, here is the output of my debug session: (note: the program is named uart.elf because I&#8217;m using the rtos/uart2 example files, I replaced the code with the one above)
~~~
gdb-multiarch
layout split
file uart.elf
target extended-remote :4242
load uart.elf
b main
~~~
At that point the everything looks fine from my point of view: <a href="https://pastebin.com/raw/f7XdfiVt">gdb session</a>
Then I set a breakpoint to the xQueueSendToBack call and continue:
~~~
(gdb) b uart.c:30
Breakpoint 2 at 0x8000156: file uart.c, line 30.
(gdb) c
Continuing.
~~~
If I let the code continue and halt it afterwards I get this:
~~~
(gdb) c
Continuing.
Program received signal SIGTRAP, Trace/breakpoint trap.
0x08000e9c in prvIdleTask (pvParameters=<optimized out>) at rtos/tasks.c:3166
(gdb) bt
<h1>0  0x08000e9c in prvIdleTask (pvParameters=<optimized out>) at rtos/tasks.c:3166</h1>
<h1>1  0x08000462 in uxListRemove (pxItemToRemove=<optimized out>) at rtos/list.c:238</h1>
Backtrace stopped: previous frame identical to this frame (corrupt stack?)
~~~
There seems to be something wrong here, however I don&#8217;t know how to interpret this corrupt stack error.
Why is this example not working on my Blue-Pill? There must be something wrong in my setup but I can&#8217;t find what.
If there is any information missing please ask as I&#8217;m willing to provide as much as you need to help me fix this problem. I&#8217;m a little desperate here 🙂
Bye
</div></div><div class="thread-post"><h3 class="thread-post-title">Program hangs with libopencm3 on STM32F103C8T6 (Blue-Pill)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/rtel">rtel</a> on March 20, 2019</div><div class="thread-post-content">It is hard to see the context using the command line debugger, but it is
quite normal to be in the idle task when you stop the debugger,
especially in your application with only two asks that are blocked most
of the time.
The fact that you are in the idle task would seem to indicate that the
scheduler has started.  The fact that GDB doesn&#8217;t know how to decode the
stack can just be because there is no real end to the stack as far as
GDB knows because the task stacks from from the heap (unless you are
using xTaskCreateStatic() to create the tasks).  Using configuration
options it is possible to try an alleviate the debuggers interpretation
of the stack by ending it with a NULL value.
First thing then, are you sure the LED is working as you expect?  If you
were to ignore FreeRTOS for a moment and just try turning the LED on and
off from main() before the scheduler is started, does it turn on and off
as expected?
Next thing to do would be to check the tick interrupt is executing.
When you are stopped on the debugger try viewing the xTickCount
variable.  If it is not incrementing then time is standing still as far
as the scheduler is concerned so the blocked tasks will never time out.

</div></div><div class="thread-post"><h3 class="thread-post-title">Program hangs with libopencm3 on STM32F103C8T6 (Blue-Pill)</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/victor-lamoine">victor-lamoine</a> on March 21, 2019</div><div class="thread-post-content">I solved the issue by updating the compiler to the latest version found on https://developer.arm.com/open-source/gnu-toolchain/gnu-rm/downloads: <code>Version 8-2018-q4-major Linux 64-bit</code>
After this update and recompiling the example code everything executes as expected!
So I recommend not to use the <code>arm-none-eabi compiler</code> shipped with Kubuntu 18.04:
<code>arm-none-eabi-gcc (15:6.3.1+svn253039-1build1) 6.3.1 20170620</code>. It seems to contain a bug in <code>memcpy</code> for cortex M3 targets.
Thanks for you support.
