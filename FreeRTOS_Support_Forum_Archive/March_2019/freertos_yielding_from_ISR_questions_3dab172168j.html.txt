</div></div><div class="thread-post"><h3 class="thread-post-title">yielding from ISR questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on March 8, 2019</div><div class="thread-post-content">How portYIELD<em>FORM</em>ISR works is dependant on the port. On a lot (maybe all) of the ports that allow nesting of interrupt, the Yield is done by using an interrupt, which the portYIELD<em>FROM</em>ISR will trigger, but that trigger won&#8217;t happen until the ISR ends, so it doesn&#8217;t matter where the call actually is, so your example will be safe.
Other ports, some which don&#8217;t allow for nesting, the portYIELD<em>FROM</em>ISR actually calles the scheduler, and right at the point of the call you switch to the new task, and the rest of the ISR (like the final return from interrupt) doesn&#8217;t occur until the task that was running is switched back to. One example of this sort of machine (at least was when I last looked at them) was the Pic24 family. For those processors, the portYIELD<em>FROM</em>ISR needs to be the very last effective line of the ISR, so your example wouldn&#8217;t work.
My preference, unless I KNOW that the code will only be used on machines that it would work is to call the portYIELD<em>FROM</em>ISR only at the end of the ISR, which means that any helper functions that make FreeRTOS calls need to take a pointer to the waswoken flag, which has a side affect of making it clear which funtions are part of the isr and which can&#8217;t be.
</div></div><div class="thread-post"><h3 class="thread-post-title">yielding from ISR questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/eyalasko1">eyalasko1</a> on March 8, 2019</div><div class="thread-post-content">Thanks.
The port is for Arm cortex M4F (Nordic nRF52) which has nested interrupt model.
What about calling _fromISR() api few times inside an ISR &#8211; Should the SAME  wasWoken pointer be transferred as an argument , including &#8216;chaining&#8217; this pointer to helper functions ?
Thanks again for your prompt reply.
</div></div><div class="thread-post"><h3 class="thread-post-title">yielding from ISR questions</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richarddamon">richarddamon</a> on March 8, 2019</div><div class="thread-post-content">Arm Corex M processors all use the pending interrupt method, so multiple calls are safe. In a technical sense it doesn&#8217;t matter if each call uses its own flag or they share. The system is designed to allow an ISR to use a single flag, with a call at the end, that that is probably incrementally more efficient (there will be just a single test of the flag and set the pend interrtupt in the function as opposed to multiple).
I personally still put the portYIELD<em>FROM</em>ISR at the end of the isr and use a single flag in the isr.
It does say that a helper function could be passed a pointer to the flag, or do it inside itself and have things work. My personal preferance is to pass the pointer, but having an extra portYIELD<em>FROM</em>ISR does work.
