  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">DHCP non-aligned buffer causes assert in FreeRTOS_ReleaseUDPPayloadBuffer()</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alager12345">alager12345</a> on March 7, 2019</div><div class="thread-post-content">I fired up DHCP and found that when the offer comes in to <code>prvProcessDHCPReplies()</code>,
down at the bottom it calls <code>FreeRTOS_ReleaseUDPPayloadBuffer()</code>
which in turn calls <code>pxUDPPayloadBuffer_to_NetworkBuffer()</code>.   In this function it checks to see if the pointer to the buffer is aligned.  This check is failing because the <code>pucBuffer is 0x2000524e</code>.
I&#8217;m using BufferAllocation_1.c and I added <code>__attribute__ ((aligned (8)));</code> to both the <code>ucBuffers</code> and in <code>NetworkInterface.c</code> and to <code>xNetworkBuffers</code> in <code>BufferAllocation_1.c</code>, but to no avail.
When I look at the contents of ram where pucBuffer is pointing, it looks correct for the DHCP packet just received, so I don&#8217;t think it&#8217;s memory corruption.
I&#8217;m running on the LPC1788 and have 16.7k ram free at compile time.
I don&#8217;t have these issues with the ARP module or with ping replies, those have been working great.
What could be causing the buffers to be missaligned?
Thanks for any ideas!
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP non-aligned buffer causes assert in FreeRTOS_ReleaseUDPPayloadBuffer()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/heinbali01">heinbali01</a> on March 8, 2019</div><div class="thread-post-content">If the alignment test fails, and you are using BufferAllocation_1.c, I would suggest to recheck your implementation of <code>vNetworkInterfaceAllocateRAMToBuffers()</code>.
You could try to remove the alignment test, but I&#8217;m afraid that the next instruction will crash.
And if your CPU/compiler allows for 32-bits access on a 16-bit aligned location, that would be less efficient. Network Buffers are accessed with 32-bit instructions wherever possible.
Here is an implementation ( from the Xilinx driver ), that is know to work well:
~~~
void vNetworkInterfaceAllocateRAMToBuffers( NetworkBufferDescriptor<em>t pxNetworkBuffers[ ipconfigNUM</em>NETWORK<em>BUFFER</em>DESCRIPTORS ] )
{
<h1>define niBUFFER<em>1</em>PACKET_SIZE      1536</h1>
static uint8<em>t ucNetworkPackets[ ipconfigNUM</em>NETWORK<em>BUFFER</em>DESCRIPTORS * niBUFFER<em>1</em>PACKET<em>SIZE ] <strong>attribute</strong> ( ( aligned( 32 ) ) );
uint8</em>t *ucRAMBuffer = ucNetworkPackets;
uint32_t ul;
<pre><code>for( ul = 0; ul &lt; ipconfigNUM_NETWORK_BUFFER_DESCRIPTORS; ul++ )
{
    pxNetworkBuffers[ ul ].pucEthernetBuffer = ucRAMBuffer + ipBUFFER_PADDING;
    *( ( unsigned * ) ucRAMBuffer ) = ( unsigned ) ( &amp;( pxNetworkBuffers[ ul ] ) );
    ucRAMBuffer += niBUFFER_1_PACKET_SIZE;
}
</code></pre>
}
~~~
It uses a 32-byte alignment, which has to do with the caching system.
Note that <code>ipBUFFER_PADDING</code> has a value of 10.
All EMACs that I&#8217;ve seen until now, know about the 2-byte offset: the first byte after the 12-byte Ethernet Header is 32-bits aligned.
Some EMACs work with a pointer to the Ethernet Header, others want a pointer to 2 bytes before that header, and treat those 2 bytes as dummy.
Things would have been easier if the Ethernet Header contained 16 bytes, in stead of 14.
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP non-aligned buffer causes assert in FreeRTOS_ReleaseUDPPayloadBuffer()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alager12345">alager12345</a> on March 8, 2019</div><div class="thread-post-content">Hmmm, something isn&#8217;t right.  I replaced my <code>vNetworkInterfaceAllocateRAMToBuffers()</code> with the one you just posted, with the minor change of <code>#define niBUFFER_1_PACKET_SIZE      1068</code> due to limited ram.  This value still fits the <code>(buff-28)/8=integer</code> rule.
But when I run this, it still asserts due to the alignment.  The <code>pucBuffer is 0x2000404e</code>
How can this be, if the attribute is for 32bit alignment?
More information on this.  This is the second run through the routine.  The first time through <code>pucBuffer is 0x10006100</code>, so the test passes.  The second time through is when <code>pucBuffer is 0x2000404e</code>. 
So the code that is picking the second buffer isn&#8217;t picking on the correct alignment maybe? 
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP non-aligned buffer causes assert in FreeRTOS_ReleaseUDPPayloadBuffer()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alager12345">alager12345</a> on March 8, 2019</div><div class="thread-post-content">Clue number two on those addresses.  The first one 0x10006100 ( which works) is in bss while the second one 0x2000404e (which fails) is located in the peripheral ram which is access by the ethernet module directly during RX.
</div></div><div class="thread-post"><h3 class="thread-post-title">DHCP non-aligned buffer causes assert in FreeRTOS_ReleaseUDPPayloadBuffer()</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/alager12345">alager12345</a> on March 8, 2019</div><div class="thread-post-content">Looking at this more, is this a fundamental error in how the buffers are used?
<code>FreeRTOS_ReleaseUDPPayloadBuffer( ( void * ) pucUDPPayload );</code> contains a pointer to a UDP Payload.  On this hardware that is in the peripheral ram <code>0x2000404e</code>.  One can not simply subtract 10 from that address to get to the descriptor address back in 0x1000nnnn!
