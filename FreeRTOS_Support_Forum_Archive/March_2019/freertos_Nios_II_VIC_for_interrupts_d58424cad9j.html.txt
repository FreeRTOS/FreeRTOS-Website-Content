</div></div><div class="thread-post"><h3 class="thread-post-title">Nios II VIC for interrupts</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/ripperle">ripperle</a> on June 14, 2019</div><div class="thread-post-content">Hi,
i started to write a port for the NIOS2 with VIC (vectored interrupt controller) and the basic features (preemptive context switching with nested interrupt model, https://www.freertos.org/a00110.html#kernel_priority) already seems to work.
<strong>Here the Hardware description for the Intel (aka Altera) Qsys System:</strong>
&#8211; NIOS 2 Processor (NIOS II/f <strong>with shadow registers</strong>) @100MHz
&#8211; VIC 
&#8211; Interval Timer (@ 1ms) for the RTOS tick
&#8211; some other Timers and custum components with <strong>high priority interrupt</strong>  and minimal latency requirements
&#8211; and of course some RAM (onchip RAM, ca. 40k)
<strong>Settings in the BSP Project / Editor:</strong>
&#8211; <em>hal.linker.enable_exception_stack</em> set to false (no performance improvement with VIC)
&#8211; <em>hal.linker.enable_interrupt_stack</em> set to false (no performance improvement with VIC)
&#8211; Timer for RTOS Tick (IRQ0) set to priority 1 (RIL = 1, lowest priority)
&#8211; IRQ1 to IRQ7 set to higher prioritys, from RIL=9 to RIL=15 which is the high priority interrupt 
&#8211; The IRQ0 (RTOS Tick Timer) runs in the register set 0 (RSS=0) which is &#8220;normal&#8221; register set. This is set, because the context switch has to be customized for FreeRTOS anyway, and there will be no performance improvements with shadow registers
&#8211; IRQ1 to IRQ7 are configured to use there own shadow register set (IRQ1=RRS2, IRQ2=RRS3, &#8230;, IRQ7=RRS8)
&#8211; <em>altera_vic_driver.enable_preemption</em> set to true
&#8211; <em>altera_vic_driver.enable_preemption_into_new_register_set</em> set to true
<strong>Changes to the existing port for the NIOSII with IIC (internal interrupt controller):</strong>
&#8211; with an VIC there are seprerated interrupt entry addresses for each interrupt. These addresses are stored in a vector table.
  The altera VIC driver of the BSP will create these table in the file <em>altera_uC_VIC_vector_tbl.S</em> when generating the BSP. It places the corresponding interrupt funnels at these addresses. The funnel normally will save and restore CPU context and call the ISR, definied by the &#8220;alt<em>ic</em>isr_register()&#8221; function. With shadow registers for each ISR its unnessaccry to save and restore context. So the funnel will be very slim.
  Instead of using the altera isr funnel for the first interrupt (ISR0 aka RTOS Tick) I jump to the context switch implementation of the RTOS port:
~~~
  /* Include funnel macros header file */
<h1>include &#8220;altera<em>vic</em>funnel.h&#8221;</h1>
<pre><code>.section .text, "xa"
.align 2
.globl UC_VIC_VECTOR_TABLE
</code></pre>
UC<em>VIC</em>VECTOR<em>TABLE:
     #ALT</em>NORMAL<em>NON</em>PREEMPTIVE<em>INTERRUPT    16
     jmpi isr</em>handler
     .word 0x0
     .word 0x0
     .word 0x0
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
     ALT<em>SHADOW</em>NON<em>PREEMPTIVE</em>INTERRUPT    16
~~~
&#8211; the context switch (written in assembler) is different in contrast to the existing port for the NIIS2 IIC for these reasons:
1. Separate entry point for non interrupt exceptions. This is important because the port<em>YIELD macro of FreeRTOS will execute the &#8220;trap&#8221; instruction. Other exceptions has to be handled in an other way&#8230;
2. because of the nested interrupt model (configKERNEL</em>INTERRUPT<em>PRIORITY and configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY are defined) the interrupt enable state of the current task has to be saved and restored inside the context switch. Also the global interrupt enable bit (PIE of the CPU status register) has to be set at the beginning of the context switch to allow interrupts with priorities above configMAX<em>SYSCALL</em>INTERRUPT_PRIORITY to execute (with there own shadow registers).
<ul>
<li>new implementation of the portDISABLE<em>INTERRUPTS and portENABLE</em>INTERRUPTS macro (used by the vTaskEnterCritical and vTaskExitCritical functions). These two macros should only disable and enable interrupts at or below configMAX<em>SYSCALL</em>INTERRUPT<em>PRIORITY. Because a context switch can occur inside a critical section, the enable state of the interrupts has to be saved inside the task context, to restore it when portENABLE</em>INTERRUPTS is called. http://www.openrtos.net/FreeRTOS<em>Support</em>Forum<em>Archive/August</em>2007/freertos<em>Question</em>about<em>taskYIELD</em>1791353.html</li>
</ul>
<blockquote>
  RE: Question about taskYIELD()
  Posted by Richard on August 3, 2007
  It is the intended behaviour that the context switch occurs within the critical section &#8211; this allows the use of the scheduler locking mechanism.  Each task should maintain its own interrupt status.  Therefore a task that has interrupts disabled can call taskYIELD(), and switch to a task that may have interrupts enabled.  When the original task next runs it starts with the interrupts in the state in which it expects to find them &#8211; disabled.  Therefore this mechanism does not mean that interrupts remain disabled until the task executes again.
</blockquote>
<strong>Remaining issues, limitations and questions:</strong>
1. Only one VIC is implemented (no daisy chain of multiple VIC). 
2. I use the vTaskSetThreadLocalStoragePointer mechanism to store the interrupt state in the portDISABLE<em>INTERRUPTS macro. I dont like this method because the state can be corrupted if someone call the API with index 0 from user space. Is there a better way or place to store this information?
3. In the VIC the priority of each interrupt (e.g. IRQ0 to IRQ7) can be configured individually. So for example IRQ3 could have a higher priority than IRQ4. I save a &#8220;irq</em>disable<em>mask&#8221; variable initialized in the xPortStartScheduler functions (set corresponding bit of the variable if RIL &lt;= configMAX</em>SYSCALL<em>INTERRUPT</em>PRIORITY). At context switch I can disable necessary interrupts instantly with this mask and the INT<em>ENABLE</em>CLR register of the VIC. <strong>Therefore its not allowed to change the priority of any interrupt after starting the scheduler</strong>.
4. <strong>The <em>altera_uC_VIC_vector_tbl.S</em> is modified by hand and will be overwritten when the BSP is generated.</strong> I don&#8217;t find another way to use the custom ISR written in assembler beside the Altera VIC driver library. This topic is described in the &#8220;Embedded Peripherals IP User Guide&#8221; from Intel (Altera), chapter 37.7.4 &#8220;Positioning the ISR in Vector Table&#8221;:
<blockquote>
  &#8230;
  Positioning an ISR in a vector table is an advanced and error-prone technique, notdirectly supported by the HAL. You must exercise great caution to ensure that the ISRcode fits in the vector table entry. 
  &#8230;
  The VIC Table-Resident example requires modifying a BSP-generated file,altera<em>vic1</em>vector<em>tbl.S. If you regenerate the BSP after making these modifications, the Nios II Software Build Tools regenerate altera</em>vic1<em>vector</em>tbl.S,and your changes are overwritten.
  &#8230;
</blockquote>
As a workaround i just created a copy of the altera<em>uC</em>VIC<em>vector</em>tbl.S with the modified content and copy them as a &#8220;BUILD<em>PRE</em>PROCESS&#8221; target in the correct folder.
I am grateful for any comments or improvements from you&#8230;
Regards,
Andy
