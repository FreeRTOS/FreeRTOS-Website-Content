Getting more lost: you talk about a &#8220;power up&#8221; of the PC. The server socket has already been bound on your FreeRTOS device, or not? So why can it not bind to its server port?
<blockquote>

Is the PC complaining here, or is it FreeRTOS+TCP complaining?
The &#8216;address in use&#8217; response normally has a good and traceable reason 🙂
<blockquote>
  Power cycle makes the port/socket to be closed first and then create and bind.
  No matter how many times I try to bind, it gives same error until I power cycle the device.
</blockquote>
Again not clear: &#8220;Power cycle&#8221; what device?
And what do you mean with &#8220;Power cycle&#8221;, a cold or warm reboot? Or less than that, maybe just some reset?
<blockquote>
  I have a multi threaded system, with separate thread doing these
  Ethernet activities apart from EMAC and IP task.
</blockquote>
Where do you have a &#8220;multi threaded system&#8221;? On your PC, or within FreeRTOS?
In a PC (Linux/Windows/etc) it can very well happen that you close a socket, and that in fact it continues to exist. That happens when the socket still has a connection with the outside world. When the peer is not responding, this state may last <strong>a long time</strong>.
So, on a PC, it may happen that you can not bind a socket to a port because an earlier socket is still bound to that port ( invisibly ).
FreeRTOS+TCP is more transparent: once you have called <code>FreeRTOS_closesocket()</code> for a socket, all resources will be freed, and the port number will become available immediately.

Can you confirm that this logging statement is triggered in <code>FreeRTOS_Socket.c</code>, around line 1020:
~~~
    FreeRTOS<em>debug</em>printf( ( &#8220;vSocketBind: %sP port %d in usen&#8221;,
        pxSocket->ucProtocol == ( uint8<em>t ) FREERTOS</em>IPPROTO<em>TCP ? &#8220;TC&#8221; : &#8220;UD&#8221;,
        FreeRTOS</em>ntohs( pxAddress->sin<em>port ) ) );
    xReturn = -pdFREERTOS</em>ERRNO_EADDRINUSE;
~~~
In your case, it would print &#8216;vSocketBind: TCP port 502 in use&#8217;
When the application gets here, I&#8217;d say there must have been an earlier call to <code>FreeRTOS_bind()</code>, binding a TCP socket to port 502. And if not, it looks like <code>xBoundTCPSocketsList</code> is corrupted.
Can you make some logging about all calls to <code>FreeRTOS_bind()</code>?
This is another location where <code>EADDRNOTAVAIL</code> is returned:
~~~
    xReturn = -pdFREERTOS<em>ERRNO</em>EADDRNOTAVAIL;
    FreeRTOS<em>debug</em>printf( ( &#8220;vSocketBind: Socket no addrn&#8221; ) );
~~~
Sure it doesn&#8217;t get there?
Note also that you can define <code>socketAUTO_PORT_ALLOCATION_START_NUMBER</code> in your <code>FreeRTOSIPConfig.h</code>, it defaults to 1024
~~~
    #define socketAUTO<em>PORT</em>ALLOCATION<em>START</em>NUMBER ( ( uint16_t ) 0x0400 )
~~~
I would recommend choosing your server port numbers under this value, under 1024. Port 502 would be OK.
Another thing is about <code>vApplicationIPNetworkEventHook()</code>: the application hook is called when there is a change in the network status:
~~~
void vApplicationIPNetworkEventHook( eIPCallbackEvent_t eNetworkEvent )
{
    /* If the network has just come up&#8230;*/
    if( eNetworkEvent == eNetworkUp )
    {
        /* Create the tasks that use the IP stack if they have not already been
        created. */
        if( xTasksAlreadyCreated == pdFALSE )
        {
            /* Create tasks, and/or set a trigger to create sockets. */
            xCreateSockets = pdTRUE;
            xTasksAlreadyCreated = pdTRUE;
        }
    }
}
~~~
As socket and tasks must be created only once, it is important to use a variable like <code>xTasksAlreadyCreated</code>, which will be set to true.
It is important <strong>not to call</strong> FreeRTOS+TCP API&#8217;s from within the application hook, because the code is running from within the IP-task. The IP-task may not call many of it&#8217;s own API&#8217;s.

  Considering multiple calls to bind, yes if the bind is not successful then will try to bind it again.

In the many years that I use FreeRTOS+TCP my self, I have never see any problem with binding a socket to a port number.
It&#8217;s not useful to try binding to the same port number a second time. Something must be wrong in your code.
If you know how to iterate through a List_t, you can list all entries in <code>xBoundTCPSocketsList</code> when you get the error. I would be curious to see that.
Well, here is some code that will go through the list of bound TCP sockets, although not tested yet:
~~~
    const ListItem<em>t *pxIterator;
    const MiniListItem</em>t <em>pxEnd = ( const MiniListItem_t</em> )listGET<em>END</em>MARKER( &amp;xBoundTCPSocketsList );
    for( pxIterator  = ( const ListItem<em>t * ) listGET</em>NEXT( pxEnd );
         pxIterator != ( const ListItem<em>t * ) pxEnd;
         pxIterator  = ( const ListItem</em>t * ) listGET<em>NEXT( pxIterator ) )
    {
        pxSocket = ( FreeRTOS</em>Socket<em>t * ) listGET</em>LIST<em>ITEM</em>OWNER( pxIterator );
        /* usLocalPort is in host endian notation. */
        FreeRTOS_printf( ( &#8220;Socket bound to %un&#8221;, pxSocket->usLocalPort);
    }
~~~
What does this show at the moment you can not bind a socket?
<blockquote>
  And with vApplicationIPNetworkEventHook(), it is called initially for network
  up and nothing from my end is done inside that function.
</blockquote>

<blockquote>
