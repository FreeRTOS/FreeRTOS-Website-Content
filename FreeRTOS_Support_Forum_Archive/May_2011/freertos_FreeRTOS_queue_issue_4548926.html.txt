</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS queue issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 30, 2011</div><div class="thread-post-content">The basic problem is that the queue code needs to access some common data, and needs some form of exclusion method to protect this access. The FromISR routines use a routine provided by the portable layer to provide this, and that layer uses the assumptions of the port. For a port that doesn&#8217;t support nested interrupts, it assumes that no further interrupts are possible inside of the ISR, so no further protection is needed. You would need to update that layer to include the interrupt disable/enable code that you are using. Otherwise, at some point you will get an interrupt during one of these critical sections of code, and get a corruption of FreeRTOS data, which can cause tasks to get locked out.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS queue issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 31, 2011</div><div class="thread-post-content"><blockquote>
  So you are saying that the FromISR functions must be modified.
</blockquote>
No &#8211; the FromISR functions are all capable of working with ports that support nested interrupts already, but they rely on some port layer functions that are not implemented for some ports.&nbsp; For example, they call portSET&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#40;&#41; &#40;which disables interrupts up to a certain level, then returns the old interrupt priority mask&#41; and portCLEAR&#95;INTERRUPT&#95;MASK&#95;FROM&#95;ISR&#40;&#41; &#40;which sets the interrupt mask to that returned by the first macro&#41;.  
All prots could be made to support nested interrupts.&nbsp; How complex this is depends on the architecture.&nbsp; The question is whether the architecture speed and RAM provision warrant doing it.  
I suspect the MSP430 could easily support a compromise where the tick interrupt uses the lowest interrupt priority, and any task that wants to use FreeRTOS &#8220;FromISR&#8221; API functions also use the lowest interrupt priority, then any interrupts that are above that interrupt priority just can&#8217;t use FreeRTOS API functions.&nbsp; This is how the PIC24 port works.&nbsp; Other ports have a much more comprehensive multi-priority scheme.

</div></div><div class="thread-post"><h3 class="thread-post-title">FreeRTOS queue issue</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 31, 2011</div><div class="thread-post-content">If you want to get your program to work without changing FreeRTOS, one big question that comes up is &#8220;Why do you need to use nested interrupts?&#8221;  
An interrupt when using an RTOS should generally be very short, not much longer than the time it takes to pull any appropriate date out of the hardware and into a communication structure, like a queue. Any processing that needs to be done, which might take time, should be done at &#8220;task&#8221; level &#40;maybe a high priority task&#41;.
