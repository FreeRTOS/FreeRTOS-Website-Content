If you are sure that the compiler is not outputting any floating point instructions, and you are sure you have not accidentally turned the floating point unit on, then it is very likely your problem is not connected to the device being an M4F, as the M3 code does not itself use any floating point instructions and should &#40;does&#41; run on M4F silicon &#40;without the FPU being used&#41;.

</div></div><div class="thread-post"><h3 class="thread-post-title">CORTEX M4 vs CORTEX M3</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/petersmith27">petersmith27</a> on November 14, 2011</div><div class="thread-post-content">I have just started to look at ARM CM4+MPU+FPU and was wondering when a port of FreeRTOS might be available?

</div></div><div class="thread-post"><h3 class="thread-post-title">CORTEX M4 vs CORTEX M3</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on November 14, 2011</div><div class="thread-post-content">The Cortex-M4F can be configured to use the FPU in several ways.  
0&#41; Turn the FPU off.&nbsp; Then you can use the M3 port.  
1&#41; Turn the FPU on, but set the hardware not to save its context.  
This is fine if only one task uses the FPU, and no interrupts use the FPU.&nbsp; It is also fine if you want to save the FPU context manually for just those tasks that have registered as FPU users.&nbsp; It breaks when interrupts start using the FPU too, and is inefficient whatever as most of the time the FPU context is being saved and restored unnecessarily.  
1&#41; Set the processor to save the entire FPU context on every interrupt.  
This is a really easy way of using it.&nbsp; You would require some changes to the port layer to setup the initial stack to have an FPU context, but that is not difficult.&nbsp; However, it is <strong>&#42;massively&#42;</strong> inefficient and <strong>&#42;horrendous&#42;</strong> in run time and RAM usage, especially when you consider that very few tasks will actually use the FPU, and when interrupts start nesting and each has its own FPU context.  
2&#41; Set the processor to use the lazy save mechanism so space is allocated to the stack for the FPU context, but a context save is only triggered if an FPU instruction is actually executed.  
This is a clever and brilliant mechanism for efficient FPU usage, with interrupts, in a <strong>&#42;single threaded&#42;</strong> environment.&nbsp; Think through the consequences in a mult-threaded environment, with nested interrupts that also use FPU instructions, and you will soon see this is <strong>&#42;massively&#42;</strong> complex, with lots of corner cases, and near impossible to test, and almost unworkable with any sort of reasonable code base, size, run time limits, etc..  
Then take into account that you need to inspect the output of your compiler extremely carefully, as some versions will output FPU instructions in the prologue and epilogue of function calls, even when the task makes no use of the FPU at all.  
There is a plan to support M4F however, it is just a matter of finding the time.  
Regards.
