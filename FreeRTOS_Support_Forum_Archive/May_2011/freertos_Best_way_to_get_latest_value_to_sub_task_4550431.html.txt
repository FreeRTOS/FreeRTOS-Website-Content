  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Best way to get latest value to sub task?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmauler">cmauler</a> on May 29, 2011</div><div class="thread-post-content">Task 1: higher priority, frequent and performing a calculation to get X<br />
Task 2: lower priority, infrequent and needs to work on the latest value of X &#40;low latency&#41;  
I hoped a queue size of one, possibly &#8220;sending to front&#8221; on each task1 iteration and ignoring the overflow would then have the value ready for when task2 needed it.<br />
BUT from tests running a constantly overflowing one place queue doesn&#8217;t yield the same value as a&nbsp; long&#42; queue and draining it to the last&#33; &#40;&#42;jigged to 100 for the test but not practical for target situation&#41;<br />
I cannot find a explicit statement of what would happen in the overflow situation, as all the text/examples avoid this.<br />
Thanks for your consideration and I was wondering is there an elegant solution?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to get latest value to sub task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 29, 2011</div><div class="thread-post-content">Queue when full will just not write the new value, so your method will give Task 2 the value of X that was first computed after it grabbed a value of X.  
What you want is basically a mailbox. Declare a global variable for X, and a mutex to guard it.<br />
When Task 1 has a new value of X, it acquires the mutex, quickly stuffs the value in, then releases the mutex. When Task 2 wants a new value, it acquires the mutex, quickly copies it somewhere private to use, and releases the mutex.  
Because it it protected by the mutex, Task 2 can&#8217;t get a corrupted value by having X updated in the middle of being read,&nbsp; and due to the priority methods of th mutex, if task 2 has the mutex for coping out the value, and task 1 interrupts it and computes a new value, task 2 will get a temporary priority boost when task 1 is blocked from writing the new value of X, which is why task 2 needs to be quick at copying the value.
</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to get latest value to sub task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/cmauler">cmauler</a> on May 29, 2011</div><div class="thread-post-content">Thanks for your response

</div></div><div class="thread-post"><h3 class="thread-post-title">Best way to get latest value to sub task?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richardbarry">richardbarry</a> on May 30, 2011</div><div class="thread-post-content">Queues are just that, queues.&nbsp; Things are taken out in the order in which they are put in &#40;unless you post to the front&#41;.  
richard&#95;damon&#8217;s solution is not inelegant, and you could encapsulate the behaviour very easily in an &#8216;object&#8217;.  
I would add to richard&#95;dmaon&#8217;s solution that, if the size of the variable is equal to the natural size of the microcontroller &#40;i.e. a 32 bit variable on a 32 bit architecture, or a 16 bit variable on a 16 bit architecture,, etc.&#41; and task A only ever writes to the variable and task B only ever reads from the variable, then you don&#8217;t need to mutex even.
