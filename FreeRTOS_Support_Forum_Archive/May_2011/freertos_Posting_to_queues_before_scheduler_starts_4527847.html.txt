  <main class="main-content"><div class="thread-post"><h2 class="thread-post-title">Posting to queues before scheduler starts?</h2><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mr68360">mr68360</a> on May 12, 2011</div><div class="thread-post-content">I have been instantiating and populating queues, using <em>xQueueSend&#40;&#41;</em>, in a setup routine called from <em>main&#40;&#41;</em>, **before **calling <em>vTaskStartScheduler&#40;&#41;</em>.&nbsp; This seems to work, but the FreeRTOS manual indicates only task, queue, and semaphore **creation ** calls should be done before starting the scheduler.  
Is there a definitive &#8220;yes&#8221; or &#8220;no&#8221; to the question of calling <em>xQueueSend&#40;&#41;</em> before the scheduler starts?  
Thanks, any and all.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/edwards3">edwards3</a> on May 12, 2011</div><div class="thread-post-content">It is probably ok as long as the block time is always 0. 
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 14, 2011</div><div class="thread-post-content">When I have had to do this, I used the FromISR api functions, as these by definition will not try to block, and need less of the system set up. They also are less apt to mess up the interrupt structure.&nbsp; Note that the normal API functions use critical sections that require some information to be set up ahead of time, and may enable the interrupts on exit, before the system is really set up to handle them.
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mr68360">mr68360</a> on May 14, 2011</div><div class="thread-post-content">Thanks, Richard.&nbsp; Interesting info on the &#8216;ISR&#8217; functions.  
If we wish to start the program with a know number of available resources available &#40;that are dispensed from a queue&#41;, then there seems to be no other way to do so, except with doing a pre-scheduler-start post.  
I&#8217;m wondering if it would be better to create a &#8220;master&#8221; init thread that &#40;1&#41; has init code that initializes queues, mutexes, etc, then &#40;2&#41; spawns the rest of the worker tasks in the system in order.&nbsp; The init code would then be guaranteed to be called from within a running thread.&nbsp; &#40;That task would either suspend, or it could remain active as a &#8220;monitor task&#8221; or something-so as not to &#8220;waste&#8221; the task&#8217;s resources-we don&#8217;t use dynamic memory, so we have no task deletions.&#41;  
All the FreeRTOS examples I&#8217;ve seen show the creation of all tasks in <em>main&#40;&#41;</em>, then a final <em>vTaskStartScheduler&#40;&#41;</em> call.&nbsp; I have not attempted making <em>xTaskCreate&#40;&#41;</em> calls from within a running task, but, if that is ok to do, it just might fix some of the problems inherent with calling APIs before the scheduler has started.  
Might anyone know the legality of tasks spawning tasks?  
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/richard_damon">richard_damon</a> on May 14, 2011</div><div class="thread-post-content">Task spawning task is perfectly legal. Having an &#8220;init&#8217; thread, that then becomes something else can be a workable strategy. My first thought is you may want it to be a &#8220;high&#8221; priority task, so that as you create/start tasks you don&#8217;t interrupt the init task and delay the rest of the creation. You could start it high, and it can then change its priority low when done with the init.
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mr68360">mr68360</a> on May 14, 2011</div><div class="thread-post-content">An EXCELLENT idea regarding the change of priority.&nbsp; Thank you very much.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/destremps">destremps</a> on May 15, 2011</div><div class="thread-post-content">There&#8217;s more to say that may help. The &#8216;highest priority at the time&#8217; init task that spawns all other tasks is indeed a nice way to kick it all off. You can even suspend the init task &#8216;until&#8217; a newly created task signals it&#8217;s okay to continue. This way you can initialize hardware in a known predictable order. For example in the init task:  
create a binary semaphore<br />
take it<br />
.<br />
create a new &#8216;lower priority task&#8217; … say a driver task for some piece of hardware<br />
SUSPEND the init task<br />
.<br />
&#40;now what happens?&#41;<br />
.<br />
the newly created task is the only other task that has &#8216;anything&#8217; to do so it runs &#40;remember this is very early on in the<br />
startup&#41;…it runs till it gives the semaphore<br />
.<br />
now the startup task continues<br />
.<br />
&#40;you can repeat this&#41;  
I&#8217;ve managed the startup this way.  
</div></div><div class="thread-post"><h3 class="thread-post-title">Posting to queues before scheduler starts?</h3><div class="thread-post-author">Posted by <a href="http://sourceforge.net/users/mr68360">mr68360</a> on May 16, 2011</div><div class="thread-post-content">Nice, mizer.&nbsp; I assume that your suspend is actually a pend on the semaphore you created &#40;init waits for the dependent task to signal that it-the dependent task-is ready to allow more init to occur&#41;?  
One might wish to provide an upper-bound time limit on that pend, given that the dependent task might not itself finish its own initialization in a timely manner.  
On the other hand, if one doesn&#8217;t care about start-up order, one could create a unique semaphore for each non-init task &#40;let&#8217;s call them &#8216;child tasks&#8217;&#41;.&nbsp; These semaphores begin life in the non-signaled state.&nbsp; When the init task spawns each child, it simply waits on all of the semaphores-waiting for each child to signal that its initial operations are complete.&nbsp; The order of wait would not be critical: regardless of signaling order, the init task would only fall through when it can take all the semaphores it is waiting on.  
&#40;An example of what I mean:&nbsp; child 1 is spawned, then child 2, but child 2 signals before child 1 does.&nbsp; If init waits first for child 1, then fine-it waits.&nbsp; After init takes child 1&#8217;s semaphore, it immediately takes child 2&#8217;s semaphore-because it had previously been signaled.&nbsp; Regardless of the order, <em>eventually</em> everyone&#8217;s semaphore get&#8217;s taken.&#41;  
But, again, some upper time limit for waiting on each child might be in order.  
I like mizer&#8217;s idea because only one semaphore is involved &#40;less resources&#41;, and it lends itself to fine-grained start-up control.&nbsp; However, if the start-up sequence changes, there there must be code rearrangement.&nbsp; If the order is less important than not having to modify code-that is, if one simply wants to provide a more coarse-grained, &#8220;bulk&#8221; approach, perhaps my scheme would serve.  
I love lots of tools for lots of different problems&#33;
